# Coding Problem Study-Note Prompt (v3 — restructured)

Write a **single, compilable Java file** that's a standalone study note for this problem, from brute force to optimal. Teach me *how to discover* the solution, not just the solution itself.

## 1. Clarifying questions
Open with 4-10 questions a candidate should actually ask the interviewer before coding — specific to *this* problem (ambiguous bounds, mutability of input, undefined "valid" states, tie-breaking, output format for no-solution, etc.). One line per question on why it matters: what assumption it prevents, or how the answer changes the approach. Skip generic filler that applies to any problem.

## 2. The reasoning journey (core requirement)
- Open by pinning down what's actually being asked and the binding constraint — the thing that explains why brute force falls over at scale. A sentence or two, not a requirements doc.
- Cover every approach that's genuinely distinct in *idea*, not just brute force and the final optimum — include a distinct intermediate improvement too (hashmap version, two-pointer version, DP version, etc.) if the problem naturally has one. "Genuinely distinct" means a different core idea, not a cosmetic variation — don't manufacture a step just to pad the journey.
  - Exception: two implementations with the same asymptotic complexity but a real practical difference (e.g. recursion depth risking `StackOverflowError` in Java vs. an iterative version) can both appear briefly, with that one-line trade-off named.
- For each approach, walk the same arc:
  1. What I'd naturally try
  2. Why it works
  3. Why it's too slow/costly — concretely, time AND space (e.g. "exponential time because...", "O(N) extra space for the recursion stack because..."), tied back to the constraint
  4. What work is being repeated
  5. What property/observation removes that bottleneck
  6. How that observation leads to the next approach, closing with its cost as two clearly labeled, separately-reasoned lines — "Time Complexity: O(...) — because <what's actually visited/processed/repeated>" and "Space Complexity: O(...) — because <what's actually stored: extra structures, recursion stack, in-place vs. auxiliary>" — never just the Big-O label alone, and why that cost is fast/lean enough
- Give this same separated, reasoned Time/Space breakdown for every approach in the journey, not only the final optimal one — including the brute force, so the contrast in *why* one is expensive and the other isn't is explicit rather than implied.
- Never jump straight to a named technique ("this is the classic two-pointer trick") — make me see *why* someone would think of it.
- Once every approach is laid out, say plainly which one you'd actually write in a 45-minute interview and why — factoring in complexity, code risk, and how easy it is to get right under pressure, not just Big-O.

## 3. Edge cases (required)
An explicit list of the edge cases worth considering for this problem (empty input, single element, all-duplicates, already-sorted, boundary/overflow values, disconnected/unreachable, negative or mirrored coordinates, etc. — whichever genuinely apply here). Always include this as its own section — don't fold it silently into the examples or skip it because the test cases already cover it.

## 4. Also include — wherever it genuinely helps
Use judgment; skip anything that doesn't add value for this specific problem.
- **Key insight** — developed as a question I should learn to ask myself, with a correctness intuition ("this must work because..." not just "this seems to work").
- **Examples** — a couple of sharp ones, including one where a tempting approach fails. If the problem has any spatial or visual structure at all (grid, board, tree, graph, matrix, ranges, pointers moving through an array), include an ASCII diagram for at least the key insight or one example — don't default to skipping it just because prose could technically also work.
- **Dry run** — an explicit iteration-by-iteration trace (numbered list or small table) of the optimal approach on a typical case, showing the real state at each step (queue contents, stack, DP table, pointers) — not just before/after snapshots. Also trace, the same way, whichever teaches more: the failing-approach case or a genuine edge case (don't trace both if one alone makes the point). A narrative example alone never counts as the dry run.
- **Pitfalls** — the tempting wrong approaches for this problem (wrong data structure, off-by-one, incorrect state definition, a missed property, a Java-specific gotcha like autoboxing/`==` on wrapper objects/mutable array as a HashMap key), and why each is tempting.
- **Pattern recognition** — "when you see X, think Y," plus 1-2 other problem types the same idea transfers to.
- **Interview script** — how I'd talk through this out loud, ending with the complexity statement ("that gives us O(...) time and O(...) space") the way a real answer would.

## 5. Follow-ups (required)
A few realistic interviewer follow-up questions for this problem, with answers — always include this section, don't treat it as skippable. Draw from what's actually plausible for this problem: changed constraints (bounded vs. unbounded, weighted vs. unweighted), a different input representation, returning the path/result instead of just its value or count, multiple queries against the same input, dynamic updates, or memory restrictions — pick whichever genuinely fit rather than forcing all of them.

## 6. Java code
- One file, clean idiomatic Java. Modern features (`Deque`, `PriorityQueue`, records, streams, etc.) where they genuinely help — no cleverness for its own sake. Keep normal Java formatting — don't break simple statements across extra lines just to leave room for comments; the comments carry the teaching, not artificial code layout.
- Don't dump all the teaching into the top block comment and leave the method body thin. Distribute comments through the method itself, at each meaningful step, so the code reads as its own walkthrough top to bottom without needing to jump back to the header.
- When you introduce a non-obvious variable or data structure (a `dist`/`parent` array, a visited set, a DP table), the comment at its declaration should ground it with a tiny concrete example — actual values on a small instance of the problem, not just an abstract description of what it holds.
- Every non-trivial block gets a comment explaining *why* it's needed. If the line itself is non-obvious (dense expression, bit trick, unusual API call), briefly say *what* it does too — a reader should follow the logic and the reasoning from the comments alone, without re-deriving it or re-reading the top block.
- In `main()`, cross-check every approach that's actually implemented against representative + edge cases. If an early approach (e.g. brute force) is too slow to be worth running, describe it in the reasoning journey but don't force it into runnable code.

## 7. Close with a short summary
Core pattern, key observation, what's worth memorizing vs. understanding, most common trap, one-line mental trigger.

---
Be creative in how you teach this — vary explanation style, diagrams, and depth to fit what actually makes *this* problem click. Don't force a rigid template.
