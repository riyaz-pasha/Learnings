# Coding Problem Study-Note Prompt (v2 — condensed)

Write a **single, compilable Java file** that's a standalone study note for this problem, from brute force to optimal — teach me *how to discover* the solution, not just the solution itself.

**Start with clarifying questions:** 4-10 questions a candidate should actually ask the interviewer before writing any code for *this specific problem* — things like ambiguous input bounds, edge cases (empty input, single element), whether the input can be mutated, what "valid" move/state means if it's not fully pinned down, output format for ties or no-solution. For each, one line on why it matters (what assumption it prevents, or how the answer would change the approach). Skip generic filler questions that apply to any problem.

**Core requirement — the reasoning journey:**
Start by pinning down what's actually being asked and the binding constraint (usually the thing that explains why brute force falls over at scale) — a sentence or two, not a full requirements section. Then, for each approach, walk through: what I'd naturally try → why it works → why it's too slow (say what that costs concretely — time AND space, e.g. "exponential time because...", "O(N) extra space for the recursion stack because..." — tied to the constraint) → what work is repeated → what property/observation removes that bottleneck → how that leads to the next approach, closing with the new approach's time and space cost broken down by what's actually being visited/stored/repeated (not just the Big-O label) and why that's fast/lean enough. Never jump straight to a named technique ("this is the classic two-pointer trick") — make me see *why* someone would think of it. Cover every approach that's genuinely distinct in idea (not just brute force and the final optimum — include a distinct intermediate improvement too, e.g. a hashmap-based version, a two-pointer version, a DP version, if the problem naturally has one), but don't manufacture a step just to pad the journey — "genuinely distinct" means a different core idea, not a cosmetic variation. Exception: if two implementations share the same asymptotic complexity but differ in a real practical property (e.g. recursion depth risking `StackOverflowError` in Java vs. an iterative version), it's fine to show both briefly with that one-line trade-off named — but only when the trade-off is genuine, not as an excuse to duplicate code. Once all approaches are laid out, say plainly which one you'd actually write in a 45-minute interview and why — factoring in complexity, code risk, and how easy it is to get right under pressure, not just Big-O.

**Also include, wherever it genuinely helps** (use judgment — skip anything that doesn't add value for this specific problem):
- The key insight, developed as a question I should learn to ask myself, with a correctness intuition ("this must work because..." not just "this seems to work")
- A couple of sharp examples (including one where a tempting approach fails), with ASCII diagrams if that's how the idea is best seen
- A dry run of the optimal approach as an explicit iteration-by-iteration trace — a numbered list or small table showing, at each step, what's popped/processed and the resulting state of whatever the algorithm actually manipulates (queue contents, stack, DP table, pointers). A single illustrative example of *why* something fails doesn't satisfy this — that's a separate example, not the dry run. Give the optimal approach's trace on a typical case; also trace (same iteration-by-iteration style) whichever of these teaches the most for this problem: the case where a tempting wrong approach fails, or a genuine edge case — don't trace both if one alone makes the point.
- An explicit list of the edge cases worth considering for this problem (e.g. empty input, single element, all-duplicates, already-sorted, boundary/overflow values, disconnected/unreachable cases — whichever genuinely apply here), not just folded silently into the examples
- The tempting wrong approaches or pitfalls for this problem (wrong data structure, off-by-one, incorrect state definition, a missed property, a Java-specific gotcha like autoboxing/`==` on wrapper objects/mutable array as a HashMap key — whichever actually apply here), and why each is tempting
- The reusable pattern: "when you see X, think Y" — plus 1-2 other problem types it transfers to
- How I'd talk through this out loud in an interview, ending with the complexity statement ("that gives us O(...) time and O(...) space") the way a real answer would
- A couple of realistic interviewer follow-ups (changed constraints, weighted version, streaming/dynamic updates, etc. — only if relevant)

**Java code:** one file, clean idiomatic Java, modern features (`Deque`, `PriorityQueue`, records, streams, etc.) where they genuinely help, no cleverness for its own sake. Every non-trivial block gets a comment explaining why it's needed; if the line itself is non-obvious (a dense expression, bit trick, unusual API call), briefly say what it does too, so the comment doesn't assume the reader already parsed it. A reader should be able to follow the logic from the comments alone, without re-deriving it. In `main()`, cross-check every approach that's actually implemented against representative + edge cases; if an early approach (e.g. brute force) is too slow to be worth running, describe it in the reasoning journey but don't force it into runnable code.

**End with a short summary:** core pattern, key observation, what's worth memorizing vs. understanding, most common trap, one-line mental trigger.

Be creative in how you teach this — vary the explanation style, diagrams, and depth to fit what actually makes *this* problem click. Don't force a rigid template.
