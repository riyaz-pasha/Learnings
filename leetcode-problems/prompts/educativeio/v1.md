The file should be a **standalone interview-preparation study note**. Put the explanations directly inside Java comments so I can study the file without needing any external explanation.

## The main goal

Do NOT just teach me the solution.

Teach me **how to discover the solution**.

I want to develop the ability to take an unfamiliar interview problem and reason my way toward an efficient algorithm.

The most important part of the response is the **reasoning journey**:

```text
Understand the problem
        ↓
What exactly are we computing?
        ↓
What would I try naturally?
        ↓
Why does that work?
        ↓
Why is it too slow?
        ↓
Where is the repeated/unnecessary work?
        ↓
What structure or property can I exploit?
        ↓
What question/observation leads to a better solution?
        ↓
Can I improve it further?
        ↓
Why is the final solution correct?
        ↓
How can I recognize the same idea in other problems?
```

Do not jump from the problem statement directly to a known trick.

For example, avoid:

> "This is the classic two BFS trick."

Instead, make me understand **why someone would think of doing two BFS traversals in the first place**.

## What to include

Use your judgment rather than rigidly following a fixed template. Include whatever is genuinely useful for understanding this particular problem.

Cover the following naturally:

### 1. Understand the problem

Explain:

* What the problem is really asking
* The important constraints
* The mathematical/computational quantity we need
* Important keywords or properties that should trigger algorithmic ideas

Translate the problem into simple language I could use with an interviewer.

### 2. Build the solution progressively

Start with the most obvious solution a candidate might think of.

For each improvement, explain:

* What the idea is
* Why it works
* Why the previous solution is insufficient
* What work is being repeated
* What observation removes that bottleneck
* How that observation leads naturally to the next approach

Make the transition between solutions especially clear:

```text
Previous approach:
    We repeatedly do X.

Observation:
    Because of property Y, X can be avoided.

Therefore:
    We can instead do Z.
```

This progression is more important than the number of approaches.

Only include **meaningfully different** approaches. Don't invent artificial "better" solutions just to have more versions.

### 3. Develop the key insight

Spend extra time on the central observation.

Ask the kinds of questions I should learn to ask myself:

```text
What information do I actually need?
Can I calculate it more directly?
What work am I repeating?
What special property does the input have?
Can one traversal/query/precomputation help another?
Can I turn a global problem into a local one?
Can I eliminate candidates?
Can I exploit ordering, monotonicity, uniqueness, connectivity,
overlapping subproblems, etc.?
```

The explanation should make the final insight feel **discoverable**, not magical.

### 4. Correctness intuition

Explain why the optimal approach is guaranteed to work.

If the key insight is subtle, give a proof or proof intuition.

Clearly distinguish:

> "This seems to work"

from:

> "This must work because..."

### 5. Examples and visual reasoning

Use a few carefully chosen examples.

Prefer examples that expose the idea rather than many repetitive examples.

Use ASCII diagrams, tables, state transitions, recursion trees, DP tables, queues, stacks, heaps, etc. whenever they make the reasoning easier to visualize.

Include at least one example where a tempting approach fails.

### 6. Dry run

Do a detailed mental execution of the important/optimal solution.

Show the important state changes rather than merely saying what each line does.

The goal is that I can mentally execute the algorithm myself.

### 7. Complexity

Explain where the time and space complexity actually come from.

Don't just write `O(N)` or `O(N log N)`.

Explain what is being visited, processed, repeated, sorted, stored, etc.

Relate the complexity back to the constraints.

### 8. Wrong approaches and pitfalls

Include the most likely mistakes for this problem.

Focus on mistakes that teach something:

* Wrong data structure
* Missing an important property
* Incorrect assumption
* Off-by-one
* Incorrect traversal
* Incorrect state definition
* Complexity mistake
* Java-specific issue

Explain **why the mistake is tempting** and how to recognize it next time.

### 9. Pattern recognition

After solving the problem, extract the reusable pattern.

Explain:

```text
When you see X → start thinking about Y.

When the input has property X → ask question Y.

When brute force repeatedly does X → investigate Y.

When constraints reach X → eliminate approaches slower than Y.
```

Give a few examples of other problem types where the same reasoning pattern may apply.

The goal is to help me solve **new problems**, not memorize this one.

### 10. Interview communication

Show how I should reason out loud in an interview.

Include a natural progression such as:

```text
"I understand the problem as..."
"My first straightforward approach would be..."
"The issue with that is..."
"I notice that..."
"Because the input has..."
"So I think we can..."
"Let me verify that with an example..."
"That gives us O(...) time and O(...) space."
```

Make it sound like a strong engineer thinking, not a memorized script.

### 11. Follow-ups

Include a small number of realistic interviewer follow-up questions and explain how the solution changes if important assumptions change.

Examples might include:

* Different constraints
* Different input representation
* Weighted vs unweighted
* Returning the actual result/path instead of only its value
* Multiple queries
* Dynamic updates
* Memory restrictions
* Removing an important assumption

Only include follow-ups that are relevant.

# Java implementation

Keep everything in **one Java file**.

The code must compile and run.

Use clean, idiomatic, interview-friendly Java.

Use modern Java features such as `Deque`, `ArrayDeque`, `PriorityQueue`, `HashMap`, `HashSet`, records, etc. when they genuinely improve the solution.

Avoid unnecessary abstractions and clever code.

Each meaningful solution should be clearly separated and named.

Include a `main()` method with representative examples and edge cases, and verify that applicable approaches produce the same result.

Comments should explain **why**, not merely repeat what the code says.

Bad:

```java
// increment i
i++;
```

Good:

```java
// We move the left boundary only after the current window
// becomes invalid, preserving the invariant that every window
// we consider here satisfies the required constraint.
```

## Quality bar

Before finishing, make sure the explanation answers:

> **What would I try first, why would I try it, why does it fail at scale, what observation breaks the bottleneck, and how could I have discovered that observation myself?**

Be creative with the explanation, diagrams, examples, proofs, and teaching style. **Do not force every section if it doesn't add value. Depth and clarity are more important than following a rigid template.**
