## 1. The Problem, Restated Simply

Given an array, look at **every possible contiguous subarray**, take its **minimum**, and **add up all those minimums**.

```
arr = [3, 1, 2, 4]

Subarray        Min
---------        ---
[3]               3
[3,1]             1
[3,1,2]           1
[3,1,2,4]         1
[1]               1
[1,2]             1
[1,2,4]           1
[2]               2
[2,4]             2
[4]               4
                 ----
           Sum =  17
```

That's the whole ask. The challenge is doing it fast.

---

## 2. Why Brute Force Is Slow

There are `n*(n+1)/2` subarrays. For `n = 4` that's only 10, but for large `n` this is **O(N²)** subarrays, and finding the min of each one (naively) makes it worse. We want **O(N)** — one pass, touching each element a constant number of times.

---

## 3. The Big Mental Shift: Contribution Technique

Instead of asking, for every subarray, *"what's your minimum?"* — flip the question and ask, for every **element**:

> **"For how many subarrays am I THE minimum?"**

```
                    ┌─────────────────────────────────┐
   OLD QUESTION:    │  For each SUBARRAY, what is its  │   → O(N²) subarrays to check
                    │  minimum value?                  │
                    └─────────────────────────────────┘

                    ┌─────────────────────────────────┐
   NEW QUESTION:    │  For each ELEMENT, in how many   │   → O(N) elements to check
                    │  subarrays is it the minimum?    │
                    └─────────────────────────────────┘
```

If element `arr[i]` is the minimum of exactly `K` subarrays, its total contribution to the final answer is `arr[i] * K`. Add up every element's contribution and you have the answer — without ever explicitly listing a subarray.

This is called the **contribution technique**, and it shows up constantly in array problems ("sum of subarray maximums", "sum of subarray ranges", etc.). It's worth internalizing as a pattern on its own.

---

## 4. What We Actually Need: PSE and NSE

For element `arr[mid]` to be the minimum of some window `[start, end]`, **every value in that window must be ≥ arr[mid]**. So the window can only stretch:

- **Left**, until it hits something *smaller* than `arr[mid]` — call that blocking element the **Previous Smaller Element (PSE)**.
- **Right**, until it hits something *smaller* than `arr[mid]` — call that blocking element the **Next Smaller Element (NSE)**.

```
                 PSE                 mid                  NSE
                  |                   |                    |
      ... [bigger stuff] [ window where arr[mid] wins ] [bigger stuff] ...
                  ^                                        ^
             boundary (excluded)                     boundary (excluded)

      Number of valid START points = mid - PSE_index   ("left" in the code)
      Number of valid END points   = NSE_index - mid    ("right" in the code)

      K = left * right
      contribution of arr[mid] = arr[mid] * K
```

So the entire problem reduces to: **for every index, find its PSE and NSE, fast.** That's exactly what a monotonic stack gives us — and it gives us *both*, in a single left-to-right scan.

## 5. Monotonic Stack, From Scratch (Generic, No Subarrays Yet)

Forget subarrays for a moment. Let's solve a clean, standalone problem:

> **For every element in an array, find the Next Smaller Element (NSE) to its right.**

```
arr    = [4, 2, 5, 1, 3]
index  =  0  1  2  3  4
```

### The mental model: a waiting line of "unresolved" elements

Think of the stack as **people standing in a line, each still waiting for an answer to "who's the next smaller person after me?"**

Scan left to right, one element at a time (call it `current`):

- If `current` is **bigger** than the top of the stack → it doesn't answer anyone's question. It just joins the back of the line (**push**).
- If `current` is **smaller** than the top of the stack → it just answered that person's question! Pop them, record `NSE = current`, then check the new top — maybe `current` answers their question too (keep popping while true).

```
 RULE OF THUMB:
   bigger element arriving  →  push, nothing resolved
   smaller element arriving →  pop everyone on top who is bigger than it,
                                each pop = "found your NSE!"
```

### Full trace

```
i=0, val=4
  Stack empty → nothing to compare. Push 4.
  Stack (bottom→top): [4]

i=1, val=2
  Top = 4.  Is 4 > 2?  YES → 2 resolves 4's question!
     NSE(4) = 2
  Pop 4. Stack now empty → stop popping.
  Push 2.
  Stack: [2]

i=2, val=5
  Top = 2.  Is 2 > 5?  NO.
  Nothing resolved. Push 5.
  Stack: [2, 5]

i=3, val=1
  Top = 5.  Is 5 > 1?  YES → 1 resolves 5's question!
     NSE(5) = 1
  Pop 5. New top = 2.  Is 2 > 1?  YES → 1 resolves 2's question too!
     NSE(2) = 1
  Pop 2. Stack now empty → stop popping.
  Push 1.
  Stack: [1]

i=4, val=3
  Top = 1.  Is 1 > 3?  NO.
  Nothing resolved. Push 3.
  Stack: [1, 3]

End of array. Whoever is still in the stack (1, 3) never found
a smaller element to their right → NSE = "none".
```

**Results:**

```
value:   4   2   5   1   3
NSE:     2   1   1   -   -
```

Eyeball-check against the array `[4, 2, 5, 1, 3]`: nearest smaller value after `4` is `2` ✓. After `5` is `1` ✓. After `2` is `1` ✓ (the `5` in between isn't smaller than `2`, so it's correctly skipped). `1` and `3` have nothing smaller after them ✓.

### Why the stack stays sorted (the "monotonic" part)

Every time we push something, we've *already* popped off everything bigger sitting on top of the eventual new top. So whatever remains directly below any element is guaranteed smaller than it. Read bottom → top, the stack is **strictly increasing** at every point in time. That invariant is why it's called a **monotonic increasing stack**.

```
  ALWAYS TRUE (the invariant):          NEVER TRUE (would break it):

    top    →  [ 5 ]                       top    →  [ 2 ]
               [ 3 ]                                  [ 5 ]
               [ 1 ]                       bottom →  ...
    bottom →  ...
                                           (2 sitting above 5 is impossible —
    (increasing bottom → top)              2 would've popped 5 on arrival)
```

## 6. The Key Insight: PSE Is Decided at PUSH Time, NSE at POP Time

This is the part that usually causes confusion, so let's isolate it completely.

**It is *not* true that PSE and NSE are both found by comparison at the same moment.** Only NSE is found by comparison. PSE is *never* compared — it's simply **read off from what's already sitting below you**, and that fact was fixed **earlier**, back when you were pushed.

### The rule for PSE

> Whoever is sitting **directly below you** in the stack, **at the moment you get pushed**, is your PSE — permanently, for as long as you remain in the stack.

### Why it can never change

A stack has exactly **one door**: the top. Things only enter or leave from the top (LIFO — Last In, First Out). So the instant element `X` is pushed on top of element `L`:

```
  top    →  [ X ]
             [ L ]
  bottom →  ...
```

Nothing can ever be inserted **between** `L` and `X` afterward. The only things that can happen next are:
- (a) something *bigger* than `X` gets pushed on top of `X` — doesn't touch `L` at all, or
- (b) `X` itself gets popped.

`L` stays glued directly beneath `X` for `X`'s entire lifetime in the stack. So `L` was, is, and remains `X`'s nearest-smaller-to-the-left neighbor from the moment `X` joined — full stop. There's no future event that could invalidate it.

### The rule for NSE

NSE genuinely **cannot** be known at push time — the future hasn't happened yet! It's only revealed later, when some future smaller value shows up and pops `X` off. That's a real, live comparison, happening at a **different point in time** than the push.

### Side-by-side trace, separating the two events

Reusing `arr = [4, 2, 5, 1, 3]`. Watch: **PSE is only ever written at a push. NSE is only ever written at a pop.**

```
i=0, val=4
  PUSH 4.  Nothing below → PSE(4) = none.
  Stack: [4]

i=1, val=2
  Compare top(4) vs 2 → 4>2 → POP 4.
     NSE(4) = 2                 ← discovered NOW, at pop time
     (PSE(4) = none was already fixed back at i=0 — nothing new)
  PUSH 2.  Nothing below → PSE(2) = none.
  Stack: [2]

i=2, val=5
  Compare top(2) vs 5 → 2 not>5 → no pop.
  PUSH 5.  What's below right now? → 2.   PSE(5) = 2.
  Stack: [2, 5]
     (NSE(5) totally unknown still — hasn't happened yet)

i=3, val=1
  Compare top(5) vs 1 → 5>1 → POP 5.
     NSE(5) = 1                 ← discovered NOW
     (PSE(5) = 2 was already fixed back at i=2 — just recall it)
  Compare top(2) vs 1 → 2>1 → POP 2.
     NSE(2) = 1                 ← discovered NOW
     (PSE(2) = none was already fixed back at i=1)
  PUSH 1.  Nothing below → PSE(1) = none.
  Stack: [1]

i=4, val=3
  Compare top(1) vs 3 → 1 not>3 → no pop.
  PUSH 3.  What's below? → 1.   PSE(3) = 1.
  Stack: [1, 3]
     (NSE(3) unknown — array ends before anyone smaller appears)
```

### So why does the code make it LOOK simultaneous?

Because we only ever *need* both values **at the moment an element is popped** — that's the only moment we compute its final answer and discard it. So at pop time, the code just does two reads back-to-back:

```java
while (!stack.isEmpty() && arr[stack.peek()] > current) {
    int mid = stack.pop();
    int leftIndex  = stack.isEmpty() ? -1 : stack.peek();  // RECALLING old news → PSE
    int rightIndex = i;                                     // BREAKING news right now → NSE
    ...
}
```

One is **breaking news** (just happened). The other is **recalling a fact that was already true** and simply hadn't been "read" yet. It's one line of code, so it *looks* like one event — but conceptually they happened at two different times, for the same reason a filing cabinet drawer can hold something you put there yesterday: opening the drawer today doesn't mean the paper was written today.

```
  TIMELINE for element X:

  ─────●───────────────────────────●─────────────►  time
     PUSH X                      POP X
     (PSE fixed HERE,            (NSE discovered HERE,
      just sitting quietly        and PSE is simply
      in the stack until           re-read at this
      X gets popped)                same moment)
```

---

## 7. Why This Is Provably Correct (Not Just Lucky)

Two small proofs, stated plainly:

**Claim 1 — the PSE we read off is genuinely the *nearest* smaller element to the left, not just *some* smaller element.**
Proof sketch: while `X` sits in the stack with `L` directly below it, nothing between `L`'s position and `X`'s position in the array could have been smaller than `X` — if something had been, it would have popped `X` already (that's the whole popping rule). So `L` is the *nearest* qualifying element.

**Claim 2 — the NSE we discover at pop time is genuinely the *nearest* smaller element to the right.**
Proof sketch: we scan strictly left to right, and `X` remains in the stack completely undisturbed until the first (i.e. nearest) index whose value is smaller than it. That index is, by definition, the one that finally pops it. No smaller value could have appeared earlier without already triggering the pop.

Both boundaries are therefore the *nearest* ones, exactly what "subarray minimum territory" requires.

## 8. Bringing It Back: Full Trace of the Original Problem

Now let's re-run `arr = [3, 1, 2, 4]`, this time computing full contributions, using everything above.

```
Array (with sentinel):  index:  0  1  2  3   4(virtual)
                         value:  3  1  2  4   0
```

```
i=0, val=3
  Stack empty → push. PSE(3) = none (index -1).
  Stack: [0]                         (holds indices; val shown for clarity: [3])

i=1, val=1
  Compare top: arr[0]=3 > 1 → POP index 0 (val 3).
     NSE = index 1.   PSE = -1 (stack now empty).
     left  = 0 - (-1) = 1
     right = 1 - 0     = 1
     K = 1*1 = 1   →  contribution = 3 * 1 = 3
     running total = 3
  Push index 1. PSE(1) = none (stack empty below it).
  Stack: [1]                          ([1])

i=2, val=2
  Compare top: arr[1]=1 > 2?  NO.
  Push index 2. PSE(2) = index 1 (val 1).
  Stack: [1, 2]                       ([1, 2])

i=3, val=4
  Compare top: arr[2]=2 > 4?  NO.
  Push index 3. PSE(4) = index 2 (val 2).
  Stack: [1, 2, 3]                    ([1, 2, 4])

i=4, val=0 (sentinel — smaller than everything, forces full flush)
  Compare top: arr[3]=4 > 0 → POP index 3 (val 4).
     NSE = index 4.   PSE = index 2 (val 2, now exposed at top).
     left  = 3 - 2 = 1
     right = 4 - 3 = 1
     K = 1*1 = 1  →  contribution = 4 * 1 = 4
     running total = 3 + 4 = 7

  Compare top: arr[2]=2 > 0 → POP index 2 (val 2).
     NSE = index 4.   PSE = index 1 (val 1, now exposed at top).
     left  = 2 - 1 = 1
     right = 4 - 2 = 2
     K = 1*2 = 2  →  contribution = 2 * 2 = 4
     running total = 7 + 4 = 11

  Compare top: arr[1]=1 > 0 → POP index 1 (val 1).
     NSE = index 4.   PSE = -1 (stack now empty).
     left  = 1 - (-1) = 2
     right = 4 - 1     = 3
     K = 2*3 = 6  →  contribution = 1 * 6 = 6
     running total = 11 + 6 = 17

  Stack now empty. Push sentinel index 4.

FINAL ANSWER = 17  ✓
```

```
 Contribution summary:

   element   PSE idx   NSE idx   left   right   K    contribution
   -------   -------   -------   ----   -----   --   ------------
     3          -1         1       1      1      1        3
     1          -1         4       2      3      6         6
     2           1         4       1      2      2         4
     4           2         4       1      1      1         4
                                                   sum  =  17
```

(Order of rows differs from array order because they're processed in the order they get *popped*, not pushed — but the total is the same either way.)

## 9. Why the Sentinel (Dummy 0) at the End

Look at the trace above: after processing the real array (`i=0..3`), the stack still held `[1, 2, 3]` (indices for values `1, 2, 4`) — none of them had found an NSE yet, because nothing smaller ever showed up after them in the real array.

```
 Without a sentinel:

   real array ends → stack = [1, 2, 4] still sitting there
   → their contributions NEVER get computed
   → answer would be WRONG (missing 4 + 4 + 6 = 14, i.e. only 3 would count)
```

By appending one virtual element equal to `0` (smaller than any real value in this problem, since constraints guarantee positive integers), we guarantee the `while` loop's pop condition triggers one final time for every remaining stack entry, flushing everybody out and computing their contributions. It's a clean way to avoid writing a separate "drain the stack" loop after the main loop.

```
  WITHOUT sentinel:                    WITH sentinel:

  for i in 0..n-1:                     for i in 0..n:      (note: <= n)
      ... main logic ...                   current = (i==n) ? 0 : arr[i]
                                            ... same logic, now self-flushing
  # stack may still have leftovers
  while stack not empty:               # stack guaranteed empty at the end
      ... duplicate the same
          popping logic again ...
```

## 10. Why Duplicates Need Asymmetric `>` vs `>=`

Consider `arr = [2, 1, 1, 2]`. There are two `1`s. If both `1`s "claim" the subarray `[1, 1]` as one where they're the minimum, it gets **double-counted**.

The fix: make the two sides of the comparison **asymmetric**.

```
  Pop condition used in the code:      arr[stack.peek()]  >  current
                                                            ^
                                                     STRICT inequality

  Effect:
    - Going right (finding NSE), an EQUAL value does NOT trigger a pop.
      So an element's "territory" extends through equal values on the right,
      stopping only at something STRICTLY smaller.
    - Going left (via the stack invariant, finding PSE), because the pop
      condition is strict, an element already in the stack that is EQUAL
      to an incoming value stays put — it isn't treated as "smaller" either
      way, so effectively the LEFT boundary search behaves as "stop at the
      first value that is smaller-or-equal" once you trace through how
      equal values accumulate in the stack without popping each other.

  Net result: each occurrence of a repeated value owns a distinct,
  non-overlapping slice of "who is the minimum of this subarray" —
  no subarray gets attributed to two different indices.
```

The precise mechanical rule to remember: **strict `>` on the pop condition means "equal values don't kick each other out."** Combined with scanning strictly left-to-right, this reliably assigns every subarray-with-a-tied-minimum to exactly one specific index (in this implementation, the *rightmost* occurrence ends up absorbing ties extending left, and the *leftmost* occurrence absorbs ties extending right — the asymmetry is what prevents overlap). You don't need to re-derive this from first principles every time — just remember: **one strict side, one non-strict side, always, whenever the array can contain duplicates.**

## 11. Complexity Analysis

```
 Time:  O(N)
   - Every index is PUSHED exactly once.
   - Every index is POPPED at most once.
   - Therefore total push+pop operations ≤ 2N → O(N) overall,
     even though there's a "while" loop nested inside a "for" loop —
     it's NOT O(N²), because the inner while loop's total iterations
     across the ENTIRE run are bounded by N (amortized analysis).

 Space: O(N)
   - Stack holds at most N+1 indices (worst case: strictly increasing
     array, nothing ever gets popped until the sentinel flush).
```

```
  Amortized cost intuition:

    "Charge" each pop to the push that put it there.
    Since each index is pushed once, it can only be popped once.
    Total charges ≤ total pushes = N.
    → inner while loop's lifetime cost, summed over the WHOLE
      outer for loop, is O(N), not O(N) per iteration.
```

## 12. Mental Checklist / Cheat Sheet

```
┌──────────────────────────────────────────────────────────────────┐
│ 1. Reframe the problem:                                          │
│    "sum over subarrays" → "sum over elements' contributions"     │
│                                                                    │
│ 2. Contribution of arr[mid] = arr[mid] * (left choices)           │
│                                          * (right choices)         │
│                                                                    │
│ 3. left  = mid - PSE_index      (Previous Smaller Element)        │
│    right = NSE_index - mid      (Next Smaller Element)            │
│                                                                    │
│ 4. Monotonic increasing stack finds BOTH in one pass:              │
│      PUSH  → fixes PSE (whatever's below you, right now)          │
│      POP   → fixes NSE (whoever caused you to be popped)          │
│                                                                    │
│ 5. Why PSE never changes after push:                               │
│      stack = LIFO = one door (the top) = nothing can be            │
│      inserted beneath you once you're in                          │
│                                                                    │
│ 6. Append a sentinel (value smaller than everything) at the end   │
│    to flush any elements still stuck in the stack.                │
│                                                                    │
│ 7. Duplicates → use strict `>` on one side only, to avoid          │
│    double-counting tied minimums across two equal elements.       │
│                                                                    │
│ 8. Result: O(N) time, O(N) space — every index pushed once,       │
│    popped at most once.                                           │
└──────────────────────────────────────────────────────────────────┘
```
