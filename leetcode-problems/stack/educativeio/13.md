# Second Greater Element — Full Breakdown

## 1. The Problem, Precisely

For every index `i`, find the **second** element to its right that is strictly greater than `nums[i]`. If fewer than two such elements exist, the answer is `-1`.

```
nums  = [2, 4, 0, 9, 6]
index    0  1  2  3  4
```

Walk through index 0 (`value = 2`) by hand:
- Elements to its right: `4, 0, 9, 6`
- Keep only the ones greater than 2: `4, 9, 6`
- 1st greater = `4`, 2nd greater = `9` → **answer for index 0 is 9**

Do this for every index and you get:

```
res = [9, -1, 6, -1, -1]
```

The naive way to compute this is O(n²) — for each index, scan right and track the first two larger values. The two-stack technique gets this down to **O(n) time, O(n) space**. The rest of this doc is about *why* that technique works, not just *that* it works.

---

## 2. The Central Reframe: Stop Thinking "Search," Start Thinking "State"

The naive approach asks, for each index: *"let me look forward and find two things."*

The O(n) approach flips the question entirely. Instead of each index looking forward, we process the array left→right and ask, for each **new** value arriving: *"which earlier indices does this value complete?"*

Every index, at any moment, is in exactly one of three states:

```
STATE 0                 STATE 1                    STATE 2 (done)
"found 0 greater        "found 1 greater            "found 2 greater
 elements yet"           element, waiting            elements — answer
                          for the 2nd"                is recorded"

   lives in  s1   ---first greater arrives--->   lives in  s2   ---second greater arrives--->  res[i] set
```

That's the whole idea. `s1` and `s2` are not "two random stacks the algorithm happens to use" — they are literally the two waiting rooms in this state machine. Every index is born into `s1` (state 0), and graduates forward one state at a time, never backward, never skipping a state.

This reframing is the single most important thing to internalize: **the number of stacks you need equals the number of "greater elements" you're counting.** If this problem asked for the *third* greater element, you'd need three stacks (`s1 → s2 → s3 → answer`). That generalization is worth remembering — we'll come back to it in §8.

---

## 3. Why Left → Right (and not the "obvious" Right → Left)?

Your instinct for "find something to the right" problems is usually: scan from the right, since the answer lives to the right of the current index. That instinct is correct for the *classic* Next Greater Element problem — but it breaks down here, and it's worth understanding exactly why.

**Classic Next Greater Element (right→left works great):**
At index `i`, you only need to know "what's the smallest value greater than everything discarded so far, i.e. the next thing standing tall to my right." A single monotonic stack captures that perfectly, because you only ever need to remember *one* candidate answer per index.

**Second Greater Element (right→left breaks down):**
At index `i`, you need to know not one but *two* future values, **and their relative order matters** (which one comes first). If you're standing at index 0 looking right-to-left, by the time you've walked backward to index 0, you've already seen indices 4, 3, 2, 1 — but you don't inherently know which of the "greater than 2" values you saw *first* in left-to-right order, unless you maintain something much richer than a simple stack (an ordered structure, binary search, a Fenwick/segment tree, etc.). That's real complexity for no good reason.

**Left→right solves this for free**, because of one simple fact:

> When you're standing at index `i` moving forward, `nums[i]` is a **candidate completion** for everything unresolved *before* it. You don't need to "look ahead" — you just let the future come to you, one element at a time, and each new element gets to complete the earliest still-open requirement of everyone behind it.

So instead of index 0 hunting for its 1st and 2nd greater element, we let index 1's value (4) walk up to index 0 and say "I am your first greater element" and later let index 3's value (9) walk up and say "I am your second." Direction flips, but the *relationship* found is identical.

## 4. Why Two Stacks Aren't Enough Conceptually — You Need `s1`, `s2`, *and* a Transfer Mechanism

Once you accept the two-waiting-room idea, a subtlety appears: **moving many elements from `s1` to `s2` at once must preserve their relative order** — and a plain stack pop/push does not do that for free.

### 4.1 Concrete illustration of the ordering bug

Say `s1` currently holds indices whose values are `[2, 3, 4]` (bottom → top), and `current = 10` arrives. All three are smaller than 10, so all three graduate to `s2` in the same step.

If you naively do:
```java
while (!s1.isEmpty() && nums[s1.peek()] < current) {
    s2.push(s1.pop());   // WRONG — reverses order
}
```

Trace it:
```
s1 (top→bottom): 4, 3, 2
pop 4 → push to s2   → s2 = [4]
pop 3 → push to s2   → s2 = [4, 3]
pop 2 → push to s2   → s2 = [4, 3, 2]   (top = 2)
```

`s2` ends up with `2` on top — but `2` was the **oldest**, bottom-most element in `s1`. We've silently reversed the order of who's "next in line" to be resolved. Since `s2`'s ordering determines who gets matched with future values first, this corrupts the algorithm's correctness.

### 4.2 The fix: bounce through a `temp` stack

```java
while (!s1.isEmpty() && nums[s1.peek()] < current) {
    temp.push(s1.pop());     // first reversal:  s1 → temp
}
while (!temp.isEmpty()) {
    s2.push(temp.pop());     // second reversal: temp → s2
}
```

Two reversals cancel out — this is the classic "use an auxiliary stack to flip a stack back to its original order" trick, same principle as reversing a stack using another stack.

```
s1 (top→bottom): 4, 3, 2

Pass 1 — pop s1, push temp:
  temp (top→bottom): 2, 3, 4

Pass 2 — pop temp, push s2:
  s2 (top→bottom): 4, 3, 2   ... wait, let's actually track it carefully:
```

Let's be careful and trace index positions instead of guessing:

```
s1 before:      bottom [2] [3] [4] top      (values shown, top = 4)

Step A: while nums[s1.top] < current: move s1 → temp
   pop 4 → temp: [4]
   pop 3 → temp: [4][3]
   pop 2 → temp: [4][3][2]         (temp top→bottom, left = bottom: read as bottom[4,3,2]top)

Step B: while temp not empty: move temp → s2
   pop 2 → s2: [2]
   pop 3 → s2: [2][3]
   pop 4 → s2: [2][3][4]           (s2 bottom→top: 2, 3, 4 — top is 4)
```

So `s2` ends up bottom→top as `2, 3, 4`, meaning **`4` is on top of `s2`**, exactly matching the order it had in `s1` before the move (`4` was on top of `s1` too). **Order preserved.** `temp` is not a third logical waiting room — it's purely plumbing, needed only because stacks are LIFO and we're moving a *batch*, not a single element.

> **Rule of thumb to remember:** whenever you need to move a *contiguous run* of elements from the top of one stack to another *while keeping their order*, you need this double-reversal trick (or equivalent, like recursion). Moving a single element stack-to-stack never needs it — only batches do.

## 5. Full Annotated Code

```java
import java.util.*;

public class Solution {

    public int[] secondGreaterElement(int[] nums) {
        int n = nums.length;

        int[] res = new int[n];
        Arrays.fill(res, -1);          // default: no second-greater found

        Deque<Integer> s1 = new ArrayDeque<>();   // waiting for 1st greater
        Deque<Integer> s2 = new ArrayDeque<>();   // waiting for 2nd greater
        Deque<Integer> temp = new ArrayDeque<>(); // order-preserving bridge (s1 -> s2)

        for (int i = 0; i < n; i++) {
            int current = nums[i];

            // STEP 1 — resolve anyone in s2 whose SECOND greater has just arrived
            while (!s2.isEmpty() && nums[s2.peek()] < current) {
                res[s2.pop()] = current;
            }

            // STEP 2 — anyone in s1 whose FIRST greater has just arrived
            //          must be promoted to s2 (via temp, to preserve order)
            while (!s1.isEmpty() && nums[s1.peek()] < current) {
                temp.push(s1.pop());
            }

            // STEP 3 — flush temp into s2, restoring correct order
            while (!temp.isEmpty()) {
                s2.push(temp.pop());
            }

            // STEP 4 — current index starts its own journey in s1
            s1.push(i);
        }

        return res;
    }
}
```

### Why Step 1 must run *before* Step 2 (ordering matters!)

This is a detail both source versions glossed over. If you swapped Steps 1 and 2, an index could be promoted `s1 → s2` and then, **in the same iteration**, immediately be checked against `s2`'s resolution condition and incorrectly resolved against the *same* `current` value that only qualifies as its *first* greater element, not its second. Running Step 1 first guarantees: anything resolved out of `s2` this iteration got there in an **earlier** iteration (so `current` is legitimately a different, later value than their first-greater match). Only *after* that resolution do we let new members join `s2` for future iterations to resolve.

## 6. Full Dry Run: `nums = [2, 4, 0, 9, 6]`

Legend: stacks shown bottom→top (rightmost = top of stack). Indices are stored, but values are shown alongside for clarity as `idx(val)`.

```
Start: s1=[], s2=[], res=[-1,-1,-1,-1,-1]
```

**i=0, current=2**
- s2 empty → nothing resolved
- s1 empty → nothing promoted
- push 0 → `s1 = [0(2)]`

**i=1, current=4**
- s2 empty → nothing resolved
- s1 top is `0(2)`, and `2 < 4` → promote: `temp=[0(2)]`, `s1=[]`
- flush temp → `s2 = [0(2)]`
- push 1 → `s1 = [1(4)]`

State meaning: index 0 found its first greater (waiting for 2nd), index 1 is waiting for its first.

**i=2, current=0**
- s2 top is `0(2)`, but `2 < 0` is false → nothing resolved
- s1 top is `1(4)`, but `4 < 0` is false → nothing promoted
- push 2 → `s1 = [1(4), 2(0)]`

**i=3, current=9**
- s2 top is `0(2)`, `2 < 9` → resolve: `res[0] = 9`; pop → `s2 = []`
- s1 top is `2(0)`, `0 < 9` → promote: `temp=[2(0)]`; next top is `1(4)`, `4 < 9` → promote: `temp=[2(0), 1(4)]`; s1 empty now
- flush temp → pop `1(4)` first (top of temp) → `s2=[1(4)]`; pop `2(0)` → `s2=[1(4), 2(0)]`
- push 3 → `s1 = [3(9)]`

State: index 0 is done (`res[0]=9`). `s2` now holds index 1 (waiting for 2nd) at the bottom and index 2 (waiting for 2nd) on top — note index 1 sits *below* index 2 in `s2`, correctly reflecting that index 1 became "waiting for 2nd" *before* index 2 did.

**i=4, current=6**
- s2 top is `2(0)`, `0 < 6` → resolve: `res[2] = 6`; pop → `s2 = [1(4)]`
- s2 top is now `1(4)`, `4 < 6` → resolve: `res[1] = 6`; pop → `s2 = []`
- s1 top is `3(9)`, `9 < 6` is false → nothing promoted
- push 4 → `s1 = [3(9), 4(6)]`

**End of array.** Final:
```
res = [9, 6, 6, -1, -1]
```

Wait — let's sanity check this against a manual brute-force check, because it's worth verifying by hand rather than trusting the trace blindly:

- index 0 (`2`): rightward greater-than-2 values in order: `4, 9, 6` → 1st=4, 2nd=9 ✓ matches `res[0]=9`
- index 1 (`4`): rightward greater-than-4 values in order: `9, 6` → 1st=9, 2nd=6 ✓ matches `res[1]=6`
- index 2 (`0`): rightward greater-than-0 values in order: `9, 6` → 1st=9, 2nd=6 ✓ matches `res[2]=6`
- index 3 (`9`): nothing to its right is greater than 9 → `res[3]=-1` ✓
- index 4 (`6`): nothing to its right → `res[4]=-1` ✓

Final answer: **`[9, 6, 6, -1, -1]`**

> Note: this differs from the `[9, -1, 6, -1, -1]` claimed in the original comment block you shared — that was a mistake in the original walkthrough (it forgot that `4`'s second-greater is also `6`). Always verify a traced example against brute force when learning a new pattern; it catches exactly this kind of slip.

## 7. Complexity Analysis

**Time: O(n).** This isn't obvious just from "there are nested while loops" — it requires an *amortized* argument:

- Every index is pushed into `s1` exactly once (Step 4).
- Every index can be popped out of `s1` at most once (Step 2) — once popped, it never re-enters `s1`.
- Every index can be pushed into `temp` at most once per promotion, and immediately popped out — `temp`'s net traffic per index is O(1) total across the whole run.
- Every index can be pushed into `s2` at most once and popped out of `s2` at most once (Step 1).

So each index contributes a *constant* number of push/pop operations across the entire algorithm's lifetime — even though a single iteration of the outer loop might pop many elements out of `s1`/`s2` at once (e.g., when `current` is a new maximum), those pops are "paid for" by earlier pushes and never repeated. This is the same amortized reasoning used to justify O(n) for the classic single-stack Next Greater Element problem — just applied twice, once per stack.

**Space: O(n).** In the worst case (strictly decreasing array, e.g. `[9,8,7,6,5]`), every index sits in `s1` simultaneously since nothing is ever promoted.

## 8. Generalizing the Pattern (worth internalizing, not just memorizing)

The state-machine view scales cleanly to "find the **K-th** greater element to the right":

```
s1 --1st greater--> s2 --2nd greater--> s3 --3rd greater--> ... --> sK --Kth greater--> res
```

Each promotion step between `s_j` and `s_{j+1}` needs the same `temp`-bridge trick to preserve ordering, since you're still moving *batches* of elements between LIFO structures. The number of stacks equals K, and both time and space stay O(n·K) — linear in array size, scaled by how many "greater elements" you're chasing.

This generalization is the real payoff of understanding *why* the two-stack trick works (state promotion + order-preserving transfer), rather than memorizing the four-step loop body as a fixed recipe.

---

## 9. Common Pitfalls When Implementing This Yourself

1. **Swapping Step 1 and Step 2's order** — breaks correctness, as explained in §5.
2. **Pushing directly `s1 → s2` without the `temp` bridge** — silently corrupts ordering only when *more than one* element is promoted in a single iteration; easy to miss in small test cases where at most one element ever gets promoted per step.
3. **Using `<=` instead of `<`** in the comparison conditions — the problem asks for *strictly* greater, so equal values must not resolve or promote anything.
4. **Forgetting `Arrays.fill(res, -1)`** — Java arrays of `int` default to `0`, not `-1`, which is a valid array value and would silently produce wrong answers for elements with no second-greater.
