You actually **don’t need `extraNumbers` in this implementation**. There is a subtle issue in the logic.

Let's walk through why.

### What are we trying to do?

After cyclic sort, every number `1..n` is placed at its correct position if it exists.

For example:

```text
arr = [3, -1, 4, 5, 5]
n = 5
```

After cyclic sort:

```text
[ -1, 3, 4, 5, 5]
```

Then we scan:

```text
index:  0   1   2   3   4
value: -1   3   4   5   5
need:   1   2   3   4   5
```

So:

```text
1 missing
2 missing
```

If we still need more, we start at:

```text
n + 1 = 6
```

Now here's the important observation:

> **Numbers greater than `n` cannot have been placed by cyclic sort.**

They remain wherever they were.

But your `extraNumbers` is only populated when you find a missing number:

```java
if (arr[i] > n) {
    extraNumbers.add(arr[i]);
}
```

That means it only remembers `> n` values that happen to sit at positions where a number is missing.

### Example where the set matters

Consider:

```text
arr = [1, 2, 3, 4, 6]
n = 5
k = 2
```

After cyclic sort:

```text
[1, 2, 3, 4, 6]
```

Scan:

```text
1 → present
2 → present
3 → present
4 → present
5 → missing
```

Your code does:

```java
if (arr[4] > n) {
    extraNumbers.add(arr[4]);  // adds 6
}
```

So:

```text
missingNumbers = [5]
extraNumbers = {6}
```

Now we search beyond `n`:

```text
candidate = 6
```

But `6` **exists in the original array**, so we must NOT report it.

That's why:

```java
if (!extraNumbers.contains(candidate)) {
    missingNumbers.add(candidate);
}
```

Without the set, we'd incorrectly return:

```text
[5, 6] ❌
```

instead of:

```text
[5, 7] ✅
```

## But there's an even simpler way

You don't actually need a `Set`.

Because after cyclic sort, you can simply check whether each candidate `n+1, n+2, ...` exists in the array.

However, doing a linear search for every candidate would make the solution potentially **O(nk)**.

The standard Cyclic Sort solution therefore uses a `Set` of the numbers **greater than `n`**:

```java
Set<Integer> extraNumbers = new HashSet<>();

for (int num : arr) {
    if (num > n) {
        extraNumbers.add(num);
    }
}
```

Then:

```java
int candidate = n + 1;

while (k > 0) {
    if (!extraNumbers.contains(candidate)) {
        missingNumbers.add(candidate);
        k--;
    }
    candidate++;
}
```

### Why collect all `> n` numbers?

Because the array can contain:

```text
[1, 2, 3, 4, 6]
```

and `6` is **not a missing positive number**, even though cyclic sort only organizes `1..n`.

### One correction to your code

Your current code builds `extraNumbers` only inside:

```java
if (arr[i] != i + 1)
```

But a cleaner approach is to collect all values `> n` separately:

```java
Set<Integer> extraNumbers = new HashSet<>();

for (int num : arr) {
    if (num > n) {
        extraNumbers.add(num);
    }
}
```

Then scan for missing `1..n`.

So the mental model is:

```text
Cyclic Sort
    ↓
Find missing numbers 1..n
    ↓
Still need more?
    ↓
Look at n+1, n+2, ...
    ↓
Skip numbers that already existed in the array
    ↓
extraNumbers Set
```

**The key reason for the set:** cyclic sort only handles `1..n`, but when we start looking beyond `n`, we still need to know which larger numbers were already present in the original array.

Your solution is **correct in its overall approach**, but I would simplify it. For an interview, there is a cleaner standard implementation.

### Your approach

You do:

1. Cyclic sort `1..n`
2. Find missing numbers in `1..n`
3. Track numbers `> n`
4. Continue from `n + 1`

The idea is good, but this part makes it harder to reason about:

```java
if (arr[i] > n) {
    extraNumbers.add(arr[i]);
}
```

and the `extraNumbers` logic is mixed into the missing-number scan.

### Cleaner implementation

I'd write it like this:

```java
import java.util.*;

public class Solution {

    public static List<Integer> firstKMissingNumbers(int[] arr, int k) {
        List<Integer> result = new ArrayList<>();

        int n = arr.length;

        // 1. Cyclic sort numbers in the range [1, n]
        int i = 0;

        while (i < n) {
            int correctIndex = arr[i] - 1;

            if (arr[i] > 0 &&
                arr[i] <= n &&
                arr[i] != arr[correctIndex]) {

                swap(arr, i, correctIndex);
            } else {
                i++;
            }
        }

        // 2. Find missing numbers in [1, n]
        Set<Integer> extraNumbers = new HashSet<>();

        for (int num : arr) {
            if (num > n) {
                extraNumbers.add(num);
            }
        }

        for (i = 0; i < n && result.size() < k; i++) {
            if (arr[i] != i + 1) {
                result.add(i + 1);
            }
        }

        // 3. Find remaining missing numbers > n
        int candidate = n + 1;

        while (result.size() < k) {
            if (!extraNumbers.contains(candidate)) {
                result.add(candidate);
            }
            candidate++;
        }

        return result;
    }

    private static void swap(int[] arr, int i, int j) {
        int temp = arr[i];
        arr[i] = arr[j];
        arr[j] = temp;
    }
}
```

### But there's an even nicer improvement

We can avoid explicitly storing **all** `> n` numbers.

Instead, after cyclic sort, when we encounter a missing number, the value at that position can tell us about a potentially relevant `> n` value.

That's essentially what your implementation is doing.

So your version is actually **space-efficient in terms of what it tracks**, but it makes the explanation less obvious.

## What I'd use in an interview

I'd probably use this version:

```java
public static List<Integer> firstKMissingNumbers(int[] arr, int k) {

    List<Integer> result = new ArrayList<>();
    int n = arr.length;

    // Cyclic sort
    int i = 0;

    while (i < n) {
        int correctIndex = arr[i] - 1;

        if (arr[i] > 0 &&
            arr[i] <= n &&
            arr[i] != arr[correctIndex]) {

            swap(arr, i, correctIndex);
        } else {
            i++;
        }
    }

    // Numbers > n that already exist
    Set<Integer> extras = new HashSet<>();

    for (int num : arr) {
        if (num > n) {
            extras.add(num);
        }
    }

    // Missing numbers from 1..n
    for (i = 0; i < n && result.size() < k; i++) {
        if (arr[i] != i + 1) {
            result.add(i + 1);
        }
    }

    // Missing numbers after n
    for (int candidate = n + 1;
         result.size() < k;
         candidate++) {

        if (!extras.contains(candidate)) {
            result.add(candidate);
        }
    }

    return result;
}
```

### Complexity

|              | Complexity   |
| ------------ | ------------ |
| Cyclic sort  | `O(n)`       |
| Build set    | `O(n)`       |
| Find missing | `O(n + k)`   |
| **Total**    | **O(n + k)** |
| Extra space  | **O(n)**     |

The important interview insight is:

> **Cyclic sort solves the `[1, n]` portion. The Set solves the portion after `n`.**

Your implementation has the right idea; I'd mainly refactor it for **clarity and separation of responsibilities**, rather than changing the algorithm.
