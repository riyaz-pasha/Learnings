# **A\* Algorithm: Understand the intuition, not the formula**

The easiest way to understand A\* is to start with one question:

**When searching for the shortest path from A to B, how can we avoid exploring paths that are clearly taking us in the wrong direction?**

That is the entire motivation behind A\*.

A\* is a shortest-path algorithm that combines two pieces of information:

1. **What have I spent so far?**
2. **How much more do I estimate I will need to reach the destination?**

Let's build that intuition from the beginning.

# **1. First, understand the problem Dijkstra solves**

Imagine you're driving from Vijayawada to Hyderabad.

You have a road network:

- Each city is a node.
- Each road is an edge.
- Each road has a cost, such as distance or travel time.
- You want to find the cheapest route from your starting city to your destination.

One approach is to start at Vijayawada and gradually explore the roads.

Suppose the network looks like this:

```
                  A -------- B
                 /            \
                /              \
        Start --                -- Destination
                \              /
                 \            /
                  C -------- D
```

There may also be many other roads and cities connected to these nodes.

The question is:

**Which city should we explore next?**

Dijkstra's algorithm answers:

> Explore the city that has the smallest known distance from the starting city.

Suppose we have these distances:

| City | Distance from Start |
| ---- | ------------------- |
| A    | 5                   |
| B    | 12                  |
| C    | 7                   |
| D    | 15                  |

Dijkstra picks A because reaching A currently costs only 5.

It then explores A's neighbours, updates their distances, and repeats.

This is a perfectly reasonable strategy.

But notice something important.

**Dijkstra only considers how far you have travelled from the starting point. It doesn't consider how close you are to your destination.**

That's where the inefficiency can come from.

# **2. Why can Dijkstra explore too many nodes?**

Imagine the following road network:

```
                         A -------- B -------- C
                        /                       \
                       /                         \
                      /                           \
        Start --------                             Destination
                      \                           /
                       \                         /
                        X -------- Y -------- Z
```

Let's say the upper route is the shortest route.

However, there are many connected cities around the lower route, and the lower route is also relatively close to the starting point.

Dijkstra doesn't know which direction leads to the destination.

It only knows the distance from the start.

For example:

```
Start
  |
  +---- A      distance = 5
  |
  +---- X      distance = 6
  |
  +---- P      distance = 7
  |
  +---- Q      distance = 8
```

Dijkstra chooses A first, then X, then P, then Q, depending on their current distances.

It may spend time exploring many cities that are not useful for reaching the destination.

Why?

Because a city that is close to the starting point isn't necessarily close to the destination.

This is the key limitation.

**Dijkstra has no idea where the destination is when deciding which node to explore next.**

It is not that Dijkstra is poorly designed. It is deliberately solving a more general problem: finding shortest paths based on distances from a source.

But in many problems, we know our destination in advance.

Can we use that knowledge?

Yes. That's what A\* does.

# **3. The central idea behind A\***

Imagine you're in a city and want to reach a particular destination.

When choosing your next road, you naturally consider two things:

- How far have I already travelled?
- Approximately how far is this city from my destination?

For example:

| City | Distance travelled so far | Estimated distance to destination |
| ---- | ------------------------- | --------------------------------- |
| A    | 5 km                      | 20 km                             |
| B    | 8 km                      | 3 km                              |
| C    | 4 km                      | 30 km                             |

Which city looks more promising?

Probably B.

Although reaching B costs 8 km, it is estimated to be only 3 km from the destination.

The estimated total journey through B is:

\\[ 8 + 3 = 11 \text{ km} \\]

Through A:

\\[ 5 + 20 = 25 \text{ km} \\]

Through C:

\\[ 4 + 30 = 34 \text{ km} \\]

So B looks like the most promising direction.

This is the idea behind A\*.

Instead of prioritizing nodes using only the distance travelled, A\* prioritizes nodes using:

\\[ \boxed{f(n) = g(n) + h(n)} \\]

Don't memorize this yet. Understand what the three terms mean.

| Term       | Meaning                                      | Think of it as               |
| ---------- | -------------------------------------------- | ---------------------------- |
| \\(g(n)\\) | Actual cost from the start to node \\(n\\)   | Cost already paid            |
| \\(h(n)\\) | Estimated cost from node \\(n\\) to the goal | Cost still expected          |
| \\(f(n)\\) | Estimated total cost through node \\(n\\)    | Total estimated journey cost |

A\* chooses the node with the smallest estimated total journey cost.

That's the algorithm.

The formula is simply a mathematical representation of the decision a person would naturally make.

# **4. Understand it with a concrete example**

Consider this weighted graph:

```
                 2
           A -------- C
          /            \
         /              \ 5
        /                \
       S                  G
        \                /
         \              / 3
          B -------- D
                 1
```

Let's define the edges:

| Edge  | Cost |
| ----- | ---- |
| S → A | 1    |
| S → B | 4    |
| A → C | 2    |
| C → G | 5    |
| B → D | 1    |
| D → G | 3    |

There are two possible routes:

```
Route 1: S → A → C → G
Cost:    1 + 2 + 5 = 8

Route 2: S → B → D → G
Cost:    4 + 1 + 3 = 8
```

Both routes have the same cost.

Now suppose we have an estimate of the remaining cost from each node to G.

These estimates are our heuristic values:

| Node | Estimated cost to G: h(n) |
| ---- | ------------------------- |
| S    | 7                         |
| A    | 6                         |
| B    | 4                         |
| C    | 5                         |
| D    | 3                         |
| G    | 0                         |

These estimates never exceed the actual cheapest remaining costs.

Let's run A\*.

### **Step 1: Start at S**

Initially:

\\[ g(S) = 0 \\]

\\[ h(S) = 7 \\]

\\[ f(S) = 0 + 7 = 7 \\]

We add S to our priority queue.

```
Priority Queue:
[S: f=7]
```

We take S out and explore its neighbours.

### **Step 2: Explore S's neighbours**

S has two neighbours: A and B.

For A:

```
g(A) = g(S) + cost(S, A)
     = 0 + 1
     = 1

h(A) = 6

f(A) = 1 + 6 = 7
```

For B:

```
g(B) = g(S) + cost(S, B)
     = 0 + 4
     = 4

h(B) = 4

f(B) = 4 + 4 = 8
```

Our priority queue now contains:

| Node | g(n) | h(n) | f(n) |
| ---- | ---- | ---- | ---- |
| A    | 1    | 6    | 7    |
| B    | 4    | 4    | 8    |

A\* chooses A because it has the smallest f value.

Notice the important distinction:

- Dijkstra would also choose A here, because its g value is smaller.
- But A\* also knows that A appears to be a promising direction towards G.

### **Step 3: Explore A**

A has one relevant neighbour: C.

```
g(C) = g(A) + cost(A, C)
     = 1 + 2
     = 3

h(C) = 5

f(C) = 3 + 5 = 8
```

The queue becomes:

| Node | g(n) | h(n) | f(n) |
| ---- | ---- | ---- | ---- |
| B    | 4    | 4    | 8    |
| C    | 3    | 5    | 8    |

Both have the same estimated total cost.

We can explore either one. Assume we explore C first.

### **Step 4: Explore C**

C connects to G.

```
g(G) = g(C) + cost(C, G)
     = 3 + 5
     = 8

h(G) = 0

f(G) = 8 + 0 = 8
```

Our queue now contains:

| Node | g(n) | h(n) | f(n) |
| ---- | ---- | ---- | ---- |
| B    | 4    | 4    | 8    |
| G    | 8    | 0    | 8    |

We remove G from the queue.

**G is our destination, so we have found an optimal path with cost 8.**

The path is:

```
S → A → C → G

Total cost = 1 + 2 + 5 = 8
```

We didn't need to explore D.

This is the benefit of using information about the destination.

One important detail: this example has a tie in f values, so another tie-breaking policy could explore B first. A\* does not guarantee that it will always follow only one visually direct route. Its advantage comes from the quality of the heuristic across the search space.

# **5. So how exactly does A\* make Dijkstra faster?**

Let's compare their decision-making.

Dijkstra:

\\[ f(n) = g(n) \\]

A\*:

\\[ f(n) = g(n) + h(n) \\]

That's the fundamental difference.

Imagine Dijkstra and A\* have discovered the same three nodes:

| Node | g(n) | h(n) |
| ---- | ---- | ---- |
| A    | 4    | 20   |
| B    | 7    | 3    |
| C    | 9    | 10   |

Dijkstra prioritizes:

| Node | Priority |
| ---- | -------- |
| A    | 4        |
| B    | 7        |
| C    | 9        |

It explores A first.

A\* prioritizes:

| Node | Priority |
| ---- | -------- |
| A    | 24       |
| B    | 10       |
| C    | 19       |

It explores B first.

Why?

Because B is estimated to lead to a much cheaper complete route.

**Dijkstra asks: "Which node is cheapest to reach from the start?"**

*A asks: "Which node appears to give me the cheapest complete route to the destination?"*\*

This is why A\* can explore considerably fewer nodes.

It isn't using a fundamentally faster priority queue or a cheaper graph traversal operation.

It is making better-informed decisions about which nodes are worth exploring.

# **6. What exactly is a heuristic?**

This is the most important concept to understand when implementing A\*.

A heuristic is simply an estimate of the remaining cost to reach the destination.

It is usually represented by:

\\[ h(n) \\]

The algorithm doesn't magically know this value.

**We design the heuristic based on the problem we're solving.**

For example, imagine finding the shortest path on a map.

We can estimate the distance between two locations using their geographical coordinates.

We don't know the actual road distance, but we can estimate the remaining journey using straight-line distance.

That straight-line distance is a heuristic.

Let's examine some common examples.

## **Example A: Grid movement (up, down, left, right)**

Imagine a character moving on a grid.

```
S . . . .
. # # . .
. . . # .
. # . . .
. . . . G
```

Assume:

- Movement is allowed only up, down, left, and right.
- Each move costs 1.
- `#` represents an obstacle.
- The character needs to reach G.

Suppose the current position is:

```
Current: (2, 1)
Goal:    (5, 4)
```

How can we estimate the remaining cost?

The difference in rows is:

\\[ |5 - 2| = 3 \\]

The difference in columns is:

\\[ |4 - 1| = 3 \\]

Even without considering obstacles, we must move at least 3 steps vertically and 3 steps horizontally.

Therefore:

\\[ \boxed{h(n) = |x_2-x_1| + |y_2-y_1|} \\]

This is called **Manhattan distance**.

It gives us a lower bound on the remaining number of moves.

For example:

```
Current position: (2, 1)
Goal position:    (5, 4)

Manhattan distance = 3 + 3 = 6
```

The actual route could be longer because obstacles may force detours. But it cannot be shorter than 6.

That's a useful heuristic.

## **Example B: Grid movement with diagonal movement**

Suppose diagonal movement is allowed too.

```
. . .
. X .
. . G
```

Now Manhattan distance may overestimate the actual cost.

For example, moving diagonally from `(0, 0)` to `(2, 2)` takes only 2 moves if each diagonal move costs 1.

But Manhattan distance says:

\\[ |2-0| + |2-0| = 4 \\]

That is an overestimate.

For this movement model, we need a different heuristic.

If horizontal/vertical moves cost 1 and diagonal moves also cost 1, use **Chebyshev distance**:

\\[ h(n) = \max(|x_2-x_1|, |y_2-y_1|) \\]

If horizontal/vertical moves cost 1 and diagonal moves cost \\(\sqrt{2}\\), use the **octile distance**:

\\[ h(n) = \max(dx,dy) + (\sqrt{2}-1)\min(dx,dy) \\]

These estimates match the movement rules better.

The lesson is:

**Your heuristic must understand the rules of the search problem.**

## **Example C: Road navigation**

Suppose you're finding a route between two cities.

You could use:

- Straight-line distance.
- Great-circle distance between geographical coordinates.
- An estimate based on geographical distance and maximum possible travel speed, if the cost is travel time.

For shortest road distance, straight-line distance is a lower bound on road distance.

For shortest travel time, an estimate based on straight-line distance divided by a valid upper bound on travel speed can be a lower bound on the travel time.

The heuristic must use the same cost units as the actual edge costs.

For example, don't add kilometres to minutes.

# **7. A very important property: admissible heuristic**

Now we need to understand why A\* can still guarantee the shortest path.

Remember, the heuristic is an estimate. It might not be the exact remaining cost.

But if we want A\* to guarantee an optimal solution, we need an important property.

A heuristic is called **admissible** when it never overestimates the true minimum remaining cost.

Mathematically:

\\[ \boxed{h(n) \leq h^\*(n)} \\]

Where:

- \\(h(n)\\) is our estimated remaining cost.
- \\(h^\*(n)\\) is the actual cheapest remaining cost.

Let's understand this with an example.

Suppose the actual minimum distance from A to the destination is 20 km.

| Heuristic estimate | Admissible? |
| ------------------ | ----------- |
| 5 km               | Yes         |
| 12 km              | Yes         |
| 19 km              | Yes         |
| 20 km              | Yes         |
| 25 km              | No          |

An estimate of 12 km is acceptable, even though it isn't particularly accurate.

An estimate of 25 km is not acceptable because we are overestimating the remaining journey.

Why does this matter?

Imagine two routes:

```
Route A:
Cost so far = 5
Estimated remaining = 100
Estimated total = 105

Route B:
Cost so far = 20
Estimated remaining = 5
Estimated total = 25
```

A\* will prefer B.

But suppose our heuristic overestimates the remaining cost on route A.

Perhaps the actual total cost through A is only 10.

A\* might completely ignore the optimal route because our estimate incorrectly makes it look expensive.

That's why admissibility matters.

*When using an admissible heuristic, A can guarantee an optimal path, provided it handles nodes correctly and uses non-negative edge costs.*\*

One useful way to remember admissibility:

> An estimate can be optimistic, but it must not be too pessimistic.

# **8. Another property: consistent heuristic**

You will also encounter something called a consistent heuristic (also known as a monotone heuristic).

It means that the estimated remaining cost should obey the triangle inequality across every edge.

For every edge from node \\(n\\) to node \\(n'\\):

\\[ \boxed{h(n) \leq c(n,n') + h(n')} \\]

Where \\(c(n,n')\\) is the cost of moving from \\(n\\) to \\(n'\\).

Think about it:

Suppose:

- Estimated cost from A to G = 10.
- Cost from A to B = 3.
- Estimated cost from B to G = 5.

Then:

\\[ 10 \leq 3 + 5 \\]

This is false.

The estimate from A is claiming that the destination costs at most 10, but going through B gives us an estimated total of only 8. The estimates are inconsistent.

A consistent heuristic also has to satisfy:

\\[ h(G)=0 \\]

An important relationship:

- Every consistent heuristic is admissible, assuming \\(h(G)=0\\) and non-negative edge costs.
- An admissible heuristic does not necessarily have to be consistent.

Why should we care about consistency?

With a consistent heuristic, once we remove a node from the priority queue for expansion, its best path cost is final. We don't need to reopen that node later.

With an admissible but inconsistent heuristic, we may need to revisit and re-expand a node if a cheaper route to it is discovered.

The Java implementation below supports those revisits.

For many common problems, such as ordinary grid pathfinding with Manhattan or octile distance chosen correctly, the heuristic is consistent.

# **9. Is A\* just Dijkstra with an additional estimate?**

Yes. This is a particularly useful way to understand the relationship.

Consider what happens when we choose:

\\[ h(n)=0 \\]

for every node.

Then:

\\[ f(n)=g(n)+0 \\]

Therefore:

\\[ f(n)=g(n) \\]

And what does Dijkstra use to prioritize nodes?

Exactly that: the cost from the start.

So:

\\[ \boxed{\text{Dijkstra is A\* with } h(n)=0} \\]

This is a very important conceptual connection.

A\* is a generalization of Dijkstra's algorithm.

Dijkstra has no directional information.

A\* uses a heuristic to guide the search towards the goal.

It is not that you need to learn two completely unrelated algorithms.

You can understand A\* as Dijkstra with additional knowledge about the destination.

# **10. A\* versus Greedy Best-First Search**

There is another algorithm that looks similar to A\*.

It is called **Greedy Best-First Search**.

It uses only the heuristic:

\\[ f(n)=h(n) \\]

It ignores the cost already spent.

Let's compare all three.

| Algorithm         | Priority        | What does it consider?                        |
| ----------------- | --------------- | --------------------------------------------- |
| Dijkstra          | \\(g(n)\\)      | Cost from start                               |
| Greedy Best-First | \\(h(n)\\)      | Estimated remaining cost                      |
| A\*               | \\(g(n)+h(n)\\) | Cost already spent + estimated remaining cost |

Why is ignoring g(n) dangerous?

Imagine:

```
                  A -------- G
                 /            /
                /             /
               S             /
                \           /
                 \         /
                  B ------ G
```

Suppose:

- Reaching A costs 100.
- Reaching G from A costs 1.
- Reaching B costs 2.
- Reaching G from B costs 10.

The actual total costs are:

```
S → A → G = 101

S → B → G = 12
```

Greedy Best-First Search could choose A if its heuristic estimates that A is very close to G.

It might find the route with cost 101 even though the route through B costs only 12.

Why?

Because it ignores the cost already spent.

A\* avoids this problem by considering both.

This is why A\* is often described as a balance between:

- Dijkstra: cost already travelled.
- Greedy search: estimated cost remaining.

# **11. How to implement A\* in Java**

Now that we understand the idea, the implementation should look natural.

We'll implement A\* for a general weighted graph.

Assumptions:

- The graph is represented using an adjacency list.
- Every edge has a non-negative cost.
- The heuristic is admissible.
- The heuristic for the goal is zero.
- We want the shortest path from `start` to `goal`.

We'll use:

- `PriorityQueue` to select the most promising node.
- `dist[]` to remember the cheapest known cost from the start.
- `parent[]` to reconstruct the path.
- `heuristic[]` to estimate the remaining cost.

## **11.1 Data structures**

First, define an edge:

```
record Edge(int to, long cost) {}
```

A node in the priority queue needs to store:

```
record State(int node, long g, long f) {}
```

Here:

- `node` is the current node.
- `g` is the actual cost from the start.
- `f` is the priority, calculated as `g + h`.

Why store `g` inside the queue?

Because the priority queue may contain outdated entries.

We'll understand that shortly.

## **11.2 Complete implementation**

```

import java.util.*;

public class AStar {

    record Edge(int to, long cost) {}

    record State(int node, long g, long f) {}

    record PathResult(List<Integer> path, long cost) {}

    public static PathResult findShortestPath(
            List<List<Edge>> graph,
            int start,
            int goal,
            long[] heuristic
    ) {
        int n = graph.size();

        if (heuristic.length != n) {
            throw new IllegalArgumentException(
                "Heuristic size must match the number of nodes."
            );
        }

        if (start < 0 || start >= n || goal < 0 || goal >= n) {
            throw new IllegalArgumentException("Invalid start or goal.");
        }

        // Best known actual cost from start to each node.
        long[] dist = new long[n];
        Arrays.fill(dist, Long.MAX_VALUE);

        // Used to reconstruct the final path.
        int[] parent = new int[n];
        Arrays.fill(parent, -1);

        // Lowest f = g + h gets processed first.
        PriorityQueue<State> pq = new PriorityQueue<>(
            Comparator.comparingLong(State::f)
                      .thenComparingLong(State::g)
        );

        dist[start] = 0;

        pq.offer(new State(
            start,
            0,
            heuristic[start]
        ));

        while (!pq.isEmpty()) {

            State current = pq.poll();

            int u = current.node();
            long currentG = current.g();

            // Ignore outdated queue entries.
            if (currentG != dist[u]) {
                continue;
            }

            // The goal is optimal when removed from the queue.
            if (u == goal) {
                return new PathResult(
                    reconstructPath(parent, goal),
                    dist[goal]
                );
            }

            // Explore all neighbours.
            for (Edge edge : graph.get(u)) {

                int v = edge.to();
                long newG = currentG + edge.cost();

                // A cheaper path to v has been found.
                if (newG < dist[v]) {

                    dist[v] = newG;
                    parent[v] = u;

                    long newF = newG + heuristic[v];

                    pq.offer(new State(v, newG, newF));
                }
            }
        }

        // Destination cannot be reached.
        return new PathResult(List.of(), -1);
    }

    private static List<Integer> reconstructPath(
            int[] parent,
            int goal
    ) {
        List<Integer> path = new ArrayList<>();

        int current = goal;

        while (current != -1) {
            path.add(current);
            current = parent[current];
        }

        Collections.reverse(path);

        return path;
    }
}

```

This implementation uses Java records and a standard priority queue.

Let's understand why each important part exists.

## **11.3 Why do we need&#x20;**`dist[]`**?**

```
long[] dist = new long[n];
Arrays.fill(dist, Long.MAX_VALUE);
```

This stores the cheapest known cost from the start to each node.

For example:

```
dist[A] = 5
dist[B] = 12
dist[C] = 8
```

Suppose we discover a new path to B that costs 9.

We update:

```
if (newG < dist[v]) {
    dist[v] = newG;
}
```

Why?

Because we have found a better route to B.

This is the same relaxation concept used by Dijkstra.

*A still needs to maintain the actual shortest-known cost to every node.*\*

The heuristic does not replace this information.

## **11.4 Why do we use&#x20;**`PriorityQueue`**?**

```
PriorityQueue<State> pq = new PriorityQueue<>(
    Comparator.comparingLong(State::f)
);
```

We always want to process the node with the smallest estimated total cost.

Remember:

```
f = g + h
```

The queue makes that selection efficient.

For a binary heap, inserting and removing an element usually takes \\(O(\log V)\\) when the heap contains \\(O(V)\\) elements, although this implementation can temporarily hold duplicate entries.

## **11.5 Why can the same node appear multiple times in the queue?**

This is an important implementation detail.

Imagine we discover two paths to node C:

```
S → A → C

Cost = 10
```

Later, we discover:

```
S → B → C

Cost = 6
```

Our first queue entry for C is no longer useful.

The queue might contain:

```
C, g=10, f=15
C, g=6,  f=11
```

We don't need to search the priority queue for the old C entry and remove it.

Instead, we insert the better entry and ignore the outdated one when it is eventually removed.

That's why we have:

```
if (currentG != dist[u]) {
    continue;
}
```

This check means:

> Is this queue entry still representing the cheapest known path to this node?

If not, ignore it.

This technique is commonly used when implementing Dijkstra with a priority queue too.

## **11.6 Why don't we maintain a permanent&#x20;**`visited[]`**&#x20;array?**

You may have seen Dijkstra implementations that mark nodes as visited.

For A\*, a permanent visited set is safe when the heuristic is consistent.

But an admissible heuristic can be inconsistent.

In that case, a cheaper path to a previously expanded node may be discovered later.

The implementation above allows that node to be added to the queue again.

The `dist[]` comparison prevents unnecessary processing of outdated entries.

This is a useful general-purpose approach when you don't want to rely on heuristic consistency.

## **11.7 Why can we stop when the goal is removed from the queue?**

This is another crucial detail.

We don't stop just because we discover the goal.

We stop when the goal is removed from the priority queue as the current best entry.

Why?

Because finding a path to the goal does not prove that it's the cheapest path.

There might still be another promising path that leads to a cheaper solution.

When the heuristic is admissible, and the implementation allows nodes to be reopened when a better path is discovered, removing the goal from the queue establishes that its cost is optimal.

# **12. Why is A\* optimal? Build the intuition**

This is worth understanding because it explains why we can trust the algorithm.

Suppose the optimal route costs 20.

Now imagine that A\* is currently considering some node N that lies along that optimal route.

The actual remaining cost from N to the goal might be 12.

The cost already spent to reach N might be 8.

So the actual complete cost through N is:

\\[ 8 + 12 = 20 \\]

Because our heuristic is admissible, it cannot overestimate the actual remaining cost:

\\[ h(N) \leq 12 \\]

Therefore:

\\[ f(N) = g(N) + h(N) \leq 8+12 \\]

\\[ f(N) \leq 20 \\]

Now imagine A\* has found a route to the goal that costs 25.

For the goal:

\\[ f(G) = g(G) + h(G) \\]

Since \\(h(G)=0\\):

\\[ f(G)=25 \\]

Could A\* remove this goal from the priority queue while a cheaper solution still exists?

No.

There would still be some node on the optimal route with an estimated total cost no greater than 20.

A\* would have to process that lower-priority node first.

Eventually, it discovers and processes the optimal route before accepting the goal at cost 25.

That's the intuition behind the optimality guarantee.

The important ingredients are:

- A heuristic that doesn't overestimate.
- Non-negative edge costs.
- Reopening nodes when a better path is discovered, unless consistency makes reopening unnecessary.
- Checking the goal when it is removed from the priority queue, not when it is first discovered.

# **13. When is A\* faster than Dijkstra?**

The quality of the heuristic makes a huge difference.

Let's consider three situations.

### **Situation 1: Very good heuristic**

Suppose the actual remaining distance is 20.

Our heuristic estimates 19.

That's excellent.

A\* has a strong indication of which nodes are promising.

It can avoid exploring many unrelated parts of the graph.

### **Situation 2: Weak heuristic**

Suppose the actual remaining distance is 20.

Our heuristic estimates 2.

This is still admissible.

But it doesn't provide much information.

A\* may explore many unnecessary nodes.

It is still correct, but the performance advantage can be small.

### **Situation 3: No useful heuristic**

Suppose we use:

```
heuristic[node] = 0;
```

Then:

```
f = g
```

A\* behaves like Dijkstra.

No search guidance is being provided.

This gives us a useful rule:

*The closer your admissible heuristic is to the actual remaining cost, the more effectively A can usually guide the search.*\*

There is an ideal heuristic:

\\[ h(n)=h^\*(n) \\]

That means the heuristic knows the exact cheapest remaining cost.

This is called a perfect heuristic.

It provides the strongest possible guidance while preserving optimality.

Of course, calculating the exact remaining cost can be just as difficult as solving the original problem. That's why we use simpler estimates.

# **14. Time and space complexity**

You may see different complexity statements for A\*, depending on whether the discussion assumes a finite graph, a tree search, or a particular heuristic.

For a graph represented using an adjacency list and a binary heap:

| Algorithm | Typical finite-graph worst-case time                                                        | Space                                |
| --------- | ------------------------------------------------------------------------------------------- | ------------------------------------ |
| BFS       | \\(O(V+E)\\)                                                                                | \\(O(V)\\)                           |
| Dijkstra  | \\(O((V+E)\log V)\\)                                                                        | \\(O(V+E)\\)                         |
| A\*       | Can explore the entire graph; heap-based implementation has Dijkstra-like worst-case bounds | \\(O(V+E)\\) for this implementation |

A\* is not guaranteed to have a better worst-case asymptotic complexity than Dijkstra on a finite graph.

Its practical advantage is that a useful heuristic can dramatically reduce how many nodes it expands.

You'll also see the classic AI search complexity analysis:

- \\(b\\) = average branching factor.
- \\(d\\) = depth of the optimal solution.

In a tree-search setting, A\* can have exponential time and space requirements, often described in terms of \\(O(b^d)\\) in the worst case.

This highlights another important fact:

*A can be memory-intensive.*\*

It maintains discovered nodes in its frontier and stores information required to reconstruct the path.

For large navigation problems, this can become a limitation.

# **15. When should you use BFS, Dijkstra, or A\*?**

This is what matters when solving actual problems.

| Problem                                                                             | Recommended algorithm                                      | Why                                                           |
| ----------------------------------------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------- |
| Unweighted graph, shortest number of edges                                          | BFS                                                        | Every edge has equal cost                                     |
| Weighted graph, non-negative edges, any destination or many destinations            | Dijkstra                                                   | Finds shortest paths without a heuristic                      |
| Weighted graph, non-negative edges, known destination, useful lower-bound heuristic | A\*                                                        | Uses destination information to guide the search              |
| Weighted graph with negative edges                                                  | Bellman-Ford (or another suitable negative-edge algorithm) | Dijkstra and standard A\* assumptions don't hold              |
| Grid pathfinding with obstacles                                                     | A\*                                                        | Manhattan, Chebyshev, or octile heuristics can guide movement |

Some practical applications:

**1. Maps and navigation**

Find a route from your current location to a destination. Straight-line distance can guide the search.

**2. Game development**

Find paths for characters moving through a map. Grid-based movement and obstacles make A\* particularly useful.

**3. Robotics**

Find a route through a physical environment, accounting for obstacles and movement costs.

**4. Puzzle solving**

Find the shortest sequence of moves needed to solve a puzzle. For example, a heuristic for the 8-puzzle can count how many tiles are not in their goal positions.

**5. Network routing**

Find a low-cost route between network locations when a useful lower-bound estimate is available.

# **16. Common mistakes when implementing A\***

These are worth remembering because they are more likely to cause bugs than the formula itself.

| Mistake                                                  | Why it is wrong                                                             |
| -------------------------------------------------------- | --------------------------------------------------------------------------- |
| Using only `h(n)`                                        | That becomes Greedy Best-First Search; it can ignore the cost already spent |
| Using only `g(n)`                                        | That becomes Dijkstra                                                       |
| Using an overestimating heuristic                        | Optimality is no longer guaranteed                                          |
| Using a heuristic with incorrect units                   | The sum of `g` and `h` becomes meaningless                                  |
| Stopping when the goal is first discovered               | A cheaper path may still exist                                              |
| Never allowing nodes to be revisited with a better path  | Can break correctness with inconsistent heuristics                          |
| Using Manhattan distance when diagonal moves are cheaper | The heuristic may overestimate                                              |
| Using negative edge costs                                | Standard A\* assumptions do not hold                                        |

One additional distinction:

You may encounter **Weighted A**\*, which uses:

\\[ f(n)=g(n)+w\cdot h(n) \\]

where \\(w>1\\).

This makes the algorithm more aggressive about moving towards the destination.

It can find a solution faster, but it no longer has the ordinary A\* guarantee of finding the exact optimal path. Some variants provide bounded-suboptimality guarantees under specific assumptions.

# **17. The mental model to take into interviews and real problems**

Forget the implementation for a moment.

Imagine you're finding a route to a destination.

You have two competing strategies:

**Strategy A:**

Explore the cheapest place to reach from where you started.

This is Dijkstra.

**Strategy B:**

Explore the place that looks most promising when considering both the cost already spent and the estimated remaining cost.

This is A\*.

The second strategy works well because you have additional information: you know where you want to go.

That's all A\* is doing.

The implementation follows naturally:

1. Maintain the cheapest known cost from the start to each node.
2. Estimate the remaining cost from each node to the destination.
3. Put discovered nodes into a priority queue ordered by `g + h`.
4. Explore the most promising node.
5. Update neighbours when you discover cheaper paths.
6. Stop when the destination is removed from the queue as the current best entry.

And remember the relationship:

\\[ \boxed{ \begin{aligned} \text{Dijkstra:} && f(n)&=g(n)\\\ \text{Greedy:} && f(n)&=h(n)\\\ \text{A\*:} && f(n)&=g(n)+h(n) \end{aligned} } \\]
