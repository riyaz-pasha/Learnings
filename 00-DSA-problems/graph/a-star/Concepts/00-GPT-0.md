# **A\* (A-Star) Algorithm — Understand It So You Never Have to Memorise It**

The easiest way to understand A\* is to forget the algorithm for a moment and imagine that you are navigating through a city.

You are at point **S**, and you want to reach destination **G**.

You have two pieces of information:

1. **How far have I already travelled?**
2. **How far do I think I still need to travel?**

A\* combines these two pieces of information to decide which direction to explore next.

That is essentially the entire idea behind A\*.

\\[ \boxed{f(n)=g(n)+h(n)} \\]

Where:

- \\(g(n)\\) = actual cost from the starting point to node \\(n\\).
- \\(h(n)\\) = estimated cost from node \\(n\\) to the destination.
- \\(f(n)\\) = estimated total cost of a path going through node \\(n\\).

A\* always prioritises the node with the smallest \\(f(n)\\).

But there is a lot of important reasoning hidden behind this simple formula:

- Why do we need the heuristic?
- Why does it make Dijkstra's algorithm more efficient?
- How do we calculate a heuristic?
- Why must some heuristics never overestimate?
- How do we choose Manhattan, Euclidean, or other heuristics?
- How do we implement A\* correctly?
- When should we use A\* instead of Dijkstra, BFS, or something else?

Let's derive everything from the beginning.

# **1. First understand the problem Dijkstra solves**

Suppose we have this graph:

```

        2
   S -------- A
   |           |
 1 |           | 5
   |           |
   B ---- C --- G
       2     2

```

The edges are:

| Edge  | Cost |
| ----- | ---- |
| S → A | 2    |
| S → B | 1    |
| A → G | 5    |
| B → C | 2    |
| C → G | 2    |

We want to find the cheapest path from `S` to `G`.

There are two possible routes:

**Route 1:**

\\[ S \rightarrow A \rightarrow G \\]

Cost:

\\[ 2+5=7 \\]

**Route 2:**

\\[ S \rightarrow B \rightarrow C \rightarrow G \\]

Cost:

\\[ 1+2+2=5 \\]

The optimal path is:

\\[ \boxed{S \rightarrow B \rightarrow C \rightarrow G} \\]

## **How does Dijkstra solve it?**

Dijkstra maintains a priority queue.

It prioritises nodes based on their known cost from the starting node.

In other words:

\\[ Priority(n)=g(n) \\]

Let's execute it.

**Step 1: Start at S**

Initially:

| Node | Cost from S |
| ---- | ----------- |
| S    | 0           |
| A    | ∞           |
| B    | ∞           |
| C    | ∞           |
| G    | ∞           |

Explore `S`.

We discover:

- A costs 2.
- B costs 1.

Priority queue:

| Node | Cost |
| ---- | ---- |
| B    | 1    |
| A    | 2    |

**Step 2: Explore B**

B has the smallest cost.

From B, we discover C.

\\[ g(C)=g(B)+2=1+2=3 \\]

Priority queue:

| Node | Cost |
| ---- | ---- |
| A    | 2    |
| C    | 3    |

**Step 3: Explore A**

A has the smallest cost.

From A, we discover G.

\\[ g(G)=2+5=7 \\]

Priority queue:

| Node | Cost |
| ---- | ---- |
| C    | 3    |
| G    | 7    |

**Step 4: Explore C**

From C, we discover another path to G.

\\[ g(G)=3+2=5 \\]

This is better than the previously discovered cost of 7.

So we update G.

Priority queue:

| Node | Cost |
| ---- | ---- |
| G    | 5    |

**Step 5: Explore G**

We have reached our destination with the optimal cost of 5.

Done.

## **But what is the problem?**

Look at what Dijkstra did.

It explored `A`, even though the route through A was not useful for reaching our destination optimally.

Why did it explore A?

Because Dijkstra only knows:

> How cheaply can I reach this node from the starting point?

It does not know:

> Does this node seem to take me closer to my destination?

Dijkstra has no concept of direction towards the destination.

It explores based on accumulated cost, not estimated remaining distance.

This is where A\* improves the search.

# **2. The intuition behind A\***

Imagine you are driving to a destination.

You have two possible roads.

- Road A: You have travelled 2 km, but your destination is probably another 20 km away.
- Road B: You have travelled 5 km, but your destination is probably another 3 km away.

Which road looks more promising?

Road B.

Why?

Because your estimated total journey through B is:

\\[ 5+3=8 \\]

Your estimated total journey through A is:

\\[ 2+20=22 \\]

Even though you have travelled further through B, the total journey looks much shorter.

*This is exactly what A does.*\*

Instead of considering only how much we have travelled, it also estimates how much distance remains.

\\[ \boxed{f(n)=g(n)+h(n)} \\]

Let's understand each component carefully.

## **2.1 Actual cost — g(n)**

This is the same information Dijkstra uses.

It represents the cost of the best-known path from the starting node to the current node.

For example:

\\[ S \rightarrow B \rightarrow C \\]

If:

- S → B costs 1.
- B → C costs 2.

Then:

\\[ g(C)=1+2=3 \\]

This is not an estimate. It is the actual accumulated path cost.

## **2.2 Estimated remaining cost — h(n)**

This is the new information.

It estimates how expensive it would be to travel from the current node to the goal.

For example:

Suppose we are currently at C.

We estimate that reaching G from C costs 2.

Then:

\\[ h(C)=2 \\]

Important: This is an estimate. It does not have to be the exact remaining cost.

We will discuss how to calculate this estimate and what makes a good estimate later.

## **2.3 Estimated total cost — f(n)**

Now combine both.

\\[ f(n)=g(n)+h(n) \\]

For C:

\\[ f(C)=3+2=5 \\]

This tells us:

> The estimated total cost of reaching G through C is 5.

A\* puts nodes in its priority queue based on this value.

The smallest `f` gets explored first.

# **3. See exactly how A\* avoids unnecessary exploration**

Let's reuse our graph.

Actual edges:

- S → A = 2
- S → B = 1
- A → G = 5
- B → C = 2
- C → G = 2

Suppose we have the following heuristics:

| Node | Estimated remaining cost h(n) |
| ---- | ----------------------------- |
| S    | 5                             |
| A    | 5                             |
| B    | 4                             |
| C    | 2                             |
| G    | 0                             |

These estimates are reasonable because they do not overestimate the actual cheapest remaining cost.

Now execute A\*.

### **Step 1: Start at S**

Initially:

\\[ g(S)=0 \\]

\\[ h(S)=5 \\]

\\[ f(S)=0+5=5 \\]

We explore S and discover A and B.

For A:

\\[ g(A)=2 \\]

\\[ f(A)=2+5=7 \\]

For B:

\\[ g(B)=1 \\]

\\[ f(B)=1+4=5 \\]

Priority queue:

| Node | g(n) | h(n) | f(n)  |
| ---- | ---- | ---- | ----- |
| B    | 1    | 4    | **5** |
| A    | 2    | 5    | 7     |

Which node should we explore?

B.

Why?

Because the estimated total cost of reaching the destination through B is lower.

### **Step 2: Explore B**

From B, we discover C.

\\[ g(C)=g(B)+2=1+2=3 \\]

\\[ f(C)=3+2=5 \\]

Priority queue:

| Node | g(n) | h(n) | f(n)  |
| ---- | ---- | ---- | ----- |
| C    | 3    | 2    | **5** |
| A    | 2    | 5    | 7     |

Explore C.

### **Step 3: Explore C**

From C, we discover G.

\\[ g(G)=3+2=5 \\]

\\[ h(G)=0 \\]

\\[ f(G)=5+0=5 \\]

Priority queue:

| Node | g(n) | h(n) | f(n)  |
| ---- | ---- | ---- | ----- |
| G    | 5    | 0    | **5** |
| A    | 2    | 5    | 7     |

Explore G.

We have reached the destination with cost 5.

**Notice what happened.**

A\* never needed to explore A.

Dijkstra explored A because its accumulated cost was relatively small.

A\* avoided A because its estimated total cost was higher.

This is the key difference.

| Dijkstra                               | A\*                                                          |
| -------------------------------------- | ------------------------------------------------------------ |
| Prioritises smallest `g(n)`            | Prioritises smallest `g(n) + h(n)`                           |
| Considers cost already travelled       | Considers cost travelled and estimated remaining             |
| No destination-directed guidance       | Uses a heuristic to guide towards the destination            |
| Can explore many irrelevant directions | Often avoids directions unlikely to lead to the goal cheaply |

A\* is not magically faster in every situation. It is faster when the heuristic provides useful guidance.

# **4. What exactly is a heuristic?**

This is probably the most important concept to understand.

A **heuristic is a function that estimates the remaining cost from a given state to the goal.**

Mathematically:

\\[ h(n)\approx Cost(n,Goal) \\]

Think of it as answering:

> From where I am currently standing, what is the minimum amount of work or cost I expect to need to reach the destination?

For example, imagine a map.



You are at point A, and your destination is point G.

You could estimate the remaining distance by drawing a straight line between A and G.

That straight-line distance gives you a quick approximation of the remaining journey.

But the actual road might:

- Go around buildings.
- Go around rivers.
- Follow roads instead of straight lines.
- Have traffic restrictions.

So the real route might be longer.

Nevertheless, the straight-line distance gives us useful information.

It tells us which locations are geographically closer to our destination.

That is a heuristic.

## **A heuristic does not have to know the actual answer**

This is important.

Suppose the actual cheapest cost from A to G is 15.

A heuristic might return:

\\[ h(A)=10 \\]

This is an estimate.

We don't need to calculate the exact shortest path from every node to G just to run A\*.

Doing that would defeat the purpose of A\*.

We need a relatively cheap function that provides useful guidance.

## **Why is the heuristic so important?**

Imagine these three situations.

| Heuristic quality   | What A\* does                                       |
| ------------------- | --------------------------------------------------- |
| Very weak heuristic | Behaves similarly to Dijkstra                       |
| Good heuristic      | Explores fewer irrelevant nodes                     |
| Exact heuristic     | Gets very direct guidance towards the optimal route |

However, there is a catch.

If we want A\* to guarantee the optimal answer, our heuristic must obey certain mathematical properties.

Let's understand those.

# **5. Admissible heuristic — the most important rule**

Suppose the actual cheapest remaining cost from a node to the destination is 10.

Which estimates are acceptable?

| Estimated cost | Acceptable? |
| -------------- | ----------- |
| 5              | Yes         |
| 7              | Yes         |
| 9              | Yes         |
| 10             | Yes         |
| 11             | No          |
| 20             | No          |

Why?

Because if the heuristic overestimates the remaining cost, A\* might incorrectly reject a route that is actually optimal.

The rule is:

\\[ \boxed{h(n)\leq h^\*(n)} \\]

Where:

- \\(h(n)\\) is the heuristic estimate.
- \\(h^\*(n)\\) is the actual optimal remaining cost.

A heuristic that never overestimates the true cheapest remaining cost is called an **admissible heuristic**.

In simpler language:

> An admissible heuristic is optimistic. It may underestimate the remaining cost, but it must never claim that the remaining cost is higher than it really is.

Also:

\\[ h(Goal)=0 \\]

The actual remaining cost when we are already at the goal is zero.

## **Why does overestimating cause problems?**

Consider two possible routes:

| Route   | Actual total cost | Estimated cost |
| ------- | ----------------- | -------------- |
| Route A | 10                | 20             |
| Route B | 15                | 15             |

Suppose we use an overestimating heuristic that makes Route A look expensive.

A\* might prefer Route B and return a path with cost 15, even though the optimal path costs only 10.

The algorithm has been misled.

An admissible heuristic prevents this problem.

### **Important distinction**

An admissible heuristic does not need to be accurate.

It only needs to be a lower bound.

For example, if the actual remaining cost is 100, both 10 and 90 are admissible.

But 90 is usually more useful because it gives A\* better guidance.

This leads to an important principle:

**Among admissible heuristics, stronger lower bounds are generally better.**

A stronger heuristic estimates the remaining cost more closely without exceeding it.

# **6. Consistent heuristic — another important property**

You will often hear about two types of heuristics:

1. Admissible.
2. Consistent (also called monotone).

They are related, but they are not the same thing.

A heuristic is consistent if, for every edge from node \\(n\\) to its neighbour \\(n'\\):

\\[ \boxed{h(n)\leq c(n,n')+h(n')} \\]

Where \\(c(n,n')\\) is the cost of travelling from \\(n\\) to \\(n'\\).

Let's understand why this rule exists.

Imagine you are at A.

Your estimated remaining cost is 10.

There is an edge from A to B costing 3.

Suppose your estimate at B is 5.

Then:

\\[ 10\leq3+5 \\]

\\[ 10\leq8 \\]

This is false.

What does that mean?

Your heuristic claims that:

- From A, the remaining journey costs at most 10.
- But after moving to B for 3, only 5 remains.

The estimate suddenly dropped by 5, even though you only paid 3 to move.

This violates consistency.

A consistent heuristic follows the triangle inequality: the estimated cost from the current node cannot be greater than the cost of taking one edge plus the estimate from its neighbour.

## **Why do we care about consistency?**

Consistency gives A\* an important property:

\\[ f(n')\geq f(n) \\]

For an edge from \\(n\\) to \\(n'\\), assuming we follow the same path:

\\[ \begin{aligned} f(n') &= g(n')+h(n')\\\ &=g(n)+c(n,n')+h(n')\\\ &\geq g(n)+h(n)\\\ &=f(n) \end{aligned} \\]

So the `f` value never decreases as we move along a path.

This makes graph-search implementations simpler.

With a consistent heuristic, once a node is removed from the priority queue with its best known cost, we do not need to reopen it later.

With an admissible but inconsistent heuristic, a node may need to be reopened if a better route is discovered.

**Practical rule:**

- Admissible heuristic + proper node reopening: A\* can guarantee an optimal path.
- Consistent heuristic: A\* can guarantee an optimal path and avoid reopening already-finalised nodes.

Most common grid heuristics, such as Manhattan and Euclidean distance under their appropriate movement assumptions, are consistent.

# **7. Different types of heuristics — and when to use them**

Now we reach the practical part.

How do you actually calculate `h(n)`?

The answer depends on the problem.

There is no single heuristic formula that works for every problem.

You must understand the movement rules, costs, and goal condition.

Let's look at the most important heuristics.

## **7.1 Manhattan Distance**

Used when movement is allowed only in four directions:

- Up
- Down
- Left
- Right

Imagine a grid:

```

S . . . .
. . . . .
. . . . .
. . . . G

```

Suppose:

- Starting point = (0, 0)
- Goal = (3, 4)

You can move horizontally or vertically, but not diagonally.

How many minimum steps are required?

Horizontal difference:

\\[ |4-0|=4 \\]

Vertical difference:

\\[ |3-0|=3 \\]

Total:

\\[ 4+3=7 \\]

So:

\\[ \boxed{h(n)=|x_1-x_2|+|y_1-y_2|} \\]

This is Manhattan distance.

### **Why is it correct?**

Imagine travelling through a city with perfectly aligned streets.

You cannot travel diagonally through buildings.

You must travel:

- Four streets horizontally.
- Three streets vertically.

Therefore, at least seven steps are required.

Obstacles may force you to travel even further, but they cannot make the minimum journey shorter than seven steps.

That is why Manhattan distance is a useful lower bound.

### **Java implementation**

```
static int manhattan(int x1, int y1, int x2, int y2) {
    return Math.abs(x1 - x2) + Math.abs(y1 - y2);
}
```

### **When should you use it?**

Use Manhattan distance when:

- Movement is restricted to four directions.
- Every horizontal and vertical movement has equal cost.
- There are obstacles, but no diagonal shortcuts.
- You need a lower-bound estimate.

For example:

- Grid pathfinding.
- Warehouse robots moving along grid aisles.
- Board-game movement with four-direction movement.

## **7.2 Euclidean Distance**

Now imagine you can move in any direction.

You are not restricted to horizontal and vertical movement.

You can travel diagonally or along any angle.

Then the shortest possible distance between two points is a straight line.

By Pythagoras:

\\[ \boxed{h(n)=\sqrt{(x_1-x_2)^2+(y_1-y_2)^2}} \\]

Example:

Starting point:

\\[ (0,0) \\]

Goal:

\\[ (3,4) \\]

Then:

\\[ h(n)=\sqrt{3^2+4^2} \\]

\\[ =\sqrt{9+16} \\]

\\[ =\sqrt{25}=5 \\]

The straight-line distance is 5.

### **Java implementation**

```
static double euclidean(int x1, int y1, int x2, int y2) {
    int dx = x1 - x2;
    int dy = y1 - y2;

    return Math.sqrt(dx * dx + dy * dy);
}
```

### **When should you use it?**

Use Euclidean distance when:

- Movement can happen in any direction.
- The movement cost corresponds to physical distance.
- Straight-line distance is a valid lower bound on the actual travel cost.

Examples:

- Robot navigation.
- Continuous 2D navigation.
- Geometric pathfinding.
- Certain map and spatial problems.

**Important:** Euclidean distance is not automatically valid for every grid.

For example, suppose a diagonal move costs 1, while the Euclidean distance of that diagonal is \\(\sqrt{2}\\).

Euclidean distance would overestimate the cost of that move.

That would violate admissibility.

Always check your movement costs before selecting the formula.

## **7.3 Chebyshev Distance**

What happens when diagonal movement is allowed, but diagonal movement costs exactly the same as horizontal or vertical movement?

For example:

- Move up: cost 1.
- Move down: cost 1.
- Move left: cost 1.
- Move right: cost 1.
- Move diagonally: cost 1.

Consider:

Start = (0, 0)

Goal = (3, 4)

You can cover one horizontal and one vertical difference simultaneously with a diagonal move.

The movements can be:

1. Diagonal.
2. Diagonal.
3. Diagonal.
4. Right.

Only four movements are required.

Notice that 4 is simply the larger coordinate difference.

\\[ \boxed{h(n)=\max(|x_1-x_2|,|y_1-y_2|)} \\]

This is called Chebyshev distance.

### **Java implementation**

```
static int chebyshev(int x1, int y1, int x2, int y2) {
    int dx = Math.abs(x1 - x2);
    int dy = Math.abs(y1 - y2);

    return Math.max(dx, dy);
}
```

### **When should you use it?**

Use Chebyshev distance when:

- All eight directions are allowed.
- Diagonal and straight movements have equal cost.

Examples:

- Certain chess-like movement systems.
- Games where diagonal movement costs one unit.
- Eight-direction grid navigation with equal movement costs.

## **7.4 Octile Distance**

This is particularly important in grid pathfinding.

What happens when:

- Horizontal movement costs 1.
- Vertical movement costs 1.
- Diagonal movement costs \\(\sqrt{2}\\).

This is common in games and pathfinding systems.

A diagonal movement covers both horizontal and vertical distance simultaneously, but its cost is slightly higher than a straight movement.

Using Manhattan distance would overestimate the actual cost because diagonal movement is cheaper than taking two separate straight moves.

Using Euclidean distance may be admissible, but it is not always the strongest lower bound for this movement model.

We can calculate the exact shortest distance in an obstacle-free eight-direction grid.

Let:

\\[ dx=|x_1-x_2| \\]

\\[ dy=|y_1-y_2| \\]

First, use diagonal movements to cover the difference in both coordinates.

The maximum number of diagonal moves is:

\\[ \min(dx,dy) \\]

Any remaining difference must be covered using straight movements.

Therefore:

\\[ \boxed{ h(n)=D\cdot(\max(dx,dy)-\min(dx,dy)) +D_2\cdot\min(dx,dy) } \\]

Where:

- \\(D\\) = cost of a straight movement.
- \\(D_2\\) = cost of a diagonal movement.

For the common case:

\\[ D=1,\quad D_2=\sqrt{2} \\]

Suppose:

\\[ dx=4,\quad dy=3 \\]

We need:

- 3 diagonal moves.
- 1 straight move.

Cost:

\\[ 3\sqrt{2}+1 \\]

\\[ \approx5.24 \\]

### **Java implementation**

```
static double octile(int x1, int y1, int x2, int y2) {
    int dx = Math.abs(x1 - x2);
    int dy = Math.abs(y1 - y2);

    int min = Math.min(dx, dy);
    int max = Math.max(dx, dy);

    double D = 1.0;
    double D2 = Math.sqrt(2);

    return D * (max - min) + D2 * min;
}
```

This standard formula assumes that diagonal movement is not cheaper than a straight movement and does not cost more than two straight movements:

\\[ D\leq D_2\leq2D \\]

### **When should you use it?**

Use octile distance when:

- Eight-direction movement is allowed.
- Diagonal movement costs approximately \\(\sqrt{2}\\) times straight movement.
- You are implementing grid-based pathfinding.

# **8. Comparing the common grid heuristics**

Let's put everything together.

| Movement rules                                                        | Suitable heuristic | Formula                                 |
| --------------------------------------------------------------------- | ------------------ | --------------------------------------- |
| Four directions, equal costs                                          | Manhattan          | \\(\|dx\|+\|dy\|\\)                     |
| Eight directions, diagonal cost equals straight cost                  | Chebyshev          | \\(\max(dx,dy)\\)                       |
| Eight directions, diagonal cost is \\(\sqrt{2}\\) times straight cost | Octile             | \\(\max(dx,dy)+(\sqrt2-1)\min(dx,dy)\\) |
| Any-angle movement, cost proportional to distance                     | Euclidean          | \\(\sqrt{dx^2+dy^2}\\)                  |

This table is something you can derive rather than memorise.

Ask yourself:

1. What movements are allowed?
2. How much does each movement cost?
3. How can I cover the coordinate differences with the minimum possible cost?
4. Can obstacles or other constraints only increase that cost?

The last question is particularly important.

A heuristic should estimate a lower bound on the remaining cost, not necessarily calculate the actual path.

# **9. What about weighted graphs and different movement costs?**

So far, we assumed that each movement had a fixed cost.

Real systems are often more complicated.

For example, imagine a grid where:

| Terrain | Movement cost |
| ------- | ------------- |
| Road    | 1             |
| Grass   | 3             |
| Mud     | 5             |
| Water   | 10            |

Now Manhattan distance alone might not give a meaningful cost estimate.

Suppose you need at least 5 movements to reach the destination.

Every movement costs at least 1.

Therefore:

\\[ h(n)=ManhattanDistance(n,Goal)\times1 \\]

This is still admissible.

Why?

Because even if every remaining move uses the cheapest possible terrain, the route cannot cost less than that value.

More generally:

\\[ \boxed{h(n)=GeometricLowerBound(n,Goal)\times MinimumCostPerUnit} \\]

The important idea is:

**Use the cheapest possible movement cost when calculating your lower bound.**

Do not use the average terrain cost or the most expensive terrain cost. Either could overestimate the actual remaining cost.

For a graph with arbitrary edge weights, a useful generic approach is to construct a simpler version of the problem by replacing or relaxing constraints and costs in a way that cannot make a solution more expensive.

The shortest distance in this simplified problem is a valid lower bound for the original problem.

We will explore that idea next.

# **10. A more powerful way to design heuristics: Relaxed problems**

The grid formulas are useful, but how do we design heuristics for problems that are not grids?

This is where understanding the concept is more valuable than memorising formulas.

Imagine you have a problem with these restrictions:

- You can move only along certain roads.
- Some roads have restrictions.
- Some movements require extra operations.
- Some states cannot be visited until certain conditions are satisfied.

Finding the exact cheapest path may be difficult.

But what if we temporarily remove some restrictions?

The resulting problem becomes easier.

Its optimal cost can be calculated more easily.

Because we removed restrictions, the simplified problem can never be more expensive than the original problem.

Therefore:

\\[ \boxed{ Cost(RelaxedProblem)\leq Cost(OriginalProblem) } \\]

That gives us an admissible heuristic.

This is one of the most general ways to construct good heuristics.

## **Example: The 8-puzzle problem**

Consider a sliding puzzle.

```

1 2 3
4 5 6
7 _ 8

```

Goal:

```

1 2 3
4 5 6
7 8 _

```

You can move one neighbouring tile into the empty space.

Our objective is to reach the goal configuration using the minimum number of moves.

What heuristic could we use?

### **Heuristic 1: Number of misplaced tiles**

Ignore how the tiles can move.

Just count how many tiles are not in their correct positions.

In our example:

- 1 is correct.
- 2 is correct.
- 3 is correct.
- 4 is correct.
- 5 is correct.
- 6 is correct.
- 7 is correct.
- 8 is misplaced.

Therefore:

\\[ h(n)=1 \\]

Why is this admissible?

Because every misplaced tile must be moved at least once to reach the correct configuration.

So the number of misplaced tiles is a lower bound on the number of required moves.

### **Heuristic 2: Manhattan distance of all tiles**

We can do better.

Instead of counting only incorrectly placed tiles, calculate how far each tile is from its goal position.

For each tile:

\\[ Manhattan(tile)=|currentRow-goalRow|+|currentCol-goalCol| \\]

Add the distances of all tiles, excluding the blank space.

\\[ \boxed{ h(n)=\sum\_{tile} Manhattan(tile) } \\]

Why does this work?

Imagine a tile is three positions away from its destination.

It must move at least three times before reaching its correct position.

The total Manhattan distance gives a lower bound on the total number of moves.

It is generally stronger than simply counting misplaced tiles.

**Notice what we did:**

We relaxed the problem.

We ignored the restriction that tiles must move into the empty space.

We essentially allowed each tile to move independently towards its destination.

That simplified problem is easier to estimate.

Its cost cannot exceed the actual cost of solving the puzzle.

That's why Manhattan distance works.

## **More advanced heuristic: Pattern databases**

For difficult puzzles, even Manhattan distance may be weak.

We can precompute the exact solution costs for an abstraction of the problem.

For example:

- Consider only tiles 1, 2, and 3.
- Ignore the other tiles or represent them as unspecified positions.
- Precompute the minimum number of moves to solve that abstraction.
- Store these values in a lookup table.

During A\*:

\\[ h(n)=PrecomputedAbstractCost(n) \\]

This is called a **pattern database heuristic**.

It can provide much stronger guidance than a simple geometric estimate.

The important idea remains the same:

> Solve an easier version of the original problem and use its optimal cost as a lower bound.

# **11. Other useful heuristic techniques**

Beyond geometric and relaxed-problem heuristics, there are several techniques worth knowing.

| Technique                 | Main idea                                              | Where it is useful                                          |
| ------------------------- | ------------------------------------------------------ | ----------------------------------------------------------- |
| Zero heuristic            | Always return 0                                        | When no useful estimate exists; becomes Dijkstra            |
| Misplaced items           | Count objects not in their destination positions       | Sliding puzzles and arrangement problems                    |
| Manhattan heuristic       | Sum minimum axis-aligned distances                     | Grid movement and sliding puzzles                           |
| Euclidean heuristic       | Use straight-line distance                             | Geometric navigation                                        |
| Octile heuristic          | Account for diagonal movement cost                     | Eight-direction grid navigation                             |
| Landmark heuristic        | Precompute distances to selected important nodes       | Large road networks and graph navigation                    |
| Pattern database          | Precompute exact costs for simplified states           | Puzzles and combinatorial search                            |
| Domain-specific heuristic | Estimate remaining work using knowledge of the problem | Scheduling, planning, games, and other specialised problems |

## **Landmark heuristic — useful for large graphs**

Suppose you have a very large road network.

Computing geometric distances may be insufficient because roads do not always follow straight lines.

You can choose a few important locations called landmarks.

Precompute shortest-path distances between each landmark and other nodes.

For an undirected graph, one useful lower bound is:

\\[ \boxed{ h(v)=\max_L|d(L,Goal)-d(L,v)| } \\]

Here:

- \\(L\\) is a landmark.
- \\(d(L,Goal)\\) is the shortest distance from the landmark to the goal.
- \\(d(L,v)\\) is the shortest distance from the landmark to the current node.

Why is this a lower bound?

By the triangle inequality:

\\[ d(L,Goal)\leq d(L,v)+d(v,Goal) \\]

Rearranging:

\\[ d(v,Goal)\geq d(L,Goal)-d(L,v) \\]

The reverse direction gives the opposite inequality. Combining them:

\\[ d(v,Goal)\geq|d(L,Goal)-d(L,v)| \\]

Taking the maximum over several landmarks gives a stronger lower bound.

This is a more advanced technique often used in large-scale graph search.

For directed graphs, the corresponding formulas must account for edge direction; the absolute-difference formula above should not be applied blindly.

# **12. Can we combine multiple heuristics?**

Yes.

Suppose you have two admissible heuristics:

\\[ h_1(n) \\]

\\[ h_2(n) \\]

You might want to use both.

The safest general-purpose combination is:

\\[ \boxed{h(n)=\max(h_1(n),h_2(n))} \\]

Why?

Both heuristics are guaranteed not to overestimate the actual remaining cost.

Therefore, whichever is larger is still a lower bound.

Example:

| Heuristic             | Estimate |
| --------------------- | -------- |
| h1                    | 5        |
| h2                    | 8        |
| Actual remaining cost | 10       |

Both are valid.

Taking the maximum gives:

\\[ h(n)=8 \\]

This is a stronger estimate without violating admissibility.

### **What about adding them?**

Be careful.

\\[ h(n)=h_1(n)+h_2(n) \\]

This is not automatically admissible.

Why?

Because both heuristics might be counting the same work twice.

For example, in the 8-puzzle:

- Misplaced tiles counts tiles that need to move.
- Manhattan distance counts how far those same tiles need to move.

Adding them could count some required movements multiple times.

However, adding heuristics can be valid when they measure independent portions of the work, or when a mathematical argument guarantees that the costs they count do not overlap.

A common example is additive pattern databases with carefully designed disjoint cost partitions.

**Practical rule:** Use `max()` when combining admissible heuristics unless you have a reason and proof that their costs can safely be added.

# **13. Now derive the A\* algorithm itself**

We understand:

- `g(n)` = actual cost travelled.
- `h(n)` = estimated remaining cost.
- `f(n)` = estimated total cost.

Now how do we implement the algorithm?

Think of it as a small extension of Dijkstra.

Dijkstra already maintains:

1. A priority queue.
2. The best-known cost to reach each node.
3. A way to update a node when a cheaper path is found.
4. A way to recover the shortest path.

A\* uses the same structure.

The only major difference is the priority queue ordering.

Dijkstra:

\\[ Priority=g(n) \\]

A\*:

\\[ \boxed{Priority=g(n)+h(n)} \\]

## **The algorithm**

Maintain the following data structures:

| Data structure     | Purpose                                                 |
| ------------------ | ------------------------------------------------------- |
| Priority Queue     | Stores nodes ordered by smallest `f`                    |
| `gScore`           | Best-known actual cost to reach each node               |
| `parent`           | Stores the previous node so we can reconstruct the path |
| Heuristic function | Estimates remaining cost to the goal                    |

Now follow these steps.

### **Step 1: Initialise the starting node**

Set:

\\[ g(start)=0 \\]

\\[ f(start)=g(start)+h(start) \\]

Insert the starting node into the priority queue.

### **Step 2: Get the most promising node**

Remove the node with the smallest `f` from the priority queue.

### **Step 3: Check whether it is the destination**

If the node is the goal, reconstruct the path using the parent map and return it.

**Important:** Stop when the goal is removed from the priority queue, not merely when it is first discovered.

A discovered goal might still have a cheaper path through another node.

### **Step 4: Explore its neighbours**

For each neighbour:

Calculate the cost of reaching it through the current node.

\\[ tentativeG=g(current)+edgeCost \\]

### **Step 5: Check whether we found a better path**

Compare:

\\[ tentativeG\<g(neighbour) \\]

If true, we found a better route.

Update:

\\[ g(neighbour)=tentativeG \\]

Update its parent:

\\[ parent(neighbour)=current \\]

Calculate:

\\[ f(neighbour)=g(neighbour)+h(neighbour) \\]

Insert the neighbour into the priority queue.

### **Step 6: Repeat**

Continue until:

- The goal is removed from the priority queue, or
- The priority queue becomes empty.

If the queue becomes empty, no path exists.

# **14. Java implementation of A\***

Let's implement a general graph-based A\* algorithm.

This implementation works with:

- Weighted graphs.
- Non-negative edge costs.
- Different heuristic functions.
- Path reconstruction.
- Better paths discovered after a node has already been explored.

The last point matters for admissible but inconsistent heuristics.

Instead of permanently closing nodes, we allow them to be processed again when a better path is discovered.

We also allow duplicate priority-queue entries and ignore outdated ones when they are removed.

## **Complete Java implementation**

```

import java.util.*;
import java.util.function.ToDoubleFunction;

public class AStar {

    static class Edge {
        int to;
        double cost;

        Edge(int to, double cost) {
            this.to = to;
            this.cost = cost;
        }
    }

    static class State {
        int node;
        double g;
        double f;

        State(int node, double g, double f) {
            this.node = node;
            this.g = g;
            this.f = f;
        }
    }

    public static List<Integer> shortestPath(
            Map<Integer, List<Edge>> graph,
            int start,
            int goal,
            ToDoubleFunction<Integer> heuristic
    ) {

        // Best known actual cost from start to each node.
        Map<Integer, Double> gScore = new HashMap<>();

        // Previous node in the best-known path.
        Map<Integer, Integer> parent = new HashMap<>();

        // Prioritise nodes with the smallest f = g + h.
        PriorityQueue<State> open = new PriorityQueue<>(
            Comparator.comparingDouble(state -> state.f)
        );

        gScore.put(start, 0.0);

        double startH = heuristic.applyAsDouble(start);

        open.offer(new State(
            start,
            0.0,
            startH
        ));

        while (!open.isEmpty()) {

            State current = open.poll();

            // Ignore outdated queue entries.
            double bestKnown =
                gScore.getOrDefault(current.node, Double.POSITIVE_INFINITY);

            if (Double.compare(current.g, bestKnown) != 0) {
                continue;
            }

            // Goal has been removed from the priority queue.
            if (current.node == goal) {
                return reconstructPath(parent, start, goal);
            }

            // Explore all neighbours.
            for (Edge edge :
                    graph.getOrDefault(current.node, Collections.emptyList())) {

                if (edge.cost < 0) {
                    throw new IllegalArgumentException(
                        "A* requires non-negative edge costs."
                    );
                }

                int neighbour = edge.to;

                double tentativeG = current.g + edge.cost;

                double oldG = gScore.getOrDefault(
                    neighbour,
                    Double.POSITIVE_INFINITY
                );

                // We found a better route.
                if (tentativeG < oldG) {

                    gScore.put(neighbour, tentativeG);

                    parent.put(neighbour, current.node);

                    double h = heuristic.applyAsDouble(neighbour);

                    double f = tentativeG + h;

                    open.offer(new State(
                        neighbour,
                        tentativeG,
                        f
                    ));
                }
            }
        }

        // No path exists.
        return Collections.emptyList();
    }

    private static List<Integer> reconstructPath(
            Map<Integer, Integer> parent,
            int start,
            int goal
    ) {

        List<Integer> path = new ArrayList<>();

        int current = goal;

        path.add(current);

        while (current != start) {

            Integer previous = parent.get(current);

            if (previous == null) {
                return Collections.emptyList();
            }

            current = previous;

            path.add(current);
        }

        Collections.reverse(path);

        return path;
    }
}

```

## **Understand the important implementation details**

### **1. Why do we store both g and f in the priority queue?**

```
static class State {
    int node;
    double g;
    double f;
}
```

We need `f` to decide which node should be explored next.

But we also need `g` because we must know the actual cost associated with that particular queue entry.

We cannot calculate everything using `f` alone.

Remember:

\\[ f=g+h \\]

The actual path cost is still important when exploring neighbours.

### **2. Why do we store gScore separately?**

```
Map<Integer, Double> gScore = new HashMap<>();
```

Suppose we discover:

```
S -> A -> C

Cost = 10
```

Later, we discover:

```
S -> B -> C

Cost = 6
```

We must remember that 6 is the best-known cost to C.

Therefore:

```
gScore.put(C, 6);
```

The best-known cost should be updated whenever a cheaper route is discovered.

### **3. Why do we store parent?**

```
parent.put(neighbour, current.node);
```

This remembers where the node was reached from.

For example:

```
parent[B] = S
parent[C] = B
parent[G] = C
```

Starting from G, we can reconstruct:

```
G -> C -> B -> S
```

Reverse it:

```
S -> B -> C -> G
```

That gives us the actual path.

### **4. Why do we insert duplicate nodes into the priority queue?**

Java's standard `PriorityQueue` does not provide an efficient decrease-key operation.

Imagine we insert C with cost 10.

Later we find a better path with cost 6.

We could try to find the old C entry and update it, but that is inconvenient and potentially expensive.

Instead, simply insert another entry for C with the improved values.

The queue might contain:

```
C: g=10, f=15
C: g=6,  f=11
```

When the old entry eventually comes out, this check removes it:

```
if (Double.compare(current.g, bestKnown) != 0) {
    continue;
}
```

Only the current best-known entry is processed.

### **5. Why don't we permanently mark a node as visited?**

This implementation deliberately does not use a permanent `visited` set.

Why?

Because with an inconsistent heuristic, we might discover a better path to a previously explored node.

We must allow that node to be reopened.

With a consistent heuristic, we can use a closed set to avoid processing a node again after it has been finalised.

But the implementation above handles the more general admissible-heuristic case.

**Optimality conditions for this implementation:** Edge costs must be non-negative, the heuristic must be admissible, and the goal heuristic must be zero. The implementation must continue allowing improved paths to reopen nodes, as it does here.

# **15. How do I use A\* in a grid?**

Let's connect the generic implementation to a practical grid problem.

Suppose we have a grid:

```

S . . . .
. # # . .
. . . . .
. # # . G

```

Where:

- `S` is the starting position.
- `G` is the goal.
- `#` represents an obstacle.
- `.` represents a walkable cell.

Assume:

- We can move up, down, left, and right.
- Every movement costs 1.
- Obstacles cannot be crossed.

We can represent each cell using an integer ID.

For a grid with `cols` columns:

\\[ id=row\times cols+col \\]

To recover the coordinates:

\\[ row=id/cols \\]

\\[ col=id\\%cols \\]

Now our heuristic can be:

```
ToDoubleFunction<Integer> heuristic = id -> {

    int row = id / cols;
    int col = id % cols;

    return Math.abs(row - goalRow)
         + Math.abs(col - goalCol);
};
```

Why Manhattan distance?

Because movement is restricted to four directions, and every movement costs 1.

The obstacles do not invalidate Manhattan distance.

Why?

Because ignoring obstacles can only make the estimated path shorter.

The actual path may have to go around obstacles, but it can never be shorter than the Manhattan distance.

That makes it admissible.

For diagonal movement, replace Manhattan with the appropriate octile or Chebyshev formula depending on the movement cost.

# **16. Why does A\* still guarantee the shortest path?**

This is worth understanding rather than accepting as a theorem to memorise.

Remember the two properties:

\\[ g(n)=ActualCost(Start\rightarrow n) \\]

\\[ h(n)\leq ActualCost(n\rightarrow Goal) \\]

Therefore:

\\[ f(n)=g(n)+h(n) \\]

is a lower bound on the cost of any complete path that goes through \\(n\\).

Now imagine the optimal route has cost:

\\[ C^\* \\]

A\* always processes the node with the smallest `f`.

Suppose A\* removes the goal from the queue with a cost greater than \\(C^\*\\).

That would imply that the algorithm somehow ignored a cheaper path.

But consider the first unexplored node on the optimal route.

Its `f` cannot exceed the total optimal path cost:

\\[ f(n)\leq C^\* \\]

This follows because its actual cost so far plus its admissible estimate of the remaining cost cannot be greater than the actual optimal total cost.

Therefore, before a suboptimal goal costing more than \\(C^\*\\) could be removed from the priority queue, A\* would have to process a node on the optimal route whose `f` is at most \\(C^\*\\).

That lets it continue discovering the optimal route.

So the first goal removed from the queue has optimal cost.

This is why the following rule matters:

**Do not stop when you discover the goal. Stop when you remove the goal from the priority queue.**

Finding the goal is not the same as proving that the path is optimal.

# **17. Why is A\* faster than Dijkstra? What is the actual complexity?**

Let's be precise here.

Dijkstra is not inherently slow.

It is an excellent shortest-path algorithm.

The problem is that it does not have any information about which nodes are promising relative to a specific destination.

A\* uses that additional information to avoid exploring some unnecessary nodes.

## **Dijkstra's search area**

Imagine an open grid with a starting point and a destination far to the right.

Dijkstra explores nodes based on their distance from the starting point.

This tends to form expanding cost regions around the start.

It might explore many nodes to the:

- Left.
- Right.
- Top.
- Bottom.

Even though we only care about reaching one particular destination.

## **A\*'s search area**

A\* uses the heuristic to bias the search towards the destination.

It explores nodes with promising estimated total path costs first.

In a well-behaved grid with a good heuristic, this can reduce the number of explored nodes significantly.

### **Complexity**

For an explicit finite graph, standard Dijkstra with a binary heap has approximately:

\\[ O((V+E)\log V) \\]

where:

- \\(V\\) = number of vertices.
- \\(E\\) = number of edges.

A\* with a binary heap has similar heap-related costs in terms of the nodes and edges actually explored, although duplicate queue entries can increase the practical overhead.

If A\* explores only a small subset of the graph, it can be substantially faster in practice.

However, A\* does not have a universal guarantee that it will explore fewer nodes than Dijkstra.

In large state spaces, A\* can still have exponential worst-case time and memory requirements.

Its performance depends heavily on the quality of the heuristic.

## **What happens when h(n) = 0?**

This is a beautiful property.

Suppose:

\\[ h(n)=0 \\]

for every node.

Then:

\\[ f(n)=g(n)+0 \\]

\\[ f(n)=g(n) \\]

That is exactly Dijkstra's priority rule.

\\[ \boxed{A^\* \text{ with } h(n)=0 \text{ becomes Dijkstra}} \\]

This tells you something important:

*A is essentially a goal-directed extension of Dijkstra.*\*

The heuristic is the additional information that guides the search.

# **18. What if we want A\* to be even faster?**

Sometimes even an admissible heuristic is not enough.

Suppose you have a very large map and need an answer quickly.

You might be willing to sacrifice the guarantee of finding the exact shortest path.

One common technique is **Weighted A**\*.

Instead of:

\\[ f(n)=g(n)+h(n) \\]

Use:

\\[ \boxed{f(n)=g(n)+w\cdot h(n)} \\]

Where:

\\[ w>1 \\]

For example:

\\[ f(n)=g(n)+2h(n) \\]

What does this do?

It gives more importance to the estimated remaining distance.

A\* becomes more aggressive about heading towards the goal.

This often means fewer explored nodes, but it can return a suboptimal path.

Think of it this way:

| Algorithm                | How it prioritises                                       |
| ------------------------ | -------------------------------------------------------- |
| Dijkstra                 | Actual cost so far                                       |
| A\*                      | Actual cost + estimated remaining cost                   |
| Weighted A\*             | Actual cost + extra emphasis on estimated remaining cost |
| Greedy Best-First Search | Estimated remaining cost only                            |

Greedy Best-First Search uses:

\\[ f(n)=h(n) \\]

It ignores how much it has already cost to reach the node.

It may find a route quickly, but it does not guarantee an optimal route.

Weighted A\* sits between standard A\* and more aggressive heuristic-guided approaches.

Do not use Weighted A\* when you absolutely need the optimal path unless your implementation and assumptions provide the required guarantee.

# **19. Common mistakes when implementing A\***

These are particularly important in coding interviews and real implementations.

| Mistake                                               | Why it is wrong                                   | Correct approach                                      |
| ----------------------------------------------------- | ------------------------------------------------- | ----------------------------------------------------- |
| Using only `h(n)`                                     | This becomes Greedy Best-First Search             | Use `g(n) + h(n)`                                     |
| Using only `g(n)`                                     | This becomes Dijkstra                             | Add a useful heuristic                                |
| Using a heuristic that overestimates                  | Can lose optimality                               | Use an admissible heuristic for optimal A\*           |
| Using Manhattan distance with cheap diagonal movement | May overestimate                                  | Use octile or Chebyshev as appropriate                |
| Using average terrain cost for a lower bound          | Can overestimate                                  | Use a valid minimum cost                              |
| Stopping when the goal is discovered                  | A cheaper route might still exist                 | Stop when the goal is removed from the priority queue |
| Marking nodes permanently visited too early           | A better path might later be found                | Reopen nodes when needed                              |
| Forgetting to update `parent`                         | Path reconstruction becomes incorrect             | Update parent whenever `gScore` improves              |
| Ignoring outdated priority-queue entries              | An obsolete, more expensive path may be processed | Compare popped `g` with current `gScore`              |
| Using negative edge weights                           | Standard A\* assumptions no longer apply          | Use an algorithm appropriate for negative weights     |

One more important consideration: A\* can consume substantial memory because it stores frontier states and explored information.

For huge state spaces, memory may become the main limitation even when the heuristic is good.

## **Some practical applications**

**1. Maps and navigation**

Find the lowest-cost route between two locations.

Heuristic: Straight-line distance or a road-network lower bound.

**2. Video games**

Find a path for a character to reach a target.

Heuristic: Manhattan, Chebyshev, or octile distance depending on movement rules.

**3. Robotics**

Find a route for a robot to reach a target while avoiding obstacles.

Heuristic: Euclidean distance or a suitable lower bound that respects the robot's movement model.

**4. Sliding puzzles**

Find the minimum number of moves required to reach a target arrangement.

Heuristic: Misplaced tiles, Manhattan distance, or pattern databases.

**5. State-space planning**

Find the cheapest sequence of actions to reach a target state.

Heuristic: Estimate the minimum remaining operations or cost using a relaxed problem.

# **21. How to identify a heuristic in an unfamiliar problem**

This is the framework I would recommend following instead of memorising dozens of heuristic formulas.

Whenever you encounter a problem where A\* might be useful, think through these steps.

### **Step 1: Identify the state**

What exactly represents a node?

Examples:

- A coordinate in a grid.
- A city in a road network.
- A particular arrangement of puzzle tiles.
- The current state of a game.
- The current configuration of a planning problem.

### **Step 2: Identify the goal**

What condition tells us that we have reached the destination?

For example:

- Reaching coordinate `(10, 10)`.
- Reaching city G.
- Arranging all puzzle tiles in the correct positions.
- Achieving a desired system configuration.

### **Step 3: Identify the actions and their costs**

What transitions are allowed?

For a grid:

- Four or eight directions?
- Are diagonal moves more expensive?
- Are some cells more expensive to enter?

For a puzzle:

- Which tiles can move?
- What is the cost of one move?

This step determines what your heuristic must respect.

### **Step 4: Ask: What is the minimum work remaining?**

This is the most important question.

Do not immediately search for a formula.

Try to reason:

> Even under the most favourable conditions, what is the minimum cost I must pay to reach the goal?

Examples:

- Four-direction movement → Manhattan distance.
- Arbitrary-angle movement → Euclidean distance, when cost is proportional to distance.
- Diagonal movement → Octile or Chebyshev.
- Tiles needing to reach positions → Sum their minimum displacement.
- Complicated constraints → Relax the problem and solve the easier version.

### **Step 5: Check whether the heuristic can overestimate**

Ask:

> Can the actual solution ever be cheaper than my estimate?

If yes, your heuristic is not admissible.

Make the estimate weaker until it becomes a valid lower bound.

### **Step 6: Check whether the heuristic is computationally cheap**

Remember that calculating a heuristic takes time.

A complicated heuristic might reduce the number of explored nodes but spend too much time calculating estimates.

A good heuristic should ideally be:

- Relatively cheap to compute.
- A valid lower bound.
- As informative as practical.

### **Step 7: Decide whether optimality is mandatory**

If the shortest possible path is mandatory:

- Use an admissible heuristic.
- Prefer a consistent heuristic.
- Use an implementation that correctly handles reopening where needed.

If an approximate path is acceptable:

\- Consider Weighted A\* or other approximate methods.

# **22. The entire algorithm in one mental model**

Let's reduce everything to the intuition you should carry into an interview.

Imagine that you are exploring possible paths towards a destination.

At every node, ask two questions:

**Question 1: How much have I already spent to reach this node?**

\\[ g(n) \\]

**Question 2: How much more might I need to spend to reach the destination?**

\\[ h(n) \\]

Add them:

\\[ f(n)=g(n)+h(n) \\]

Explore the node with the smallest estimated total cost.

When you discover a cheaper way to reach a node, update its cost and parent.

Continue until the destination is removed from the priority queue.

That's A\*.

## **The complete mental cheat sheet**

| Concept              | Remember it as                                        |
| -------------------- | ----------------------------------------------------- |
| `g(n)`               | Cost already paid                                     |
| `h(n)`               | Estimated cost still remaining                        |
| `f(n)`               | Estimated total journey cost                          |
| Priority Queue       | Explore the most promising node first                 |
| Admissible heuristic | Never overestimate the actual cheapest remaining cost |
| Consistent heuristic | Estimate obeys the triangle inequality                |
| Parent map           | Remembers how we reached each node                    |
| Better `gScore`      | Found a cheaper way to reach a node                   |
| `h(n) = 0`           | A\* becomes Dijkstra                                  |
| `f(n) = h(n)`        | Greedy Best-First Search                              |
| Weighted A\*         | Prioritises the heuristic more aggressively           |

## **Final understanding: A\* vs Dijkstra**

The most important thing to remember is not the formula.

It is the problem each algorithm is trying to solve.

**Dijkstra asks:**

> Which node can I reach with the lowest cost so far?

*A asks:*\*

> Which node looks like the cheapest overall route to my destination, considering both what I have already spent and what I still expect to spend?

That one additional question — estimating the remaining cost — is what makes A\* goal-directed.

And the heuristic is simply the function that helps answer it.

\\[ \boxed{ \underbrace{f(n)}\_{\text{Estimated total cost}} = \underbrace{g(n)}\_{\text{Actual cost so far}} + \underbrace{h(n)}\_{\text{Estimated cost remaining}} } \\]

Once you understand why those three quantities exist, the algorithm becomes much easier to derive, implement, and adapt to completely different problems.&#x20;
