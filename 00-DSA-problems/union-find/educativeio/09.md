# Minimum Cost to Supply Water to All Houses — Java 24

This problem is a classic Minimum Spanning Tree (MST) problem. The key trick is to treat building a well as just another connection in the graph. Once we do that, we can use Kruskal's algorithm with a Disjoint Set Union (DSU).

I'll explain the intuition first, then walk through examples, compare approaches, and provide fully commented Java solutions.

## 0. Understand the problem in simple words

Imagine there are 4 houses. Every house needs water, and water can reach a house in either of two ways:

- Build a well at that house.
- Connect it through a pipe to another house that already has water.

For example:

- Building a well at house 1 costs 5.
- Building a well at house 2 costs 8.
- Connecting house 1 and house 2 with a pipe costs 2.

Instead of building two wells for a total of \\(5+8=13\\), we can build a well at house 1 for 5 and a pipe to house 2 for 2. Total cost = 7.

The challenge is to find the cheapest combination of wells and pipes that supplies water to every house.

The important point is that a house doesn't need its own well if it can receive water through a connected network from another house's well.

## 1. Clarifying questions to ask the interviewer

These questions establish the assumptions that determine the correct solution.

1\. Can water originate only from wells? Why: We need to know whether each connected network must contain at least one well. Under the given statement, yes.

2\. Can pipes be used in either direction? Why: The answer would differ if pipes were directed. Here, pipes are bidirectional, so the graph is undirected.

3\. Can multiple pipes connect the same pair of houses? Why: We need to know whether parallel edges are valid. Here, they are, and we can simply consider their costs as separate options.

4\. Can pipe costs be zero? Why: Zero-cost edges affect which connections Kruskal selects. Yes, zero-cost pipes are allowed.

5\. Must every house have its own well? Why: If that were required, the problem would be trivial. No, a house may receive water through pipes.

6\. What should happen if the pipe network is disconnected? Why: We need to ensure every house can still receive water. Since we can build a well at any house, the problem always has a feasible solution.

## 2. Core intuition: Convert wells into pipes

The most important insight is this:

Imagine a special virtual house numbered `0`. It is not a real house; it represents the water source.

- A well at house `1` costing `5` becomes an edge `(0, 1, 5)`.
- A well at house `2` costing `8` becomes an edge `(0, 2, 8)`.
- A pipe connecting houses `1` and `2` costing `2` remains an edge `(1, 2, 2)`.

Now every available option is represented uniformly as an edge in a graph.

Original problem

House 1

Well: 5

House 2

Well: 8

House 3

Well: 6

Pipes provide additional connections between houses.

Transformed graph

Virtual node 0

Water source

Connect node 0 to each house using its well cost.

House 1

House 2

House 3

Pipe edges connect the house nodes to each other.

We have transformed the problem into a graph with:

- \\(n+1\\) vertices: the \\(n\\) houses plus virtual node `0`.
- \\(m+n\\) edges: \\(m\\) available pipes plus \\(n\\) possible wells.
- An edge weight representing the cost of the corresponding construction option.

Our objective is now to connect every vertex to the virtual node with minimum total edge weight.

That is exactly the Minimum Spanning Tree (MST) problem.

### Why does a minimum spanning tree solve this?

A spanning tree connects all vertices without cycles. For \\(n+1\\) vertices, it contains exactly \\(n\\) edges.

Every real house must be connected to node `0`, directly or indirectly. Any path from node `0` to a house represents a way for water to reach that house.

- An edge from node `0` to a house means building a well.
- An edge between two houses means building a pipe.
- A connected path from node `0` means the house receives water.

An MST finds the cheapest combination of these edges.

We don't need a separate well for every house. The tree will choose wells where they are cost-effective and pipes where sharing a water source is cheaper.

## 3. Example with a complete dry run

Suppose:

```
n = 3
wells = [5, 8, 6]

pipes = [
    [1, 2, 2],
    [2, 3, 3],
    [1, 3, 10]
]
```

The transformed graph has the following edges.

| Edge   | Meaning              | Cost |
| ------ | -------------------- | ---- |
| (0, 1) | Well at house 1      | 5    |
| (0, 2) | Well at house 2      | 8    |
| (0, 3) | Well at house 3      | 6    |
| (1, 2) | Pipe between 1 and 2 | 2    |
| (2, 3) | Pipe between 2 and 3 | 3    |
| (1, 3) | Pipe between 1 and 3 | 10   |

### Step 1: Sort all edges by cost

```
(1, 2) -> 2
(2, 3) -> 3
(0, 1) -> 5
(0, 3) -> 6
(0, 2) -> 8
(1, 3) -> 10
```

### Step 2: Process edges using Kruskal's algorithm

Kruskal's algorithm processes the cheapest edge first. We accept an edge only if it connects two different components; otherwise, it would create a cycle.

1

Choose (1, 2), cost 2

Houses 1 and 2 become connected.

Accepted · Total = 2

2

Choose (2, 3), cost 3

Houses 1, 2 and 3 are now connected to one another.

Accepted · Total = 5

3

Choose (0, 1), cost 5

The virtual water source joins the component containing all three houses. Every house now has access to water.

Accepted · Total = 10

Stop

We have selected \\(n=3\\) edges for the \\(n+1=4\\) vertices.

## Minimum cost = 10

The selected edges mean:

- Build a pipe between houses 1 and 2 for 2.
- Build a pipe between houses 2 and 3 for 3.
- Build a well at house 1 for 5.

Total cost = \\(2+3+5=10\\).

Notice that building all three wells would cost \\(5+8+6=19\\). Sharing water through pipes reduces the cost to 10.

                 House 2

## 4. Edge cases to watch out for

1. Cheapest option is a well: If a well is cheaper than all useful pipes, Kruskal will select that well edge.
2. Zero-cost pipes or wells: These are valid. The algorithm handles zero weights normally.
3. Duplicate pipes with different costs: Keep the entries as separate edges. Sorting naturally considers the cheapest option first.
4. Disconnected pipe network: No issue. Virtual-node well edges guarantee that every house can eventually be connected.
5. All houses have expensive wells but cheap pipes: The algorithm can build one well and connect many houses through pipes.
6. Equal-cost edges: Any valid MST with the same minimum total cost is acceptable.
7. Integer overflow: With the given constraints, the maximum possible answer is at most \\(10^4 \times 10^5 = 10^9\\), which fits in an `int`, but using `long` for accumulated costs is a safe habit.
8. House indexing: The well cost for house `i` is `wells[i - 1]`; Java arrays are zero-indexed, whereas houses are one-indexed.

## 5. Solution 1 — Brute force: Enumerate all possible edge subsets

The most direct mathematical approach is to consider every possible subset of edges and find the cheapest subset that connects all vertices.

However, this is not practical for the given constraints.

- There are \\(E=n+m\\) total edges.
- Each edge can either be selected or not selected.
- Therefore, there are \\(2^E\\) possible subsets.
- For each subset, we would need to check whether it connects every vertex and calculate its cost.

Time complexity: \\(O(2^E(V+E))\\), where \\(V=n+1\\).

This approach explains the search space, but we should not implement it for \\(n,m\\) up to \\(10^4\\). We can do much better by exploiting the MST property.

## 6. Solution 2 — Kruskal's algorithm with DSU (optimal practical solution)

This is my recommended interview solution.

The algorithm is:

1. Add the well edges `(0, house, wellCost)`.
2. Add every pipe edge.
3. Sort all edges by cost.
4. Use DSU to determine whether the endpoints of an edge are already connected.
5. If they are not connected, select the edge and union their components.
6. Stop after selecting `n` edges.

Why stop after `n` edges? The graph has `n + 1` vertices, including the virtual source. A spanning tree over `n + 1` vertices contains exactly `n` edges.

Here is the complete Java 24 implementation. The inline comments explain the reasoning, invariants, and complexity.

```
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

public class WaterDistribution {

    // Each edge represents one available construction option:
    // either a well (from virtual node 0) or a pipe (between houses).
    private record Edge(int from, int to, int cost) {}

    // Disjoint Set Union (Union-Find) efficiently tracks which houses
    // belong to the same connected component of our growing MST.
    private static final class DSU {
        private final int[] parent;
        private final int[] size;

        DSU(int n) {
            parent = new int[n];
            size = new int[n];

            for (int i = 0; i < n; i++) {
                parent[i] = i;
                size[i] = 1;
            }
        }

        // Find the representative of x's component.
        // Path compression makes future find operations faster by
        // connecting visited nodes directly to the representative.
        int find(int x) {
            if (parent[x] != x) {
                parent[x] = find(parent[x]);
            }
            return parent[x];
        }

        // Merge two different components.
        // Union by size attaches the smaller component to the larger one.
        // Returns true if a merge happened, false if already connected.
        boolean union(int a, int b) {
            int rootA = find(a);
            int rootB = find(b);

            // An edge within the same component would create a cycle,
            // so Kruskal must reject it.
            if (rootA == rootB) {
                return false;
            }

            if (size[rootA] < size[rootB]) {
                int temp = rootA;
                rootA = rootB;
                rootB = temp;
            }

            parent[rootB] = rootA;
            size[rootA] += size[rootB];

            return true;
        }
    }

    public static long minCostToSupplyWater(
            int n, int[] wells, int[][] pipes) {

        // There are n real houses numbered 1..n and one virtual
        // water-source node numbered 0.
        //
        // The virtual node converts the well-building decision into
        // an ordinary graph edge:
        // (0, i, wells[i - 1]) means "build a well at house i".
        //
        // A pipe [u, v, cost] remains the edge (u, v, cost).
        // Therefore, choosing edges in an MST chooses wells and pipes
        // together, minimizing their combined construction cost.
        List<Edge> edges = new ArrayList<>(n + pipes.length);

        for (int house = 1; house <= n; house++) {
            edges.add(new Edge(0, house, wells[house - 1]));
        }

        for (int[] pipe : pipes) {
            edges.add(new Edge(pipe[0], pipe[1], pipe[2]));
        }

        // Kruskal considers the cheapest available option first.
        // Duplicate pipes are safe: each entry is simply another edge.
        edges.sort(Comparator.comparingInt(Edge::cost));

        // There are n + 1 vertices, so a spanning tree needs exactly n
        // accepted edges. DSU initially treats every vertex separately.
        DSU dsu = new DSU(n + 1);
        long totalCost = 0;
        int edgesUsed = 0;

        for (Edge edge : edges) {

            // Accept only edges joining different components.
            // This prevents cycles and maintains a valid forest.
            if (dsu.union(edge.from(), edge.to())) {
                totalCost += edge.cost();
                edgesUsed++;

                // All vertices are connected once n edges are accepted.
                // The virtual source is connected to every real house,
                // directly or through a path, so every house has water.
                if (edgesUsed == n) {
                    return totalCost;
                }
            }
        }

        // This cannot happen for valid input: every house has a
        // virtual-source well edge, so the augmented graph is connected.
        throw new IllegalStateException("All houses should be connectable");
    }

    public static void main(String[] args) {
        int n = 3;
        int[] wells = {5, 8, 6};

        int[][] pipes = {
            {1, 2, 2},
            {2, 3, 3},
            {1, 3, 10}
        };

        System.out.println(minCostToSupplyWater(n, wells, pipes));
        // Output: 10
    }
}
```

### Complexity analysis

Let \\(V=n+1\\) be the number of vertices and \\(E=n+m\\) the number of edges.

- Building the edge list takes \\(O(n+m)\\) time.
- Sorting all edges takes \\(O(E\log E)\\) time.
- DSU operations take \\(O(E\alpha(V))\\) amortized time, where \\(\alpha\\) is the inverse Ackermann function, which grows so slowly that it is effectively constant for practical input sizes.
- The edge list takes \\(O(E)\\) space.
- DSU requires \\(O(V)\\) additional space.

Therefore:

- Time: \\(O(E\log E)\\), dominated by sorting.
- Space: \\(O(E+V)=O(n+m)\\), including the edge list and DSU.

For the given constraints, this is efficient and reliable.

## 7. Solution 3 — Prim's algorithm

Kruskal is not the only way to find an MST. Prim's algorithm is another optimal approach.

The difference is in how the tree is constructed:

- Kruskal: Globally sorts edges and accepts edges that connect different components.
- Prim: Starts from a vertex and repeatedly adds the cheapest edge leading from the growing tree to a vertex outside it.

For this problem, start Prim from virtual node `0`. Its edges lead to every house, with weights equal to the well costs.

### Java 24 implementation

```
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;
import java.util.PriorityQueue;

public class WaterDistributionPrim {

    // An adjacency-list edge stores a neighboring vertex and its cost.
    private record Neighbor(int to, int cost) {}

    // The priority queue stores the next candidate vertex and the
    // minimum known cost of connecting it to the growing tree.
    private record Candidate(int vertex, int cost) {}

    public static long minCostToSupplyWater(
            int n, int[] wells, int[][] pipes) {

        // Build an undirected graph with virtual node 0.
        // Each well becomes an edge from 0 to its house.
        List<List<Neighbor>> graph = new ArrayList<>(n + 1);

        for (int i = 0; i <= n; i++) {
            graph.add(new ArrayList<>());
        }

        for (int house = 1; house <= n; house++) {
            int cost = wells[house - 1];

            graph.get(0).add(new Neighbor(house, cost));
            graph.get(house).add(new Neighbor(0, cost));
        }

        for (int[] pipe : pipes) {
            int u = pipe[0];
            int v = pipe[1];
            int cost = pipe[2];

            graph.get(u).add(new Neighbor(v, cost));
            graph.get(v).add(new Neighbor(u, cost));
        }

        // Prim starts with virtual node 0, representing the water source.
        // At each step, it chooses the cheapest edge leaving the current
        // tree. A vertex is added only once.
        boolean[] visited = new boolean[n + 1];

        PriorityQueue<Candidate> pq = new PriorityQueue<>(
                Comparator.comparingInt(Candidate::cost));

        pq.offer(new Candidate(0, 0));

        long totalCost = 0;
        int verticesAdded = 0;

        while (!pq.isEmpty() && verticesAdded < n + 1) {
            Candidate current = pq.poll();
            int vertex = current.vertex();

            // Multiple candidate edges may point to the same vertex.
            // Once a vertex enters the MST, ignore stale candidates.
            if (visited[vertex]) {
                continue;
            }

            visited[vertex] = true;
            verticesAdded++;
            totalCost += current.cost();

            // Offer connections from this newly added vertex to all
            // unvisited neighbors. The priority queue chooses the
            // cheapest candidate available across the entire frontier.
            for (Neighbor neighbor : graph.get(vertex)) {
                if (!visited[neighbor.to()]) {
                    pq.offer(new Candidate(
                            neighbor.to(), neighbor.cost()));
                }
            }
        }

        return totalCost;
    }

    public static void main(String[] args) {
        int n = 3;
        int[] wells = {5, 8, 6};

        int[][] pipes = {
            {1, 2, 2},
            {2, 3, 3},
            {1, 3, 10}
        };

        System.out.println(minCostToSupplyWater(n, wells, pipes));
        // Output: 10
    }
}
```

### Complexity analysis

With an adjacency list and binary min-heap:

- Building the graph takes \\(O(V+E)\\) time and space.
- Each vertex is finalized once.
- Each adjacency-list entry may generate a heap insertion, giving at most \\(O(E)\\) insertions.
- Heap operations cost \\(O(\log E)\\) each.

Therefore:

- Time: \\(O((V+E)\log E)\\), commonly written as \\(O(E\log E)\\) for this connected graph.
- Space: \\(O(V+E)\\) for the graph, visited array, and priority queue.

Both Prim and Kruskal produce the minimum total cost. Kruskal is particularly straightforward here because all well and pipe options can be represented in a single edge list.

## 8. Which solution should you choose in an interview?

| Approach                       | Time complexity  | Space complexity | Practical? |
| ------------------------------ | ---------------- | ---------------- | ---------- |
| Enumerate all edge subsets     | Exponential      | Exponential      | No         |
| Kruskal + DSU                  | \\(O(E\log E)\\) | \\(O(V+E)\\)     | Excellent  |
| Prim + adjacency list and heap | \\(O(E\log E)\\) | \\(O(V+E)\\)     | Excellent  |

Here, \\(V=n+1\\) and \\(E=n+m\\).

My recommendation: Present Kruskal with DSU as the main solution. The virtual node is the key modeling insight, and the DSU cleanly prevents cycles. Mention Prim as an alternative if the interviewer asks for another MST implementation.

## 9. Interviewer follow-up questions and answers

Q1. Why is the virtual node necessary?

It transforms two different types of decisions—building wells and constructing pipes—into a uniform set of weighted graph edges. This lets us apply a standard MST algorithm.

Q2. Why not build the cheapest well first and then connect all houses?

The cheapest well alone does not determine the optimal network. The best solution depends on the combination of well costs and pipe costs. Kruskal evaluates all options together.

Q3. Can the MST contain multiple well edges?

Yes. If two groups of houses are much cheaper to serve using separate wells than by connecting those groups with pipes, the MST can select multiple edges from node `0`.

Q4. What if several pipes connect the same pair of houses?

Keep them all. Kruskal processes them by cost, and a more expensive parallel edge cannot improve the MST over a cheaper edge with the same endpoints.

Q5. What if the pipe network alone is disconnected?

The augmented graph is still connected because node `0` has a well edge to every house. Therefore, a solution always exists.

Q6. Why does Kruskal stop after `n` edges instead of `n + 1`?

There are \\(n+1\\) vertices. A spanning tree has one fewer edge than vertices, so the MST contains exactly \\(n\\) edges.

Q7. Can we solve the problem without creating a virtual node?

Yes, but we would need to explicitly reason about which connected components receive wells. The virtual-node transformation avoids this extra complexity and reduces the problem to a standard MST.

Q8. Does the solution work when costs are equal or zero?

Yes. Kruskal only requires nonnegative or, more generally, comparable edge weights. Equal weights may yield different MSTs with the same total cost, and zero-cost edges are handled normally.

The central lesson is to recognize that a well is simply an edge to a shared virtual source. Once that modeling trick is clear, the problem becomes a standard MST problem rather than a special-purpose water-distribution algorithm.
