# Most Stones Removed with Same Row or Column — Java 24

Pattern: Union-Find (Disjoint Set Union / DSU)

LeetCode 947 — Medium

The key insight is that we don't need to simulate removing stones one by one. Instead, we can find connected groups of stones and determine how many stones must remain in each group.

## 1. Understand the problem

You are given stones represented by coordinates `(x, y)`.

You can remove a stone if another stone that has not been removed shares either:

- The same row (`x` coordinate).
- The same column (`y` coordinate).

Return the maximum number of stones you can remove.

Why?

All six stones are connected through shared rows or columns. We can remove five stones while keeping one stone behind.

Important observation: A stone may not share a row or column directly with the final remaining stone, but it can still be removable through a chain of other stones.

For example:

```
Stone A shares a row with Stone B
Stone B shares a column with Stone C
Stone C shares a row with Stone D
```

These stones belong to the same connected group, even if A and D do not directly share a row or column.

## 2. The most important observation

Think of every stone as a vertex in an undirected graph.

Connect two stones if they share a row or column.

For example:

```
Stone 0 = (0, 0)
Stone 1 = (0, 1)
Stone 2 = (1, 0)
```

- Stone 0 and Stone 1 share row `0`.
- Stone 0 and Stone 2 share column `0`.

Therefore, all three stones are in the same connected component.

The central result is:

\\[ \boxed{\text{Maximum removals}=n-\text{number of connected components}} \\]

Why?

- Every connected component can be reduced to one remaining stone.
- You cannot remove the last stone in a component because it has no other remaining stone in that component to support its removal.
- Therefore, if there are \\(C\\) connected components among \\(n\\) stones, exactly \\(C\\) stones must remain.

So:

\\[ \text{Answer}=n-C \\]

The challenge is efficiently counting connected components without explicitly building every edge between every pair of stones.

## 3. Solution 1 — Union-Find on rows and columns (recommended)

This is the most interesting optimization for the Union-Find pattern.

### Intuition: connect coordinates, not stones

Instead of creating a graph where every stone is a node, create nodes for rows and columns.

Since the constraints say:

\\[ 0 \le x_i,y_i \le 50 \\]

there are only 51 possible row coordinates and 51 possible column coordinates.

We can represent them using 102 nodes:

- Row nodes: `0` through `50`.
- Column nodes: `51` through `101`.

For a stone `(x, y)`, connect its row node to its column node:

```
union(x, y + 51);
```

The offset `51` is important because row `0` and column `0` are different entities.

### Visualizing the transformation

Suppose we have these stones:

```
(0, 0)
(0, 1)
(1, 0)
(3, 3)
```

We construct this graph:

```
Row 0 ─── Column 0
  │
  └────── Column 1

Row 1 ─── Column 0


Row 3 ─── Column 3
```

The first three stones belong to one connected component. The last stone belongs to another.

There are two connected components containing stones, so:

\\[ 4-2=\boxed{2} \\]

### Java 24 implementation

```
import java.util.HashSet;
import java.util.Set;

class Solution {

    public int removeStones(int[][] stones) {
        // Coordinates range from 0 to 50.
        // Nodes 0..50 represent rows.
        // Nodes 51..101 represent columns.
        final int OFFSET = 51;
        final int TOTAL_NODES = 102;

        DSU dsu = new DSU(TOTAL_NODES);

        // Step 1: Connect the row and column of every stone.
        for (int[] stone : stones) {
            int row = stone[0];
            int column = stone[1] + OFFSET;

            // A stone represents a connection between its row and column.
            dsu.union(row, column);
        }

        // Step 2: Count distinct connected components that contain stones.
        // We count only rows actually used by stones, so unused DSU nodes
        // do not incorrectly increase the component count.
        Set<Integer> components = new HashSet<>();

        for (int[] stone : stones) {
            int row = stone[0];

            // Every stone in the same component has the same row-node root.
            components.add(dsu.find(row));
        }

        // Each connected component must retain exactly one stone.
        return stones.length - components.size();
    }

    private static class DSU {
        private final int[] parent;
        private final int[] size;

        DSU(int n) {
            parent = new int[n];
            size = new int[n];

            for (int i = 0; i < n; i++) {
                parent[i] = i;
                size[i] = 1;
            }
        }

        int find(int x) {
            // Find the root and compress the path for future operations.
            if (parent[x] != x) {
                parent[x] = find(parent[x]);
            }

            return parent[x];
        }

        void union(int a, int b) {
            int rootA = find(a);
            int rootB = find(b);

            // Already connected: no change to the component structure.
            if (rootA == rootB) {
                return;
            }

            // Union by size: attach the smaller tree to the larger tree.
            if (size[rootA] < size[rootB]) {
                int temp = rootA;
                rootA = rootB;
                rootB = temp;
            }

            parent[rootB] = rootA;
            size[rootA] += size[rootB];
        }
    }
}
```

| `(3,3)` | `union(3,54)`   | Create a separate component          |

```

```

Number of components = 2

```

### Complexity

Let \\(n\\) be the number of stones and \\(U=102\\) be the number of possible row/column nodes.

- Time: \\(O((U+n)\alpha(U))\\), including initialization, with \\(O(n\alpha(U))\\) DSU work after initialization.
- Space: \\(O(U+n)\\), including the DSU arrays and the set of distinct roots.

Here, \\(\alpha\\) is the inverse Ackermann function, which is effectively constant for practical input sizes. Since \\(U=102\\) is fixed by the constraints, the algorithm is effectively linear in \\(n\\).

Why this is efficient: Instead of comparing every pair of stones, we only process each stone once to build the connectivity structure.

## 4. Solution 2 — Union-Find on stone indices

This is the most direct DSU solution and is particularly useful for learning the underlying pattern.

### Intuition

Make each stone its own DSU component. Then compare every pair of stones:

- If they share the same row, union their indices.
- If they share the same column, union their indices.

At the end, count the remaining connected components.

\\[ \text{Answer}=n-\text{components} \\]

### Java implementation

```
class Solution {

    public int removeStones(int[][] stones) {
        int n = stones.length;

        // Initially, each stone is its own component.
        DSU dsu = new DSU(n);

        // Compare every pair of stones.
        // A pair belongs to the same component if they share a row or column.
        for (int i = 0; i < n; i++) {
            for (int j = i + 1; j < n; j++) {

                boolean sameRow = stones[i][0] == stones[j][0];
                boolean sameColumn = stones[i][1] == stones[j][1];

                if (sameRow || sameColumn) {
                    // Merge the two stones' connected components.
                    dsu.union(i, j);
                }
            }
        }

        // Count how many distinct components remain.
        int components = 0;

        for (int i = 0; i < n; i++) {
            if (dsu.find(i) == i) {
                // A root represents one connected component.
                components++;
            }
        }

        return n - components;
    }

    private static class DSU {
        private final int[] parent;
        private final int[] size;

        DSU(int n) {
            parent = new int[n];
            size = new int[n];

            for (int i = 0; i < n; i++) {
                parent[i] = i;
                size[i] = 1;
            }
        }

        int find(int x) {
            if (parent[x] != x) {
                parent[x] = find(parent[x]);
            }
            return parent[x];
        }

        void union(int a, int b) {
            int rootA = find(a);
            int rootB = find(b);

            if (rootA == rootB) {
                return;
            }

            // Union by size keeps the trees shallow.
            if (size[rootA] < size[rootB]) {
                int temp = rootA;
                rootA = rootB;
                rootB = temp;
            }

            parent[rootB] = rootA;
            size[rootA] += size[rootB];
        }
    }
}
```

### Complexity

- Time: \\(O(n^2\alpha(n))\\), because we examine all pairs.
- Space: \\(O(n)\\), for the DSU arrays.

With \\(n\le 1000\\), there are at most \\(499{,}500\\) pairs, which is entirely manageable.

When to use it: When the coordinate range is large or unknown, or when you want a simple DSU solution without coordinate compression.

## 5. Solution 3 — Graph + DFS

This solution follows the problem statement most literally.

### Intuition

1. Treat each stone as a graph vertex.
2. Connect two vertices if their stones share a row or column.
3. Run DFS from every unvisited vertex.
4. Each new DFS traversal discovers one connected component.
5. Return `n - components`.

### Java implementation

```
class Solution {

    public int removeStones(int[][] stones) {
        int n = stones.length;
        boolean[] visited = new boolean[n];
        int components = 0;

        // Start a DFS from every stone that has not been visited.
        for (int i = 0; i < n; i++) {
            if (!visited[i]) {
                components++;

                // This DFS visits every stone connected to stone i.
                dfs(i, stones, visited);
            }
        }

        return n - components;
    }

    private void dfs(int current, int[][] stones, boolean[] visited) {
        visited[current] = true;

        // Explore every stone that shares the current stone's row or column.
        for (int next = 0; next < stones.length; next++) {
            boolean sameRow =
                    stones[current][0] == stones[next][0];

            boolean sameColumn =
                    stones[current][1] == stones[next][1];

            if (!visited[next] && (sameRow || sameColumn)) {
                dfs(next, stones, visited);
            }
        }
    }
}
```

### Complexity

- Time: \\(O(n^2)\\). Each DFS call scans all stones, and there are at most \\(n\\) calls.
- Space: \\(O(n)\\) for the visited array and up to \\(O(n)\\) recursive call stack.

This approach is easy to reason about, but it can use more stack space than an iterative approach. For larger constraints, iterative DFS avoids recursion-depth concerns.

## 6. Compare all three approaches

| Approach        | Time complexity                    | Auxiliary space                 | Recommendation                         |
| --------------- | ---------------------------------- | ------------------------------- | -------------------------------------- |
| Row/column DSU  | \\(O(n\alpha(U)+U)\\), \\(U=102\\) | \\(O(U+n)\\)                    | Best for these constraints             |
| Stone-index DSU | \\(O(n^2\alpha(n))\\)              | \\(O(n)\\)                      | Best for learning basic DSU            |
| DFS             | \\(O(n^2)\\)                       | \\(O(n)\\), including recursion | Best for learning connected components |

For this problem, I recommend learning stone-index DSU first, then the row/column DSU optimization. The first teaches the fundamental pattern; the second teaches how to model a problem more efficiently.

## 7. Edge cases

| Input                       | Components | Maximum removals | Reason                                      |
| --------------------------- | ---------- | ---------------- | ------------------------------------------- |
| `[[0,0]]`                   | 1          | 0                | A single stone cannot be removed            |
| `[[0,0],[1,1]]`             | 2          | 0                | Neither stone shares a row or column        |
| `[[0,0],[0,1]]`             | 1          | 1                | Both stones share a row                     |
| `[[0,0],[1,0],[2,0]]`       | 1          | 2                | All stones share a column                   |
| `[[0,0],[0,1],[1,0],[3,3]]` | 2          | 2                | Three stones are connected; one is isolated |

Notice that a stone is not necessarily removable just because it has a connection initially. Its removal must leave at least one other stone in its connected component. This is why each component contributes exactly one stone that must remain.

## 8. How to derive the solution in an interview

Here is a practical thought process you can use when solving this problem.

Step 1: Identify the relationship.

Ask: What makes two stones related?

Answer: Sharing a row or column.

Step 2: Identify the structure.

If relationships are undirected and transitive, think about connected components.

If two stones are connected through a chain of other stones, they belong to the same component.

Step 3: Find the relationship between components and the answer.

Ask: How many stones can be removed from a component containing \\(k\\) stones?

Answer: \\(k-1\\), because one must remain.

For \\(C\\) components containing \\(n\\) stones in total:

\\[ \sum\_{i=1}^{C}(k_i-1) =\sum\_{i=1}^{C}k_i-C =n-C \\]

Step 4: Choose the algorithm.

- Use DFS/BFS if you want to traverse connected components.
- Use DSU if you want to merge connected components.
- Inspect the constraints for optimization opportunities. Here, the small coordinate range makes row/column DSU especially effective.

## 9. Interview follow-up questions and answers

### Q1. Why can't we remove all the stones?

The last remaining stone in any connected component has no other remaining stone in that component to share a row or column with it. Thus, at least one stone per component must remain.

### Q2. Does the order of removal matter?

The order may change which particular stones are removed, but it does not change the maximum number of stones removable. Every connected component can be reduced to one stone.

### Q3. Why do we add an offset of 51 to column coordinates?

Rows and columns are separate entities. Row `0` must not be confused with column `0`. Since valid coordinates range from 0 to 50, adding 51 maps columns to indices 51 through 101.

### Q4. Why count distinct roots instead of counting all DSU nodes?

In the row/column DSU solution, many nodes are never used. Counting all DSU roots would include components that contain no stones. Instead, we count the roots associated with the rows of actual stones.

### Q5. Can we use a `HashMap` instead of fixed-size arrays?

Yes. If coordinate values are very large or the coordinate range is unknown, you can use a map-based DSU or coordinate compression. The fixed-size arrays are simpler and more efficient under the given constraints.

### Q6. What is the role of path compression and union by size?

- Path compression: Makes nodes point closer to the root during `find`.
- Union by size: Attaches the smaller component's tree to the larger one.

Together, they make DSU operations nearly constant time in practice.

### Q7. What if two stones have exactly the same coordinates?

They are connected, so the DSU solution naturally merges their components. The standard LeetCode formulation uses distinct stone positions, but the reasoning still works for duplicate entries if they are treated as separate stones.

### Q8. Is this problem fundamentally a Union-Find problem?

Not exclusively. It is fundamentally a connected-components problem. DFS, BFS, and DSU can all solve it. DSU is particularly attractive because the answer depends only on the number of connected components, not on the actual paths.

Remember this reusable pattern:

```
Identify connectivity
        ↓
Find connected components using DSU / DFS / BFS
        ↓
Determine what must remain in each component
        ↓

```

For Most Stones Removed with Same Row or Column:

The most valuable interview skill here is not memorizing the formula. It is recognizing that a problem about removing elements can often be reduced to understanding the connected components those elements belong to.

# 1. First, understand when a stone can be removed

Suppose we have three stones:

```
Stone A = (0, 0)
Stone B = (0, 1)
Stone C = (0, 2)
```

All three stones are in the same row because their `x` coordinate is `0`.

We can remove them like this:

Step 1: Initially, three stones

A (0,0)

B (0,1)

C (0,2)

All three stones share the same row.

Step 2: Remove A

B and C remain. A can be removed because B or C shares its row.

Step 3: Remove B

C remains. B can be removed because C shares its row.

Step 4: Stop

Only C remains. We cannot remove C because there is no other stone left.

1 stone remains

We started with three stones and removed two.

\\[ \text{Maximum removals}=3-1=2 \\]

This gives us our first important observation:

If all stones are connected, we can remove every stone except one.

But what if the stones are not all connected? Let's find out.

# 3. The tricky part: stones can be connected indirectly

This is usually where the problem becomes confusing.

Consider these stones:

```
int[][] stones = {
    {0, 0},  // A
    {0, 1},  // B
    {1, 1}   // C
};
```

Their positions are:

```
        Column 0    Column 1

Row 0      A -------- B
                       |
Row 1                  C
```

- A and B share a row.
- B and C share a column.
- A and C do not share a row or column.

Still, all three stones belong to the same connected group because we can travel from A to C through B:

```
A → B → C
```

We can remove A first, then C, and keep B.

```
Initial: A, B, C
Remove A:    B, C
Remove C:    B
```

Answer: `2`.

This is the difference between direct connection and connected component.

- Direct connection: two stones share a row or column.
- Connected component: stones are connected through any chain of direct connections.

We care about connected components, not just direct connections.

# 4. Why does every connected group need exactly one remaining stone?

Let's prove it using a group of five connected stones.

```
A — B — C — D — E
```

The lines represent connections through a shared row or column.

We can remove stones from the ends inward:

```
A — B — C — D — E
    B — C — D — E
        C — D — E
            D — E
                E
```

Each removed stone had another stone in its connected group that was still present.

Eventually, one stone remains.

Could we remove that final stone? No. There is no other remaining stone in its connected group to share a row or column with.

So a connected component containing \\(k\\) stones allows us to remove:

\\[ k-1 \\]

If there are several groups, we apply the same reasoning to each one.

For example:

| Group | Stones | Removable | Must remain |
| ----- | ------ | --------- | ----------- |
| A     | 5      | 4         | 1           |
| B     | 3      | 2         | 1           |
| C     | 2      | 1         | 1           |
| Total | 10     | 7         | 3           |

Therefore:

\\[ \boxed{\text{Answer}=n-\text{number of groups}} \\]

We now understand the mathematics. The remaining question is: How do we find those groups efficiently?

# 5. Introduce Union-Find, one step at a time

Union-Find is a data structure that helps us maintain groups of connected elements.

It has two main operations:

| Operation     | Meaning                                 |
| ------------- | --------------------------------------- |
| `find(x)`     | Find which group element `x` belongs to |
| `union(a, b)` | Merge the groups containing `a` and `b` |

Think of each group as having a representative, called its root.

For example:

```
Group 1                 Group 2

    0                       3
   / \                     /
  1   2                   4
```

The root of the first group is `0`; the root of the second is `3`.

If we call:

```
union(2, 4);
```

the groups merge. Now all five elements belong to one group.

The exact shape of the tree doesn't matter. What matters is that all elements in the same group have the same root when we call `find`.

## Step 1: Initially, every stone is its own group

For our four-stone example:

```
int[][] stones = {
    {0, 0},  // Stone 0
    {0, 1},  // Stone 1
    {1, 0},  // Stone 2
    {3, 3}   // Stone 3
};
```

Initially:

```
Stone 0     Stone 1     Stone 2     Stone 3

   0           1           2           3
```

There are four groups.

## Step 2: Merge stones that share a row or column

Compare Stone 0 `(0,0)` and Stone 1 `(0,1)`.

They share row `0`.

Call:

```
union(0, 1);
```

Now they belong to one group.

```
Group 1          Group 2       Group 3

   0                2             3
   |
   1
```

Next, compare Stone 0 `(0,0)` and Stone 2 `(1,0)`.

They share column `0`.

Call:

```
union(0, 2);
```

Now Stone 2 joins the first group.

```
Group 1                Group 2

   0                      3
  / \
 1   2
```

Stone 3 `(3,3)` has no connection to any other stone, so it remains alone.

We now have two groups.

## Step 3: Count the groups

The roots are:

```
Group 1: root 0
Group 2: root 3
```

Therefore:

```
Total stones = 4
Connected groups = 2

Answer = 4 - 2 = 2
```

Notice that we did not actually remove any stones. We only identified their connectivity, which is enough to calculate the maximum removals.

# 6. Complete Java solution — start with the easiest DSU approach

For learning purposes, I recommend starting with this version. It treats each stone as a node, which makes the code match the explanation directly.

```
class Solution {

    public int removeStones(int[][] stones) {
        int n = stones.length;

        // Initially, each stone belongs to its own connected component.
        DSU dsu = new DSU(n);

        // STEP 1: Discover connections between stones.
        //
        // Compare each pair only once:
        //   i = 0, j = 1
        //   i = 0, j = 2
        //   ...
        //   i = 1, j = 2
        //
        // We do not compare a stone with itself, and we do not need
        // to compare both (i, j) and (j, i).
        for (int i = 0; i < n; i++) {
            for (int j = i + 1; j < n; j++) {

                // Two stones are directly connected if they share
                // either their row coordinate or their column coordinate.
                boolean sameRow = stones[i][0] == stones[j][0];
                boolean sameColumn = stones[i][1] == stones[j][1];

                if (sameRow || sameColumn) {
                    // They belong to the same connected component.
                    // Merge their components, including any stones
                    // already connected indirectly through other stones.
                    dsu.union(i, j);
                }
            }
        }

        // STEP 2: Count the distinct connected components.
        int components = 0;

        for (int i = 0; i < n; i++) {
            // A root represents one component.
            // parent[i] == i means i is currently a root.
            if (dsu.find(i) == i) {
                components++;
            }
        }

        // STEP 3: Every component must keep one stone.
        // All other stones in each component can be removed.
        return n - components;
    }

    private static class DSU {
        // parent[x] tells us the parent of x in the DSU tree.
        private final int[] parent;

        // size[root] records the number of elements in a root's component.
        // It helps us merge smaller trees into larger trees.
        private final int[] size;

        DSU(int n) {
            parent = new int[n];
            size = new int[n];

            // Initially, every stone is its own root and has size 1.
            for (int i = 0; i < n; i++) {
                parent[i] = i;
                size[i] = 1;
            }
        }

        int find(int x) {
            // If x is its own parent, x is the root of its component.
            if (parent[x] == x) {
                return x;
            }

            // Path compression:
            // Make x point directly to the root so future find operations
            // on this path become faster.
            parent[x] = find(parent[x]);

            return parent[x];
        }

        void union(int a, int b) {
            // First find the roots of the two components.
            int rootA = find(a);
            int rootB = find(b);

            // If the roots are identical, both elements are already
            // in the same component. Nothing needs to change.
            if (rootA == rootB) {
                return;
            }

            // Union by size:
            // Attach the smaller component below the larger component's root.
            // This prevents the DSU trees from becoming unnecessarily tall.
            if (size[rootA] < size[rootB]) {
                int temp = rootA;
                rootA = rootB;
                rootB = temp;
            }

            // Merge component B into component A.
            parent[rootB] = rootA;

            // The new component contains the elements of both components.
            size[rootA] += size[rootB];
        }
    }
}
```

Let's trace the exact example:

### Initial state

```

Every stone is its own group.

### Process each pair

| Pair     | Same row/column? | Operation     | Result                         |
| -------- | ---------------- | ------------- | ------------------------------ |
| `(0, 1)` | Same row         | `union(0, 1)` | Merge stones 0 and 1           |
| `(0, 2)` | Same column      | `union(0, 2)` | Merge stone 2 into their group |
| `(0, 3)` | No               | None          | No change                      |
| `(1, 2)` | No               | None          | No change                      |
| `(1, 3)` | No               | None          | No change                      |
| `(2, 3)` | No               | None          | No change                      |

After the unions, one possible parent array is:

```
parent = [0, 0, 0, 3]
```

This means:

```
Stone 0 → root 0
Stone 1 → root 0
Stone 2 → root 0
Stone 3 → root 3
```

The first three stones form one component, and the last stone forms another.

The final count is:

```
i = 0 → find(0) = 0 → root; count = 1
i = 1 → find(1) = 0 → not a root
i = 2 → find(2) = 0 → not a root
i = 3 → find(3) = 3 → root; count = 2
```

Finally:

```
return n - components;
```

\\[ 4-2=\boxed{2} \\]

## 8. How do we optimize it using rows and columns?

Once you understand the solution above, there's a useful optimization.

In the first solution, we compare every pair of stones, giving \\(O(n^2)\\) pair comparisons.

But look at the constraints:

\\[ 0 \le x_i,y_i \le 50 \\]

There are only 51 possible row values and 51 possible column values.

Instead of treating each stone as a node, we can represent each row and each column as a node.

For a stone `(x, y)`, connect row `x` with column `y`.

For example:

```
Stone (0, 0) → connect Row 0 with Column 0
Stone (0, 1) → connect Row 0 with Column 1
Stone (1, 0) → connect Row 1 with Column 0
```

The graph becomes:

```
Row 0 ───── Column 0 ───── Row 1
  |
  |
Column 1
```

These three stones are connected because their row/column nodes are connected.

Since row `0` and column `0` must be different nodes, we assign column nodes an offset of `51`:

```
union(x, y + 51);
```

There are only 102 possible nodes in total.

### Optimized Java code

```
import java.util.HashSet;
import java.util.Set;

class Solution {

    public int removeStones(int[][] stones) {
        // Coordinates range from 0 to 50.
        // Nodes 0..50 represent rows.
        // Nodes 51..101 represent columns.
        final int OFFSET = 51;
        final int TOTAL_NODES = 102;

        DSU dsu = new DSU(TOTAL_NODES);

        // Step 1: Build connectivity between rows and columns.
        for (int[] stone : stones) {
            int row = stone[0];
            int column = stone[1] + OFFSET;

            // A stone connects its row to its column.
            dsu.union(row, column);
        }

        // Step 2: Count distinct components containing actual stones.
        Set<Integer> roots = new HashSet<>();

        for (int[] stone : stones) {
            // Every stone in the same component has the same root.
            // Using the row node ensures we count only components
            // that contain at least one stone.
            roots.add(dsu.find(stone[0]));
        }

        // One stone must remain in each connected component.
        return stones.length - roots.size();
    }

    private static class DSU {
        private final int[] parent;
        private final int[] size;

        DSU(int n) {
            parent = new int[n];
            size = new int[n];

            for (int i = 0; i < n; i++) {
                parent[i] = i;
                size[i] = 1;
            }
        }

        int find(int x) {
            if (parent[x] != x) {
                // Path compression speeds up subsequent lookups.
                parent[x] = find(parent[x]);
            }

            return parent[x];
        }

        void union(int a, int b) {
            int rootA = find(a);
            int rootB = find(b);

            if (rootA == rootB) {
                return;
            }

            // Union by size keeps the DSU trees shallow.
            if (size[rootA] < size[rootB]) {
                int temp = rootA;
                rootA = rootB;
                rootB = temp;
            }

            parent[rootB] = rootA;
            size[rootA] += size[rootB];
        }
    }
}
```

### Complexity comparison

|         | Stone-index DSU       | Row/column DSU            |
| ------- | --------------------- | ------------------------- |
| Time    | \\(O(n^2\alpha(n))\\) | \\(O((n+U)\alpha(U))\\)   |
| Space   | \\(O(n)\\)            | \\(O(U)\\)                |
| \\(U\\) | Not applicable        | 102 for these constraints |

Here, \\(\alpha\\) is the inverse Ackermann function, which is effectively constant for these input sizes.

The row/column approach is more efficient for this problem's coordinate constraints. The stone-index approach is often easier to understand initially.

## The one thing to remember

Don't start by thinking, "Which stone should I remove first?"

Instead, think:

1. Which stones are connected, directly or indirectly?
2. How many connected groups exist?
3. How many stones must remain? One per group.
4. Subtract the groups from the total.

\\[ \boxed{\text{Maximum stones removable}=n-\text{connected components}} \\]

That is the entire reasoning behind this problem. Union-Find is simply the tool we use to identify those connected groups efficiently.
