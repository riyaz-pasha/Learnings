# Accounts Merge — Java 24 Solutions

This is a classic Union-Find (Disjoint Set Union / DSU) problem. It can also be solved using a graph and DFS/BFS.

The key challenge is that names alone cannot identify a person. Two accounts belong to the same person only when they have the same name and at least one common email, and accounts can be connected indirectly through other accounts.

## 1. Understand the problem with an example

Input:

```
String[][] accounts = {
    {"John", "johnsmith@mail.com", "john_newyork@mail.com"},
    {"John", "johnsmith@mail.com", "john00@mail.com"},
    {"Mary", "mary@mail.com"},
    {"John", "johnnybravo@mail.com"}
};
```

The first and second accounts share `johnsmith@mail.com`, so they belong to the same person.

The third account belongs to Mary. The fourth account belongs to a different John because it has no common email with the other John accounts.

Expected output:

```
[
  ["John", "john00@mail.com", "john_newyork@mail.com", "johnsmith@mail.com"],
  ["John", "johnnybravo@mail.com"],
  ["Mary", "mary@mail.com"]
]
```

Notice three important rules:

1. Accounts are merged based on shared emails, not names.
2. Email connections can be transitive: if A shares an email with B, and B shares another email with C, all three accounts merge.
3. Emails must be unique and sorted using Java's natural `String` ordering, which compares UTF-16 code units lexicographically. For the ASCII characters used in ordinary email addresses, this gives the required ASCII-style ordering.

## 2. How to recognize the Union-Find pattern

Ask yourself:

- Do I have multiple entities that may belong to the same group?
- Can I identify a connection between two entities?
- Do I need to combine connected entities into groups?

Here, each account is an entity, and sharing an email creates a connection between accounts.

Union-Find is ideal for merging these connected groups.

There is one subtlety: emails, not account names, are the most useful identifiers. We can associate each unique email with an account and union accounts whenever the same email appears again.

## 3. Solution 1 — Union-Find (recommended for the pattern)

### Intuition

Instead of merging whole account lists directly, separate the problem into three stages:

1. Connect accounts: If an email appears in multiple accounts, union those account indices.
2. Collect emails: After all unions, group every email by its account's final DSU root.
3. Format the result: Sort each group's emails and prepend the corresponding person's name.

### Step 1: Connect accounts using emails

Maintain a map:

```
Map<String, Integer> emailToAccount = new HashMap<>();
```

It records the first account in which each email appeared.

When processing an email:

- If it is new, remember the current account.
- If it already exists, union the current account with the previously recorded account.

For example:

```
Account 0: John, a@mail.com, b@mail.com
Account 1: John, b@mail.com, c@mail.com
Account 2: John, c@mail.com, d@mail.com
```

The unions are:

```
Account 0 -- b@mail.com -- Account 1
Account 1 -- c@mail.com -- Account 2

Final group: {Account 0, Account 1, Account 2}
```

Even though accounts 0 and 2 do not share an email directly, they end up in the same group through account 1.

### Complete Java 24 code

```
import java.util.*;

public class AccountsMerge {

    public static List<List<String>> accountsMerge(
            List<List<String>> accounts) {

        int n = accounts.size();

        // Step 1: Initially, every account is its own component.
        DSU dsu = new DSU(n);

        // Maps each email to the first account containing that email.
        Map<String, Integer> emailToAccount = new HashMap<>();

        // Step 2: Union accounts that share at least one email.
        for (int accountIndex = 0; accountIndex < n; accountIndex++) {

            List<String> account = accounts.get(accountIndex);

            // Index 0 contains the name; emails start at index 1.
            for (int j = 1; j < account.size(); j++) {

                String email = account.get(j);

                // If this email has appeared before, both accounts
                // must belong to the same connected component.
                Integer previousAccount = emailToAccount.putIfAbsent(
                        email, accountIndex);

                if (previousAccount != null) {
                    dsu.union(accountIndex, previousAccount);
                }
            }
        }

        // Step 3: Collect all unique emails by their final DSU root.
        Map<Integer, Set<String>> rootToEmails = new HashMap<>();

        for (Map.Entry<String, Integer> entry : emailToAccount.entrySet()) {

            String email = entry.getKey();
            int accountIndex = entry.getValue();

            // Find the final representative after all unions.
            int root = dsu.find(accountIndex);

            // TreeSet automatically deduplicates and sorts emails.
            rootToEmails.computeIfAbsent(
                    root, ignored -> new TreeSet<>()
            ).add(email);
        }

        // Step 4: Build the required output.
        List<List<String>> result = new ArrayList<>();

        for (Map.Entry<Integer, Set<String>> entry
                : rootToEmails.entrySet()) {

            int root = entry.getKey();

            // All accounts in a component belong to the same person,
            // so the name at the root account is a valid name.
            String name = accounts.get(root).get(0);

            List<String> mergedAccount = new ArrayList<>();
            mergedAccount.add(name);
            mergedAccount.addAll(entry.getValue());

            result.add(mergedAccount);
        }

        return result;
    }

    // Disjoint Set Union with path compression and union by size.
    static class DSU {

        private final int[] parent;
        private final int[] size;

        DSU(int n) {
            parent = new int[n];
            size = new int[n];

            for (int i = 0; i < n; i++) {
                parent[i] = i; // Every account starts as its own root.
                size[i] = 1;
            }
        }

        // Finds the representative of the component containing x.
        // Path compression makes future find operations faster.
        int find(int x) {
            if (parent[x] != x) {
                parent[x] = find(parent[x]);
            }

            return parent[x];
        }

        // Merges the components containing a and b.
        // Union by size keeps the trees shallow.
        void union(int a, int b) {

            int rootA = find(a);
            int rootB = find(b);

            // Already connected; nothing needs to be merged.
            if (rootA == rootB) {
                return;
            }

            // Attach the smaller tree to the larger tree.
            if (size[rootA] < size[rootB]) {
                int temp = rootA;
                rootA = rootB;
                rootB = temp;
            }

            parent[rootB] = rootA;
            size[rootA] += size[rootB];
        }
    }

    public static void main(String[] args) {

        List<List<String>> accounts = List.of(
                List.of("John", "johnsmith@mail.com",
                        "john_newyork@mail.com"),
                List.of("John", "johnsmith@mail.com",
                        "john00@mail.com"),
                List.of("Mary", "mary@mail.com"),
                List.of("John", "johnnybravo@mail.com")
        );

        System.out.println(accountsMerge(accounts));
    }
}
```

### Why use `putIfAbsent()`?

This statement is the central trick:

```
Integer previousAccount =
        emailToAccount.putIfAbsent(email, accountIndex);
```

- If the email is new, it stores `email -> accountIndex` and returns `null`.
- If the email already exists, it returns the original account index without replacing it.
- When the return value is not `null`, we union both accounts.

We only need one representative account per email. Every later account containing that email can be connected to the representative.

### Why use `TreeSet`?

```
Map<Integer, Set<String>> rootToEmails = new HashMap<>();
```

Using a `TreeSet` for the values gives us two properties automatically:

- No duplicate emails.
- Emails are sorted lexicographically.

If we used `HashSet` instead, we would have to copy the emails into a list and sort them explicitly.

The order of the final account rows is not specified in the problem, so the outer `HashMap` order is acceptable.

### Dry run

Consider:

```
Account 0: John, a@mail.com, b@mail.com
Account 1: John, b@mail.com, c@mail.com
Account 2: Mary, d@mail.com
```

Initially:

```
parent = [0, 1, 2]
```

Process `b@mail.com` in account 1. The email was already seen in account 0, so we union accounts 1 and 0.

```
parent = [0, 0, 2]  // One possible representation
```

Account 2 remains independent.

Now group the emails by their final roots:

```
Root 0 -> a@mail.com, b@mail.com, c@mail.com
Root 2 -> d@mail.com
```

Sort the emails and prepend the corresponding names:

```
[
  [John, a@mail.com, b@mail.com, c@mail.com],
  [Mary, d@mail.com]
]
```

The exact internal parent array may differ depending on union order, but the final groups remain the same.

### Complexity analysis

Let:

- \\(A\\) = number of accounts.
- \\(E\\) = total number of email occurrences across all accounts.
- \\(U\\) = number of unique email addresses.

| Operation                         | Complexity                        |
| --------------------------------- | --------------------------------- |
| Initialize DSU                    | \\(O(A)\\)                        |
| Process emails and union accounts | \\(O(E\alpha(A))\\) amortized     |
| Group emails by root              | \\(O(U\alpha(A))\\)               |
| Sort emails with `TreeSet`        | \\(O(U\log U)\\) worst case       |
| Overall                           | \\(O(A + E\alpha(A) + U\log U)\\) |
| Auxiliary space                   | \\(O(A+U)\\)                      |

Here, \\(\alpha(A)\\) is the inverse Ackermann function, which is effectively constant for practical input sizes.

The sorting bound above assumes string comparisons take constant time; strictly, a comparison can inspect multiple characters. If \\(L\\) is the maximum email length, account for up to \\(O(L)\\) per comparison.

## 4. Solution 2 — Graph + DFS

Union-Find is not the only natural solution. This problem can also be represented as a graph, where each unique email is a vertex, and emails appearing in the same account are connected.

### Intuition

For an account:

```
John, a@mail.com, b@mail.com, c@mail.com
```

Create connections:

```
a@mail.com
   |
b@mail.com
   |
c@mail.com
```

More precisely, we can connect every email in an account to its first email. We do not need to create every possible pairwise connection.

If two accounts share an email, their email graphs become connected. A DFS visits every email belonging to the same person.

### Complete Java 24 code

```
import java.util.*;

public class AccountsMergeDFS {

    public static List<List<String>> accountsMerge(
            List<List<String>> accounts) {

        // Each email maps to its neighboring emails.
        Map<String, Set<String>> graph = new HashMap<>();

        // Each email maps to the name associated with its account.
        Map<String, String> emailToName = new HashMap<>();

        // Step 1: Build the email graph.
        for (List<String> account : accounts) {

            String name = account.get(0);
            String firstEmail = account.get(1);

            for (int i = 1; i < account.size(); i++) {

                String email = account.get(i);

                // Store the name for output construction.
                emailToName.putIfAbsent(email, name);

                // Ensure every email has a graph vertex.
                graph.computeIfAbsent(email, ignored -> new HashSet<>());

                // Connect every email to the first email in its account.
                // This is sufficient to make all emails in the account
                // part of the same connected component.
                if (!email.equals(firstEmail)) {
                    graph.get(firstEmail).add(email);
                    graph.get(email).add(firstEmail);
                }
            }
        }

        // Step 2: Find connected components using DFS.
        Set<String> visited = new HashSet<>();
        List<List<String>> result = new ArrayList<>();

        for (String email : graph.keySet()) {

            if (visited.contains(email)) {
                continue;
            }

            List<String> mergedEmails = new ArrayList<>();

            // Explore every email connected to this starting email.
            dfs(email, graph, visited, mergedEmails);

            // Step 3: Sort emails in the component.
            Collections.sort(mergedEmails);

            // All emails in this component belong to the same person.
            String name = emailToName.get(email);

            List<String> mergedAccount = new ArrayList<>();
            mergedAccount.add(name);
            mergedAccount.addAll(mergedEmails);

            result.add(mergedAccount);
        }

        return result;
    }

    private static void dfs(
            String email,
            Map<String, Set<String>> graph,
            Set<String> visited,
            List<String> mergedEmails) {

        // Mark before visiting neighbors to avoid repeated traversal
        // and infinite recursion in cycles.
        visited.add(email);
        mergedEmails.add(email);

        for (String neighbor : graph.get(email)) {

            if (!visited.contains(neighbor)) {
                dfs(neighbor, graph, visited, mergedEmails);
            }
        }
    }
}
```

### Complexity

Let \\(U\\) be the number of unique emails and \\(E\\) the number of email occurrences. The graph construction creates at most \\(O(E)\\) adjacency entries, and DFS traverses the graph in \\(O(U+E)\\).

- Graph construction: \\(O(E)\\) expected time with hash-based collections.
- DFS traversal: \\(O(U+E)\\).
- Sorting: \\(O(U\log U)\\) worst case across all components.
- Auxiliary space: \\(O(U+E)\\), including graph adjacency lists.

In this complexity analysis, \\(E\\) counts input email occurrences; the graph has at most a linear number of edges in that count.

### Which approach should you choose?

| Factor                   | Union-Find                         | Graph + DFS                   |
| ------------------------ | ---------------------------------- | ----------------------------- |
| Main concept             | Merge connected components         | Traverse connected components |
| Key structure            | Parent and size arrays             | Adjacency map                 |
| Email storage            | Email-to-account map               | Email adjacency graph         |
| Extra graph memory       | Not needed                         | Required                      |
| Best for                 | Practicing DSU and repeated unions | Practicing graph traversal    |
| Interview recommendation | Excellent                          | Equally valid                 |

For a Union-Find pattern interview, use Solution 1. For a connected-components graph interview, Solution 2 is a strong alternative.

## 5. Solution 3 — Brute force account comparison

This is useful to understand why Union-Find is needed, although I would not recommend it as the final interview solution.

### Idea

Compare every pair of accounts:

1. Check whether their names match.
2. Check whether they share at least one email.
3. If both conditions hold, merge them.
4. Repeat until no more accounts can be merged, then deduplicate and sort the emails.

The problem is that merging one pair can create a connection with another account, so a straightforward implementation may need repeated scans. Managing merged lists also becomes complicated.

A naive implementation can take up to \\(O(A^2K^2)\\) time per round of comparisons, where \\(K\\) is the maximum number of emails per account, and repeated rounds can make it even more expensive.

Interview takeaway: Use a graph or DSU to represent transitive connectivity instead of repeatedly comparing and merging account lists.

## 6. Edge cases to discuss in an interview

| Edge case                                 | Expected behavior                                                              |
| ----------------------------------------- | ------------------------------------------------------------------------------ |
| Same name, no common email                | Keep accounts separate                                                         |
| Different names, common email             | The problem's guarantees imply this cannot occur for valid input               |
| Three accounts connected transitively     | Merge all three                                                                |
| Duplicate email within an account         | Output the email only once                                                     |
| Account with one email                    | Output the name and that email                                                 |
| Multiple independent people               | Return one row per connected component                                         |
| Emails in arbitrary input order           | Sort the output emails                                                         |
| Different capitalization in email strings | Treat as different strings unless the problem explicitly defines normalization |

One important distinction: although email addresses are generally case-sensitive in some contexts and case-insensitive in others, this coding problem expects string-based matching. Do not normalize email addresses to lowercase unless instructed.

## 7. How to derive the DSU solution during an interview

You can use this sequence of questions to build the solution naturally.

Question 1: Can I use the name as a key?

No. Multiple people can have the same name.

Question 2: What uniquely connects two accounts?

A shared email address.

Question 3: What if account A shares an email with B, and B shares another email with C?

All three accounts must be merged. This is transitive connectivity.

Question 4: Which data structure handles transitive connectivity efficiently?

Union-Find or a graph traversal.

Question 5: How do I avoid comparing every pair of accounts?

Maintain `emailToAccount`. When an email appears again, immediately union its current account with the account already associated with that email.

Question 6: How do I produce the final output?

After all unions, find the root for each unique email, group emails by root, sort each group, and prepend the account name.

This derivation is more valuable in an interview than memorizing the code.

## 8. Follow-up questions and answers

Q1. Why is Union-Find better than comparing every pair of accounts?

Union-Find processes email connections incrementally. With path compression and union by size, each operation is amortized \\(O(\alpha(A))\\), rather than repeatedly scanning account pairs.

Q2. Why can't we union accounts only when their names match?

Because names are not unique identifiers. Two people named John must remain separate unless their accounts are connected by a shared email.

Q3. Why does one representative account per email suffice?

Suppose an email appears in accounts 2, 5, and 8. Unioning account 5 with 2 and account 8 with 2 connects all three. We do not need to union every pair.

Q4. Why do we group emails after all union operations?

The representative of a component may change as more unions occur. Grouping emails only after processing every account ensures we use the final component representatives.

Q5. Can we use `HashSet` instead of `TreeSet`?

Yes. Collect emails into a `HashSet`, convert them to a list, and call `Collections.sort()`. This makes deduplication and sorting separate operations. `TreeSet` keeps them sorted throughout insertion.

Q6. Can the final result's rows be in any order?

Yes, unless the problem specifies an ordering for the accounts themselves. The essential requirement is that each account's email addresses are unique and sorted.

Q7. What is the difference between this problem and Number of Connected Components?

Both require grouping connected entities. The difference is that here, the connections are implicit: they must be discovered by matching email strings across accounts.

Q8. Can we use BFS instead of DFS?

Absolutely. Both visit every vertex and edge in a connected component, so their asymptotic complexities are the same.

Q9. What if an account has thousands of emails?

The same approach still works. DSU handles each email occurrence efficiently, and the primary additional cost becomes sorting the unique emails.

Q10. What is the most important optimization?

Avoid creating all pairwise email edges or comparing every pair of accounts. The email-to-account map in DSU, or the star-shaped email graph in DFS, keeps the number of connections linear in the total email occurrences.

## Final recommendation

For your Union-Find practice sequence, solve Accounts Merge after understanding basic `find`, `union`, path compression, and union by size.

Remember this reusable pattern:

```
Entities + shared identifiers
          |
          v
Map identifier -> representative entity
          |
          v
Repeated identifier? Union the entities
          |
          v
Group entities/identifiers by final root
          |
          v
Format and sort the result
```

The most important lesson is that Union-Find discovers groups; it does not automatically construct the final output. You still need a separate grouping and formatting phase after all unions are complete.
