# 2349. Design a Number Container System — Java 24

The key to this problem is understanding that we need two different views of the same data:

1. Given an index, what number is currently stored there?
2. Given a number, what is the smallest index currently storing that number?

These are reverse lookup operations. The first suggests a `HashMap`; the second suggests a `PriorityQueue` (min-heap).

The tricky part is that `change(index, number)` can replace an existing number. We need to handle that efficiently without searching through every index whenever `find(number)` is called.

## 0. Simplify the problem

Imagine containers placed at integer indices.

Initially, every container is empty.

```
change(2, 10)   // index 2 stores 10
change(1, 10)   // index 1 stores 10
change(3, 10)   // index 3 stores 10

find(10)        // returns 1, the smallest index
```

Now replace the number at index 1:

```
change(1, 20)
```

The system now looks like this:

```
Index:   1    2    3
Number: 20   10   10

find(10)  -> 2
find(20)  -> 1
find(30)  -> -1
```

Notice that index 1 must no longer be considered a valid location for number 10.

Our challenge: support both operations efficiently, even when indices are changed repeatedly.

## 1. Clarifying questions to ask the interviewer

These questions help establish the required data structure and avoid solving a different problem.

- Can an existing index be reassigned to another number? Yes, and the old number must stop considering that index valid.
- Can the same number occur at multiple indices? Yes. Otherwise, finding the smallest index would be trivial.
- Can `find` be called before any matching `change`? Yes. It must return `-1` when no matching index exists.
- Are indices and numbers bounded? Both can be as large as \\(10^9\\), so allocating an array of that size is impractical.
- How many operations are expected? Up to \\(10^5\\), so scanning all indices on every `find` would be too slow.

The constraints point toward hash-based lookup and an ordered structure that can efficiently return the minimum.

## 2. Core intuition: how to discover the optimal approach

### Step 1: Start with the simplest representation

Use a map to store the current value at every occupied index.

```
indexToNumber

1 -> 20
2 -> 10
3 -> 10
```

This makes `change(index, number)` straightforward: update the map entry.

But how do we implement `find(10)`?

We could scan every entry and remember the smallest matching index. This works, but each `find` takes \\(O(n)\\) time, where \\(n\\) is the number of occupied indices.

With \\(10^5\\) operations, repeatedly scanning the entire map can lead to roughly \\(O(nq)\\) work, where \\(q\\) is the number of queries.

We need a second data structure.

### Step 2: Reverse the lookup

Ask yourself: if I want the smallest index containing number 10, what information would make that query easy?

Instead of searching from indices to numbers, maintain the reverse relationship:

```
numberToIndices

10 -> [1, 2, 3]
20 -> [1]
```

Now the question becomes: how do we retrieve the smallest index from each collection?

There are two natural choices:

- A `TreeSet<Integer>` for each number: keeps indices sorted and supports insertion, removal, and minimum lookup in \\(O(\log n)\\) and \\(O(1)\\), respectively.
- A `PriorityQueue<Integer>` for each number: keeps the smallest index at the top, but removing an arbitrary index is expensive.

The second option has a clever optimization that leads to the common optimal interview solution.

### Step 3: Use a min-heap and lazy deletion

A min-heap guarantees that its smallest stored index is at the top.

For example:

```
Heap for number 10:

          1
         / \
        2   5
       /
      3

peek() -> 1
```

But suppose we execute:

```
change(1, 20);
```

The index 1 is still physically inside the heap for number 10. Removing it directly from a Java `PriorityQueue` would require a linear search.

Instead, leave obsolete indices in the heap and remove them only when they reach the top. This technique is called lazy deletion.

We determine whether an index is still valid by consulting `indexToNumber`.

```
indexToNumber:
1 -> 20
2 -> 10
3 -> 10

Heap for 10:
[1, 2, 3]

find(10):
  top = 1
  current number at index 1 is 20, not 10
  discard 1

  top = 2
  current number at index 2 is 10
  return 2
```

The heap may contain stale entries, but it never returns one as a valid answer.

### Mental model

```
                    change(index, number)
                             |
                 +-----------+-----------+
                 |                       |
          Update index map       Add index to number's
                                 min-heap (new number)
                                         |
                                         v
                                  Old heap entries
                                  may become stale


                      find(number)
                           |
                           v
                      Inspect heap top
                           |
                  +--------+--------+
                  |                 |
               Valid             Stale
                  |                 |
                Return          Remove top
                                    |
                                    +----> Repeat
```

The central insight is that `change` does not need to clean up every old data structure. It updates the source of truth, and `find` cleans up obsolete entries when necessary.

## 3. All solutions — from brute force to optimal

### Solution 1: HashMap and linear scan

This is the simplest correct approach. It establishes the baseline against which we can improve.

```
import java.util.HashMap;
import java.util.Map;

class NumberContainersBruteForce {

    // The source of truth: each occupied index has exactly one current number.
    private final Map<Integer, Integer> indexToNumber = new HashMap<>();

    public void change(int index, int number) {
        // Replacing a value automatically overwrites the previous assignment.
        indexToNumber.put(index, number);

        // Time: O(1) expected.
        // Space: O(1) auxiliary per operation; O(n) total map storage.
    }

    public int find(int number) {
        int smallestIndex = Integer.MAX_VALUE;

        // We must inspect all occupied indices because the map is not ordered.
        for (Map.Entry<Integer, Integer> entry : indexToNumber.entrySet()) {
            if (entry.getValue() == number) {
                smallestIndex = Math.min(smallestIndex, entry.getKey());
            }
        }

        // If no matching index exists, preserve the required -1 result.
        return smallestIndex == Integer.MAX_VALUE ? -1 : smallestIndex;

        // Time: O(n) expected per find, where n is the number of occupied indices.
        // Space: O(1) auxiliary for find.
        // Total space: O(n).
        //
        // Why it is not optimal:
        // Every find scans the entire map, even if the answer is immediately
        // obvious. Up to 10^5 repeated queries can make this too expensive.
    }
}
```

### Solution 2: HashMap and TreeSet

This solution maintains both directions of the relationship, and each number's indices remain sorted.

```
import java.util.HashMap;
import java.util.Map;
import java.util.TreeSet;

class NumberContainersTreeSet {

    // index -> current number; this is the authoritative assignment.
    private final Map<Integer, Integer> indexToNumber = new HashMap<>();

    // number -> all indices currently assigned to that number, in sorted order.
    private final Map<Integer, TreeSet<Integer>> numberToIndices = new HashMap<>();

    public void change(int index, int number) {
        Integer oldNumber = indexToNumber.get(index);

        // If the index already had a value, remove it from the old number's set.
        if (oldNumber != null) {
            if (oldNumber == number) {
                // Nothing changed. Avoid unnecessary tree operations.
                return;
            }

            TreeSet<Integer> oldIndices = numberToIndices.get(oldNumber);
            oldIndices.remove(index);

            // Optional cleanup: do not retain empty sets for numbers with no indices.
            if (oldIndices.isEmpty()) {
                numberToIndices.remove(oldNumber);
            }
        }

        // Update the authoritative mapping.
        indexToNumber.put(index, number);

        // Create the sorted set on first use, then insert this index.
        numberToIndices.computeIfAbsent(number, ignored -> new TreeSet<>())
                       .add(index);

        // Time: O(log n) for TreeSet insertion/removal, plus expected O(1)
        // for hash-map operations. Here n is the number of occupied indices.
        // Space: O(n) for the index map and up to O(n) set entries overall.
    }

    public int find(int number) {
        TreeSet<Integer> indices = numberToIndices.get(number);

        // TreeSet.first() returns the minimum without scanning the set.
        // An absent or empty set means no index currently contains this number.
        return indices == null || indices.isEmpty() ? -1 : indices.first();

        // Time: O(1) for first() and expected O(1) for the hash-map lookup.
        // Space: O(1) auxiliary.
    }
}
```

Why this works: the sets are always kept accurate. When an index changes numbers, we explicitly remove it from its old set before inserting it into its new set.

Trade-off: the implementation is clean and has predictable bounds, but every replacement must update two collections. TreeSet operations cost \\(O(\log n)\\).

### Solution 3: HashMap and min-heaps with lazy deletion — optimal interview approach

This approach avoids searching for an arbitrary element inside a heap. It inserts the new assignment and cleans up stale indices only when `find` needs them.

```
import java.util.HashMap;
import java.util.Map;
import java.util.PriorityQueue;

class NumberContainers {

    /*
     * SOURCE OF TRUTH
     *
     * indexToNumber[index] tells us which number is CURRENTLY assigned
     * to an index.
     *
     * This map is essential for identifying stale heap entries.
     * We never trust an index in a heap without checking this map.
     */
    private final Map<Integer, Integer> indexToNumber = new HashMap<>();

    /*
     * REVERSE LOOKUP
     *
     * numberToIndices[number] is a min-heap containing indices that have
     * been assigned to this number at some point.
     *
     * It can contain stale indices because we intentionally avoid removing
     * arbitrary elements from heaps when change() replaces a value.
     */
    private final Map<Integer, PriorityQueue<Integer>> numberToIndices =
            new HashMap<>();

    public NumberContainers() {
        // Both maps start empty. No array allocation is needed because
        // indices can be as large as 10^9.
    }

    public void change(int index, int number) {
        /*
         * Step 1: Update the source of truth.
         *
         * If this index previously stored a different number, overwriting
         * the map entry immediately makes its old heap entries stale.
         *
         * Example:
         *   Before: indexToNumber = {1 -> 10}
         *   change(1, 20)
         *   After:  indexToNumber = {1 -> 20}
         *
         * The heap for 10 might still contain 1, but the map now tells
         * us that index 1 no longer belongs to number 10.
         */
        indexToNumber.put(index, number);

        /*
         * Step 2: Insert the index into the new number's min-heap.
         *
         * computeIfAbsent creates the heap on the first assignment of
         * a number. The PriorityQueue orders integer indices naturally,
         * so peek() always returns the smallest stored index.
         *
         * If the index was assigned to the same number repeatedly,
         * duplicate heap entries are harmless. find() can discard them
         * once the first valid occurrence is reached and returned.
         */
        numberToIndices
                .computeIfAbsent(number, ignored -> new PriorityQueue<>())
                .offer(index);

        /*
         * Expected time: O(log H) for heap insertion, where H is the
         * size of this number's heap. Hash-map operations are expected O(1).
         *
         * Additional space: O(1) per call, although every call can add
         * another heap entry. Total heap space can grow to O(q), where
         * q is the total number of change() calls.
         */
    }

    public int find(int number) {
        /*
         * Step 1: Find the heap for this number.
         *
         * No heap means no index has ever been assigned to this number.
         */
        PriorityQueue<Integer> indices = numberToIndices.get(number);

        if (indices == null) {
            return -1;
        }

        /*
         * Step 2: Repeatedly discard stale entries from the heap's top.
         *
         * The heap gives us the smallest candidate, but not necessarily
         * the smallest CURRENTLY valid index.
         *
         * An entry is valid exactly when indexToNumber still maps that
         * index to the requested number.
         *
         * Why inspect only the top?
         * If the top is stale, it cannot be a valid answer. Removing it
         * exposes the next-smallest candidate. Once the top is valid,
         * every remaining index is at least as large, so the answer is
         * guaranteed to be the smallest valid index.
         */
        while (!indices.isEmpty()) {
            int smallestIndex = indices.peek();

            Integer currentNumber = indexToNumber.get(smallestIndex);

            if (currentNumber != null && currentNumber == number) {
                // The smallest candidate is still valid.
                return smallestIndex;
            }

            // The index was reassigned, or its entry is an obsolete duplicate.
            // Lazy deletion: remove stale entries only when they reach the top.
            indices.poll();
        }

        /*
         * The heap has been exhausted without finding a valid index.
         * Every candidate was stale, so no index currently contains number.
         */
        return -1;

        /*
         * Time:
         *   - A single find() may remove many stale entries.
         *   - If it removes s entries from a heap of size H, its cost is
         *     O((s + 1) log H) in the worst case.
         *   - However, each heap entry is inserted once and removed at
         *     most once. Across q operations, total heap-cleanup work
         *     is O(q log q).
         *
         * Amortized time per operation: O(log q), including heap cleanup.
         * A particular find() can still take O(q log q) in the worst case.
         *
         * Space: O(n + q), where n is the number of distinct occupied
         * indices and q is the total number of change() calls. Stale entries
         * consume space until they are removed from their respective heaps.
         */
    }
}
```

## 4. Dry run: understand lazy deletion

Consider these operations:

```
NumberContainers nc = new NumberContainers();

nc.change(2, 10);
nc.change(1, 10);
nc.change(3, 10);
nc.change(1, 20);

nc.find(10); // 2
nc.find(20); // 1
nc.find(30); // -1
```

After the first three changes:

```
indexToNumber:
    1 -> 10
    2 -> 10
    3 -> 10

Heap for 10 (conceptually sorted):
    [1, 2, 3]
```

After `change(1, 20)`:

```
indexToNumber:
    1 -> 20
    2 -> 10
    3 -> 10

Heap for 10: [1, 2, 3]  // 1 is now stale
Heap for 20: [1]
```

The heap for 10 has not been updated directly. That is intentional.

Now call `find(10)`:

| Step | Heap top | Current assignment | Action         |
| ---- | -------- | ------------------ | -------------- |
| 1    | 1        | `1 -> 20`          | Remove stale 1 |
| 2    | 2        | `2 -> 10`          | Return 2       |

The result is `2`, which is correct.

## 5. Edge cases to watch out for

| Scenario                                | Expected behavior                       | Why                                 |
| --------------------------------------- | --------------------------------------- | ----------------------------------- |
| Find a number never assigned            | `-1`                                    | No heap exists                      |
| Replace an index's number               | Old number no longer considers it valid | The map is authoritative            |
| Assign the same number repeatedly       | Return the same smallest valid index    | Duplicate entries are harmless      |
| All indices for a number become stale   | `-1`                                    | Cleanup eventually empties the heap |
| Large index, such as \\(10^9\\)         | Works normally                          | HashMaps avoid huge arrays          |
| Several indices contain the same number | Return the smallest                     | Min-heap orders indices             |
| Replace the smallest index repeatedly   | Return the next valid minimum           | Stale minimum entries are discarded |

One important distinction: the optimal solution is amortized-efficient, not necessarily constant-time for every `find` call. A single query may clean up many stale entries.

## 6. Time and space complexity comparison

Let:

- \\(n\\) = number of distinct currently occupied indices.
- \\(q\\) = total number of operations.
- \\(H\\) = size of a particular number's heap.

| Approach                 | `change`            | `find`                    | Total space  |
| ------------------------ | ------------------- | ------------------------- | ------------ |
| HashMap + scan           | Expected \\(O(1)\\) | \\(O(n)\\)                | \\(O(n)\\)   |
| HashMap + TreeSet        | \\(O(\log n)\\)     | Expected \\(O(1)\\)       | \\(O(n)\\)   |
| HashMap + lazy min-heaps | \\(O(\log H)\\)     | Amortized \\(O(\log q)\\) | \\(O(n+q)\\) |

The heap approach is often preferred because it avoids arbitrary removals from heaps and has efficient amortized performance. The TreeSet approach is also a strong solution when maintaining an exact, up-to-date collection is more important than minimizing update overhead.

## 7. Interviewer follow-up questions

Q1. Why not use a `HashSet` for each number?

A `HashSet` does not maintain ordering, so finding the smallest index would require scanning all indices in the set.

Q2. Why not remove the old index from its heap inside `change()`?

Java's `PriorityQueue.remove(Object)` takes \\(O(H)\\) time in the worst case because it must locate the element first. Lazy deletion avoids this linear search.

Q3. Can a stale index incorrectly be returned?

No. Before returning an index, `find()` verifies that `indexToNumber` still maps it to the requested number.

Q4. Why is the minimum heap element the correct answer once it is valid?

The heap orders every stored index from smallest to largest. If its top is valid, no other stored index can be smaller. Therefore, no other valid index can beat it.

Q5. What is the disadvantage of lazy deletion?

Heap storage can grow with the total number of `change()` calls, rather than only the number of current assignments. Stale entries also cause occasional expensive cleanup. If memory usage must remain proportional to current assignments, the TreeSet solution is a useful alternative.

Q6. What if `change()` is called a million times on the same index?

The authoritative map still stores only one assignment for that index, but the heap-based solution may accumulate many entries. Lazy cleanup removes obsolete entries as they reach the top. A TreeSet-based solution avoids this accumulation by removing old assignments immediately.

Q7. Which solution should you present in an interview?

Start with the linear-scan solution to establish correctness. Then identify the need for reverse lookup. Present the TreeSet solution as a direct improvement, and finally explain lazy deletion with min-heaps as an alternative that avoids arbitrary heap removals.

The most important thing to explain is not merely how a priority queue works, but why stale entries are safe: the map determines current truth, and the heap only supplies ordered candidates.
