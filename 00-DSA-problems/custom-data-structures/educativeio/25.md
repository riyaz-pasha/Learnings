# 1912. Design Movie Rental System — Java 24

Difficulty: Hard Core concepts: HashMap, HashSet, TreeSet, custom comparators, ordered data structures, and maintaining multiple views of the same data.

The key interview lesson is that this is not just a sorting problem. It is a data structure design problem: we need to keep two different collections efficiently ordered while the same movie copies move between them.

## 0. Understand the problem in simple terms

Imagine a movie rental company with multiple shops. Each shop has at most one copy of a particular movie, and every copy has a fixed rental price.

We need to support four operations:

| Operation           | Meaning                          | What should be returned?               |
| ------------------- | -------------------------------- | -------------------------------------- |
| `search(movie)`     | Find shops with an unrented copy | Up to 5 cheapest shop IDs              |
| `rent(shop, movie)` | Rent a copy                      | Nothing                                |
| `drop(shop, movie)` | Return a rented copy             | Nothing                                |
| `report()`          | Find all currently rented copies | Up to 5 cheapest `(shop, movie)` pairs |

Both search and report return results in a specific order.

- `search`: sort by price, then shop ID.
- `report`: sort by price, then shop ID, then movie ID.

For example, suppose movie `1` is available at these shops:

| Shop | Movie | Price |
| ---- | ----- | ----- |
| 0    | 1     | 5     |
| 1    | 1     | 4     |
| 2    | 1     | 5     |

`search(1)` returns `[1, 0, 2]`.

Why? Shop 1 is cheapest. Shops 0 and 2 have equal prices, so the smaller shop ID comes first.

After `rent(0, 1)`, that copy must disappear from search results and appear in the rental report. Its price does not change; only its state changes.

## 1. Clarifying questions to ask in an interview

The problem statement answers most of these, but asking them demonstrates that you're thinking about correctness and constraints before choosing data structures.

1. Can a shop have multiple copies of the same movie? The statement says no. Therefore, `(shop, movie)` uniquely identifies a copy, and we don't need a quantity field.
2. Can prices change after initialization? No price-update operation is provided. We can treat each copy's price as immutable.
3. Can `rent` or `drop` receive invalid operations? The constraints guarantee valid calls. We don't need to define recovery behavior for invalid transitions.
4. Must search and report return the first five results in the exact specified order? Yes. This rules out relying on an unordered `HashSet` or `HashMap` for output.
5. Can we use additional memory to make queries faster? The constraints allow up to \\(10^5\\) copies and \\(10^5\\) operations. Maintaining sorted indexes is a reasonable trade-off.

The fifth question leads directly to the optimal design: maintain the ordering instead of sorting everything whenever a query arrives.

## 2. Core intuition: maintain two ordered views

Think of every physical movie copy as belonging to exactly one of two states:

- Available: it can be rented.
- Rented: it is currently out of the shop.

A copy moves between these states when `rent` or `drop` is called.

We can model this with two `TreeSet`s:

1. `availableByMovie[movie]`: all available copies of a particular movie, sorted by price and shop.
2. `rentedMovies`: all rented copies across every movie, sorted by price, shop, and movie.

We also need a `HashMap` to retrieve the fixed price for any `(shop, movie)` pair in constant expected time.

### Visualize the architecture

```
                 MovieRentalSystem
                         |
             +-----------+-----------+
             |           |           |
          Prices      Available     Rented
             |           |           |
        (shop,movie)  movie ->     One global
          -> price    TreeSet      TreeSet
                         |
                    price, shop
                    ordering
```

When renting a copy:

```
Available TreeSet
       |
       | rent(shop, movie)
       v
Remove from available
Add to rented TreeSet
```

When returning a copy, perform the reverse transition.

The invariant: every known copy is in exactly one of the two ordered indexes. This is the central idea that makes the design efficient.

## 3. Compare the possible solutions

There are several ways to solve this problem. The important part of the interview is to explain why we move from one approach to the next.

| Approach                                           | `search`                | `rent` / `drop` | `report`           |
| -------------------------------------------------- | ----------------------- | --------------- | ------------------ |
| Brute force: scan every copy                       | \\(O(M)\\)              | \\(O(1)\\)      | \\(O(M)\\)         |
| Scan and sort per query                            | \\(O(M+M\log M)\\)      | \\(O(1)\\)      | \\(O(M+M\log M)\\) |
| Maintain sorted indexes with `TreeSet`             | \\(O(5)\\) after lookup | \\(O(\log M)\\) | \\(O(5)\\)         |
| Maintain sorted indexes, counting output traversal | \\(O(\log M+5)\\)       | \\(O(\log M)\\) | \\(O(5)\\)         |

Here, \\(M\\) is the number of movie copies, and the last two rows describe the same general approach with the lookup cost made explicit. Since the maximum output size is five, returning results requires at most five iterations.

### Approach 1: Brute force

Store all movie copies in a collection. For every search, scan all copies, keep those matching the movie and available for rent, sort them, and return the first five. For report, scan all rented copies, sort them, and return the first five.

This is easy to implement, but expensive when queries are frequent.

```
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

class MovieRentingSystemBruteForce {

    /*
     * Each copy remembers its shop, movie, price, and current state.
     *
     * Keeping the state on the copy makes this implementation simple:
     * we do not need to maintain separate collections.
     */
    private static final class Copy {
        final int shop;
        final int movie;
        final int price;
        boolean rented;

        Copy(int shop, int movie, int price) {
            this.shop = shop;
            this.movie = movie;
            this.price = price;
        }
    }

    private final List<Copy> copies = new ArrayList<>();

    /*
     * Search ordering: price ascending, then shop ascending.
     */
    private static final Comparator<Copy> SEARCH_ORDER =
            Comparator.comparingInt((Copy copy) -> copy.price)
                    .thenComparingInt(copy -> copy.shop);

    /*
     * Report ordering: price ascending, then shop ascending,
     * then movie ascending.
     */
    private static final Comparator<Copy> REPORT_ORDER =
            Comparator.comparingInt((Copy copy) -> copy.price)
                    .thenComparingInt(copy -> copy.shop)
                    .thenComparingInt(copy -> copy.movie);

    public MovieRentingSystemBruteForce(int n, int[][] entries) {
        for (int[] entry : entries) {
            copies.add(new Copy(entry[0], entry[1], entry[2]));
        }
    }

    public List<Integer> search(int movie) {
        List<Copy> candidates = new ArrayList<>();

        /*
         * We must inspect every copy because no precomputed index tells
         * us which copies match this movie and are currently available.
         *
         * Time: O(M) for the scan.
         */
        for (Copy copy : copies) {
            if (copy.movie == movie && !copy.rented) {
                candidates.add(copy);
            }
        }

        /*
         * Sorting guarantees the exact price/shop tie-breaking rules.
         *
         * If K copies match, sorting costs O(K log K).
         * K can be as large as M.
         */
        candidates.sort(SEARCH_ORDER);

        List<Integer> result = new ArrayList<>(5);

        /*
         * We only need five results, even if there are many matches.
         * The list is already sorted, so the first five are correct.
         */
        for (int i = 0; i < Math.min(5, candidates.size()); i++) {
            result.add(candidates.get(i).shop);
        }

        return result;
    }

    public void rent(int shop, int movie) {
        /*
         * A brute-force implementation also needs to locate the copy.
         * Under the problem's valid-operation guarantee, the matching
         * copy exists and is available.
         *
         * Time: O(M), because we have no direct lookup index.
         */
        for (Copy copy : copies) {
            if (copy.shop == shop && copy.movie == movie) {
                copy.rented = true;
                return;
            }
        }
    }

    public void drop(int shop, int movie) {
        /*
         * The same linear lookup is required when returning a copy.
         */
        for (Copy copy : copies) {
            if (copy.shop == shop && copy.movie == movie) {
                copy.rented = false;
                return;
            }
        }
    }

    public List<List<Integer>> report() {
        List<Copy> rentedCopies = new ArrayList<>();

        /*
         * Scan all copies and retain only rented ones.
         * Time: O(M).
         */
        for (Copy copy : copies) {
            if (copy.rented) {
                rentedCopies.add(copy);
            }
        }

        /*
         * If R copies are rented, sorting costs O(R log R),
         * which is O(M log M) in the worst case.
         */
        rentedCopies.sort(REPORT_ORDER);

        List<List<Integer>> result = new ArrayList<>(5);

        for (int i = 0; i < Math.min(5, rentedCopies.size()); i++) {
            Copy copy = rentedCopies.get(i);
            result.add(List.of(copy.shop, copy.movie));
        }

        return result;
    }
}
```

Why this is not sufficient: even `rent` and `drop` cost \\(O(M)\\), because the implementation must find the copy by scanning. With up to \\(10^5\\) operations, repeated scans can become expensive.

### Approach 2: Scan, then sort

We can improve the first solution by using a `HashMap` for direct copy lookup, reducing `rent` and `drop` to expected \\(O(1)\\). We still scan all copies and sort matches for `search` and `report`.

This is a useful intermediate solution because it separates two problems:

- Finding a copy by its identity.
- Finding the cheapest copies in the required order.

The first is solved by hashing. The second still requires scanning and sorting.

The optimal solution addresses the second problem by maintaining the order continuously.

## 4. Optimal solution: HashMap + TreeSet

The best way to think about the optimal solution is:

> Don't repeatedly ask the system to find the cheapest copies. Keep the copies sorted so that the cheapest ones are already at the front.

### Step 1: Choose the right data structures

We will use three data structures.

1\. `copiesByKey`: `HashMap<CopyKey, Copy>`

Maps `(shop, movie)` to the corresponding copy, including its fixed price.

Why? `rent` and `drop` receive a shop and movie. We should locate the copy directly instead of scanning all entries.

2\. `availableByMovie`: `HashMap<Integer, TreeSet<Copy>>`

Each movie maps to its available copies, sorted by:

```
price → shop
```

Why? `search(movie)` only needs copies of one movie. We can retrieve that movie's sorted set directly and read its first five elements.

3\. `rentedCopies`: `TreeSet<Copy>`

Contains every currently rented copy, sorted by:

```
price → shop → movie
```

Why? `report()` must compare copies of different movies and shops. One global ordered set provides the correct ordering.

### Step 2: Define the identity and ordering correctly

We will use Java records for immutable data.

```
private record CopyKey(int shop, int movie) {}

private record Copy(int shop, int movie, int price) {}
```

`CopyKey` identifies a physical copy, while `Copy` holds its immutable attributes.

Notice that the sort orders are deliberately different:

```
Available copies of one movie:
    price → shop

All rented copies:
    price → shop → movie
```

The movie ID is unnecessary in the first comparator because each available set contains copies of only one movie. It is required in the global rented set to resolve all ties.

A `TreeSet` uses its comparator to determine whether two elements are equivalent for set membership. If a comparator returns zero for two different elements, one can be discarded. Therefore, the rented comparator must distinguish copies by movie ID after comparing price and shop.

### Step 3: Keep the indexes synchronized

| Operation           | Available index | Rented index    |
| ------------------- | --------------- | --------------- |
| Initialize          | Add every copy  | Empty           |
| `rent(shop, movie)` | Remove the copy | Add the copy    |
| `drop(shop, movie)` | Add the copy    | Remove the copy |
| `search(movie)`     | Read first five | Unchanged       |
| `report()`          | Unchanged       | Read first five |

The price and identity of a copy never change. Only its membership in the two ordered indexes changes.

## 5. Complete Java 24 implementation

This is the implementation I would recommend presenting in an interview. It uses records, immutable copy data, clear comparator definitions, and small helper methods.

```
import java.util.ArrayList;
import java.util.Comparator;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.TreeSet;

class MovieRentingSystem {

    /*
     * A shop/movie pair uniquely identifies a physical movie copy.
     *
     * Why use a record?
     * - It gives us immutable fields, equals(), and hashCode().
     * - HashMap can use it as a reliable composite key.
     * - We avoid error-prone manual key encoding, such as shop * 100_000 + movie.
     */
    private record CopyKey(int shop, int movie) {}

    /*
     * A movie copy's shop, movie ID, and price never change.
     *
     * We do not store a mutable "rented" flag here. Rental state is represented
     * by membership in the appropriate TreeSet, avoiding duplicated state
     * that could become inconsistent with the indexes.
     */
    private record Copy(int shop, int movie, int price) {}

    /*
     * Direct lookup:
     *
     * (shop, movie) -> Copy, including its fixed price.
     *
     * This lets rent() and drop() locate a copy in expected O(1) time.
     * It also avoids scanning entries to find a copy's price.
     */
    private final Map<CopyKey, Copy> copiesByKey = new HashMap<>();

    /*
     * Available index:
     *
     * movie ID -> all currently available copies of that movie.
     *
     * Each TreeSet is ordered by price, then shop.
     * Therefore, its iterator begins with the cheapest available copy.
     *
     * The map is sparse: we only need sets for movie IDs that have entries.
     */
    private final Map<Integer, TreeSet<Copy>> availableByMovie =
            new HashMap<>();

    /*
     * Rented index:
     *
     * One global TreeSet containing all rented copies.
     *
     * The ordering is price, then shop, then movie.
     * This is exactly the ordering required by report().
     */
    private final TreeSet<Copy> rentedCopies =
            new TreeSet<>(
                    Comparator.comparingInt(Copy::price)
                            .thenComparingInt(Copy::shop)
                            .thenComparingInt(Copy::movie)
            );

    /*
     * For a particular movie, shop ID resolves equal-price ties.
     *
     * Movie ID is not needed in this comparator because each set in
     * availableByMovie contains copies of exactly one movie.
     *
     * Since a shop carries at most one copy of a given movie, no two
     * distinct copies in this set can share both price and shop.
     */
    private static final Comparator<Copy> AVAILABLE_ORDER =
            Comparator.comparingInt(Copy::price)
                    .thenComparingInt(Copy::shop);

    public MovieRentingSystem(int n, int[][] entries) {

        /*
         * n is not required for the implementation: entries already specify
         * every available shop/movie copy.
         *
         * Build all indexes once. Initially, every copy is available and
         * no copy is rented.
         *
         * For M entries:
         * - HashMap insertion takes expected O(1) per entry.
         * - TreeSet insertion takes O(log M) per entry.
         * Total initialization: O(M log M).
         */
        for (int[] entry : entries) {
            int shop = entry[0];
            int movie = entry[1];
            int price = entry[2];

            Copy copy = new Copy(shop, movie, price);

            copiesByKey.put(new CopyKey(shop, movie), copy);

            availableByMovie
                    .computeIfAbsent(movie, ignored -> new TreeSet<>(AVAILABLE_ORDER))
                    .add(copy);
        }
    }

    public List<Integer> search(int movie) {

        /*
         * Retrieve the pre-sorted set for this movie.
         *
         * If the movie does not exist, there are no matching copies.
         * HashMap lookup takes expected O(1) time.
         */
        TreeSet<Copy> available = availableByMovie.get(movie);

        if (available == null || available.isEmpty()) {
            return List.of();
        }

        List<Integer> result = new ArrayList<>(5);

        /*
         * TreeSet iteration visits copies in price/shop order.
         * We only visit at most five elements, so we do not sort or scan
         * all copies belonging to the movie.
         *
         * Time: O(1 + min(5, K)) = O(1), where K is the number of
         * available copies of this movie. The constant 5 is fixed.
         *
         * Space: O(1) auxiliary space for at most five result elements.
         */
        for (Copy copy : available) {
            result.add(copy.shop());

            if (result.size() == 5) {
                break;
            }
        }

        return result;
    }

    public void rent(int shop, int movie) {

        /*
         * Find the exact copy in expected O(1) time.
         * The problem guarantees that this copy is currently available.
         */
        Copy copy = copiesByKey.get(new CopyKey(shop, movie));

        /*
         * Remove it from the movie's available set.
         *
         * TreeSet removal costs O(log K), where K is the size of that
         * movie's available set. Because Copy is immutable and its
         * comparator fields do not change, removal uses the same ordering
         * under which the copy was inserted.
         */
        TreeSet<Copy> available = availableByMovie.get(movie);
        available.remove(copy);

        /*
         * Add the same copy to the global rented set.
         *
         * TreeSet insertion costs O(log R), where R is the number of
         * rented copies after the transition.
         *
         * Both indexes are updated as part of the same operation:
         * the copy is no longer available and is now rented.
         */
        rentedCopies.add(copy);
    }

    public void drop(int shop, int movie) {

        /*
         * The problem guarantees that this copy is currently rented.
         * The price is recovered from the canonical copy record.
         */
        Copy copy = copiesByKey.get(new CopyKey(shop, movie));

        /*
         * Remove from the global rented index in O(log R).
         * The record's price, shop, and movie are unchanged, so the
         * comparator can locate the same element correctly.
         */
        rentedCopies.remove(copy);

        /*
         * Restore the copy to the available index for its movie.
         *
         * Insertion costs O(log K), where K is the resulting set size.
         * We reuse the existing set even if it temporarily became empty.
         */
        availableByMovie.get(movie).add(copy);
    }

    public List<List<Integer>> report() {

        if (rentedCopies.isEmpty()) {
            return List.of();
        }

        List<List<Integer>> result = new ArrayList<>(5);

        /*
         * The global TreeSet already enforces:
         *
         *   price ascending
         *   -> shop ascending
         *   -> movie ascending
         *
         * Therefore, no additional sorting is needed.
         *
         * We stop after five copies, so we never traverse all R rented
         * copies unless R < 5.
         *
         * Time: O(1) for the fixed five-element traversal.
         * Space: O(1) auxiliary space for at most five result pairs.
         */
        for (Copy copy : rentedCopies) {
            result.add(List.of(copy.shop(), copy.movie()));

            if (result.size() == 5) {
                break;
            }
        }

        return result;
    }
}
```

## 6. Walk through the example

Initial entries:

```
[0, 1, 5]
[0, 2, 6]
[0, 3, 7]
[1, 1, 4]
[1, 2, 7]
[2, 1, 5]
```

Initially, all copies are available and the rented set is empty.

### Operation 1: `search(1)`

The set for movie `1` contains:

```
(price=4, shop=1)
(price=5, shop=0)
(price=5, shop=2)
```

The iterator returns shops in the correct order:

```
[1, 0, 2]
```

### Operation 2: `rent(0, 1)`

The copy `(shop=0, movie=1, price=5)` moves between the indexes.

```
Available movie 1: [(1, 4), (2, 5)]
Rented copies:     [(0, 1, 5)]
```

For readability, the available entries above are `(shop, price)`; rented entries are `(shop, movie, price)`.

### Operation 3: `rent(1, 2)`

Movie `2` at shop `1` costs `7`, so it is removed from movie `2`'s available set and added to the global rented set.

```
Rented copies, ordered by price/shop/movie:

(shop=0, movie=1, price=5)
(shop=1, movie=2, price=7)
```

### Operation 4: `report()`

The rented set is already sorted, so the method returns:

```
[[0, 1], [1, 2]]
```

### Operation 5: `drop(1, 2)`

The copy is removed from the rented set and restored to the available set for movie `2`.

### Operation 6: `search(2)`

Movie `2` is now available at shops `0` and `1`, with prices `6` and `7`.

```
[0, 1]
```

The implementation produces the required output without sorting during any query.

## 7. Edge cases to watch out for

1. No available copies of a movie: `search(movie)` returns an empty list.
2. No rented copies: `report()` returns an empty list.
3. Fewer than five results: Return every matching copy without padding the result.
4. More than five results: Stop after the first five elements of the sorted set.
5. Equal prices: The comparator must apply the correct tie-breakers, not just price.
6. Same shop, different movies: These are distinct copies. The global rented comparator includes movie ID.
7. Renting the cheapest copy: Removing it from the available set automatically makes the next-cheapest copy the first result.
8. Returning a copy: It must reappear at its original position according to price and shop.
9. Repeated rent/drop cycles: Immutable records ensure that a copy's comparator fields never change while it is stored in a `TreeSet`.
10. Missing movie IDs: The map lookup may return `null`; `search` handles this case explicitly.

## 8. Time and space complexity

Let:

- \\(M\\) = total number of movie copies.
- \\(K\\) = number of available copies for the queried movie.
- \\(R\\) = number of currently rented copies.

| Operation           | Time complexity  | Reason                                                              |
| ------------------- | ---------------- | ------------------------------------------------------------------- |
| Constructor         | \\(O(M\log M)\\) | Each copy is inserted into a `TreeSet`                              |
| `search(movie)`     | \\(O(1)\\)       | Hash lookup plus at most five iterations                            |
| `rent(shop, movie)` | \\(O(\log M)\\)  | Expected \\(O(1)\\) lookup and two ordered-set updates              |
| `drop(shop, movie)` | \\(O(\log M)\\)  | Expected \\(O(1)\\) lookup and two ordered-set updates              |
| `report()`          | \\(O(1)\\)       | At most five iterations                                             |
| Total space         | \\(O(M)\\)       | Each copy is stored in the lookup map and exactly one ordered index |

The \\(O(1)\\) query bounds for `search` and `report` assume the required result limit remains fixed at five. More generally, if the limit were \\(L\\), returning the results would take \\(O(L)\\) time.

The logarithmic bounds for `rent` and `drop` use \\(M\\) as an upper bound on the size of either ordered set. More precisely, each operation performs updates costing \\(O(\log K+\log R)\\), bounded by \\(O(\log M)\\).

One important correction to the brute-force comparison: without a direct lookup map, the brute-force implementation's `rent` and `drop` also cost \\(O(M)\\), because each must scan for the copy. Adding a `HashMap` makes those operations expected \\(O(1)\\), even before introducing the ordered indexes.

## 9. Interviewer follow-up questions and answers

Q1. Why use `TreeSet` instead of `PriorityQueue`?

A priority queue gives efficient access to its minimum element, but it does not efficiently remove an arbitrary copy when it is rented or returned. Here, a copy must be removed from one index and inserted into another immediately. `TreeSet` supports both operations in \\(O(\log M)\\) while preserving sorted iteration.

Q2. Why not sort a list each time?

Because the system can receive up to \\(10^5\\) operations. Repeatedly sorting large collections wastes work. Maintaining ordered indexes moves the cost to updates and makes queries much cheaper.

Q3. Why do we need two ordered indexes?

Search and report have different filtering and ordering requirements. Search is restricted to one movie, whereas report compares all rented movies globally. One global set alone would make movie-specific search expensive; separate sets keep both operations efficient.

Q4. Why use a record instead of a mutable class?

The copy's identity attributes and price do not change. Records express that immutability clearly and provide value-based equality and hashing. More importantly, changing comparator fields while an object is inside a `TreeSet` can corrupt the set's ordering.

Q5. Could we use lazy deletion with heaps?

Yes. We could maintain heaps and ignore stale entries when they reach the top. However, repeated rental transitions can accumulate stale entries, complicating correctness and potentially increasing memory usage. Since this problem requires frequent arbitrary removals, `TreeSet` is a cleaner fit.

Q6. What if the system allowed a configurable result limit instead of five?

The same data structures would work. The query would take \\(O(L)\\) time to return \\(L\\) results, rather than constant time. The ordered indexes would still avoid scanning or sorting all copies.

Q7. What is the most important invariant to explain?

Every copy belongs to exactly one state: available or rented. The canonical lookup map preserves the copy's identity and price, while the two ordered indexes represent its current state. Every successful transition removes the copy from one index and inserts it into the other.

Q8. Is this design thread-safe?

No. `HashMap` and `TreeSet` are not designed for unsynchronized concurrent mutations. A concurrent production implementation would need synchronization or an appropriate locking strategy to ensure that both indexes are updated atomically.

## 10. How to derive this solution in an interview

Follow this reasoning rather than memorizing the implementation.

1. Identify the operations and their output ordering.
2. Recognize that `search` and `report` both require the cheapest five items.
3. Notice that sorting during every query repeats work.
4. Ask whether the required order can be maintained as items change state.
5. Use one ordered index for available copies of each movie and one global ordered index for rented copies.
6. Add a hash map so that the system can locate a copy by `(shop, movie)` immediately.
7. Define comparators carefully, including every tie-breaker.
8. Verify that `rent` and `drop` update both indexes consistently.

The central insight is simple: when a problem repeatedly asks for the smallest few elements of a changing collection, consider maintaining an ordered index rather than sorting from scratch for every query.
