# 1472. Design Browser History — Java 24

The key to this problem is recognizing that browser history is a sequence with a current position, and visiting a new URL deletes everything after that position.

We can solve it using an `ArrayList` and a current index, a doubly linked list, or even two stacks. The `ArrayList` approach is particularly straightforward because the constraints allow at most 5,000 operations.

## 0. Simplify the problem

Imagine browsing these pages:

```
leetcode.com → google.com → facebook.com → youtube.com
```

You are currently on `youtube.com`.

- `back(1)` takes you to `facebook.com`.
- `back(1)` again takes you to `google.com`.
- `forward(1)` takes you to `facebook.com`.
- `visit("linkedin.com")` creates a new path from `facebook.com`.

The important rule: visiting a new URL clears the forward history.

```
Before visiting linkedin.com:

leetcode.com → google.com → facebook.com → youtube.com
                            ↑ current

After visiting linkedin.com:

leetcode.com → google.com → facebook.com → linkedin.com
                            ↑ current
```

`youtube.com` is no longer part of the browser history.

## 1. Clarifying questions to ask the interviewer

These questions help establish the invariants and avoid implementing behavior that the problem doesn't require.

1. Can the browser move beyond the homepage or the last visited page? No. `back()` stops at the homepage, and `forward()` stops at the latest page in the history.
2. Does visiting a URL discard all forward history? Yes. This is the defining behavior of `visit()`.
3. Can a URL appear more than once? Yes, unless otherwise restricted. We must store visits as history entries, not use a set of unique URLs.
4. Are the operation count and `steps` bounded? Yes. There are at most 5,000 calls, and `steps` is at most 100. This makes a simple array-backed solution more than sufficient.

## 2. Core idea: history plus a pointer

Think of browser history as an array and the current page as an index into that array.

For example:

```
Index:    0          1           2            3
       leetcode → google → facebook → youtube
                              ↑
                         current = 2
```

We maintain two pieces of state:

- `history`: the URLs in the current browsing path.
- `current`: the index of the page currently displayed.

Each operation becomes a simple index or list update:

| Operation        | Action                                                                              |
| ---------------- | ----------------------------------------------------------------------------------- |
| `visit(url)`     | Delete entries after `current`, append `url`, move `current` to the new last index. |
| `back(steps)`    | Move `current` left, stopping at index `0`.                                         |
| `forward(steps)` | Move `current` right, stopping at the last index.                                   |

The most important invariant is:

Every URL after `current` represents forward history, and every URL before it represents backward history.

## 3. Step-by-step walkthrough

Let's trace the example using the array-and-pointer model.

| Operation         | History                                  | Current index | Result     |
| ----------------- | ---------------------------------------- | ------------- | ---------- |
| Initialize        | `[leetcode]`                             | 0             | —          |
| `visit(google)`   | `[leetcode, google]`                     | 1             | —          |
| `visit(facebook)` | `[leetcode, google, facebook]`           | 2             | —          |
| `visit(youtube)`  | `[leetcode, google, facebook, youtube]`  | 3             | —          |
| `back(1)`         | Same                                     | 2             | `facebook` |
| `back(1)`         | Same                                     | 1             | `google`   |
| `forward(1)`      | Same                                     | 2             | `facebook` |
| `visit(linkedin)` | `[leetcode, google, facebook, linkedin]` | 3             | —          |
| `forward(2)`      | Same                                     | 3             | `linkedin` |
| `back(2)`         | Same                                     | 1             | `google`   |
| `back(7)`         | Same                                     | 0             | `leetcode` |

Notice that `visit(linkedin)` removes `youtube` because the browser was at index `2` before the visit.

## 4. Solutions from brute force to optimal

### Solution 1: ArrayList with a current index — recommended

This is the simplest approach to explain and implement in an interview.

```java
import java.util.ArrayList;
import java.util.List;

class BrowserHistory {

    // Stores the active browsing path in chronological order.
    // Entries after current represent forward history.
    private final List<String> history;

    // Index of the page currently displayed.
    private int current;

    public BrowserHistory(String homepage) {
        history = new ArrayList<>();
        history.add(homepage);
        current = 0;

        // Invariant: 0 <= current < history.size().
        // There is always at least one page: the homepage.
    }

    public void visit(String url) {
        // Everything after current is forward history.
        // A new visit invalidates that entire future path.
        //
        // Example:
        // [A, B, C, D], current = 1
        // Visiting X produces [A, B, X].
        //
        // Remove from the end so every removal is O(1)
        // amortized for ArrayList.
        while (history.size() > current + 1) {
            history.remove(history.size() - 1);
        }

        // Append the new page after the current page.
        history.add(url);

        // The newly visited URL becomes the current page.
        current = history.size() - 1;
    }

    public String back(int steps) {
        // Never move before the homepage (index 0).
        // Math.max clamps the requested position to the boundary.
        current = Math.max(0, current - steps);

        // Return the URL at the final, possibly clamped position.
        return history.get(current);
    }

    public String forward(int steps) {
        // Never move beyond the latest page in the active history.
        // history.size() - 1 is the final valid index.
        current = Math.min(history.size() - 1, current + steps);

        return history.get(current);
    }
}

/*
 * COMPLEXITY ANALYSIS
 *
 * Let H be the maximum number of URLs stored in the active history.
 *
 * Constructor:
 *   Time:  O(1)
 *   Space: O(1) initially, excluding the homepage string.
 *
 * visit(url):
 *   Time:  O(H) worst case, because it may remove many forward entries.
 *          Appending is O(1) amortized.
 *   Space: O(1) auxiliary space; O(H) total history space.
 *
 * back(steps):
 *   Time:  O(1)
 *   Space: O(1)
 *
 * forward(steps):
 *   Time:  O(1)
 *   Space: O(1)
 *
 * Why is ArrayList a good choice?
 *   - We need random access to the current URL.
 *   - Moving back and forward is an index update, not traversal.
 *   - Removing entries from the end avoids shifting elements.
 *   - The implementation is compact and preserves the problem's
 *     required semantics without extra data structures.
 *
 * Across N operations, total time is O(N + total URLs removed),
 * which is O(N) amortized when counting each inserted URL and each
 * removal once. The history uses O(H) space.
 */
```

Interview note: This is the implementation I would present first. Although an individual `visit()` can remove \\(O(H)\\) entries, each inserted history entry can be removed at most once. Therefore, over a sequence of operations, the total cost of all those removals is linear in the number of inserted entries.

### Solution 2: Two stacks

Another way to think about the problem is to divide the history into two groups:

- `backStack`: pages behind the current page, with the nearest previous page on top.
- `forwardStack`: pages ahead of the current page, with the nearest next page on top.

The current page is stored separately.

```java
import java.util.ArrayDeque;
import java.util.Deque;

class BrowserHistory {

    // The top of backStack is the immediately previous page.
    private final Deque<String> backStack = new ArrayDeque<>();

    // The top of forwardStack is the immediately next page.
    private final Deque<String> forwardStack = new ArrayDeque<>();

    private String current;

    public BrowserHistory(String homepage) {
        current = homepage;
    }

    public void visit(String url) {
        // The old current page becomes the previous page.
        backStack.push(current);

        // Visiting a new URL invalidates every forward entry.
        forwardStack.clear();

        // Display the new URL.
        current = url;
    }

    public String back(int steps) {
        // Move backward until we exhaust the requested steps
        // or reach the homepage (an empty backStack).
        while (steps-- > 0 && !backStack.isEmpty()) {
            // The page we leave becomes the next forward page.
            forwardStack.push(current);

            // The most recent previous page becomes current.
            current = backStack.pop();
        }

        return current;
    }

    public String forward(int steps) {
        // Move forward until we exhaust the requested steps
        // or there are no more forward pages.
        while (steps-- > 0 && !forwardStack.isEmpty()) {
            // The page we leave becomes available for going back.
            backStack.push(current);

            // The closest forward page becomes current.
            current = forwardStack.pop();
        }

        return current;
    }
}

/*
 * COMPLEXITY
 *
 * visit(url):
 *   O(F) time in the worst case because forwardStack.clear()
 *   discards F forward entries. Other stack operations are O(1).
 *
 * back(steps):
 *   O(min(steps, B)) time, where B is the number of previous pages.
 *
 * forward(steps):
 *   O(min(steps, F)) time, where F is the number of forward pages.
 *
 * Space: O(H), where H is the total number of retained history entries.
 *
 * This is a natural model when you think in terms of undo/redo:
 * going backward moves a page from one stack to the other, while
 * making a new visit clears the redo stack.
 */
```

The two-stack approach is valid and intuitive, especially if you have already solved problems involving undo/redo functionality. Its navigation operations, however, are \\(O(\text{steps})\\), whereas the array-and-index approach makes them \\(O(1)\\).

### Solution 3: Doubly linked list

A doubly linked list can represent each page as a node, with a pointer to the currently displayed node. Each node points to its previous and next pages.

```
null ← [A] ⇄ [B] ⇄ [C] → null
                ↑
              current
```

```java
class BrowserHistory {

    // Each page knows its immediate predecessor and successor.
    private static final class Page {
        final String url;
        Page previous;
        Page next;

        Page(String url) {
            this.url = url;
        }
    }

    private Page current;

    public BrowserHistory(String homepage) {
        current = new Page(homepage);
    }

    public void visit(String url) {
        // Discard the entire forward chain.
        // Detaching the first forward node makes it unreachable
        // from the current browsing path.
        current.next = null;

        // Append the new page after the current page.
        Page nextPage = new Page(url);
        nextPage.previous = current;
        current.next = nextPage;

        // The new page is now displayed.
        current = nextPage;
    }

    public String back(int steps) {
        // Follow previous pointers until the requested distance
        // is covered or the homepage boundary is reached.
        while (steps-- > 0 && current.previous != null) {
            current = current.previous;
        }

        return current.url;
    }

    public String forward(int steps) {
        // Follow next pointers until the requested distance
        // is covered or no next page exists.
        while (steps-- > 0 && current.next != null) {
            current = current.next;
        }

        return current.url;
    }
}

/*
 * COMPLEXITY
 *
 * visit(url):
 *   O(1) time, excluding garbage collection of discarded nodes.
 *   A single pointer update disconnects the forward chain.
 *
 * back(steps):
 *   O(min(steps, B)) time, where B is the available backward distance.
 *
 * forward(steps):
 *   O(min(steps, F)) time, where F is the available forward distance.
 *
 * Space: O(H) for the nodes in the active history.
 *
 * Advantage:
 *   - Visiting a page is O(1), with no loop to delete forward entries.
 *   - Previous/next navigation is directly represented by pointers.
 *
 * Trade-off:
 *   - More code and pointer management.
 *   - Back and forward require traversal rather than a direct index jump.
 *   - Discarded nodes become eligible for garbage collection, but
 *     reclaiming their memory is not guaranteed to happen immediately.
 */
```

### Solution 4: Simple array with a manually managed size

If you know an upper bound for the number of visited pages, a fixed-size array is also possible. It avoids `ArrayList` resizing, but requires capacity management or a sufficiently large allocation.

The central operations are the same as Solution 1:

- `history[0 ... size - 1]` stores the active path.
- `current` stores the current index.
- On a visit, set `size = current + 1`, write the new URL at `history[size]`, increment `size`, and update `current`.
- On back/forward, clamp the index to the valid range.

Because this problem allows 5,000 calls, the maximum number of visited pages is bounded by 5,001, including the homepage. A fixed array can therefore work, but the `ArrayList` implementation is cleaner and avoids hardcoding the capacity.

### Comparing the approaches

| Approach            | `visit` worst case | `back` / `forward`    | Extra structure    |
| ------------------- | ------------------ | --------------------- | ------------------ |
| `ArrayList` + index | \\(O(H)\\)         | \\(O(1)\\)            | List and integer   |
| Two stacks          | \\(O(F)\\)         | \\(O(\text{steps})\\) | Two stacks         |
| Doubly linked list  | \\(O(1)\\)         | \\(O(\text{steps})\\) | Nodes and pointers |
| Fixed array + index | \\(O(1)\\)         | \\(O(1)\\)            | Array and integers |

Here, \\(H\\) is the history size and \\(F\\) is the forward-history size.

The array-backed approach is the best fit for this problem because the current position is an integer index, so navigation is constant time. The other approaches are useful alternatives to discuss, rather than necessary optimizations.

## 5. Edge cases to watch out for

1. Back beyond the homepage
   ```
   back(100); // Returns the homepage if there is no earlier page.
   ```
   Clamp the current index to `0`.
2. Forward beyond the latest page
   ```
   forward(100); // Returns the latest page in the history.
   ```
   Clamp the current index to `history.size() - 1`.
3. Visiting after going backward
   ```
   A → B → C → D
       ↑ current

   visit(X)

   A → B → X
   ```
   Remove all entries after the current position before appending the new URL.
4. Visiting immediately after initialization
   ```
   A → B
   ```
   The new page must become the current page, with the homepage still available for `back(1)`.
5. Repeated URLs
   ```
   A → B → A
   ```
   These are separate history entries. Do not use a `Set` to deduplicate URLs.
6. The current page is already at a boundary

   Calling `back(1)` at the homepage or `forward(1)` at the last page must leave the current URL unchanged.

## 6. How to identify this pattern in an interview

When you see a design problem involving history, ask yourself these questions:

1. Is the data a sequence? Yes. Browser visits form an ordered sequence.
2. Is there a current position? Yes. The browser displays one of the stored URLs.
3. Can the user navigate in both directions? Yes. This suggests either an index, two stacks, or bidirectional pointers.
4. Does a new action invalidate the future? Yes. Visiting after going backward destroys forward history.
5. Can I express the state with a small invariant? Yes: the current index is valid, and everything after it is forward history.

That reasoning leads naturally to an array-backed sequence and an index.

## 7. Interviewer follow-up questions and answers

Q1. Why not use a `HashMap`?

A map provides lookup by key, but browser history requires ordering, repeated URLs, and navigation by position. A map alone does not model these requirements.

Q2. Why is `ArrayList` better than a singly linked list here?

We need direct access to the page at the current index. An `ArrayList` supports indexed access in \\(O(1)\\), while a singly linked list would require traversal to reach a particular position.

Q3. Can we make `visit()` worst-case \\(O(1)\\)?

Yes. A doubly linked list can discard the forward chain by setting `current.next = null`, then append the new node in constant time. The trade-off is that back and forward navigation require traversing nodes.

Q4. What is the amortized time complexity of the `ArrayList` implementation?

Across \\(N\\) operations, the total time is \\(O(N)\\), assuming each visit inserts one URL and each inserted URL can be removed at most once. More precisely, this bound is for the sequence of operations; an individual `visit()` may take \\(O(H)\\) time when it discards a long forward history.

Q5. What if the interviewer changes the requirements to support multiple tabs?

Each tab should have its own history state. A map from tab IDs to independent browser-history instances would let each tab maintain its own current page and navigation path.

Q6. What if we need a persistent browser history that survives application restarts?

The in-memory data structure would need to be backed by persistent storage, such as a database or a log. We would also need to define which history changes must be committed and how the current position is restored.

Q7. Why is the current index an invariant rather than just an implementation detail?

It is the key fact that makes the design correct. Every operation must preserve:

\\[ 0 \leq current < history.size() \\]

The homepage is always present, so the history never becomes empty. `back()` and `forward()` clamp the index to valid bounds, while `visit()` truncates the future and then appends a new page.

Final recommendation: Present the `ArrayList` plus current-index implementation first. It is the clearest solution, provides \\(O(1)\\) back/forward operations, and is easy to verify using the history invariant. Discuss two stacks and a doubly linked list if the interviewer asks for alternatives or changes the operation requirements.
