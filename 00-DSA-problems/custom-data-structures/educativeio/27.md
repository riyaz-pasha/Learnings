# 732. My Calendar III — Java 24 Interview Solution

Difficulty: Hard Core pattern: Sweep Line + Ordered Map, with a Segment Tree as an alternative for more advanced implementations.

The most important thing to understand is that we are not trying to find which events overlap each other directly. We are trying to find the maximum number of events active at the same time, after each new booking.

## 0. Simplify the problem

Imagine you manage rooms for meetings. Every booking has a start time and an end time:

`[startTime, endTime)`

The interval is start-inclusive and end-exclusive. An event is active at its start time but no longer active at its end time.

For example:

Bookings on a timeline

A

10 ━━━━━ 20

B

10 ━━━━━━━━━━━━━ 40

C

5 ━━━━━━━ 15

Between time 10 and time 15, all three events are active. Therefore, the maximum overlap is `3`.

The `book(startTime, endTime)` method must return the maximum overlap across the entire calendar after including the new event, not just the overlap involving that new event.

For example:

```java
MyCalendarThree calendar = new MyCalendarThree();

calendar.book(10, 20); // 1
calendar.book(10, 40); // 2
calendar.book(5, 15);  // 3
calendar.book(50, 60); // 3, not 1
```

Notice the last call: even though the new event does not overlap the previous ones, the calendar's historical maximum is still `3`.

## 1. Clarifying questions to ask the interviewer

These questions establish the assumptions behind the implementation.

1. Are intervals start-inclusive and end-exclusive? Why: This determines how adjacent events behave. `[10, 20)` and `[20, 30)` do not overlap, so they must not produce a maximum of `2`.
2. Can bookings arrive in arbitrary order? Why: We should not assume bookings are sorted by start time. A data structure that supports ordered time points handles arbitrary booking order naturally.
3. Must we return the maximum overlap after every booking? Why: Yes, that means we need to maintain or recompute the global maximum, not merely count overlaps with the latest event.
4. What are the constraints on time values and number of bookings? Why: Here, times can reach \\(10^9\\), but there are at most 400 bookings. This makes an ordered map particularly attractive; scanning the entire timeline or allocating an array indexed by time is inappropriate.
5. Can a booking be rejected if it overlaps another booking? Why: No. Unlike My Calendar I, overlapping bookings are allowed. We count how many events overlap instead of rejecting conflicts.

## 2. Core intuition: Think in terms of changes, not events

The key observation is that an event only changes the number of active bookings at two moments:

- At `startTime`, the active count increases by `1`.
- At `endTime`, the active count decreases by `1`.

Instead of repeatedly comparing every event with every other event, we can represent these changes on a timeline.

### Example: Three bookings

Suppose we book:

```
[10, 20)
[10, 40)
[5, 15)
```

Each booking contributes two changes:

| Time | Change | Why                           |
| ---- | ------ | ----------------------------- |
| 5    | +1     | Third event starts            |
| 10   | +2     | First and second events start |
| 15   | -1     | Third event ends              |
| 20   | -1     | First event ends              |
| 40   | -1     | Second event ends             |

Now process these changes in ascending time order.

```
Time     Change     Active bookings     Maximum so far
------------------------------------------------------
  5        +1              1                   1
 10        +2              3                   3
 15        -1              2                   3
 20        -1              1                   3
 40        -1              0                   3
```

The answer is `3`.

### The mental model

```
Booking [start, end)
         |         |
         v         v
        +1        -1

Sort all time points
        |
        v
Apply changes from left to right
        |
        v
Track current active bookings
        |
        v
Return the largest active count
```

This technique is called the sweep-line algorithm: imagine a vertical line moving across the timeline while maintaining the number of active events.

The crucial insight is that we only need to inspect event boundaries. Between two consecutive boundaries, the active booking count cannot change.

## 3. Edge cases to watch out for

- Adjacent events: `[10, 20)` and `[20, 30)` have maximum overlap `1`, not `2`.
- Same start time: `[10, 20)` and `[10, 40)` overlap immediately, giving `2`.
- Same end time: `[10, 30)` and `[20, 30)` both stop at time `30`; the count must decrease by `2`.
- Nested intervals: `[10, 100)`, `[20, 30)`, and `[25, 35)` produce a maximum of `3`.
- Disjoint bookings: The answer stays at the historical maximum even when the new event is far away.
- Repeated identical bookings: Each booking contributes another `+1` and `-1`, so the overlap count increases accordingly.
- Very large times: Do not allocate an array of size \\(10^9+1\\). Use an ordered map or a dynamic segment tree.
- End-exclusive boundaries: Process the net change at a timestamp before evaluating the active count for the interval immediately after that timestamp. With the delta-map approach, combining all changes at a timestamp handles this naturally.

## 4. Solution 1 — Brute force

The simplest correct approach is to store every booking and recompute the answer after each new booking.

At each call:

1. Save the new interval.
2. Collect all start and end times.
3. At each distinct boundary, count the bookings active immediately after that boundary.
4. Return the largest count.

We do not need to test arbitrary times because the active count changes only at event boundaries.

```java
import java.util.ArrayList;
import java.util.List;
import java.util.TreeSet;

class MyCalendarThreeBruteForce {

    // Store every booking. We never reject a booking because overlap is allowed.
    private final List<Booking> bookings = new ArrayList<>();

    // A record makes the immutable representation of one interval explicit.
    private record Booking(int start, int end) {}

    public int book(int startTime, int endTime) {
        // Step 1: Include the new booking before calculating the answer.
        bookings.add(new Booking(startTime, endTime));

        // Step 2: Only event boundaries can change the active count.
        // TreeSet sorts them and removes duplicates.
        TreeSet<Integer> boundaries = new TreeSet<>();

        for (Booking booking : bookings) {
            boundaries.add(booking.start());
            boundaries.add(booking.end());
        }

        int maximumOverlap = 0;

        // Step 3: At each boundary t, count intervals active at t.
        // An interval [start, end) is active exactly when:
        // start <= t && t < end.
        //
        // This correctly excludes events that end at t and includes
        // events that begin at t.
        for (int time : boundaries) {
            int activeBookings = 0;

            for (Booking booking : bookings) {
                if (booking.start() <= time && time < booking.end()) {
                    activeBookings++;
                }
            }

            maximumOverlap = Math.max(maximumOverlap, activeBookings);
        }

        // Step 4: Return the maximum over the entire calendar.
        return maximumOverlap;
    }

    /*
     * Complexity after the n-th booking:
     *
     * Time: O(n^2 + n log n).
     * - Collecting boundaries: O(n log n) because TreeSet insertion
     *   takes O(log n) per endpoint.
     * - There are at most 2n distinct boundaries.
     * - At each boundary, we scan all n bookings: O(n^2).
     * - Total: O(n^2).
     *
     * Auxiliary space: O(n) for the distinct boundaries.
     * Stored bookings: O(n).
     *
     * Why this is not optimal:
     * We repeatedly recount all active bookings from scratch.
     * Still, it is a useful baseline for explaining correctness.
     */
}
```

For at most 400 bookings, this is perfectly reasonable. However, interviewers usually expect you to recognize that the same information can be maintained incrementally.

## 5. Solution 2 — Sweep line with `TreeMap` (recommended)

This is the most natural solution for the given constraints.

Instead of storing all events, maintain a map:

```
time -> net change in active bookings
```

For example, booking `[10, 20)` performs:

```
delta.merge(10,  1, Integer::sum);
delta.merge(20, -1, Integer::sum);
```

When another booking starts at time `10`, its `+1` is combined with the existing change at `10`.

### Why `TreeMap`?

A regular `HashMap` cannot guarantee chronological iteration. A `TreeMap` keeps the timestamps sorted, which allows us to sweep through the timeline directly.

```java
import java.util.Map;
import java.util.TreeMap;

class MyCalendarThree {

    // Key: timestamp.
    // Value: net change in the number of active bookings at that timestamp.
    //
    // TreeMap maintains timestamps in ascending order.
    // This is essential because the active count must be calculated
    // chronologically.
    private final TreeMap<Integer, Integer> deltaByTime = new TreeMap<>();

    public int book(int startTime, int endTime) {
        // Every booking increases the active count at its start.
        // merge() adds to an existing change rather than overwriting it.
        deltaByTime.merge(startTime, 1, Integer::sum);

        // Every booking decreases the active count at its end.
        // Because intervals are end-exclusive, the event is no longer
        // active at endTime.
        deltaByTime.merge(endTime, -1, Integer::sum);

        int activeBookings = 0;
        int maximumOverlap = 0;

        // Sweep across all known boundaries in ascending order.
        //
        // For each timestamp:
        // 1. Apply the combined change at that timestamp.
        // 2. Update the maximum active count.
        //
        // Combining all changes at the same timestamp is important.
        // For example, one event ending at 20 and another starting at 20
        // have net change -1 + 1 = 0. There is no extra overlap.
        for (int change : deltaByTime.values()) {
            activeBookings += change;
            maximumOverlap = Math.max(maximumOverlap, activeBookings);
        }

        // The answer is the maximum overlap anywhere in the calendar,
        // including regions that do not overlap the latest booking.
        return maximumOverlap;
    }

    /*
     * Complexity:
     *
     * Let n = number of bookings already made, including the new booking.
     * There are at most 2n distinct timestamps.
     *
     * book():
     * - Two TreeMap updates: O(log n).
     * - Sweep over all distinct timestamps: O(n).
     * - Total time per booking: O(n).
     *
     * Across N bookings:
     * O(N^2) total time in the worst case.
     *
     * Space:
     * O(n) for at most 2n timestamp entries.
     *
     * Why this is a strong interview answer:
     * - The code directly expresses the sweep-line idea.
     * - It handles arbitrary booking order.
     * - It handles duplicate boundaries without special cases.
     * - It uses memory proportional to the number of bookings,
     *   not the size of the time domain.
     *
     * Interview nuance:
     * TreeMap updates are logarithmic, but the full sweep is linear.
     * Therefore, the entire book() method is O(n), not O(log n).
     */
}
```

### Walk through the first three bookings

Initially, the map is empty.

Booking 1: `[10, 20)`

```
10 -> +1
20 -> -1
```

Sweep:

```
At 10: active = 1, maximum = 1
At 20: active = 0, maximum = 1

Return 1
```

Booking 2: `[10, 40)`

The second booking adds `+1` at `10` and `-1` at `40`.

```
10 -> +2
20 -> -1
40 -> -1
```

Sweep:

```
At 10: active = 2, maximum = 2
At 20: active = 1, maximum = 2
At 40: active = 0, maximum = 2

Return 2
```

Booking 3: `[5, 15)`

The resulting map is:

```
 5 -> +1
10 -> +2
15 -> -1
20 -> -1
40 -> -1
```

Sweep:

```
At  5: active = 1, maximum = 1
At 10: active = 3, maximum = 3
At 15: active = 2, maximum = 3
At 20: active = 1, maximum = 3
At 40: active = 0, maximum = 3

Return 3
```

Notice how each new booking changes only two entries in the map, but we still scan the entire map to obtain the maximum.

That observation leads to a more advanced alternative.

## 6. Solution 3 — Dynamic segment tree (faster per booking)

If the interviewer asks, "Can you do better than scanning every timestamp after every booking?", a dynamic segment tree is a good follow-up.

The time range is enormous, up to \\(10^9\\), so a normal array-based segment tree would waste too much memory. Instead, create tree nodes only for portions of the timeline that we actually update.

### The mental model

- Each booking adds `1` to every time slot in its interval.
- Each tree node stores the maximum overlap in its time range.
- A lazy value records an update that applies to an entire range, postponing updates to descendants until necessary.
- The root's maximum is the answer after every booking.

Because all input endpoints are integers, we can model the time slots as integer positions in `[0, 1_000_000_000)`. A booking `[start, end)` becomes an inclusive range update `[start, end - 1]`.

```java
class MyCalendarThreeSegmentTree {

    // All possible integer time slots are in [0, LIMIT).
    // Since endTime <= 1_000_000_000, the last valid slot is
    // 999_999_999.
    private static final int LIMIT = 1_000_000_000;

    // The root covers the entire time domain.
    private final Node root = new Node();

    private static final class Node {
        // Children are allocated only when a partial-range update needs them.
        private Node left;
        private Node right;

        // Maximum overlap among slots represented by this node.
        private int maximum;

        // Number of increments applied to this entire range but not yet
        // propagated to its children.
        private int lazy;
    }

    public int book(int startTime, int endTime) {
        // Convert [startTime, endTime) into the equivalent integer-slot
        // range [startTime, endTime - 1].
        add(root, 0, LIMIT - 1, startTime, endTime - 1);

        // Every booking adds one to its covered slots.
        // Therefore, the root always stores the global maximum overlap.
        return root.maximum;
    }

    private void add(
            Node node,
            int segmentStart,
            int segmentEnd,
            int queryStart,
            int queryEnd) {

        // Case 1: The current segment is entirely inside the booking.
        // Every slot in this segment gains one overlap.
        //
        // We do not need to visit its descendants. Store the update
        // lazily and update this segment's maximum immediately.
        if (queryStart <= segmentStart && segmentEnd <= queryEnd) {
            node.maximum++;
            node.lazy++;
            return;
        }

        // Compute the midpoint without risking integer overflow.
        int mid = segmentStart + (segmentEnd - segmentStart) / 2;

        // Case 2: The booking intersects only part of this segment.
        // Before descending, propagate any pending full-segment updates
        // so that the children represent the correct overlap counts.
        pushDown(node);

        // Recurse into the left half only if the booking intersects it.
        if (queryStart <= mid) {
            add(
                node.left,
                segmentStart,
                mid,
                queryStart,
                queryEnd
            );
        }

        // Recurse into the right half only if the booking intersects it.
        if (queryEnd > mid) {
            add(
                node.right,
                mid + 1,
                segmentEnd,
                queryStart,
                queryEnd
            );
        }

        // After updating the necessary children, recompute this segment's
        // maximum. Its maximum is the larger of its children's maxima.
        //
        // Any pending lazy increment was already propagated to the children,
        // so node.lazy is zero here.
        node.maximum = Math.max(
            node.left.maximum,
            node.right.maximum
        );
    }

    private void pushDown(Node node) {
        // Allocate children on demand rather than building a tree for
        // one billion time slots.
        if (node.left == null) {
            node.left = new Node();
        }
        if (node.right == null) {
            node.right = new Node();
        }

        // If this node has a pending full-range increment, both children
        // must inherit it before we perform a partial-range update.
        if (node.lazy != 0) {
            int pending = node.lazy;

            node.left.maximum += pending;
            node.left.lazy += pending;

            node.right.maximum += pending;
            node.right.lazy += pending;

            // The increment now lives in the children.
            node.lazy = 0;
        }
    }

    /*
     * Complexity:
     *
     * Let C = 1,000,000,000 and N = number of bookings.
     *
     * Time per booking:
     * O(log C), because a range update visits only the segment-tree
     * boundary paths and fully covered segments. Lazy propagation
     * prevents us from descending through every covered slot.
     *
     * Since C is fixed, this is effectively O(1) with respect to N,
     * although the more informative bound is O(log C).
     *
     * Space:
     * O(N log C) nodes in the worst case after N range updates.
     * Each update creates at most O(log C) new nodes along its
     * boundary paths, up to a constant factor.
     *
     * Why this is more complex:
     * - You must correctly implement range addition and lazy propagation.
     * - The root maximum is correct only if every child update and
     *   maximum recomputation preserves the segment-tree invariant.
     * - It is faster for many bookings, but harder to implement and debug.
     *
     * Important boundary detail:
     * We use [startTime, endTime - 1] only because the constraints
     * guarantee integer endpoints and the answer depends on overlap
     * between integer time slots. For arbitrary real-valued endpoints,
     * coordinate compression or a different representation is needed.
     */
}
```

## 7. Compare the approaches

Let \\(N\\) be the number of bookings so far and \\(C=10^9\\).

| Approach             | Time per booking | Space            | Best use                     |
| -------------------- | ---------------- | ---------------- | ---------------------------- |
| Brute force          | \\(O(N^2)\\)     | \\(O(N)\\)       | Establishing correctness     |
| `TreeMap` sweep line | \\(O(N)\\)       | \\(O(N)\\)       | Recommended for this problem |
| Dynamic segment tree | \\(O(\log C)\\)  | \\(O(N\log C)\\) | Faster range updates         |

Strictly speaking, the brute-force solution also sorts up to \\(2N\\) boundaries, so its full bound is \\(O(N^2)\\) per call. The segment tree has a larger implementation cost but avoids the repeated full sweep.

My interview recommendation: Start with the brute-force reasoning, derive the sweep-line solution, and implement the `TreeMap` version. The constraints of only 400 calls make it a clean, efficient, and maintainable answer. Present the dynamic segment tree if the interviewer specifically asks for faster updates.

## 8. Interviewer follow-up questions and answers

Q1. Why not just use a `HashMap`?

Because we need to process timestamps in chronological order. A `HashMap` does not guarantee sorted iteration. We would have to sort its keys separately.

Q2. Why do we update two timestamps per booking?

Because an event affects the active count only at its boundaries: `+1` when it starts and `-1` when it ends.

Q3. Why do we take the maximum after applying each delta?

After applying the net change at timestamp \\(t\\), the resulting count represents the interval immediately after \\(t\\), until the next timestamp. Since the count is constant between consecutive boundaries, inspecting these counts finds the global maximum.

Q4. What happens if an event ends at exactly the time another begins?

Their changes cancel at that timestamp: `-1 + 1 = 0`. The first event is no longer active when the second begins, so the two events do not overlap.

Q5. Why is the `TreeMap` solution \\(O(N)\\) per booking, even though inserting into it is \\(O(\log N)\\)?

There are at most \\(2N\\) distinct timestamps. Although the two map updates cost \\(O(\log N)\\), calculating the maximum requires iterating through all timestamps, which costs \\(O(N)\\).

Q6. Can we cache the maximum and avoid the sweep?

Not with only the two delta updates and a plain `TreeMap`. A new booking can increase overlap at a time far from the latest booking's endpoints, and deletions or changes in delta values can affect the global prefix maximum. Maintaining that maximum efficiently requires a more advanced data structure, such as a segment tree that supports range updates and maximum queries.

Q7. How does this differ from My Calendar I and My Calendar II?

- My Calendar I: Reject a booking if it overlaps any existing booking.
- My Calendar II: Reject a booking if it would cause a triple booking.
- My Calendar III: Accept every booking and report the maximum overlap seen so far.

The sweep-line technique is useful in all three, but the required behavior differs.

Q8. What should you say before coding?

A concise interview explanation would be:

> "Every booking contributes a `+1` at its start and a `-1` at its end. I'll store these changes in a sorted map, sweep through the timestamps in chronological order, maintain a running active count, and return its maximum. This avoids scanning every possible time value, and it uses space proportional to the number of distinct boundaries."

That explanation establishes the invariant, explains the data structure, and naturally leads to the implementation.

# My Calendar III (732) — How to Think About Sweep Line in an Interview

The goal is not to memorize the `TreeMap` solution. It is to learn how to look at a problem, recognize its underlying structure, and derive the solution yourself.

Let's build the idea from scratch, as if you were solving this problem in a senior Java interview.

## 1. First, forget the data structure. What is the problem really asking?

We receive bookings one at a time:

```
book(10, 20)
book(50, 60)
book(10, 40)
book(5, 15)
```

After every booking, we must return the maximum number of events happening simultaneously.

Imagine a calendar with time running from left to right.

Booking 1: [10, 20)

10

Event A

20

Maximum overlap = 1

Booking 2: [10, 40)

10

Event A + Event B

20

20

Event B

40

Maximum overlap = 2

The word to focus on is simultaneously.

We are not asked:

- How many bookings exist?
- How many events overlap the latest event?
- Which event starts first?
- How long is each event?

We are asked:

At what time is the number of active events largest?

That reframing is the first important interview skill.

### The first question to ask yourself

Whenever you see intervals, ask:

> Do I care about the individual intervals, or do I care about what happens at each point on the timeline?

For My Calendar III, the answer is the second one.

This tells us to reason about the timeline rather than compare every pair of bookings.

## 2. How to identify a sweep-line problem

Sweep line is not a trick specific to calendars. It is a general way to solve problems involving objects distributed over an ordered dimension, such as time or space.

Look for these clues:

- There are intervals, ranges, rectangles, or events.
- The question asks about overlap, coverage, concurrency, or the maximum number of active objects.
- Something changes at boundaries.
- Between consecutive boundaries, the situation stays unchanged.
- Processing boundaries in sorted order can replace checking every possible point.

Typical examples include:

| Problem                         | What changes as we sweep?                |
| ------------------------------- | ---------------------------------------- |
| Maximum meeting overlap         | Number of active meetings                |
| Minimum meeting rooms           | Number of simultaneously active meetings |
| Website concurrent users        | Number of active sessions                |
| Number of overlapping intervals | Active interval count                    |
| Skyline problem                 | Visible building heights                 |
| Rectangle union or overlap      | Active horizontal or vertical ranges     |

The exact data structure can differ. The common idea is that we sort the important boundary events and maintain just enough information about what is currently active.

### A mental checklist for interviews

When you see a problem involving intervals, walk through this sequence:

1. What is the quantity I need to maximize or minimize?
2. At which moments can that quantity change?
3. Can I process only those moments rather than every time value?
4. What state should I maintain while moving from left to right?
5. How can I obtain the final answer from that state?

For My Calendar III, the answers are:

1. Maximize the number of active bookings.
2. The count changes at booking starts and ends.
3. Yes, there are at most two boundaries per booking.
4. Maintain the active booking count.
5. Return the largest count seen during the sweep.

You have now derived the core algorithm before choosing a Java collection.

## 3. Build the solution from brute force instead of jumping to `TreeMap`

This is how I would guide myself through the interview.

### Step 1: Start with the most obvious solution

Suppose the bookings are:

```
A = [10, 20)
B = [10, 40)
C = [ 5, 15)
D = [25, 55)
```

One possible approach is to examine the timeline and count active events at every time.

At time `12`:

```
A: active
B: active
C: active
D: inactive

Count = 3
```

At time `30`:

```
A: inactive
B: active
C: inactive
D: active

Count = 2
```

The maximum is `3`.

But the time domain goes up to \\(10^9\\). Checking every possible time is impractical.

Interview question: Do we really need to inspect every time?

No. Between consecutive start and end times, the active events cannot change.

For example, if the only boundaries near a region are `10` and `20`, then the active count is constant throughout `[10, 20)`.

That gives us our first optimization:

> Check the boundaries, not every point in time.

### Step 2: Identify the important moments

For the four bookings above, the boundaries are:

```
A = [10, 20)  -> 10, 20
B = [10, 40)  -> 10, 40
C = [ 5, 15)  ->  5, 15
D = [25, 55)  -> 25, 55
```

Sort and deduplicate them:

```
5, 10, 15, 20, 25, 40, 55
```

Now the timeline is divided into regions:

```
       5       10      15      20      25             40      55
       |--------|-------|-------|-------|--------------|-------|
Region 1      Region 2 Region 3 Region 4 Region 5     Region 6

Active count:
       1         3       2       1       2             1
```

The exact count changes only at a boundary. Thus, we can reduce a billion possible time positions to at most \\(2N\\) relevant boundaries.

### Step 3: Stop recounting events. Track changes instead.

Now ask a more powerful question:

> When a booking starts or ends, how does the active count change?

Every booking has exactly two effects:

```
[start, end)

At start: +1
At end:   -1
```

We do not need to know which events are active individually if our only goal is to count them.

For the four bookings:

```
Booking A: [10, 20)  -> 10:+1, 20:-1
Booking B: [10, 40)  -> 10:+1, 40:-1
Booking C: [ 5, 15)  ->  5:+1, 15:-1
Booking D: [25, 55)  -> 25:+1, 55:-1
```

Combine changes that happen at the same timestamp:

```
Time:       5   10   15   20   25   40   55
Net change: +1  +2   -1   -1   +1   -1   -1
```

The `+2` at time `10` occurs because two bookings begin there.

Now we have transformed the original problem into a simpler one:

Given sorted changes, compute the maximum prefix sum.

This is the key mathematical reduction.

### Step 4: Derive the running-sum algorithm

Start with zero active bookings.

| Time | Net change | Active count | Maximum so far |
| ---- | ---------- | ------------ | -------------- |
| 5    | +1         | 1            | 1              |
| 10   | +2         | 3            | 3              |
| 15   | -1         | 2            | 3              |
| 20   | -1         | 1            | 3              |
| 25   | +1         | 2            | 3              |
| 40   | -1         | 1            | 3              |
| 55   | -1         | 0            | 3              |

The algorithm is now almost inevitable:

```
activeBookings += change;
maximumOverlap = Math.max(maximumOverlap, activeBookings);
```

The only remaining data-structure decision is how to keep the changes in chronological order.

Since new bookings can arrive in any order, we need an ordered structure. In Java, `TreeMap<Integer, Integer>` is a natural fit.

## 4. Sweep line explained from first principles

Let's understand what the term actually means.

Imagine a vertical line moving from left to right across a timeline. Everything to the left has already been processed; everything to the right has not.

At any moment, the algorithm maintains a summary of what is currently active.

For this problem:

```
Already processed         Current position          Not processed
------------------|-------------------------|--------------------
                  ^
             Sweep line
```

As the sweep line crosses a start boundary, a booking becomes active. As it crosses an end boundary, a booking stops being active.

The algorithm does not need to revisit the past. It only needs to update the current state.

### 4.1 The three building blocks of sweep line

1\. Events

An event describes something that changes the state.

For My Calendar III:

```
(startTime, +1)
(endTime,   -1)
```

2\. Ordering

Events must be processed in the order of their coordinates. Here, the coordinate is time.

3\. State

We maintain the information needed to answer the question. Here, it is the active booking count and its maximum.

Different sweep-line problems use different states:

- Maximum overlap: active count.
- Skyline: maximum active building height.
- Closest pair of points: a set of nearby candidate points.
- Rectangle union: covered length across a cross-section.

The sweep-line framework stays the same; the state and update rules change.

### 4.2 Why does sorting boundaries work?

Let the distinct boundaries be:

\\[ t_1 < t_2 < \cdots < t_m \\]

Consider any two consecutive boundaries \\(t_i\\) and \\(t\_{i+1}\\).

There is no event start or end between them. Therefore, no booking begins or ends in that region, and the active count remains constant.

Consequently, the maximum active count can be found by processing the changes at the sorted boundaries. We do not need to inspect any other time.

### 4.3 Why do we use a running sum?

Let \\(\Delta(t)\\) be the total change at time \\(t\\).

The active count immediately after processing timestamp \\(t_i\\) is:

\\[ A_i = \sum\_{j=1}^{i}\Delta(t_j) \\]

The answer is:

\\[ K = \max\_{1\le i\le m} A_i \\]

In plain English:

- Add all changes encountered so far.
- The sum tells us how many bookings are active in the current region.
- Keep the largest sum encountered.

This is why sweep line and prefix sums often appear together.

### 4.4 Why do the changes at the same timestamp need to be combined?

Consider:

```
A = [10, 20)
B = [20, 30)
```

The change at `20` is:

```
A ends: -1
B starts: +1
Net change: 0
```

The active count is `1` before time `20` and `1` immediately after time `20`. There is no region where both bookings are active.

This also explains the interval convention `[start, end)`. End-exclusive intervals allow adjacent bookings without overlap.

If we use a delta map, all changes at the same timestamp are combined into a single net change. We do not need to decide arbitrarily whether the start or end event should be processed first.

### 4.5 What makes sweep line different from brute force?

Brute force repeatedly asks:

> Which bookings are active at this time?

Sweep line asks:

> Given the previous active count, what changed at this boundary?

That is the deeper optimization. We reuse information from the previous region instead of reconstructing it from scratch.

## 5. The most important interview decision: `TreeMap` or another data structure?

A common mistake is to hear "sweep line" and immediately think `TreeMap`. But sweep line is the algorithmic idea; the map is only one way to implement it.

For My Calendar III, there are two distinct optimization questions.

1. How do we avoid scanning every possible time? Use only event boundaries.
2. How do we avoid scanning every boundary after every booking? Use a data structure that maintains the maximum more efficiently.

The first gives us the `TreeMap` solution. The second leads to a segment tree.

### Why the `TreeMap` solution is a good fit here

There are at most 400 bookings. Therefore, there are at most 800 distinct endpoints.

Even if we sweep over all 800 endpoints for every booking, that is a small amount of work.

The algorithm is easy to explain, and its correctness follows directly from the running-sum invariant.

### What if the number of bookings becomes enormous?

Then repeatedly scanning all endpoints could become expensive. A dynamic segment tree can support range increments and maximum queries in logarithmic time relative to the time domain.

The important interview lesson is not "always use a segment tree." It is:

> First derive the simplest correct algorithm. Then use the constraints to decide whether a more advanced data structure is justified.

## 6. The Java implementation I would present in the interview

This version keeps the implementation compact while making the invariants explicit in the comments.

```java
import java.util.TreeMap;

class MyCalendarThree {

    /*
     * CORE IDEA: SWEEP LINE
     *
     * Every booking [startTime, endTime) produces two changes:
     *
     *     startTime -> +1
     *     endTime   -> -1
     *
     * deltaByTime stores the NET change at each timestamp.
     *
     * Why TreeMap?
     * We must process timestamps in ascending order to calculate the
     * running number of active bookings. TreeMap maintains sorted keys.
     *
     * Why store deltas instead of bookings?
     * Our answer depends on how many bookings are active, not on their
     * individual identities. We can summarize all starts and ends at
     * each timestamp with one integer.
     */
    private final TreeMap<Integer, Integer> deltaByTime = new TreeMap<>();

    public int book(int startTime, int endTime) {

        /*
         * Add the new booking's two boundary events.
         *
         * merge() adds to the existing value when a timestamp already
         * exists. This is essential when multiple bookings share a
         * start or end time.
         *
         * Example:
         * If two bookings start at time 10, deltaByTime.get(10) becomes 2.
         */
        deltaByTime.merge(startTime, 1, Integer::sum);
        deltaByTime.merge(endTime, -1, Integer::sum);

        int activeBookings = 0;
        int maximumOverlap = 0;

        /*
         * SWEEP FROM LEFT TO RIGHT
         *
         * Because the map is ordered, values() visits the net changes
         * in chronological order.
         *
         * Invariant:
         * After processing each timestamp, activeBookings equals the
         * number of bookings active immediately after that timestamp.
         *
         * The active count stays constant until the next timestamp.
         * Therefore, the maximum of these running counts is the global
         * maximum overlap.
         */
        for (int change : deltaByTime.values()) {
            activeBookings += change;

            // Preserve the maximum across the entire calendar, not just
            // the portion affected by the most recent booking.
            maximumOverlap = Math.max(maximumOverlap, activeBookings);
        }

        /*
         * Complexity:
         *
         * Let n be the number of bookings after this call.
         * There are at most 2n distinct timestamps.
         *
         * Two TreeMap updates: O(log n).
         * Full sweep:           O(n).
         * Total per book():     O(n).
         *
         * Across N bookings:    O(N^2) worst-case total time.
         * Space:                O(N) for the distinct timestamps.
         *
         * Why this is appropriate:
         * The problem permits at most 400 bookings, so the straightforward
         * sweep is efficient and much easier to maintain than a segment tree.
         */
        return maximumOverlap;
    }
}
```
