# LeetCode 295 — Find Median from Data Stream

The key to solving this problem is to realize that we don't need to sort every number to find the median. We only need to maintain the middle of the data in the correct order.

The optimal solution uses two heaps:

- A max-heap containing the smaller half of the numbers.
- A min-heap containing the larger half of the numbers.

Let's build the intuition from scratch, compare all the approaches, and then implement them in Java 24 with detailed comments.

## 0. Understand the problem in simple terms

Numbers arrive one at a time, and we must support two operations:

1. `addNum(num)` — add a number to the stream.
2. `findMedian()` — return the median of every number received so far.

The challenge is that we don't know which numbers will arrive next, and we may need to find the median after every insertion.

For example, consider this stream:

```
addNum(1)
addNum(2)
findMedian()  -> 1.5

addNum(3)
findMedian()  -> 2.0

addNum(4)
findMedian()  -> 2.5
```

The sorted numbers at each step are:

```
After adding 1:       [1]
Median:                1

After adding 2:       [1, 2]
Median:                (1 + 2) / 2 = 1.5

After adding 3:       [1, 2, 3]
Median:                2

After adding 4:       [1, 2, 3, 4]
Median:                (2 + 3) / 2 = 2.5
```

Notice that the median depends on the middle element or middle two elements, not on the entire sorted order.

That observation is the foundation of the optimal solution.

## 1. Clarifying questions to ask the interviewer

Even if the problem statement already answers these questions, asking them demonstrates that you are thinking about correctness and constraints.

1. Can `findMedian()` be called before any number is added?

   Why: We need to know whether to handle an empty data structure. Here, the constraints guarantee at least one number before a median query.
2. Can duplicate and negative numbers occur?

   Why: The data structure must handle duplicates correctly and cannot assume all values are positive. Both are allowed.
3. Do we need to support arbitrary insertion order?

   Why: We cannot rely on the stream being sorted. Numbers can arrive in any order.
4. What are the expected time complexities?

   Why: With up to 50,000 calls, repeatedly sorting the data is unnecessary work. We should aim for \\(O(\log n)\\) insertion and \\(O(1)\\) median retrieval.
5. Are there any special constraints on the number range?

   Why: The general problem permits values from \\(-10^5\\) to \\(10^5\\), but the follow-ups introduce a bounded range that enables a different solution.

## 2. The intuition: Maintain the two halves

Imagine that all the numbers were sorted. We could split them into two groups at the median.

For example:

```
Numbers:  1, 2, 3, 4, 5, 6

Smaller half:  1, 2, 3
Larger half:   4, 5, 6
```

We don't need every element to be sorted inside its group. We only need to know the largest element in the smaller half and the smallest element in the larger half.

Those two elements are enough to calculate the median.

### The two heaps

We maintain two priority queues:

- `lowerHalf`: a max-heap. Its root is the largest number in the smaller half.
- `upperHalf`: a min-heap. Its root is the smallest number in the larger half.

The important distinction is that a heap is not a sorted array. The heap only guarantees the parent-child ordering property. We don't care about the exact order of all the other elements.

### The two invariants (rules that must always hold)

Rule 1: Every number in the lower half must be less than or equal to every number in the upper half.

Equivalently:

```
lowerHalf.peek() <= upperHalf.peek()
```

when both heaps are nonempty.

This guarantees that the two roots are the middle boundary elements of the complete dataset.

Rule 2: The heaps must have balanced sizes.

```
lowerHalf.size() == upperHalf.size()

OR

lowerHalf.size() == upperHalf.size() + 1
```

We deliberately allow the lower heap to contain one extra element.

Why? It makes median calculation simple:

- If the sizes are equal, the median is the average of the two roots.
- If the lower heap has one extra element, its root is the median.

These two invariants are the entire strategy.

## 3. Walk through the optimal approach step by step

Let's process the example `[1, 2, 3, 4, 5]`.

### Step 1: Add `1`

Initially both heaps are empty.

Insert `1` into the lower heap.

```
lowerHalf = [1]     // max-heap
upperHalf = []

Sizes: 1 and 0
Median = 1
```

The lower heap has one extra element, so its root is the median.

### Step 2: Add `2`

Since `2` is greater than the largest element in the lower half (`1`), it belongs in the upper half.

```
lowerHalf = [1]
upperHalf = [2]

Sizes: 1 and 1
Median = (1 + 2) / 2 = 1.5
```

Both heaps have the same size. Their roots are the two middle values.

### Step 3: Add `3`

Since `3` is greater than `lowerHalf.peek()`, insert it into the upper heap.

```
lowerHalf = [1]
upperHalf = [2, 3]

Sizes: 1 and 2
```

The upper heap is now too large. Move its smallest element (`2`) into the lower heap.

```
lowerHalf = [2, 1]    // max-heap, root = 2
upperHalf = [3]       // min-heap, root = 3

Sizes: 2 and 1
Median = 2
```

Notice that we moved only one element. We did not sort all three numbers.

### Step 4: Add `4`

`4` belongs in the upper heap.

```
lowerHalf = [2, 1]
upperHalf = [3, 4]

Sizes: 2 and 2
Median = (2 + 3) / 2 = 2.5
```

### Step 5: Add `5`

Insert `5` into the upper heap. Then move the smallest upper element (`3`) to the lower heap to rebalance.

```
lowerHalf = [3, 1, 2]
upperHalf = [4, 5]

Sizes: 3 and 2
Median = 3
```

Summary:

| Inserted number | Lower root | Upper root | Median |
| --------------- | ---------- | ---------- | ------ |
| 1               | 1          | —          | 1.0    |
| 2               | 1          | 2          | 1.5    |
| 3               | 2          | 3          | 2.0    |
| 4               | 2          | 3          | 2.5    |
| 5               | 3          | 4          | 3.0    |

The internal heap arrays may differ from the values shown above because heaps do not maintain complete sorted order. The roots and size invariants are what matter.

## 4. All important solution approaches

### Approach 1: Store every number and sort whenever we query

The simplest solution is to append each number to a list, sort the list when `findMedian()` is called, and return the middle element or average of the middle two elements.

```
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

class MedianFinder {

    private final List<Integer> numbers = new ArrayList<>();

    public void addNum(int num) {
        // Append in O(1) amortized time.
        // We do not maintain sorted order while inserting.
        numbers.add(num);
    }

    public double findMedian() {
        // Sorting the complete list costs O(n log n) time.
        // This is wasteful if median queries happen frequently.
        Collections.sort(numbers);

        int n = numbers.size();
        int middle = n / 2;

        if (n % 2 == 1) {
            // Odd number of elements: the middle element is the median.
            return numbers.get(middle);
        }

        // Even number of elements: average the two middle values.
        // Cast before adding to prevent integer overflow in the sum.
        return ((long) numbers.get(middle - 1) + numbers.get(middle)) / 2.0;
    }

    /*
     * Let n be the number of values currently stored.
     *
     * addNum:
     *   Time: O(1) amortized for ArrayList.append().
     *   Space: O(1) auxiliary per insertion, excluding the stored value.
     *
     * findMedian:
     *   Time: O(n log n) per query because we sort the entire list.
     *   Extra space: depends on the sorting implementation; Java's object
     *   list sort may use O(n) temporary space in the worst case.
     *
     * Total storage: O(n).
     *
     * Verdict: Easiest to understand, but inefficient for frequent queries.
     */
}
```

This works correctly, but it repeats sorting work even when only one new value has arrived.

### Approach 2: Maintain a sorted list

Instead of sorting during every query, keep the list sorted as numbers arrive.

To insert a new number:

1. Use binary search to find its insertion position in \\(O(\log n)\\).
2. Shift subsequent elements to make room and insert it in \\(O(n)\\).

```
import java.util.ArrayList;
import java.util.List;

class MedianFinder {

    private final List<Integer> sortedNumbers = new ArrayList<>();

    public void addNum(int num) {
        // Binary search finds where the new value belongs.
        // Inserting at that index preserves the sorted-order invariant.
        int left = 0;
        int right = sortedNumbers.size();

        // Find the first index whose value is >= num.
        // Using a lower bound also handles duplicates correctly.
        while (left < right) {
            int mid = left + (right - left) / 2;

            if (sortedNumbers.get(mid) < num) {
                left = mid + 1;
            } else {
                right = mid;
            }
        }

        // Binary search was O(log n), but ArrayList insertion shifts
        // elements to the right and costs O(n) in the worst case.
        sortedNumbers.add(left, num);
    }

    public double findMedian() {
        // Because the list is already sorted, the middle values are
        // available directly. No sorting or scanning is required.
        int n = sortedNumbers.size();
        int middle = n / 2;

        if (n % 2 == 1) {
            return sortedNumbers.get(middle);
        }

        return ((long) sortedNumbers.get(middle - 1)
                + sortedNumbers.get(middle)) / 2.0;
    }

    /*
     * addNum:
     *   Time: O(log n) to find the position + O(n) to shift elements
     *         = O(n) worst case.
     *
     * findMedian:
     *   Time: O(1), because ArrayList provides O(1) indexed access.
     *
     * Total storage: O(n).
     *
     * Verdict: Good when median queries are frequent and insertions are
     * relatively rare. Still, each insertion can shift O(n) elements.
     */
}
```

Important: Binary search makes finding the insertion position faster, but it does not make insertion into an `ArrayList` logarithmic. The shifting cost remains \\(O(n)\\).

### Approach 3: Two heaps — optimal general solution

The two-heap approach avoids maintaining the entire dataset in sorted order. It maintains only the boundary between the smaller and larger halves.

In Java, `PriorityQueue` is a min-heap by default. We can create a max-heap by using `Comparator.reverseOrder()`.

The implementation below uses a simple strategy:

1. Add the number to the lower heap if it is no greater than the lower heap's maximum; otherwise, add it to the upper heap.
2. Rebalance the sizes if necessary.
3. Read the roots to calculate the median.

```
import java.util.Comparator;
import java.util.PriorityQueue;

class MedianFinder {

    /*
     * Mental model:
     *
     * lowerHalf = the smaller half of the complete dataset.
     *             Its root is the largest value in this half.
     *
     * upperHalf = the larger half of the complete dataset.
     *             Its root is the smallest value in this half.
     *
     * We do NOT need the values inside either half to be fully sorted.
     * We only need their boundary values and balanced sizes.
     */

    private final PriorityQueue<Integer> lowerHalf =
            new PriorityQueue<>(Comparator.reverseOrder());

    private final PriorityQueue<Integer> upperHalf =
            new PriorityQueue<>();

    public void addNum(int num) {

        // INVARIANT 1 — partition order:
        // Every value in lowerHalf must be <= every value in upperHalf.
        //
        // Since lowerHalf.peek() is its maximum, comparing num with that
        // boundary tells us whether num can be added to the lower half.
        //
        // If lowerHalf is empty, put the first value there.
        if (lowerHalf.isEmpty() || num <= lowerHalf.peek()) {
            lowerHalf.offer(num);
        } else {
            upperHalf.offer(num);
        }

        // INVARIANT 2 — size balance:
        // lowerHalf.size() must equal upperHalf.size(), OR exceed it by 1.
        //
        // If lowerHalf has more than one extra value, move its maximum
        // to upperHalf. This restores balance without breaking partition
        // order: the moved value was the largest value in lowerHalf.
        if (lowerHalf.size() > upperHalf.size() + 1) {
            upperHalf.offer(lowerHalf.poll());
        }

        // If upperHalf has more values than lowerHalf, move its minimum
        // to lowerHalf. This preserves partition order because the moved
        // value is the smallest value in the upper half.
        if (upperHalf.size() > lowerHalf.size()) {
            lowerHalf.offer(upperHalf.poll());
        }

        // After rebalancing:
        // lowerHalf has either the same number of values as upperHalf,
        // or exactly one more.
        //
        // Both invariants hold, so the roots identify the middle values.
    }

    public double findMedian() {

        // The problem guarantees that at least one number exists.
        //
        // Case 1: Odd total count.
        // lowerHalf contains one extra value. Its maximum is the middle
        // element of the complete dataset.
        if (lowerHalf.size() > upperHalf.size()) {
            return lowerHalf.peek();
        }

        // Case 2: Even total count.
        // Both halves have the same size. The median is the average of
        // the largest value in the lower half and the smallest in upper.
        //
        // Convert to long before addition so the sum cannot overflow int.
        return ((long) lowerHalf.peek() + upperHalf.peek()) / 2.0;
    }

    /*
     * COMPLEXITY ANALYSIS
     *
     * Let n be the number of inserted values.
     *
     * addNum(num):
     *   - One heap insertion costs O(log n).
     *   - At most one rebalance move is needed for the chosen insertion
     *     strategy; a move consists of a heap removal and insertion,
     *     each O(log n).
     *   - Total: O(log n) worst-case time per insertion.
     *
     * findMedian():
     *   - Reads one or two heap roots.
     *   - peek() is O(1).
     *   - Total: O(1) time.
     *
     * Space:
     *   - Every inserted number is stored in exactly one heap.
     *   - Total: O(n) space.
     *
     * Overall: O(log n) per insertion, O(1) per median query, O(n) space.
     * This is the standard optimal solution for the general constraints.
     */
}
```

## 5. Edge cases to watch out for

These are particularly useful to discuss during an interview because they test the invariants, not just the happy path.

| Edge case                  | Example             | Expected result | What it tests                  |
| -------------------------- | ------------------- | --------------- | ------------------------------ |
| One number                 | `[7]`               | `7.0`           | First insertion                |
| Two numbers                | `[1, 2]`            | `1.5`           | Even-sized median              |
| Negative numbers           | `[-5, -2]`          | `-3.5`          | Correct ordering of negatives  |
| Duplicate numbers          | `[2, 2, 2]`         | `2.0`           | Equal values across heaps      |
| Descending stream          | `[5, 4, 3, 2, 1]`   | `3.0`           | Repeated rebalancing           |
| Ascending stream           | `[1, 2, 3, 4, 5]`   | `3.0`           | Repeated upper-heap insertions |
| Extreme values             | `[-100000, 100000]` | `0.0`           | Correct numeric averaging      |
| Odd count after even count | `[1, 2, 3]`         | `2.0`           | Size invariant after insertion |

### Why integer overflow matters

Consider these two expressions:

```
return (lowerHalf.peek() + upperHalf.peek()) / 2.0;
```

```
return ((long) lowerHalf.peek() + upperHalf.peek()) / 2.0;
```

The first expression adds two `int` values before dividing. If their sum exceeds the `int` range, overflow occurs before Java converts the result to `double`.

The second expression promotes the first operand to `long` before addition, making the sum safe for the full `int` range.

Even though this particular problem has relatively small values, the second version is safer and demonstrates good interview habits.

### Why duplicates do not cause problems

Suppose the stream is:

```
[5, 5, 5, 5]
```

All four values are equal, so either half can contain a `5` without violating partition order.

Our condition uses `num <= lowerHalf.peek()`. That consistently directs equal values to the lower heap. Rebalancing then keeps the sizes valid.

The heaps do not require unique values.

## 6. Follow-up questions and answers

### Follow-up 1: What if all integers are in the range `[0, 100]`?

We can optimize further using a frequency array instead of heaps.

Because there are only 101 possible values, we can maintain how many times each number has appeared.

For example, for the stream:

```
[1, 2, 2, 3, 5]
```

the frequency array contains:

```
Value:       0  1  2  3  4  5  ...  100
Frequency:   0  1  2  1  0  1  ...    0
```

We also maintain the total count of inserted values.

To find the median, scan the frequency array from `0` to `100`, accumulating counts until we reach the middle position.

This is efficient because we scan at most 101 entries, regardless of how many numbers are in the stream.

```
class MedianFinder {

    // Since every input is guaranteed to be in [0, 100], we need
    // exactly 101 counters. We store frequencies, not individual values.
    private final int[] frequency = new int[101];

    // Number of values received so far, including duplicates.
    private int size;

    public void addNum(int num) {
        // Each value is guaranteed to satisfy 0 <= num <= 100.
        // Increment its frequency in constant time.
        frequency[num]++;
        size++;
    }

    public double findMedian() {
        // A zero-based sorted index i corresponds to one-based rank i + 1.
        //
        // For odd size, both target ranks are the same.
        // For even size, we need the two central ranks.
        int leftRank = (size + 1) / 2;
        int rightRank = (size + 2) / 2;

        // Locate both ranks by counting how many values are <= each
        // candidate value. Duplicate values naturally occupy multiple ranks.
        int cumulativeCount = 0;
        int leftValue = -1;
        int rightValue = -1;

        for (int value = 0; value <= 100; value++) {
            cumulativeCount += frequency[value];

            if (leftValue == -1 && cumulativeCount >= leftRank) {
                leftValue = value;
            }

            if (cumulativeCount >= rightRank) {
                rightValue = value;
                break;
            }
        }

        // For odd size, leftRank == rightRank, so both values are equal.
        // For even size, average the two middle values.
        return ((long) leftValue + rightValue) / 2.0;
    }

    /*
     * Let R = 101 be the fixed number of possible input values.
     *
     * addNum:
     *   Time: O(1).
     *
     * findMedian:
     *   Time: O(R) = O(101), which is O(1) when the range is fixed.
     *
     * Space:
     *   O(R) = O(101), also O(1) for the fixed range.
     *
     * Compared with two heaps, insertion is faster and storage is bounded.
     * The trade-off is that this works only when the value range is known
     * and small.
     */
}
```

Why does the frequency array work?

A sorted list would repeat each value according to its frequency. The frequency array represents that same ordering implicitly.

For example:

```
frequency[1] = 1
frequency[2] = 2
frequency[3] = 1
frequency[5] = 1
```

represents:

```
[1, 2, 2, 3, 5]
```

The cumulative count tells us when we have passed each target rank. We never need to construct the sorted list.

### Follow-up 2: What if 99% of numbers are in `[0, 100]`?

This is trickier because the remaining 1% may be outside the range. We cannot simply index those values into the frequency array.

A robust approach is to use:

- A frequency array for values in `[0, 100]`.
- A `TreeMap<Integer, Integer>` for values outside the range, storing each outlier and its frequency.
- A total count of all values.

The map maintains outliers in sorted key order, while the array stores in-range values compactly.

To locate a target rank, count outliers below zero first, then scan the 101 in-range frequencies, and finally examine outliers above 100 if necessary.

```
import java.util.Map;
import java.util.TreeMap;

class MedianFinder {

    // Compact storage for the common values in the inclusive range [0, 100].
    private final int[] frequency = new int[101];

    // Stores values outside [0, 100], in ascending order.
    // Each map entry represents a value and the number of its occurrences.
    private final TreeMap<Integer, Integer> outliers = new TreeMap<>();

    private int size;

    public void addNum(int num) {
        if (num >= 0 && num <= 100) {
            frequency[num]++;
        } else {
            outliers.merge(num, 1, Integer::sum);
        }

        size++;
    }

    public double findMedian() {
        int leftRank = (size + 1) / 2;
        int rightRank = (size + 2) / 2;

        int leftValue = findKthSmallest(leftRank);
        int rightValue = findKthSmallest(rightRank);

        return ((long) leftValue + rightValue) / 2.0;
    }

    private int findKthSmallest(int rank) {
        // Stage 1: Outliers below 0 are smaller than every in-range value.
        // Count their occurrences in ascending key order.
        int seen = 0;

        for (Map.Entry<Integer, Integer> entry : outliers.headMap(0).entrySet()) {
            seen += entry.getValue();

            if (seen >= rank) {
                return entry.getKey();
            }
        }

        // Stage 2: Scan the bounded in-range frequency array.
        // 'seen' already includes all outliers below zero, so ranks remain
        // correct when we continue counting through values 0 to 100.
        for (int value = 0; value <= 100; value++) {
            seen += frequency[value];

            if (seen >= rank) {
                return value;
            }
        }

        // Stage 3: If the rank lies above the in-range values, continue
        // through the outliers greater than 100, in ascending order.
        for (Map.Entry<Integer, Integer> entry : outliers.tailMap(100).entrySet()) {
            seen += entry.getValue();

            if (seen >= rank) {
                return entry.getKey();
            }
        }

        // Unreachable when rank is valid and at least one value exists.
        throw new IllegalStateException("Rank exceeds the number of values");
    }

    /*
     * Let n be the total number of values and m the number of distinct
     * outlier values.
     *
     * addNum:
     *   In-range value: O(1).
     *   Outlier: O(log m) for TreeMap insertion/update.
     *
     * findMedian:
     *   O(m + 101) worst case per query, because a rank lookup may scan
     *   all distinct outliers and the fixed frequency array.
     *
     * Space:
     *   O(101 + m) = O(m) for a fixed range.
     *
     * This approach uses compact storage for the common values and
     * preserves exact results even when outliers affect the median.
     *
     * Important qualification:
     *   The statement "99% of the numbers are in [0, 100]" alone does
     *   not justify ignoring outliers. A correct implementation must
     *   account for their ordering and multiplicities.
     */
}
```

The main advantage is reduced storage when many values repeat within the small range. However, this implementation does not guarantee constant-time median queries because outliers may need to be scanned.

If we need both efficient updates and efficient rank queries over arbitrary outliers, we can use a more sophisticated order-statistics tree that tracks subtree sizes. Java's standard `TreeMap` does not provide subtree-size rank queries directly.

## 7. Interviewer follow-up questions

### Q1. Why do we use a max-heap for the lower half and a min-heap for the upper half?

Because the median depends on the boundary between the halves.

- The max-heap gives us the largest value among the smaller elements.
- The min-heap gives us the smallest value among the larger elements.

Those are precisely the two candidates for the median when the total count is even.

If both heaps were min-heaps, we could not efficiently retrieve the largest element of the lower half.

### Q2. Why not use a single heap?

A single min-heap exposes only the smallest value, while a single max-heap exposes only the largest value. Neither directly exposes the middle boundary.

We could remove elements repeatedly to reach the middle, but that would modify the data structure and cost \\(O(n\log n)\\) in the worst case.

Two heaps expose both required boundaries without removing elements during median queries.

### Q3. Why do we balance the heap sizes rather than balance the sums?

Because the median depends on positions in sorted order, not on the sum of the numbers in each half.

For example:

```
lowerHalf: [-100, 1, 2]
upperHalf: [3, 4]
```

The sums are very different, but the sizes are valid and the median is `2`.

Balancing by sum would have no useful relationship to the median's position.

### Q4. How do we know rebalancing preserves the correct partition?

Assume the partition is correct before inserting a new number.

- If the new number is placed in the lower half, it is no greater than the lower half's previous maximum. If that half becomes too large, moving its maximum to the upper half preserves the ordering.
- If the new number is placed in the upper half, it is greater than the lower half's maximum. If the upper half becomes too large, moving its minimum to the lower half preserves the ordering.

Only one move is needed because the size difference before insertion was at most one.

Thus, after rebalancing, both invariants hold again.

### Q5. What is the exact complexity comparison?

Let \\(n\\) be the number of inserted elements.

| Approach                      | `addNum()`                    | `findMedian()`   | Space          |
| ----------------------------- | ----------------------------- | ---------------- | -------------- |
| Sort on every query           | \\(O(1)\\) amortized          | \\(O(n\log n)\\) | \\(O(n)\\)     |
| Sorted `ArrayList`            | \\(O(n)\\)                    | \\(O(1)\\)       | \\(O(n)\\)     |
| Two heaps                     | \\(O(\log n)\\)               | \\(O(1)\\)       | \\(O(n)\\)     |
| Fixed-range frequency array   | \\(O(1)\\)                    | \\(O(101)\\)     | \\(O(101)\\)   |
| Frequency array + outlier map | \\(O(1)\\) or \\(O(\log m)\\) | \\(O(m+101)\\)   | \\(O(m+101)\\) |

Here, \\(m\\) is the number of distinct outlier values.

For the general problem, two heaps are the best practical choice because they provide logarithmic insertion, constant-time median retrieval, and support arbitrary integers.

### Q6. Can we use `PriorityQueue<Integer>` for both heaps?

Yes. Java's default `PriorityQueue` is a min-heap, so the upper heap needs no custom comparator.

For the lower heap, use:

```
PriorityQueue<Integer> lowerHalf =
        new PriorityQueue<>(Comparator.reverseOrder());
```

This is preferable to negating every number, which can introduce integer-overflow problems for `Integer.MIN_VALUE`.

### Q7. What if the stream is very large and memory is limited?

The standard two-heap solution stores every value, so it requires \\(O(n)\\) space. An exact median generally requires retaining enough information to distinguish the middle ranks.

If the problem permits approximation, streaming quantile algorithms can estimate the median using much less memory. If exactness is required, the appropriate approach depends on the input constraints, whether external storage is allowed, and the available value range.

## 8. Final mental model to remember

When you see a problem asking for the median of a continuously growing stream, think:

1. What information is needed? Only the middle element or the two middle elements.
2. How can we expose those elements efficiently? Split the values into lower and upper halves.
3. How do we expose the boundary values? Use a max-heap for the lower half and a min-heap for the upper half.
4. How do we preserve correctness? Maintain the partition ordering and keep the lower half equal in size to the upper half or one element larger.
5. How do we answer a query? Read one root for odd counts or average both roots for even counts.

The core insight is that we do not need to maintain a fully sorted collection; we only need to maintain the correct boundary around the median.
