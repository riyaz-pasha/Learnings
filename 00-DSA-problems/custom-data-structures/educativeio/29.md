# 2353. Design a Food Rating System — Java 24

The key interview insight is that this problem combines two different lookup requirements:

1. Given a food name, quickly find its current cuisine and rating.
2. Given a cuisine, quickly find its highest-rated food, breaking ties by lexicographically smaller name.

A `HashMap` handles the first requirement well. For the second, we need an ordered data structure, such as a `TreeSet` or `PriorityQueue`.

The most straightforward optimal interview solution is a `HashMap` plus a `TreeSet` for each cuisine.

## 0. Simplify the problem

Imagine we have these Japanese foods:

| Food  | Rating |
| ----- | ------ |
| miso  | 12     |
| sushi | 8      |
| ramen | 14     |

When we ask for the highest-rated Japanese food, the answer is `ramen`.

Now change `sushi`'s rating from 8 to 16. The answer becomes `sushi`.

Next, change `ramen`'s rating from 14 to 16. Both foods have the same rating, so the answer is `ramen`, because `ramen` comes before `sushi` alphabetically.

Our system must maintain these rules after every update.

### Clarifying questions to ask the interviewer

- Can food names repeat? The constraints guarantee distinct food names, so each food can be uniquely identified by its name.
- Can a food change its cuisine? No. Only its rating changes, so we can store the cuisine permanently.
- What happens when ratings tie? Return the lexicographically smaller food name. This must be part of our sorting rule, not an afterthought.
- How many operations can occur? Up to \\(2 \times 10^4\\) total updates and queries. This favors an approach that avoids scanning every food on every query.

These clarifications tell us what information to store and which data structure to choose.

## 1. The core idea: separate lookup from ranking

Think of the system as two indexes that serve different purposes.

```

Food name
   |
   v
HashMap<String, Food>
   |
   +----> cuisine
   +----> current rating

Cuisine
   |
   v
HashMap<String, TreeSet<Food>>
   |
   v
Foods ordered by:
1. Higher rating first
2. Alphabetically smaller name first

```

The first index answers: What is the current information about this food?

The second index answers: Which food ranks first in this cuisine?

We should not use one structure to do both jobs inefficiently.

### Why `TreeSet`?

A `TreeSet` maintains its elements in sorted order. It supports insertion, removal, and lookup of the first element in \\(O(\log n)\\) time, or \\(O(1)\\) to access the first element once located.

We define the ordering as:

1. Higher rating comes first.
2. If ratings are equal, smaller food name comes first.

Java's `TreeSet` does not automatically know that higher ratings are better. We must encode the rule in a comparator.

## 2. The critical update insight

When a food's rating changes, remove it using its old rating before updating it.

For example:

Before the update:

```
Japanese TreeSet:
ramen(14) < sushi(8) < miso(12)  // Conceptually, sorted by our ranking
```

More precisely, the actual sorted order is:

```
ramen(14), miso(12), sushi(8)
```

Suppose `sushi` changes from 8 to 16.

1. Look up `sushi` in the food map.
2. Remove `sushi(8)` from the Japanese `TreeSet`.
3. Change its rating to 16.
4. Insert `sushi(16)` into the same set.

The set now contains:

```
sushi(16), ramen(14), miso(12)
```

The highest-rated food is available immediately as the first element.

Why remove first? A `TreeSet` uses its comparator to determine where an element belongs. If we mutate a field that the comparator uses while the element remains inside the set, its physical position may no longer agree with the ordering. Removal using the old ordering, followed by mutation and reinsertion, preserves the tree's correctness.

## 3. Solution 1 — Brute force

The simplest approach is to store every food in a map. Whenever `highestRated(cuisine)` is called, scan every food, filter by cuisine, and choose the best candidate.

This is an excellent starting point in an interview because it establishes the correct behavior before optimizing.

```
import java.util.HashMap;
import java.util.Map;

class FoodRatingsBruteForce {

    // A food's cuisine never changes, so only its rating is mutable.
    private static final class Food {
        private final String name;
        private final String cuisine;
        private int rating;

        private Food(String name, String cuisine, int rating) {
            this.name = name;
            this.cuisine = cuisine;
            this.rating = rating;
        }
    }

    // Key = food name; value = current information about that food.
    private final Map<String, Food> foodsByName = new HashMap<>();

    public FoodRatingsBruteForce(
            String[] foods,
            String[] cuisines,
            int[] ratings) {

        for (int i = 0; i < foods.length; i++) {
            foodsByName.put(
                foods[i],
                new Food(foods[i], cuisines[i], ratings[i])
            );
        }
    }

    public void changeRating(String foodName, int newRating) {
        // Direct lookup avoids scanning for the food being updated.
        foodsByName.get(foodName).rating = newRating;
    }

    public String highestRated(String cuisine) {
        Food best = null;

        // Examine every food because there is no index organized by cuisine.
        for (Food candidate : foodsByName.values()) {
            if (!candidate.cuisine.equals(cuisine)) {
                continue;
            }

            // Prefer higher ratings; break ties using natural String order.
            if (best == null
                    || candidate.rating > best.rating
                    || (candidate.rating == best.rating
                        && candidate.name.compareTo(best.name) < 0)) {
                best = candidate;
            }
        }

        // The problem guarantees that every queried cuisine has a food.
        return best.name;
    }

    /*
     * Let n = number of foods.
     *
     * Constructor: O(n) expected time for HashMap insertions.
     * changeRating: O(1) expected time for lookup and mutation.
     * highestRated: O(n) time because every food may need examination.
     * Space: O(n) for the food map and Food objects.
     *
     * Why is this not ideal?
     * With up to 20,000 total operations, repeated full scans can perform
     * O(n * q) work, where q is the number of highestRated queries.
     */
}
```

## 4. Solution 2 — Optimal `HashMap` + `TreeSet`

This is the recommended interview solution. It keeps the food lookup and cuisine ranking separate.

### Java 24 implementation

```
import java.util.Comparator;
import java.util.HashMap;
import java.util.Map;
import java.util.NavigableSet;
import java.util.TreeSet;

class FoodRatings {

    /*
     * Immutable name and cuisine, mutable rating.
     *
     * Cuisine is fixed by the problem. Keeping it on the food object means
     * changeRating can find the correct cuisine set without another lookup.
     *
     * A record would be a poor fit for the mutable rating itself because
     * records are designed for immutable data carriers.
     */
    private static final class Food {
        private final String name;
        private final String cuisine;
        private int rating;

        private Food(String name, String cuisine, int rating) {
            this.name = name;
            this.cuisine = cuisine;
            this.rating = rating;
        }
    }

    /*
     * Index 1: food name -> Food object.
     *
     * This gives expected O(1) lookup when changeRating receives a food name.
     * It also provides the authoritative current rating.
     */
    private final Map<String, Food> foodsByName = new HashMap<>();

    /*
     * Index 2: cuisine -> foods ranked from best to worst.
     *
     * Each cuisine has its own TreeSet, so querying Japanese food does not
     * require inspecting Korean, Greek, or any other cuisine.
     */
    private final Map<String, NavigableSet<Food>> foodsByCuisine =
            new HashMap<>();

    /*
     * Ranking rules:
     *
     * 1. Higher rating comes first, so compare ratings in descending order.
     * 2. Equal ratings are ordered by food name in ascending lexicographic
     *    order.
     * 3. Names are unique, so distinct foods cannot compare as equal.
     *
     * Integer.compare avoids subtraction-based comparator overflow.
     * String.compareTo implements the required lexicographic ordering.
     */
    private static final Comparator<Food> FOOD_RANKING =
            Comparator.comparingInt((Food food) -> food.rating)
                    .reversed()
                    .thenComparing(food -> food.name);

    public FoodRatings(
            String[] foods,
            String[] cuisines,
            int[] ratings) {

        for (int i = 0; i < foods.length; i++) {
            Food food = new Food(foods[i], cuisines[i], ratings[i]);

            // Register the food for direct name-based lookup.
            foodsByName.put(food.name, food);

            // Create the cuisine's ordered set the first time we encounter it.
            foodsByCuisine
                    .computeIfAbsent(
                            food.cuisine,
                            ignored -> new TreeSet<>(FOOD_RANKING))
                    .add(food);
        }
    }

    public void changeRating(String foodName, int newRating) {
        // Step 1: Find the existing object in expected O(1) time.
        Food food = foodsByName.get(foodName);

        // Step 2: Find the ordered set for this food's fixed cuisine.
        NavigableSet<Food> cuisineFoods =
                foodsByCuisine.get(food.cuisine);

        /*
         * Step 3: Remove the food BEFORE changing its rating.
         *
         * The TreeSet orders elements using rating and name. Changing rating
         * while the object remains in the set would invalidate the ordering
         * assumptions used by the tree.
         *
         * Removal is O(log k), where k is the number of foods in this cuisine.
         * It works because the comparator still sees the old rating.
         */
        cuisineFoods.remove(food);

        // Step 4: Update the authoritative Food object.
        food.rating = newRating;

        /*
         * Step 5: Reinsert using the new rating.
         *
         * TreeSet finds the correct position under the updated comparator
         * values. After insertion, the set is correctly ordered again.
         */
        cuisineFoods.add(food);
    }

    public String highestRated(String cuisine) {
        /*
         * first() returns the smallest element according to FOOD_RANKING.
         * Since that comparator puts the best food first, no scan is needed.
         *
         * TreeSet.first() is O(1) for a non-empty set.
         * The problem guarantees that the requested cuisine exists.
         */
        return foodsByCuisine.get(cuisine).first().name;
    }

    /*
     * COMPLEXITY ANALYSIS
     *
     * Let:
     * n = total number of foods.
     * k = number of foods in the cuisine being updated.
     *
     * Constructor:
     * - Each food enters a HashMap in expected O(1) time.
     * - Each food enters a TreeSet in O(log k) time for its cuisine.
     * - Total: O(n log n) worst-case upper bound, with O(n) storage.
     *
     * changeRating:
     * - HashMap lookup: O(1) expected.
     * - TreeSet removal: O(log k).
     * - Rating assignment: O(1).
     * - TreeSet insertion: O(log k).
     * - Total: O(log k), bounded by O(log n).
     *
     * highestRated:
     * - HashMap lookup: O(1) expected.
     * - TreeSet.first(): O(1).
     * - Total: O(1) expected.
     *
     * Space:
     * - O(n) Food objects in the name map.
     * - O(n) references across all cuisine-specific TreeSets.
     * - Total: O(n).
     *
     * Why this is optimal for the intended design:
     * We avoid scanning all foods for every query, while maintaining the
     * ranking incrementally after each update. TreeSet updates cost
     * logarithmic time and the highest-ranked food is immediately accessible.
     */
}
```

## 6. Solution 3 — `HashMap` + lazy `PriorityQueue`

Another valid approach uses a max-heap for each cuisine.

The key difference is that Java's `PriorityQueue` does not efficiently remove an arbitrary food after its rating changes. Instead of removing old entries, we insert a new entry and leave the old one in the heap. When querying, we discard outdated entries until the top entry matches the current rating in the food map.

```
import java.util.Comparator;
import java.util.HashMap;
import java.util.Map;
import java.util.PriorityQueue;

class FoodRatingsWithLazyHeap {

    private record FoodState(String name, String cuisine, int rating) {}

    // The current, authoritative rating for every food.
    private final Map<String, FoodState> currentFoods = new HashMap<>();

    // Each cuisine has a heap ordered by best rating, then smallest name.
    private final Map<String, PriorityQueue<FoodState>> heapsByCuisine =
            new HashMap<>();

    private static final Comparator<FoodState> BEST_FIRST =
            Comparator.comparingInt(FoodState::rating)
                    .reversed()
                    .thenComparing(FoodState::name);

    public FoodRatingsWithLazyHeap(
            String[] foods, String[] cuisines, int[] ratings) {

        for (int i = 0; i < foods.length; i++) {
            FoodState state =
                    new FoodState(foods[i], cuisines[i], ratings[i]);

            currentFoods.put(state.name(), state);

            heapsByCuisine
                    .computeIfAbsent(
                            state.cuisine(),
                            ignored -> new PriorityQueue<>(BEST_FIRST))
                    .offer(state);
        }
    }

    public void changeRating(String foodName, int newRating) {
        FoodState oldState = currentFoods.get(foodName);

        // Replace the authoritative state with a new immutable record.
        FoodState newState =
                new FoodState(oldState.name(), oldState.cuisine(), newRating);

        currentFoods.put(foodName, newState);

        /*
         * Do not attempt to remove oldState from the heap.
         * PriorityQueue.remove(Object) is O(k), not O(log k).
         * Add the new state instead; the old entry becomes stale.
         */
        heapsByCuisine.get(newState.cuisine()).offer(newState);
    }

    public String highestRated(String cuisine) {
        PriorityQueue<FoodState> heap = heapsByCuisine.get(cuisine);

        /*
         * A food can have multiple entries in the heap after multiple
         * rating changes. Only the entry matching the current authoritative
         * rating is valid.
         *
         * Because food names are unique, comparing the rating is sufficient
         * to identify a stale entry: all entries for that food have its name.
         */
        while (!heap.isEmpty()) {
            FoodState candidate = heap.peek();
            FoodState current = currentFoods.get(candidate.name());

            if (candidate.rating() == current.rating()) {
                return candidate.name();
            }

            // Discard a stale entry. It can never become current again.
            heap.poll();
        }

        throw new IllegalStateException("Cuisine has no valid food");
    }

    /*
     * Let n be the initial number of foods, u the number of rating updates,
     * and k the size of a cuisine's heap, including stale entries.
     *
     * Constructor: O(n log n) worst-case upper bound.
     * changeRating: O(log k) for insertion.
     * highestRated: O(1) if the heap top is valid; otherwise O(s log k)
     * for s stale entries discarded during that call.
     *
     * Across the entire execution, every inserted entry is polled at most
     * once. Therefore, all stale-entry cleanup costs O((n + u) log(n + u))
     * in aggregate. Individual queries can nevertheless be expensive.
     *
     * Space: O(n + u), because stale entries accumulate until removed.
     *
     * Interview trade-off:
     * The heap avoids arbitrary deletion but requires lazy cleanup and can
     * use more memory. TreeSet is generally the cleaner choice here because
     * rating changes can be handled with explicit removal and reinsertion.
     */
}
```

## 7. Edge cases to discuss

| Edge case                                                         | Expected behavior                                                                            |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Only one food in a cuisine                                        | Return that food.                                                                            |
| Two foods have the same rating                                    | Return the lexicographically smaller name.                                                   |
| Rating increases                                                  | Remove and reinsert at its new position.                                                     |
| Rating decreases                                                  | Remove and reinsert at its new position.                                                     |
| Rating remains unchanged                                          | The TreeSet solution still works correctly; removing and reinserting preserves the ordering. |
| Repeated updates to the same food                                 | Always use its latest rating.                                                                |
| Different cuisines contain foods with identical ratings and names | Each cuisine has an independent ranking; foods in another cuisine are irrelevant.            |
| Food names are prefixes of other names                            | Java's `String.compareTo` correctly puts the shorter prefix first when otherwise equal.      |

## 8. Interviewer follow-up questions

Q1. Why not use a `HashMap` for everything?

A `HashMap` provides efficient lookup by key, but it does not maintain the foods in ranking order. Finding the highest-rated food would require scanning all foods in the cuisine.

Q2. Why not use a `TreeMap<Integer, String>` keyed by rating?

Multiple foods can share the same rating, so a rating alone is not a unique key. We would need a nested structure, such as a map from ratings to sorted food names, plus additional logic to find the highest rating. A `TreeSet` of food objects directly expresses the complete ordering.

Q3. Why is the comparator's tie-breaker necessary?

If two distinct foods have the same rating and the comparator returns zero, a `TreeSet` treats them as equivalent and may discard one. Comparing by name ensures that distinct food names remain distinct in the ordered set.

Q4. Why is `TreeSet` better than `PriorityQueue` here?

`TreeSet` supports removal of an arbitrary known element in \\(O(\log n)\\) time, which is exactly what a rating update needs. `PriorityQueue` is excellent for retrieving the best element but does not support efficient arbitrary deletion, making lazy cleanup necessary.

Q5. Can we make updates faster with a `TreeSet`?

Not asymptotically for arbitrary rating changes. Removing and reinserting requires \\(O(\log k)\\) time. We could use more specialized indexed data structures, but they add complexity without a practical advantage for these constraints.

Q6. What is the overall complexity of the recommended solution?

- Initialization: \\(O(n \log n)\\) worst-case upper bound.
- `changeRating`: \\(O(\log n)\\) expected overall, dominated by ordered-set removal and insertion.
- `highestRated`: \\(O(1)\\) expected, since we retrieve the first element from the cuisine's ordered set.
- Space: \\(O(n)\\).

## 9. Final interview takeaway

The most important skill is recognizing the two different access patterns:

- Lookup by food name: use a `HashMap`.
- Retrieve the best food by cuisine: use a sorted structure for each cuisine.

Whenever a problem requires frequent updates to objects and repeated queries for the minimum, maximum, or best-ranked object, consider maintaining an ordered index instead of repeatedly scanning all objects.

For this problem, `HashMap + TreeSet` gives the cleanest balance of efficient updates, immediate highest-rated lookups, predictable complexity, and straightforward tie-breaking.
