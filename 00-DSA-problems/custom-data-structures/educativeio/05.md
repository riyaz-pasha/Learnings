# LRU Cache — Complete Java 24 Interview Solution

## 0. Simplify the problem statement

We need to implement a cache that stores key-value pairs and has a fixed capacity.

The cache supports two operations:

- `get(key)`: Return the value associated with the key. If the key does not exist, return `-1`.
- `set(key, value)`: Insert a new key-value pair or update an existing key.

The special rule is LRU — Least Recently Used.

When the cache is full and we insert a new key, we must remove the key that has gone the longest without being accessed.

Important: Both `get` and `set` count as usage. Updating an existing key also makes it recently used.

### Example

Suppose the cache capacity is `2`.

| Operation    | Cache contents, oldest → newest | Result         |
| ------------ | ------------------------------- | -------------- |
| `set(1, 10)` | `[1=10]`                        | Insert         |
| `set(2, 20)` | `[1=10, 2=20]`                  | Insert         |
| `get(1)`     | `[2=20, 1=10]`                  | `10`           |
| `set(3, 30)` | `[1=10, 3=30]`                  | Evict key `2`  |
| `get(2)`     | `[1=10, 3=30]`                  | `-1`           |
| `get(1)`     | `[3=30, 1=10]`                  | `10`           |
| `set(3, 35)` | `[1=10, 3=35]`                  | Update key `3` |
| `set(4, 40)` | `[3=35, 4=40]`                  | Evict key `1`  |

Notice that after `get(1)`, key `1` becomes the most recently used key. Therefore, key `2` is evicted when key `3` is inserted.

## 1. Clarifying questions to ask the interviewer

1\. Does `get` update the usage order? Why ask: In an LRU cache, reading an entry usually makes it recently used. Otherwise, we might implement a different eviction policy.

2\. Does updating an existing key count as recent usage? Why ask: Usually, yes. Updating should change the value and move the key to the most-recently-used position.

3\. What should `get` return for a missing key? Why ask: Here, the statement specifies `-1`, so we do not need an exception or a nullable result.

4\. Can the capacity be zero or negative? Why ask: This determines constructor validation and edge-case behavior. The supplied constraints guarantee `1 <= capacity <= 3000`, so we can rely on positive capacity.

5\. What performance is expected? Why ask: With up to \\(2 \times 10^5\\) operations, an \\(O(n)\\) scan per operation could be too slow. The standard target is \\(O(1)\\) average time per `get` and `set`.

## 2. Core idea and intuition

The challenge is not storing key-value pairs. A `HashMap` already does that efficiently.

The challenge is keeping track of which key was used least recently while also supporting fast updates.

### Approach 1: HashMap + doubly linked list

Use two data structures, each with a specific responsibility:

- HashMap: Quickly find a node using its key.
- Doubly linked list: Maintain usage order, with the least recently used node at the front and the most recently used node at the back.

We will use two sentinel nodes, `head` and `tail`, to simplify list operations.

Order shown below: LRU → MRU

```
head <-> [Key 2] <-> [Key 1] <-> [Key 3] <-> tail
          oldest                       newest
```

The map points directly to the corresponding list nodes:

```
HashMap:
2 -> Node(key=2, value=20)
1 -> Node(key=1, value=10)
3 -> Node(key=3, value=30)
```

The map does not need to maintain the order. The linked list does that.

### How `get(key)` works

Suppose the list is:

```
head <-> [2] <-> [1] <-> [3] <-> tail
```

We call `get(2)`.

1. Look up key `2` in the map.
2. Find its node in average \\(O(1)\\) time.
3. Remove that node from its current position.
4. Move it to the end, next to `tail`.
5. Return its value.

The list becomes:

```
head <-> [1] <-> [3] <-> [2] <-> tail
```

Key `2` is now the most recently used.

### How `set(key, value)` works

There are three cases.

Case A: The key already exists.

- Update its value.
- Move its node to the most-recently-used position.

Case B: The key does not exist and the cache has space.

- Create a new node.
- Add it to the map.
- Insert it at the end of the linked list.

Case C: The key does not exist and the cache is full.

- Remove the first real node after `head`. This is the least recently used entry.
- Remove that key from the map.
- Insert the new entry at the end of the list.
- Add the new key to the map.

The key insight is that we never search the linked list. The map finds a node directly, and the doubly linked list allows us to remove and reposition that node in constant time.

## 4. All solutions: brute force to optimal

### Solution 1 — HashMap + timestamp / usage counter

Idea: Store each key's value and the time at which it was last used.

On every `get` or `set`, update that timestamp. When inserting into a full cache, scan all entries and evict the one with the smallest timestamp.

```
import java.util.HashMap;
import java.util.Map;

public class LRUCacheTimestamp {

    private record Entry(int value, long lastUsed) {}

    private final int capacity;
    private final Map<Integer, Entry> cache = new HashMap<>();
    private long clock = 0;

    public LRUCacheTimestamp(int capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException("Capacity must be positive");
        }
        this.capacity = capacity;
    }

    public int get(int key) {
        Entry entry = cache.get(key);

        if (entry == null) {
            return -1;
        }

        // Every successful access receives a newer timestamp.
        cache.put(key, new Entry(entry.value(), ++clock));
        return entry.value();
    }

    public void set(int key, int value) {
        // Updating an existing key must not trigger eviction.
        if (cache.containsKey(key)) {
            cache.put(key, new Entry(value, ++clock));
            return;
        }

        if (cache.size() == capacity) {
            int lruKey = -1;
            long oldestTime = Long.MAX_VALUE;

            // BRUTE-FORCE STEP: scan every cached entry to find the oldest.
            // This scan takes O(capacity) time because there is no direct
            // pointer to the least-recently-used entry.
            for (Map.Entry<Integer, Entry> item : cache.entrySet()) {
                if (item.getValue().lastUsed() < oldestTime) {
                    oldestTime = item.getValue().lastUsed();
                    lruKey = item.getKey();
                }
            }

            cache.remove(lruKey);
        }

        cache.put(key, new Entry(value, ++clock));
    }
}

/*
 * Time complexity:
 * - get: O(1) average for the HashMap lookup and update.
 * - set existing key: O(1) average.
 * - set new key when space is available: O(1) average.
 * - set new key when full: O(capacity) because we scan all entries.
 *
 * Space complexity: O(capacity), since the map holds at most capacity entries.
 *
 * Limitation:
 * The eviction scan makes this unsuitable for the strongest performance
 * requirement when there are many operations and a large cache.
 */
```

This is a useful first solution because the eviction rule is easy to understand. But we can do better by eliminating the scan.

### Solution 2 — Java's built-in `LinkedHashMap`

Java's `LinkedHashMap` can maintain entries in access order. It already combines a hash table with a linked ordering of entries.

```
import java.util.LinkedHashMap;
import java.util.Map;

public class LRUCacheBuiltIn {

    private final int capacity;
    private final LinkedHashMap<Integer, Integer> cache;

    public LRUCacheBuiltIn(int capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException("Capacity must be positive");
        }

        this.capacity = capacity;

        // accessOrder = true means iteration order goes from least recently
        // accessed to most recently accessed.
        this.cache = new LinkedHashMap<>(capacity, 0.75f, true) {
            @Override
            protected boolean removeEldestEntry(
                    Map.Entry<Integer, Integer> eldest) {

                // Java automatically removes the oldest entry after an
                // insertion if the number of entries exceeds capacity.
                return size() > LRUCacheBuiltIn.this.capacity;
            }
        };
    }

    public int get(int key) {
        // In access-order mode, a successful get also updates the order.
        // Missing keys return null; the problem requires -1 instead.
        Integer value = cache.get(key);
        return value == null ? -1 : value;
    }

    public void set(int key, int value) {
        // A new key is appended to the newest position.
        // Updating an existing key also refreshes its access order.
        cache.put(key, value);
    }
}

/*
 * Time complexity:
 * - get: O(1) average.
 * - set: O(1) average, including automatic eviction.
 *
 * Space complexity: O(capacity).
 *
 * Advantage:
 * This is short, readable, and interview-friendly when library usage is
 * permitted.
 *
 * Caveat:
 * If the interviewer asks you to implement the data structure itself,
 * use the custom doubly linked list solution below instead.
 *
 * This implementation is not thread-safe by itself.
 */
```

### Solution 3 — Optimal custom implementation: HashMap + doubly linked list

This is the most important interview solution because it shows exactly how to achieve constant-time operations.

The list provides four essential operations:

- `remove(node)` — detach any known node.
- `addLast(node)` — insert a node as the newest entry.
- `moveToMostRecent(node)` — remove and reinsert a node at the end.
- `removeLeastRecent()` — remove the oldest real node, immediately after `head`.

All of them require only a constant number of pointer updates.

```
import java.util.HashMap;
import java.util.Map;

public class LRUCache {

    /*
     * Each node represents one key-value pair.
     *
     * prev and next allow us to remove a node from the middle of the
     * list in O(1) time, without searching for its predecessor.
     */
    private static final class Node {
        final int key;
        int value;
        Node prev;
        Node next;

        Node(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }

    private final int capacity;

    /*
     * Maps each key directly to its corresponding list node.
     *
     * This is essential: without this map, finding a node by key would
     * require scanning the linked list in O(n) time.
     */
    private final Map<Integer, Node> cache = new HashMap<>();

    /*
     * Sentinel nodes simplify insertion and removal.
     *
     * head.next is always the least recently used real node.
     * tail.prev is always the most recently used real node.
     *
     * Empty list:
     *
     * head <-> tail
     */
    private final Node head = new Node(-1, -1);
    private final Node tail = new Node(-1, -1);

    public LRUCache(int capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException(
                    "Capacity must be positive");
        }

        this.capacity = capacity;

        // Initialize an empty doubly linked list.
        head.next = tail;
        tail.prev = head;

        /*
         * Time: O(1), because only two sentinel pointers are initialized.
         * Space: O(1) for the two sentinel nodes.
         */
    }

    public int get(int key) {
        /*
         * Step 1: Find the node using the HashMap.
         *
         * HashMap lookup takes O(1) average time.
         */
        Node node = cache.get(key);

        /*
         * Step 2: If the key is absent, return the required sentinel
         * value -1. A failed access does not change the list.
         */
        if (node == null) {
            return -1;
        }

        /*
         * Step 3: A successful get counts as usage.
         *
         * Move the node to the MRU position so that it will not be
         * evicted before entries that have been unused for longer.
         */
        moveToMostRecent(node);

        /*
         * Time: O(1) average.
         * - One HashMap lookup: O(1) average.
         * - A constant number of pointer updates: O(1).
         *
         * Auxiliary space: O(1); no new nodes or collections are created.
         */
        return node.value;
    }

    public void set(int key, int value) {
        /*
         * CASE 1: The key already exists.
         *
         * Update its value and mark it as recently used.
         * Importantly, updating an existing key does not increase the
         * number of entries and must not cause an eviction.
         */
        Node existing = cache.get(key);

        if (existing != null) {
            existing.value = value;
            moveToMostRecent(existing);

            /*
             * Time: O(1) average.
             * Space: O(1) auxiliary.
             */
            return;
        }

        /*
         * CASE 2: The key is new and the cache is full.
         *
         * Because the list is ordered from LRU to MRU, head.next
         * identifies the eviction candidate immediately.
         *
         * We do not search the list.
         */
        if (cache.size() == capacity) {
            Node lru = head.next;

            // Remove the entry from BOTH data structures.
            removeNode(lru);
            cache.remove(lru.key);

            /*
             * Both removals take O(1) average time.
             * Removing only from the list would leave a stale map entry.
             * Removing only from the map would leave a stale list node.
             */
        }

        /*
         * CASE 3: Insert the new key-value pair.
         *
         * The cache now has room, either because it was not full or
         * because we evicted one entry.
         */
        Node newNode = new Node(key, value);

        // The map provides direct access to the new node in the future.
        cache.put(key, newNode);

        // New entries are always the most recently used.
        addLast(newNode);

        /*
         * Time: O(1) average for the map operations and O(1) for list
         * pointer updates. This includes eviction when the cache is full.
         *
         * Auxiliary space: O(1) for the new node; the cache as a whole
         * uses O(capacity) space.
         */
    }

    /*
     * Detach an existing node from its current position.
     *
     * Before:
     *   A <-> node <-> B
     *
     * After:
     *   A <-> B
     *
     * The caller already has a reference to node, so no traversal occurs.
     */
    private void removeNode(Node node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;

        /*
         * Time: O(1), exactly two neighboring links are updated.
         * Space: O(1), no additional data structure is created.
         */
    }

    /*
     * Insert a node immediately before tail.
     *
     * This is the MRU position.
     *
     * Before:
     *   A <-> tail
     *
     * After:
     *   A <-> node <-> tail
     */
    private void addLast(Node node) {
        Node last = tail.prev;

        last.next = node;
        node.prev = last;

        node.next = tail;
        tail.prev = node;

        /*
         * Time: O(1), only a fixed number of links are updated.
         * Space: O(1), the existing node is reused.
         */
    }

    /*
     * Move an existing node to the MRU position.
     *
     * First detach it, then insert it immediately before tail.
     *
     * This helper is shared by successful get operations and updates
     * to existing keys.
     */
    private void moveToMostRecent(Node node) {
        removeNode(node);
        addLast(node);

        /*
         * Time: O(1) because both helper operations are O(1).
         * Space: O(1), no extra nodes or collections are allocated.
         */
    }
}

/*
 * ================================================================
 * OVERALL COMPLEXITY
 * ================================================================
 *
 * Let C = cache capacity and n = current number of cached entries.
 *
 * Constructor:
 *   Time:  O(1)
 *   Space: O(1) initially, excluding the map's internal allocation.
 *
 * get(key):
 *   Time:  O(1) average.
 *   Space: O(1) auxiliary.
 *
 * set(key, value):
 *   Time:  O(1) average, including eviction.
 *   Space: O(1) auxiliary per operation, excluding stored entries.
 *
 * Entire cache:
 *   Space: O(C), because at most C nodes and C map entries are stored.
 *
 * HashMap operations are O(1) on average, not an unconditional
 * worst-case guarantee for every possible collision pattern.
 *
 * The linked-list operations themselves are worst-case O(1).
 */
```

## 5. Edge cases to watch out for

| Scenario                                 | Expected behavior                                           |
| ---------------------------------------- | ----------------------------------------------------------- |
| `get` on a missing key                   | Return `-1`; do not modify the order                        |
| `set` on an existing key                 | Update the value and move the key to MRU                    |
| Capacity is `1`                          | Every new distinct key evicts the previous key              |
| Cache is full                            | Evict exactly one LRU entry before inserting                |
| Access the current LRU key               | It becomes MRU, changing the next eviction candidate        |
| Repeated `get` on the same key           | The key remains MRU                                         |
| Values are `0`                           | Return `0` normally; do not confuse it with a missing entry |
| Keys are `0`                             | Treat key `0` as a normal valid key                         |
| Insert an existing key into a full cache | Do not evict another key                                    |

### A particularly important bug

When evicting a node, always remove it from both structures:

```
Node lru = head.next;
removeNode(lru);
cache.remove(lru.key);
```

If we remove only the node from the list, the map may still point to it. A later `get` could incorrectly return an evicted entry.

Another common bug is moving a node to MRU only on insertion. A successful `get` must also update the order; otherwise, the cache implements insertion-order eviction rather than LRU.

## 6. Interviewer follow-up questions and answers

Q1. Why do we need a doubly linked list instead of a singly linked list?

A doubly linked list lets us remove any known node in \\(O(1)\\) time because the node contains a pointer to its predecessor and successor. With a singly linked list, removing an arbitrary node generally requires finding its predecessor, which takes \\(O(n)\\) time.

Q2. Why use both a HashMap and a linked list?

The map provides fast key-based lookup, while the list maintains usage order. Neither structure alone efficiently supports both requirements.

Q3. Why use sentinel nodes?

Sentinels eliminate special cases for removing the first or last real node. We always have neighboring nodes, even when the cache is empty or contains just one entry.

Q4. Can we use a priority queue to find the LRU entry?

A priority queue can track timestamps, but changing a key's priority and handling outdated entries complicates the implementation. Typical priority-queue operations take \\(O(\log n)\\), whereas the map-plus-list solution supports average \\(O(1)\\) operations.

Q5. Is `LinkedHashMap` a valid interview answer?

Yes, if standard library implementations are allowed. If the interviewer wants to evaluate data-structure fundamentals, implement the custom map-plus-list solution.

Q6. Is the cache thread-safe?

No. Concurrent calls can interleave map changes and linked-list pointer updates, corrupting the state. Thread safety requires synchronization or another concurrency design.

Q7. What if the cache needs to support expiration by time?

LRU eviction and time-based expiration are different requirements. A production design might add expiration timestamps and a cleanup strategy, such as a priority queue or timing wheel, depending on the expiration semantics.

Q8. What happens if the cache capacity changes dynamically?

If capacity shrinks below the current size, evict LRU entries until the size satisfies the new limit. Increasing capacity requires no eviction. Both behaviors can be implemented with the same list and map.

## 7. Final interview takeaway

Remember this pairing:

- HashMap: Find a key's node quickly.
- Doubly linked list: Maintain and change recency quickly.

The four key operations—lookup, remove a known node, append to MRU, and evict LRU—require no list traversal.

That is why the custom implementation achieves \\(O(1)\\) average time for both `get` and `set`, with \\(O(\text{capacity})\\) total space.

## 2. Corrected LRU cache using your custom linked list

The simplest fix is to introduce a `CacheEntry` class containing both the key and value.

```
import java.util.HashMap;
import java.util.Map;

class LRUCache {

    /*
     * Each node must preserve BOTH the key and the value.
     *
     * Why?
     * - The value is returned by get(key).
     * - The key is required to remove an evicted entry from the HashMap.
     */
    private static class CacheEntry {
        int key;
        int value;

        CacheEntry(int key, int value) {
            this.key = key;
            this.value = value;
        }
    }

    /*
     * LinkedList stores CacheEntry objects.
     *
     * HEAD = most recently used (MRU).
     * TAIL = least recently used (LRU).
     *
     * Your map directly points to each entry's linked-list node.
     */
    private final LinkedList<CacheEntry> list;
    private final Map<Integer, LinkedListNode<CacheEntry>> map;
    private final int capacity;

    public LRUCache(int capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException(
                    "Capacity must be positive");
        }

        this.capacity = capacity;
        this.list = new LinkedList<>();
        this.map = new HashMap<>();
    }

    public int get(int key) {

        // Step 1: Find the node directly through the HashMap.
        LinkedListNode<CacheEntry> node = map.get(key);

        // Step 2: Return -1 if the key is absent.
        if (node == null) {
            return -1;
        }

        // Step 3: A successful access makes this entry MRU.
        list.remove(node);
        list.addFirst(node);

        // Step 4: Return the VALUE, not the key.
        return node.data.value;

        /*
         * Time: O(1) average.
         * HashMap lookup, node removal, and insertion at the head
         * all take O(1) time.
         */
    }

    public void set(int key, int value) {

        // CASE 1: The key already exists.
        if (map.containsKey(key)) {

            LinkedListNode<CacheEntry> node = map.get(key);

            // Update only the value; preserve the key.
            node.data.value = value;

            // Updating also makes the entry most recently used.
            list.remove(node);
            list.addFirst(node);

            // No eviction is needed because the size did not increase.
            return;
        }

        // CASE 2: New key and cache is full.
        // Use >= as a defensive check before inserting a new entry.
        if (list.size() >= capacity) {

            // The tail contains the least recently used entry.
            LinkedListNode<CacheEntry> lastNode = list.getLast();

            // Remove the evicted KEY from the map.
            map.remove(lastNode.data.key);

            // Remove the corresponding node from the list.
            list.removeLast();
        }

        // CASE 3: Insert the new entry at the MRU position.
        CacheEntry entry = new CacheEntry(key, value);
        list.insertAtHead(entry);

        // The new head is the node associated with this key.
        map.put(key, list.getFirst());

        /*
         * Time: O(1) average.
         * Space: O(1) additional per insertion; total cache storage
         * remains O(capacity).
         */
    }
}
```

## 3. Fix your linked list's `remove` method

Your existing linked list is mostly suitable. But the `remove` implementation should detach the node properly and update the length safely.

Replace your current `remove(LinkedListNode<T> node)` method with this version:

```
public void remove(LinkedListNode<T> node) {

    // Nothing to remove.
    if (node == null) {
        return;
    }

    /*
     * Ignore an already-detached node.
     * A node belonging to this list must be either a boundary node
     * or have at least one neighboring link.
     */
    boolean isHead = (node == head);
    boolean isTail = (node == tail);

    if (!isHead && !isTail
            && node.prev == null && node.next == null) {
        return;
    }

    // Connect the predecessor to the successor.
    if (node.prev != null) {
        node.prev.next = node.next;
    }

    // Connect the successor to the predecessor.
    if (node.next != null) {
        node.next.prev = node.prev;
    }

    // If removing the head, advance the head pointer.
    if (isHead) {
        head = node.next;
    }

    // If removing the tail, move the tail pointer backward.
    if (isTail) {
        tail = node.prev;
    }

    // Ensure both ends are null when the list becomes empty.
    if (head == null) {
        tail = null;
    }

    if (tail == null) {
        head = null;
    }

    // Completely detach the removed node.
    node.prev = null;
    node.next = null;

    // Decrease size exactly once.
    length--;
}
```

Also fix your `addFirst` and `addLast` methods to explicitly reset the new node's links when the list is empty:

```
public void addFirst(LinkedListNode<T> newNode) {
    if (newNode == null) {
        return;
    }

    if (head == null) {
        head = newNode;
        tail = newNode;
        newNode.prev = null;
        newNode.next = null;
    } else {
        newNode.prev = null;
        newNode.next = head;
        head.prev = newNode;
        head = newNode;
    }

    length++;
}

public void addLast(LinkedListNode<T> newNode) {
    if (newNode == null) {
        return;
    }

    if (head == null) {
        head = newNode;
        tail = newNode;
        newNode.prev = null;
        newNode.next = null;
    } else {
        newNode.next = null;
        newNode.prev = tail;
        tail.next = newNode;
        tail = newNode;
    }

    length++;
}
```

Your `remove(T data)` method should also use value equality:

```
public void remove(T data) {
    LinkedListNode<T> current = head;

    while (current != null) {
        if (java.util.Objects.equals(current.data, data)) {
            remove(current);
            return;
        }

        current = current.next;
    }
}
```

## 4. Dry run of the corrected cache

For `capacity = 2`, we perform:

```
LRUCache cache = new LRUCache(2);

cache.set(1, 10);
cache.set(2, 20);

System.out.println(cache.get(1)); // 10

cache.set(3, 30);                 // Evicts key 2

System.out.println(cache.get(2)); // -1
System.out.println(cache.get(1)); // 10
System.out.println(cache.get(3)); // 30
```

The linked list changes as follows, with the head holding the MRU entry:

```
After set(1, 10):
HEAD -> [1:10] <- TAIL

After set(2, 20):
HEAD -> [2:20] <-> [1:10] <- TAIL

After get(1):
HEAD -> [1:10] <-> [2:20] <- TAIL

After set(3, 30):
HEAD -> [3:30] <-> [1:10] <- TAIL
```

Key `2` was evicted because it was the least recently used entry.

## 5. Complexity

| Operation           | Average time | Explanation                                                                |
| ------------------- | ------------ | -------------------------------------------------------------------------- |
| `get(key)`          | \\(O(1)\\)   | Map lookup plus constant-time node movement                                |
| `set(key, value)`   | \\(O(1)\\)   | Map lookup/insertion plus constant-time list updates and optional eviction |
| Remove a known node | \\(O(1)\\)   | Update neighboring pointers                                                |
| Insert at head      | \\(O(1)\\)   | Update a fixed number of pointers                                          |
| Evict LRU           | \\(O(1)\\)   | Read the tail and remove its node                                          |
| Total space         | \\(O(C)\\)   | At most \\(C\\) entries in the map and linked list                         |

One final interview tip: Your original design was correct. The most important changes are storing both the key and value in each node, removing the evicted key from the map, and moving successfully accessed entries to the MRU position. Those three ideas are the heart of an LRU cache.
