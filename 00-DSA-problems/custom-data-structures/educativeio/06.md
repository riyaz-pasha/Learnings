# Randomized Set — Java 24 Interview Solution

## 0. Simplify the problem statement

We need to implement a data structure called `RandomizedSet` that supports three operations:

- `insert(data)`: Add an integer only if it does not already exist.
- `delete(data)`: Remove an integer only if it exists.
- `getRandom()`: Return one of the currently stored integers, chosen uniformly at random.

The main requirement is that all three operations should take \\(O(1)\\) average time.

For example:

```
RandomizedSet set = new RandomizedSet();

set.insert(10);    // true
set.insert(20);    // true
set.insert(10);    // false, already exists

set.getRandom();   // 10 or 20, each with probability 1/2

set.delete(10);   // true
set.getRandom();   // 20

set.delete(99);   // false, does not exist
```

The order of random results is unpredictable, but each element must have an equal probability of being selected.

## 1. Clarifying questions to ask the interviewer

1. Can the set contain duplicate values? The statement says no. This allows us to maintain one index per integer in a hash map.
2. Must `getRandom()` select every element with equal probability? We should confirm uniform randomness, rather than merely returning some random element.
3. Can we use Java's built-in collections? We will use `ArrayList` and `HashMap`, both of which provide average \\(O(1)\\) operations for the required use cases.
4. Can the set contain negative integers and extreme integer values? Yes. We must handle the full `int` range, including `Integer.MIN_VALUE` and `Integer.MAX_VALUE`.
5. Is the data structure required to be thread-safe? Not specified. We will assume single-threaded access; concurrent modifications would require additional synchronization.
6. What should happen when `getRandom()` is called on an empty set? The problem guarantees that the set is non-empty whenever `getRandom()` is called, so we do not need to define empty-set behavior for this implementation.

## 2. Core intuition: combine an array and a hash map

The trick is to use two data structures together, because neither one alone solves all three operations efficiently.

- An `ArrayList<Integer>` lets us pick a random element by index in \\(O(1)\\) time.
- A `HashMap<Integer, Integer>` tells us the index of any element in average \\(O(1)\\) time.

The challenge is deletion: removing an arbitrary element from the middle of an `ArrayList` normally takes \\(O(n)\\) time because the remaining elements must shift.

The key insight is to replace the element we want to delete with the last element, then remove the last position. No shifting is required.

### Visualize the data structures

Suppose we insert `10`, `20`, and `30`.

```
ArrayList:
Index:   0    1    2
       +----+----+----+
Value: | 10 | 20 | 30 |
       +----+----+----+

HashMap:
10 -> 0
20 -> 1
30 -> 2
```

The array provides fast random access, and the map provides fast lookup.

### Example: delete 20

The map tells us that `20` is at index `1`. The last element is `30`, at index `2`.

Instead of shifting `30` left, swap `20` with `30`, then remove the last position.

Before deletion

```
Array: [10, 20, 30]
        0   1   2

Map:   {10=0, 20=1, 30=2}
```

Step 1: Move the last element into the deleted element's position

```
Array: [10, 30, 30]
        0   1   2
```

Step 2: Update the moved element's index in the map

```
Map:   {10=0, 30=1}
```

Step 3: Remove the last array position

```
Array: [10, 30]
        0   1

Map:   {10=0, 30=1}
```

The final state is correct, and deletion takes average \\(O(1)\\) time.

### Why this also makes random selection easy

For an array of size \\(n\\), generate a random integer from `0` through `n - 1` and return the element at that index.

```
Array: [10, 30, 40, 50]

Possible random indices: 0, 1, 2, 3

Probability of selecting each element: 1/4
```

Every array position is equally likely, so every stored element is equally likely to be returned.

## 3. All approaches: brute force to optimal

| Approach            | Insert          | Delete          | Get random |
| ------------------- | --------------- | --------------- | ---------- |
| ArrayList only      | \\(O(n)\\)      | \\(O(n)\\)      | \\(O(1)\\) |
| HashSet only        | \\(O(1)\\) avg. | \\(O(1)\\) avg. | \\(O(n)\\) |
| HashMap + ArrayList | \\(O(1)\\) avg. | \\(O(1)\\) avg. | \\(O(1)\\) |

Here, \\(n\\) is the current number of elements. The `avg.` qualification matters because Java hash collections have average constant-time operations, not an unconditional worst-case guarantee.

## 4. Approach 1 — Brute force using an ArrayList

This is the simplest implementation to understand. We store all elements in a list and use `contains()` to check whether an element exists.

```
import java.util.ArrayList;
import java.util.concurrent.ThreadLocalRandom;

class RandomizedSetBruteForce {

    private final ArrayList<Integer> values = new ArrayList<>();

    public boolean insert(int data) {
        // WHY: An ArrayList allows duplicates, so we must check first.
        // WHAT: contains() scans the list until it finds the value or
        // reaches the end.
        // TIME: O(n), because contains() may inspect every element.
        // SPACE: O(1) auxiliary space for this operation.
        if (values.contains(data)) {
            return false;
        }

        values.add(data);

        // TIME: O(1) amortized for ArrayList.add() at the end.
        // Overall insert time: O(n), dominated by contains().
        return true;
    }

    public boolean delete(int data) {
        // WHY: We must not delete a value that does not exist.
        // WHAT: indexOf() searches for the first matching value.
        // TIME: O(n), because the list may need a complete scan.
        int index = values.indexOf(data);

        if (index == -1) {
            return false;
        }

        // WHAT: Removing a middle element shifts later elements left.
        // TIME: O(n) in the worst case.
        // SPACE: O(1) auxiliary space.
        values.remove(index);

        return true;
    }

    public int getRandom() {
        // PRECONDITION: The list is non-empty, as guaranteed by the problem.
        // WHY: Every list position must have the same probability.
        // WHAT: nextInt(size) returns an index in [0, size).
        // TIME: O(1).
        // SPACE: O(1) auxiliary space.
        int randomIndex =
                ThreadLocalRandom.current().nextInt(values.size());

        return values.get(randomIndex);
    }
}
```

Why is this not optimal? `insert()` and `delete()` take \\(O(n)\\) time because of their linear searches and, potentially, element shifting. Only `getRandom()` is \\(O(1)\\).

This is a good starting point in an interview because it establishes correctness before optimization.

## 5. Approach 2 — HashSet

A `HashSet` supports fast insertion, deletion, and membership checks. However, it does not provide direct indexed access.

To select a random element, we would have to iterate through the set until reaching a randomly selected position.

```
import java.util.HashSet;
import java.util.concurrent.ThreadLocalRandom;

class RandomizedSetHashSet {

    private final HashSet<Integer> values = new HashSet<>();

    public boolean insert(int data) {
        // HashSet.add() returns false if the value already exists.
        // TIME: O(1) average; O(n) in a pathological collision case.
        // SPACE: O(1) auxiliary space, excluding collection growth.
        return values.add(data);
    }

    public boolean delete(int data) {
        // HashSet.remove() returns false if the value is absent.
        // TIME: O(1) average; worst-case behavior depends on collisions.
        // SPACE: O(1) auxiliary space.
        return values.remove(data);
    }

    public int getRandom() {
        // PRECONDITION: The set is non-empty.
        // WHY: A HashSet does not expose a random-access index.
        // WHAT: Choose a random ordinal, then iterate to that element.
        // TIME: O(n), because the iterator may visit nearly every element.
        // SPACE: O(1) auxiliary space; no temporary collection is created.
        int target = ThreadLocalRandom.current().nextInt(values.size());

        for (int value : values) {
            if (target-- == 0) {
                return value;
            }
        }

        // Unreachable when the set is non-empty and unmodified.
        throw new IllegalStateException("Set unexpectedly empty");
    }
}
```

Why is this still not optimal? Although `insert()` and `delete()` are average \\(O(1)\\), `getRandom()` is \\(O(n)\\). We need both fast membership operations and fast indexed access, which motivates combining a hash map with an array list.

## 6. Approach 3 — Optimal: HashMap + ArrayList

This is the recommended interview solution.

The invariant we must maintain after every operation is:

> For every value at `values[i]`, the map must contain `indices.get(values[i]) == i`, and the map must contain exactly the values stored in the list.

The invariant is what makes the swap-and-remove trick safe.

```
import java.util.ArrayList;
import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.ThreadLocalRandom;

public class RandomizedSet {

    // Stores values contiguously, allowing random access by index in O(1).
    private final ArrayList<Integer> values;

    // Maps each stored value to its exact position in values.
    // This lets us find an element's position in O(1) average time.
    private final Map<Integer, Integer> indices;

    public RandomizedSet() {
        // Start with an empty array and an empty map.
        // TIME: O(1) initialization, ignoring internal allocation details.
        // SPACE: O(1) initial logical state, excluding collection overhead.
        values = new ArrayList<>();
        indices = new HashMap<>();
    }

    public boolean insert(int data) {
        // STEP 1: Check whether the value already exists.
        // WHY: The structure is a set, so duplicate values are forbidden.
        // TIME: O(1) average HashMap lookup.
        // SPACE: O(1) auxiliary space.
        if (indices.containsKey(data)) {
            return false;
        }

        // STEP 2: Append the new value to the end of the array.
        // WHY: Appending avoids shifting existing elements.
        // TIME: O(1) amortized; an occasional resize can take O(n).
        values.add(data);

        // STEP 3: Record the index where we appended the value.
        // WHY: Future deletions must locate this value without scanning.
        // TIME: O(1) average HashMap insertion.
        // SPACE: O(1) additional entry, amortized.
        indices.put(data, values.size() - 1);

        // OVERALL TIME: O(1) average/amortized.
        // OVERALL EXTRA SPACE: O(1) per newly inserted distinct value.
        return true;
    }

    public boolean delete(int data) {
        // STEP 1: Find the element's index using the map.
        // WHY: Searching the array would cost O(n).
        // TIME: O(1) average.
        // SPACE: O(1) auxiliary space.
        Integer index = indices.get(data);

        // A null result means the value does not exist.
        // All valid indices are non-negative, so null is unambiguous.
        if (index == null) {
            return false;
        }

        // STEP 2: Identify the last element in the array.
        // WHY: We can remove the last position without shifting elements.
        // TIME: O(1).
        int lastIndex = values.size() - 1;
        int lastValue = values.get(lastIndex);

        // STEP 3: Fill the deleted position with the last element,
        // but only if the deleted element is not already the last one.
        // WHY: ArrayList.remove(index) could shift O(n) elements.
        // Replacing the element lets us remove the last position instead.
        if (index != lastIndex) {
            values.set(index, lastValue);

            // STEP 4: Update the moved value's map entry.
            // WHY: lastValue now lives at 'index', not 'lastIndex'.
            // Without this update, the map invariant would be broken.
            // TIME: O(1) average.
            indices.put(lastValue, index);
        }

        // STEP 5: Remove the old last position.
        // WHY: It is now either the original deleted value or a duplicate
        // of the moved value that we copied into the deleted position.
        // TIME: O(1), because this removes the final ArrayList element.
        values.remove(lastIndex);

        // STEP 6: Remove the deleted value from the map.
        // WHY: It must no longer be recognized as a member of the set.
        // TIME: O(1) average.
        indices.remove(data);

        // OVERALL TIME: O(1) average.
        // OVERALL EXTRA SPACE: O(1) auxiliary space for this operation.
        return true;
    }

    public int getRandom() {
        // PRECONDITION: At least one element exists.
        // The problem guarantees this whenever getRandom() is called.

        // STEP 1: Choose a uniformly random valid array index.
        // WHY: Every stored element occupies exactly one array position.
        // nextInt(bound) returns an integer in [0, bound).
        // TIME: O(1).
        // SPACE: O(1) auxiliary space.
        int randomIndex =
                ThreadLocalRandom.current().nextInt(values.size());

        // STEP 2: Return the element at that position.
        // WHY: ArrayList supports direct indexed access.
        // TIME: O(1).
        // OVERALL TIME: O(1); OVERALL EXTRA SPACE: O(1).
        return values.get(randomIndex);
    }
}
```

## 7. Detailed dry run of the optimal solution

Let's trace the actual array and map after every operation.

| Operation    | Array (`values`) | Map (`indices`)      | Result  |
| ------------ | ---------------- | -------------------- | ------- |
| `insert(10)` | `[10]`           | `{10=0}`             | `true`  |
| `insert(20)` | `[10, 20]`       | `{10=0, 20=1}`       | `true`  |
| `insert(30)` | `[10, 20, 30]`   | `{10=0, 20=1, 30=2}` | `true`  |
| `insert(20)` | `[10, 20, 30]`   | `{10=0, 20=1, 30=2}` | `false` |
| `delete(20)` | `[10, 30]`       | `{10=0, 30=1}`       | `true`  |
| `delete(30)` | `[10]`           | `{10=0}`             | `true`  |
| `delete(99)` | `[10]`           | `{10=0}`             | `false` |

Notice the deletion of `20`:

1. The map identifies its index as `1`.
2. The last element, `30`, is moved into index `1`.
3. The map entry for `30` is updated to index `1`.
4. The final array element is removed.
5. The entry for `20` is removed from the map.

The order of elements changes after deletion, but that is perfectly fine because a set does not promise any particular ordering.

## 8. Edge cases to watch out for

| Case                                              | Expected behavior                   | Important detail                             |
| ------------------------------------------------- | ----------------------------------- | -------------------------------------------- |
| Insert a duplicate                                | Return `false`                      | Do not change either data structure.         |
| Delete a missing value                            | Return `false`                      | Leave the array and map unchanged.           |
| Delete the last element                           | Return `true`                       | No swap is necessary.                        |
| Delete the only element                           | Return `true`                       | Both structures become empty.                |
| Insert negative values                            | Works normally                      | Negative integers are valid map keys.        |
| Insert `Integer.MIN_VALUE` or `Integer.MAX_VALUE` | Works normally                      | No arithmetic on the stored value is needed. |
| Random selection from one element                 | Return that element                 | The only valid index is `0`.                 |
| Random selection from multiple elements           | Return any stored element uniformly | Select an index, not a random integer value. |

One subtle bug to avoid: if you move the last element during deletion but forget to update its index in the map, a later deletion of that moved element may remove the wrong position or corrupt the data structure.

## 9. Time and space complexity

Let \\(n\\) be the number of elements currently stored.

| Operation             | Average / amortized time      | Extra space per operation           |
| --------------------- | ----------------------------- | ----------------------------------- |
| Constructor           | \\(O(1)\\)                    | \\(O(1)\\) initial state            |
| `insert()`            | \\(O(1)\\) average, amortized | \\(O(1)\\) per new distinct element |
| `delete()`            | \\(O(1)\\) average            | \\(O(1)\\)                          |
| `getRandom()`         | \\(O(1)\\)                    | \\(O(1)\\)                          |
| Entire data structure | —                             | \\(O(n)\\)                          |

A few precision points worth mentioning in an interview:

- `HashMap` operations are average \\(O(1)\\); pathological collision behavior can be worse.
- `ArrayList.add()` is amortized \\(O(1)\\), although resizing can occasionally cost \\(O(n)\\).
- `ArrayList.remove(lastIndex)` is \\(O(1)\\), unlike removing an arbitrary middle position.
- `getRandom()` is \\(O(1)\\) because it generates an index and performs direct array access.
- The total storage is \\(O(n)\\) because each distinct element appears once in the array and once as a map key.

## 10. Interviewer follow-up questions and answers

Q1. Why can't we use only a HashMap?

A `HashMap` provides fast membership checks, but it does not provide direct random access to its entries by index. Selecting a random entry generally requires iterating over entries or building another collection. The array solves this problem.

Q2. Why can't we use only an ArrayList?

An array list supports random access, but checking whether a value exists requires a linear scan. Removing an arbitrary element also requires a scan and potentially shifting elements. The map eliminates the need to search for the element's index.

Q3. Why do we swap with the last element instead of shifting everything left?

Shifting elements requires updating the indices of every element that moves. That would cost \\(O(n)\\). Moving just the last element requires updating only one map entry, making deletion average \\(O(1)\\).

Q4. Is `getRandom()` truly uniform?

Yes, provided the random-index generator is uniform. If there are \\(n\\) elements, each has exactly one corresponding array index, and every index has probability \\(1/n\\) of being selected.

Q5. Does the implementation preserve insertion order?

No. The internal array may change order when an element is deleted. The problem does not require insertion order, so this is an acceptable tradeoff for constant-time deletion.

Q6. Is the data structure thread-safe?

No. Concurrent calls to `insert()`, `delete()`, and `getRandom()` can observe inconsistent states or cause incorrect results. Thread safety would require synchronization or another concurrency strategy.

Q7. What happens if the set becomes empty?

The stated constraints guarantee that `getRandom()` is only called when the set is non-empty. If that guarantee were removed, we should define the empty-set behavior explicitly, for example by throwing `NoSuchElementException`.

Q8. Can we use `Random` instead of `ThreadLocalRandom`?

Yes. Both can generate a random index. `ThreadLocalRandom.current()` is convenient for modern Java applications and avoids sharing a single `Random` instance across threads, although this does not make the data structure itself thread-safe.

## 11. Final interview takeaway

Remember this combination:

- ArrayList: gives us random access in \\(O(1)\\).
- HashMap: gives us the index of a value in average \\(O(1)\\).
- Swap with last + remove last: makes arbitrary deletion average \\(O(1)\\).

The most important interview insight is not simply choosing two data structures. It is maintaining the invariant that every value's map entry always points to its current array index.

Once you understand that invariant and the swap-and-remove technique, the entire `RandomizedSet` implementation becomes straightforward.
