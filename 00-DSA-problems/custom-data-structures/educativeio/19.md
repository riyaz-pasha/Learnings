# LeetCode 622 — Design Circular Queue

The key idea is to implement a queue using a fixed-size array and circular indexing. Instead of shifting elements after every removal, we move pointers and wrap around to the beginning of the array when we reach its end.

We'll build the solution from the simplest approach to the optimal one, with detailed Java 24 code comments explaining the intuition, reasoning, edge cases, and complexity.

## 0. Understand the problem in simple terms

A normal queue follows FIFO: First In, First Out.

Imagine a queue with capacity `3`:

```
Initially:
[ _ ][ _ ][ _ ]

enQueue(10):
[10 ][ _ ][ _ ]

enQueue(20):
[10 ][20 ][ _ ]

enQueue(30):
[10 ][20 ][30 ]   FULL
```

Now we try `enQueue(40)`. It must fail because all three positions are occupied.

Next, we remove the front element, `10`.

```
deQueue():

[ _ ][20 ][30 ]
```

There is now an empty position at the beginning. A circular queue allows us to reuse it:

```
enQueue(40):

[40 ][20 ][30 ]
```

Logically, the queue is now:

```
Front → 20 → 30 → 40 ← Rear
```

The array's physical order is no longer the same as the queue's logical order. That is perfectly fine.

The important observation: We don't need to move existing elements. We only need to update the indices that identify the front and rear.

## 1. Clarifying questions to ask the interviewer

These questions establish the assumptions behind the implementation.

1. Is the capacity fixed after construction? Yes, the problem specifies a fixed capacity `k`. This lets us allocate one array and avoid resizing.
2. Can the queue contain duplicate values or zero? Yes. Values range from `0` to `1000`, so we cannot use `0` to represent an empty slot.
3. What should happen when the queue is empty or full? `Front()` and `Rear()` return `-1` when empty. Insertion into a full queue and removal from an empty queue return `false`.
4. Can we use a built-in queue? No. We must implement the queue's storage and behavior ourselves.
5. Should every operation be efficient? Ideally, yes. Since all operations can be implemented with array indexing and constant-time pointer updates, we can achieve \\(O(1)\\) time per operation.

## 2. Core intuition: Think of the array as a ring

The array is physically linear, but we treat it as if its last index connects back to index `0`.

For a capacity of `5`, the index progression is:

```
         index 0
       ┌─────────┐
 index 4         index 1
       │         │
 index 3         index 2
       └─────────┘
```

This is a conceptual ring: after index `4`, the next index is `0`.

We achieve this with the modulo operator:

```
nextIndex = (currentIndex + 1) % capacity;
```

For example, if `capacity = 5`:

```
currentIndex = 0  → next = (0 + 1) % 5 = 1
currentIndex = 1  → next = (1 + 1) % 5 = 2
currentIndex = 3  → next = (3 + 1) % 5 = 4
currentIndex = 4  → next = (4 + 1) % 5 = 0
```

That last transition is what makes the queue circular.

### The three pieces of state

We can solve the problem with three variables and one array.

| Variable   | Meaning                                   |
| ---------- | ----------------------------------------- |
| `elements` | Fixed-size array storing the values       |
| `front`    | Index of the first logical queue element  |
| `size`     | Number of elements currently in the queue |

The capacity is `elements.length`, so we don't need to store it separately.

Why choose `front` and `size` instead of maintaining both `front` and `rear`?

Because we can calculate the rear index whenever we need it:

\\[ rear = (front + size - 1) \bmod capacity \\]

This formula works because the last occupied element is `size - 1` positions ahead of the front, with circular wrapping.

For example, with capacity `5`, `front = 3`, and `size = 3`:

```
Index:      0    1    2    3    4
Array:     [30] [  ] [  ] [10] [20]
                             ↑    ↑
                           front  rear

rear = (3 + 3 - 1) % 5
     = 5 % 5
     = 0
```

Correction to the illustration's index interpretation: when `front = 3` and `size = 3`, the occupied positions are indices `3, 4, 0`. Thus, `rear = 0`. The array representation is:

```
Index:      0    1    2    3    4
Array:     [30] [  ] [  ] [10] [20]
            ↑              ↑    ↑
           rear           front
```

The logical queue is `10 → 20 → 30`, even though those elements wrap around the end of the array.

## 3. Derive the operations one by one

Before writing code, let's establish the rules that must always hold.

### Rule 1: `isEmpty()`

The queue is empty exactly when:

```
size == 0
```

### Rule 2: `isFull()`

The queue is full exactly when:

```
size == elements.length
```

Using `size` removes ambiguity between empty and full. A front/rear pointer-only design needs extra state or a reserved array slot to distinguish these cases.

### Rule 3: `enQueue(value)`

To insert an element:

1. If the queue is full, return `false`.
2. Calculate the next rear position.
3. Store the value there.
4. Increase `size`.
5. Return `true`.

The rear index is:

\\[ rear = (front + size) \bmod capacity \\]

Notice that this is different from the formula for the current rear: we use `front + size` because we want the next available position.

### Rule 4: `deQueue()`

To remove an element:

1. If the queue is empty, return `false`.
2. Advance `front` by one position, wrapping around if necessary.
3. Decrease `size`.
4. Return `true`.

We don't need to erase the old value from the array. Once `front` and `size` change, that slot is no longer logically part of the queue. A later insertion can overwrite it.

### Rule 5: `Front()` and `Rear()`

- If empty, return `-1`.
- Otherwise, `Front()` reads `elements[front]`.
- `Rear()` reads the element at `(front + size - 1) % capacity`.

All operations take constant time.

## 4. Solution 1 — Brute force: Shift elements after removal

The simplest implementation keeps the queue elements contiguously starting at index `0`.

When removing the front element, it shifts every remaining element one position to the left.

```
class MyCircularQueue {

    /*
     * BRUTE-FORCE / NON-CIRCULAR BASELINE
     *
     * Mental model:
     * - Keep all logical queue elements in elements[0 .. size - 1].
     * - Insert at elements[size].
     * - Remove the front by shifting every remaining element left.
     *
     * This approach is easy to understand, but it does not obtain the
     * main benefit of a circular queue: reusing array slots without shifting.
     *
     * Time complexity:
     * - enQueue: O(1), because insertion happens at the end.
     * - deQueue: O(k), because up to k - 1 elements must be shifted.
     * - Front, Rear, isEmpty, isFull: O(1).
     *
     * Space complexity: O(k) for the fixed-size array.
     *
     * This is a baseline for comparison, not the recommended solution.
     */

    private final int[] elements;
    private int size;

    public MyCircularQueue(int k) {
        elements = new int[k];
        size = 0;
    }

    public boolean enQueue(int value) {
        if (isFull()) {
            return false;
        }

        // The queue is contiguous, so its next insertion position is size.
        elements[size] = value;
        size++;
        return true;
    }

    public boolean deQueue() {
        if (isEmpty()) {
            return false;
        }

        /*
         * Remove elements[0] logically.
         *
         * Since this baseline keeps the queue contiguous, shift each
         * remaining value one index left to fill the gap.
         *
         * Example:
         * [10, 20, 30, _] -> [20, 30, _, _]
         *
         * This shifting is the expensive part: O(size) time.
         */
        for (int i = 1; i < size; i++) {
            elements[i - 1] = elements[i];
        }

        size--;
        return true;
    }

    public int Front() {
        return isEmpty() ? -1 : elements[0];
    }

    public int Rear() {
        return isEmpty() ? -1 : elements[size - 1];
    }

    public boolean isEmpty() {
        return size == 0;
    }

    public boolean isFull() {
        return size == elements.length;
    }
}
```

Why isn't this optimal? If the queue contains `k` elements, a single removal can move `k - 1` elements. Repeated removals can therefore perform a lot of unnecessary work.

The circular approach fixes this by moving an index instead of moving the data.

## 5. Solution 2 — Optimal circular array with `front` and `size`

This is the recommended solution for LeetCode 622.

```
class MyCircularQueue {

    /*
     * OPTIMAL APPROACH: FIXED-SIZE CIRCULAR ARRAY
     *
     * Mental model:
     * - The array is a ring, not a line.
     * - front identifies the first logical queue element.
     * - size tells us how many consecutive logical positions are occupied.
     * - The rear index is derived instead of stored.
     *
     * INVARIANTS (facts that must remain true after every operation):
     *
     * 1. 0 <= size <= elements.length.
     *
     * 2. If size > 0, elements[front] is the logical front element.
     *
     * 3. If size > 0, the logical rear is at:
     *      (front + size - 1) % elements.length
     *
     * 4. The logical queue consists of exactly size elements, starting
     *    from front and wrapping around the array if needed.
     *
     * Why store size?
     * - size == 0 means empty.
     * - size == capacity means full.
     * - This distinguishes empty from full even when front and rear
     *   happen to point to the same index.
     *
     * Why modulo?
     * - It wraps an index back to 0 after the final array index.
     *
     * Time complexity:
     * - Constructor: O(k) to allocate/initialize the array.
     * - enQueue: O(1).
     * - deQueue: O(1).
     * - Front: O(1).
     * - Rear: O(1).
     * - isEmpty: O(1).
     * - isFull: O(1).
     *
     * Space complexity: O(k), for the array.
     *
     * No built-in queue, linked list, or element shifting is used.
     */

    private final int[] elements;
    private int front;
    private int size;

    public MyCircularQueue(int k) {
        elements = new int[k];

        // Initially no elements exist. Index 0 is the initial front.
        front = 0;
        size = 0;
    }

    public boolean enQueue(int value) {
        // There is no available logical slot when size equals capacity.
        if (isFull()) {
            return false;
        }

        /*
         * The current logical elements occupy:
         *
         * front, front + 1, ..., front + size - 1 (modulo capacity).
         *
         * Therefore, the next insertion position is:
         * (front + size) % capacity.
         *
         * Example: capacity = 5, front = 3, size = 3.
         * Occupied indices are 3, 4, 0.
         * The next insertion index is (3 + 3) % 5 = 1.
         */
        int rear = (front + size) % elements.length;

        // Store the new value in the next logical rear position.
        elements[rear] = value;

        // The new element is now part of the logical queue.
        size++;

        return true;
    }

    public boolean deQueue() {
        // Removing from an empty queue is not possible.
        if (isEmpty()) {
            return false;
        }

        /*
         * The front element is removed logically by advancing front.
         *
         * We do not shift the other values. The old slot becomes
         * available for reuse when the rear wraps around.
         *
         * Example: capacity = 5, front = 4.
         * After removing the front, front becomes (4 + 1) % 5 = 0.
         */
        front = (front + 1) % elements.length;

        // Exactly one logical element has been removed.
        size--;

        return true;
    }

    public int Front() {
        // -1 is the required sentinel value when no element exists.
        return isEmpty() ? -1 : elements[front];
    }

    public int Rear() {
        if (isEmpty()) {
            return -1;
        }

        /*
         * The rear is size - 1 positions after front.
         * Subtracting 1 is necessary because the first element is
         * already at offset 0.
         *
         * Example: front = 3, size = 3, capacity = 5.
         * rear = (3 + 3 - 1) % 5 = 0.
         */
        int rear = (front + size - 1) % elements.length;
        return elements[rear];
    }

    public boolean isEmpty() {
        return size == 0;
    }

    public boolean isFull() {
        return size == elements.length;
    }
}
```

### Why the formulas work

There are two similar-looking formulas, and it's important to understand the difference.

| What we need                   | Formula                         | Reason                                                            |
| ------------------------------ | ------------------------------- | ----------------------------------------------------------------- |
| Next insertion index           | `(front + size) % capacity`     | The next slot is one past the last occupied position.             |
| Current rear index             | `(front + size - 1) % capacity` | The last occupied position is `size - 1` offsets after the front. |
| Next front index after removal | `(front + 1) % capacity`        | Removal advances the front by one position.                       |

A useful rule to remember: `size` describes the number of occupied positions, not the sum of the values stored in the queue.

## 6. Dry run: Follow every index change

Let's use the example from the problem with capacity `3`.

```
MyCircularQueue queue = new MyCircularQueue(3);
```

Initially:

```
elements = [_, _, _]
front    = 0
size     = 0
```

The following table shows both the array and the logical queue after each operation.

| Operation      | Array       | `front` | `size` | Result  |
| -------------- | ----------- | ------- | ------ | ------- |
| Constructor(3) | `[_, _, _]` | 0       | 0      | —       |
| `enQueue(1)`   | `[1, _, _]` | 0       | 1      | `true`  |
| `enQueue(2)`   | `[1, 2, _]` | 0       | 2      | `true`  |
| `enQueue(3)`   | `[1, 2, 3]` | 0       | 3      | `true`  |
| `enQueue(4)`   | `[1, 2, 3]` | 0       | 3      | `false` |
| `Rear()`       | `[1, 2, 3]` | 0       | 3      | `3`     |
| `isFull()`     | `[1, 2, 3]` | 0       | 3      | `true`  |
| `deQueue()`    | `[1, 2, 3]` | 1       | 2      | `true`  |
| `enQueue(4)`   | `[1, 4, 3]` | 1       | 3      | `true`  |
| `Rear()`       | `[1, 4, 3]` | 1       | 3      | `4`     |

Notice the important part: after `deQueue()`, the value `1` remains physically stored at index `0`. That does not mean it is still in the queue.

The logical queue starts at `front = 1` and contains `size = 2` elements:

```
Index:          0    1    2
Array:         [1]  [2]  [3]
                     ↑    ↑
                   front  rear

Logical queue: 2 → 3
```

After `enQueue(4)`:

```
Index:          0    1    2
Array:         [1]  [4]  [3]
                     ↑    ↑
                   front  rear

Logical queue: 2 → 3 → 4
```

The new value is written to index `0`, not index `2`, because:

\\[ rear = (front + size) \bmod capacity \\]

\\[ rear = (1 + 2) \bmod 3 = 0 \\]

So the physical array is `[4, 2, 3]` if the indices are updated according to the logical operations above. The logical queue is `2 → 3 → 4`, with `front = 1`, `size = 3`, and `Rear() = elements[0] = 4`.

The key point is that the logical queue is determined by `front` and `size`, not by reading the array from left to right.

## 7. Edge cases to watch out for

These are the cases I'd expect you to reason through in a senior-level interview.

### Case 1: Inserting into a full queue

```
queue.enQueue(10);
queue.enQueue(20);
queue.enQueue(30);
queue.enQueue(40); // false
```

Why? `size == capacity`. We must check this before writing to the array, or we could overwrite an element still in the queue.

### Case 2: Removing from an empty queue

```
queue.deQueue(); // false
queue.Front();   // -1
queue.Rear();    // -1
```

Why? There is no logical element to remove or return.

### Case 3: Capacity equals one

```
MyCircularQueue queue = new MyCircularQueue(1);

queue.enQueue(7); // true
queue.isFull();   // true
queue.Front();    // 7
queue.Rear();     // 7
queue.deQueue();  // true
queue.isEmpty();  // true
```

This tests whether your formulas work when every index wraps back to `0`.

### Case 4: Repeatedly emptying and refilling

```
queue.enQueue(10);
queue.deQueue();
queue.enQueue(20);
```

The second insertion must work even though the array slot used by `10` may still physically contain that old value. The logical state, rather than the old contents, determines whether the queue is empty.

### Case 5: The queue wraps around multiple times

Don't assume `front` or `rear` always increases toward the end of the array. Every index transition must use modulo arithmetic.

### Case 6: Zero is a valid value

```
queue.enQueue(0);
queue.Front(); // 0, not -1
```

Never use the value `0` as an indicator that a slot is empty. Use `size` to determine whether the queue contains elements.

## 8. Alternative design: Store both `front` and `rear`

A second optimal solution maintains both indices explicitly, along with `size`.

The difference is that `rear` identifies the last inserted element, so insertion advances it before writing.

```
class MyCircularQueue {

    /*
     * ALTERNATIVE OPTIMAL DESIGN: EXPLICIT FRONT AND REAR
     *
     * Invariants:
     * - front points to the first logical element when the queue is nonempty.
     * - rear points to the last logical element when the queue is nonempty.
     * - size distinguishes empty from full.
     *
     * Initially front = 0 and rear = -1. The first insertion advances
     * rear to index 0, making the initialization convenient.
     *
     * enQueue:
     * - Advance rear circularly, then store the value.
     *
     * deQueue:
     * - Advance front circularly.
     *
     * Both operations take O(1) time.
     * All read and status operations take O(1) time.
     * Space complexity is O(k).
     *
     * This is equally efficient, but has an extra index to maintain.
     */

    private final int[] elements;
    private int front;
    private int rear;
    private int size;

    public MyCircularQueue(int k) {
        elements = new int[k];
        front = 0;
        rear = -1;
        size = 0;
    }

    public boolean enQueue(int value) {
        if (isFull()) {
            return false;
        }

        // Move rear to the next physical slot, wrapping around if necessary.
        rear = (rear + 1) % elements.length;

        // Store the new logical last element.
        elements[rear] = value;
        size++;

        return true;
    }

    public boolean deQueue() {
        if (isEmpty()) {
            return false;
        }

        // The old front is removed logically; no values need to move.
        front = (front + 1) % elements.length;
        size--;

        return true;
    }

    public int Front() {
        return isEmpty() ? -1 : elements[front];
    }

    public int Rear() {
        return isEmpty() ? -1 : elements[rear];
    }

    public boolean isEmpty() {
        return size == 0;
    }

    public boolean isFull() {
        return size == elements.length;
    }
}
```

One subtle point: when the queue becomes empty, `front` and `rear` may retain old indices. This is safe because `size` determines whether any element exists. The next successful insertion advances `rear` and establishes the new logical element.

## 9. Interview follow-up questions and answers

Q1. Why is the circular queue better than a normal array-backed queue?

A normal array-backed queue that shifts elements on every removal requires \\(O(k)\\) time for a dequeue in the worst case. The circular queue only advances an index, so dequeue takes \\(O(1)\\).

Q2. Why not use `front == rear` to detect an empty queue?

Depending on how the indices are maintained, `front == rear` can represent either a queue with one element or a queue with no elements. Tracking `size` distinguishes these states reliably.

Q3. Why do we use modulo instead of an `if` statement?

Both approaches are possible. Modulo directly expresses circular movement:

```
index = (index + 1) % capacity;
```

An equivalent conditional implementation is:

```
index++;
if (index == capacity) {
    index = 0;
}
```

Both take constant time.

Q4. Can we implement the queue without a `size` variable?

Yes. We could maintain a count through another mechanism, or reserve one slot to distinguish full from empty. In the reserved-slot approach, a buffer of length `k + 1` is required to store `k` values. Tracking `size` is straightforward and uses the requested capacity directly.

Q5. What if we use a linked list instead?

A linked list with head and tail pointers can implement queue operations in \\(O(1)\\) time. However, it allocates nodes dynamically, incurs extra pointer and object overhead, and doesn't make use of a fixed-size array's compact storage. For this problem, the circular array is a natural fit.

Q6. Is the circular queue thread-safe?

No. This implementation assumes a single thread or externally synchronized access. Concurrent producers and consumers would need synchronization or a carefully designed concurrent ring buffer.

Q7. Why don't we clear the array slot after a dequeue?

We can set the old slot to zero, but it isn't necessary for correctness. The `front` and `size` fields determine which slots belong to the logical queue. Clearing a slot would not change the asymptotic complexity, but it would be an unnecessary write for this integer-only implementation.

Q8. What is the amortized complexity of this circular queue?

Every individual operation is already \\(O(1)\\) in the worst case. There is no need for amortized analysis, which is often used when operations occasionally trigger expensive work, such as resizing a dynamic array.

```
int rear = (front + size) % elements.length;
```

```
int rear = (front + size - 1) % elements.length;
```

The best way to understand them is not to memorize either formula. Instead, let's derive both from what `front` and `size` actually mean.

# 1. First, forget the formulas

Imagine a circular queue with capacity `5`.

```
Index:      0    1    2    3    4
           [ ]  [ ]  [ ]  [ ]  [ ]
```

We have two pieces of information:

- `front` tells us where the first element is.
- `size` tells us how many elements are in the queue.

Suppose:

```
front = 1;
size = 3;
```

And our queue contains `10, 20, 30`.

Because the queue is circular, its elements occupy three consecutive positions, starting from index `1`:

```
Index:      0    1    2    3    4
           [ ]  [10] [20] [30] [ ]

                  ↑         ↑
                front      rear
```

The queue contains:

```
Front → 10 → 20 → 30 ← Rear
```

Now let's answer two different questions.

1. Where is the last existing element (`30`)?
2. Where should the next element be inserted?

These are different positions. That is the entire reason for the difference between the two formulas.

# 2. Understand `size` by counting steps

We know:

```
front = 1;
size = 3;
```

Start at the front, index `1`.

```
Index:       0    1    2    3    4
                  10   20   30
                  ↑    ↑    ↑
Step:             0    1    2
```

Pay attention to the step numbers:

| Position              | Index | Steps forward from `front` |
| --------------------- | ----- | -------------------------- |
| First element (`10`)  | 1     | 0                          |
| Second element (`20`) | 2     | 1                          |
| Third element (`30`)  | 3     | 2                          |
| Next empty position   | 4     | 3                          |

Here's the crucial insight:

If there are `size` elements, the last existing element is only `size - 1` steps away from the front. The next empty position is `size` steps away.

Why?

Because the first element already occupies the starting position. It takes zero steps to reach it.

For three elements:

- First element: 0 steps.
- Second element: 1 step.
- Third element: 2 steps.
- Next position: 3 steps.

That gives us the formulas naturally.

# 3. Formula A: `(front + size - 1) % capacity`

```
int rear = (front + size - 1) % elements.length;
```

This calculates the index of the last existing element.

Let's derive it without memorizing anything.

We have:

```
front = 1;
size = 3;
capacity = 5;
```

Start at index `1`.

There are three existing elements, so the last one is two steps away:

```
Number of steps to last element = size - 1
                                = 3 - 1
                                = 2
```

Add those steps to `front`:

```
Last element index = front + size - 1
                   = 1 + 3 - 1
                   = 3
```

Therefore:

```
int rear = (1 + 3 - 1) % 5;
// rear = 3
```

Why do we need `% 5`? Because the queue is circular. If the calculation goes past index `4`, we must wrap around to index `0`.

So the full formula is:

```
int rear = (front + size - 1) % capacity;
```

Think of this as:

> Start at the front and move `size - 1` steps to find the last element that already exists.

# 4. Formula B: `(front + size) % capacity`

```
int rear = (front + size) % elements.length;
```

In the insertion code, this variable represents the next insertion position, not the current rear.

Let's use the exact same example:

```
front = 1;
size = 3;
capacity = 5;
```

The existing elements are:

```
Index:      0    1    2    3    4
           [ ]  [A]  [B]  [C]  [ ]

                 ↑              ↑
               front       next insertion
```

We already have three elements. To find the next position, we move three steps from the front:

```
Step 0: index 1 → A
Step 1: index 2 → B
Step 2: index 3 → C
Step 3: index 4 → next insertion position
```

So:

```
int rear = (1 + 3) % 5;
// rear = 4
```

The formula is:

```
int nextInsertionIndex = (front + size) % capacity;
```

Think of it as:

> Start at the front and move `size` steps to find the position immediately after all existing elements.

Why `size` rather than `size - 1`? Because we want the position after the last element, not the last element itself.

# 5. Now make it circular: what happens when we reach the end?

This is where the modulo operator becomes important.

Suppose:

```
capacity = 5;
front = 3;
size = 3;
```

Our queue wraps around the array:

```
Index:       0    1    2    3    4
            [C]  [ ]  [ ]  [A]  [B]
             ↑              ↑    ↑
           rear            front
```

The logical queue is:

```
A → B → C
```

Let's calculate both positions.

### Find the last existing element

The last element `C` is two steps from `front`.

```
int lastElementIndex = (front + size - 1) % capacity;

int lastElementIndex = (3 + 3 - 1) % 5;
//                     5 % 5
//                     0
```

Correct: `C` is at index `0`.

### Find the next insertion position

The next position is three steps from `front`.

```
int nextInsertionIndex = (front + size) % capacity;

int nextInsertionIndex = (3 + 3) % 5;
//                        6 % 5
//                        1
```

Correct: index `1` is the next position.

```
Index:       0    1    2    3    4
            [C]  [ ]  [ ]  [A]  [B]
             ↑    ↑              ↑
          last   next           front
          item   insert
```

The `% capacity` part converts a position that extends beyond the physical array into a valid index.

For example:

```
Index 5 → 5 % 5 = 0
Index 6 → 6 % 5 = 1
Index 7 → 7 % 5 = 2
```

This is simply circular movement.

# 6. See both formulas side by side

Let's use a capacity of `5` and `front = 3`.

| `size` | Existing elements | Last existing index | Next insertion index |
| ------ | ----------------- | ------------------- | -------------------- |
| 1      | A                 | 3                   | 4                    |
| 2      | A, B              | 4                   | 0                    |
| 3      | A, B, C           | 0                   | 1                    |
| 4      | A, B, C, D        | 1                   | 2                    |
| 5      | A, B, C, D, E     | 2                   | 3                    |

For example, with `size = 3`:

```
// The third element is at index 0.
int lastElementIndex = (3 + 3 - 1) % 5; // 0

// The next insertion position is index 1.
int nextInsertionIndex = (3 + 3) % 5;   // 1
```

When the queue is full (`size = 5`), the next insertion formula points back to the front. That's expected: every physical slot is occupied, so we must check `isFull()` before inserting.

In a full queue, the next insertion position is not actually available; the formula only tells us where the circular index would wrap to.

# 7. Why the two formulas appear in different methods

Look at the two relevant parts of the Java implementation.

```
public boolean enQueue(int value) {
    if (isFull()) {
        return false;
    }

    // We want the NEXT position, where the new value will be stored.
    int nextInsertionIndex = (front + size) % elements.length;

    elements[nextInsertionIndex] = value;
    size++;

    return true;
}

public int Rear() {
    if (isEmpty()) {
        return -1;
    }

    // We want the LAST existing element, which is already in the queue.
    int lastElementIndex = (front + size - 1) % elements.length;

    return elements[lastElementIndex];
}
```

I've deliberately changed the variable names from `rear` to `nextInsertionIndex` and `lastElementIndex`.

The name `rear` alone can be confusing because one calculation identifies the current last element, while the other identifies where the next last element will go.

## 8. The mental model to keep forever

Imagine people standing in a line.

- `front` identifies the first person.
- `size` tells you how many people are in the line.
- The last person is `size - 1` steps away from the first person because the first person is already at step zero.
- The next available position is `size` steps away because you must go one step beyond the last person.

Therefore:

```
// Find the LAST EXISTING element:
(front + size - 1) % capacity

// Find the NEXT INSERTION position:
(front + size) % capacity
```

Here's a tiny visual to make the distinction stick:

```
front
  |
  v
 [A] [B] [C] [ _ ]
  0   1   2    3
  |           |
  |           +-- Next insertion: front + size
  |
  +-------------- Last element: front + size - 1
```

The array indices in this illustration assume `front = 0` and `size = 3`.

The key is to count steps, not elements. The first element takes zero steps to reach, so the last of `size` elements is `size - 1` steps away. The position after all `size` elements is `size` steps away.

Once you understand that distinction, you can derive both formulas yourself rather than memorize them.
