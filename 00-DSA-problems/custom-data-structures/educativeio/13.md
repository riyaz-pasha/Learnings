# MKAverage — Data Structure Design in Java 24

## 0. Understand the problem in simple terms

Imagine integers arriving one by one in a stream. We want to calculate an average of the most recent `m` numbers, but we don't want the smallest `k` numbers or the largest `k` numbers to influence that average.

This is called a trimmed mean.

For example, suppose:

- `m = 6`: consider the last 6 numbers.
- `k = 1`: discard the smallest 1 number and largest 1 number.

The current window is:

`[3, 1, 10, 5, 8, 4]`

First, sort the window:

`[1, 3, 4, 5, 8, 10]`

Remove the smallest and largest elements:

`[3, 4, 5, 8]`

Calculate the average of the remaining elements:

\\[ \left\lfloor\frac{3+4+5+8}{6-2(1)}\right\rfloor =\left\lfloor\frac{20}{4}\right\rfloor=5 \\]

Notice that we divide by `m - 2k`, not by `m`, because we removed `2k` elements.

The data structure must support three operations:

- `MKAverage(m, k)`: initialize an empty stream.
- `addElement(num)`: add a number to the stream and retain only the latest `m` numbers for future calculations.
- `calculateMKAverage()`: return `-1` until at least `m` numbers have arrived; otherwise, return the trimmed average, rounded down.

The key challenge is efficiency. Sorting the last `m` elements every time we calculate the average would be expensive.

## 1. Clarifying questions to ask the interviewer

1\. Is the window always the last `m` elements? Yes, according to the statement. This means we need a FIFO structure to identify the element that expires when a new element arrives.

2\. Can the same number appear multiple times? Yes. We must track duplicates correctly, including when equal numbers appear in different partitions.

3\. What should happen before `m` elements arrive? Return `-1`, without attempting to calculate an average.

4\. Can the sum exceed Java's `int` range? Yes. Since numbers can be as large as \\(10^5\\) and `m` can be as large as \\(10^5\\), the sum can reach \\(10^{10}\\). Use `long` for the running sum.

5\. What performance is expected? With up to \\(10^5\\) elements, repeatedly sorting the window is undesirable. We should target approximately \\(O(\log m)\\) per insertion and removal, and \\(O(1)\\) per average calculation.

## 2. Core intuition: maintain three groups

The most useful way to think about this problem is:

Instead of repeatedly sorting the entire window, keep the window sorted logically by maintaining three ordered groups.

We need these groups:

1. `low`: the smallest `k` elements.
2. `mid`: the middle `m - 2k` elements.
3. `high`: the largest `k` elements.

We also maintain the sum of `mid`, so calculating the answer takes constant time.

### Visualize the three groups

Suppose `m = 7`, `k = 2`, and the current window contains:

`[9, 1, 7, 3, 10, 4, 2]`

After ordering the elements, we maintain:

The answer is `14 / (7 - 4) = 4`.

The ordering invariant is:

\\[ \text{every low element}\leq \text{every mid element}\leq \text{every high element} \\]

And the sizes must always be:

- `low.size() = k`
- `mid.size() = m - 2k`
- `high.size() = k`

Once these conditions hold, the answer is simply:

\\[ \left\lfloor\frac{\text{midSum}}{m-2k}\right\rfloor \\]

The hard part is maintaining those conditions as elements arrive and old elements expire.

### Why use ordered multisets?

Java's `TreeMap<Integer, Integer>` can act as a multiset: a sorted collection that stores how many times each integer occurs.

It supports:

- `firstKey()` — smallest value.
- `lastKey()` — largest value.
- `put` / `merge` — add an occurrence.
- Decrement a frequency or remove a key when its frequency reaches zero.

Each operation takes \\(O(\log m)\\) time.

Unlike a `TreeSet`, a multiset preserves duplicates. For example, `[2, 2, 2, 5]` contains four elements, not two.

## 3. The update strategy

Every new element may cause an old element to leave the window. We need to update the groups without breaking their sizes or ordering.

Consider `m = 5`, `k = 1`. Our groups should contain:

- One smallest element.
- Three middle elements.
- One largest element.

Suppose the current window is `[1, 3, 5, 7, 9]`. The groups are:

```
LOW       MID          HIGH
[1]       [3, 5, 7]   [9]
```

Now `2` arrives. Since the window is full, `1` expires.

The new window must be `[3, 5, 7, 9, 2]`, which sorts to `[2, 3, 5, 7, 9]`.

The correct groups are:

```
LOW       MID          HIGH
[2]       [3, 5, 7]   [9]
```

Our algorithm should not rebuild everything from scratch. Instead, it removes the expired occurrence, inserts the new occurrence into an appropriate group, and rebalances the groups.

### A reliable way to rebalance

After inserting or removing an element:

1. Move the smallest element from `mid` to `low` until `low` contains exactly `k` elements.
2. Move the largest element from `low` to `mid` if `low` is too large.
3. Move the largest element from `mid` to `high` until `high` contains exactly `k` elements.
4. Move the smallest element from `high` to `mid` if `high` is too large.
5. Ensure the groups remain correctly ordered.

There is a cleaner implementation technique: maintain the groups with ordered multisets and rebalance by moving boundary elements. We'll use that for the optimal solution.

## 4. Solution 1 — Brute force: sort the window on every calculation

The simplest correct approach is to store the latest `m` numbers in a queue. Whenever `calculateMKAverage()` is called, copy and sort the window, skip the first `k` and last `k` elements, and sum the remaining values.

This is the best starting point in an interview because it establishes correctness before optimization.

```
import java.util.*;

class MKAverageBruteForce {
    /*
     * WHY THIS WORKS:
     * The queue stores exactly the most recent m elements.
     * Sorting a copy lets us discard the k smallest and k largest.
     *
     * WHY WE COPY:
     * Sorting the queue itself would destroy the arrival order, which
     * we need to know which element expires next.
     *
     * TIME:
     * addElement: O(1) amortized, because removing from and appending
     *             to an ArrayDeque are constant-time operations.
     * calculateMKAverage: O(m log m) for sorting, plus O(m) to sum.
     *
     * SPACE:
     * O(m) for the queue and the temporary array.
     *
     * LIMITATION:
     * Repeated sorting can be too slow for up to 10^5 operations.
     */
    private final int m;
    private final int k;
    private final Deque<Integer> window = new ArrayDeque<>();

    public MKAverageBruteForce(int m, int k) {
        this.m = m;
        this.k = k;
    }

    public void addElement(int num) {
        window.addLast(num);

        // FIFO eviction: the oldest number leaves the sliding window.
        if (window.size() > m) {
            window.removeFirst();
        }
    }

    public int calculateMKAverage() {
        if (window.size() < m) {
            return -1;
        }

        int[] sorted = window.stream()
                .mapToInt(Integer::intValue)
                .toArray();

        Arrays.sort(sorted);

        long sum = 0;

        // Indices [k, m-k) exclude exactly k elements from each end.
        for (int i = k; i < m - k; i++) {
            sum += sorted[i];
        }

        // Integer division truncates toward zero; the sum is nonnegative,
        // so this is exactly the required floor.
        return (int) (sum / (m - 2 * k));
    }
}
```

## 5. Solution 2 — Optimal: sliding window + three TreeMap multisets

The improvement is to avoid sorting the same elements repeatedly.

The data structure maintains:

- A queue containing the last `m` numbers in arrival order.
- Three `TreeMap` multisets representing `low`, `mid`, and `high`.
- A `long midSum` that is updated whenever an element enters or leaves `mid`.

A crucial implementation detail is that we only need to initialize the partitions when the window first becomes full. Before then, there is no valid answer, so we can simply maintain the queue.

### Modern Java 24 implementation

```
import java.util.*;

class MKAverage {
    private final int m;
    private final int k;
    private final int midSize;

    // Preserves arrival order, so we can remove the expired oldest element.
    private final Deque<Integer> window = new ArrayDeque<>();

    // Sorted multisets: each key is a number and its value is its frequency.
    private final NavigableMap<Integer, Integer> low = new TreeMap<>();
    private final NavigableMap<Integer, Integer> mid = new TreeMap<>();
    private final NavigableMap<Integer, Integer> high = new TreeMap<>();

    // Sum of every occurrence in mid; use long because the sum can reach 1e10.
    private long midSum = 0;

    public MKAverage(int m, int k) {
        this.m = m;
        this.k = k;
        this.midSize = m - 2 * k;
    }

    // Adds one occurrence to a multiset. Duplicates increase its frequency.
    private void add(NavigableMap<Integer, Integer> set, int value) {
        set.merge(value, 1, Integer::sum);
    }

    // Removes exactly one occurrence; a key disappears only when its
    // frequency becomes zero.
    private void remove(NavigableMap<Integer, Integer> set, int value) {
        int frequency = set.get(value);

        if (frequency == 1) {
            set.remove(value);
        } else {
            set.put(value, frequency - 1);
        }
    }

    // The following helpers maintain midSum automatically.

    private void addLow(int value) {
        add(low, value);
    }

    private void removeLow(int value) {
        remove(low, value);
    }

    private void addMid(int value) {
        add(mid, value);
        midSum += value;
    }

    private void removeMid(int value) {
        remove(mid, value);
        midSum -= value;
    }

    private void addHigh(int value) {
        add(high, value);
    }

    private void removeHigh(int value) {
        remove(high, value);
    }

    /*
     * INITIALIZATION:
     * When the window first reaches m elements, sort its contents once.
     * The first k go to low, the next m-2k go to mid, and the final k
     * go to high.
     *
     * COST: O(m log m) time and O(m) additional space.
     */
    private void initializePartitions() {
        int[] sorted = window.stream()
                .mapToInt(Integer::intValue)
                .toArray();

        Arrays.sort(sorted);

        for (int i = 0; i < m; i++) {
            if (i < k) {
                addLow(sorted[i]);
            } else if (i < m - k) {
                addMid(sorted[i]);
            } else {
                addHigh(sorted[i]);
            }
        }
    }

    /*
     * INSERTION:
     * Place a new value in the group suggested by the current boundaries.
     * The multiset sizes may temporarily be incorrect; rebalance() fixes
     * them after the insertion or eviction.
     */
    private void insertValue(int value) {
        if (low.isEmpty() || value <= low.lastKey()) {
            addLow(value);
        } else if (high.isEmpty() || value >= high.firstKey()) {
            addHigh(value);
        } else {
            addMid(value);
        }
    }

    /*
     * EVICTION:
     * Remove one occurrence from whichever partition contains the expired
     * value. Boundary comparisons identify a valid partition because the
     * partition ordering invariant is maintained.
     *
     * Equality is intentional: if value == low.lastKey(), low contains
     * at least one such occurrence; removing any equal occurrence is fine.
     */
    private void removeValue(int value) {
        if (!low.isEmpty() && value <= low.lastKey()) {
            removeLow(value);
        } else if (!high.isEmpty() && value >= high.firstKey()) {
            removeHigh(value);
        } else {
            removeMid(value);
        }
    }

    /*
     * REBALANCING:
     * The goal is always:
     * low.size()  = k
     * mid.size()  = m - 2k
     * high.size() = k
     *
     * First fix low by moving boundary elements between low and mid.
     * Then fix high by moving boundary elements between mid and high.
     *
     * Moving an element into or out of mid also updates midSum.
     * Since we only rebalance a single insertion/eviction at a time,
     * the number of boundary moves is bounded by a constant.
     */
    private void rebalance() {
        // Fix the number of smallest elements.
        while (low.size() > k) {
            int value = low.lastKey();
            removeLow(value);
            addMid(value);
        }

        while (low.size() < k) {
            int value = mid.firstKey();
            removeMid(value);
            addLow(value);
        }

        // Fix the number of largest elements.
        while (high.size() > k) {
            int value = high.firstKey();
            removeHigh(value);
            addMid(value);
        }

        while (high.size() < k) {
            int value = mid.lastKey();
            removeMid(value);
            addHigh(value);
        }
    }

    public void addElement(int num) {
        window.addLast(num);

        if (window.size() < m) {
            // Not enough numbers for a valid MK Average yet.
            return;
        }

        if (window.size() == m && low.isEmpty()
                && mid.isEmpty() && high.isEmpty()) {
            // The first complete window: establish the partitions once.
            initializePartitions();
            return;
        }

        // When the queue becomes m+1, its oldest element expires.
        // We remove it from the queue and from its corresponding partition.
        if (window.size() > m) {
            int expired = window.removeFirst();
            removeValue(expired);
        }

        insertValue(num);
        rebalance();
    }

    public int calculateMKAverage() {
        if (window.size() < m) {
            return -1;
        }

        // The middle group has exactly m-2k elements.
        // Integer division gives the floor because all values are positive.
        return (int) (midSum / midSize);
    }
}
```

## 6. Edge cases to watch out for

| Edge case                     | Expected behavior                                   |
| ----------------------------- | --------------------------------------------------- |
| Fewer than `m` elements       | Return `-1`.                                        |
| Exactly `m` elements          | Calculate the first valid answer.                   |
| Repeated values               | Track occurrences, not just distinct values.        |
| All values are equal          | Return that value.                                  |
| `k = 1`                       | Remove one smallest and one largest element.        |
| `m - 2k = 1`                  | The middle contains exactly one element; return it. |
| Expired element is in `low`   | Remove it, then restore the partition sizes.        |
| Expired element is in `mid`   | Remove it and subtract it from `midSum`.            |
| Expired element is in `high`  | Remove it, then restore the partition sizes.        |
| Large values and large window | Use `long` for the middle sum.                      |

### A particularly important test: duplicates

For `m = 5`, `k = 1`, consider:

```
Window: [5, 5, 5, 5, 5]

LOW       MID          HIGH
[5]       [5, 5, 5]   [5]

midSum = 15
MKAverage = 15 / 3 = 5
```

When a `5` expires, it does not matter which partition's occurrence is removed, provided the multiset frequencies, group sizes, and `midSum` remain consistent. Equal values are interchangeable.

### Why `long` matters

The maximum possible sum of the middle elements is:

\\[ 10^5 \times 10^5 = 10^{10} \\]

Java's `int` only holds values up to approximately \\(2.147 \times 10^9\\), so an `int` sum can overflow. Using `long` prevents that problem.

## 7. Complexity analysis

Let `m` be the window size and `k` be the number removed from each end.

| Operation                    | Brute force          | Three-`TreeMap` solution  |
| ---------------------------- | -------------------- | ------------------------- |
| Constructor                  | \\(O(1)\\)           | \\(O(1)\\)                |
| `addElement`                 | \\(O(1)\\) amortized | \\(O(\log m)\\) amortized |
| `calculateMKAverage`         | \\(O(m\log m)\\)     | \\(O(1)\\)                |
| Initialization of partitions | Not applicable       | \\(O(m\log m)\\), once    |
| Space                        | \\(O(m)\\)           | \\(O(m)\\)                |

The optimal implementation has a one-time \\(O(m\log m)\\) initialization cost when the first complete window is formed. Subsequent updates take \\(O(\log m)\\) time because only a constant number of multiset insertions, removals, and boundary moves are needed.

This gives us the desired efficient streaming behavior.

## 8. Interviewer follow-up questions and answers

### Q1. Why not use a `PriorityQueue` for each partition?

A min-heap and max-heap can retrieve extreme elements efficiently, but Java's `PriorityQueue.remove(value)` takes \\(O(m)\\) time because it must search for the value. An expired element can be anywhere in a heap.

Three `TreeMap` multisets support removal of a specific value in \\(O(\log m)\\), which is a better fit for this sliding-window problem.

A heap-based implementation can also be optimized using lazy deletion, but it requires extra bookkeeping to handle stale elements.

### Q2. Why do we need both a queue and three multisets?

They serve different purposes:

- The queue tells us which element expires next.
- The multisets tell us where each element belongs by sorted rank.
- `midSum` tells us the sum of the retained elements without rescanning them.

None of these structures alone provides all three capabilities efficiently.

### Q3. Why does the answer take \\(O(1)\\) time?

Because the sum of the middle partition is maintained incrementally. We never need to enumerate the middle elements during a query.

The calculation is one division:

```
return (int) (midSum / midSize);
```

### Q4. What if the interviewer asks for an array-based solution instead?

Since the constraints cap the window size at \\(10^5\\), we could store the window in a circular array and use an order-statistics data structure or coordinate compression with a Fenwick tree.

A Fenwick tree is especially useful when the values belong to a known bounded domain, as they do here: `1` through `100000`. It can maintain frequencies and sums, allowing us to find the first `k` and last `k` elements by rank and compute the middle sum efficiently. This is another optimal approach, though it needs more careful implementation.

### Q5. Which solution would you present in an interview?

I would proceed in this order:

1. Explain the brute-force approach to establish correctness.
2. Identify repeated sorting as the bottleneck.
3. Introduce the three partitions and the running middle sum.
4. Implement the three-multiset approach.
5. Explain the ordering and size invariants, duplicate handling, and why `long` is necessary.

The main insight to remember is that we do not need to sort the entire window again; we only need to maintain the boundaries separating the smallest, middle, and largest elements.

```
Value → Frequency

\\[ 2+1=3 \\]

private int elementCount(NavigableMap<Integer, Integer> set) {
    return set.values()
              .stream()
              .mapToInt(Integer::intValue)
              .sum();
}

while (elementCount(low) > k) {
    // Move one occurrence from low to mid.
}

}
```

Important: this fixes the element-counting issue, but the helper takes \\(O(d)\\) time, where `d` is the number of unique keys. Calling it repeatedly would make the solution slower.

For an efficient implementation, maintain an explicit count of occurrences in each partition, updating it whenever an element is added or removed. Then the checks become \\(O(1)\\):

```
while (lowCount > k) {
    // Move one occurrence from low to mid.
}

while (lowCount < k) {
    // Move one occurrence from mid to low.
}
```

Here, `lowCount` counts all occurrences, including duplicates, rather than unique keys or the sum of values.

The same applies to `mid` and `high`.

# MKAverage — Building the Intuition from Scratch

Let's rebuild the solution from the beginning, focusing on why the data structure works, how to think about it, and how duplicates affect the implementation.

The most important correction to our earlier code is this:

> `k` is a number of elements, not a sum of values. And `TreeMap.size()` counts distinct keys, not all occurrences.

We'll fix that and build a correct, efficient Java solution.

## 1. Understand the problem with a concrete example

Suppose:

```
m = 7;
k = 2;
```

Numbers arrive in a stream:

```
5, 1, 9, 3, 1, 7, 5
```

We need to consider the latest `m = 7` numbers. Since seven numbers have arrived, our window is:

```
Arrival order:
[5, 1, 9, 3, 1, 7, 5]
```

For the MK Average, we temporarily sort them:

```
Sorted:
[1, 1, 3, 5, 5, 7, 9]
```

We remove the smallest `k = 2` elements and largest `k = 2` elements.

```
Discard smallest 2: [1, 1]
Keep middle:        [3, 5, 5]
Discard largest 2:  [7, 9]
```

Therefore:

\\[ MKAverage=\left\lfloor\frac{3+5+5}{7-2(2)}\right\rfloor =\left\lfloor\frac{13}{3}\right\rfloor=4 \\]

Notice that we kept three occurrences in the middle, even though the middle has only two distinct values: `3` and `5`.

That distinction is the key to understanding the implementation.

## 2. The mental model: three buckets

Instead of sorting all seven numbers every time we calculate the average, we maintain three buckets:

- `low`: the smallest `k` elements.
- `mid`: the middle `m - 2k` elements.
- `high`: the largest `k` elements.

For our example:

```
                    ALL 7 ELEMENTS
                           |
              +------------+------------+
              |            |            |
           LOW (2)       MID (3)      HIGH (2)
              |            |            |
            [1, 1]       [3, 5, 5]     [7, 9]
              |            |            |
          Discard       Keep these    Discard
                         Sum = 13
```

The answer is always:

```
midSum / (m - 2 * k)
```

Why? Because the other two buckets already contain exactly the elements that must be discarded.

This leads to our main strategy:

Maintain the three buckets correctly whenever a number arrives or leaves. Then the answer requires only one division.

## 3. Why `TreeMap.size()` caused the confusion

Let's take this code:

```
TreeMap<Integer, Integer> low = new TreeMap<>();

low.put(1, 2);
low.put(3, 1);
```

What does this map contain?

```
Key (number) | Value (frequency)
-------------|------------------
1            | 2
3            | 1
```

This represents the multiset:

```
[1, 1, 3]
```

But Java sees only two distinct keys: `1` and `3`.

```
low.size(); // 2
```

The actual number of elements is:

```
Frequency of 1 + frequency of 3
= 2 + 1
= 3
```

So this is the difference:

| Expression                    | What it counts                             |
| ----------------------------- | ------------------------------------------ |
| `low.size()`                  | Distinct keys: `2`                         |
| `low.get(1)`                  | Occurrences of value `1`: `2`              |
| Sum of all frequencies        | Total occurrences: `3`                     |
| `lowSum` (if we maintain one) | Sum of the numeric values, not their count |

For MKAverage, we need the total number of occurrences in each bucket.

For example, if `k = 2`, then `low` must hold two elements. Both of these are valid representations of a bucket with two elements:

```
low = {1 → 2}
```

```
low = {1 → 1, 3 → 1}
```

In both cases, the bucket contains exactly two elements, even though the number of distinct keys differs.

## 4. How do we maintain the correct number of elements?

There are two possible approaches.

### Approach A: Recalculate the number of occurrences

We could calculate the total frequency every time:

```
int count = low.values()
               .stream()
               .mapToInt(Integer::intValue)
               .sum();
```

This is correct, but it takes \\(O(d)\\) time, where `d` is the number of distinct keys in the map.

We don't want to scan the map repeatedly.

### Approach B: Maintain an explicit occurrence count

This is the better approach.

Whenever we insert one occurrence into `low`, increment `lowCount`.

Whenever we remove one occurrence from `low`, decrement `lowCount`.

```
lowCount++; // One occurrence entered low.
lowCount--; // One occurrence left low.
```

Now:

```
while (lowCount > k) {
    // Move one element from low to mid.
}

while (lowCount < k) {
    // Move one element from mid to low.
}
```

These conditions now mean exactly what we want:

- `lowCount > k`: too many elements in `low`.
- `lowCount < k`: too few elements in `low`.
- `lowCount == k`: exactly the required number.

We use the same principle for `mid` and `high`.

Importantly, the count is not the sum of the values. If `low = [1, 100]`, then its element count is `2`, while its sum is `101`.

## 5. How do the buckets change when a new number arrives?

Let's work through a complete sliding-window example.

Suppose:

```
m = 5
k = 1
```

Therefore:

```
low must contain 1 element
mid must contain 3 elements
high must contain 1 element
```

### Step 1: The first five numbers arrive

The stream receives:

```
4, 1, 7, 3, 9
```

The sorted order is:

```
[1, 3, 4, 7, 9]
```

Our buckets are:

```
LOW          MID              HIGH
[1]          [3, 4, 7]        [9]
```

The middle sum is:

```
midSum = 3 + 4 + 7 = 14
```

So:

```
MKAverage = 14 / 3 = 4
```

### Step 2: The number `2` arrives

The current window has five numbers, so the oldest number, `4`, must expire.

Before the update:

```
Window: [4, 1, 7, 3, 9]
```

After adding `2` and removing `4`:

```
Window: [1, 7, 3, 9, 2]
```

Sorted:

```
[1, 2, 3, 7, 9]
```

The correct buckets are now:

```
LOW          MID              HIGH
[1]          [2, 3, 7]        [9]
```

The middle sum is now:

```
midSum = 2 + 3 + 7 = 12
```

The answer becomes:

```
MKAverage = 12 / 3 = 4
```

We didn't need to sort the entire window again. We removed the expired value, inserted the new value, and repaired the buckets.

### Step 3: What if a new number belongs in `low`?

Suppose the next number is `0`.

The current window becomes:

```
[1, 7, 3, 9, 2, 0]
```

After the oldest number (`1`) expires, the new window is:

```
[7, 3, 9, 2, 0]
```

Sorted:

```
[0, 2, 3, 7, 9]
```

The buckets must be:

```
LOW          MID              HIGH
[0]          [2, 3, 7]        [9]
```

The new `0` belongs in `low`. But the old `1` also belonged in `low`, so we remove `1` and insert `0`. The bucket counts stay correct.

This is a simple case: no additional rebalancing is required.

### Step 4: What if an insertion makes a bucket too large?

Suppose the window is:

```
[2, 3, 5, 7, 9]
```

Its buckets are:

```
LOW          MID              HIGH
[2]          [3, 5, 7]        [9]
```

Now the oldest element `2` expires and `1` arrives.

After removing `2`, `low` has zero elements. Inserting `1` puts it into `low` again, restoring the expected count.

Other cases can cause a bucket to temporarily contain too many or too few elements. We fix these by moving boundary elements:

```
If low has too many elements:
    Move the largest low element into mid.

If low has too few elements:
    Move the smallest mid element into low.

If high has too many elements:
    Move the smallest high element into mid.

If high has too few elements:
    Move the largest mid element into high.
```

Why these particular elements? Because moving the boundary element preserves the sorted ordering between the buckets.

## 6. Complete corrected Java solution

The following implementation uses three `TreeMap` multisets, explicit occurrence counts, a queue for the sliding window, and a running sum for the middle partition.

This is the implementation to study and use as your main interview solution.

```
import java.util.ArrayDeque;
import java.util.Arrays;
import java.util.Deque;
import java.util.NavigableMap;
import java.util.TreeMap;

class MKAverage {

    private final int m;
    private final int k;
    private final int midSize;

    /*
     * WHY DO WE NEED A QUEUE?
     *
     * We must always consider the most recent m numbers.
     * The oldest number expires whenever a new number arrives
     * after the window is already full.
     *
     * ArrayDeque keeps insertion order and removes the oldest
     * element in O(1) time.
     */
    private final Deque<Integer> window = new ArrayDeque<>();

    /*
     * WHY THREE TREEMAPS?
     *
     * low  = k smallest occurrences.
     * mid  = m - 2*k middle occurrences.
     * high = k largest occurrences.
     *
     * Each TreeMap stores:
     *     number -> frequency
     *
     * Example:
     *     {2 -> 3, 5 -> 1}
     *
     * represents the multiset [2, 2, 2, 5].
     *
     * TreeMap keeps DISTINCT keys sorted, but its size()
     * does not count duplicate occurrences.
     */
    private final NavigableMap<Integer, Integer> low =
            new TreeMap<>();

    private final NavigableMap<Integer, Integer> mid =
            new TreeMap<>();

    private final NavigableMap<Integer, Integer> high =
            new TreeMap<>();

    /*
     * IMPORTANT:
     *
     * These counters count TOTAL OCCURRENCES, not distinct keys.
     *
     * For example:
     *     low = {2 -> 3}
     *
     * Then:
     *     low.size() = 1       (one distinct key)
     *     lowCount   = 3       (three occurrences)
     *
     * We need occurrence counts because k refers to the number
     * of elements that must be discarded.
     */
    private int lowCount = 0;
    private int midCount = 0;
    private int highCount = 0;

    /*
     * The sum of all values in mid.
     *
     * Use long because as many as 100,000 values of up to
     * 100,000 can contribute to the sum: up to 10^10.
     */
    private long midSum = 0;

    public MKAverage(int m, int k) {
        this.m = m;
        this.k = k;
        this.midSize = m - 2 * k;
    }

    // ---------------------------------------------------------
    // 1. BASIC MULTISET OPERATIONS
    // ---------------------------------------------------------

    /*
     * Add exactly one occurrence of value to the given multiset.
     *
     * merge(value, 1, Integer::sum) means:
     * - If value is absent, store frequency 1.
     * - If value exists, increment its frequency.
     *
     * Time: O(log m).
     */
    private void addToSet(
            NavigableMap<Integer, Integer> set,
            int value) {

        set.merge(value, 1, Integer::sum);
    }

    /*
     * Remove exactly one occurrence.
     *
     * Example:
     *     {2 -> 3}
     *
     * Removing one 2 produces:
     *     {2 -> 2}
     *
     * If its frequency was already 1, remove the key entirely.
     *
     * Time: O(log m).
     */
    private void removeFromSet(
            NavigableMap<Integer, Integer> set,
            int value) {

        int frequency = set.get(value);

        if (frequency == 1) {
            set.remove(value);
        } else {
            set.put(value, frequency - 1);
        }
    }

    // ---------------------------------------------------------
    // 2. PARTITION-AWARE OPERATIONS
    // ---------------------------------------------------------

    /*
     * Every insertion/removal goes through these helpers.
     *
     * WHY?
     *
     * We want the TreeMap contents, occurrence counts, and midSum
     * to stay synchronized.
     *
     * This prevents subtle bugs where a value moves between
     * partitions but midSum is not updated.
     */

    private void addLow(int value) {
        addToSet(low, value);
        lowCount++;
    }

    private void removeLow(int value) {
        removeFromSet(low, value);
        lowCount--;
    }

    private void addMid(int value) {
        addToSet(mid, value);
        midCount++;
        midSum += value;
    }

    private void removeMid(int value) {
        removeFromSet(mid, value);
        midCount--;
        midSum -= value;
    }

    private void addHigh(int value) {
        addToSet(high, value);
        highCount++;
    }

    private void removeHigh(int value) {
        removeFromSet(high, value);
        highCount--;
    }

    // ---------------------------------------------------------
    // 3. INITIALIZE THE FIRST COMPLETE WINDOW
    // ---------------------------------------------------------

    /*
     * Before m elements arrive, calculateMKAverage() returns -1.
     *
     * Once the first m elements arrive, we must establish
     * the three partitions for the first time.
     *
     * We sort the window ONCE:
     *
     *     [smallest k]
     *     [middle m - 2*k]
     *     [largest k]
     *
     * Subsequent updates do not require sorting the whole window.
     *
     * Time: O(m log m).
     */
    private void initializePartitions() {

        int[] sorted = window.stream()
                .mapToInt(Integer::intValue)
                .toArray();

        Arrays.sort(sorted);

        for (int i = 0; i < m; i++) {

            if (i < k) {
                addLow(sorted[i]);

            } else if (i < m - k) {
                addMid(sorted[i]);

            } else {
                addHigh(sorted[i]);
            }
        }
    }

    // ---------------------------------------------------------
    // 4. INSERT A NEW VALUE INTO AN APPROPRIATE PARTITION
    // ---------------------------------------------------------

    /*
     * We use the boundary values to decide where a number belongs.
     *
     * If value <= the largest value in low:
     *     It belongs in low.
     *
     * Otherwise, if value >= the smallest value in high:
     *     It belongs in high.
     *
     * Otherwise:
     *     It belongs in mid.
     *
     * WHY DO WE COMPARE BOUNDARIES?
     *
     * We maintain the ordering invariant:
     *
     *     every low value <= every mid value
     *     every mid value <= every high value
     *
     * Therefore, the boundary comparisons tell us the appropriate
     * partition without sorting the entire window.
     *
     * The insertion may temporarily change partition sizes.
     * rebalance() will restore the required counts afterward.
     */
    private void insertValue(int value) {

        if (lowCount == 0 || value <= low.lastKey()) {

            addLow(value);

        } else if (highCount == 0 || value >= high.firstKey()) {

            addHigh(value);

        } else {

            addMid(value);
        }
    }

    // ---------------------------------------------------------
    // 5. REMOVE THE EXPIRED VALUE
    // ---------------------------------------------------------

    /*
     * The queue tells us WHICH VALUE expires.
     *
     * The boundary comparisons tell us which partition contains
     * an occurrence of that value.
     *
     * Because equal values are interchangeable, we may remove
     * any matching occurrence, even if that particular numeric
     * occurrence originally entered a different partition.
     *
     * Example:
     *     low = {5 -> 1}
     *     mid = {5 -> 2}
     *
     * Removing one occurrence of 5 from low instead of mid is
     * still valid if the expired value is 5. The resulting
     * multiset of values is identical.
     *
     * This works because the partition ordering is maintained.
     */
    private void removeValue(int value) {

        if (lowCount > 0 && value <= low.lastKey()) {

            removeLow(value);

        } else if (highCount > 0 && value >= high.firstKey()) {

            removeHigh(value);

        } else {

            removeMid(value);
        }
    }

    // ---------------------------------------------------------
    // 6. REBALANCE THE THREE PARTITIONS
    // ---------------------------------------------------------

    /*
     * THIS IS THE CORE OF THE SOLUTION.
     *
     * The required occurrence counts are:
     *
     *     lowCount  = k
     *     midCount  = m - 2*k
     *     highCount = k
     *
     * We fix low first, then high.
     *
     * Notice that we use lowCount, midCount, and highCount.
     * We NEVER use TreeMap.size() to check the number of elements.
     *
     * Moving boundary elements preserves sorted ordering.
     *
     * Each operation changes a partition count and, when relevant,
     * adjusts midSum through addMid/removeMid.
     */
    private void rebalance() {

        // STEP A: Make low contain exactly k occurrences.

        while (lowCount > k) {

            /*
             * low has too many elements.
             *
             * Move its LARGEST element into mid.
             * It is the closest boundary element, so the ordering
             * between low and mid remains valid.
             */
            int value = low.lastKey();

            removeLow(value);
            addMid(value);
        }

        while (lowCount < k) {

            /*
             * low has too few elements.
             *
             * Move the SMALLEST element in mid into low.
             *
             * That value is the next-smallest candidate for low.
             */
            int value = mid.firstKey();

            removeMid(value);
            addLow(value);
        }

        // STEP B: Make high contain exactly k occurrences.

        while (highCount > k) {

            /*
             * high has too many elements.
             *
             * Move its SMALLEST element into mid.
             */
            int value = high.firstKey();

            removeHigh(value);
            addMid(value);
        }

        while (highCount < k) {

            /*
             * high has too few elements.
             *
             * Move the LARGEST element in mid into high.
             */
            int value = mid.lastKey();

            removeMid(value);
            addHigh(value);
        }

        /*
         * WHY IS MID'S SIZE NOW CORRECT?
         *
         * The total number of occurrences across all three
         * partitions is exactly m.
         *
         * We have made:
         *     lowCount  = k
         *     highCount = k
         *
         * Therefore:
         *
         *     midCount = m - k - k
         *              = m - 2*k
         *
         * We don't need a separate loop to rebalance mid.
         *
         * The partition boundaries are preserved because we only
         * move the smallest or largest boundary elements.
         */
    }

    // ---------------------------------------------------------
    // 7. ADD A NUMBER TO THE STREAM
    // ---------------------------------------------------------

    public void addElement(int num) {

        // Preserve arrival order for FIFO expiration.
        window.addLast(num);

        if (window.size() < m) {

            /*
             * The window is not full yet.
             *
             * We don't need to build partitions until the first
             * valid MK Average can be calculated.
             */
            return;
        }

        if (window.size() == m && lowCount == 0) {

            /*
             * This is the first time the window has reached m.
             *
             * Initialize the partitions from the complete window.
             */
            initializePartitions();
            return;
        }

        /*
         * The window is now m+1 elements long.
         *
         * Remove the oldest element from BOTH:
         * 1. The FIFO window.
         * 2. Its corresponding partition.
         */
        if (window.size() > m) {

            int expired = window.removeFirst();

            removeValue(expired);
        }

        /*
         * Insert the new value into the appropriate partition.
         */
        insertValue(num);

        /*
         * Removing an old value and inserting a new one may change
         * the partition counts.
         *
         * Restore the exact counts before the next query.
         */
        rebalance();
    }

    // ---------------------------------------------------------
    // 8. CALCULATE THE MK AVERAGE
    // ---------------------------------------------------------

    public int calculateMKAverage() {

        if (window.size() < m) {
            return -1;
        }

        /*
         * The middle partition contains exactly m - 2*k elements.
         *
         * Its sum is already maintained incrementally in midSum.
         *
         * No sorting or iteration is required.
         *
         * Integer division rounds down because the inputs and sum
         * are nonnegative.
         *
         * Time: O(1).
         */
        return (int) (midSum / midSize);
    }
}
```

## 7. Dry run: watch the counts and the sum change

Let's trace the corrected implementation with:

```
m = 5
k = 1
```

The required state after every update is:

```
lowCount  = 1
midCount  = 3
highCount = 1
```

### First five insertions

Stream:

```
4, 1, 7, 3, 9
```

After initialization:

```
low  = {1 -> 1}
mid  = {3 -> 1, 4 -> 1, 7 -> 1}
high = {9 -> 1}
```

The state variables are:

| Variable    | Value | Meaning                    |
| ----------- | ----- | -------------------------- |
| `lowCount`  | 1     | One occurrence in `low`    |
| `midCount`  | 3     | Three occurrences in `mid` |
| `highCount` | 1     | One occurrence in `high`   |
| `midSum`    | 14    | `3 + 4 + 7`                |

The answer is `14 / 3 = 4`.

### The next number is `2`

The stream becomes:

```
4, 1, 7, 3, 9, 2
```

The oldest element `4` expires.

Before inserting `2`, the partitions become:

```
low  = {1 -> 1}
mid  = {3 -> 1, 7 -> 1}
high = {9 -> 1}
```

Now `2` is inserted into `mid`, because it is greater than `low.lastKey()` (`1`) and less than `high.firstKey()` (`9`).

The updated partitions are:

```
low  = {1 -> 1}
mid  = {2 -> 1, 3 -> 1, 7 -> 1}
high = {9 -> 1}
```

The current window is:

```
[1, 7, 3, 9, 2]
```

The counts are again `1`, `3`, and `1`. The middle sum is:

```
midSum = 2 + 3 + 7 = 12
```

Therefore, the MK Average is `12 / 3 = 4`.

### Now let's see why explicit counts matter with duplicates

Suppose the window is:

```
[1, 1, 2, 2, 3]
```

For `m = 5` and `k = 1`, the partitions should be:

```
low  = [1]
mid  = [1, 2, 2]
high = [3]
```

The corresponding maps are:

```
low  = {1 -> 1}
mid  = {1 -> 1, 2 -> 2}
high = {3 -> 1}
```

Look at the middle partition:

```
mid.size(); // 2: distinct keys, 1 and 2
midCount;   // 3: total occurrences
midSum;     // 5: 1 + 2 + 2
```

This is why our corrected code uses `midCount` to track the number of occurrences and `midSum` to track their numeric sum.

The average is:

```
5 / 3 = 1
```

If we incorrectly used `mid.size()` as the divisor, we would calculate `5 / 2 = 2`, which is wrong.

## 8. The three invariants to remember

Whenever you design this data structure, mentally check these three rules.

Invariant 1: Correct partition sizes

```
lowCount  == k
midCount  == m - 2*k
highCount == k
```

These counters count occurrences, not distinct keys.

Invariant 2: Correct partition ordering

```
Every value in low <= every value in mid
Every value in mid <= every value in high
```

We preserve this ordering by moving boundary elements.

Invariant 3: Correct middle sum

```
midSum == sum of all occurrences in mid
```

Every insertion into `mid` increases `midSum`; every removal from `mid` decreases it.

If these three invariants hold, `calculateMKAverage()` is correct.

## 9. Time and space complexity

Let `m` be the window size.

- Constructor: \\(O(1)\\).
- First complete window: \\(O(m\log m)\\), because we sort once to initialize the partitions.
- Each subsequent `addElement`: \\(O(\log m)\\), because it performs a constant number of `TreeMap` operations and boundary moves.
- Each `calculateMKAverage`: \\(O(1)\\), because it divides the maintained middle sum by the middle element count.
- Space: \\(O(m)\\), for the queue and the three multisets.

The overall strategy is to pay a small cost whenever the window changes, rather than repeatedly sorting the entire window whenever someone asks for the average.

## 10. Final interview takeaway

The critical insight is not simply “use three `TreeMap`s.” It is to separate three responsibilities:

1. The queue tracks which value expires.
2. The ordered multisets track which values are the smallest, middle, and largest.
3. The explicit occurrence counters and `midSum` track how many elements belong to each partition and their sum.

Whenever you see `low.size() > k` in a multiset implementation, ask yourself: Does `size()` mean the number of occurrences, or the number of distinct values?

That question prevents one of the most subtle bugs in this problem.
