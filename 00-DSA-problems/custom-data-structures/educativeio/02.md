# Moving Average from Data Stream — Java 24 Interview Solution

## 0. Understand the problem in simple words

We receive integers one at a time. We need to calculate the average of the most recent `size` integers whenever a new integer arrives.

For example, suppose `size = 3`.

We receive the stream `1, 10, 3, 5`.

| Call       | Numbers received | Numbers in the current window | Moving average |
| ---------- | ---------------- | ----------------------------- | -------------- |
| `next(1)`  | 1                | 1                             | 1.0            |
| `next(10)` | 1, 10            | 1, 10                         | 5.5            |
| `next(3)`  | 1, 10, 3         | 1, 10, 3                      | 4.67           |
| `next(5)`  | 1, 10, 3, 5      | 10, 3, 5                      | 6.0            |

Important: Before the window fills, calculate the average of all values received so far. After it fills, discard the oldest value whenever a new value arrives.

## 1. Clarifying questions to ask the interviewer

1. Should we average fewer than `size` elements initially? Usually, yes. For example, with a window size of 3, the first call returns the average of just one value.
2. Should the window contain only the most recent `size` values? Yes, that is the standard sliding-window interpretation. Older values must no longer contribute to the average.
3. Can the input contain negative integers? Yes. The given constraints allow negative values, so the sum must handle them correctly.
4. Can we assume `size` is positive? Yes. The constraint guarantees `1 <= size <= 100`, so no extra validation is necessary for this problem.
5. Should `next()` return a fractional average? Yes. The return type is `double`, so we must avoid integer division.

## 2. Core idea and intuition

The key observation is that we do not need to recalculate the sum of the entire window on every call.

Suppose the window size is 3, and the current window is:

```
Window: [1, 10, 3]
Sum:     14
Average: 14 / 3 = 4.6667
```

The next value is `5`. The new window should be:

```
Old window: [1, 10, 3]
                         \
New value:                5

New window: [10, 3, 5]
```

Instead of adding all three new window values again, update the sum incrementally:

1. Remove the outgoing value `1` from the sum.
2. Add the incoming value `5` to the sum.
3. Calculate the average using the updated sum and the current window size.

```
Old sum = 14
Remove 1: 14 - 1 = 13
Add 5:    13 + 5 = 18

New average = 18 / 3 = 6.0
```

This gives us an efficient approach: maintain a queue of recent values and a running sum.

## 4. All solutions

### Solution 1: Brute force — store the window and recalculate the sum

Idea: Keep the most recent values in a queue. For every `next()` call, add the new value, remove the oldest if necessary, and iterate over the queue to calculate its sum.

```
import java.util.ArrayDeque;
import java.util.Deque;

class MovingAverageBruteForce {

    private final int size;
    private final Deque<Integer> window;

    public MovingAverageBruteForce(int size) {
        this.size = size;
        this.window = new ArrayDeque<>();

        // We use a queue because we must remove the oldest value
        // first (FIFO: First In, First Out).
        //
        // Constructor time: O(1), excluding any implementation-specific
        // initialization overhead.
        // Auxiliary space: O(size) for at most 'size' stored values.
    }

    public double next(int val) {

        // Step 1: Add the new value to the end of the window.
        window.offerLast(val);

        // Step 2: If the window exceeds its allowed size, remove
        // the oldest value from the front.
        //
        // This ensures that only the most recent 'size' values remain.
        if (window.size() > size) {
            window.pollFirst();
        }

        // Step 3: Recalculate the entire sum from scratch.
        // This is the expensive part: we visit every value in the window
        // on every call, even though most values have not changed.
        long sum = 0;

        for (int value : window) {
            sum += value;
        }

        // Step 4: Divide by the number of values actually present.
        // Initially, there may be fewer than 'size' values.
        //
        // Casting to double before division prevents integer division.
        return (double) sum / window.size();
    }

    // Time complexity:
    //   Queue insertion: O(1) amortized.
    //   Queue removal:   O(1) amortized.
    //   Summation:       O(k), where k = min(number of values received, size).
    //   Overall next():  O(size) worst case.
    //
    // Space complexity:
    //   O(size) for the queue.
    //
    // This solution is easy to understand, but repeatedly adds values
    // that were already included in the previous sum.
}
```

### Solution 2: Optimal interview solution — queue + running sum

Idea: Instead of recalculating the sum, maintain it as part of the object's state.

Whenever a value arrives:

- If the window is already full, remove the oldest value and subtract it from the sum.
- Add the incoming value and add it to the sum.
- Return `sum / numberOfValuesInWindow`.

```
import java.util.ArrayDeque;
import java.util.Deque;

class MovingAverage {

    private final int size;
    private final Deque<Integer> window;
    private long sum;

    public MovingAverage(int size) {
        this.size = size;
        this.window = new ArrayDeque<>();
        this.sum = 0L;

        // We keep the queue and running sum as instance variables
        // because every next() call must continue from the previous state.
        //
        // The queue stores the current window.
        // The sum stores the total of exactly those queued values.
        //
        // Constructor time: O(1).
        // Auxiliary space: O(size).
    }

    public double next(int val) {

        // Step 1: Remove the outgoing value BEFORE adding the new one.
        //
        // If the queue is already full, its oldest value will no longer
        // belong to the next window.
        //
        // Removing it from both the queue and sum keeps the two data
        // structures consistent.
        if (window.size() == size) {
            int oldest = window.pollFirst();
            sum -= oldest;
        }

        // Step 2: Add the incoming value to the window and running sum.
        //
        // After these operations, the queue contains exactly the most
        // recent values, up to the maximum of 'size' elements.
        window.offerLast(val);
        sum += val;

        // Step 3: Calculate the average of the CURRENT window.
        //
        // Before the window fills, divide by its actual number of values.
        // Once full, the divisor remains equal to 'size'.
        //
        // Casting to double is essential: without it, integer division
        // would discard the fractional part of the average.
        return (double) sum / window.size();
    }

    // Time complexity:
    //   Checking the queue size: O(1).
    //   Removing the oldest value, when necessary: O(1) amortized.
    //   Inserting the new value: O(1) amortized.
    //   Updating the running sum: O(1).
    //   Computing the average: O(1).
    //
    //   Therefore, next() is O(1) amortized per call.
    //
    // Space complexity:
    //   The queue stores at most 'size' integers: O(size).
    //   The running sum uses one long variable: O(1) additional space.
    //   Total auxiliary space: O(size).
    //
    // Why is this optimal?
    //   Each next() call must process the incoming value, so O(1) time
    //   per call is asymptotically optimal.
}
```

This is the standard solution I would recommend presenting in an interview. It uses a familiar data structure, has a simple invariant, and achieves constant-time updates.

### Solution 3: Optimal — fixed-size circular array

We can avoid the queue entirely by using an array of exactly `size` elements.

The array acts as a circular buffer: when it fills, the next incoming value overwrites the oldest value.

```
class MovingAverageCircularBuffer {

    private final int size;
    private final int[] window;

    private int nextIndex;
    private int count;
    private long sum;

    public MovingAverageCircularBuffer(int size) {
        this.size = size;
        this.window = new int[size];

        this.nextIndex = 0;
        this.count = 0;
        this.sum = 0L;

        // nextIndex identifies the array position that will be written
        // next. Once it reaches the end, it wraps around to index zero.
        //
        // count tracks how many values have been received, capped at size.
        //
        // Constructor time: O(size), because the array is initialized.
        // Auxiliary space: O(size), for the fixed-size array.
    }

    public double next(int val) {

        // If the buffer is full, window[nextIndex] is the oldest value.
        // Subtract that outgoing value before overwriting it.
        if (count == size) {
            sum -= window[nextIndex];
        } else {
            // During the initial filling phase, no value is overwritten.
            count++;
        }

        // Write the incoming value into the current circular position.
        window[nextIndex] = val;
        sum += val;

        // Move to the next position. Modulo wraps the index back to zero
        // when nextIndex reaches size.
        nextIndex = (nextIndex + 1) % size;

        // count is the number of values currently in the window.
        // It is less than size during initialization and equals size
        // once the circular buffer has filled.
        return (double) sum / count;
    }

    // Time complexity:
    //   Reading or overwriting one array position: O(1).
    //   Updating the running sum and count: O(1).
    //   Advancing the circular index: O(1).
    //   Therefore, next() is O(1) worst-case time.
    //
    // Space complexity:
    //   The fixed-size array uses O(size) space.
    //   All other fields use O(1) additional space.
    //
    // Compared with ArrayDeque, this implementation provides predictable
    // O(1) worst-case updates and avoids queue-node/deque bookkeeping.
    // The trade-off is that circular-index management is slightly less
    // straightforward to explain and implement.
}
```

## 5. Dry run of the optimal queue solution

Let `size = 3` and call `next(1)`, `next(10)`, `next(3)`, `next(5)`, and `next(8)`.

| Input | Action           | Window after the call | Running sum | Returned average |
| ----- | ---------------- | --------------------- | ----------- | ---------------- |
| `1`   | Add 1            | `[1]`                 | 1           | 1.0              |
| `10`  | Add 10           | `[1, 10]`             | 11          | 5.5              |
| `3`   | Add 3            | `[1, 10, 3]`          | 14          | 4.6667           |
| `5`   | Remove 1, add 5  | `[10, 3, 5]`          | 18          | 6.0              |
| `8`   | Remove 10, add 8 | `[3, 5, 8]`           | 16          | 5.3333           |

The important invariant is:

`sum` must always equal the sum of every value currently in `window`.

Every removal subtracts from `sum`, and every insertion adds to `sum`. As a result, we never need to recalculate the entire sum.

## 6. Edge cases to watch out for

1. Window size is 1. Each call should return the incoming value itself because the previous value is immediately removed.
2. Fewer values than the window size. Divide by the number of values received, not by `size`.
3. Negative values. Subtraction and addition must work correctly for negative numbers.
4. Repeated values. Every occurrence counts independently; duplicates must not be removed just because they are equal.
5. Fractional averages. Use `(double) sum / window.size()` rather than `sum / window.size()`.
6. Running sum overflow. A `long` is a safe, robust choice for the given constraints, even though an `int` would also be sufficient for this specific problem.

## 7. Interviewer follow-up questions and answers

Q1. Why use a running sum instead of recalculating the sum?

Because adjacent windows overlap in all but one outgoing and one incoming element. Updating the previous sum avoids traversing the entire window on every call.

Q2. Why use a queue?

A queue naturally models the order of the stream. The oldest value is at the front, and the newest value is at the back, so FIFO operations match the sliding-window requirements.

Q3. Why does the average initially use fewer than `size` values?

The problem asks for the average of the most recent values available. Until enough values arrive, the window cannot contain `size` elements.

Q4. Can we solve this without storing the window?

Not if we need to remove the outgoing value from the running sum and have no other way to recover it. We must remember the values that will eventually leave the window, or maintain equivalent information.

Q5. Is the queue solution truly \\(O(1)\\) per call?

Yes, amortized \\(O(1)\\) time. Queue insertion and removal at the ends are constant-time operations in the usual `ArrayDeque` implementation. The circular-array solution offers worst-case \\(O(1)\\) updates.

Q6. What if the window size changes dynamically?

The fixed-size circular buffer would need to be resized or rebuilt. A deque-based implementation can accommodate a changed window size more easily, although existing values must be trimmed or retained according to the desired semantics.

Q7. Can we use `int sum`?

Yes, under these constraints, the absolute sum of at most 100 values is at most \\(100 \times 1000 = 100{,}000\\), which fits in an `int`. Using `long` is still a good habit for running sums because it reduces overflow risk if the constraints change.

## 8. Complexity comparison

| Approach                     | `next()` time                   | Auxiliary space      | Recommendation                 |
| ---------------------------- | ------------------------------- | -------------------- | ------------------------------ |
| Queue + recomputed sum       | \\(O(\text{size})\\) worst case | \\(O(\text{size})\\) | Easiest baseline               |
| Queue + running sum          | \\(O(1)\\) amortized            | \\(O(\text{size})\\) | Best interview-friendly choice |
| Circular array + running sum | \\(O(1)\\) worst case           | \\(O(\text{size})\\) | Best for predictable updates   |

Final interview takeaway: Use the queue plus running sum unless the interviewer specifically asks for a fixed-size array implementation. The essential optimization is to subtract the outgoing value and add the incoming value rather than recomputing the sum.
