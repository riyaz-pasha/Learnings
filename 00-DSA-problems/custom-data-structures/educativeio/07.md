# Time-Based Key-Value Store — Java 24 Interview Solution

## 0. Understand the problem in simple terms

We need to design a data structure that stores multiple values for the same key, each associated with a timestamp.

The data structure supports two operations:

- `setValue(key, value, timestamp)` — save a value for a key at a particular timestamp.
- `getValue(key, timestamp)` — return the value associated with the latest timestamp that is less than or equal to the requested timestamp.

If no value exists at or before the requested timestamp, return `""`.

### Example

Suppose we store the following values:

```
setValue("name", "Alice", 1)
setValue("name", "Bob",   4)
setValue("name", "Carol", 7)
```

The values stored for `"name"` look like this:

```
Key: "name"

Timestamp:  1       4       7
            |       |       |
Value:    Alice    Bob    Carol
```

Now consider these queries:

| Query                    | Result    | Reason                                   |
| ------------------------ | --------- | ---------------------------------------- |
| `getValue("name", 1)`    | `"Alice"` | Exact timestamp exists                   |
| `getValue("name", 3)`    | `"Alice"` | Timestamp 1 is the latest timestamp ≤ 3  |
| `getValue("name", 5)`    | `"Bob"`   | Timestamp 4 is the latest timestamp ≤ 5  |
| `getValue("name", 7)`    | `"Carol"` | Exact timestamp exists                   |
| `getValue("name", 10)`   | `"Carol"` | Timestamp 7 is the latest timestamp ≤ 10 |
| `getValue("name", 0)`    | `""`      | No timestamp ≤ 0                         |
| `getValue("unknown", 5)` | `""`      | Key does not exist                       |

The most important detail: we are not looking for the closest timestamp in either direction. We must find the latest timestamp that is less than or equal to the query timestamp.

## 1. Clarifying questions to ask the interviewer

Even when constraints are provided, asking these questions shows that you understand the design requirements.

1. Are timestamps strictly increasing for each key or globally?

   Why: This determines whether values can be appended directly or whether they must be inserted in sorted order. The problem guarantees that all timestamps passed to `setValue` are strictly increasing, so appending is sufficient.
2. Should an exact timestamp match return its associated value?

   Why: This establishes whether the lookup condition is `timestamp <= queryTimestamp` or strictly `<`. Here, exact matches must be returned.
3. What should happen when the key does not exist or all its timestamps are too large?

   Why: We need a clearly defined missing-value behavior. The answer is an empty string.
4. Can timestamps arrive out of order?

   Why: Out-of-order writes would require sorted insertion or another indexing strategy. The given constraints guarantee increasing timestamps, so we do not need to handle that case.
5. What are the expected time complexities?

   Why: With up to 1,000 operations, a linear scan is possible, but binary search provides a more efficient lookup and demonstrates good algorithmic reasoning.

## 2. Core intuition — how to think about the optimal solution

The key observation is that each key can have multiple values, and the timestamps for those values are already sorted in increasing order.

This means we can combine:

- A `HashMap` to find a key's history quickly.
- An `ArrayList` to store that key's timestamp-value pairs in chronological order.
- Binary search to find the latest timestamp that does not exceed the requested timestamp.

### Recommended data structure

```
HashMap<String, List<TimeValue>>

"name" ──► [(1, "Alice"), (4, "Bob"), (7, "Carol")]
"city" ──► [(2, "Paris"), (6, "Tokyo")]
```

Each `TimeValue` record stores a timestamp and its corresponding value.

For example, `getValue("name", 5)` searches this history:

```
Index:       0          1          2
          ┌────────┬──────────┬──────────┐
Timestamp │   1    │    4     │    7     │
Value     │ Alice  │   Bob    │  Carol   │
          └────────┴──────────┴──────────┘
                                  ▲
                         Too late: 7 > 5

                    Latest valid timestamp
                              ▲
                           Bob (4)
```

The answer is `"Bob"` because timestamp `4` is the largest timestamp satisfying `4 <= 5`.

### Binary search mental model

We want to find the rightmost valid timestamp.

- If the middle timestamp is less than or equal to the query, save its index as a possible answer and search farther right.
- If the middle timestamp is greater than the query, search to the left.
- If no valid timestamp exists, return `""`.

This is a variation of binary search for the rightmost element less than or equal to a target.

## 3. Solutions from brute force to optimal

### Approach 1: HashMap of HashMaps — straightforward lookup

Store each key's timestamp-value pairs in a `TreeMap`. The `floorEntry()` method directly returns the entry with the greatest timestamp less than or equal to the requested timestamp.

```
import java.util.HashMap;
import java.util.Map;
import java.util.NavigableMap;
import java.util.TreeMap;

class TimeStampTreeMap {

    // WHY: A key can have many timestamp-value pairs.
    // The outer HashMap gives expected O(1) access to a key's history.
    // The inner TreeMap keeps timestamps sorted automatically.
    private final Map<String, NavigableMap<Integer, String>> values =
            new HashMap<>();

    public TimeStampTreeMap() {
        // The maps start empty; no explicit initialization is needed
        // for individual keys because computeIfAbsent creates their histories.
    }

    public void setValue(String key, String value, int timestamp) {
        // WHAT: Find or create this key's sorted timestamp map, then store
        // the value at the supplied timestamp.
        //
        // WHY: TreeMap maintains sorted timestamps, allowing floorEntry()
        // to locate the correct historical value without scanning all entries.
        //
        // Time: O(log m), where m is the number of timestamps for this key.
        // Space: O(1) additional space for this operation, excluding the
        // newly stored entry; total storage is O(N) across N writes.
        values.computeIfAbsent(key, ignored -> new TreeMap<>())
              .put(timestamp, value);
    }

    public String getValue(String key, int timestamp) {
        // WHY: If the key was never written, no historical value exists.
        NavigableMap<Integer, String> history = values.get(key);

        if (history == null) {
            return "";
        }

        // WHAT: floorEntry(t) returns the entry with the greatest timestamp
        // that is <= t. This also correctly handles exact timestamp matches.
        Map.Entry<Integer, String> entry = history.floorEntry(timestamp);

        // WHY: A null entry means every stored timestamp is greater than
        // the requested timestamp, so the required answer is an empty string.
        //
        // Time: O(log m) for TreeMap.floorEntry().
        // Space: O(1) additional space for the lookup.
        return entry == null ? "" : entry.getValue();
    }
}
```

Complexities

Let \\(m\\) be the number of timestamps associated with the queried key.

- `setValue`: \\(O(\log m)\\).
- `getValue`: \\(O(\log m)\\).
- Total storage: \\(O(N)\\), where \\(N\\) is the total number of stored timestamp-value pairs.

This solution is elegant because Java's `TreeMap` already implements the required ordered lookup. However, it does not fully exploit the problem's guarantee that timestamps arrive in strictly increasing order.

### Approach 2: HashMap + ArrayList + linear search

Because writes arrive in increasing timestamp order, we can append every new timestamp-value pair to a list. For queries, scan the list until timestamps become too large.

```
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

class TimeStampLinear {

    // Modern Java record: an immutable pair containing a timestamp and value.
    private record TimeValue(int timestamp, String value) {}

    // WHY: HashMap locates the history for a key efficiently, and ArrayList
    // stores that key's timestamp-value pairs in chronological order.
    private final Map<String, List<TimeValue>> values = new HashMap<>();

    public TimeStampLinear() {
        // The HashMap is already initialized and starts empty.
    }

    public void setValue(String key, String value, int timestamp) {
        // WHY: The problem guarantees strictly increasing write timestamps.
        // Therefore, the new pair always belongs at the end of the list.
        values.computeIfAbsent(key, ignored -> new ArrayList<>())
              .add(new TimeValue(timestamp, value));

        // Time: Amortized O(1) for HashMap access and ArrayList append.
        // Space: O(1) additional space per write; O(N) total storage.
    }

    public String getValue(String key, int timestamp) {
        List<TimeValue> history = values.get(key);

        // No history means no valid answer.
        if (history == null) {
            return "";
        }

        // Scan from oldest to newest.
        // Keep the last value whose timestamp is <= the requested timestamp.
        String answer = "";

        for (TimeValue entry : history) {
            // Since timestamps are sorted, this and all subsequent timestamps
            // are too large. We can stop immediately.
            if (entry.timestamp() > timestamp) {
                break;
            }

            answer = entry.value();
        }

        // Time: O(m) worst case, where m is this key's history size.
        // Space: O(1) additional space for the lookup.
        return answer;
    }
}
```

This solution is simple and correct, but a lookup might inspect every timestamp belonging to the key. We can improve it using binary search.

### Approach 3: Optimal interview solution — binary search

This is the recommended implementation. It preserves the simplicity of the list-based solution while reducing lookup time from linear to logarithmic.

```
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

class TimeStamp {

    // Each record represents one historical version of a key's value.
    //
    // WHY use a record?
    // Java 24 records provide a concise immutable data carrier with generated
    // accessors, such as timestamp() and value(), and clear value semantics.
    private record TimeValue(int timestamp, String value) {}

    // DATA STRUCTURE:
    //
    // key -> chronological history of timestamp-value pairs
    //
    // Example:
    // "name" -> [(1, "Alice"), (4, "Bob"), (7, "Carol")]
    //
    // WHY this structure?
    // 1. HashMap provides expected O(1) access to a key's history.
    // 2. ArrayList provides O(1) indexed access, which binary search needs.
    // 3. Increasing write timestamps mean each new pair can be appended
    //    without sorting or shifting existing elements.
    private final Map<String, List<TimeValue>> values = new HashMap<>();

    public TimeStamp() {
        // Initialize the empty dictionary.
        // Individual histories are created lazily when a key is first written.
    }

    public void setValue(String key, String value, int timestamp) {
        // STEP 1: Find this key's existing history, or create an empty list.
        //
        // STEP 2: Append the new timestamp-value pair.
        //
        // WHY can we append without sorting?
        // The problem guarantees that timestamps passed to setValue are
        // strictly increasing. Thus, each new timestamp is greater than
        // every timestamp already stored.
        values.computeIfAbsent(key, ignored -> new ArrayList<>())
              .add(new TimeValue(timestamp, value));

        // Time complexity: Expected O(1) amortized.
        // - HashMap lookup/insertion: expected O(1).
        // - ArrayList append: amortized O(1), with occasional O(m) resizing.
        // Overall, append is amortized O(1); a resizing operation may take O(m).
        //
        // Space complexity: O(1) amortized additional space per write,
        // excluding the new record and list growth; O(N) total stored history.
    }

    public String getValue(String key, int timestamp) {
        // STEP 1: Retrieve the history for this key.
        List<TimeValue> history = values.get(key);

        // EDGE CASE: An unknown key has no historical values.
        if (history == null) {
            return "";
        }

        // STEP 2: Set up binary search.
        //
        // We are NOT searching for an arbitrary timestamp match.
        // We need the RIGHTMOST index whose timestamp <= the query timestamp.
        //
        // low and high define the current inclusive search interval.
        int low = 0;
        int high = history.size() - 1;

        // -1 means we have not found any valid timestamp yet.
        // This is important when the requested timestamp is earlier than
        // the first stored timestamp.
        int answerIndex = -1;

        while (low <= high) {
            // WHY this midpoint formula?
            // It avoids the potential integer overflow of (low + high) / 2.
            int mid = low + (high - low) / 2;

            TimeValue current = history.get(mid);

            if (current.timestamp() <= timestamp) {
                // The current timestamp is valid, so record it as a candidate.
                //
                // But there may be a LATER valid timestamp to its right.
                // Move right to find the rightmost valid index.
                answerIndex = mid;
                low = mid + 1;
            } else {
                // The current timestamp is too large.
                //
                // Because the list is sorted, every timestamp to the right
                // is also too large. Search only the left half.
                high = mid - 1;
            }
        }

        // STEP 3: Convert the resulting index into the required value.
        //
        // If answerIndex is -1, every stored timestamp is greater than
        // the requested timestamp, so return the required empty string.
        //
        // Otherwise, answerIndex identifies the latest valid timestamp,
        // and its associated value is the answer.
        return answerIndex == -1
                ? ""
                : history.get(answerIndex).value();

        // Time complexity:
        // O(log m), where m is the number of timestamp-value pairs for this key.
        // Each iteration halves the search interval, and indexed ArrayList
        // access takes O(1). The initial HashMap lookup is expected O(1).
        //
        // Auxiliary space complexity: O(1).
        // Only low, high, mid, and answerIndex are needed; no extra collection
        // is allocated during the search.
    }
}
```

## 4. Dry run of the optimal solution

Assume we execute:

```
TimeStamp store = new TimeStamp();

store.setValue("name", "Alice", 1);
store.setValue("name", "Bob", 4);
store.setValue("name", "Carol", 7);

System.out.println(store.getValue("name", 5));
```

The history is:

```
Index:       0           1           2
          ┌─────────┬───────────┬───────────┐
Timestamp │    1    │     4     │     7     │
Value     │  Alice  │   Bob     │  Carol    │
          └─────────┴───────────┴───────────┘

Query timestamp = 5
```

The binary search proceeds as follows.

| Step | `low` | `high` | `mid` | Timestamp | Decision                             |
| ---- | ----- | ------ | ----- | --------- | ------------------------------------ |
| 1    | 0     | 2      | 1     | 4         | Valid; save index 1 and search right |
| 2    | 2     | 2      | 2     | 7         | Too large; search left               |
| 3    | 2     | 1      | —     | —         | Search ends                          |

The final `answerIndex` is `1`, so the result is `"Bob"`.

Notice that binary search does not need to examine timestamp `1` at all. It finds the correct answer by repeatedly eliminating half of the remaining search interval.

## 5. Edge cases to watch out for

| Scenario                     | Example                        | Expected result     |
| ---------------------------- | ------------------------------ | ------------------- |
| Unknown key                  | `getValue("x", 5)`             | `""`                |
| Query before first timestamp | Stored at 3; query at 2        | `""`                |
| Exact timestamp              | Stored at 3; query at 3        | Stored value        |
| Between two timestamps       | Stored at 3 and 8; query at 5  | Value at 3          |
| Query after last timestamp   | Stored at 3 and 8; query at 10 | Value at 8          |
| Only one stored value        | Stored at 5; query at 5        | Stored value        |
| Several different keys       | Each key has its own history   | Never mix histories |

One particularly important bug to avoid is returning the value at the first timestamp greater than the query. The required answer always comes from a timestamp that is less than or equal to the query.

## 6. Complexity comparison

Let \\(N\\) denote the total number of stored entries and \\(m\\) the number of entries for a particular key.

| Approach                       | `setValue`           | `getValue`      | Total space |
| ------------------------------ | -------------------- | --------------- | ----------- |
| HashMap + TreeMap              | \\(O(\log m)\\)      | \\(O(\log m)\\) | \\(O(N)\\)  |
| HashMap + list + linear scan   | Amortized \\(O(1)\\) | \\(O(m)\\)      | \\(O(N)\\)  |
| HashMap + list + binary search | Amortized \\(O(1)\\) | \\(O(\log m)\\) | \\(O(N)\\)  |

Why the binary-search solution is optimal for these constraints: writes are already ordered, so list insertion is efficient, and binary search efficiently finds the rightmost valid timestamp. It avoids the extra per-entry tree structure needed by `TreeMap`.

## 7. Interviewer follow-up questions and answers

Q1. Why use a `HashMap` instead of one global list?

A: Each key has an independent history. The `HashMap` lets us locate the correct history in expected \\(O(1)\\) time instead of searching entries belonging to unrelated keys.

Q2. Why is binary search correct?

A: The timestamps are sorted. When a midpoint timestamp is valid, it becomes a candidate and we search to the right for a later valid timestamp. When it is too large, all timestamps to its right are also too large, so we discard that half. The saved index is therefore the rightmost valid timestamp.

Q3. What if timestamps are no longer guaranteed to arrive in increasing order?

A: Appending would no longer preserve sorted order. We would need to insert into the list at the appropriate position, which costs \\(O(m)\\) per insertion in an `ArrayList`, or use a `TreeMap` for \\(O(\log m)\\) insertion and lookup.

Q4. Can we use `Collections.binarySearch()` instead of implementing binary search?

A: Yes, with a comparator or a search over timestamps. However, implementing the search directly makes it easier to express the precise requirement: finding the rightmost timestamp less than or equal to the target. A normal exact-match binary search does not directly provide that result.

Q5. What if timestamps are strictly increasing globally, not merely per key?

A: The same implementation remains correct. Global increasing order implies increasing order within each key's history as well, so every write can still be appended.

Q6. What if there are millions of writes and most queries ask for very recent timestamps?

A: The current approach remains a strong default with \\(O(\log m)\\) lookup. Further optimizations would depend on the query distribution, memory constraints, and whether we can safely exploit temporal locality or cache recent results.

Q7. What if we need thread-safe concurrent writes and reads?

A: The current implementation is not thread-safe. We could synchronize access or use suitable concurrent data structures and per-key synchronization, taking care that readers never observe partially updated histories.

## Final interview recommendation

Use Approach 3: `HashMap<String, List<TimeValue>>` with binary search.

It is concise, easy to explain, exploits the increasing-timestamp guarantee, and achieves amortized \\(O(1)\\) writes, \\(O(\log m)\\) reads, and \\(O(N)\\) storage.
