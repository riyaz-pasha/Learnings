# Range Module — Interview-Ready Java 24 Solution

## 0. Understand the problem in simple terms

We need to build a data structure that remembers which parts of a number line are currently being tracked.

It supports three operations:

- `addRange(left, right)`: Start tracking every number in the interval \\([left,right)\\).
- `queryRange(left, right)`: Return `true` only if every number in the requested interval is tracked.
- `removeRange(left, right)`: Stop tracking every number in the interval \\([left,right)\\).

The important detail is that intervals are half-open: the left endpoint is included, but the right endpoint is excluded.

For example, \\([10,20)\\) includes 10 but excludes 20.

### A complete example

| Operation             | Tracked ranges afterward | Result  |
| --------------------- | ------------------------ | ------- |
| `addRange(10, 20)`    | `[10, 20)`               | —       |
| `addRange(15, 25)`    | `[10, 25)`               | —       |
| `queryRange(12, 24)`  | `[10, 25)`               | `true`  |
| `queryRange(12, 26)`  | `[10, 25)`               | `false` |
| `removeRange(14, 18)` | `[10, 14)`, `[18, 25)`   | —       |
| `queryRange(12, 20)`  | `[10, 14)`, `[18, 25)`   | `false` |

The key observation is that we should maintain the union of tracked intervals, rather than storing every operation independently.

## 1. Clarifying questions to ask the interviewer

These questions establish the assumptions that influence the data structure.

1. Can interval endpoints be integers while the ranges represent real numbers? Why: The statement refers to real numbers, so we should not assume that checking integer points is sufficient. We need interval-based logic.
2. Can overlapping or adjacent intervals be merged? Why: Merging simplifies queries and removals. Under half-open semantics, adjacent intervals can safely be represented by one interval.
3. Can `addRange` and `removeRange` receive intervals that are not currently tracked? Why: They should generally work even when the requested interval partially overlaps or does not overlap any tracked range.
4. Can we assume `left < right` for every call? Why: Empty or reversed intervals would need explicitly defined behavior. The stated constraints guarantee valid, nonempty intervals.
5. What performance target is expected? Why: With at most \\(10^3\\) operations, a straightforward solution may be acceptable. However, the problem is a good opportunity to discuss binary search, balanced trees, and lazy segment trees.

We will use the stated constraints and assume valid half-open intervals, with no need to preserve the original history of operations.

## 2. Core intuition: think of tracked ranges as merged segments

Imagine a number line covered by several non-overlapping segments.

Instead of remembering every `addRange` call, keep only the segments that describe the currently tracked set.

For example:

```
Before adding [14, 23):

Tracked:  [2, 8)   [12, 18)   [25, 30)

Add:                 [14, 23)

After merging:

Tracked:  [2, 8)   [12, 23)   [25, 30)
```

The new interval overlaps `[12, 18)`, so those intervals become `[12, 23)`.

Now suppose we remove `[15, 27)`:

```
Before:

[2, 8)   [12, 23)   [25, 30)

Remove:

          [15, 27)

After:

[2, 8)   [12, 15)   [27, 30)
```

The removal can do three things to an existing interval:

- Leave it unchanged if there is no overlap.
- Trim one side if the removal overlaps one endpoint.
- Split it into two intervals if the removal lies inside it.

That last case is especially important: removing the middle of a tracked interval can create two separate intervals.

### The invariant

Our main solution will maintain this invariant:

> All tracked intervals are sorted by their left endpoint and are pairwise disjoint. Adjacent intervals are merged as well.

This invariant makes the three operations easier to implement correctly.

## 3. Edge cases to watch out for

Before coding, mentally test these cases:

| Case                          | Example                                   | Expected behavior   |
| ----------------------------- | ----------------------------------------- | ------------------- |
| Empty module                  | `queryRange(1, 5)`                        | `false`             |
| Exact match                   | Track `[1, 5)`, query `[1, 5)`            | `true`              |
| Query extends beyond coverage | Track `[1, 5)`, query `[1, 6)`            | `false`             |
| Adjacent intervals            | Track `[1, 3)`, add `[3, 5)`              | Merge into `[1, 5)` |
| Overlapping addition          | Track `[1, 5)`, add `[3, 8)`              | Merge into `[1, 8)` |
| Removal with no overlap       | Track `[1, 5)`, remove `[8, 10)`          | No change           |
| Remove from the beginning     | Track `[1, 10)`, remove `[1, 4)`          | `[4, 10)`           |
| Remove from the end           | Track `[1, 10)`, remove `[7, 10)`         | `[1, 7)`            |
| Remove the middle             | Track `[1, 10)`, remove `[4, 6)`          | `[1, 4)`, `[6, 10)` |
| Remove everything             | Track `[1, 10)`, remove `[1, 10)`         | Empty               |
| Add a contained interval      | Track `[1, 10)`, add `[3, 6)`             | No change           |
| Query across a gap            | Track `[1, 4)`, `[6, 10)`, query `[2, 8)` | `false`             |

The most common bugs are failing to merge adjacent intervals, treating `right` as inclusive, and forgetting that removing a middle section creates two intervals.

## 4. Solution 1 — Brute force using a set of integer points

This approach is useful as a baseline, but it is not a correct general solution for the stated real-number problem.

The following implementation is valid only if the problem is changed to tracking integer points within a bounded domain. It cannot represent arbitrary real-valued ranges, so we should not submit it for the original specification.

```
import java.util.HashSet;
import java.util.Set;

class RangeModuleBruteForce {
    // This baseline assumes integer points in the interval [0, 10_000].
    // It is not a valid representation of arbitrary real-number intervals.

    private final Set<Integer> tracked = new HashSet<>();

    public void addRange(int left, int right) {
        // Track every integer x satisfying left <= x < right.
        // Time: O(right - left) expected.
        // Space: O(number of distinct tracked integer points).
        for (int x = left; x < right; x++) {
            tracked.add(x);
        }
    }

    public boolean queryRange(int left, int right) {
        // Every integer point must be tracked.
        // This checks integer coverage only, not real-number coverage.
        // Time: O(right - left) expected.
        // Auxiliary space: O(1).
        for (int x = left; x < right; x++) {
            if (!tracked.contains(x)) {
                return false;
            }
        }

        return true;
    }

    public void removeRange(int left, int right) {
        // Remove every integer point in the half-open interval.
        // Time: O(right - left) expected.
        // Auxiliary space: O(1).
        for (int x = left; x < right; x++) {
            tracked.remove(x);
        }
    }
}
```

Why reject it in an interview? Because checking integer points cannot prove that every real number in an interval is covered. We need to represent intervals themselves.

## 5. Solution 2 — Sorted list of merged intervals

A more appropriate solution stores intervals directly in a sorted list. Each interval is represented as a pair `(start, end)`.

- `addRange`: scan the intervals, merge every interval that overlaps or touches the new interval, and insert the merged result in sorted order.
- `queryRange`: find an interval that starts at or before `left` and check whether it reaches at least `right`.
- `removeRange`: scan all intervals, preserving non-overlapping intervals and splitting partially overlapping ones as necessary.

This solution is straightforward and can be a good choice for small input sizes.

```
import java.util.ArrayList;
import java.util.List;

class RangeModuleList {
    // Each pair [start, end) represents a tracked interval.
    // The list is always sorted, disjoint, and coalesced:
    // consecutive intervals have a genuine gap between them.
    private record Interval(int start, int end) {}

    private final List<Interval> ranges = new ArrayList<>();

    public void addRange(int left, int right) {
        // Rebuild the list in sorted order while merging the new interval.
        // We merge adjacency too: [a,b) and [b,c) form [a,c).
        // Time: O(n), because the current intervals are scanned and copied.
        // Auxiliary space: O(n) for the replacement list.
        var merged = new ArrayList<Interval>();
        int start = left;
        int end = right;
        boolean inserted = false;

        for (var interval : ranges) {
            // Strictly before the new interval: no overlap or adjacency.
            if (interval.end() < start) {
                merged.add(interval);
            } else if (end < interval.start()) {
                // The new interval is strictly before this interval.
                // Insert it once, then preserve the remaining sorted intervals.
                if (!inserted) {
                    merged.add(new Interval(start, end));
                    inserted = true;
                }
                merged.add(interval);
            } else {
                // Overlap or adjacency: expand the pending interval.
                start = Math.min(start, interval.start());
                end = Math.max(end, interval.end());
            }
        }

        if (!inserted) {
            merged.add(new Interval(start, end));
        }

        ranges.clear();
        ranges.addAll(merged);
    }

    public boolean queryRange(int left, int right) {
        // Only one merged interval can cover the whole query.
        // If a gap exists, the merged representation keeps it visible.
        // Time: O(n) worst case; auxiliary space: O(1).
        for (var interval : ranges) {
            if (interval.start() <= left && right <= interval.end()) {
                return true;
            }

            if (interval.start() > left) {
                // No later interval can start early enough to cover left.
                return false;
            }
        }

        return false;
    }

    public void removeRange(int left, int right) {
        // Preserve disjoint intervals; trim or split intersecting intervals.
        // For half-open intervals, [a,b) and [left,right) overlap exactly
        // when a < right && left < b.
        // Time: O(n); auxiliary space: O(n).
        var remaining = new ArrayList<Interval>();

        for (var interval : ranges) {
            int start = interval.start();
            int end = interval.end();

            if (end <= left || start >= right) {
                // No overlap: keep the interval unchanged.
                remaining.add(interval);
                continue;
            }

            if (start < left) {
                // The portion before the removed interval remains tracked.
                remaining.add(new Interval(start, left));
            }

            if (end > right) {
                // The portion after the removed interval remains tracked.
                remaining.add(new Interval(right, end));
            }
        }

        ranges.clear();
        ranges.addAll(remaining);
    }
}
```

One subtlety: because the list is already sorted and disjoint, a query only needs to find the interval covering `left`. If that interval ends before `right`, the query fails.

## 6. Solution 3 — Optimal practical approach using `TreeMap`

This is the solution I would recommend presenting in an interview.

### Mental model

Use a `TreeMap<Integer, Integer>` where:

- The key is the start of an interval.
- The value is its exclusive end.
- Intervals are stored in sorted order.
- Intervals are always disjoint and non-adjacent.

For example:

```
TreeMap:
1  -> 5
8  -> 12
20 -> 25

Represents:

[1, 5)    [8, 12)    [20, 25)
```

Why use a `TreeMap`?

- `floorEntry(left)` finds the interval whose start is the greatest start not exceeding `left`.
- `ceilingEntry(start)` finds the next interval starting at or after `start`.
- Insertions, lookups, and removals by key take \\(O(\log n)\\) time, where \\(n\\) is the number of stored intervals.

The core reasoning for each operation is:

Add: Find the first interval that may overlap or touch the new range. Expand the new range to include each overlapping or adjacent interval, remove those old entries, and insert the merged interval.

Query: Find the interval with the greatest start not exceeding `left`. The query succeeds exactly when that interval's end is at least `right`.

Remove: Find all intervals intersecting the removal range. Preserve any surviving left and right pieces, delete the affected intervals, and insert the surviving pieces.

### Java 24 implementation

```
import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.TreeMap;

class RangeModule {
    // The map represents the union of tracked half-open intervals.
    //
    // Invariant:
    // 1. Every entry (start -> end) represents [start, end).
    // 2. Starts are sorted automatically by TreeMap.
    // 3. Intervals never overlap or touch: previousEnd < nextStart.
    //
    // Why this representation?
    // We need interval-level operations, not individual-point tracking.
    // A TreeMap supports efficient predecessor/successor searches.
    private final TreeMap<Integer, Integer> ranges = new TreeMap<>();

    public RangeModule() {
        // An empty map means that no points are tracked.
        // Time: O(1); auxiliary space: O(1).
    }

    public void addRange(int left, int right) {
        // Goal: add [left, right), merging every interval that overlaps
        // or touches it, while preserving all existing tracked points.
        //
        // Step 1: Check the predecessor interval.
        // floorEntry(left) gives the interval with the greatest start <= left.
        // If its end >= left, it overlaps or touches the new interval.
        //
        // Step 2: Repeatedly inspect the next interval beginning at or
        // before the expanding right endpoint. Merge it if its start <= right.
        //
        // Step 3: Delete the old intervals being merged and insert one
        // consolidated interval.
        //
        // Let n be the number of stored intervals and k the number merged.
        // Time: O((k + 1) log n) using TreeMap searches/removals/insertion.
        // Auxiliary space: O(1), excluding temporary collection storage;
        // the list below uses O(k) space to remember removed keys.
        int start = left;
        int end = right;

        var toRemove = new ArrayList<Integer>();

        Map.Entry<Integer, Integer> entry = ranges.floorEntry(start);

        if (entry != null && entry.getValue() >= start) {
            // The predecessor overlaps or is adjacent.
            // Expand both boundaries to preserve its entire tracked range.
            start = entry.getKey();
            end = Math.max(end, entry.getValue());
            toRemove.add(entry.getKey());
        }

        // Examine successors while they start no later than the current end.
        // The end can expand after each merge, so re-evaluate the condition.
        entry = ranges.ceilingEntry(start);

        while (entry != null && entry.getKey() <= end) {
            // This interval overlaps or touches [start, end).
            end = Math.max(end, entry.getValue());
            toRemove.add(entry.getKey());

            // Move to the next successor without mutating the map mid-iteration.
            entry = ranges.higherEntry(entry.getKey());
        }

        // Delete only after traversal to keep successor navigation simple.
        for (int key : toRemove) {
            ranges.remove(key);
        }

        // The new interval now represents the union of all merged intervals.
        ranges.put(start, end);
    }

    public boolean queryRange(int left, int right) {
        // Goal: determine whether every point in [left, right) is tracked.
        //
        // Because stored intervals are disjoint and sorted, only the interval
        // with the greatest start <= left can possibly cover the entire query.
        // If there is no predecessor, left is not tracked.
        // If its end < right, the query extends beyond its coverage.
        //
        // Time: O(log n) for floorEntry.
        // Auxiliary space: O(1).
        Map.Entry<Integer, Integer> entry = ranges.floorEntry(left);

        return entry != null && entry.getValue() >= right;
    }

    public void removeRange(int left, int right) {
        // Goal: remove every point in [left, right), preserving everything else.
        //
        // An existing interval [start, end) intersects the removal range
        // exactly when start < right && left < end.
        //
        // The affected interval can leave:
        // - no piece, if completely removed;
        // - [start, left), if its left portion survives;
        // - [right, end), if its right portion survives;
        // - both pieces, if the removal splits an interval.
        //
        // We first collect affected keys and surviving pieces, then mutate
        // the map. This avoids modifying TreeMap during successor traversal.
        //
        // Let k be the number of affected intervals.
        // Time: O((k + 1) log n), including searches, removals, and insertions.
        // Auxiliary space: O(k) for affected keys and surviving pieces.
        var keysToRemove = new ArrayList<Integer>();
        var piecesToKeep = new ArrayList<Interval>();

        // Start from the predecessor that might extend into [left, right).
        Map.Entry<Integer, Integer> entry = ranges.floorEntry(left);

        if (entry == null || entry.getValue() <= left) {
            // No predecessor overlaps the removal range.
            entry = ranges.ceilingEntry(left);
        }

        while (entry != null && entry.getKey() < right) {
            int start = entry.getKey();
            int end = entry.getValue();

            if (end > left) {
                // There is a genuine intersection.
                keysToRemove.add(start);

                if (start < left) {
                    // Preserve the portion strictly before the removal.
                    piecesToKeep.add(new Interval(start, left));
                }

                if (end > right) {
                    // Preserve the portion strictly after the removal.
                    piecesToKeep.add(new Interval(right, end));
                }
            }

            // Find the next interval before performing any deletion.
            entry = ranges.higherEntry(start);
        }

        // Remove every affected interval.
        for (int key : keysToRemove) {
            ranges.remove(key);
        }

        // Restore any surviving pieces.
        for (Interval interval : piecesToKeep) {
            ranges.put(interval.start(), interval.end());
        }
    }

    // Java record: immutable pair representing a half-open interval.
    private record Interval(int start, int end) {}
}
```

### Why this implementation is correct

The proof follows from the invariant.

- Addition: Every interval that overlaps or touches the new interval is absorbed into the merged boundaries. All other intervals remain unchanged, so the tracked union is preserved and the invariant still holds.
- Query: Because intervals are disjoint, at most one interval can contain `left`. If its exclusive end is at least `right`, it covers the whole requested range. Otherwise, the query is not fully tracked.
- Removal: Every intersecting interval is deleted. Its portions outside the removal range are restored, so exactly the requested points stop being tracked.

### Complexity summary

Let \\(n\\) be the number of stored intervals and \\(k\\) be the number affected by an update.

| Operation     | Time                 | Extra space |
| ------------- | -------------------- | ----------- |
| Constructor   | \\(O(1)\\)           | \\(O(1)\\)  |
| `addRange`    | \\(O((k+1)\log n)\\) | \\(O(k)\\)  |
| `queryRange`  | \\(O(\log n)\\)      | \\(O(1)\\)  |
| `removeRange` | \\(O((k+1)\log n)\\) | \\(O(k)\\)  |

The worst case for an update is \\(O(n\log n)\\), when nearly all stored intervals are affected. The number of intervals is at most proportional to the number of operations, since every operation can introduce only a constant number of new interval boundaries.

## 7. Solution 4 — Dynamic segment tree (advanced alternative)

A dynamic segment tree is useful when the coordinate domain is huge, updates and queries are frequent, and we want logarithmic operation times without storing every interval explicitly.

The following implementation assumes integer endpoints and an integer coordinate domain from `1` through `10_000`, matching the common bounded-domain version of this problem. It tracks coverage of elementary segments between consecutive integer coordinates, which represents the original real-number intervals with integer endpoints.

```
class RangeModuleSegmentTree {
    // Each node represents a segment of the coordinate domain.
    // covered = true means the entire segment is tracked.
    // mixed = true means coverage differs within this segment.
    // Children are allocated lazily to avoid building the entire tree.
    private static final class Node {
        boolean covered;
        boolean mixed;
        Node left;
        Node right;
    }

    private static final int MIN = 1;
    private static final int MAX = 10_000;

    private final Node root = new Node();

    public void addRange(int left, int right) {
        // Convert [left, right) into the elementary segment-index range
        // [left, right - 1] for this bounded integer-coordinate tree.
        // Time: O(log C) when using lazy propagation and uniform states.
        // Space: O(log C) new nodes per update in the usual sparse case,
        // but previously created nodes remain allocated.
        if (left < right) {
            update(root, MIN, MAX, left, right - 1, true);
        }
    }

    public void removeRange(int left, int right) {
        // Mark the covered elementary segments as uncovered.
        // Time: O(log C) for a range update with lazy propagation.
        if (left < right) {
            update(root, MIN, MAX, left, right - 1, false);
        }
    }

    public boolean queryRange(int left, int right) {
        // Every elementary segment corresponding to [left, right)
        // must be fully covered.
        // Time: O(log C) for a range query.
        return left < right
                && query(root, MIN, MAX, left, right - 1);
    }

    private void update(
            Node node,
            int lo,
            int hi,
            int ql,
            int qr,
            boolean value) {

        // No intersection: leave this subtree unchanged.
        if (qr < lo || hi < ql) {
            return;
        }

        // Full containment: the whole node becomes uniformly covered
        // or uniformly uncovered, so its children are no longer needed
        // to answer queries under this node.
        if (ql <= lo && hi <= qr) {
            node.covered = value;
            node.mixed = false;
            node.left = null;
            node.right = null;
            return;
        }

        // A partial update requires examining the children.
        int mid = lo + (hi - lo) / 2;

        // Expand a previously uniform node into two children.
        // Its previous state must be copied to both children first.
        if (!node.mixed) {
            node.left = new Node();
            node.right = new Node();

            node.left.covered = node.covered;
            node.right.covered = node.covered;
            node.mixed = true;
        }

        if (ql <= mid) {
            update(node.left, lo, mid, ql, qr, value);
        }

        if (qr > mid) {
            update(node.right, mid + 1, hi, ql, qr, value);
        }

        // Recompute whether the parent is uniformly covered.
        // If both children are covered, the parent can collapse.
        if (!node.left.mixed && node.left.covered
                && !node.right.mixed && node.right.covered) {
            node.covered = true;
            node.mixed = false;
            node.left = null;
            node.right = null;
        } else if (!node.left.mixed && !node.left.covered
                && !node.right.mixed && !node.right.covered) {
            node.covered = false;
            node.mixed = false;
            node.left = null;
            node.right = null;
        }
    }

    private boolean query(
            Node node,
            int lo,
            int hi,
            int ql,
            int qr) {

        if (qr < lo || hi < ql) {
            // No part of the query lies in this node.
            return true;
        }

        if (!node.mixed) {
            // Uniform coverage lets us answer without descending.
            return node.covered;
        }

        int mid = lo + (hi - lo) / 2;

        boolean leftCovered = ql > mid
                || query(node.left, lo, mid, ql, qr);

        boolean rightCovered = qr <= mid
                || query(node.right, mid + 1, hi, ql, qr);

        return leftCovered && rightCovered;
    }
}
```

The segment tree has \\(O(\log C)\\) recursion depth, where \\(C\\) is the coordinate-domain size. Its sparse representation can use substantially less memory than a fully allocated tree, but its total node count can grow with the number and shape of updates.

For this particular problem, I would choose the `TreeMap` solution: it models real-number intervals directly, is easier to explain, and has no artificial coordinate-domain restriction.

## 8. Interviewer follow-up questions and answers

Q1. Why use half-open intervals instead of closed intervals?

Half-open intervals compose cleanly. For example, `[1, 5)` and `[5, 8)` meet without overlapping, and their union is `[1, 8)`. This avoids special handling for adjacent endpoints.

Q2. Why does a query need only one `floorEntry` lookup?

Because the map maintains sorted, disjoint intervals. If an interval begins before or at `left`, it is the only possible interval that can cover `left`. If it ends before `right`, there is a gap or insufficient coverage; no other interval can bridge that gap because adjacent intervals have already been merged.

Q3. Why merge adjacent intervals during addition?

It preserves the invariant and reduces the number of entries. Although adjacency does not mean the original half-open intervals overlap, their union is one continuous half-open interval.

Q4. What if the coordinate domain is extremely large?

The `TreeMap` approach does not require allocating a structure proportional to the coordinate domain. A dynamic segment tree is another option when the coordinate domain is bounded or can be mapped to a suitable index range.

Q5. Can the update operations be made \\(O(\log n)\\) in the worst case?

Not necessarily with a `TreeMap` representation of merged intervals. A single update may merge or remove \\(O(n)\\) intervals, so those entries must be processed. The total cost is output-sensitive: it depends on how many intervals the operation affects.

Q6. What is the most important invariant to communicate?

All tracked intervals are sorted, disjoint, and non-adjacent. Once that invariant is established, queries reduce to a predecessor lookup, while updates only need to process intervals that intersect or touch the update range.

## Final recommendation

For a senior Java interview, start with the interval-list approach to establish correctness, then optimize to the `TreeMap` approach. Explain the half-open boundary rules, prove the merged-interval invariant, and explicitly test removal that splits an interval into two pieces. Those are the most important parts of this problem.

# Range Module — Let's build the intuition from scratch

The confusing part of this problem is usually not Java or `TreeMap`. It's understanding how three operations can be performed using one simple representation of intervals.

Let's forget the code for a moment and build the solution as if we were designing the data structure on a whiteboard in an interview.

## 1. First, imagine that you own a number line

Suppose you have a number line, and you want to mark some parts of it as tracked.

Initially, nothing is tracked.

Initially

Nothing is tracked.

Now someone calls:

```
addRange(10, 20);
```

This means: track every number from 10 up to, but not including, 20.

After `addRange(10, 20)`

- 10 is included.
- 15 is included.
- 19.999 is included.
- 20 is excluded.

That is what `[10, 20)` means. We use a half-open interval because the left boundary is included and the right boundary is excluded.

The data structure does not need to store all the individual numbers. It can simply remember:

```
10 -> 20
```

This means the interval `[10, 20)` is tracked.

That is our first big idea: store ranges, not individual numbers.

## 2. Why store merged intervals?

Let's add another range:

```
addRange(15, 25);
```

Before the operation, we have:

```
Tracked:  [10, 20)

New:          [15, 25)
```

The new range overlaps the existing one.

Before merging

After merging

We only need to store `[10, 25)`.

Why?

Because the two intervals together cover exactly the same numbers as one interval, `[10, 25)`.

We do not need to remember that one call added `[10, 20)` and another added `[15, 25)`. The data structure cares only about what is currently tracked.

Now consider a slightly different example:

```
Tracked: [10, 15) and [20, 25)
New:     [14, 21)
```

The new interval connects both existing intervals.

```
Before:

[10, 15)   [20, 25)
         [14, 21)

After:

[10,                 25)
```

All three become one continuous range.

### The invariant we want

At all times, store intervals so that:

1. They are sorted by their starting points.
2. They never overlap.
3. They never touch without being merged.

For example, this is a valid representation:

```
[2, 8)    [12, 18)    [25, 30)
```

This is not the representation we want:

```
[2, 8)    [5, 10)    [10, 15)
```

We would merge those three into:

```
[2, 15)
```

Once we maintain this invariant, `queryRange` and `removeRange` become much easier to reason about.

## 3. Understand the three operations separately

Now let's reason about each operation without looking at Java code.

### A. `addRange(left, right)` — join ranges when necessary

Suppose our tracked intervals are:

```
[2, 8)     [12, 18)     [25, 30)
```

We call:

```
addRange(14, 27);
```

Step 1: Start with the new interval.

```
New interval: [14, 27)
```

Step 2: Compare it with `[2, 8)`.

There is a gap between 8 and 14. This interval is unaffected.

Step 3: Compare it with `[12, 18)`.

They overlap. The combined interval now starts at the smaller start and ends at the larger end:

```
start = min(14, 12) = 12
end   = max(27, 18) = 27

Combined: [12, 27)
```

Step 4: Compare the expanded interval with `[25, 30)`.

It overlaps again, so expand it:

```
start = min(12, 25) = 12
end   = max(27, 30) = 30

Combined: [12, 30)
```

The final result is:

```
Before: [2, 8)    [12, 18)    [25, 30)
Add:                  [14, 27)

After:  [2, 8)    [12, 30)
```

The important point: the interval may grow as we merge, so we must keep checking the next interval against the newly expanded end.

### B. `queryRange(left, right)` — find one interval that covers the whole query

Suppose we have:

```
[2, 8)     [12, 18)     [25, 30)
```

Consider these queries:

```
queryRange(13, 17);  // true
queryRange(13, 19);  // false
queryRange(8, 12);   // false
```

Why?

- `[13, 17)` is completely inside `[12, 18)`.
- `[13, 19)` extends past 18, so not all its points are tracked.
- `[8, 12)` lies in a gap. Neither endpoint is enough to establish coverage.

Here's the trick: because our intervals are sorted and merged, a query can only succeed if the interval containing `left` also reaches `right`.

For a query `[13, 17)`:

```
Tracked:       [12, ---------------- 18)
Query:              [13, ------ 17)

Result: true
```

For a query `[13, 19)`:

```
Tracked:       [12, ---------------- 18)
Query:              [13, ----------- 19)

Result: false
```

In mathematical terms, if the covering interval is `[start, end)`, the condition is:

```
start <= left && right <= end
```

Since `TreeMap` can locate the interval with the greatest start that is less than or equal to `left`, we do not have to scan every interval.

### C. `removeRange(left, right)` — remove only the requested portion

This is usually the trickiest operation.

Suppose we have:

```
Tracked: [10, 30)
```

And we call:

```
removeRange(16, 22);
```

We must stop tracking `[16, 22)`, but everything outside that range must remain tracked.

So the original interval is split into two pieces:

```
Original:  [10, -------------------------- 30)
Remove:              [16, ---- 22)
                         ↓

Remaining: [10, 16)     [22, 30)
```

We can derive the two remaining intervals directly:

- If `start < left`, keep `[start, left)`.
- If `end > right`, keep `[right, end)`.

Apply that reasoning to different cases:

| Original interval | Remove     | Remaining              |
| ----------------- | ---------- | ---------------------- |
| `[10, 30)`        | `[16, 22)` | `[10, 16)`, `[22, 30)` |
| `[10, 30)`        | `[5, 15)`  | `[15, 30)`             |
| `[10, 30)`        | `[25, 40)` | `[10, 25)`             |
| `[10, 30)`        | `[10, 30)` | Nothing                |
| `[10, 30)`        | `[35, 40)` | `[10, 30)`             |

The last case is particularly simple: if there is no overlap, do nothing.

The rule for two half-open intervals `[start, end)` and `[left, right)` to overlap is:

```
start < right && left < end
```

Why strict `<` instead of `<=`? Because `[10, 15)` and `[15, 20)` do not overlap. The first interval excludes 15.

## 4. Now understand `TreeMap` — the tool that makes the solution efficient

We'll represent each interval using a map entry:

```
TreeMap<Integer, Integer> ranges = new TreeMap<>();
```

The key is the interval's start; the value is its exclusive end.

For example:

```
ranges.put(2, 8);
ranges.put(12, 18);
ranges.put(25, 30);
```

Conceptually, the map represents:

```
Start -> End

  2    ->  8       [2, 8)
 12    -> 18       [12, 18)
 25    -> 30       [25, 30)
```

We use three `TreeMap` methods.

| Method            | Meaning                            | Example                               |
| ----------------- | ---------------------------------- | ------------------------------------- |
| `floorEntry(x)`   | Entry with the greatest key `<= x` | `floorEntry(15)` returns `12 -> 18`   |
| `ceilingEntry(x)` | Entry with the smallest key `>= x` | `ceilingEntry(15)` returns `25 -> 30` |
| `higherEntry(x)`  | Entry with the smallest key `> x`  | `higherEntry(12)` returns `25 -> 30`  |

These are the building blocks of the solution.

Think of them this way:

- `floorEntry` looks backward.
- `ceilingEntry` looks forward, including an exact match.
- `higherEntry` moves strictly forward to the next interval.

A `TreeMap` is backed by a balanced search tree, so each of these searches takes \\(O(\log n)\\) time, where \\(n\\) is the number of stored intervals.

## 5. The complete Java solution, with detailed comments

Read the comments as if you were explaining your reasoning aloud to the interviewer.

```
import java.util.ArrayList;
import java.util.Map;
import java.util.TreeMap;

class RangeModule {

    /*
     * OUR REPRESENTATION
     *
     * Each TreeMap entry represents one tracked interval:
     *
     *     key   = interval's inclusive start
     *     value = interval's exclusive end
     *
     * Example:
     *
     *     ranges.put(2, 8);
     *     ranges.put(12, 18);
     *     ranges.put(25, 30);
     *
     * Represents:
     *
     *     [2, 8)    [12, 18)    [25, 30)
     *
     * IMPORTANT INVARIANT:
     *
     * Intervals are sorted, non-overlapping, and non-adjacent.
     *
     * For example, we never store both [2, 8) and [8, 12).
     * Those intervals would be merged into [2, 12).
     *
     * Why maintain this invariant?
     *
     * 1. Addition only needs to merge affected intervals.
     * 2. A query can find coverage with one predecessor lookup.
     * 3. Removal only needs to process intersecting intervals.
     */
    private final TreeMap<Integer, Integer> ranges = new TreeMap<>();

    /*
     * Constructor
     *
     * Initially, nothing is tracked, so the map is empty.
     *
     * Time:  O(1)
     * Space: O(1)
     */
    public RangeModule() {
    }

    /*
     * ADD RANGE
     *
     * Add every point in [left, right) to the tracked set.
     *
     * CORE IDEA:
     *
     * Imagine drawing the new interval on the number line.
     * Every existing interval that overlaps or touches it must
     * become part of one larger interval.
     *
     * Example:
     *
     * Existing:
     *     [2, 8)    [12, 18)    [25, 30)
     *
     * Add:
     *                    [14, 27)
     *
     * First, [14, 27) merges with [12, 18):
     *     [12, 27)
     *
     * That expanded interval then merges with [25, 30):
     *     [12, 30)
     *
     * Final:
     *     [2, 8)    [12, 30)
     *
     * WHY CAN'T WE JUST INSERT [14, 27)?
     *
     * Because that would leave overlapping intervals in the map.
     * Our query algorithm relies on the invariant that intervals
     * are already merged and disjoint.
     *
     * HOW WE FIND THE INTERVALS TO MERGE:
     *
     * floorEntry(start) finds the interval starting at or before
     * the new interval's left endpoint.
     *
     * If that interval ends at or after start, it overlaps or
     * touches the new interval. We move start backward to its start.
     *
     * Then ceilingEntry(start) finds the first interval whose start
     * is at least the expanded start.
     *
     * We keep visiting intervals while their starts are <= end.
     * Notice that end may grow during the loop!
     *
     * We collect keys first and remove them after traversal so that
     * successor navigation is easy to follow.
     */
    public void addRange(int left, int right) {

        // The interval we are building begins as the requested range.
        int start = left;
        int end = right;

        // Store the keys of old intervals that will be absorbed.
        // We delete them after identifying every interval to merge.
        var keysToRemove = new ArrayList<Integer>();

        /*
         * STEP 1: Look for an interval that begins before or at left.
         *
         * Example:
         *
         * Existing: [12, 18)
         * New:         [14, 27)
         *
         * floorEntry(14) returns 12 -> 18.
         *
         * Since 18 >= 14, the existing interval overlaps the new one.
         * We must include its entire range in the merged result.
         */
        Map.Entry<Integer, Integer> previous = ranges.floorEntry(start);

        if (previous != null && previous.getValue() >= start) {

            // The merged interval must begin where the old interval begins.
            start = previous.getKey();

            // Keep whichever interval has the larger right endpoint.
            end = Math.max(end, previous.getValue());

            // The predecessor will be merged into the new interval.
            keysToRemove.add(previous.getKey());
        }

        /*
         * STEP 2: Find the first interval at or after the expanded start.
         *
         * ceilingEntry(start) returns the smallest key >= start.
         *
         * If we found an overlapping predecessor in STEP 1, this
         * lookup may return that same interval. That is intentional:
         * it will be collected for removal by the loop below.
         */
        Map.Entry<Integer, Integer> current = ranges.ceilingEntry(start);

        /*
         * STEP 3: Merge every interval that overlaps or touches.
         *
         * Why current.getKey() <= end?
         *
         * An interval starting before end overlaps the new interval.
         * An interval starting exactly at end is adjacent:
         *
         *     [10, 20) and [20, 30)
         *
         * Their union is [10, 30), so we merge adjacency too.
         *
         * Why might this loop need multiple iterations?
         *
         * Merging one interval can increase end, which may make
         * another previously distant interval reachable.
         */
        while (current != null && current.getKey() <= end) {

            // Extend the merged interval to include the current interval.
            end = Math.max(end, current.getValue());

            // Remember this interval's key so we can delete it later.
            keysToRemove.add(current.getKey());

            // Move to the next interval in sorted order.
            current = ranges.higherEntry(current.getKey());
        }

        /*
         * STEP 4: Remove the old intervals that we merged.
         *
         * Removing by key is O(log n) per entry in a TreeMap.
         * Duplicate keys are harmless if a key was collected twice.
         */
        for (int key : keysToRemove) {
            ranges.remove(key);
        }

        /*
         * STEP 5: Insert the single merged interval.
         *
         * The map is now back to our invariant:
         * sorted, disjoint, non-adjacent intervals.
         */
        ranges.put(start, end);
    }

    /*
     * QUERY RANGE
     *
     * Return true if every point in [left, right) is tracked.
     *
     * CORE IDEA:
     *
     * Because intervals are merged, a query must fit completely
     * inside ONE stored interval.
     *
     * Example:
     *
     * Stored: [2, 8)    [12, 18)
     *
     * Query [13, 17):
     *     true, because [13, 17) is inside [12, 18).
     *
     * Query [13, 19):
     *     false, because the stored interval ends at 18.
     *
     * Query [8, 12):
     *     false, because this range is not tracked.
     *
     * floorEntry(left) finds the interval with the greatest start
     * that is <= left. If no such interval exists, left is uncovered.
     *
     * If an interval is found, it covers the whole query exactly when
     *
     *     interval.start <= left
     *     AND
     *     right <= interval.end
     *
     * The first condition is already guaranteed by floorEntry(left).
     * Therefore, we only need to check interval.end >= right.
     *
     * Time:  O(log n)
     * Space: O(1)
     */
    public boolean queryRange(int left, int right) {

        // Find the interval that starts closest to left without passing it.
        Map.Entry<Integer, Integer> interval = ranges.floorEntry(left);

        // No interval starts at or before left: left is not covered.
        if (interval == null) {
            return false;
        }

        // The interval must extend to the query's exclusive right endpoint.
        // If it ends earlier, the query contains an uncovered portion.
        return interval.getValue() >= right;
    }

    /*
     * REMOVE RANGE
     *
     * Stop tracking every point in [left, right).
     *
     * CORE IDEA:
     *
     * Find all intervals that intersect the removal range.
     * Delete each affected interval.
     * Restore any portions that lie outside the removal range.
     *
     * Example:
     *
     * Existing: [10, 30)
     * Remove:        [16, 22)
     *
     * Left portion survives:
     *     [10, 16)
     *
     * Right portion survives:
     *     [22, 30)
     *
     * Final:
     *     [10, 16)    [22, 30)
     *
     * The removal can split one interval into two, which is why
     * we must preserve both sides independently.
     *
     * TWO INTERVALS OVERLAP WHEN:
     *
     *     existingStart < right && left < existingEnd
     *
     * Strict inequalities are important for half-open intervals.
     *
     * For example, [10, 15) and [15, 20) do not overlap.
     *
     * Time:  O((k + 1) log n), where k is the number of affected intervals.
     * Space: O(k), for the keys and surviving interval pieces.
     */
    public void removeRange(int left, int right) {

        // Keys of intervals that intersect the removal range.
        var keysToRemove = new ArrayList<Integer>();

        // Surviving left and right pieces of affected intervals.
        var piecesToKeep = new ArrayList<Interval>();

        /*
         * STEP 1: Find where to begin.
         *
         * floorEntry(left) may return an interval that extends across left.
         *
         * Example:
         *     Existing: [10, 30)
         *     Remove:       [16, 22)
         *
         * floorEntry(16) returns 10 -> 30.
         * We must process it because it overlaps the removal range.
         *
         * But if the predecessor ends at or before left, it cannot overlap.
         * In that case, start from ceilingEntry(left), the first interval
         * whose start is at or after left.
         */
        Map.Entry<Integer, Integer> current = ranges.floorEntry(left);

        if (current == null || current.getValue() <= left) {
            current = ranges.ceilingEntry(left);
        }

        /*
         * STEP 2: Visit intervals that start before right.
         *
         * Once an interval starts at or beyond right, it cannot overlap
         * the removal range, so we can stop.
         */
        while (current != null && current.getKey() < right) {

            int start = current.getKey();
            int end = current.getValue();

            /*
             * Does this interval actually overlap the removal range?
             *
             * Because the intervals are sorted, only the first candidate
             * could end at or before left. Later candidates start at or
             * after left and are considered only if start < right.
             *
             * The end > left condition explicitly checks for intersection.
             */
            if (end > left) {

                // This entire old interval must be removed before rebuilding.
                keysToRemove.add(start);

                /*
                 * CASE 1: A left portion survives.
                 *
                 * Existing: [10, 30)
                 * Remove:       [16, 22)
                 *
                 * Since 10 < 16, preserve [10, 16).
                 *
                 * If start == left, there is no left portion to preserve.
                 */
                if (start < left) {
                    piecesToKeep.add(new Interval(start, left));
                }

                /*
                 * CASE 2: A right portion survives.
                 *
                 * Since 30 > 22, preserve [22, 30).
                 *
                 * If end == right, there is no right portion to preserve.
                 */
                if (end > right) {
                    piecesToKeep.add(new Interval(right, end));
                }

                /*
                 * If neither condition is true, the old interval lies
                 * entirely inside the removal range and disappears.
                 *
                 * If both are true, the removal splits it into two.
                 */
            }

            // Save the next entry before modifying the map.
            current = ranges.higherEntry(start);
        }

        /*
         * STEP 3: Delete every affected original interval.
         *
         * We delayed deletion until traversal was complete so that
         * higherEntry() could safely find the next entry.
         */
        for (int key : keysToRemove) {
            ranges.remove(key);
        }

        /*
         * STEP 4: Restore surviving pieces.
         *
         * The pieces were created from disjoint intervals, so they cannot
         * overlap each other or any unaffected interval.
         */
        for (Interval piece : piecesToKeep) {
            ranges.put(piece.start(), piece.end());
        }
    }

    /*
     * A Java record provides a concise immutable pair for an interval.
     *
     * Example:
     *     new Interval(10, 16) represents [10, 16).
     *
     * It is used only as temporary storage while removing intervals.
     */
    private record Interval(int start, int end) {}
}
```

## 6. Dry run the complete implementation

Let's run several operations and watch the map change.

| Step | Operation             | Contents of `ranges`       |
| ---- | --------------------- | -------------------------- |
| 1    | `addRange(10, 20)`    | `{10=20}`                  |
| 2    | `addRange(15, 25)`    | `{10=25}`                  |
| 3    | `queryRange(12, 24)`  | `{10=25}` → `true`         |
| 4    | `queryRange(12, 26)`  | `{10=25}` → `false`        |
| 5    | `removeRange(14, 18)` | `{10=14, 18=25}`           |
| 6    | `queryRange(12, 20)`  | `{10=14, 18=25}` → `false` |
| 7    | `addRange(14, 18)`    | `{10=25}`                  |

Let's examine the most important transition.

Before step 5:

```
Map: {10=25}

Tracked interval:
[10, 25)
```

We call `removeRange(14, 18)`.

The old interval overlaps the removal range, so we save:

```
Left piece:  [10, 14)
Right piece: [18, 25)
```

We remove the old entry `10=25`, then insert the two surviving pieces.

```
Map: {10=14, 18=25}

Tracked:

[10, 14)      [18, 25)
```

Now `queryRange(12, 20)` returns `false`. The query starts in the first interval, but that interval ends at 14, before the query's right endpoint of 20. The gap from 14 to 18 is not tracked.

Finally, adding `[14, 18)` merges the two intervals because they touch at their endpoints. The map returns to `{10=25}`.

## 7. The three things to remember in an interview

1. Store intervals, not points. Use the map's key as the start and value as the exclusive end.
2. Maintain merged intervals. Addition joins every overlapping or adjacent interval, and removal preserves the pieces outside the removed range.
3. Exploit sorted order. A query needs just one `floorEntry(left)` lookup because a valid query must fit inside a single merged interval.

If these three ideas make sense, the code becomes a translation of the number-line reasoning rather than something you have to memorize.
