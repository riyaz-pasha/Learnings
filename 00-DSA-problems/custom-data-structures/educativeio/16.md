# LeetCode 2034 — Stock Price Fluctuation

The key idea is to use one `HashMap` and two `PriorityQueue`s (min-heap and max-heap) to efficiently handle out-of-order updates and corrections.

The most important thing to understand is this: when a timestamp's price changes, the old price must stop affecting the minimum and maximum, even though Java's priority queues do not efficiently support removing an arbitrary element.

We'll build the solution from the problem statement to the optimal implementation, including why this data structure works and how to reason about edge cases.

## 0. Understand the problem in simple terms

Imagine we are maintaining a stock price history. Each timestamp identifies one record, and each timestamp must have exactly one current price.

For example:

| Timestamp | Current price |
| --------- | ------------- |
| 1         | 10            |
| 2         | 5             |
| 3         | 8             |

We need to support four operations:

- `update(timestamp, price)` — insert a new record or correct an existing record.
- `current()` — return the price associated with the largest timestamp.
- `maximum()` — return the highest price among all current records.
- `minimum()` — return the lowest price among all current records.

Notice that timestamps can arrive out of order, and a later update can correct an earlier record.

For example:

```
update(1, 10)
update(2, 5)
update(1, 3)   // Correction: timestamp 1 now has price 3
```

The current history is:

```
Timestamp:  1   2
Price:      3   5
```

Therefore:

```
current() = 5
maximum() = 5
minimum() = 3
```

The old price `10` must no longer count toward either the maximum or the minimum.

## 1. Clarifying questions to ask the interviewer

The constraints answer several questions already, but explicitly checking the requirements demonstrates good interview judgment.

1. Can timestamps arrive out of order? Yes. We cannot assume that the most recently received update has the latest timestamp.
2. Can the same timestamp be updated multiple times? Yes. A correction replaces the previous price. We must ensure that only the corrected price contributes to our answers.
3. Does `current()` mean the most recently received price or the price at the greatest timestamp? It means the price at the greatest timestamp. These are different when records arrive out of order.
4. Can query methods be called before any update? The constraints guarantee that they are called only after at least one update. This means we don't need to define special empty-state return values for LeetCode.
5. What performance is expected? With up to \\(10^5\\) operations, a solution with linear scans per query could take \\(O(n^2)\\) overall. We should target approximately \\(O(\log n)\\) updates and \\(O(1)\\) queries.

## 2. Core intuition — how to think about the optimal solution

The problem has three different questions, so separate them instead of forcing one data structure to answer everything.

### A. Remember the correct price for every timestamp

Use a `HashMap<Integer, Integer>`:

```
timestampToPrice

1 -> 10
2 -> 5
3 -> 8
```

If `update(1, 3)` arrives, replace the mapping:

```
1 -> 3
2 -> 5
3 -> 8
```

This map is our source of truth. It tells us which price is currently valid for each timestamp.

### B. Track the latest timestamp

Maintain an integer called `latestTimestamp`.

```
latestTimestamp = max(all timestamps received)
```

Whenever we receive an update, compare its timestamp with the latest timestamp. If it is greater, update `latestTimestamp`.

Then `current()` is simply:

```
return timestampToPrice.get(latestTimestamp);
```

Why not use the most recently received price? Because an update might correct an old timestamp.

```
update(10, 100)
update(20, 200)
update(5, 50)
```

The latest timestamp is `20`, so `current()` returns `200`, not `50`.

### C. Track the minimum and maximum prices

We could scan every price in the map whenever `minimum()` or `maximum()` is called. That is correct, but potentially slow.

Instead, use two heaps:

- A min-heap puts the smallest price at the top.
- A max-heap puts the largest price at the top.

Java's `PriorityQueue` is a min-heap by default. A max-heap can be created with a reversed comparator.

But this introduces the hardest part of the problem.

### D. The tricky part: stale heap entries

Suppose our updates are:

```
update(1, 10)
update(2, 5)
update(1, 3)
```

The map contains:

```
1 -> 3
2 -> 5
```

But if we simply insert every new price into the heaps, the heaps may contain:

```
Min-heap: [3, 5, 10]
Max-heap: [10, 5, 3]
```

The old `10` is now stale. It no longer represents the current price at timestamp `1`.

Java's `PriorityQueue` does not efficiently remove an arbitrary entry. Searching for and removing an old entry can cost \\(O(n)\\).

The trick is lazy deletion: leave obsolete entries in the heaps, and remove them only when they reach the top.

Every heap entry stores both the timestamp and price:

```
record PriceRecord(int timestamp, int price) {}
```

When examining a heap's top entry, compare its price against the map:

```
timestampToPrice.get(record.timestamp()) == record.price()
```

- If they match, the record is current.
- If they differ, the record is stale and must be removed.

We repeat this until the top entry is valid.

For example:

```
Current map:
1 -> 3
2 -> 5

Max-heap (conceptually):
(1, 10)  <- stale
(2, 5)   <- valid
(1, 3)   <- valid
```

When `maximum()` sees `(1, 10)`, it notices that timestamp `1` now has price `3`. It discards `(1, 10)` and continues until it reaches `(2, 5)`.

The resulting answer is `5`.

## 3. Edge cases to watch out for

| Case                                 | Example                                | Expected behavior                                                                             |
| ------------------------------------ | -------------------------------------- | --------------------------------------------------------------------------------------------- |
| First update                         | `update(1, 10)`                        | All queries return `10`.                                                                      |
| Out-of-order timestamps              | `update(10, 5)`, then `update(2, 8)`   | `current()` returns `5`.                                                                      |
| Correct the maximum                  | `update(1, 100)`, then `update(1, 10)` | Maximum must no longer be `100`.                                                              |
| Correct the minimum                  | `update(1, 1)`, then `update(1, 20)`   | Minimum must no longer be `1`, unless another record still has price `1`.                     |
| Same timestamp and price             | `update(1, 10)` twice                  | No change in the logical history.                                                             |
| Correct a price back to an old value | `10 → 5 → 10` for one timestamp        | The final price `10` is valid; stale entries with that same timestamp and price are harmless. |
| Equal prices at different timestamps | `update(1, 10)`, `update(2, 10)`       | Correctly handle duplicate prices.                                                            |
| New latest timestamp                 | `update(10, 5)`, then `update(20, 3)`  | `current()` returns `3`.                                                                      |

The most important testing principle is to correct both a maximum and a minimum. Many incorrect solutions handle one of these cases but not the other.

## 4. Solution 1 — Brute force

The simplest approach uses only a map and a variable for the latest timestamp.

For `minimum()` and `maximum()`, scan all current prices. This is a good starting point because it establishes the correct behavior before optimizing.

```
import java.util.HashMap;
import java.util.Map;

class StockPriceBruteForce {

    // Stores the authoritative, current price for each timestamp.
    // A correction overwrites the previous mapping.
    private final Map<Integer, Integer> timestampToPrice = new HashMap<>();

    // The greatest timestamp ever received, not the most recent update.
    private int latestTimestamp = 0;

    public void update(int timestamp, int price) {
        // Replacing an existing mapping automatically corrects its price.
        timestampToPrice.put(timestamp, price);

        // Updates can arrive out of order, so use the maximum timestamp.
        latestTimestamp = Math.max(latestTimestamp, timestamp);
    }

    public int current() {
        // HashMap lookup is expected O(1).
        return timestampToPrice.get(latestTimestamp);
    }

    public int maximum() {
        // Brute-force strategy: inspect every CURRENT price.
        // We scan the map, rather than the entire update history, so
        // corrections cannot leave obsolete prices in our answer.
        int maximumPrice = Integer.MIN_VALUE;

        for (int price : timestampToPrice.values()) {
            maximumPrice = Math.max(maximumPrice, price);
        }

        return maximumPrice;
    }

    public int minimum() {
        // Symmetrically, inspect every current price to find the minimum.
        int minimumPrice = Integer.MAX_VALUE;

        for (int price : timestampToPrice.values()) {
            minimumPrice = Math.min(minimumPrice, price);
        }

        return minimumPrice;
    }
}

/*
COMPLEXITY
Let n = the number of distinct timestamps currently stored.

update:
    Expected O(1) for the HashMap operation, plus O(1) for max().
    Total expected O(1).

current:
    Expected O(1) for a HashMap lookup.

maximum:
    O(n) time because every current price must be inspected.
    O(1) auxiliary space for the scan.

minimum:
    O(n) time for the same reason.
    O(1) auxiliary space for the scan.

Space:
    O(n) for the map.

Limitation:
    If there are n timestamps and many queries, repeatedly scanning
    the map is expensive. In the worst case, 10^5 operations can
    lead to O(n^2) total work.
*/
```

When is this useful? When the number of records is small, or when maximum/minimum queries are rare. Otherwise, we should optimize.

## 5. Solution 2 — Two `TreeMap`s

Before using heaps, there is another clean solution worth knowing.

Use:

1. `timestampToPrice`: the authoritative price for every timestamp.
2. `priceCounts`: the number of timestamps currently having each price, sorted by price.

A `TreeMap` maintains keys in sorted order, so `firstKey()` gives the minimum price and `lastKey()` gives the maximum price.

### The key insight: maintain price frequencies

Suppose the current records are:

```
Timestamp -> Price

1 -> 10
2 -> 5
3 -> 10
```

The price-frequency map is:

```
Price -> Number of timestamps

5  -> 1
10 -> 2
```

Now correct timestamp `1` from `10` to `3`.

First, remove one occurrence of `10`:

```
5  -> 1
10 -> 1
```

Then add one occurrence of `3`:

```
3  -> 1
5  -> 1
10 -> 1
```

The minimum and maximum are now correct.

Why use counts rather than a set of prices? Because multiple timestamps can have the same price. If one timestamp changes, that price must remain in the sorted map if another timestamp still uses it.

```
import java.util.Map;
import java.util.TreeMap;

class StockPriceTreeMap {

    private final Map<Integer, Integer> timestampToPrice = new TreeMap<>();

    // Sorted price -> number of timestamps currently having that price.
    private final TreeMap<Integer, Integer> priceCounts = new TreeMap<>();

    public void update(int timestamp, int price) {
        Integer oldPrice = timestampToPrice.put(timestamp, price);

        // If this timestamp already existed, remove its old price
        // from the frequency map before adding the corrected price.
        if (oldPrice != null) {
            removePrice(oldPrice);
        }

        // Add one occurrence of the new current price.
        priceCounts.merge(price, 1, Integer::sum);
    }

    private void removePrice(int price) {
        int count = priceCounts.get(price);

        if (count == 1) {
            // No timestamp uses this price anymore.
            priceCounts.remove(price);
        } else {
            // Other timestamps still use this price.
            priceCounts.put(price, count - 1);
        }
    }

    public int current() {
        // TreeMap.lastKey() gives the greatest timestamp.
        // The outer map's lookup then gives its current price.
        // This version uses a TreeMap for timestamps as well.
        int latestTimestamp = ((TreeMap<Integer, Integer>) timestampToPrice)
                .lastKey();

        return timestampToPrice.get(latestTimestamp);
    }

    public int maximum() {
        // Sorted prices mean the last key is the maximum current price.
        return priceCounts.lastKey();
    }

    public int minimum() {
        // The first key is the minimum current price.
        return priceCounts.firstKey();
    }
}

/*
COMPLEXITY
Let n = the number of distinct timestamps and p = the number of
distinct current prices, where p <= n.

update:
    O(log n) to update the timestamp TreeMap.
    O(log p) to update the price-frequency TreeMap.
    Total O(log n + log p), which is O(log n).

current:
    O(log n) to locate the largest timestamp in a TreeMap,
    followed by O(log n) to look up its price.
    Total O(log n).

maximum / minimum:
    O(log p) worst-case to access the first or last key.
    Total O(log n).

Space:
    O(n + p) = O(n).

Important:
    This implementation is correct, but the field must be declared
    as TreeMap, not Map, to call lastKey() without a cast. The cast
    above works because the object is a TreeMap, but a cleaner
    declaration is preferable in production code.
*/
```

For cleaner modern Java, declare the timestamp map as a `TreeMap` directly. That removes the cast and makes the implementation easier to read.

This solution is particularly attractive when you want no stale entries and straightforward correctness. The next approach is the standard heap-based solution for this LeetCode problem.

## 6. Solution 3 — Optimal practical approach: lazy deletion with two heaps

We use three pieces of state:

```
timestampToPrice  -> authoritative current prices
minHeap           -> smallest candidate price first
maxHeap           -> largest candidate price first
latestTimestamp   -> timestamp used by current()
```

Every update does three things:

1. Correct the map.
2. Add the new `(timestamp, price)` record to both heaps.
3. Update the greatest timestamp if needed.

We deliberately do not search the heaps for the old price. That would be inefficient.

Instead, a query removes stale records only from the top of its relevant heap.

### Complete Java 24 implementation

```
import java.util.Comparator;
import java.util.HashMap;
import java.util.Map;
import java.util.PriorityQueue;

class StockPrice {

    /*
     * A heap entry must contain BOTH timestamp and price.
     *
     * Why not store just the price?
     *
     * Suppose timestamp 1 changes from 100 to 10. If a heap contains
     * only 100, we cannot identify which timestamp produced it.
     *
     * With (timestamp, price), we can check whether that exact record
     * still agrees with the authoritative map.
     *
     * A record is valid precisely when:
     *     timestampToPrice.get(record.timestamp()) == record.price()
     *
     * Java 16+ records are useful here because this is an immutable
     * data carrier. Java 24 supports this syntax.
     */
    private record PriceRecord(int timestamp, int price) {}

    /*
     * SOURCE OF TRUTH:
     *
     * This map contains exactly one current price per timestamp.
     * All corrections overwrite this mapping.
     *
     * The heaps may contain stale records, but this map never does.
     */
    private final Map<Integer, Integer> timestampToPrice = new HashMap<>();

    /*
     * MIN-HEAP:
     *
     * PriorityQueue is a min-heap by default, but we explicitly specify
     * the comparator to make the intended ordering clear.
     *
     * The lowest price is at the root.
     *
     * We compare prices, not timestamps, because minimum() asks for
     * the minimum PRICE.
     */
    private final PriorityQueue<PriceRecord> minHeap =
            new PriorityQueue<>(Comparator.comparingInt(PriceRecord::price));

    /*
     * MAX-HEAP:
     *
     * Reverse the price comparator so the largest price is at the root.
     *
     * Use a comparator rather than subtracting prices. Subtraction
     * inside comparators can overflow for unrestricted integer values.
     */
    private final PriorityQueue<PriceRecord> maxHeap =
            new PriorityQueue<>(
                    Comparator.comparingInt(PriceRecord::price).reversed()
            );

    /*
     * Tracks the greatest timestamp ever received.
     *
     * We do not derive this from heap ordering because the heaps are
     * ordered by PRICE, not by TIMESTAMP.
     *
     * Constraints guarantee timestamp >= 1 and queries occur only
     * after at least one update, so zero is a safe initial value.
     */
    private int latestTimestamp = 0;

    public void update(int timestamp, int price) {

        /*
         * STEP 1: Correct the authoritative map.
         *
         * If timestamp already exists, put() replaces its old price.
         * If it does not exist, put() inserts a new timestamp.
         *
         * We intentionally do not remove the old record from either
         * heap. Arbitrary heap removal is O(n) in Java PriorityQueue.
         */
        timestampToPrice.put(timestamp, price);

        /*
         * STEP 2: Add the new record to BOTH heaps.
         *
         * Each heap may now contain obsolete records from earlier
         * corrections. This is intentional: lazy deletion handles them.
         *
         * Inserting one element into a heap costs O(log n) for a heap
         * of size n.
         */
        PriceRecord record = new PriceRecord(timestamp, price);

        minHeap.offer(record);
        maxHeap.offer(record);

        /*
         * STEP 3: Update the latest timestamp.
         *
         * An update can arrive out of order. For example, after
         * update(10, 50), update(3, 100) must NOT change current().
         *
         * Therefore, keep the maximum timestamp seen so far.
         */
        latestTimestamp = Math.max(latestTimestamp, timestamp);
    }

    public int current() {

        /*
         * The latest timestamp determines current(), not the most
         * recently received update.
         *
         * HashMap lookup is expected O(1).
         *
         * Corrections are reflected automatically because the map
         * always contains the current price for each timestamp.
         */
        return timestampToPrice.get(latestTimestamp);
    }

    public int maximum() {

        /*
         * Before returning the root, discard obsolete records that
         * happen to be at the top of the max-heap.
         *
         * We do not need to clean the entire heap. Only its root can
         * affect the answer to this query.
         */
        removeStaleRecords(maxHeap);

        /*
         * After cleanup, the root is the greatest VALID current price.
         * Constraints guarantee that at least one update has occurred.
         */
        return maxHeap.peek().price();
    }

    public int minimum() {

        /*
         * The same logic applies to the min-heap: stale records that
         * could incorrectly appear to be the minimum must be removed.
         */
        removeStaleRecords(minHeap);

        /*
         * The root is now the smallest valid current price.
         */
        return minHeap.peek().price();
    }

    private void removeStaleRecords(PriorityQueue<PriceRecord> heap) {

        /*
         * Repeatedly inspect the top until it represents the current
         * price for its timestamp.
         *
         * A heap does NOT need to contain only valid records. It only
         * needs to have a valid root whenever we return an answer.
         */
        while (!heap.isEmpty()) {

            PriceRecord record = heap.peek();

            /*
             * Look up the CURRENT price for this record's timestamp.
             *
             * If the map contains a different price, the heap record
             * is obsolete and must not be used as an answer.
             *
             * The comparison unboxes Integer to int. The record is
             * guaranteed to refer to a timestamp that was inserted,
             * so the map lookup is non-null.
             */
            int currentPrice = timestampToPrice.get(record.timestamp());

            if (currentPrice == record.price()) {

                /*
                 * This record matches the authoritative map.
                 *
                 * It is valid, and because it is at the root of the
                 * appropriate heap, it is the correct minimum/maximum.
                 */
                break;
            }

            /*
             * This record is stale.
             *
             * Remove it from the root and inspect the next candidate.
             * poll() costs O(log n).
             *
             * Crucially, we remove only from the heap passed to this
             * method. The other heap may still contain its own copy
             * of this stale record; it will discard it when necessary.
             */
            heap.poll();
        }
    }
}

/*
 * ================================================================
 * COMPLEXITY ANALYSIS
 * ================================================================
 *
 * Let:
 *   u = total number of update calls so far.
 *   n = number of distinct timestamps currently stored.
 *
 * The heaps can contain up to O(u) records because corrections append
 * new entries rather than removing old ones immediately.
 *
 * update(timestamp, price):
 *   - HashMap.put(): expected O(1).
 *   - latestTimestamp update: O(1).
 *   - One insertion into each heap: O(log u) per insertion.
 *   Total: O(log u) time.
 *
 * current():
 *   - One HashMap lookup.
 *   Total: expected O(1).
 *
 * minimum() / maximum():
 *   - Each stale root removed costs O(log u).
 *   - A single query may remove many stale records, so its worst-case
 *     time can be O(u log u).
 *   - However, every inserted record is removed from each heap at most
 *     once. Across the entire sequence of operations, the total work
 *     of stale-record cleanup is O(u log u).
 *   - Thus, cleanup is amortized O(log u) per operation over a sequence
 *     of O(u) operations, rather than O(u log u) on every query.
 *
 * Space:
 *   - Map: O(n).
 *   - Both heaps: O(u) in the worst case.
 *   Total: O(n + u) = O(u).
 *
 * IMPORTANT DISTINCTION:
 *   The heap approach has good amortized performance, but it is not
 *   guaranteed to give O(log n) space. Repeated corrections can leave
 *   stale entries in the heaps until they reach the top.
 *
 * The TreeMap solution avoids stale heap entries and uses O(n) space.
 */
```

### A small but important detail

The heap solution does not need to remove a stale record from both heaps immediately.

Suppose `(1, 10)` becomes stale after timestamp `1` is corrected to `3`.

- If `(1, 10)` reaches the top of the max-heap, the max-heap removes it.
- If it has not reached the top of the min-heap, it can remain there.
- When it eventually reaches the top of the min-heap, that heap will remove it too.

This is safe because each query cleans its own heap before returning an answer.

## 7. Compare the solutions

| Operation     | Brute force         | Two `TreeMap`s  | Two heaps with lazy deletion |
| ------------- | ------------------- | --------------- | ---------------------------- |
| `update`      | Expected \\(O(1)\\) | \\(O(\log n)\\) | \\(O(\log u)\\)              |
| `current`     | Expected \\(O(1)\\) | \\(O(\log n)\\) | Expected \\(O(1)\\)          |
| `minimum`     | \\(O(n)\\)          | \\(O(\log n)\\) | Amortized \\(O(\log u)\\)    |
| `maximum`     | \\(O(n)\\)          | \\(O(\log n)\\) | Amortized \\(O(\log u)\\)    |
| Space         | \\(O(n)\\)          | \\(O(n)\\)      | \\(O(u)\\)                   |
| Stale entries | No                  | No              | Yes, until cleaned           |

Here, \\(n\\) is the number of distinct timestamps, and \\(u\\) is the number of updates performed.

Which should you choose in an interview?

- Start with brute force to establish correctness.
- Present the `TreeMap` approach if you want predictable logarithmic operations, no stale entries, and linear space.
- Present the two-heap approach if you want the classic solution that gives constant-time `current()` and amortized logarithmic cleanup.

Both optimized approaches are valid. For this problem, the two-heap solution is especially useful to explain because lazy deletion is a common technique in heap-based interview questions.

## 8. Interview follow-up questions and answers

### Q1. Why can't we simply remove the old price from the priority queue during `update()`?

Java's `PriorityQueue` does not support efficient arbitrary-element removal. Finding the old entry can take \\(O(n)\\), which defeats the purpose of using a heap.

Lazy deletion avoids that search. We invalidate the old entry logically by updating the map, and physically remove it when it reaches the top.

### Q2. Why do we need the timestamp inside each heap record?

Because the same price can occur at multiple timestamps. The timestamp lets us check whether a particular entry still matches the current record for that timestamp.

Without the timestamp, we cannot reliably determine whether a price entry is stale.

### Q3. Why not maintain only the maximum and minimum values as variables?

Suppose the maximum is `100`, but its timestamp is corrected to `10`. We cannot determine the new maximum from the old maximum alone; we need to find the next-highest valid price.

The same problem occurs when the minimum is corrected upward. Heaps or an ordered price-frequency map solve this problem.

### Q4. What happens if two timestamps have the same price?

Both timestamps remain in the map. In the `TreeMap` approach, the price frequency is incremented for each timestamp. In the heap approach, each entry carries its own timestamp, so equal prices are handled naturally.

### Q5. What if a timestamp changes from `10` to `5` and then back to `10`?

The map's final value is `10`. An old heap entry with `(timestamp, 10)` will match the map again and be considered valid.

This is safe: even if it is an older copy of the record, it has the same timestamp and price as the current record. It cannot produce an incorrect minimum or maximum.

### Q6. Can a query take linear time even though the heap approach is efficient?

Yes. One `minimum()` or `maximum()` call might discard many stale entries, taking \\(O(u \log u)\\) in the worst case. But those entries cannot be discarded repeatedly: each is removed at most once from each heap. The total cleanup cost over the full sequence of operations is \\(O(u \log u)\\), giving amortized logarithmic cleanup per operation.

### Q7. How could we guarantee \\(O(\log n)\\) updates and queries without stale entries?

Use the two-`TreeMap` solution:

- One ordered map from timestamp to current price.
- Another ordered map from price to the number of timestamps using that price.

When a timestamp is corrected, decrement the old price's frequency and increment the new price's frequency. Delete a price key when its frequency reaches zero.

This gives \\(O(n)\\) space and predictable logarithmic updates and queries.

### Q8. What is the single most important invariant to remember?

The map is always correct; the heaps are only candidate collections.

Every update immediately changes the map to reflect the latest truth. The heaps may contain obsolete records, but before returning a minimum or maximum, the relevant heap discards stale roots until its top matches the map.

If you remember that distinction, the entire lazy-deletion approach becomes much easier to reason about.
