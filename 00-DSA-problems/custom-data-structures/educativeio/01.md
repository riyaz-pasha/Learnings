# Design MyHashSet — Java 24 Interview Guide

## 0. Simplify the problem statement

We need to build our own `HashSet` without using Java's built-in `HashSet`, `HashMap`, or any other hash table library.

Our class must support three operations:

- `add(key)`: Store the key if it is not already present.
- `contains(key)`: Return `true` if the key exists; otherwise, return `false`.
- `remove(key)`: Delete the key if it exists. Do nothing if it does not.

Constraints:

- `key` ranges from `0` to `1_000_000`, inclusive.
- At most `10_000` operations will be performed.

The most important observation is that the range of possible keys is known and relatively small. We can use that information to build a very simple, efficient solution.

## 1. Clarifying questions to ask the interviewer

1. Can keys be negative? No, according to the constraints. This lets us use the key directly as an array index.
2. Can the same key be added multiple times? A set stores unique values, so adding an existing key must not create a duplicate.
3. What should happen when removing a missing key? Nothing; the operation should be safe and have no effect.
4. Can we use a boolean array? We should confirm whether a direct-address array is acceptable, because it uses memory proportional to the entire key range rather than the number of stored keys.
5. Are built-in hash table libraries forbidden entirely? Yes. We will implement the operations ourselves.

Why ask these questions? They help establish the allowed data structures, the behavior of duplicate operations, and whether a memory-for-speed trade-off is acceptable.

## 2. Core idea and intuition

There are multiple ways to implement this problem. Let's understand them from simplest to optimal for the given constraints.

### Approach 1: Use a boolean array — direct addressing

Imagine every possible key has its own light switch.

- `false` means the key is absent.
- `true` means the key is present.

Since keys range from `0` to `1_000_000`, we need an array of `1_000_001` boolean entries.

For example, suppose we execute:

```
add(5)
add(10)
add(5)
contains(5)
contains(7)
remove(5)
contains(5)
```

The array changes as follows:

Step 1: Initially, every key is absent.

Only a few relevant indexes are shown.

### 5

false

### 7

false

### 10

false

Step 2: Execute add(5), add(10), add(5).

### 5

true

### 7

false

### 10

true

Adding 5 twice changes nothing the second time. Each key has only one slot.

Step 3: Execute contains(5), contains(7).

- `contains(5)` returns `true`.
- `contains(7)` returns `false`.

  Step 4: Execute remove(5).
  ### 5
  false
  ### 7
  false
  ### 10
  true

  `contains(5)` now returns `false`.

The key insight is that the key itself tells us exactly where its membership information is stored.

For example, key `10` always uses `present[10]`. We don't need to search for it.

### Why is this better than searching a list?

A list might require checking thousands of stored elements to find a key. With direct addressing, we jump straight to the corresponding array index.

The operations become:

```
present[key] = true;    // add
present[key];           // contains
present[key] = false;   // remove
```

No loops, hashing, linked lists, or collision handling are required.

### Mental model

```
key = 5
   |
   v
present[5]
   |
   +---- true  --> key exists
   |
   +---- false --> key does not exist
```

This is called direct addressing, not a traditional hash-table implementation.

## 3. All possible solutions

### Approach A: Boolean array — optimal for these constraints

```
class MyHashSet {

    /*
     * We are given keys in the inclusive range [0, 1_000_000].
     *
     * Therefore, there are exactly 1_000_001 possible keys.
     *
     * present[k] tells us whether key k is currently in the set:
     *     true  -> present
     *     false -> absent
     *
     * Why a boolean array?
     * - The key itself is a valid array index.
     * - We never need to search for a key.
     * - Duplicate insertions are naturally handled.
     * - Removing an absent key is safe.
     *
     * Space complexity: O(U), where U = 1_000_001.
     * This space is allocated regardless of how many keys are stored.
     */
    private final boolean[] present = new boolean[1_000_001];

    /*
     * add(key):
     *
     * Mark the key as present.
     *
     * If the key was already present, assigning true again changes
     * nothing. This automatically preserves set uniqueness.
     *
     * Time: O(1), one array write.
     * Extra space: O(1).
     */
    public void add(int key) {
        present[key] = true;
    }

    /*
     * contains(key):
     *
     * Read the membership flag directly from the array.
     *
     * There is no loop and no search.
     *
     * Time: O(1), one array read.
     * Extra space: O(1).
     */
    public boolean contains(int key) {
        return present[key];
    }

    /*
     * remove(key):
     *
     * Mark the key as absent.
     *
     * If the key was already absent, assigning false again is harmless.
     * No preliminary contains() check is necessary.
     *
     * Time: O(1), one array write.
     * Extra space: O(1).
     */
    public void remove(int key) {
        present[key] = false;
    }
}
```

Complexity analysis

Let \\(U=1{,}000{,}001\\), the size of the key universe, and \\(Q\\) be the number of operations.

| Operation        | Time       | Extra space |
| ---------------- | ---------- | ----------- |
| `add`            | \\(O(1)\\) | \\(O(1)\\)  |
| `contains`       | \\(O(1)\\) | \\(O(1)\\)  |
| `remove`         | \\(O(1)\\) | \\(O(1)\\)  |
| Entire structure | —          | \\(O(U)\\)  |

For \\(Q\\) operations, the total time is \\(O(Q)\\), excluding the one-time array initialization cost of \\(O(U)\\).

The boolean array has roughly one million entries. Java boolean-array elements are typically represented compactly relative to integer arrays, although the exact memory footprint depends on the JVM.

### Approach B: Boolean array with a smaller initial footprint — lazy allocation

If the key universe were much larger, allocating the entire array could be wasteful. One alternative is to allocate fixed-size blocks only when needed.

For this problem, it is unnecessary complexity, but it illustrates how to trade implementation simplicity against memory usage.

```
import java.util.HashMap; // Not allowed for the original problem.

class MyHashSetLazy {
    // This is intentionally NOT a valid solution under the restriction
    // against built-in hash table libraries. It illustrates why using
    // a map would be a shortcut, not an implementation.
}
```

We will not use a built-in map or hash set in the actual solution.

### Approach C: Store keys in a linked list

We can build the set ourselves using nodes.

```
class MyHashSetList {

    /*
     * Each node stores one key and a pointer to the next node.
     *
     * A linked list avoids allocating a million slots upfront, but it
     * must search linearly to determine whether a key exists.
     */
    private static final class Node {
        final int key;
        Node next;

        Node(int key, Node next) {
            this.key = key;
            this.next = next;
        }
    }

    private final Node dummy = new Node(-1, null);

    /*
     * Find the node immediately before the target, if it exists.
     *
     * Returning the predecessor makes removal easy because singly
     * linked lists cannot move backward.
     *
     * Time: O(n), where n is the number of stored keys.
     */
    private Node findPrevious(int key) {
        Node previous = dummy;

        while (previous.next != null && previous.next.key != key) {
            previous = previous.next;
        }

        return previous;
    }

    /*
     * Add only if the key is absent.
     *
     * Time: O(n) for the search, O(1) for insertion.
     * Total: O(n).
     */
    public void add(int key) {
        Node previous = findPrevious(key);

        if (previous.next == null) {
            previous.next = new Node(key, null);
        }
    }

    /*
     * Search the list and report whether the next node is the target.
     *
     * Time: O(n).
     */
    public boolean contains(int key) {
        Node previous = findPrevious(key);
        return previous.next != null;
    }

    /*
     * Find the predecessor and bypass the target node if present.
     *
     * previous.next = previous.next.next removes the target by
     * changing a pointer; Java's garbage collector reclaims the
     * unreachable node when appropriate.
     *
     * Time: O(n).
     */
    public void remove(int key) {
        Node previous = findPrevious(key);

        if (previous.next != null) {
            previous.next = previous.next.next;
        }
    }
}
```

The linked-list approach is valid and uses no built-in hash table. However, each operation may examine every stored key.

If there are \\(n\\) stored keys:

- `add`: \\(O(n)\\)
- `contains`: \\(O(n)\\)
- `remove`: \\(O(n)\\)
- Space: \\(O(n)\\)

It can be more memory-efficient than a full boolean array when only a handful of keys are stored, but it is slower for membership checks.

### Approach D: Implement a real hash set with buckets

A traditional hash set maps keys into a smaller array of buckets using a hash function. Different keys may map to the same bucket, so we need collision handling, such as separate chaining with linked lists.

For this problem, the hash function could be `key % capacity`. However, with keys in a known range and only 10,000 operations, direct addressing is simpler and offers deterministic constant-time operations.

A real hash-table implementation is worthwhile when the key universe is enormous or unbounded and allocating one slot per possible key is impractical.

## 4. Edge cases to watch out for

| Scenario                       | Expected behavior                     |
| ------------------------------ | ------------------------------------- |
| Add a key for the first time   | Store it                              |
| Add the same key repeatedly    | Still one membership entry            |
| Search for a missing key       | Return `false`                        |
| Remove a missing key           | Do nothing                            |
| Remove the same key repeatedly | Safe; remains absent                  |
| Add after removal              | Key becomes present again             |
| Key `0`                        | Valid; use index `0`                  |
| Key `1_000_000`                | Valid; last array index               |
| Empty set                      | Every `contains` call returns `false` |

Important off-by-one mistake: the key range is inclusive. An array of length `1_000_000` is not sufficient, because the largest valid key is `1_000_000`. The correct array length is `1_000_001`.

## 5. Interviewer follow-up questions and answers

Q1. Why is a boolean array better than a hash table here?

Because the entire key range is known, and each key can directly index its membership flag. We avoid hashing, collision handling, and linked-list traversal.

Q2. What if keys ranged from 0 to \\(10^{12}\\)?

A direct-address array would require an impractical amount of memory. We would use a custom hash table with collision handling, or a tree-based structure depending on the requirements.

Q3. Is `add()` idempotent?

Yes. Calling `add(key)` multiple times has the same final effect as calling it once. Setting the same boolean to `true` repeatedly does not change the result.

Q4. Why not check `contains(key)` before adding?

It is unnecessary. `present[key] = true` already handles both absent and existing keys. An extra check would add work without changing behavior.

Q5. Why not check `contains(key)` before removing?

Also unnecessary. Setting `present[key] = false` is correct whether the key is present or absent.

Q6. What is the difference between a hash set and direct addressing?

A hash set computes a bucket index using a hash function and must handle collisions. Direct addressing uses the key itself as the index. Direct addressing is possible here because the key range is small enough.

Q7. What is the total time complexity for 10,000 operations?

Each operation takes \\(O(1)\\), so all operations together take \\(O(Q)\\), or \\(O(10^4)\\) for the maximum number of calls. Initializing the array costs \\(O(10^6)\\) once.

Q8. Can we reduce memory usage?

Yes. A `BitSet` could store membership using approximately one bit per possible key, but Java's `BitSet` is a built-in data structure and may not be permitted by the problem's restrictions. A custom bit array could provide similar savings, but the boolean-array implementation is simpler and entirely sufficient for the given constraints.

## Final interview recommendation

Use the boolean-array solution for this exact problem. It is the simplest solution, requires no hashing or collision handling, and gives deterministic \\(O(1)\\) time for every operation. If the interviewer changes the constraints to allow an enormous or unknown key universe, explain why you would switch to a custom hash table.
