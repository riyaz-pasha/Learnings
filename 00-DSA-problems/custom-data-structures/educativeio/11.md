# AllOne Data Structure — Average O(1) Operations (Java 24)

## 0. Simplify the problem statement

We need to design a data structure that maintains strings and their frequencies, supporting four operations:

- `inc(key)`: Increase the key's frequency by one. If it does not exist, insert it with frequency `1`.
- `dec(key)`: Decrease its frequency by one. Remove the key when its frequency reaches `0`.
- `getMaxKey()`: Return any key with the largest frequency.
- `getMinKey()`: Return any key with the smallest frequency.

The main challenge: All four operations must run in average \\(O(1)\\) time.

A straightforward `HashMap<String, Integer>` supports updates in average \\(O(1)\\), but finding the minimum or maximum frequency requires scanning the map, taking \\(O(n)\\) time.

We need a structure that keeps both the frequencies and their ordering efficient.

## 1. Clarifying questions to ask the interviewer

1. Can multiple keys have the same frequency? Yes, and we can return any one of the tied keys. This means we do not need to maintain a particular order among keys with equal frequencies.
2. Can `dec(key)` be called for a nonexistent key? The statement guarantees the key exists. We can rely on that precondition.
3. What should happen when the structure is empty? Both query methods return `""`.
4. Does the order of keys matter? No. Any key tied for minimum or maximum is acceptable, so a `HashSet` can store keys sharing a frequency.
5. Are all operations required to be average \\(O(1)\\)? Yes. This rules out scanning all keys or sorting frequencies during a query.

These clarifications let us use hash-based lookups and maintain minimum and maximum frequencies incrementally, rather than recomputing them after each operation.

## 2. Core idea and intuition

The optimal solution combines two hash maps and a doubly linked list of frequency buckets.

- A hash map from key to its frequency bucket.
- A doubly linked list of buckets ordered by increasing frequency.
- Each bucket stores a frequency and a `HashSet` of keys with that frequency.
- A second hash map is optional because the ordered bucket list itself gives access to the minimum and maximum buckets through its ends. We use a sentinel-based doubly linked list, so the minimum bucket is immediately after the head sentinel and the maximum bucket is immediately before the tail sentinel.

The critical observation is that when a key's frequency changes by one, its destination bucket can only be the adjacent frequency bucket or a new bucket inserted beside its current bucket. We never need to search for the destination frequency.

### Mental model: buckets, not individual counts

Suppose the data structure contains:

Minimum

## 2

banana

## 5

Maximum

Each box represents a frequency bucket, not a single key. The linked list connects buckets in increasing frequency order; frequencies need not be consecutive.

For example, when `banana` moves from frequency `2` to `3`:

- If a bucket for frequency `3` exists immediately after its current bucket, move `banana` into it.
- Otherwise, create a frequency-`3` bucket immediately after the frequency-`2` bucket.
- If the old bucket becomes empty, remove it.

No full-list traversal is needed.

### Data structure diagram

```

  apple  -> bucket(1)
  pear   -> bucket(1)
  banana -> bucket(2)
  orange -> bucket(5)

Doubly linked list:

HEAD <-> [count=1: apple, pear]
      <-> [count=2: banana]
      <-> [count=5: orange] <-> TAIL

Minimum = first real bucket
Maximum = last real bucket
```

The hash map gives direct access to a key's bucket, while the linked list provides direct access to the minimum and maximum buckets.

## 3. Edge cases to watch out for

- Empty structure: Both queries must return `""`.
- First insertion: Create the frequency-`1` bucket.
- Last key removed: Delete its empty bucket; the list becomes empty.
- Bucket becomes empty: Unlink it immediately, or the minimum/maximum pointer may refer to an empty bucket.
- Frequency bucket already exists: Reuse it rather than creating a duplicate bucket for the same frequency.
- Frequency bucket does not exist: Create it next to the source bucket.
- Incrementing a key at the maximum: Its new bucket may become the new maximum.
- Decrementing a key at the minimum: Its new frequency may become the new minimum, or the key may disappear entirely.
- Ties: Any key from a bucket's `HashSet` is valid.
- Nonconsecutive frequencies: For example, buckets `1`, `4`, and `9` are valid. Never assume the next frequency is always present.

## 4. All possible solutions

### Approach 1 — Brute force

Maintain a map of keys to counts. For each query, scan all entries to find the minimum or maximum.

- `inc` and `dec`: average \\(O(1)\\).
- `getMinKey` and `getMaxKey`: \\(O(n)\\).
- Space: \\(O(n)\\).

This approach is simple but violates the required query complexity.

### Approach 2 — Map plus ordered structure

Maintain counts in a hash map and use a sorted map such as `TreeMap<Integer, Set<String>>` to group keys by frequency.

- Updates and min/max access: \\(O(\log b)\\), where \\(b\\) is the number of distinct frequencies.
- Space: \\(O(n+b)\\), which simplifies to \\(O(n)\\) because \\(b \le n\\).

This is easier to implement, but does not meet the average \\(O(1)\\) requirement.

### Approach 3 — Optimal: Hash map + doubly linked frequency buckets

Use the bucket structure described above.

- `inc`: average \\(O(1)\\).
- `dec`: average \\(O(1)\\).
- `getMinKey`: \\(O(1)\\).
- `getMaxKey`: \\(O(1)\\).
- Space: \\(O(n)\\).

This is the standard optimal solution because every key update touches only its own bucket and at most one neighboring bucket.

## 5. Java 24 implementations

### Solution 1: Brute force

```
import java.util.HashMap;
import java.util.Map;

class AllOneBruteForce {
    // Store each key's current frequency.
    private final Map<String, Integer> counts = new HashMap<>();

    public void inc(String key) {
        // HashMap lookup/update takes average O(1).
        counts.merge(key, 1, Integer::sum);
    }

    public void dec(String key) {
        // The problem guarantees that key exists.
        int count = counts.get(key);

        if (count == 1) {
            // A zero-frequency key must be removed entirely.
            counts.remove(key);
        } else {
            counts.put(key, count - 1);
        }
    }

    public String getMaxKey() {
        // Brute force: inspect every entry to find the maximum.
        // Time: O(n), where n is the number of distinct keys.
        String answer = "";

        int max = Integer.MIN_VALUE;

        for (var entry : counts.entrySet()) {
            if (entry.getValue() > max) {
                max = entry.getValue();
                answer = entry.getKey();
            }
        }

        // An empty map leaves answer as "".
        return answer;
    }

    public String getMinKey() {
        // Brute force: inspect every entry to find the minimum.
        // Time: O(n); this is why the approach is not optimal.
        String answer = "";

        int min = Integer.MAX_VALUE;

        for (var entry : counts.entrySet()) {
            if (entry.getValue() < min) {
                min = entry.getValue();
                answer = entry.getKey();
            }
        }

        return answer;
    }

    // Complexity:
    // inc: average O(1)
    // dec: average O(1)
    // getMinKey/getMaxKey: O(n)
    // Space: O(n)
}
```

### Solution 2: HashMap + TreeMap

```
import java.util.HashMap;
import java.util.HashSet;
import java.util.Map;
import java.util.Set;
import java.util.TreeMap;

class AllOneTreeMap {
    // keyToCount provides average O(1) access to a key's frequency.
    private final Map<String, Integer> keyToCount = new HashMap<>();

    // countToKeys keeps frequencies sorted.
    // Each frequency maps to every key with that frequency.
    private final TreeMap<Integer, Set<String>> countToKeys =
            new TreeMap<>();

    public void inc(String key) {
        int oldCount = keyToCount.getOrDefault(key, 0);
        int newCount = oldCount + 1;

        if (oldCount > 0) {
            // Remove the key from its old frequency bucket.
            removeFromBucket(key, oldCount);
        }

        // Add the key to its new frequency bucket.
        countToKeys.computeIfAbsent(
                newCount, ignored -> new HashSet<>()
        ).add(key);

        keyToCount.put(key, newCount);
    }

    public void dec(String key) {
        // The key is guaranteed to exist.
        int oldCount = keyToCount.get(key);

        removeFromBucket(key, oldCount);

        if (oldCount == 1) {
            // Frequency zero means the key no longer exists.
            keyToCount.remove(key);
        } else {
            int newCount = oldCount - 1;

            countToKeys.computeIfAbsent(
                    newCount, ignored -> new HashSet<>()
            ).add(key);

            keyToCount.put(key, newCount);
        }
    }

    private void removeFromBucket(String key, int count) {
        Set<String> keys = countToKeys.get(count);
        keys.remove(key);

        if (keys.isEmpty()) {
            // Do not retain empty frequency buckets.
            countToKeys.remove(count);
        }
    }

    public String getMinKey() {
        // firstEntry returns the lowest frequency bucket.
        // TreeMap lookup is O(log b), where b is distinct frequencies.
        if (countToKeys.isEmpty()) {
            return "";
        }

        return countToKeys.firstEntry().getValue()
                .iterator().next();
    }

    public String getMaxKey() {
        // lastEntry returns the highest frequency bucket.
        if (countToKeys.isEmpty()) {
            return "";
        }

        return countToKeys.lastEntry().getValue()
                .iterator().next();
    }

    // Complexity:
    // inc/dec: O(log b) due to TreeMap insertion/removal.
    // getMinKey/getMaxKey: O(1) to locate an end entry,
    // plus O(1) to obtain an arbitrary HashSet element.
    // Space: O(n + b) = O(n).
    // This is a useful intermediate design, but not the required
    // average O(1) update solution.
}
```

### Solution 3: Optimal average O(1) implementation

This is the implementation to present in an interview.

```
import java.util.HashMap;
import java.util.HashSet;
import java.util.Map;
import java.util.Set;

class AllOne {

    /*
     * Each bucket groups all keys having the same frequency.
     *
     * The frequency buckets are connected in increasing order.
     * We use a doubly linked list because removing a bucket and
     * inserting an adjacent bucket must take O(1) time.
     */
    private static final class Bucket {
        int count;
        final Set<String> keys = new HashSet<>();

        Bucket prev;
        Bucket next;

        Bucket(int count) {
            this.count = count;
        }
    }

    /*
     * Maps each key directly to its frequency bucket.
     *
     * This is the essential ingredient that prevents us from
     * searching the linked list for a key.
     */
    private final Map<String, Bucket> keyToBucket = new HashMap<>();

    /*
     * Sentinel nodes eliminate special cases at the ends.
     *
     * HEAD <-> first frequency bucket <-> ... <-> TAIL
     *
     * HEAD.next is the minimum-frequency bucket.
     * TAIL.prev is the maximum-frequency bucket.
     * If HEAD.next == TAIL, the structure is empty.
     */
    private final Bucket head = new Bucket(0);
    private final Bucket tail = new Bucket(0);

    public AllOne() {
        // Initially, the sentinel nodes are adjacent.
        head.next = tail;
        tail.prev = head;
    }

    public void inc(String key) {
        Bucket current = keyToBucket.get(key);

        if (current == null) {
            // A new key always starts with frequency 1.
            Bucket first = head.next;

            if (first != tail && first.count == 1) {
                // Reuse the frequency-1 bucket when it already exists.
                first.keys.add(key);
                keyToBucket.put(key, first);
            } else {
                // Otherwise create frequency 1 directly after HEAD.
                Bucket one = new Bucket(1);
                one.keys.add(key);

                insertAfter(head, one);
                keyToBucket.put(key, one);
            }

            // No traversal is required: all operations above are O(1)
            // apart from expected constant-time hash operations.
            return;
        }

        /*
         * Existing key: its new frequency is current.count + 1.
         * Because the list is sorted, the destination can only be
         * current.next, or a new bucket inserted after current.
         */
        Bucket next = current.next;
        int newCount = current.count + 1;

        if (next != tail && next.count == newCount) {
            // The correct neighboring bucket already exists.
            next.keys.add(key);
            keyToBucket.put(key, next);
        } else {
            // Create the missing frequency bucket adjacent to current.
            Bucket incremented = new Bucket(newCount);
            incremented.keys.add(key);

            insertAfter(current, incremented);
            keyToBucket.put(key, incremented);
        }

        // The key has moved, so remove it from its previous bucket.
        current.keys.remove(key);

        if (current.keys.isEmpty()) {
            // Empty buckets are unnecessary and must be unlinked.
            removeBucket(current);
        }

        /*
         * Time: average O(1).
         * HashMap access and HashSet updates are expected O(1).
         * Linked-list insertion/removal uses a constant number of
         * pointer assignments. There is no traversal.
         */
    }

    public void dec(String key) {
        // The problem guarantees that the key exists.
        Bucket current = keyToBucket.get(key);
        int newCount = current.count - 1;

        if (newCount == 0) {
            // Frequency zero means complete removal.
            current.keys.remove(key);
            keyToBucket.remove(key);

            if (current.keys.isEmpty()) {
                // Keep only buckets that contain at least one key.
                removeBucket(current);
            }

            return;
        }

        /*
         * For a decrement, the destination can only be current.prev
         * or a new bucket inserted immediately before current.
         */
        Bucket prev = current.prev;

        if (prev != head && prev.count == newCount) {
            // Reuse the neighboring bucket when its count matches.
            prev.keys.add(key);
            keyToBucket.put(key, prev);
        } else {
            // Create the missing lower-frequency bucket.
            Bucket decremented = new Bucket(newCount);
            decremented.keys.add(key);

            insertAfter(current.prev, decremented);
            keyToBucket.put(key, decremented);
        }

        // Remove the key from its old frequency bucket.
        current.keys.remove(key);

        if (current.keys.isEmpty()) {
            // Unlinking an empty bucket also preserves correct min/max.
            removeBucket(current);
        }

        /*
         * Time: average O(1).
         * The destination is found using one neighboring pointer;
         * we never scan buckets or recompute the minimum/maximum.
         */
    }

    public String getMaxKey() {
        // The last real bucket always has the largest frequency.
        if (tail.prev == head) {
            return "";
        }

        // All keys in this bucket tie for maximum frequency.
        // Returning any one key satisfies the problem statement.
        return tail.prev.keys.iterator().next();
    }

    public String getMinKey() {
        // The first real bucket always has the smallest frequency.
        if (head.next == tail) {
            return "";
        }

        // All keys in this bucket tie for minimum frequency.
        return head.next.keys.iterator().next();
    }

    /*
     * Inserts node immediately after position.
     *
     * Before: position <-> oldNext
     * After:  position <-> node <-> oldNext
     *
     * This operation changes a constant number of pointers, so O(1).
     */
    private void insertAfter(Bucket position, Bucket node) {
        Bucket oldNext = position.next;

        node.prev = position;
        node.next = oldNext;

        position.next = node;
        oldNext.prev = node;
    }

    /*
     * Removes an existing bucket from the linked list.
     *
     * Before: node.prev <-> node <-> node.next
     * After:  node.prev <-> node.next
     *
     * The bucket must already be empty, so no key-map updates are needed.
     */
    private void removeBucket(Bucket node) {
        node.prev.next = node.next;
        node.next.prev = node.prev;
    }

    /*
     * Complexity analysis:
     *
     * Let n = number of distinct keys and b = number of nonempty buckets.
     *
     * inc(key):
     *   Average O(1) for the key lookup and hash-set operations.
     *   At most one bucket is created and at most one is removed.
     *   Total average O(1).
     *
     * dec(key):
     *   Average O(1) for hash operations and linked-list modifications.
     *   At most one bucket is created and at most one is removed.
     *   Total average O(1).
     *
     * getMinKey():
     *   Reads head.next and chooses a key from its HashSet.
     *   Expected O(1).
     *
     * getMaxKey():
     *   Reads tail.prev and chooses a key from its HashSet.
     *   Expected O(1).
     *
     * Space:
     *   O(n) for the key-to-bucket map and the sets containing keys.
     *   O(b) for the linked-list buckets, where b <= n.
     *   Total O(n).
     *
     * The O(1) guarantee is average/expected, relying on normal
     * HashMap and HashSet hashing behavior.
     */
}
```

| Operation       | Frequency buckets after operation |
| --------------- | --------------------------------- |

| `inc("banana")` | `1: [apple, banana]`              |
| `inc("apple")`  | `1: [banana] ↔ 2: [apple]`        |
| `inc("banana")` | `2: [apple, banana]`              |
| `inc("banana")` | `2: [apple] ↔ 3: [banana]`        |
| `getMinKey()`   | `"apple"`                         |
| `getMaxKey()`   | `"banana"`                        |
| `dec("banana")` | `2: [apple, banana]`              |
| `getMaxKey()`   | Either `"apple"` or `"banana"`    |

Notice that when `banana` moves from frequency `1` to `2`, the existing frequency-`2` bucket is reused. When it moves from `2` to `3`, a new bucket is inserted adjacent to its current bucket.

## 7. Interviewer follow-up questions and answers

Q1. Why use a doubly linked list instead of a singly linked list?

A doubly linked list lets us remove any known bucket in \\(O(1)\\), because we can directly update both neighboring pointers. A singly linked list would require finding the predecessor, potentially taking \\(O(n)\\).

Q2. Why store a `HashSet<String>` in each bucket?

Multiple keys can share a frequency. A set allows expected \\(O(1)\\) insertion, deletion, and retrieval of any key. We do not need to maintain an order among tied keys.

Q3. Why can we avoid searching for the next frequency?

Every increment or decrement changes a frequency by exactly one. Because the buckets are sorted, the destination must be the immediately adjacent bucket with the required frequency, or a new bucket inserted next to the current one.

Q4. Why remove empty buckets?

Empty buckets are not useful. If we keep them, `head.next` or `tail.prev` could point to an empty bucket, making minimum and maximum queries incorrect.

Q5. Can we guarantee worst-case \\(O(1)\\) time for hash operations?

No. Java's `HashMap` and `HashSet` provide expected or average constant-time behavior under normal hashing assumptions, not an unconditional worst-case guarantee. The linked-list operations themselves are worst-case \\(O(1)\\).

Q6. Can the minimum and maximum frequencies have gaps?

Yes. For example, the buckets can have frequencies `1`, `4`, and `9`. The algorithm depends on linked-list adjacency, not on consecutive integer frequencies.

Q7. What is the maximum number of frequency buckets?

If there are \\(n\\) distinct keys, there can be at most \\(n\\) nonempty buckets, because each bucket must contain at least one key.

Q8. What changes would be needed to make the data structure thread-safe?

We would need synchronization or an appropriate concurrency design covering the entire operation. Updating the hash map and linked list independently is insufficient because an operation must preserve consistency between both structures.

| `getMinKey` | \\(O(n)\\)         | \\(O(1)\\)      | \\(O(1)\\) expected |

| Space       | \\(O(n)\\)         | \\(O(n)\\)      | \\(O(n)\\)          |

The key insight to remember: Use a hash map to find a key's bucket directly, and a doubly linked list to maintain ordered frequency buckets. Since a key's count changes by only one per operation, its destination is always adjacent. This removes the need for any traversal and achieves the required average \\(O(1)\\) operations.











































# How to Develop the Intuition for the AllOne Data Structure

The most important skill in this problem is not memorizing the doubly linked list solution. It is learning how to derive the data structure from the operations and their time-complexity requirements.

Let's approach it as you would in a senior Java interview: start with the obvious solution, identify exactly why it fails, and use that failure to discover the optimal design. Then we will derive the corner cases systematically instead of trying to memorize a list.

## 1. First, understand what the problem is really asking

We have four operations:

```
inc(String key)
dec(String key)
getMaxKey()
getMinKey()
```

Imagine we are tracking how often users search for products.

After these operations:

```
inc("apple");
inc("banana");
inc("apple");
inc("orange");
inc("banana");
inc("apple");
```

Our frequencies are:

```
apple  -> 3
banana -> 2
orange -> 1
```

We need to answer:

- Which key has the highest frequency? `apple`
- Which key has the lowest frequency? `orange`
- What happens if `banana` is incremented? Its frequency becomes `3`.
- What happens if `orange` is decremented? Its frequency becomes `0`, so we remove it.

So far, this looks like a simple frequency-counting problem.

But the actual challenge is the requirement that every operation must run in average \\(O(1)\\) time.

That requirement changes how we design the data structure.

## 2. How should you start thinking in an interview?

Use this four-step mental process:

## 1

Identify the information we must maintain

We need each key's frequency, plus the current minimum and maximum frequencies.

## 2

Choose a structure for each requirement

A hash map is good for finding a key quickly. An ordered structure is good for finding minimum and maximum values.

## 3

Look for conflicts with the complexity target

A scan is too slow. A balanced search tree takes \\(O(\log n)\\). We need something better.

## 4

Exploit the fact that counts change by exactly one

Incrementing and decrementing are local changes. This is the clue that lets us maintain the ordering without searching for a new position.

The fourth step is the breakthrough. Let's understand why.

## 3. Derive the solution from the simplest approach

### Step 1: Start with a HashMap

The first data structure you should think of is:

```
Map<String, Integer> count = new HashMap<>();
```

Why?

Because we need to:

- Find a key's frequency.
- Increase its frequency.
- Decrease its frequency.
- Insert or remove keys.

A hash map supports all of these in average \\(O(1)\\) time.

But try to implement `getMaxKey()`:

```
String getMaxKey() {
    String answer = "";
    int max = Integer.MIN_VALUE;

    for (var entry : count.entrySet()) {
        if (entry.getValue() > max) {
            max = entry.getValue();
            answer = entry.getKey();
        }
    }

    return answer;
}
```

What is the problem?

We must examine every key. With \\(n\\) distinct keys, this takes \\(O(n)\\).

Interview lesson: A data structure can make three operations fast while making the fourth too slow. Always evaluate the complexity of every required operation.

### Step 2: What if we maintain the maximum and minimum ourselves?

Suppose we add two variables:

```
int minCount;
int maxCount;
```

At first, this seems promising. When a key's frequency changes, we can update these variables.

But consider this state:

```
apple  -> 1
banana -> 2
orange -> 3
```

The maximum frequency is `3`, belonging to `orange`.

Now:

```
dec("orange");
```

The state becomes:

```
apple  -> 1
banana -> 2
orange -> 2
```

The maximum is now `2`, which we can update easily.

But what if we decrement `banana` from `2` to `1` and then remove `apple` by decrementing it from `1` to `0`?

```
banana -> 1
orange -> 2
```

The minimum is now `1`.

That example is easy. The harder situation is when the last key at the current minimum or maximum disappears.

For example:

```
apple  -> 1
banana -> 1
orange -> 4
```

Remove both `apple` and `banana`:

```
orange -> 4
```

The minimum and maximum are both `4`.

How do we know which frequency comes next after the last key in the minimum bucket disappears? We could search all keys, but that would take \\(O(n)\\).

Lesson: Storing the answer in a variable does not mean we can update it efficiently. We must maintain enough information to discover the replacement answer immediately.

### Step 3: What if we use a sorted map?

We could store keys grouped by frequency:

```
1 -> [apple, pear]
2 -> [banana]
5 -> [orange]
```

A `TreeMap<Integer, Set<String>>` makes it easy to find the smallest and largest frequency.

However, adding or removing a frequency bucket costs \\(O(\log b)\\), where \\(b\\) is the number of distinct frequencies.

That is good engineering in many real applications, but it does not satisfy this problem's average \\(O(1)\\) requirement for every operation.

Now ask yourself:

> What if I could keep frequencies sorted without having to search for where each updated frequency belongs?

That question leads to the optimal solution.

## 4. The key intuition: a frequency changes by only one

This is the most important observation in the entire problem.

An increment performs:

\\[ c \rightarrow c+1 \\]

A decrement performs:

\\[ c \rightarrow c-1 \\]

The change is always exactly one.

Imagine that we already maintain frequency groups in sorted order:

```
HEAD <-> [1: apple, pear] <-> [2: banana] <-> [5: orange] <-> TAIL
```

Suppose `banana` has frequency `2`.

When we increment it, its new frequency is `3`.

Where should it go?

There are only two possibilities:

1. A bucket with frequency `3` is immediately after the bucket with frequency `2`.
2. There is no such bucket, so we create one immediately after the bucket with frequency `2`.

We never need to search for the frequency-`3` bucket elsewhere in the list.

Why not?

Because the list is sorted, and there cannot be another frequency between `2` and `3`.

The same reasoning works for decrementing from `2` to `1`: the destination is either the immediately preceding bucket or a new bucket inserted immediately before the current one.

### The mental model

```
Increment:

Before:
[1: apple] <-> [2: banana] <-> [5: orange]

After increment("banana"):
[1: apple] <-> [3: banana] <-> [5: orange]

Decrement:

Before:
[1: apple] <-> [3: banana] <-> [5: orange]

After decrement("banana"):
[1: apple] <-> [2: banana] <-> [5: orange]
```

The frequency buckets are ordered, but the frequencies do not have to be consecutive.

A bucket is created or reused locally. This is why a doubly linked list works so well.

General problem-solving pattern: When a value changes by a small, bounded amount, ask whether its new position can be determined from its current position and a constant number of neighbors.

This idea appears in cache designs, scheduling systems, frequency trackers, and other data structures that maintain changing priorities.

## 5. Why do we need both a HashMap and a doubly linked list?

We have discovered how to maintain the ordered frequency buckets. But we still need to find a key's current bucket quickly.

Suppose the list is:

```
HEAD <-> [1: apple, pear] <-> [2: banana] <-> [5: orange] <-> TAIL
```

If we want to increment `banana`, we need to find its frequency-`2` bucket.

Searching the linked list would take \\(O(b)\\) time.

So we add a hash map:

```
Map<String, Bucket> keyToBucket;
```

It gives us direct access:

```
apple  -> Bucket(1)
pear   -> Bucket(1)
banana -> Bucket(2)
orange -> Bucket(5)
```

Now we have solved two different problems using two different structures:

| Requirement                       | Data structure               | Why it works                             |
| --------------------------------- | ---------------------------- | ---------------------------------------- |
| Find a key's current bucket       | `HashMap`                    | Average \\(O(1)\\) lookup                |
| Find keys with the same frequency | `HashSet` inside each bucket | Average \\(O(1)\\) insertion and removal |
| Move between frequencies          | Doubly linked list           | Direct access to adjacent buckets        |
| Find minimum frequency            | `head.next`                  | First real bucket is the minimum         |
| Find maximum frequency            | `tail.prev`                  | Last real bucket is the maximum          |

This is an important interview technique: do not force one data structure to solve every problem. Combine structures, each responsible for the operation it handles best.

## 6. How to think about corner cases systematically

Many candidates memorize a few edge cases and still miss bugs. A stronger approach is to derive them from the operations and the invariants of the data structure.

Ask four questions:

1. Does the object exist before the operation?
2. Does its frequency become zero?
3. Does its source bucket become empty?
4. Does its destination bucket already exist?

These questions generate almost every important edge case for `inc` and `dec`.

### First, define the invariants

An invariant is a condition that must remain true after every operation.

For AllOne, maintain these five invariants:

Invariant 1 — Every stored key has exactly one bucket.

If `keyToBucket` contains `"apple"`, the bucket referenced by that entry must contain `"apple"` in its `keys` set.

Invariant 2 — Every bucket contains at least one key.

Empty buckets must be removed immediately.

Invariant 3 — The bucket list is sorted in strictly increasing frequency order.

For example:

```
HEAD <-> [1: apple] <-> [3: banana] <-> [7: orange] <-> TAIL
```

The counts `1`, `3`, and `7` are strictly increasing even though they are not consecutive.

Invariant 4 — There is at most one bucket for each frequency.

If a frequency-`3` bucket already exists, an increment from `2` to `3` must reuse it.

Invariant 5 — The sentinel nodes remain connected.

The head and tail sentinels simplify insertion and removal at the ends. Even when there are no keys, `head.next == tail` and `tail.prev == head`.

If you can preserve these invariants, the minimum and maximum queries are correct automatically.

### Now derive corner cases for `inc(key)`

There are two fundamental situations.

#### Case A: The key does not exist

```
inc("apple");
```

The new frequency must be `1`.

Ask: Does a frequency-`1` bucket already exist?

If yes:

```
Before:
HEAD <-> [1: pear] <-> TAIL

After:
HEAD <-> [1: pear, apple] <-> TAIL
```

Reuse the bucket.

If no:

```
Before:
HEAD <-> [2: banana] <-> TAIL

After:
HEAD <-> [1: apple] <-> [2: banana] <-> TAIL
```

Create the new bucket immediately after `head`.

This covers both first insertion into an empty structure and insertion when the smallest frequency is greater than `1`.

#### Case B: The key already exists

Suppose `apple` is in the frequency-`2` bucket.

Ask: Does a frequency-`3` bucket immediately follow the current bucket?

If yes: Move the key to that bucket.

If no: Insert a frequency-`3` bucket immediately after the current bucket.

After moving the key, ask another question:

> Did the old bucket become empty?

If yes, remove it.

This final question is easy to forget, but it is essential. Otherwise, an empty bucket could incorrectly become the minimum or maximum.

### Now derive corner cases for `dec(key)`

Decrement has three distinct situations.

#### Case A: The frequency is `1`

```
HEAD <-> [1: apple] <-> TAIL
```

Call:

```
dec("apple");
```

The new frequency would be zero, which is not a valid stored frequency.

Therefore:

1. Remove `"apple"` from its bucket.
2. Remove `"apple"` from the hash map.
3. Remove the bucket if it is now empty.

The result is:

```
HEAD <-> TAIL
```

Both `getMinKey()` and `getMaxKey()` must now return `""`.

#### Case B: The frequency is greater than `1`, and the destination bucket exists

Suppose:

```
HEAD <-> [2: apple] <-> [3: banana] <-> TAIL
```

Call:

```
dec("banana");
```

`banana` moves from frequency `3` to frequency `2`.

The destination bucket already exists, so we reuse it:

```
HEAD <-> [2: apple, banana] <-> TAIL
```

Remove the old frequency-`3` bucket if it is empty.

#### Case C: The frequency is greater than `1`, but the destination bucket does not exist

Suppose:

```
HEAD <-> [2: apple] <-> [5: banana] <-> TAIL
```

Call:

```
dec("banana");
```

Its new frequency is `4`. There is no frequency-`4` bucket.

Create one immediately before the current frequency-`5` bucket:

```
HEAD <-> [2: apple] <-> [4: banana] <-> TAIL
```

Again, no search is needed.

### What about `getMinKey()` and `getMaxKey()`?

These methods should be the simplest methods in the class.

For `getMinKey()`:

- If `head.next == tail`, return `""`.
- Otherwise, return any key from `head.next.keys`.

For `getMaxKey()`:

- If `tail.prev == head`, return `""`.
- Otherwise, return any key from `tail.prev.keys`.

Do not scan the list. Do not recompute frequencies. Do not maintain separate minimum and maximum variables.

The list already maintains the information you need.

## 7. A complete corner-case matrix

When I interview a candidate, I want to see them derive tests from the invariants rather than write random examples.

Here is a systematic test plan.

| Scenario                        | Example                   | Expected behavior                           |
| ------------------------------- | ------------------------- | ------------------------------------------- |
| Initially empty                 | `getMinKey()`             | `""`                                        |
| Initially empty                 | `getMaxKey()`             | `""`                                        |
| First insertion                 | `inc("a")`                | One bucket with count `1`                   |
| Repeated increment              | `inc("a")` twice          | Count becomes `2`                           |
| Multiple keys tied              | `inc("a")`, `inc("b")`    | Both have count `1`; either can be returned |
| Increment into existing bucket  | `a:1, b:2`; increment `a` | Both share bucket `2`                       |
| Increment creates new maximum   | `a:1`; increment `a`      | Bucket `2` becomes maximum                  |
| Decrement into existing bucket  | `a:2, b:1`; decrement `a` | Both share bucket `1`                       |
| Decrement creates a new bucket  | `a:4`; decrement `a`      | Bucket `3` is created                       |
| Delete the last key in a bucket | `a:1, b:2`; decrement `a` | Bucket `1` disappears                       |
| Delete the final key            | `a:1`; decrement `a`      | List becomes empty                          |
| Remove the maximum bucket       | `a:1, b:2`; decrement `b` | Maximum becomes frequency `1`               |
| Remove the minimum bucket       | `a:1, b:2`; increment `a` | Minimum becomes frequency `2`               |
| Nonconsecutive frequencies      | `a:1, b:5`; increment `a` | A frequency-`2` bucket is created           |

One subtle point: because the specification allows any key tied for minimum or maximum, tests should verify the returned key's frequency, not a specific key string.

For example, if both `"apple"` and `"banana"` have frequency `3`, either is a correct result from `getMaxKey()`.

## 8. How to test the invariants, not just the outputs

A good technique is to create a small test harness that checks the internal structure after every operation.

For the production solution, the invariant checks below would normally belong in tests rather than the class itself.

```
/*
 * DEBUGGING STRATEGY
 *
 * After every inc/dec operation, verify:
 *
 * 1. Every real bucket has at least one key.
 * 2. Bucket counts increase strictly from head to tail.
 * 3. Every key in a bucket maps back to that bucket in keyToBucket.
 * 4. Every key in keyToBucket appears in exactly one bucket.
 * 5. Neighbor pointers are consistent:
 *      node.next.prev == node
 *      node.prev.next == node
 * 6. head.next == tail if and only if tail.prev == head.
 *
 * These checks catch structural bugs before they appear as
 * incorrect minimum/maximum results.
 */
```

Why is this so useful?

Imagine your `getMaxKey()` returns the wrong answer. The problem may not be in `getMaxKey()` at all. An earlier `dec()` might have failed to remove an empty bucket, or an `inc()` might have created two buckets with the same count.

Testing invariants helps you find the operation that corrupted the data structure.

## 9. A complete dry run: follow every pointer change

Let's trace a slightly more interesting sequence.

```
inc("a");
inc("b");
inc("a");
inc("c");
inc("c");
inc("c");
dec("c");
dec("a");
dec("a");
```

Start with an empty structure:

```
HEAD <-> TAIL
```

Operation 1: `inc("a")`

The key is new, so create bucket `1`.

```
HEAD <-> [1: a] <-> TAIL
```

Operation 2: `inc("b")`

Bucket `1` already exists. Reuse it.

```
HEAD <-> [1: a, b] <-> TAIL
```

Operation 3: `inc("a")`

Move `a` from bucket `1` to bucket `2`.

```
HEAD <-> [1: b] <-> [2: a] <-> TAIL
```

Operation 4: `inc("c")`

`c` is new. Reuse bucket `1`.

```
HEAD <-> [1: b, c] <-> [2: a] <-> TAIL
```

Operation 5: `inc("c")`

Move `c` from `1` to `2`. Bucket `2` already exists.

```
HEAD <-> [1: b] <-> [2: a, c] <-> TAIL
```

Operation 6: `inc("c")`

Move `c` from `2` to `3`. Create a new bucket.

```
HEAD <-> [1: b] <-> [2: a] <-> [3: c] <-> TAIL
```

Operation 7: `dec("c")`

Move `c` from `3` to `2`. Reuse bucket `2`. Bucket `3` becomes empty, so remove it.

```
HEAD <-> [1: b] <-> [2: a, c] <-> TAIL
```

Operation 8: `dec("a")`

Move `a` from `2` to `1`. Reuse bucket `1`.

```
HEAD <-> [1: a, b, c] <-> [2: c] <-> TAIL
```

Correction to the trace: after operation 7, `c` is in bucket `2` with `a`. Therefore, operation 8 moves `a` to bucket `1`, leaving `c` in bucket `2`. The resulting structure is:

```
HEAD <-> [1: a, b] <-> [2: c] <-> TAIL
```

Operation 9: `dec("a")`

`a` moves from frequency `1` to `0`, so remove it entirely. Bucket `1` still contains `b`, so it remains.

```
HEAD <-> [1: b] <-> [2: c] <-> TAIL
```

The final result is:

```
a -> absent
b -> 1
c -> 2

getMinKey() -> "b"
getMaxKey() -> "c"
```

The lesson from this trace is to follow four actions carefully for every move:

1. Find the current bucket.
2. Find or create the destination bucket.
3. Move the key and update the hash map.
4. Remove the source bucket if it becomes empty.

Keeping this sequence consistent prevents most implementation bugs.

## 10. Your reusable problem-solving checklist

When you encounter a new data-structure design problem, use this sequence.

Step 1: List every operation and its required complexity.

For AllOne, all four operations need average \\(O(1)\\).

Step 2: Start with the simplest correct structure.

A hash map stores the frequencies, but minimum and maximum queries require scanning.

Step 3: Identify what the slow operations need.

Minimum and maximum queries need the frequencies to be ordered.

Step 4: Ask whether maintaining that order can be cheaper than rebuilding it.

A sorted map costs \\(O(\log n)\\). Maintaining separate min/max variables creates difficult invalidation cases.

Step 5: Look for a property that makes updates local.

The frequency changes by exactly one. Therefore, the destination bucket is adjacent.

Step 6: Combine structures.

Use a hash map for direct access and a doubly linked list for ordered buckets.

Step 7: Write invariants before writing code.

This makes the edge cases easier to derive and helps you decide when to create, reuse, or remove buckets.

Step 8: Test the boundaries of every operation.

Test absent versus present keys, frequency `1` versus larger frequencies, existing versus missing destination buckets, and empty versus nonempty source buckets.

The deeper takeaway is this: the optimal solution comes from discovering that frequency updates are local, not from memorizing that AllOne uses a doubly linked list. Once you notice the local-update property, the hash map and neighboring buckets follow naturally.
