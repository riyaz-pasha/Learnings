# LeetCode 352 — Data Stream as Disjoint Intervals

The key to this problem is to maintain a sorted collection of non-overlapping intervals instead of storing every number and rebuilding the intervals each time.

The most important idea is that when a new number arrives, it can do only four things:

1. Create a new interval.
2. Extend an existing interval on its left.
3. Extend an existing interval on its right.
4. Merge two existing intervals into one.

Once you understand these four cases, the implementation becomes much easier.

## 0. Simplify the problem statement

Imagine numbers arriving one at a time:

```
addNum(1)
addNum(3)
addNum(7)
addNum(2)
addNum(6)
```

We need to summarize all distinct numbers seen so far as sorted, disjoint intervals.

An interval `[start, end]` represents every integer from `start` through `end`, inclusive.

For example, the numbers

```
1, 2, 3, 6, 7
```

can be represented as:

```
[1, 3], [6, 7]
```

Why?

- `[1, 3]` represents `1, 2, 3`.
- `[6, 7]` represents `6, 7`.
- There is a gap between `3` and `6`, so the intervals must remain separate.
- The intervals are sorted by their starting values.

Our class must implement:

- `addNum(value)`: Add a number, updating the intervals as necessary.
- `getIntervals()`: Return the current intervals in sorted order.

Important: Duplicate numbers do not create duplicate entries or change the summary.

## 1. Clarifying questions to ask the interviewer

These questions help establish which optimizations and data structures are appropriate.

1. Can the same number arrive more than once? The problem's data stream can contain duplicates. We should ensure adding an existing number changes nothing.
2. Must intervals be sorted and non-overlapping? Yes. This lets us maintain a canonical representation where each interval is maximal: adjacent consecutive numbers belong to the same interval.
3. Are the values bounded? Yes, `0 <= value <= 10^4`. This makes a boolean-array solution possible, although it is not necessarily the best general-purpose design.
4. How often is `getIntervals()` called compared with `addNum()`? This matters because we can choose to spend more time maintaining intervals during insertion or rebuilding the answer during retrieval.
5. What does the follow-up mean by lots of merges and relatively few intervals? It suggests maintaining only the intervals and locating the affected interval efficiently, rather than repeatedly processing every individual number.

## 2. Core intuition: Think in terms of interval boundaries

Suppose our current intervals are:

```
[1, 3]    [7, 7]
```

Now a new number arrives.

The only thing that matters is how that number relates to the interval immediately to its left and the interval immediately to its right.

For an existing interval `[start, end]` and new value `x`:

- The number is already covered if `start <= x <= end`.
- It can connect to the left interval if that interval ends at `x - 1`.
- It can connect to the right interval if that interval starts at `x + 1`.
- If both connections exist, the new number bridges the two intervals.

### Visualize the four cases

Case 1 — Create a new interval

```
Before: [1, 3]       [7, 7]
Add:         5
After:  [1, 3] [5, 5] [7, 7]
```

Neither neighbor is consecutive to `5`.

Case 2 — Extend the left interval

```
Before: [1, 3]       [7, 7]
Add:           4
After:  [1, 4]       [7, 7]
```

Since `3 = 4 - 1`, extend the interval ending at `3`.

Case 3 — Extend the right interval

```
Before: [1, 3]       [7, 7]
Add:               6
After:  [1, 3]       [6, 7]
```

Since `7 = 6 + 1`, move the right interval's start to `6`.

Case 4 — Merge two intervals

```
Before: [1, 3]       [5, 7]
Add:           4
After:  [1, 7]
```

The new number bridges the gap. The left interval ends at `3`, and the right interval starts at `5`. Adding `4` makes them one continuous interval.

There is also one additional check: if the number is already contained in an interval, do nothing.

### The most useful mental model

Think of every interval as a connected block of consecutive integers.

When a new number arrives, it can:

- connect to zero blocks,
- connect to one block, or
- connect two blocks together.

It cannot require merging three separate blocks at once, because the existing intervals are already disjoint and sorted.

## 3. Walk through the example step by step

Let's trace the actual input:

```
addNum(1)
addNum(3)
addNum(7)
addNum(2)
addNum(6)
```

| Operation   | Reasoning                                         | Current intervals     |
| ----------- | ------------------------------------------------- | --------------------- |
| `addNum(1)` | No intervals exist; create `[1,1]`.               | `[[1,1]]`             |
| `addNum(3)` | `3` is not consecutive to `1`.                    | `[[1,1],[3,3]]`       |
| `addNum(7)` | `7` is separate from both intervals.              | `[[1,1],[3,3],[7,7]]` |
| `addNum(2)` | `2` connects `[1,1]` and `[3,3]`.                 | `[[1,3],[7,7]]`       |
| `addNum(6)` | `6` is immediately before `7`, so extend `[7,7]`. | `[[1,3],[6,7]]`       |

The most interesting operation is `addNum(2)`.

Before insertion:

```
1       3           7
[1,1]   [3,3]       [7,7]
```

Adding `2` creates a connection between the first two intervals:

```
1 - 2 - 3            7
[------1,3------]   [7,7]
```

We replace `[1,1]` and `[3,3]` with `[1,3]`.

Notice that we never need to store the individual values `1`, `2`, and `3` separately in the interval-based solution. The interval `[1,3]` already represents all of them.

## 4. Edge cases to watch out for

These are the cases I would explicitly test during an interview.

| Case                      | Example                         | Expected behavior                 |
| ------------------------- | ------------------------------- | --------------------------------- |
| Empty stream              | No insertions                   | Return an empty array             |
| Duplicate                 | `[1,3]`, add `2`                | No change                         |
| Isolated value            | `[1,1]`, add `5`                | Create `[5,5]`                    |
| Extend left interval      | `[1,3]`, add `4`                | Become `[1,4]`                    |
| Extend right interval     | `[5,7]`, add `4`                | Become `[4,7]`                    |
| Merge both sides          | `[1,2]`, `[4,6]`, add `3`       | Become `[1,6]`                    |
| Insert smaller value      | `[5,8]`, add `1`                | Become `[1,1]`, `[5,8]`           |
| Insert larger value       | `[1,3]`, add `10`               | Become `[1,3]`, `[10,10]`         |
| Boundary value zero       | Empty stream, add `0`           | Become `[0,0]`                    |
| Repeated bridge insertion | `[1,2]`, `[4,5]`, add `3` twice | First merges; second does nothing |

Common bug: Forgetting the case where a number bridges two intervals. Extending only one side produces incorrect answers.

Another common bug is treating intervals as half-open ranges. This problem uses inclusive intervals `[start, end]`, so `[1,3]` includes `3`.

## 5. Solution 1 — Brute force: Store all numbers and rebuild on every query

The simplest approach is to store every distinct number in a sorted set. Whenever `getIntervals()` is called, walk through the sorted numbers and combine consecutive values.

This is a useful baseline because it separates the two tasks:

- Store the numbers.
- Construct intervals when requested.

```
import java.util.ArrayList;
import java.util.List;
import java.util.TreeSet;

class SummaryRangesBruteForce {

    // TreeSet maintains unique numbers in ascending order.
    // This automatically handles duplicate insertions.
    private final TreeSet<Integer> numbers = new TreeSet<>();

    public void addNum(int value) {
        // O(log n): insert the number into a balanced search tree.
        // Adding a duplicate has no effect.
        numbers.add(value);
    }

    public int[][] getIntervals() {
        // Every query rebuilds the complete interval summary.
        List<int[]> intervals = new ArrayList<>();

        for (int value : numbers) {
            // The first number always starts the first interval.
            if (intervals.isEmpty()) {
                intervals.add(new int[]{value, value});
                continue;
            }

            int[] last = intervals.get(intervals.size() - 1);

            // If value is consecutive to the last interval's end,
            // extend that interval instead of creating a new one.
            if (value == last[1] + 1) {
                last[1] = value;
            } else {
                // A gap exists, so this number starts another interval.
                intervals.add(new int[]{value, value});
            }
        }

        // Convert the list to the required return type.
        return intervals.toArray(int[][]::new);
    }
}

/*
COMPLEXITY
Let:
    n = number of distinct values received so far
    k = number of disjoint intervals in the result

addNum(value):
    Time:  O(log n), because TreeSet insertion takes O(log n).
    Space: O(n), because every distinct value is stored.

getIntervals():
    Time:  O(n), because we traverse all distinct values in sorted order.
    Space: O(k) for the temporary interval list and O(k) for the result.

WHY THIS IS NOT THE BEST DESIGN:
    Even if there are only two intervals representing thousands of values,
    every getIntervals() call still examines every distinct number.

    The follow-up specifically hints that the number of intervals may
    be much smaller than the number of values. We should exploit that.
*/
```

### What this solution teaches us

Suppose the stream contains every number from `1` through `10,000`.

The interval summary is simply:

```
[1, 10000]
```

Yet `getIntervals()` still visits all 10,000 values.

This motivates storing the summary itself rather than storing every individual number.

## 6. Solution 2 — Boolean array (exploit the bounded input range)

The constraints say:

```
0 <= value <= 10^4
```

That means we can create an array of size `10,001`, where `seen[x]` tells us whether `x` has arrived.

When a number arrives, mark it as present. When asked for intervals, scan the array from left to right and combine consecutive present values.

This solution is simple and can be excellent when the value range is small and fixed.

```
import java.util.ArrayList;
import java.util.List;

class SummaryRangesBooleanArray {

    // Values range from 0 through 10,000, inclusive.
    // seen[x] == true means x has appeared in the stream.
    private static final int MAX_VALUE = 10_000;
    private final boolean[] seen = new boolean[MAX_VALUE + 1];

    public void addNum(int value) {
        // O(1): mark the value as present.
        // Repeated insertions are harmless because true stays true.
        seen[value] = true;
    }

    public int[][] getIntervals() {
        List<int[]> intervals = new ArrayList<>();

        int value = 0;

        while (value <= MAX_VALUE) {

            // Skip missing values: they represent gaps between intervals.
            if (!seen[value]) {
                value++;
                continue;
            }

            // The first present value is the beginning of an interval.
            int start = value;

            // Consume all consecutive present values.
            // Stop at the first missing value or the end of the array.
            while (value <= MAX_VALUE && seen[value]) {
                value++;
            }

            // value is now the first missing number after the interval,
            // so the inclusive end of the interval is value - 1.
            intervals.add(new int[]{start, value - 1});
        }

        return intervals.toArray(int[][]::new);
    }
}

/*
COMPLEXITY
Let:
    U = size of the value universe = 10,001
    k = number of disjoint intervals

addNum(value):
    Time:  O(1).
    Space: O(1) additional space per call; the fixed boolean array already
           occupies O(U) space.

getIntervals():
    Time:  O(U), because we may scan the entire array.
    Space: O(k) for the temporary list and returned intervals.

Overall storage:
    O(U), independent of the number of repeated insertions.

ADVANTAGES:
    - Very simple.
    - Constant-time insertion.
    - Duplicate handling is automatic.

DISADVANTAGES:
    - Requires a known, reasonably small value range.
    - Even when only a few intervals exist, getIntervals() may scan all U
      possible values.
    - It does not exploit a sparse value range with very few actual values.

INTERVIEW TAKEAWAY:
    A bounded universe makes direct addressing possible. Always check
    whether the constraints allow an array-based design before choosing
    a more complicated data structure.
*/
```

## 7. Solution 3 — Optimal general-purpose design: TreeMap of intervals

This is the solution I would focus on for the interview, especially because of the follow-up.

### The key change in thinking

Instead of storing every number, store only interval boundaries in a `TreeMap`.

Each entry means:

```
key   = interval start
value = interval end
```

For example:

```
TreeMap:
    1 -> 3
    7 -> 7
    12 -> 15
```

Represents:

```
[1, 3], [7, 7], [12, 15]
```

The `TreeMap` keeps interval starts sorted and supports efficient searches for neighboring intervals.

### Why do we need `floorEntry()` and `ceilingEntry()`?

Suppose we are adding `4` to:

```
[1, 3]     [7, 9]     [12, 15]
```

We don't need to examine every interval.

We need only:

- `floorEntry(4)`: the interval with the greatest start that is less than or equal to `4`. Here, it is `[1,3]`.
- `ceilingEntry(4)`: the interval with the smallest start greater than or equal to `4`. Here, it is `[7,9]`.

These two intervals are the only ones that could be affected by inserting `4`.

If `4` is already inside the floor interval, we do nothing. Otherwise, we compare its distance from the two boundaries.

### A decision table for insertion

Let:

- `L` be the interval immediately to the left, with end `L.end`.
- `R` be the interval immediately to the right, with start `R.start`.
- `x` be the incoming number.

| Condition                               | Action                                            |
| --------------------------------------- | ------------------------------------------------- |
| `L.end >= x`                            | `x` already exists inside an interval; do nothing |
| `L.end == x - 1` and `R.start == x + 1` | Merge `L` and `R`                                 |
| `L.end == x - 1` only                   | Extend `L` to end at `x`                          |
| `R.start == x + 1` only                 | Move `R`'s start back to `x`                      |
| Neither side is consecutive             | Create `[x,x]`                                    |

If either neighboring interval does not exist, treat that side as unavailable.

### Walk through the merge case

Initially:

```
TreeMap:
1 -> 2
4 -> 6
```

This represents:

```
[1,2]      [4,6]
```

Now call `addNum(3)`.

Step 1: Find the neighboring intervals.

```
L = [1,2]
R = [4,6]
x = 3
```

Step 2: Check the left connection.

```
L.end == x - 1
2 == 3 - 1  // true
```

Step 3: Check the right connection.

```
R.start == x + 1
4 == 3 + 1  // true
```

Step 4: Merge both intervals.

```
New interval = [L.start, R.end]
             = [1, 6]
```

Update the map:

```
Before:
1 -> 2
4 -> 6

After:
1 -> 6
```

Notice the subtle but important operation: we keep the left interval's start, extend its end to the right interval's end, and remove the right interval's entry.

### Complete Java 24 implementation

```
import java.util.Map;
import java.util.TreeMap;

class SummaryRanges {

    /*
     * Each map entry represents exactly one maximal interval:
     *
     *     key   = inclusive interval start
     *     value = inclusive interval end
     *
     * Example:
     *     1 -> 3
     *     7 -> 9
     *
     * represents [1, 3] and [7, 9].
     *
     * TreeMap keeps keys sorted and supports floorEntry() and
     * ceilingEntry() in O(log k), where k is the number of intervals.
     *
     * INVARIANT:
     *   1. Every interval contains only values seen so far.
     *   2. Intervals are sorted by start.
     *   3. Intervals do not overlap.
     *   4. Intervals are not adjacent: if one ends at e, the next
     *      interval must start strictly greater than e + 1.
     *
     * The fourth property means every interval is already as large
     * as possible. Adjacent intervals should always have been merged.
     */
    private final TreeMap<Integer, Integer> intervals = new TreeMap<>();

    public SummaryRanges() {
        // TreeMap starts empty, so the stream initially has no intervals.
    }

    public void addNum(int value) {

        /*
         * STEP 1: Find the closest interval starting at or before value.
         *
         * floorEntry(value) returns the entry with the greatest key
         * that is <= value.
         *
         * This is the only interval that could already contain value
         * or connect to value from the left.
         */
        Map.Entry<Integer, Integer> left =
                intervals.floorEntry(value);

        /*
         * STEP 2: Handle duplicates.
         *
         * Because left.start <= value, if left.end >= value, then:
         *
         *     left.start <= value <= left.end
         *
         * Therefore, value is already represented in the summary.
         *
         * We must return immediately. Otherwise, we might create
         * duplicate or overlapping intervals.
         */
        if (left != null && left.getValue() >= value) {
            return;
        }

        /*
         * STEP 3: Find the closest interval starting at or after value.
         *
         * Since the duplicate case has already returned, a ceiling
         * entry, if present, starts strictly after value.
         *
         * This is the only interval that could connect from the right.
         */
        Map.Entry<Integer, Integer> right =
                intervals.ceilingEntry(value);

        /*
         * STEP 4: Determine whether value touches either neighbor.
         *
         * Left connection:
         *     The left interval ends at value - 1.
         *
         * Right connection:
         *     The right interval starts at value + 1.
         *
         * Given the problem's bound (value <= 10,000), value + 1
         * cannot overflow an int.
         */
        boolean joinsLeft =
                left != null && left.getValue() == value - 1;

        boolean joinsRight =
                right != null && right.getKey() == value + 1;

        if (joinsLeft && joinsRight) {

            /*
             * CASE 1: BRIDGE BOTH INTERVALS.
             *
             * Before:
             *     left.start -> value - 1
             *     value + 1  -> right.end
             *
             * After:
             *     left.start -> right.end
             *
             * Keep the left interval's start and extend its end
             * across value to the end of the right interval.
             *
             * Remove the right interval because it is now part of
             * the merged interval.
             */
            int mergedStart = left.getKey();
            int mergedEnd = right.getValue();
            int rightStart = right.getKey();

            intervals.put(mergedStart, mergedEnd);
            intervals.remove(rightStart);

        } else if (joinsLeft) {

            /*
             * CASE 2: EXTEND THE LEFT INTERVAL.
             *
             * Example:
             *     [1, 3] + 4 -> [1, 4]
             *
             * The start remains unchanged; only the end moves.
             *
             * The existing left entry is mutable through put().
             * No new interval is required.
             */
            intervals.put(left.getKey(), value);

        } else if (joinsRight) {

            /*
             * CASE 3: EXTEND THE RIGHT INTERVAL.
             *
             * Example:
             *     [5, 7] + 4 -> [4, 7]
             *
             * This case is slightly trickier:
             *
             * The map is keyed by interval START, and that start
             * changes from 5 to 4.
             *
             * Therefore, we must remove the old key and insert
             * the interval again with the new start.
             */
            int oldStart = right.getKey();
            int oldEnd = right.getValue();

            intervals.remove(oldStart);
            intervals.put(value, oldEnd);

        } else {

            /*
             * CASE 4: CREATE A NEW SINGLETON INTERVAL.
             *
             * Neither neighboring interval is consecutive to value.
             *
             * Example:
             *     [1, 3], [7, 9] + 5
             *       -> [1, 3], [5, 5], [7, 9]
             *
             * A new number that is not adjacent to either interval
             * must be represented by its own interval [value, value].
             */
            intervals.put(value, value);
        }
    }

    public int[][] getIntervals() {

        /*
         * TreeMap iterates in ascending key order, which is exactly
         * the order required by the problem.
         *
         * We return a fresh array instead of exposing the internal map.
         * Callers can modify the returned arrays without corrupting
         * the internal interval structure.
         */
        int[][] result = new int[intervals.size()][2];

        int index = 0;

        for (Map.Entry<Integer, Integer> interval
                : intervals.entrySet()) {

            result[index][0] = interval.getKey();
            result[index][1] = interval.getValue();
            index++;
        }

        return result;
    }
}

/*
COMPLEXITY
Let:
    k = number of currently disjoint intervals
    n = number of distinct values received so far

addNum(value):
    Time: O(log k).
        - floorEntry() costs O(log k).
        - ceilingEntry() costs O(log k).
        - Each put() or remove() costs O(log k).
        - There are only a constant number of tree operations.
        Therefore, the total remains O(log k).
        For an empty map, insertion is O(1); O(log(k + 1)) is a
        convenient unified bound.

    Auxiliary space: O(1) per operation, excluding the stored map.
    Persistent space: O(k), because only the disjoint intervals
                      are stored.

getIntervals():
    Time: O(k), because every interval must be copied into the result.
    Auxiliary space: O(1) beyond the returned array and its contents.
    Output space: O(k).

TOTAL PERSISTENT SPACE: O(k), rather than O(n).

WHY THIS IS THE BEST GENERAL-PURPOSE APPROACH:
    - We store the summary rather than every number.
    - Insertions locate relevant neighbors in logarithmic time.
    - Duplicate values do not alter the map.
    - The returned intervals are already sorted.
    - If thousands of values collapse into one interval, we store
      just one map entry.

FOLLOW-UP BENEFIT:
    When k is much smaller than n, the memory savings are substantial.
    This is exactly the situation described by the problem's follow-up.
*/
```

## 8. Compare all approaches

Let:

- \\(n\\) = number of distinct values received.
- \\(k\\) = number of disjoint intervals.
- \\(U\\) = size of the allowed value universe.

| Approach                  | `addNum`        | `getIntervals` | Persistent space | Best use case                        |
| ------------------------- | --------------- | -------------- | ---------------- | ------------------------------------ |
| Store values in `TreeSet` | \\(O(\log n)\\) | \\(O(n)\\)     | \\(O(n)\\)       | Simple baseline                      |
| Boolean array             | \\(O(1)\\)      | \\(O(U)\\)     | \\(O(U)\\)       | Small, fixed value range             |
| `TreeMap` of intervals    | \\(O(\log k)\\) | \\(O(k)\\)     | \\(O(k)\\)       | General-purpose interval maintenance |

The `TreeMap` approach is the strongest general-purpose answer, while the boolean array can be attractive under these particular constraints.

One nuance: the `TreeSet` solution above already uses a sorted set, so its insertion is logarithmic rather than linear. A truly naive solution that stores values in an unsorted list and sorts them on each query would take \\(O(n\log n)\\) per query.

## 9. Follow-up questions an interviewer might ask

### Q1. Why use a `TreeMap` instead of a `HashMap`?

A `HashMap` does not maintain keys in sorted order and cannot efficiently find the nearest interval start on either side of a value.

We need predecessor and successor searches:

```
intervals.floorEntry(value);
intervals.ceilingEntry(value);
```

`TreeMap` provides both in \\(O(\log k)\\) time.

### Q2. Why does `getIntervals()` take \\(O(k)\\) time even though the map is sorted?

Sorting is not the expensive part because the map is already sorted. However, we must still construct an output containing \\(k\\) intervals.

Writing \\(k\\) intervals alone requires \\(\Omega(k)\\) time. Therefore, \\(O(k)\\) is optimal for producing a fresh array of the required size.

### Q3. Can `addNum()` be \\(O(1)\\)?

Under the bounded input constraints, yes: the boolean-array solution inserts in \\(O(1)\\).

For a general-purpose dynamic interval structure using a balanced search tree, insertion takes \\(O(\log k)\\) because the algorithm must locate the neighboring intervals and update the ordered map.

### Q4. What if the number of intervals is tiny compared with the number of values?

That is precisely where the `TreeMap` approach shines.

Imagine the stream contains all integers from `0` through `10,000`.

```
Number of distinct values: 10,001
Number of intervals:       1

TreeMap:
0 -> 10000
```

The interval-based structure stores only one entry. Inserting another value already inside that interval requires just a neighbor lookup and an early return.

### Q5. Why not use a `TreeMap` keyed by interval end instead?

You could design a similar solution using interval ends as keys. However, the start-keyed representation makes it natural to locate the interval immediately before or after the incoming value using `floorEntry()` and `ceilingEntry()`.

Either design can work, but consistency is essential: the key must represent the same boundary throughout insertion, merging, and retrieval.

### Q6. What if we also need to remove a number?

Removal is more complicated because deleting a value from the middle of an interval may split it into two intervals.

For example:

```
Before removing 4:
[1, 7]

Remove 4:

After:
[1, 3], [5, 7]
```

If the value is at an endpoint, we shorten the interval. If it is a singleton interval, we remove it. If it is in the middle, we split the interval into two entries.

With a `TreeMap`, locating the containing interval is \\(O(\log k)\\), and the necessary updates take \\(O(\log k)\\).

### Q7. What is the single most important invariant to maintain?

Every map entry must represent one maximal interval of consecutive values.

That means:

- No duplicate values.
- No overlapping intervals.
- No adjacent intervals that should have been merged.
- Intervals remain sorted by their starts.

If this invariant holds after every `addNum()`, `getIntervals()` becomes straightforward: iterate over the map and copy each start and end into the result.

## 10. Final interview mental model

When solving this problem, follow this reasoning chain:

```
We receive numbers incrementally.
          |
          v
Rebuilding the answer from every number is wasteful.
          |
          v
Store only disjoint intervals.
          |
          v
For each incoming number, locate its left and right neighbors.
          |
          v
Check whether it is already present.
          |
          v
Connect to zero, one, or two neighboring intervals.
          |
          v
Maintain maximal, sorted, disjoint intervals.
```

The key interview insight is not simply choosing `TreeMap`. It is recognizing that the state of the problem is the set of disjoint intervals, not the set of individual numbers.

Once the data structure represents the right abstraction, both the algorithm and the complexity become much easier to reason about.

# LeetCode 352 — Data Stream as Disjoint Intervals

## Two designs: Faster insertion vs. faster retrieval

There are two useful ways to design `SummaryRanges`, depending on which operation we want to optimize:

1. Faster insertion: Maintain the intervals as numbers arrive, using a `TreeMap`. Each insertion takes \\(O(\log k)\\), and retrieval takes \\(O(k)\\).
2. Faster retrieval: Store incoming numbers in a boolean array and maintain the interval summary incrementally, or use a boolean array and rebuild the summary when queried. The best choice depends on whether we optimize retrieval latency or insertion latency.

Let's make the trade-off precise before looking at the implementations.

## 1. Understand what we are optimizing

Let:

- \\(n\\) = number of distinct values received.
- \\(k\\) = number of disjoint intervals.
- \\(U = 10{,}001\\) = size of the allowed universe (`0` through `10,000`).

Consider this stream:

```
addNum(1)
addNum(2)
addNum(3)
...
addNum(10000)
```

The summary is just:

```
[1, 10000]
```

Although 10,000 distinct values have arrived, only one interval is needed.

We can choose to maintain this interval continuously, or postpone some of the work until `getIntervals()` is called.

## 2. Design A — Faster insertion with `TreeMap`

This design maintains the interval summary immediately after each insertion.

```
Incoming number
      |
      v
Find neighboring intervals
      |
      v
Already present? ---- yes ---> Do nothing
      |
      no
      v
Connect to left? Connect to right?
      |
      v
Create / extend / merge
      |
      v
Updated TreeMap
```

### Why it works

The map stores only interval boundaries:

```
1 -> 3
7 -> 9
12 -> 15
```

means:

```
[1,3], [7,9], [12,15]
```

When inserting `10`, the only relevant neighbors are `[7,9]` and `[12,15]`. We extend the left interval:

```
[7,10], [12,15]
```

When inserting `11`, we bridge them:

```
[7,15]
```

We do not need to visit all numbers or all intervals. The ordered map finds the relevant neighbors in logarithmic time.

### Java implementation — insertion-optimized version

```
import java.util.Map;
import java.util.TreeMap;

class SummaryRangesFastInsert {

    /*
     * Store only disjoint intervals.
     *
     * key   = inclusive start of an interval
     * value = inclusive end of an interval
     *
     * Example:
     *   1 -> 3
     *   7 -> 9
     *
     * represents [1,3], [7,9].
     *
     * Why TreeMap?
     *   floorEntry(x) finds the interval starting at or immediately
     *   before x.
     *
     *   ceilingEntry(x) finds the interval starting at or immediately
     *   after x.
     *
     *   These searches take O(log k), where k is the number of intervals.
     *
     * INVARIANT:
     *   All intervals are sorted, disjoint, and non-adjacent.
     *   Adjacent intervals must always be merged.
     */
    private final TreeMap<Integer, Integer> intervals = new TreeMap<>();

    public void addNum(int value) {

        // Find the interval that could contain value or connect from left.
        var left = intervals.floorEntry(value);

        // If value is already covered, the summary does not change.
        if (left != null && left.getValue() >= value) {
            return;
        }

        // Find the next interval to the right, if one exists.
        var right = intervals.ceilingEntry(value);

        // Does the incoming value connect to either interval?
        boolean joinsLeft =
                left != null && left.getValue() == value - 1;

        boolean joinsRight =
                right != null && right.getKey() == value + 1;

        if (joinsLeft && joinsRight) {

            // BRIDGE:
            // [left.start, value - 1] + value + [value + 1, right.end]
            // becomes [left.start, right.end].
            //
            // Keep the left key, extend its end, and delete the right key.
            intervals.put(left.getKey(), right.getValue());
            intervals.remove(right.getKey());

        } else if (joinsLeft) {

            // EXTEND LEFT:
            // [1,3] + 4 -> [1,4].
            // The start/key does not change.
            intervals.put(left.getKey(), value);

        } else if (joinsRight) {

            // EXTEND RIGHT:
            // [5,7] + 4 -> [4,7].
            //
            // The key is the interval start, so the old entry must
            // be removed before inserting the interval with its new key.
            int oldEnd = right.getValue();

            intervals.remove(right.getKey());
            intervals.put(value, oldEnd);

        } else {

            // ISOLATED VALUE:
            // Neither neighbor is consecutive, so create [value,value].
            intervals.put(value, value);
        }
    }

    public int[][] getIntervals() {

        // Every map entry is already one complete interval.
        // TreeMap iteration is sorted by interval start.
        int[][] result = new int[intervals.size()][2];

        int i = 0;

        for (var entry : intervals.entrySet()) {
            result[i][0] = entry.getKey();
            result[i][1] = entry.getValue();
            i++;
        }

        // Return a fresh array, so callers cannot corrupt internal state.
        return result;
    }
}

/*
 * COMPLEXITY
 *
 * addNum(value):
 *   O(log(k + 1)) time.
 *   We perform a constant number of balanced-tree lookups, insertions,
 *   and removals. The number of intervals is k.
 *
 * getIntervals():
 *   O(k) time to copy all intervals into the output array.
 *
 * Persistent space:
 *   O(k), because we store only the current disjoint intervals.
 *
 * Best when:
 *   - addNum() is called frequently.
 *   - The number of intervals is relatively small.
 *   - We need to keep the interval summary correct after every insertion.
 */
```

### Complexity summary

| Operation        | Complexity         |
| ---------------- | ------------------ |
| `addNum(value)`  | \\(O(\log(k+1))\\) |
| `getIntervals()` | \\(O(k)\\)         |
| Stored space     | \\(O(k)\\)         |

This is a strong choice when insertion is frequent, because we never scan all the intervals to find where a number belongs.

## 3. Design B — Faster retrieval with a sorted interval list

Now suppose `getIntervals()` is called frequently, and we want the simplest, fastest possible traversal of the interval summary.

Instead of a tree, maintain a sorted `ArrayList` of intervals.

```
[1,3]  [7,9]  [12,15]
   ^
   |
Sorted array-backed list
```

An array-backed list has good cache locality and low traversal overhead. We can use binary search to locate the insertion position in \\(O(\log k)\\), but inserting into the middle of an array-backed list can require shifting \\(O(k)\\) entries.

After finding the insertion position, we apply the same four cases: create, extend left, extend right, or merge.

The result is:

- `addNum()` takes \\(O(k)\\) worst-case time.
- `getIntervals()` takes \\(O(k)\\) time to return a fresh array.
- Stored space is \\(O(k)\\).

The advantage is that retrieval is a simple sequential traversal over a compact array-backed list, with no tree-entry traversal overhead.

### Java implementation — retrieval-optimized version

This version maintains the intervals in sorted order using an `ArrayList`. It also caches the most recently generated result so repeated `getIntervals()` calls can avoid rebuilding the snapshot.

There is one important API trade-off: returning the cached `int[][]` directly means callers must not mutate the returned array. Otherwise, they could corrupt the cached result. This implementation documents that contract explicitly.

```
import java.util.ArrayList;
import java.util.List;

class SummaryRangesFastRetrieve {

    /*
     * Each int[] is one interval: [start, end].
     *
     * The list is always sorted by start, and intervals are maximal:
     * no two intervals overlap or are adjacent.
     *
     * Why ArrayList?
     *   - Compact, array-backed storage.
     *   - Fast sequential traversal.
     *   - Low overhead when reading all intervals.
     *
     * Why not TreeMap?
     *   - We do not need tree-based predecessor/successor searches.
     *   - We can find the insertion position using binary search.
     *   - Insertion may shift O(k) elements, which is acceptable when
     *     retrieval is more important than insertion.
     */
    private final List<int[]> intervals = new ArrayList<>();

    /*
     * Cached output snapshot.
     *
     * null means the intervals changed since the last retrieval.
     * Otherwise, it contains the most recently generated int[][].
     *
     * Contract: callers must not modify the returned array or its rows.
     * This is necessary to make repeated retrieval truly O(1).
     */
    private int[][] cachedResult;

    public void addNum(int value) {

        int k = intervals.size();

        /*
         * Binary search for the last interval whose start <= value.
         *
         * This is an upper-bound search:
         * find the first index whose interval start is > value.
         *
         * Subtracting one gives the possible left interval.
         * The next index is the possible right interval.
         */
        int low = 0;
        int high = k;

        while (low < high) {
            int mid = low + (high - low) / 2;

            if (intervals.get(mid)[0] <= value) {
                low = mid + 1;
            } else {
                high = mid;
            }
        }

        int rightIndex = low;
        int leftIndex = rightIndex - 1;

        int[] left = leftIndex >= 0 ? intervals.get(leftIndex) : null;
        int[] right = rightIndex < k ? intervals.get(rightIndex) : null;

        /*
         * Duplicate check:
         * if value is inside the interval on its left, nothing changes.
         */
        if (left != null && left[1] >= value) {
            return;
        }

        boolean joinsLeft = left != null && left[1] == value - 1;
        boolean joinsRight = right != null && right[0] == value + 1;

        if (joinsLeft && joinsRight) {

            /*
             * BRIDGE TWO INTERVALS.
             *
             * Example:
             *   [1,2], [4,6] + 3 -> [1,6]
             *
             * Extend the left interval to the right interval's end,
             * then remove the right interval.
             *
             * Removing from an ArrayList shifts subsequent elements,
             * so this operation costs O(k) in the worst case.
             */
            left[1] = right[1];
            intervals.remove(rightIndex);

        } else if (joinsLeft) {

            /*
             * EXTEND LEFT:
             *   [1,3] + 4 -> [1,4]
             *
             * Only the existing interval's end changes.
             */
            left[1] = value;

        } else if (joinsRight) {

            /*
             * EXTEND RIGHT:
             *   [5,7] + 4 -> [4,7]
             *
             * The start changes, but the interval stays at rightIndex.
             * Its position remains correct because value was located
             * immediately before the old start.
             */
            right[0] = value;

        } else {

            /*
             * CREATE A SINGLETON:
             *   [1,3], [7,9] + 5 -> [1,3], [5,5], [7,9]
             *
             * Insert at rightIndex to preserve sorted order.
             * ArrayList may shift elements, so this costs O(k) worst case.
             */
            intervals.add(rightIndex, new int[]{value, value});
        }

        /*
         * The summary changed, so the old cached snapshot is stale.
         * Invalidate it. The next getIntervals() call will rebuild it.
         */
        cachedResult = null;
    }

    public int[][] getIntervals() {

        /*
         * CACHE HIT:
         * If no insertion has changed the summary since the previous
         * retrieval, reuse the existing snapshot.
         *
         * Returning the same reference is what makes this call O(1).
         * The caller must honor the no-mutation contract.
         */
        if (cachedResult != null) {
            return cachedResult;
        }

        /*
         * CACHE MISS:
         * Build a fresh snapshot in sorted order.
         *
         * This traversal is sequential over the ArrayList, which has
         * good locality and avoids traversing tree nodes.
         */
        cachedResult = new int[intervals.size()][2];

        for (int i = 0; i < intervals.size(); i++) {
            int[] interval = intervals.get(i);

            cachedResult[i][0] = interval[0];
            cachedResult[i][1] = interval[1];
        }

        return cachedResult;
    }
}

/*
 * COMPLEXITY
 *
 * Let k be the number of intervals.
 *
 * addNum(value):
 *   Binary search: O(log(k + 1)).
 *   Actual list insertion/removal: O(k) worst case because elements
 *   may need to shift.
 *   Overall: O(k) worst case.
 *
 * getIntervals():
 *   Cache miss: O(k) to construct the array.
 *   Cache hit:  O(1), because the cached array is returned directly.
 *
 * Persistent space:
 *   O(k) for intervals plus O(k) for the cached output.
 *
 * IMPORTANT API CAVEAT:
 *   The cached array and its rows are mutable.
 *   If callers modify the returned array, the cached result is corrupted.
 *   This implementation is suitable only when callers agree not to mutate
 *   the returned snapshot.
 *
 *   For a defensive API that always returns a fresh array, copy the
 *   cached snapshot before returning it. That makes every retrieval O(k)
 *   despite caching the snapshot internally.
 */
```

## 4. Compare the two designs

| Operation                                 | Fast-insert: `TreeMap` | Fast-retrieve: `ArrayList` + cache    |
| ----------------------------------------- | ---------------------- | ------------------------------------- |
| `addNum()`                                | \\(O(\log(k+1))\\)     | \\(O(k)\\) worst case                 |
| First `getIntervals()` after a change     | \\(O(k)\\)             | \\(O(k)\\)                            |
| Repeated `getIntervals()` without changes | \\(O(k)\\)             | \\(O(1)\\)                            |
| Persistent space                          | \\(O(k)\\)             | \\(O(k)\\) for intervals and cache    |
| Returned array safe to mutate             | Yes                    | No; shared cached result              |
| Best scenario                             | Frequent insertions    | Read-heavy workloads with stable data |

### One crucial distinction about retrieval speed

If `getIntervals()` must return a fresh, independently mutable `int[][]` every time, then no implementation can achieve better than \\(O(k)\\) retrieval time: the method must produce \\(k\\) interval pairs.

The cache provides genuine \\(O(1)\\) repeated retrieval only by returning the same array reference. If you need safe, independent results, return a defensive copy instead:

```
public int[][] getIntervals() {
    if (cachedResult == null) {
        cachedResult = new int[intervals.size()][2];

        for (int i = 0; i < intervals.size(); i++) {
            cachedResult[i] = intervals.get(i).clone();
        }
    }

    // Defensive copy: callers cannot modify our cached snapshot.
    return java.util.Arrays.stream(cachedResult)
            .map(int[]::clone)
            .toArray(int[][]::new);
}
```

With this safer version, rebuilding the cache after a change costs \\(O(k)\\), copying the cached result costs \\(O(k)\\), and repeated retrievals remain \\(O(k)\\) overall. The cache still avoids rebuilding the snapshot from the interval list, but it cannot eliminate the cost of producing an independent result.

## 5. Which would I choose in an interview?

- Choose `TreeMap` when you want efficient online updates, a clean invariant, and predictable \\(O(\log k)\\) insertion. This is my recommended general-purpose solution.
- Choose `ArrayList` with a cache when reads greatly outnumber writes and the API permits an immutable-by-contract shared snapshot.
- Choose a boolean array when the input range is small and fixed, especially when constant-time insertion matters more than scanning the full range on retrieval.

The main lesson is that the fastest design depends on the workload. For the standard LeetCode API, I would present the `TreeMap` solution first because it provides efficient insertion, sorted output, and safe retrieval without relying on callers to avoid modifying returned arrays.
