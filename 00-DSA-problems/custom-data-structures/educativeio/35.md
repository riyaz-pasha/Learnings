# LeetCode 631 — Design Excel Sum Formula

Difficulty: Hard Core concepts: Design a data structure, dependency graphs, graph traversal, dynamic updates, and memoization.

Problem: [631. Design Excel Sum Formula](https://leetcode.com/problems/excel-sum-formula/?utm_source=chatgpt.com)

The key to this problem is understanding that a cell containing a formula depends on other cells, and changing one cell can affect multiple dependent cells.

We'll build the intuition from a simple spreadsheet example, compare possible approaches, and then implement the solutions in modern Java.

## 0. Simplify the problem statement

Imagine a small Excel spreadsheet:

| Cell | Value       |
| ---- | ----------- |
| A1   | 2           |
| A2   | 3           |
| B1   | 5           |
| B2   | `=A1+A2+B1` |

The value of B2 is \\(2+3+5=10\\).

The problem asks us to design a class called `Excel` that supports three operations:

- `Excel(height, width)`: create an empty spreadsheet.
- `set(row, column, value)`: assign a number to a cell.
- `sum(row, column, numbers)`: assign a formula to a cell, where the formula adds the values of specified cells or ranges, and return the result.

For example:

```
excel.sum(2, 'B', new String[]{"A1", "A2", "B1"});
```

This sets B2 to the formula `A1 + A2 + B1`.

The important distinction is that `sum()` does not merely calculate a number once. It stores a formula that must continue to reflect changes to its referenced cells.

### What happens when a referenced cell changes?

Suppose we change A1 from 2 to 10.

B2 must now equal:

\\[ 10+3+5=18 \\]

We don't explicitly call `sum()` again for B2. The spreadsheet must preserve its formula and compute the correct result when B2 is queried or used by another formula.

## 1. Clarifying questions to ask the interviewer

These questions help uncover the behavior that determines the data structure.

1. Does a formula remain active after `sum()` returns? Yes. Otherwise, a later update to A1 would not change B2.
2. What happens when `set()` overwrites a formula cell? The old formula must be discarded. The cell becomes a plain numeric value.
3. Can formulas reference ranges, and are the boundaries inclusive? Yes. `A1:B2` includes A1, B1, A2, and B2.
4. Can the same cell appear multiple times in a formula? Yes. Each occurrence contributes independently. For example, `["A1", "A1"]` means \\(2 \times A1\\).
5. Can formulas reference themselves, directly or indirectly? No. The problem guarantees no circular references, so the dependency graph is acyclic.
6. Do we need to update dependent cells immediately, or can we calculate their values when requested? This is a useful design question. Both strategies work, but they have different performance trade-offs.

A formula creates relationships between cells.

### The two main implementation strategies

| Strategy          | `set()`                            | `get()`                           | Main idea                                    |
| ----------------- | ---------------------------------- | --------------------------------- | -------------------------------------------- |
| Brute force       | Store the number                   | Recalculate every formula cell    | Simple, but repeatedly does unnecessary work |
| Lazy evaluation   | Replace the cell's value/formula   | Recursively evaluate dependencies | Calculate only when needed                   |
| Eager propagation | Update the cell and its dependents | Return a cached value             | Propagate changes immediately                |

For an interview, start with the simplest correct model, then explain why dependency tracking improves it.

## 3. Solution 1 — Recursive evaluation (lazy evaluation)

### Mental model

Store either:

- A constant value, if `set()` was called on the cell.
- A formula describing the cells it references, if `sum()` was called.

When `get()` is called, recursively evaluate the formula using the latest values of its dependencies.

For example:

```
A1 = 2
B1 = A1 + 3
C1 = B1 + A1
```

Calling `get(C1)` evaluates:

```
C1 = B1 + A1
   = (A1 + 3) + A1
   = 2 + 3 + 2
   = 7
```

If A1 becomes 10, the next `get(C1)` returns 23 without explicitly updating B1 or C1.

### Java 24 implementation

```java
import java.util.*;

class Excel {
    // A coordinate is an immutable, type-safe representation of a cell.
    private record Cell(int row, int col) {}

    // A cell either has a constant value or a formula.
    private final int[][] values;
    private final Map<Cell, Map<Cell, Integer>> formulas = new HashMap<>();

    public Excel(int height, char width) {
        values = new int[height][width - 'A' + 1];
    }

    private Cell cell(int row, char column) {
        return new Cell(row - 1, column - 'A');
    }

    private Cell parse(String ref) {
        int col = ref.charAt(0) - 'A';
        int row = Integer.parseInt(ref.substring(1)) - 1;
        return new Cell(row, col);
    }

    // Expand "A1" or "A1:B2" into individual cell references.
    // A frequency map is essential: if A1 occurs twice, its weight is 2.
    private Map<Cell, Integer> expand(String[] numbers) {
        Map<Cell, Integer> dependencies = new HashMap<>();

        for (String number : numbers) {
            String[] ends = number.split(":");
            Cell start = parse(ends[0]);
            Cell end = ends.length == 1 ? start : parse(ends[1]);

            for (int r = start.row(); r <= end.row(); r++) {
                for (int c = start.col(); c <= end.col(); c++) {
                    dependencies.merge(new Cell(r, c), 1, Integer::sum);
                }
            }
        }
        return dependencies;
    }

    public void set(int row, char column, int val) {
        Cell target = cell(row, column);

        // Overwriting a formula replaces it permanently with a constant.
        formulas.remove(target);
        values[target.row()][target.col()] = val;
    }

    public int get(int row, char column) {
        // Do not return the cached matrix value for formula cells:
        // recursively evaluate the formula so that recent changes are visible.
        return evaluate(cell(row, column));
    }

    private int evaluate(Cell current) {
        Map<Cell, Integer> dependencies = formulas.get(current);

        // A cell without a formula is a leaf in the dependency graph.
        if (dependencies == null) {
            return values[current.row()][current.col()];
        }

        int total = 0;

        // Every dependency contributes its CURRENT value times its frequency.
        for (var entry : dependencies.entrySet()) {
            total += entry.getValue() * evaluate(entry.getKey());
        }

        return total;
    }

    public int sum(int row, char column, String[] numbers) {
        Cell target = cell(row, column);

        // Store the formula, not just the current sum.
        formulas.put(target, expand(numbers));

        // Return its current result. Future get() calls reevaluate it.
        return evaluate(target);
    }

    /*
     * Complexity:
     *
     * Let V = height * width, E = number of individual dependency entries
     * traversed during an evaluation, including repeated visits.
     *
     * Constructor: O(V) time and O(V) space for the value matrix.
     * set():       O(1) expected time; removes one formula entry.
     * sum():       O(R + E_eval) time, where R is the number of cells
     *              expanded from the specified ranges and E_eval is the
     *              work of recursively evaluating the new formula.
     * get():       O(E_eval) time, potentially with repeated evaluation of
     *              shared dependencies. In the worst case, repeated
     *              subcomputations can make evaluation exponential in
     *              dependency depth.
     * Space:       O(V + E) for values and stored formulas, plus O(D)
     *              recursive stack space for maximum dependency depth D.
     *
     * This is easy to implement and correct, but repeated get() calls can
     * recompute the same formulas. Memoization can reduce repeated work
     * within one evaluation, but it does not solve incremental updates
     * across calls unless invalidation is also implemented.
     */
}
```

### What makes this solution useful?

It establishes the essential representation: formulas are stored as dependencies, not as frozen results.

Its limitation is performance. Imagine 20 cells all depending on the same large formula tree. Repeated `get()` calls can recompute the same cells many times.

The next solution avoids that repeated work by caching values and propagating changes.

## 4. Solution 2 — Optimal practical approach: eager dependency propagation

For this problem's small sheet and limited number of operations, the most interview-friendly optimized design is to cache each cell's current value and propagate changes through the dependency graph.&#x20;

### Step 1: Store two kinds of information

For each cell, maintain:

1. `values[r][c]`: its current computed value.
2. `formulas[cell]`: the cells it depends on, with multiplicities.

Additionally, maintain a reverse dependency graph:

- `dependents[source]` lists the formula cells that depend on `source`.
- Each edge has a weight representing how many times the source contributes to the dependent.

Why do we need reverse dependencies? When A1 changes, we need to find the formulas that depend on A1 without scanning the entire spreadsheet.

### Step 2: Think in terms of a change, not a complete recalculation

Suppose:

```
A1 = 2
B1 = 3
C1 = A1 + A1 + B1 = 7
D1 = C1 + 5 = 12
```

Now `set(A1, 10)` changes A1 by:

\\[ \Delta = 10 - 2 = 8 \\]

Because C1 uses A1 twice:

\\[ \Delta C1 = 2 \times 8 = 16 \\]

Therefore C1 changes from 7 to 23. D1 depends on C1 once, so:

\\[ \Delta D1 = 1 \times 16 = 16 \\]

D1 changes from 12 to 28.

We can propagate these deltas through the graph, updating each affected formula cell's cached value.

```
A1: 2 -> 10      delta = +8
       |
       | weight 2
       v
C1:  7 -> 23     delta = +16
       |
       | weight 1
       v
D1: 12 -> 28     delta = +16
```

This is the central optimization: when a value changes, update only its downstream dependents.

### Step 3: Why formulas need reverse-edge cleanup

Suppose C1 previously contained `=A1+B1`, but then we call:

```
sum(1, 'C', new String[]{"D1"});
```

The old dependencies on A1 and B1 must be removed. Otherwise, a later update to A1 would incorrectly change C1, even though C1 now depends only on D1.

Likewise, when `set()` overwrites a formula, we must remove that formula's outgoing dependency edges before storing its constant value.

## Java 24 implementation

```java
import java.util.*;

class Excel {

    // A cell is represented by zero-based row and column indices.
    private record Cell(int row, int col) {}

    private final int[][] values;

    // formula[cell] = {referenced cell -> number of occurrences}.
    // Example: C1 = A1 + A1 + B1 means {A1 -> 2, B1 -> 1}.
    private final Map<Cell, Map<Cell, Integer>> formulas = new HashMap<>();

    // dependents[source] = {formula cell -> multiplicity}.
    // This reverse graph tells us which cells must change when source changes.
    private final Map<Cell, Map<Cell, Integer>> dependents = new HashMap<>();

    public Excel(int height, char width) {
        values = new int[height][width - 'A' + 1];
    }

    private Cell cell(int row, char column) {
        return new Cell(row - 1, column - 'A');
    }

    private Cell parse(String ref) {
        return new Cell(
            Integer.parseInt(ref.substring(1)) - 1,
            ref.charAt(0) - 'A'
        );
    }

    // Converts cell references and inclusive ranges into a weighted dependency
    // map. Overlapping ranges and duplicate references retain their multiplicity.
    private Map<Cell, Integer> expand(String[] numbers) {
        Map<Cell, Integer> result = new HashMap<>();

        for (String number : numbers) {
            String[] ends = number.split(":");
            Cell start = parse(ends[0]);
            Cell end = ends.length == 1 ? start : parse(ends[1]);

            for (int r = start.row(); r <= end.row(); r++) {
                for (int c = start.col(); c <= end.col(); c++) {
                    result.merge(new Cell(r, c), 1, Integer::sum);
                }
            }
        }

        return result;
    }

    // Remove the outgoing edges of a formula that is being overwritten.
    // The target may itself still have dependents; those edges must remain.
    private void removeOldFormula(Cell target) {
        Map<Cell, Integer> old = formulas.remove(target);
        if (old == null) {
            return;
        }

        for (Cell source : old.keySet()) {
            Map<Cell, Integer> reverse = dependents.get(source);
            reverse.remove(target);

            if (reverse.isEmpty()) {
                dependents.remove(source);
            }
        }
    }

    // Propagate a value change through all downstream formula cells.
    //
    // If source changes by delta and a dependent references it k times,
    // that dependent changes by k * delta. We update its cached value and
    // propagate that change further through the graph.
    //
    // No circular references are guaranteed, so recursion terminates.
    private void propagate(Cell source, int delta) {
        if (delta == 0) {
            return;
        }

        Map<Cell, Integer> next = dependents.get(source);
        if (next == null) {
            return;
        }

        // No dependency edges are modified during propagation, so iterating
        // over this map is safe.
        for (var edge : next.entrySet()) {
            Cell dependent = edge.getKey();
            int weight = edge.getValue();

            int change = delta * weight;
            values[dependent.row()][dependent.col()] += change;

            // A downstream formula must receive the dependent's change too.
            propagate(dependent, change);
        }
    }

    public void set(int row, char column, int val) {
        Cell target = cell(row, column);

        // Remember the old displayed value before replacing a formula.
        int oldValue = values[target.row()][target.col()];

        // A direct assignment permanently replaces this cell's formula.
        removeOldFormula(target);
        values[target.row()][target.col()] = val;

        // Only the difference matters to existing dependents.
        // They already contain contributions from oldValue.
        propagate(target, val - oldValue);
    }

    public int get(int row, char column) {
        // All cached values are kept current after every update.
        return values[row - 1][column - 'A'];
    }

    public int sum(int row, char column, String[] numbers) {
        Cell target = cell(row, column);
        int oldValue = values[target.row()][target.col()];

        // Remove old dependencies first: this call replaces any old formula.
        removeOldFormula(target);

        Map<Cell, Integer> newFormula = expand(numbers);
        formulas.put(target, newFormula);

        int newValue = 0;

        for (var entry : newFormula.entrySet()) {
            Cell source = entry.getKey();
            int weight = entry.getValue();

            // Register the reverse edge so future source changes reach target.
            dependents.computeIfAbsent(source, ignored -> new HashMap<>())
                      .put(target, weight);

            // Use cached source values to calculate the new formula result.
            newValue += values[source.row()][source.col()] * weight;
        }

        values[target.row()][target.col()] = newValue;

        // Changing the formula can change the target's displayed value.
        // Its own dependents must receive that difference.
        propagate(target, newValue - oldValue);

        return newValue;
    }

    /*
     * Complexity analysis:
     *
     * Let V = height * width.
     * Let E = total number of distinct dependency edges stored.
     * Let R = number of individual cells expanded by a sum formula.
     * Let A = number of downstream dependency-edge traversals during
     *         one propagation, counting repeated visits when paths converge.
     *
     * Constructor: O(V) time and O(V) space for the matrix.
     *
     * get(): O(1), because every cell's cached value is current.
     *
     * set(): O(1) expected time for the direct assignment and removal of
     *        the target's old outgoing edges, plus O(A) propagation work.
     *
     * sum(): O(R) to expand references, plus O(R) expected work to register
     *        edges, plus O(A) to propagate the resulting value change.
     *
     * Storage: O(V + E), covering the value matrix, formulas, and reverse
     *          dependency graph. Formula edges are stored in both directions,
     *          which changes only the constant factor.
     *
     * In a DAG, each downstream cell's cached value remains correct after
     * propagation. A shared downstream node may be visited more than once
     * when multiple paths lead to it, but each visit applies the correct
     * contribution from that path. Thus A can exceed V in a general DAG.
     *
     * For this problem, the grid is at most 26 x 26 and there are at most
     * 100 operations, so this design is comfortably efficient.
     */
}
```

## 5. Walk through the official example

Consider the sequence:

```
Excel excel = new Excel(3, 'C');

excel.set(1, 'A', 2);

excel.sum(3, 'C', new String[]{"A1", "A1:B2"});

excel.set(2, 'B', 2);

System.out.println(excel.get(3, 'C'));
```

### After `set(1, 'A', 2)`

```
A1 = 2
B1 = 0
A2 = 0
B2 = 0
C3 = 0
```

### After `sum(3, 'C', {"A1", "A1:B2"})`

The formula is:

```
C3 = A1 + A1 + B1 + A2 + B2
   = 2 + 2 + 0 + 0 + 0
   = 4
```

Notice that A1 appears twice because it is referenced directly and also included in the range.

The dependency graph records these weights:

```
A1 --(2)--> C3
B1 --(1)--> C3
A2 --(1)--> C3
B2 --(1)--> C3
```

### After `set(2, 'B', 2)`

B2 changes from 0 to 2:

```
delta = 2 - 0 = 2
```

B2 has one dependent, C3, with weight 1. So C3 increases by 2:

```
C3 = 4 + 2 = 6
```

The final `get(3, 'C')` returns 6.

## 6. Edge cases to watch out for

| Edge case                                | Expected behavior                                |
| ---------------------------------------- | ------------------------------------------------ |
| All cells initially zero                 | `get()` returns 0                                |
| Formula references a zero-valued cell    | That cell still needs a dependency edge          |
| Same cell occurs multiple times          | Count each occurrence                            |
| Ranges overlap                           | Count overlapping cells multiple times           |
| Formula cell is overwritten with `set()` | Remove its old formula                           |
| Formula is replaced by another formula   | Remove old dependencies and install new ones     |
| A formula depends on another formula     | Propagate changes through both levels            |
| Negative values                          | Delta propagation still works                    |
| A changed value has no dependents        | Update only that cell                            |
| Formula result does not change           | Propagation can stop immediately when delta is 0 |

One subtle point: do not remove a cell's incoming dependency edges when its value changes. Its dependents still need to know that the cell exists as a source. Only the formula edges describing what the overwritten cell itself depends on must be removed.

## 7. Interview follow-up questions and answers

### Q1. Why not simply store the formula's calculated value?

Because a calculated value is only correct for the input values that existed when the formula was evaluated. The formula must remain live.

### Q2. Why use a weighted graph instead of a simple set of dependencies?

Because formulas may reference the same cell multiple times. If C1 is `=A1+A1`, changing A1 by 3 must change C1 by 6. The edge therefore needs a multiplicity of 2.

### Q3. Why is the dependency graph a DAG?

The problem guarantees there are no circular references. Therefore, a formula cannot ultimately depend on itself, and dependency propagation terminates.

### Q4. Could we use a queue instead of recursion?

Yes. A queue can propagate deltas iteratively and avoids recursive stack depth. However, when multiple dependency paths converge on a node, the implementation must apply each incoming contribution correctly. For a more general graph, a topological traversal can aggregate changes before processing each node once.

### Q5. How could we avoid repeatedly visiting shared downstream nodes?

Use a topological order of the affected subgraph. Accumulate all incoming deltas first, then process each node after all its upstream changes have been accounted for. This can reduce propagation work toward \\(O(V+E)\\) for the affected subgraph.

### Q6. When would lazy evaluation be preferable?

Lazy evaluation is attractive when writes are frequent but reads are rare, or when only a small subset of formulas is ever queried. Eager propagation is attractive when reads are frequent and should be constant time.

### Q7. What if circular formulas were allowed?

We would need a policy for cycles, such as rejecting circular references or defining iterative calculation with convergence rules. The current problem avoids this complication entirely.

## 8. Final interview takeaway

The intended reasoning path is:

1. Recognize that formulas are persistent dependencies, not one-time sums.
2. Represent each cell as either a constant or a formula.
3. Use a graph to model formula relationships.
4. Choose lazy evaluation for a straightforward recursive solution, or eager propagation for fast reads.
5. Track edge multiplicities so repeated references remain correct.
6. When replacing a formula, remove its old dependencies.
7. When a value changes, propagate its delta through the reverse dependency graph.

The most important insight: a spreadsheet is a dynamic dependency graph. Once you recognize that, the problem becomes a familiar graph-design problem rather than a complicated matrix problem.
