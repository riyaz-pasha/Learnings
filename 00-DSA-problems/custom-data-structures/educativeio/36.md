# LeetCode 379 — Design Phone Directory

Difficulty: Medium

Core concepts: Design a data structure, queue, hash set, and efficient resource allocation.

Problem: [Design Phone Directory — LeetCode 379](https://leetcode.com/problems/design-phone-directory/description/?utm_source=chatgpt.com)

## 0. Simplify the problem statement

Imagine a system that manages phone numbers from `0` to `maxNumbers - 1`. Initially, every number is available.

You need to implement three operations:

- `get()`: Give out an available number. If no number is available, return `-1`.
- `check(number)`: Return `true` if the number is currently available; otherwise, return `false`.
- `release(number)`: Make a previously allocated number available again.

For example, if `maxNumbers = 3`, the available numbers initially are `{0, 1, 2}`.

| Operation    | Result | Available numbers afterward |
| ------------ | ------ | --------------------------- |
| `get()`      | `0`    | `{1, 2}`                    |
| `get()`      | `1`    | `{2}`                       |
| `check(2)`   | `true` | `{2}`                       |
| `get()`      | `2`    | `{}`                        |
| `get()`      | `-1`   | `{}`                        |
| `release(1)` | —      | `{1}`                       |
| `check(1)`   | `true` | `{1}`                       |
| `get()`      | `1`    | `{}`                        |

The important detail is that a number must not be allocated twice while it is already in use.

Also, releasing a number that is already available must not create a duplicate entry.

## 1. Clarifying questions to ask the interviewer

These questions help identify the correct data structure and prevent subtle bugs.

1. Are the numbers always in the range `0` to `maxNumbers - 1`? This tells us whether we can use an array indexed directly by number.
2. Can `release(number)` be called multiple times for the same number? If so, we must prevent duplicate entries in our available-number collection.
3. Does `get()` need to return the smallest available number, or any available number? The standard problem allows any available number. If the smallest is required, the data structure may need to change.
4. Can `maxNumbers` be zero? This determines whether we need to handle an empty directory at initialization.

For the standard LeetCode problem, we can assume a fixed directory, numbers in the valid range, and that `get()` may return any available number.

## 2. Core intuition: Think of numbers as reusable resources

The key interview question is:

How can we find an available number without scanning every number, and how can we check availability instantly?

A phone directory behaves like a resource pool:

- `get()` acquires a resource.
- `release()` returns a resource.
- `check()` asks whether a resource is free.

There are several approaches. Let's derive them from simple to optimal.

### Approach 1: Scan an array

Maintain a boolean array where `available[i]` tells us whether number `i` is free.

Initially, every entry is `true`.

```
Number:     0      1      2
Available:  T      T      T
```

When `get()` is called, scan from index `0` until we find a `true` entry. Return that number and mark it `false`.

When `release(1)` is called, mark `available[1] = true`.

When `check(1)` is called, return `available[1]`.

This is easy to implement and is a good starting point in an interview.

The drawback is that `get()` might inspect every number before finding an available one—or before discovering that none exists.

### Approach 2: Maintain a queue of available numbers

Instead of searching for an available number, store the available numbers directly in a queue.

Initially:

```
Queue: [0, 1, 2]
```

Calling `get()` removes the front element.

```
get() -> 0

Queue: [1, 2]
```

Calling `get()` again:

```
get() -> 1

Queue: [2]
```

This makes allocation efficient because removing the front element of a queue takes \\(O(1)\\) time.

But there is a subtle problem: how do we implement `check(number)` efficiently, and how do we prevent duplicate entries when releasing numbers?

We can use a hash set to track availability.

### Optimal practical approach: Queue + HashSet

Maintain two structures:

- `availableQueue`: provides the next available number.
- `availableSet`: tells us instantly whether a number is available.

Both structures must represent the same collection of available numbers.

```
                  Phone Directory
                  /              \
                 /                \
       Available Queue        Available Set
          [0, 1, 2]             {0, 1, 2}
                 \                /
                  \              /
               Same available numbers
```

The operations are now straightforward:

- `get()`: Remove a number from the queue and set.
- `check(number)`: Check whether the set contains it.
- `release(number)`: If the number is not already available, add it to both structures.

The set also prevents duplicate queue entries: if the number is already in the set, `release()` does nothing.

This gives average \\(O(1)\\) time for all three operations.&#x20;

## 3. Edge cases to watch out for

Before writing code, consider these scenarios:

1. Directory is full: `get()` must return `-1`.
2. Release the same number twice: the number must not be allocated twice.
3. Release an available number: nothing should change.
4. Only one number exists: after allocating it, the next `get()` returns `-1`; releasing it makes it available again.
5. Repeated allocation and release: every number must transition correctly between available and assigned states.

The most important invariant is:

> Every available number appears exactly once in the allocation structure, and every assigned number appears zero times.

## 4. Java 24 solutions: brute force to optimal

### Solution 1 — Boolean array (brute force)

```
class PhoneDirectory {
    private final boolean[] available;

    public PhoneDirectory(int maxNumbers) {
        // Every number is initially available.
        available = new boolean[maxNumbers];
        java.util.Arrays.fill(available, true);
    }

    public int get() {
        // BRUTE-FORCE IDEA:
        // Scan from the beginning until we find a free number.
        // This is simple, but we may inspect all n entries.
        for (int number = 0; number < available.length; number++) {
            if (available[number]) {
                available[number] = false; // Allocate it immediately.
                return number;
            }
        }

        // We scanned every number: none is available.
        return -1;
    }

    public boolean check(int number) {
        // Direct array access takes O(1).
        // LeetCode guarantees that number is in the valid range.
        return available[number];
    }

    public void release(int number) {
        // Mark it available.
        // Repeated releases are harmless because this is a boolean
        // assignment, not an insertion into a collection.
        available[number] = true;
    }
}

/*
 * Complexity, where n = maxNumbers:
 *
 * Constructor: O(n) time to initialize all entries; O(n) space.
 * get():      O(n) worst case, because we may scan every number.
 * check():    O(1) time.
 * release():  O(1) time.
 *
 * Interview takeaway:
 * Start here to establish the state model. Then optimize get(),
 * because it is the only operation that scans the entire directory.
 */
```

### Solution 2 — Queue + HashSet

This is a common interview solution. The queue makes allocation fast, while the set supports membership checks and prevents duplicate releases.

```
import java.util.ArrayDeque;
import java.util.HashSet;
import java.util.Queue;
import java.util.Set;

class PhoneDirectory {
    private final Queue<Integer> availableQueue = new ArrayDeque<>();
    private final Set<Integer> availableSet = new HashSet<>();

    public PhoneDirectory(int maxNumbers) {
        // Initially, every number is available.
        // Insert each number into BOTH structures.
        for (int number = 0; number < maxNumbers; number++) {
            availableQueue.offer(number);
            availableSet.add(number);
        }
    }

    public int get() {
        // Poll returns null when the queue is empty.
        Integer number = availableQueue.poll();

        if (number == null) {
            return -1;
        }

        // The number is now assigned, so remove it from the set too.
        availableSet.remove(number);

        return number;
    }

    public boolean check(int number) {
        // The set is our fast source of truth for availability.
        return availableSet.contains(number);
    }

    public void release(int number) {
        // CRITICAL CHECK:
        // If the number is already available, do nothing.
        // Otherwise, repeated release calls could put duplicate copies
        // into the queue, allowing the same number to be allocated twice.
        if (availableSet.add(number)) {
            // Set.add returns true only when the number was absent.
            availableQueue.offer(number);
        }
    }
}

/*
 * Complexity, where n = maxNumbers:
 *
 * Constructor: O(n) time and O(n) space.
 * get():      O(1) average time.
 * check():    O(1) average time.
 * release():  O(1) average time.
 *
 * HashSet operations are average O(1), not guaranteed worst-case O(1).
 * Space is O(n) overall; the queue and set store the available numbers.
 *
 * Invariant:
 * The queue and set contain exactly the same available numbers.
 *
 * Why not just use the queue?
 * check(number) would otherwise require a search through the queue,
 * taking O(n) time. The hash set avoids that scan.
 */
```

### Solution 3 — Optimal fixed-size free list

For a stronger interview answer, we can do better than a queue and hash set.

The problem has a special property: the universe of possible numbers is fixed and dense, from `0` to `maxNumbers - 1`.

That means we can implement our own linked list using arrays rather than allocating linked-list nodes or boxing numbers into `Integer` objects.

Maintain:

- `next[i]`: the next available number after `i`.
- `head`: the first available number.
- `available[i]`: whether number `i` is free.

The array-based linked list contains only available numbers.

Initially, the free list looks like this:

```
head
 |
 v
 0 -> 1 -> 2 -> 3 -> -1
```

Here, `-1` means the end of the list.

When `get()` allocates `0`, move the head to `next[0]`:

```
head
 |
 v
 1 -> 2 -> 3 -> -1
```

When `release(0)` is called, insert `0` at the front:

```
head
 |
 v
 0 -> 1 -> 2 -> 3 -> -1
```

Every allocation and release updates only a constant number of array entries.

```
class PhoneDirectory {
    private final int[] next;
    private final boolean[] available;
    private int head;

    public PhoneDirectory(int maxNumbers) {
        next = new int[maxNumbers];
        available = new boolean[maxNumbers];

        // Build a linked list of every available number:
        // 0 -> 1 -> 2 -> ... -> maxNumbers - 1 -> -1
        for (int number = 0; number < maxNumbers; number++) {
            next[number] = number + 1;
            available[number] = true;
        }

        // The final number has no successor.
        next[maxNumbers - 1] = -1;

        // Initially, the first number is available.
        head = 0;
    }

    public int get() {
        // An empty free list means all numbers are assigned.
        if (head == -1) {
            return -1;
        }

        // Allocate the first available number.
        int number = head;

        // Remove it from the free list by advancing the head.
        head = next[number];

        // Track the state separately so check() and release()
        // can determine whether this number is currently available.
        available[number] = false;

        return number;
    }

    public boolean check(int number) {
        // Direct array lookup: no traversal is required.
        return available[number];
    }

    public void release(int number) {
        // If already free, do nothing. This prevents duplicate nodes
        // in our array-based free list.
        if (available[number]) {
            return;
        }

        // Insert this number at the front of the free list.
        next[number] = head;
        head = number;

        // The number is free again.
        available[number] = true;
    }
}

/*
 * Complexity, where n = maxNumbers:
 *
 * Constructor: O(n) time to initialize the arrays and free list.
 *             O(n) space for next[] and available[].
 *
 * get():      O(1) worst-case time: inspect head and advance it.
 * check():    O(1) worst-case time: inspect one boolean entry.
 * release():  O(1) worst-case time: inspect availability and update
 *             at most two array entries plus one boolean entry.
 *
 * Why this is the strongest of these three implementations:
 * 1. No scanning is needed.
 * 2. No HashSet or Queue is required.
 * 3. No boxed Integer objects or linked-list node objects are needed.
 * 4. Operations have deterministic O(1) time, assuming valid inputs.
 *
 * Trade-off:
 * The linked list returns the most recently released number first.
 * That is allowed because the problem permits any available number.
 */
```

LeetCode submission tip: Submit any one of these `PhoneDirectory` implementations, not all three in the same file. The array-based free list is my preferred answer when the interviewer wants deterministic constant-time operations and a deeper data-structure design.

## 6. Interview follow-up questions and answers

Q1. Why can't we just use a `HashSet` of available numbers?

We can. A hash set alone supports `check()` and `release()` in average \\(O(1)\\). However, it doesn't provide a direct way to retrieve an arbitrary element in guaranteed constant time using the standard Java `HashSet` API. A queue or free list makes allocation efficient.

Q2. Why is the `available` array needed in the free-list solution?

The free list contains only available numbers. If we release a number that's already free without checking, we might insert it into the list a second time and corrupt the list. The boolean array makes that check \\(O(1)\\).

Q3. Can the free list be implemented without the boolean array?

Yes, with a different design. For example, we could use a sentinel value in `next[]` to indicate whether a number is allocated, provided that sentinel cannot be confused with a valid free-list pointer. That saves an array but requires careful initialization and state management. The separate boolean array is easier to explain and maintain.

Q4. What if the interviewer requires the smallest available number every time?

The queue and free list no longer satisfy that requirement because they return numbers in their own allocation order. A `TreeSet<Integer>` could maintain available numbers in sorted order, providing `first()` in \\(O(\log n)\\) update costs and \\(O(1)\\) minimum retrieval, with \\(O(\log n)\\) insertion and removal. Alternatively, a min-heap with lazy invalidation can be designed, but it needs extra state and cleanup logic.

Q5. What if the directory grows dynamically?

The array-based free list assumes a fixed range. For a dynamically growing universe, we would need to extend the arrays and link newly introduced numbers into the free list, or use a suitable dynamic collection.

Q6. How do you prove the free-list solution is correct?

Maintain two invariants:

1. `available[i]` is `true` exactly when number `i` is available.
2. The free list contains every available number exactly once and no assigned numbers.

Initially, both invariants hold. `get()` removes the head and marks it assigned. `release()` inserts only an assigned number at the head and marks it available. `check()` reads the state directly. Therefore, all operations preserve the invariants.

## 7. Final interview mental model

Remember this progression:

1. Start with state: every number is either available or assigned.
2. Identify the bottleneck: scanning for a free number makes `get()` \\(O(n)\\).
3. Store free resources explicitly: use a queue to avoid scanning.
4. Support membership checks: use a hash set alongside the queue.
5. Exploit the fixed integer range: replace general-purpose collections with an array-based free list for worst-case \\(O(1)\\) operations.

The broader pattern is a resource allocator with a free list. The same idea appears in memory allocators, object pools, reusable ID generators, and systems that manage fixed pools of slots.
