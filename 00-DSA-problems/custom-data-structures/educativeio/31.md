# 1797. Design Authentication Manager — Java 24

The key to this problem is understanding how to track token expiration efficiently and, most importantly, how to handle a token that expires at the exact time an operation occurs.

## 0. Simplify the problem

Imagine an authentication server that issues tokens. Each token remains valid for `timeToLive` seconds after it is generated or renewed.

For example, if `timeToLive = 5`:

- Generate token `"aaa"` at time `2` → it expires at time `7`.
- At time `6`, it is still valid.
- At time `7`, it is expired.
- Renewing a valid token resets its expiration to `currentTime + timeToLive`.
- Renewing an expired or nonexistent token does nothing.

Important rule: A token is valid only when

\\[ \text{currentTime} < \text{expiryTime} \\]

If the current time equals the expiration time, the token is already expired.

## 1. Clarifying questions to ask the interviewer

1. Is the expiration boundary inclusive? The statement confirms that a token expiring at time \\(t\\) is invalid at \\(t\\). Therefore, validity is strictly `currentTime < expiryTime`.
2. Can token IDs be generated more than once? The constraints guarantee unique IDs across all `generate` calls. This means we can safely store one expiration time per token in a `HashMap`.
3. Are operations guaranteed to arrive in chronological order? Yes, `currentTime` is strictly increasing. This is useful because expired tokens never become valid again, and we can remove them as time advances.
4. How many operations can occur? At most 2,000. This means even a straightforward linear scan is acceptable, although we can also design a more scalable solution.

## 2. Core idea: Store expiration times, not token creation times

The most natural representation is:

```
tokenId -> expiryTime
```

For example:

```
timeToLive = 5

Token    Expiry
aaa      7
bbb      12
ccc      15
```

When a token is renewed, replace its expiration time with `currentTime + timeToLive`.

When counting, count only entries whose expiration time is strictly greater than the current time.

The key design decision is when to remove expired entries. We can use that decision to develop three solutions, from brute force to an efficient expiration queue.

## 3. Solution 1 — Brute force using a list

### Mental model

Store every token and its expiration time in a list. For every operation, scan the list to find the relevant token. When counting, scan the entire list and count valid tokens.

This is easy to implement but requires linear searches for `renew` and linear scans for counting.

```java
import java.util.ArrayList;
import java.util.List;

class AuthenticationManagerBruteForce {

    // Each token has an ID and its current expiration time.
    // A record is a concise, immutable data carrier in modern Java.
    private record Token(String id, int expiryTime) {}

    private final int timeToLive;
    private final List<Token> tokens = new ArrayList<>();

    AuthenticationManagerBruteForce(int timeToLive) {
        this.timeToLive = timeToLive;
    }

    public void generate(String tokenId, int currentTime) {
        // All generated token IDs are unique, so adding is sufficient.
        tokens.add(new Token(tokenId, currentTime + timeToLive));
    }

    public void renew(String tokenId, int currentTime) {
        // Find the token by scanning the list.
        for (int i = 0; i < tokens.size(); i++) {
            Token token = tokens.get(i);

            if (token.id().equals(tokenId)) {
                // Equality means expired: currentTime >= expiryTime.
                if (currentTime >= token.expiryTime()) {
                    return;
                }

                // Replace the immutable record with an updated record.
                tokens.set(
                    i,
                    new Token(tokenId, currentTime + timeToLive)
                );
                return;
            }
        }

        // No matching token: renewal is ignored.
    }

    public int countUnexpiredTokens(int currentTime) {
        int count = 0;

        // Check every token because expired tokens remain in the list.
        for (Token token : tokens) {
            if (currentTime < token.expiryTime()) {
                count++;
            }
        }

        return count;
    }
}

/*
 * Complexity:
 *
 * Let n be the number of tokens ever generated.
 *
 * generate: O(1), because ArrayList appends at the end in amortized O(1).
 * renew:    O(n), because locating the token requires a linear scan.
 * count:    O(n), because every stored token must be checked.
 * Space:    O(n), because expired tokens are never removed.
 *
 * Interview assessment:
 * This is useful as a baseline, but the list makes token lookup
 * unnecessarily expensive. A HashMap is a natural improvement.
 */
```

## 4. Solution 2 — Optimal for this problem's constraints: HashMap

### Mental model

Use a `HashMap` to associate each token ID with its expiration time.

The map lets us find and update tokens in expected constant time. Because there are at most 2,000 calls, we can scan the map when counting tokens instead of introducing a more complex data structure.

```java
import java.util.HashMap;
import java.util.Map;

class AuthenticationManager {

    // Maps each active or not-yet-cleaned token ID to its expiration time.
    private final Map<String, Integer> expiryByToken = new HashMap<>();

    private final int timeToLive;

    AuthenticationManager(int timeToLive) {
        this.timeToLive = timeToLive;
    }

    public void generate(String tokenId, int currentTime) {
        // Expiration is absolute: generation time + TTL.
        expiryByToken.put(tokenId, currentTime + timeToLive);
    }

    public void renew(String tokenId, int currentTime) {
        Integer expiryTime = expiryByToken.get(tokenId);

        // Missing tokens cannot be renewed.
        // Tokens expiring exactly now are already invalid.
        if (expiryTime == null || currentTime >= expiryTime) {
            return;
        }

        // A valid renewal replaces the previous expiration time.
        expiryByToken.put(tokenId, currentTime + timeToLive);
    }

    public int countUnexpiredTokens(int currentTime) {
        int count = 0;

        // Expired tokens need not be physically removed for correctness.
        // We simply exclude them from the result.
        for (int expiryTime : expiryByToken.values()) {
            if (currentTime < expiryTime) {
                count++;
            }
        }

        return count;
    }
}

/*
 * Complexity:
 *
 * Let n be the number of generated tokens and m the number of calls.
 *
 * generate: O(1) expected time for a HashMap insertion.
 * renew:    O(1) expected time for lookup and update.
 * count:    O(n) time to inspect all stored expiration times.
 * Space:    O(n).
 *
 * Why this is a good interview solution:
 * - The code directly models the requirements.
 * - HashMap eliminates linear token searches.
 * - At most 2,000 calls are allowed, so O(n) counting is entirely
 *   reasonable.
 *
 * Important limitation:
 * Expired entries remain in the map, so its size represents all tokens
 * not yet physically removed, rather than the number currently valid.
 */
```

### Walk through the example

Let `timeToLive = 5`.

| Operation                  | Token expirations after the operation | Count |
| -------------------------- | ------------------------------------- | ----- |
| `renew("aaa", 1)`          | None                                  | —     |
| `generate("aaa", 2)`       | `aaa → 7`                             | —     |
| `countUnexpiredTokens(6)`  | `aaa → 7`                             | 1     |
| `generate("bbb", 7)`       | `aaa → 7`, `bbb → 12`                 | —     |
| `renew("aaa", 8)`          | `aaa → 7`, `bbb → 12`                 | —     |
| `renew("bbb", 10)`         | `aaa → 7`, `bbb → 15`                 | —     |
| `countUnexpiredTokens(15)` | `aaa → 7`, `bbb → 15`                 | 0     |

Notice that `aaa` expires at time `7`, so it cannot be renewed at time `8`. Likewise, `bbb` expires at time `15`, so it is not counted at time `15`.

## 5. Solution 3 — PriorityQueue + HashMap

This is the scalable approach when the number of tokens and operations becomes large.

### How to identify this approach in an interview

Ask yourself three questions:

1. What do I need to find quickly? A token's latest expiration time → `HashMap`.
2. What do I need to process repeatedly? Tokens that have expired by the current time → a min-heap ordered by expiration time.
3. Does renewal change the ordering? Yes. A renewal changes the expiration time, so the heap may contain an outdated entry.

The third observation is the key.

Suppose token `aaa` is generated at time `2`, with TTL `5`. Its expiration is `7`. It is renewed at time `5`, so its new expiration is `10`.

The heap can contain both entries:

```
Heap entries (earliest expiration first):

(aaa, 7)  <- stale entry
(aaa, 10) <- current entry

HashMap:
aaa -> 10
```

We do not need to remove the old entry from the heap immediately. Instead, when an entry reaches the top, we compare its expiration with the latest expiration in the map.

- If they match, the entry is current, so remove the token from the map.
- If they differ, the entry is stale, so discard the heap entry without deleting the token.

This technique is called lazy invalidation. It avoids the complexity of removing an arbitrary element from a priority queue.

### Code — Java 24

```java
import java.util.Comparator;
import java.util.HashMap;
import java.util.Map;
import java.util.PriorityQueue;
import java.util.Queue;

class AuthenticationManager {

    // One heap entry represents a particular expiration event.
    // A token can have multiple entries if it is renewed.
    private record Expiration(String tokenId, int expiryTime) {}

    private final int timeToLive;

    // Source of truth: the latest expiration time for each token.
    private final Map<String, Integer> expiryByToken = new HashMap<>();

    // The smallest expiration time is always at the head.
    private final Queue<Expiration> expirations =
        new PriorityQueue<>(Comparator.comparingInt(Expiration::expiryTime));

    AuthenticationManager(int timeToLive) {
        this.timeToLive = timeToLive;
    }

    public void generate(String tokenId, int currentTime) {
        // Remove all expiration events that are due before processing
        // this operation. Expiration occurs before any action at that time.
        removeExpiredTokens(currentTime);

        int expiryTime = currentTime + timeToLive;

        // Record the token's current expiration.
        expiryByToken.put(tokenId, expiryTime);

        // Add an event so the token can be found efficiently when it expires.
        expirations.offer(new Expiration(tokenId, expiryTime));
    }

    public void renew(String tokenId, int currentTime) {
        // First process every expiration that has occurred by this time.
        removeExpiredTokens(currentTime);

        Integer oldExpiry = expiryByToken.get(tokenId);

        // If the token is absent, it either never existed or has expired.
        if (oldExpiry == null) {
            return;
        }

        int newExpiry = currentTime + timeToLive;

        // Replace the authoritative expiration in the map.
        expiryByToken.put(tokenId, newExpiry);

        // Insert the new expiration event.
        // The old heap entry is intentionally left in place.
        expirations.offer(new Expiration(tokenId, newExpiry));
    }

    public int countUnexpiredTokens(int currentTime) {
        // After cleanup, the map contains only currently valid tokens.
        removeExpiredTokens(currentTime);

        // No scan is necessary: the map's size is the answer.
        return expiryByToken.size();
    }

    private void removeExpiredTokens(int currentTime) {
        // Only events with expiryTime <= currentTime have expired.
        while (!expirations.isEmpty()
                && expirations.peek().expiryTime() <= currentTime) {

            Expiration event = expirations.poll();

            Integer latestExpiry = expiryByToken.get(event.tokenId());

            // Delete the token only if this is its latest expiration event.
            // If latestExpiry differs, this event is stale because the
            // token was renewed after this older expiration was scheduled.
            if (latestExpiry != null
                    && latestExpiry == event.expiryTime()) {
                expiryByToken.remove(event.tokenId());
            }
        }
    }
}

/*
 * Complexity:
 *
 * Let n be the number of generated tokens and r the number of renewals.
 * The total number of heap entries ever inserted is at most n + r.
 *
 * generate:
 *   O(log(n + r)) amortized, including insertion and cleanup.
 *
 * renew:
 *   O(log(n + r)) amortized, including cleanup and insertion.
 *
 * countUnexpiredTokens:
 *   O(k log(n + r)) for k expiration events removed during this call.
 *   The final map-size lookup is O(1) expected time.
 *   Across the complete operation sequence, every heap entry is removed
 *   at most once, so cleanup work is O((n + r) log(n + r)) in total.
 *
 * Space:
 *   O(n + r), because stale heap entries may remain until their
 *   expiration times are reached.
 *
 * Why it works:
 *   - The HashMap holds the authoritative, latest expiration.
 *   - The min-heap identifies the next expiration event.
 *   - Stale events cannot accidentally delete renewed tokens.
 *   - Cleanup uses <=, enforcing the strict validity condition:
 *     currentTime < expiryTime.
 */
```

### Comparing the approaches

| Approach           | Generate             | Renew                | Count                | Space |
| ------------------ | -------------------- | -------------------- | -------------------- | ----- |
| List               | O(1) amortized       | O(n)                 | O(n)                 | O(n)  |
| HashMap            | O(1) expected        | O(1) expected        | O(n)                 | O(n)  |
| HashMap + min-heap | O(log n) amortized\* | O(log n) amortized\* | O(1) after cleanup\* | O(n)  |

\*For the heap approach, n in the table represents the number of accumulated expiration events. Individual operations may perform additional cleanup; the total cleanup cost is amortized over all events.

Which should you choose?

For LeetCode 1797, I would implement Solution 2, the HashMap. With only 2,000 calls, it is simpler, easy to explain, and efficient enough. I would introduce the priority queue if the interviewer asked for constant-time counting or wanted a design that scales to a much larger number of operations.

## 6. Edge cases to discuss

| Case                                 | Expected behavior                                                                      |
| ------------------------------------ | -------------------------------------------------------------------------------------- |
| Renew a nonexistent token            | Ignore the request                                                                     |
| Renew exactly at expiration time     | Ignore the request                                                                     |
| Count exactly at expiration time     | Do not count the token                                                                 |
| Renew before expiration              | Extend expiry to `currentTime + timeToLive`                                            |
| Several tokens expire simultaneously | Remove or exclude all of them                                                          |
| Renew the same token multiple times  | Only its latest expiry determines validity                                             |
| Count when no tokens exist           | Return `0`                                                                             |
| Large TTL and timestamps             | Use a numeric type capable of holding their sum; `int` is safe under these constraints |

## 7. Interview follow-up questions and answers

Q1. Why not delete a token directly from the priority queue when renewing it?

Java's `PriorityQueue` does not support efficient arbitrary-element removal. Finding and removing a particular element can take \\(O(n)\\). Lazy invalidation avoids that cost by keeping the latest expiration in the map and ignoring outdated heap entries.

Q2. Why does the priority queue use a min-heap?

We need to process the earliest expiration first. Once the earliest event has an expiration greater than `currentTime`, every other heap event also has a greater or equal expiration. Therefore, no other token needs cleanup at that moment.

Q3. Why is the HashMap sufficient for the original problem?

Because there are at most 2,000 operations. The linear scan during counting is inexpensive, while the implementation stays simple and easy to reason about.

Q4. Can the priority queue's space usage grow even when few tokens are active?

Yes. Renewals create new expiration events, and stale events remain until they reach the heap's head and become eligible for cleanup. Space is proportional to generated tokens plus renewals, not just currently active tokens.

Q5. What if operations arrive out of chronological order?

The current design relies on strictly increasing timestamps. If events can arrive out of order, we must define whether past operations are allowed to alter historical state. Supporting that behavior may require a different model rather than simply changing the data structure.

Q6. Can we achieve expected \\(O(1)\\) time for all three operations?

With a different design, we can maintain expiration buckets indexed by time and track the active count, but efficiently processing expiration events and handling renewals requires additional bookkeeping. Under arbitrary TTL values and a general operation stream, a map plus heap is a straightforward scalable design; the original problem does not require constant-time counting.

## 8. Final interview thought process

When you encounter a problem involving tokens, sessions, leases, or temporary records, use this sequence:

1. Identify the entity and the state that must be stored: here, `tokenId → expiryTime`.
2. Translate validity into a precise condition: `currentTime < expiryTime`.
3. Choose a data structure for direct lookup: `HashMap`.
4. Identify the expensive repeated operation: counting every active token.
5. If counting becomes a bottleneck, maintain expiration events in chronological order with a min-heap.
6. When updates invalidate older events, use lazy invalidation rather than expensive arbitrary removal.
7. Test the exact expiration boundary before finalizing the implementation.

The most important insight is that expiration is a time-based state transition, while renewal changes the scheduled expiration event. Once those two concepts are separated, the data structure choices become much easier to derive.






























Yes, `LinkedHashMap` is a reasonable option for Design Authentication Manager, and there's an interesting optimization we can make because the problem guarantees that `currentTime` is strictly increasing.

The important question is: Can we use insertion order to identify expired tokens efficiently?

The answer is yes, but only if we maintain the correct ordering.

## 1. Why LinkedHashMap can work

A regular `HashMap` stores:

```
tokenId -> expiryTime
```

A `LinkedHashMap` stores the same mapping while also maintaining a predictable iteration order. By default, that order is insertion order, not expiration-time order.

Consider this example with `timeToLive = 5`:

```
generate("aaa", 1)  -> expires at 6
generate("bbb", 2)  -> expires at 7
renew("aaa", 3)     -> expires at 8
```

If we use insertion order, the entries might look like this:

```
aaa -> 8
bbb -> 7
```

But `bbb` expires before `aaa`, even though `aaa` appears first.

Therefore, insertion order alone does not guarantee that expired tokens appear first.

## 2. A better approach: LinkedHashMap ordered by expiration

Since timestamps strictly increase and all tokens share the same `timeToLive`, a token renewed later always has a later expiration time.

We can exploit this property:

- Store tokens in expiration order.
- When a token is renewed, remove it and reinsert it at the end.
- Remove expired tokens from the beginning until the first unexpired token is reached.
- Return the map's size to count active tokens.

Why does this work? A renewed token receives an expiration time of `currentTime + timeToLive`. Since `currentTime` strictly increases, the new expiration is later than the previous expiration of every token renewed earlier.

### Java implementation

```java
import java.util.LinkedHashMap;
import java.util.Map;

class AuthenticationManager {

    private final int timeToLive;

    // The first entry has the earliest expiration time.
    // This ordering is maintained explicitly by remove-and-reinsert on renew.
    private final LinkedHashMap<String, Integer> expiryByToken =
        new LinkedHashMap<>();

    AuthenticationManager(int timeToLive) {
        this.timeToLive = timeToLive;
    }

    public void generate(String tokenId, int currentTime) {
        // Remove expired tokens before processing the operation.
        removeExpiredTokens(currentTime);

        // Unique token IDs are guaranteed by the problem.
        // Because time increases, this new expiration belongs at the end.
        expiryByToken.put(tokenId, currentTime + timeToLive);
    }

    public void renew(String tokenId, int currentTime) {
        removeExpiredTokens(currentTime);

        Integer expiryTime = expiryByToken.get(tokenId);

        // Cleanup already removed expired tokens, so existence means valid.
        if (expiryTime == null) {
            return;
        }

        // Remove the old entry and append the renewed token at the end.
        // This preserves expiration order.
        expiryByToken.remove(tokenId);
        expiryByToken.put(tokenId, currentTime + timeToLive);
    }

    public int countUnexpiredTokens(int currentTime) {
        removeExpiredTokens(currentTime);

        // All remaining entries are unexpired.
        return expiryByToken.size();
    }

    private void removeExpiredTokens(int currentTime) {
        // LinkedHashMap preserves insertion order.
        // Because we maintain expiration order, expired tokens form a prefix.
        var iterator = expiryByToken.entrySet().iterator();

        while (iterator.hasNext()) {
            Map.Entry<String, Integer> entry = iterator.next();

            // Expiration at exactly currentTime means the token is invalid.
            if (entry.getValue() <= currentTime) {
                iterator.remove();
            } else {
                // Every later entry expires at the same time or later.
                // Therefore, we can stop at the first unexpired token.
                break;
            }
        }
    }
}

/*
 * Complexity:
 *
 * generate:
 *   O(k) worst case, where k is the number of tokens removed by cleanup.
 *   The insertion itself is O(1) expected.
 *
 * renew:
 *   O(k) worst case for cleanup, plus O(1) expected for lookup,
 *   removal, and reinsertion.
 *
 * countUnexpiredTokens:
 *   O(k) worst case, where k is the number of expired tokens removed.
 *   Returning the map size is O(1).
 *
 * Across the entire sequence:
 *   Each token is removed due to expiration at most once.
 *   Each renewal causes one deliberate removal and reinsertion.
 *   Total work is O(m) expected for m operations.
 *
 * Space:
 *   O(n), where n is the number of tokens currently stored.
 *
 * Important:
 *   The ordering invariant depends on strictly increasing timestamps
 *   and a common timeToLive. If either assumption changes, this strategy
 *   may no longer be correct.
 */
```

## 3. Compare the three options

| Data structure                           | Renew                            | Count              | Cleanup behavior                      |
| ---------------------------------------- | -------------------------------- | ------------------ | ------------------------------------- |
| `HashMap`                                | O(1) expected                    | O(n)               | Scan all entries to count             |
| `HashMap` + min-heap                     | O(log n) amortized               | O(1) after cleanup | Process earliest expiration events    |
| `LinkedHashMap` with expiration ordering | O(1) expected, excluding cleanup | O(1) after cleanup | Remove expired entries from the front |

These complexities exclude cleanup where noted. With `LinkedHashMap`, a single operation may remove many expired tokens, but each expired token is cleaned up only once. Thus, the total cleanup cost across all operations is amortized O(1) per removed token.

## 4. What I would say in an interview

"I'd initially use a `HashMap` because it directly maps token IDs to expiration times. If I want to avoid scanning all entries during counting, I can exploit the strictly increasing timestamps and common TTL. By using a `LinkedHashMap` and moving each renewed token to the end, I maintain expiration order. Expired tokens then form a prefix, allowing efficient cleanup from the front without a priority queue."

One caveat: A `LinkedHashMap` does not automatically sort entries by expiration. The solution works because we explicitly maintain the ordering invariant. If timestamps can arrive out of order, or tokens have different TTL values, I'd prefer the min-heap approach.
