# Two Sum Data Structure — Java 24 Interview Solution

## 0. Simplify the problem statement

We need to design a class called `TwoSum` that stores numbers as they arrive and checks whether any two different occurrences of numbers add up to a target.

We need to implement three things:

- `TwoSum()` — starts with an empty collection.
- `add(int number)` — adds a number to the collection.
- `find(int value)` — returns `true` if two stored numbers sum to `value`; otherwise, returns `false`.

### Example

```
TwoSum twoSum = new TwoSum();

twoSum.add(1);
twoSum.add(3);
twoSum.add(5);

twoSum.find(4);  // true, because 1 + 3 = 4
twoSum.find(7);  // true, because  2 + 5 = 7? No, 2 was never added.
```

Correction for the second query: `find(7)` returns `false`, because the stored numbers are `1, 3, 5`, and no two of them add up to `7`.

Now add another number:

```
twoSum.add(2);

twoSum.find(7);  // true, because 2 + 5 = 7
twoSum.find(6);  // true, because 1 + 5 = 6
twoSum.find(10); // false
```

Important: Duplicate numbers are allowed, and each call to `add` adds another occurrence.

For example:

```
twoSum.add(4);
twoSum.add(4);

twoSum.find(8); // true: the two occurrences of 4 add up to 8
```

But if only one `4` has been added, `find(8)` must return `false`. We cannot use the same occurrence twice.

## 1. Clarifying questions to ask the interviewer

1. Can duplicate numbers be added? Why ask: This determines whether we need to track frequencies. The solution must correctly handle pairs such as `4 + 4`.
2. Can `find` be called before any numbers have been added? Why ask: We need to define the behavior for an empty collection. Normally, it returns `false`.
3. Can the same number be used twice in a pair? Why ask: We should clarify that two distinct occurrences are required. One stored `4` is not sufficient to find `8`.
4. What matters more: fast `add` or fast `find`? Why ask: This is the central design trade-off. We can make insertion very fast and searching slower, or spend more work during insertion to accelerate queries.
5. Are the inputs and target allowed to be negative? Why ask: Negative values affect the arithmetic and rule out assumptions that all numbers are positive. Here, the constraints allow negative numbers and the full `int` range for the target.

For the given constraints, a hash-based approach is a strong default because there are at most \\(10^4\\) method calls, and we can choose a design based on the expected frequency of `find`.

## 2. Core intuition: look for the missing partner

Suppose we want to know whether two numbers add up to `10`.

If one number is `3`, the other number must be:

\\[ \text{partner} = 10 - 3 = 7 \\]

Instead of trying every possible pair, we can ask:

> For each stored number, is the number needed to complete the target also stored?

For a target `10` and stored numbers `[3, 7, 2]`:

Check the first number

## 3

Required partner: \\(10 - 3 = 7\\)

7 exists, so return `true`.

The key is how we store and search for these numbers.

There are three useful approaches:

1. Store every number in a list and examine pairs when `find` is called.
2. Store numbers in a frequency map and use it to look up each required partner.
3. Maintain a set of already-seen numbers and check complements as numbers are added, enabling constant-time lookups during `find`.

The third approach is especially attractive when `find` is called frequently, because we can maintain the set of valid pair sums as numbers arrive.

## 3. Approach 1 — Brute force using a list

### Mental model

Store all numbers in an `ArrayList`. Every time `find(target)` is called, examine every possible pair.

For each index `i`, compare the number at `i` with every number after it. Starting at `i + 1` guarantees that we never use the same occurrence twice.

```java
import java.util.ArrayList;
import java.util.List;

class TwoSumBruteForce {

    // Keep every occurrence, including duplicates.
    private final List<Integer> numbers = new ArrayList<>();

    public TwoSumBruteForce() {
        // The list starts empty.
    }

    public void add(int number) {
        // WHY: Adding to the end of an ArrayList takes amortized O(1) time.
        // We do not search for duplicates or remove existing occurrences.
        //
        // Time: O(1) amortized.
        // Space: O(1) auxiliary space for this operation;
        //        O(n) total storage after n additions.
        numbers.add(number);
    }

    public boolean find(int target) {
        int n = numbers.size();

        // WHY: Enumerate each unordered pair exactly once.
        // j starts at i + 1, so an occurrence cannot pair with itself.
        for (int i = 0; i < n; i++) {
            for (int j = i + 1; j < n; j++) {

                // WHY: Use long for the sum. Two valid int values can
                // overflow when added as ints, even though the target
                // itself is an int.
                if ((long) numbers.get(i) + numbers.get(j) == target) {
                    return true;
                }
            }
        }

        // No pair matched the target.
        return false;

        // Time: O(n^2) worst case, where n is the number of stored values.
        // There are n * (n - 1) / 2 possible pairs.
        // Space: O(1) auxiliary space; the list itself uses O(n) space.
    }
}
```

### Example walkthrough

Stored numbers: `[2, 5, 8, 3]`, target: `10`.

```
i = 0: 2 + 5 = 7
       2 + 8 = 10  -> return true
```

The search stops as soon as a valid pair is found.

When is this useful? When the implementation should be simple, or when `find` is rarely called and the collection is small.

## 4. Approach 2 — HashMap with frequencies

### Mental model

Instead of storing only a list, store each distinct number and how many times it appears.

For example:

```
Numbers added:  [2, 5, 2, 8, 5]

Frequency map:
2 -> 2
5 -> 2
8 -> 1
```

For a target of `10`, if we examine `2`, we need another `8`. If we examine `5`, we need another `5`. The map tells us both whether a partner exists and whether enough copies exist.

The important distinction is:

- If `number != complement`, one occurrence of each is sufficient.
- If `number == complement`, we need at least two occurrences.

```java
import java.util.HashMap;
import java.util.Map;

class TwoSumFrequencyMap {

    // Key = number; value = number of times it was added.
    //
    // WHY use frequencies instead of a plain set?
    // A set cannot distinguish one occurrence of 5 from two occurrences
    // of 5. Frequencies let us correctly answer find(10) in both cases.
    private final Map<Integer, Integer> frequency = new HashMap<>();

    public TwoSumFrequencyMap() {
        // Initially, there are no numbers.
    }

    public void add(int number) {
        // Merge the new occurrence into the existing count.
        // If the number is new, its initial frequency becomes 1.
        frequency.merge(number, 1, Integer::sum);

        // Time: O(1) expected per addition using a hash map.
        // Space: O(1) expected additional space per operation;
        //        O(u) total map entries, where u is the number of
        //        distinct stored values and u <= n.
    }

    public boolean find(int target) {

        // Iterate over distinct values, not every occurrence.
        for (Map.Entry<Integer, Integer> entry : frequency.entrySet()) {
            int number = entry.getKey();

            // Cast before subtraction to prevent integer overflow.
            // For example, target = Integer.MIN_VALUE and number = 1
            // require a complement outside the int range.
            long complement = (long) target - number;

            // A complement outside int range cannot be a stored number,
            // because add accepts int values only.
            if (complement < Integer.MIN_VALUE
                    || complement > Integer.MAX_VALUE) {
                continue;
            }

            int partner = (int) complement;
            Integer partnerCount = frequency.get(partner);

            // No matching partner has been added.
            if (partnerCount == null) {
                continue;
            }

            // If number and partner differ, their occurrences are
            // necessarily distinct, so one of each is enough.
            if (number != partner) {
                return true;
            }

            // If number == partner, we need two separate occurrences.
            // For example, one 5 is not enough for target 10;
            // two 5s are enough.
            if (entry.getValue() >= 2) {
                return true;
            }
        }

        return false;

        // Time: O(u) expected, where u is the number of distinct values.
        // Each map lookup is O(1) expected.
        // Space: O(1) auxiliary space for the search itself.
        // Total stored space: O(u).
    }
}
```

### Example walkthrough

Suppose the stored numbers are `[5, 2, 5]` and the target is `10`.

```
Map:
5 -> 2
2 -> 1

Examine 5:
    complement = 10 - 5 = 5
    frequency of 5 = 2
    Two occurrences exist -> true
```

If only one `5` were stored, the same query would return `false`.

When is this useful? When we want a straightforward implementation with expected constant-time insertion and a search that scans only distinct values.

## 5. Approach 3 — Maintain all possible pair sums

### Mental model

We can move the work from `find` to `add`.

Whenever a new number arrives, pair it with every number that was already stored. Save those sums in a `HashSet`.

For example:

```
Add 2:
    No earlier numbers, so no pair sums exist.

Add 5:
    2 + 5 = 7
    Pair sums = {7}

Add 8:
    2 + 8 = 10
    5 + 8 = 13
    Pair sums = {7, 10, 13}

find(10):
    Is 10 in the set? Yes -> true.
```

This is a useful design when `find` must be as fast as possible, but it can consume substantial memory.

```java
import java.util.ArrayList;
import java.util.HashSet;
import java.util.List;
import java.util.Set;

class TwoSumPairSums {

    // Store all added occurrences, because duplicates matter when forming
    // a pair such as 5 + 5.
    private final List<Integer> numbers = new ArrayList<>();

    // Store every sum that can be formed from two distinct occurrences.
    private final Set<Long> pairSums = new HashSet<>();

    public TwoSumPairSums() {
        // Both collections start empty.
    }

    public void add(int number) {

        // Pair the new number with every previously added occurrence.
        // We do this BEFORE storing the new number, which prevents a
        // single occurrence from being paired with itself.
        for (int previous : numbers) {

            // Use long so sums of int values are represented safely.
            pairSums.add((long) previous + number);
        }

        // Store the occurrence only after generating its new pairs.
        numbers.add(number);

        // Time: O(n) expected, where n is the number of previous additions.
        // Each previous number produces one sum; HashSet insertion is
        // expected O(1).
        //
        // Space: O(n) additional space in the worst case for the new sums.
        // Across n additions, there can be O(n^2) distinct pair sums.
    }

    public boolean find(int target) {

        // The answer is precomputed during add().
        // The set contains a target exactly when two distinct occurrences
        // have formed that sum.
        return pairSums.contains((long) target);

        // Time: O(1) expected.
        // Auxiliary space: O(1) for this query.
        // Total space: O(n + p), where p is the number of distinct pair sums
        // and p can be as large as n * (n - 1) / 2.
    }
}
```

### Edge cases to watch out for

| Situation                   | Example                                                  | Expected result |
| --------------------------- | -------------------------------------------------------- | --------------- |
| Empty collection            | `find(0)`                                                | `false`         |
| Only one number             | Add `4`; `find(8)`                                       | `false`         |
| Duplicate needed            | Add `4` twice; `find(8)`                                 | `true`          |
| Negative numbers            | Add `-3`, `7`; `find(4)`                                 | `true`          |
| Zero pair                   | Add `0` twice; `find(0)`                                 | `true`          |
| Target outside possible sum | Add `1`, `2`; `find(Integer.MAX_VALUE)`                  | `false`         |
| Integer overflow risk       | Add `Integer.MAX_VALUE`, `Integer.MAX_VALUE`; `find(-2)` | `false`         |

One subtle Java detail: integer arithmetic can overflow silently. The frequency-map and pair-sum implementations use `long` for sum/complement arithmetic to avoid that problem.

## 6. Which approach should we choose?

| Approach              | `add()`              | `find()`            | Total space             |
| --------------------- | -------------------- | ------------------- | ----------------------- |
| List + brute force    | \\(O(1)\\) amortized | \\(O(n^2)\\)        | \\(O(n)\\)              |
| Frequency map         | \\(O(1)\\) expected  | \\(O(u)\\) expected | \\(O(u)\\)              |
| Precomputed pair sums | \\(O(n)\\) expected  | \\(O(1)\\) expected | \\(O(n^2)\\) worst case |

Here, \\(n\\) is the number of additions and \\(u\\) is the number of distinct values.

My interview recommendation: use Approach 2, the frequency map.

It provides a good balance between insertion time, query time, and memory usage. With at most \\(10^4\\) calls, it avoids the quadratic memory growth of precomputing every possible pair sum.

If the interviewer explicitly says that `find()` must be extremely fast and memory is plentiful, Approach 3 is a reasonable alternative.

## 7. Interviewer follow-up questions

Q1. Why not use a `HashSet<Integer>` instead of a frequency map?

A set can work, but it must be supplemented with logic for duplicate values. If we store only one `5`, the set cannot tell whether one or two occurrences were added. A frequency map tracks this naturally.

Q2. Why does the brute-force solution start its inner loop at `i + 1`?

To examine each pair once and prevent an occurrence from being paired with itself. For example, a single stored `4` cannot satisfy `find(8)`.

Q3. Can the frequency-map search be improved?

Yes. If the collection is represented by a set of unique values, we can iterate over those values and look up their complements. That is already what the frequency-map approach does, with additional duplicate handling.

Q4. What if there are many more `find()` calls than `add()` calls?

Precomputing pair sums can be beneficial because each query becomes an expected \\(O(1)\\) lookup. However, its worst-case \\(O(n^2)\\) memory consumption must be considered.

Q5. What happens if the collection contains negative values?

Nothing special is required. The complement equation

\\[ \text{complement} = \text{target} - \text{number} \\]

works for positive numbers, negative numbers, and zero.

Q6. Why use `long` when the method arguments are `int`?

Two `int` values can sum to a result outside the `int` range. Casting before arithmetic avoids silent overflow and ensures that a false match is not reported.

Q7. Is `HashMap` lookup guaranteed to be \\(O(1)\\)?

No. It is \\(O(1)\\) on average under normal hashing behavior. The exact worst-case behavior depends on collisions and the implementation. For an interview analysis, we normally state expected \\(O(1)\\) lookup and insertion.

Final takeaway: The problem is fundamentally about the trade-off between doing work when a number is added and doing work when a target is queried. A frequency map is the balanced solution; precomputed pair sums optimize queries at the expense of memory.






Your implementation is almost correct and is a good interview-friendly solution. You use a `HashMap` to store each number's frequency, which allows fast insertion and efficient pair searching.

There is one important bug: integer overflow when calculating `rem = value - key`.

## 1. What your code does well

- `HashMap<Integer, Integer>` stores each number and its frequency.
- `merge(number, 1, Integer::sum)` increments the frequency cleanly.
- You correctly handle duplicates when `rem == key`.
- You iterate over distinct numbers rather than every occurrence, making `find()` efficient.

## 2. The issue: integer overflow

Consider:

```
int value = Integer.MAX_VALUE;
int key = -1;

int rem = value - key;
```

Mathematically, `rem` is `2147483648`, which exceeds the maximum `int` value. Java overflows and produces `Integer.MIN_VALUE`.

Your code could then mistakenly find a pair that does not actually add up to the target.

Fix: Calculate the complement using `long` and check that it falls within the `int` range before looking it up.

## 3. Corrected solution with detailed inline comments

```java

import java.util.*;

public class TwoSum {

    // Key   = number that has been added.
    // Value = number of occurrences of that number.
    //
    // Example:
    // Added numbers: 2, 5, 2
    // Map: {2=2, 5=1}
    //
    // WHY use frequencies?
    // We need to distinguish one occurrence of a number from two
    // occurrences when the target requires the same number twice.
    private final Map<Integer, Integer> numFreq;

    public TwoSum() {
        // Initially, no numbers have been added.
        this.numFreq = new HashMap<>();
    }

    public void add(int number) {

        // If number is absent, initialize its frequency to 1.
        // Otherwise, increment its existing frequency by 1.
        //
        // Example:
        // add(4) -> {4=1}
        // add(4) -> {4=2}
        //
        // Time: O(1) expected.
        // Space: O(1) expected additional space per call;
        //        O(u) total map storage, where u is the number
        //        of distinct numbers.
        this.numFreq.merge(number, 1, Integer::sum);
    }

    public boolean find(int value) {

        // Iterate over distinct numbers stored in the map.
        // We do not need to examine every occurrence separately.
        for (var entry : this.numFreq.entrySet()) {

            int key = entry.getKey();

            // If one number is key, its required partner is:
            //
            //     partner = target - key
            //
            // Use long to avoid integer overflow during subtraction.
            long rem = (long) value - key;

            // A stored number must fit into the int range.
            // If the complement is outside this range, it cannot exist
            // in our map, because add() accepts only int values.
            if (rem < Integer.MIN_VALUE ||
                rem > Integer.MAX_VALUE) {
                continue;
            }

            int partner = (int) rem;

            // Special case: both numbers in the pair are identical.
            //
            // Example:
            // target = 10, key = 5
            //
            // We need TWO occurrences of 5.
            // One occurrence cannot be used twice.
            if (partner == key) {
                if (entry.getValue() >= 2) {
                    return true;
                }

                // Only one occurrence exists, so this key cannot
                // form a valid pair with itself.
                continue;
            }

            // The partner differs from key.
            // If it exists in the map, one occurrence of each number
            // is enough to form a valid pair.
            if (numFreq.containsKey(partner)) {
                return true;
            }
        }

        // No valid pair was found.
        return false;

        // Time: O(u) expected, where u is the number of distinct numbers.
        // Each complement lookup takes O(1) expected time.
        //
        // Auxiliary space: O(1) for find().
        // Total space: O(u) for the frequency map.
    }
}

```

## 4. Walkthrough with an example

Suppose these calls are made:

```
TwoSum ts = new TwoSum();

ts.add(3);
ts.add(3);
ts.add(7);

System.out.println(ts.find(6));  // true
System.out.println(ts.find(10)); // true
System.out.println(ts.find(14)); // false
```

After the additions, the map contains:

```
3 -> 2
7 -> 1
```

For `find(6)`:

1. The map entry is `3 -> 2`.
2. The complement is `6 - 3 = 3`.
3. Since the frequency of `3` is `2`, two distinct occurrences exist.
4. Return `true`.

For `find(10)`:

1. For `3`, the complement is `7`.
2. The map contains `7`.
3. Return `true`.

For `find(14)`:

1. For `3`, the complement is `11`, which is absent.
2. For `7`, the complement is `7`, but its frequency is only `1`.
3. Return `false`.

Let \\(u\\) be the number of distinct numbers stored and \\(n\\) the total number of additions.
