# LeetCode 348 — Design Tic-Tac-Toe

Problem: [Design Tic-Tac-Toe](https://leetcode.com/problems/design-tic-tac-toe/description/?utm_source=chatgpt.com)

Difficulty: Medium

The key interview insight is that we do not need to store or inspect the entire board to determine whether someone has won. We can track a few counters for each row, column, and diagonal, allowing every move to be processed in \\(O(1)\\) time.

## 0. Simplify the problem

We need to design a class `TicTacToe` for an \\(n \times n\\) board.

Two players take turns:

- Player `1` places their mark.
- Player `2` places their mark.
- Each move specifies a row and column.
- A player wins when they occupy an entire row, column, main diagonal, or anti-diagonal.

Implement:

```
TicTacToe(int n)
int move(int row, int col, int player)
```

The `move` method returns:

- `0` if nobody has won yet.
- `1` if player 1 wins.
- `2` if player 2 wins.

The problem guarantees valid moves: players do not overwrite occupied cells, and moves are made according to the rules.

## 1. Clarifying questions to ask the interviewer

These questions help establish the constraints and avoid solving a more complicated problem than necessary.

1. Are all moves guaranteed to be valid? Why: If invalid moves are possible, we need extra checks for occupied cells, out-of-range coordinates, and moves after the game ends.
2. Can the board size be any positive integer? Why: This tells us whether a solution that scans the board is acceptable or whether we should optimize for large boards.
3. Can we assume there are only two players, identified by `1` and `2`? Why: The counter-based solution relies on exactly two players taking alternating turns.
4. Must we return the winner immediately after each move? Why: The required response determines whether checking only the latest move is sufficient. Here, it is: a new winning line must include the newly placed mark.
5. Are we allowed to use \\(O(n)\\) auxiliary space? Why: Two arrays of length \\(n\\) plus two diagonal counters give an \\(O(n)\\)-space solution without storing the board.

The original problem's constraints support the optimized counter-based design.

## 2. Core intuition: How should we think about this in an interview?

Start with the simplest question:

After a player makes one move, what could have changed?

Suppose player 1 places a mark at `(1, 2)` on a \\(3 \times 3\\) board.

```
    col 0  col 1  col 2
       |      |      |
row 0  .      .      .
       |      |      |
row 1  .      .      X  <-- new move
       |      |      |
row 2  .      .      .
```

Only four possible winning lines are affected:

1. Row `1`
2. Column `2`
3. Main diagonal, if `row == col`
4. Anti-diagonal, if `row + col == n - 1`

We do not need to recheck unrelated rows, columns, or diagonals.

This observation gives us our first optimization.

### Step 1: From scanning everything to scanning relevant lines

A straightforward approach checks the whole board after every move. But every move only affects at most four lines, and each line contains \\(n\\) cells.

Therefore, we can reduce the cost of checking a move from \\(O(n^2)\\) to \\(O(n)\\).

Can we do even better?

### Step 2: Remember what we already know

Imagine row `1` has three cells.

```
.  X  X
```

We already know that player 1 has two marks in this row. There is no reason to recount those marks after the next move.

Instead, maintain a counter:

```
rows[1] = 2
```

When player 1 adds another mark to row `1`:

```
rows[1] = 3
```

Since the board size is `3`, player 1 wins.

The same idea applies to every column and both diagonals.

The mental model: Store the information you repeatedly need, update it incrementally, and avoid recomputing it from scratch.

### Step 3: Reduce the counters further using signed values

We could maintain separate counters for each player:

```
player1Rows[0 ... n-1]
player2Rows[0 ... n-1]

player1Cols[0 ... n-1]
player2Cols[0 ... n-1]
```

But there is a simpler technique: let player 1 contribute `+1` and player 2 contribute `-1`.

For example, consider a row on a board of size `3`.

A line is a winning line exactly when its signed counter reaches either \\(+n\\) or \\(-n\\).

Equivalently:

```
Math.abs(counter) == n
```

Why does this work?

- A line containing only player 1's marks sums to \\(+n\\).
- A line containing only player 2's marks sums to \\(-n\\).
- A mixed line cannot reach either extreme because the opposing marks cancel each other.

We now have the optimal approach: update a constant number of counters and check them immediately.

## 3. How the diagonal checks work

The two diagonals are the most common source of mistakes.

For a \\(3 \times 3\\) board:

```
Main diagonal:             Anti-diagonal:

X  .  .                    .  .  X
.  X  .                    .  X  .
.  .  X                    X  .  .
```

The main diagonal contains cells where:

```
row == col
```

Its positions are `(0,0)`, `(1,1)`, `(2,2)`.

The anti-diagonal contains cells where:

```
row + col == n - 1
```

Its positions are `(0,2)`, `(1,1)`, `(2,0)`.

Notice that the center cell `(1,1)` belongs to both diagonals. Therefore, when a move is at the center of an odd-sized board, both diagonal counters must be updated.

Do not use `if ... else if` for these conditions. Use two independent `if` statements.

## 4. Solution 1 — Brute force: Store the board and scan everything

The simplest implementation stores every move in an \\(n \times n\\) board. After each move, it checks every row, every column, and both diagonals.

```
class TicTacToeBruteForce {

    private final int n;
    private final int[][] board;

    TicTacToeBruteForce(int n) {
        this.n = n;

        // Keep the complete board because this approach checks the board
        // directly rather than maintaining any incremental statistics.
        this.board = new int[n][n];
    }

    int move(int row, int col, int player) {
        // Record the new move. The problem guarantees that the cell is empty.
        board[row][col] = player;

        // Check every row. A row wins if all n cells belong to this player.
        for (int r = 0; r < n; r++) {
            boolean complete = true;

            for (int c = 0; c < n; c++) {
                if (board[r][c] != player) {
                    complete = false;
                    break;
                }
            }

            if (complete) {
                return player;
            }
        }

        // Check every column in the same way.
        for (int c = 0; c < n; c++) {
            boolean complete = true;

            for (int r = 0; r < n; r++) {
                if (board[r][c] != player) {
                    complete = false;
                    break;
                }
            }

            if (complete) {
                return player;
            }
        }

        // Check the main diagonal: (0,0), (1,1), ..., (n-1,n-1).
        boolean mainDiagonalComplete = true;

        for (int i = 0; i < n; i++) {
            if (board[i][i] != player) {
                mainDiagonalComplete = false;
                break;
            }
        }

        if (mainDiagonalComplete) {
            return player;
        }

        // Check the anti-diagonal: (0,n-1), (1,n-2), ..., (n-1,0).
        boolean antiDiagonalComplete = true;

        for (int i = 0; i < n; i++) {
            if (board[i][n - 1 - i] != player) {
                antiDiagonalComplete = false;
                break;
            }
        }

        if (antiDiagonalComplete) {
            return player;
        }

        // No winning line was found after this move.
        return 0;
    }

    /*
     * TIME COMPLEXITY:
     * - Constructor: O(n^2), because it allocates an n x n board.
     * - Each move: O(n^2) worst case to inspect all rows and columns.
     *   Diagonal checks take O(n), which does not change the total.
     *
     * SPACE COMPLEXITY:
     * - O(n^2) for the board.
     *
     * INTERVIEW TAKEAWAY:
     * This is a correct baseline. Next, notice that only the row, column,
     * and possibly two diagonals through the latest move can newly win.
     */
}
```

### Why this approach is not optimal

For every move, we may inspect \\(n^2\\) cells even though only one cell has changed.

If the game has \\(m\\) moves, the worst-case total work is \\(O(mn^2)\\). Because there can be up to \\(n^2\\) moves, that can become \\(O(n^4)\\).

The obvious next step is to inspect only the lines affected by the move.

## 5. Solution 2 — Check only the affected lines

We still store the board, but we only scan the current row, current column, and diagonals that pass through the latest move.

```
class TicTacToeScanAffectedLines {

    private final int n;
    private final int[][] board;

    TicTacToeScanAffectedLines(int n) {
        this.n = n;
        this.board = new int[n][n];
    }

    int move(int row, int col, int player) {
        // Store the move so that we can inspect the affected lines.
        board[row][col] = player;

        // A new winning row must contain the cell just played.
        boolean rowComplete = true;

        for (int c = 0; c < n; c++) {
            if (board[row][c] != player) {
                rowComplete = false;
                break;
            }
        }

        if (rowComplete) {
            return player;
        }

        // A new winning column must also contain the cell just played.
        boolean colComplete = true;

        for (int r = 0; r < n; r++) {
            if (board[r][col] != player) {
                colComplete = false;
                break;
            }
        }

        if (colComplete) {
            return player;
        }

        // Only inspect the main diagonal if this move belongs to it.
        if (row == col) {
            boolean complete = true;

            for (int i = 0; i < n; i++) {
                if (board[i][i] != player) {
                    complete = false;
                    break;
                }
            }

            if (complete) {
                return player;
            }
        }

        // Only inspect the anti-diagonal if this move belongs to it.
        if (row + col == n - 1) {
            boolean complete = true;

            for (int i = 0; i < n; i++) {
                if (board[i][n - 1 - i] != player) {
                    complete = false;
                    break;
                }
            }

            if (complete) {
                return player;
            }
        }

        return 0;
    }

    /*
     * TIME COMPLEXITY:
     * - Constructor: O(n^2) to allocate the board.
     * - Each move: O(n) worst case, because we inspect at most four
     *   lines, and each line contains n cells.
     *
     * SPACE COMPLEXITY:
     * - O(n^2) for the board.
     *
     * WHY IT IS BETTER:
     * We avoid inspecting unrelated rows and columns.
     *
     * WHAT IS STILL WASTEFUL:
     * Suppose a row already contains two marks from player 1. We scan that
     * row again to rediscover those two marks on the next move.
     *
     * NEXT OPTIMIZATION:
     * Remember the counts instead of recounting the cells.
     */
}
```

This approach is much better, but every move still takes \\(O(n)\\) time in the worst case.

## 6. Solution 3 — Optimal: Signed row, column, and diagonal counters

This is the solution I would recommend in an interview.

### The state we maintain

For a board of size \\(n\\), maintain:

- `rows[r]`: signed sum of the marks in row `r`.
- `cols[c]`: signed sum of the marks in column `c`.
- `diagonal`: signed sum of the main diagonal.
- `antiDiagonal`: signed sum of the anti-diagonal.

The arrays contain \\(n\\) counters each, and there are two additional integer counters.

When a player makes a move, we update only the relevant counters.

```
class TicTacToe {

    private final int n;

    // rows[r] stores the signed sum of all marks in row r.
    // Player 1 contributes +1; player 2 contributes -1.
    private final int[] rows;

    // cols[c] stores the signed sum of all marks in column c.
    private final int[] cols;

    // Sum for the main diagonal, where row == col.
    private int diagonal;

    // Sum for the anti-diagonal, where row + col == n - 1.
    private int antiDiagonal;

    TicTacToe(int n) {
        this.n = n;

        // Zero-initialized counters represent an empty board.
        // We do not need a separate n x n board for winner detection.
        this.rows = new int[n];
        this.cols = new int[n];

        // Java initializes diagonal and antiDiagonal to zero automatically.
    }

    int move(int row, int col, int player) {

        // Convert the player ID into a signed contribution.
        // Player 1 adds +1, while player 2 adds -1.
        // This lets one counter represent both players without separate arrays.
        int contribution = (player == 1) ? 1 : -1;

        // Every move belongs to exactly one row and one column.
        rows[row] += contribution;
        cols[col] += contribution;

        // A move on the main diagonal contributes to that diagonal's sum.
        if (row == col) {
            diagonal += contribution;
        }

        // A move on the anti-diagonal contributes to its sum.
        // This is an independent condition: the center cell of an odd-sized
        // board belongs to both diagonals and must update both counters.
        if (row + col == n - 1) {
            antiDiagonal += contribution;
        }

        // A line can newly become a winning line only if it contains
        // the latest move. Therefore, checking these four counters is enough.
        //
        // A sum of +n means every cell belongs to player 1.
        // A sum of -n means every cell belongs to player 2.
        // Mixed lines cannot reach either value because +1 and -1 cancel.
        //
        // We check the current row, current column, and both diagonal sums.
        // Checking diagonal sums even for a non-diagonal move is harmless:
        // those sums have not changed and cannot newly become winning.
        if (Math.abs(rows[row]) == n
                || Math.abs(cols[col]) == n
                || Math.abs(diagonal) == n
                || Math.abs(antiDiagonal) == n) {

            // A valid winning line must belong to the player who just moved.
            // Return the original player ID, not the signed contribution.
            return player;
        }

        // No winning line was completed by this move.
        return 0;
    }

    /*
     * TIME COMPLEXITY:
     * - Constructor: O(n), because the two counter arrays contain n elements.
     * - Each move: O(1), because it performs a fixed number of array accesses,
     *   additions, comparisons, and at most two diagonal updates.
     *
     * SPACE COMPLEXITY:
     * - O(n) auxiliary space for the two arrays.
     * - O(1) additional scalar state.
     * - Total auxiliary space: O(n).
     *
     * CORRECTNESS:
     * Each counter is exactly the signed sum of the corresponding line's
     * marks. A line containing n marks from one player has absolute sum n.
     * A mixed line has a smaller absolute sum because opposing marks cancel.
     *
     * Every new winning line must contain the latest move because no other
     * cells changed. Thus, checking the affected counters detects every win.
     *
     * IMPORTANT ASSUMPTION:
     * This implementation relies on the problem guarantee that moves are
     * valid and that no moves are made after a winner is found. If those
     * guarantees are removed, extra state and validation are required.
     */
}
```

The signed-counter approach and its constant-time move processing are consistent with standard solutions to this problem.&#x20;

### Walk through an example

Suppose \\(n = 3\\), and player 1 is `X`, while player 2 is `O`.

| Move    | Player | `rows[2]` | `cols[1]` | Result |
| ------- | ------ | --------- | --------- | ------ |
| `(2,0)` | 1      | 1         | 0         | 0      |
| `(1,0)` | 2      | 1         | 0         | 0      |
| `(2,1)` | 1      | 2         | 1         | 0      |
| `(2,2)` | 2      | 1         | 0         | 0      |

This example illustrates why counting only a row's total number of occupied cells is insufficient: the marks must belong to the same player.

Now consider the actual winning sequence:

```
move(0, 0, 1) -> 0
move(0, 2, 2) -> 0
move(2, 2, 1) -> 0
move(1, 1, 2) -> 0
move(2, 0, 1) -> 0
move(1, 0, 2) -> 0
move(2, 1, 1) -> 1
```

On the last move, player 1 places a mark at `(2,1)`.

The third row now contains:

```
X  X  X
```

Its signed sum becomes:

\\[ 1+1+1=3 \\]

Since `n = 3`, `Math.abs(rows[2]) == n` is true, so the method returns `1`.

### Complexity comparison

| Approach             | Constructor  | Per move     | Auxiliary space |
| -------------------- | ------------ | ------------ | --------------- |
| Scan the whole board | \\(O(n^2)\\) | \\(O(n^2)\\) | \\(O(n^2)\\)    |
| Scan affected lines  | \\(O(n^2)\\) | \\(O(n)\\)   | \\(O(n^2)\\)    |
| Signed counters      | \\(O(n)\\)   | \\(O(1)\\)   | \\(O(n)\\)      |

The optimal approach reduces the move operation to constant time, with linear auxiliary space.&#x20;

## 7. Edge cases to watch out for

1. Winning the main diagonal. Check `row == col`.
2. Winning the anti-diagonal. Check `row + col == n - 1`.
3. Center cell belongs to both diagonals. Use two independent `if` statements.
4. Mixed players in a line. A line containing both players must not be considered a win merely because all cells are occupied.
5. First move. All counters start at zero; one mark cannot win when \\(n \ge 2\\).
6. Last available move. A full board with no winning line returns `0` on the final move. A draw does not have a separate return value in this API.
7. Invalid moves. The LeetCode constraints guarantee valid moves. If this is a real production API, validate coordinates, occupied cells, player IDs, and game-over state.
8. Moves after a win. The problem guarantees these will not occur. A production implementation should store the winner and reject subsequent moves if necessary.

## 8. Interview follow-up questions and answers

Q1. Why can we check only the row and column containing the latest move?

Because the move changes only one cell. A previously incomplete row or column that does not contain that cell remains unchanged. It cannot become a winning line.

Q2. Why does the signed-counter technique work?

Player 1 contributes `+1`, and player 2 contributes `-1`. A line containing only one player's marks reaches either `+n` or `-n`. Mixed marks cancel, so their absolute sum remains less than `n`.

Q3. Could we maintain separate counters for both players instead?

Yes. We could store counts for each player's rows, columns, and diagonals, then check whether any count reaches `n`. This is also \\(O(1)\\) per move, but requires more counters.

Q4. Can we eliminate the arrays and use only constant space?

Not with this particular counter-based approach if we want to track every row and column independently for arbitrary board sizes. The arrays require \\(O(n)\\) space. Other representations may trade off update time, storage, and complexity.

Q5. What if the game supports \\(k\\) players?

The signed-counter technique in its current form no longer works directly because assigning opposing signs to more than two players does not guarantee that mixed lines cancel correctly. We would generally maintain per-player counts for each row, column, and diagonal, increasing the space to \\(O(kn)\\), while still supporting \\(O(1)\\) time per move for fixed \\(k\\).

Q6. What if we need to support undoing moves?

We would need to store move history so that we could reverse the affected counters. Each undo would subtract the original move's signed contribution from its row, column, and any relevant diagonals. If undo is allowed only in reverse chronological order, a stack of moves is sufficient.

Q7. How would you test the implementation?

Test a row win, a column win, both diagonal wins, a mixed line, a center move belonging to both diagonals, and a complete board that ends in a draw. Also verify that every non-winning move returns `0`.

## Final interview takeaway

The important lesson is not simply to memorize the four counters. It is to recognize the optimization pattern:

1. Identify what changes after an operation.
2. Determine which conditions could become true because of that change.
3. Maintain just enough state to evaluate those conditions incrementally.
4. Replace repeated scanning with constant-time updates.

This pattern appears in many design problems: maintaining running totals, tracking counts by category, incremental statistics, and avoiding repeated work in stateful APIs.
