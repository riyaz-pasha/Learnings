# LeetCode 362 — Design Hit Counter

Difficulty: Medium Main concepts: Queue, Deque, Sliding Window, Circular Array, Data Structure Design

Problem: [Design Hit Counter — LeetCode 362](https://leetcode.com/problems/design-hit-counter/description/?utm_source=chatgpt.com)

## 0. Understand the problem in simple terms

You need to design a counter that records events called hits and can answer:

How many hits occurred in the most recent 5 minutes?

The problem uses timestamps measured in seconds. Each hit has a timestamp, and `getHits(timestamp)` returns the number of hits in the previous 300 seconds, including the current timestamp.

For example, suppose these hits occur:

```
Timestamp: 1, 2, 3, 300, 301
```

At timestamp `301`, we want to count hits in this interval:

```
(301 - 300, 301] = (1, 301]
```

So the hit at timestamp `1` is excluded, while the hits at `2`, `3`, `300`, and `301` are included.

The answer is `4`.

The key detail is that the window contains the current timestamp and the preceding 299 seconds, not 300 seconds before the current timestamp plus the current second.

### What operations must we support?

```
hit(timestamp);        // Record one hit.
getHits(timestamp);    // Count hits in the latest 300 seconds.
```

The original problem guarantees that calls arrive in non-decreasing timestamp order, and `hit` and `getHits` are called with valid timestamps. This assumption is important because it lets us discard old hits permanently.

## 1. Clarifying questions to ask the interviewer

These questions help identify which data structure is appropriate.

1. Can timestamps arrive out of order? Why ask: If timestamps are chronological, a FIFO queue works naturally. If events arrive out of order, we need a different strategy.
2. Can multiple hits have the same timestamp? Why ask: Yes, multiple hits can occur in one second. We must count every hit, not just distinct timestamps.
3. Does the 300-second window include a hit exactly 300 seconds old? Why ask: This determines the expiration condition. For a query at time `301`, a hit at time `1` must be excluded. The window is `(timestamp - 300, timestamp]`.
4. How much memory should we use if the hit volume becomes enormous? Why ask: Storing each individual hit is simple, but storing a count per second can reduce memory substantially.
5. Are queries guaranteed to be chronological too? Why ask: If query timestamps never go backward, we can permanently remove expired hits. The original problem guarantees chronological calls.

## 2. Core intuition: think in terms of a sliding window

The most important interview insight is this:

We don't need to remember hits that can never affect a future answer.

Imagine the current time is `305`. A hit at time `2` is too old because:

```
305 - 2 = 303 seconds
```

It can never become relevant again because time only moves forward. Therefore, we can safely discard it.

This leads us to a queue.

### Why a queue fits naturally

Suppose the recorded hits are:

```
Front                                      Back
  |                                          |
 [1, 2, 3, 300, 300, 301]
```

The oldest hit is at the front. Since timestamps arrive in chronological order:

- The queue is already sorted by time.
- Expired hits always appear at the front.
- Once the front hit is valid, every hit behind it is also valid.

So the algorithm is straightforward:

1. `hit(timestamp)`: append the timestamp to the queue.
2. `getHits(timestamp)`: remove expired timestamps from the front.
3. Return the queue's size.

### Visualize the window

At time `301`, the valid interval is:

```
(timestamp - 300, timestamp]
           (1, 301]

Time:   1    2    3    ...   300   301
        X    ✓    ✓           ✓     ✓
```

The hit at `1` expires; the other hits remain.

This is the sliding-window pattern: as time advances, the left boundary moves forward, and old data leaves the window.

## 3. Solution 1 — Brute force

The simplest solution stores every hit timestamp and scans all recorded hits whenever `getHits` is called.

```
import java.util.ArrayList;
import java.util.List;

class HitCounterBruteForce {

    // Store every hit, including multiple hits at the same timestamp.
    private final List<Integer> timestamps = new ArrayList<>();

    public void hit(int timestamp) {
        timestamps.add(timestamp);
    }

    public int getHits(int timestamp) {
        int count = 0;
        int earliestValidTimestamp = timestamp - 299;

        // Check every hit and count only those in [timestamp - 299, timestamp].
        for (int hitTime : timestamps) {
            if (hitTime >= earliestValidTimestamp && hitTime <= timestamp) {
                count++;
            }
        }

        return count;
    }

    /*
     * TIME COMPLEXITY:
     * hit(): O(1) amortized, because ArrayList appends are amortized O(1).
     * getHits(): O(n), because every stored timestamp is examined.
     *
     * SPACE COMPLEXITY:
     * O(n), where n is the total number of hits ever recorded.
     *
     * WHY IT WORKS:
     * Every hit is stored, so scanning all timestamps lets us count
     * exactly those inside the required time interval.
     *
     * WHY IT IS NOT IDEAL:
     * Hits older than five minutes remain in memory forever.
     * Repeated queries must repeatedly scan irrelevant historical hits.
     */
}
```

This solution is easy to understand and useful as a starting point. However, it wastes both time and memory as the history grows.

## 4. Solution 2 — Queue with lazy removal (recommended interview solution)

This is the best solution to explain first in an interview because its reasoning directly follows from the chronological timestamp guarantee.

### How to derive it from brute force

Brute force scans every timestamp. Ask yourself:

> Which timestamps can I safely stop considering?

Any timestamp at or before `timestamp - 300` has expired. Since timestamps are sorted, all expired entries are at the front.

Instead of scanning everything, we remove those entries once and retain only relevant hits.

```
import java.util.ArrayDeque;
import java.util.Deque;

class HitCounter {

    // Each entry represents one hit.
    // ArrayDeque provides efficient insertion at the back and removal at the front.
    private final Deque<Integer> hitTimestamps = new ArrayDeque<>();

    public HitCounter() {
        // An empty queue means that no hits have been recorded.
    }

    public void hit(int timestamp) {
        // Calls arrive chronologically, so each new hit belongs at the back.
        // Store duplicate timestamps too: each call represents a separate hit.
        hitTimestamps.offerLast(timestamp);
    }

    public int getHits(int timestamp) {
        // A hit is valid only if timestamp - hitTime < 300.
        // Equivalently, hitTime must be strictly greater than timestamp - 300.
        int expirationBoundary = timestamp - 300;

        // Remove every hit that is exactly 300 seconds old or older.
        // The empty check prevents accessing the front of an empty queue.
        while (!hitTimestamps.isEmpty()
                && hitTimestamps.peekFirst() <= expirationBoundary) {
            hitTimestamps.pollFirst();
        }

        // Every remaining timestamp belongs to the current 300-second window.
        return hitTimestamps.size();
    }

    /*
     * TIME COMPLEXITY:
     *
     * hit(): O(1).
     * - Appending one timestamp to the deque takes O(1).
     *
     * getHits(): O(k) for one call in the worst case, where k is the
     * number of expired entries removed during that call.
     * - Each removal takes O(1).
     * - A single query can remove many old entries if time jumps forward.
     *
     * AMORTIZED COMPLEXITY:
     * - O(1) per operation over a sequence of calls.
     * - Every hit is appended exactly once and removed at most once.
     * - Across N calls, the total number of removals is at most the
     *   total number of hits, so cleanup work is O(N) overall.
     *
     * SPACE COMPLEXITY:
     * - O(h), where h is the number of hits retained in the queue.
     * - After getHits(t), retained hits are strictly newer than t - 300.
     * - If queries are infrequent, the queue can temporarily contain
     *   old hits until the next query performs cleanup.
     *
     * CORRECTNESS:
     * - Calls arrive chronologically, so the queue is ordered by timestamp.
     * - Expired hits form a prefix of the queue.
     * - Removing that prefix leaves exactly the hits in the valid window.
     * - The queue size therefore equals the required hit count.
     */
}
```

### Dry run: understand every operation

Consider these calls:

```
hit(1);
hit(2);
hit(3);
getHits(4);
hit(300);
getHits(300);
getHits(301);
```

| Operation      | Queue after operation | Result |
| -------------- | --------------------- | ------ |
| `hit(1)`       | `[1]`                 | —      |
| `hit(2)`       | `[1, 2]`              | —      |
| `hit(3)`       | `[1, 2, 3]`           | —      |
| `getHits(4)`   | `[1, 2, 3]`           | 3      |
| `hit(300)`     | `[1, 2, 3, 300]`      | —      |
| `getHits(300)` | `[1, 2, 3, 300]`      | 4      |
| `getHits(301)` | `[2, 3, 300]`         | 3      |

The critical transition happens at `getHits(301)`:

```
Current time = 301
Expiration boundary = 301 - 300 = 1

Queue before cleanup:
Front
  |
 [1, 2, 3, 300]
  |
 Back

1 <= 1  -> remove 1
2 <= 1  -> false; stop

Queue after cleanup:
 [2, 3, 300]
```

Notice why we use `<=`, rather than `<`, in the expiration condition. A hit at timestamp `1` is exactly 300 seconds old at timestamp `301`, so it must be excluded.

### Why doesn't cleanup lose information?

Suppose `hit(10)` is recorded, and later `getHits(310)` removes it.

Could any future query need that hit?

No. Future query timestamps cannot be less than `310`, so the hit at `10` will always be at least 300 seconds old. Removing it is permanent and safe.

This is called lazy removal: we remove expired entries when the next query needs the current count, rather than continuously maintaining a perfectly clean queue.

## 5. Solution 3 — Circular array with 300 buckets

The queue stores one integer for every individual hit. But the problem measures time in whole seconds, and we only care about a 300-second window.

That suggests a better question:

> Do we really need to store every hit, or can we store the number of hits for each second?

For example, these events:

```
hit(10)
hit(10)
hit(10)
hit(11)
hit(12)
```

can be represented as:

```
Second:       10   11   12
Hit count:     3    1    1
```

We can store these counts in two arrays of length 300:

- `timestamps[i]`: which actual second the bucket represents.
- `hitCounts[i]`: how many hits occurred during that second.

### Why use modulo 300?

A window is 300 seconds long, so seconds separated by 300 map to the same bucket.

```
10 % 300  = 10
310 % 300 = 10
610 % 300 = 10
```

This means bucket `10` can represent second `10`, then second `310`, then second `610`.

But a bucket must never confuse two different seconds. That's why we store the actual timestamp alongside the count.

When a hit arrives:

1. Calculate `index = timestamp % 300`.
2. If `timestamps[index] != timestamp`, this bucket represents an old second. Reset it for the new second.
3. Otherwise, increment the existing count.

When a query arrives, inspect all 300 buckets and add the counts belonging to the current window.

### Java implementation

```
class HitCounterCircularArray {

    private static final int WINDOW_SECONDS = 300;

    // Each index represents one of the 300 possible circular buckets.
    private final int[] timestamps = new int[WINDOW_SECONDS];
    private final int[] hitCounts = new int[WINDOW_SECONDS];

    public void hit(int timestamp) {
        int index = timestamp % WINDOW_SECONDS;

        // The bucket may belong to an earlier second that shares this index.
        // If so, overwrite that stale second and start its new count at 1.
        if (timestamps[index] != timestamp) {
            timestamps[index] = timestamp;
            hitCounts[index] = 1;
        } else {
            // Multiple hits during the same second share the same bucket.
            hitCounts[index]++;
        }
    }

    public int getHits(int timestamp) {
        int totalHits = 0;
        int earliestValidTimestamp = timestamp - WINDOW_SECONDS + 1;

        // Examine all 300 buckets.
        for (int i = 0; i < WINDOW_SECONDS; i++) {
            // Only count buckets whose actual timestamp lies in the window.
            // Checking the actual timestamp prevents counting stale data
            // left behind by circular-index reuse.
            if (timestamps[i] >= earliestValidTimestamp
                    && timestamps[i] <= timestamp) {
                totalHits += hitCounts[i];
            }
        }

        return totalHits;
    }

    /*
     * TIME COMPLEXITY:
     * hit(): O(1).
     * - Compute the bucket index and update at most one bucket.
     *
     * getHits(): O(300) = O(1).
     * - Always examines exactly 300 buckets, independent of hit volume.
     *
     * SPACE COMPLEXITY:
     * O(300) = O(1).
     * - Two fixed-size arrays, regardless of how many hits occur.
     *
     * WHY THIS SCALES BETTER:
     * - A million hits in the same second require only one bucket.
     * - The queue solution would store a million separate timestamps.
     *
     * TRADE-OFF:
     * - Queries inspect all 300 buckets instead of returning a queue size.
     * - For this fixed window, that is a small, constant amount of work.
     */
}
```

### A subtle point about bucket reuse

Suppose we record:

```
hit(10);
hit(310);
```

Both timestamps map to index `10`, because:

```
10  % 300 = 10
310 % 300 = 10
```

When `hit(310)` arrives, it replaces the old bucket contents:

```
Before hit(310):
timestamps[10] = 10
hitCounts[10]  = 1

After hit(310):
timestamps[10] = 310
hitCounts[10]  = 1
```

That is safe because timestamp `10` is already 300 seconds old at time `310`, and can never belong to a future valid window.

Important: The actual timestamp check is essential. An index alone cannot tell us whether its count belongs to the current second or an earlier second.

## 6. Comparing the solutions

| Approach       | `hit()`        | `getHits()`                     | Space         | Best use                                       |
| -------------- | -------------- | ------------------------------- | ------------- | ---------------------------------------------- |
| Brute force    | O(1) amortized | O(n)                            | O(n)          | Understanding the problem                      |
| Queue          | O(1)           | O(k) worst case, O(1) amortized | O(h)          | Best for explaining the sliding-window pattern |
| Circular array | O(1)           | O(300) = O(1)                   | O(300) = O(1) | High-volume hits with a fixed window           |

Here:

- `n` is the total number of hits ever recorded by brute force.
- `k` is the number of expired queue entries removed by a particular query.
- `h` is the number of hit timestamps retained by the queue.

For the original constraints, the queue is a strong choice. If the interviewer emphasizes millions of hits per second, the circular array is more memory-efficient because it stores at most 300 timestamp buckets.

## 7. Edge cases to watch out for

| Case                        | Example                   | Expected behavior      |
| --------------------------- | ------------------------- | ---------------------- |
| No hits recorded            | `getHits(100)`            | Return `0`             |
| Multiple hits in one second | Three calls to `hit(10)`  | Count all three        |
| Hit exactly 299 seconds old | `hit(1)`, `getHits(300)`  | Count it               |
| Hit exactly 300 seconds old | `hit(1)`, `getHits(301)`  | Exclude it             |
| Large time jump             | `hit(1)`, `getHits(1000)` | Return `0`             |
| Circular bucket reuse       | `hit(10)`, `hit(310)`     | Replace the old bucket |

For the queue implementation, the key condition is:

```
while (!hitTimestamps.isEmpty()
        && hitTimestamps.peekFirst() <= timestamp - 300) {
    hitTimestamps.pollFirst();
}
```

For the circular-array implementation, the key condition is:

```
if (timestamps[index] != timestamp) {
    timestamps[index] = timestamp;
    hitCounts[index] = 1;
}
```

The first condition removes stale hits. The second resets stale buckets. Both are based on the same principle: old information must not affect the current window.

## 8. Interviewer follow-up questions and answers

### Q1. Why is the queue solution amortized O(1) if one query can remove many entries?

Because each hit is inserted once and removed at most once. Across the entire sequence of operations, the total cleanup work is linear in the number of hits, even though one individual query can take longer.

### Q2. What if timestamps arrive out of order?

The queue strategy no longer works directly because an old hit could arrive after newer hits, so expired entries would not necessarily form a prefix.

We would need a different design, such as a time-indexed structure, an ordered map, or a mechanism to handle late-arriving events.

### Q3. What if the window changes from 300 seconds to 10 minutes?

For the queue solution, change the expiration duration to `600`.

For the circular array, increase the bucket count to `600` because the array must represent 600 distinct seconds.

### Q4. What if a single second receives billions of hits?

The queue stores each hit separately, which can consume enormous amounts of memory. The circular-array approach aggregates hits by second and therefore uses fixed memory.

However, its count type must be large enough. If a bucket or total can exceed the maximum `int`, use `long` for the counts and return type where the API permits it.

### Q5. Can we make `getHits()` O(1) worst case with the circular array?

Yes. The circular array already makes each query O(300), which is constant time for this fixed window. If you want to avoid even the 300-bucket scan, you can maintain a running total and carefully expire the bucket that falls out of the window as time advances. That design needs additional state and careful handling of time jumps and bucket reuse.

### Q6. Which solution should I present first in an interview?

Present the queue solution first.

It demonstrates the key reasoning clearly:

1. The timestamps are chronological.
2. Old hits expire permanently.
3. Expired hits appear at the front.
4. A queue removes them efficiently.
5. Each hit is processed only a constant number of times.

Then discuss the circular array as the optimization for high-volume traffic.

## 9. Final mental model

Think of this problem as a line of events moving through time.

```
New hits arrive at the back.
          |
          v
 [oldest] [hit] [hit] [hit] [newest]
    |
    v
Remove hits outside the 300-second window.
```

The queue solution works because expired hits leave in the same order they arrived. The circular-array solution works because we only need one aggregated count per second.

Both approaches exploit the same observation: time moves forward, and data that has expired never becomes relevant again.

That is the main interview pattern to recognize—not just for hit counters, but also for sliding-window event counts, request-rate tracking, and time-based statistics.

# Design Hit Counter — Interview Follow-ups and Alternative Solutions

The best way to master LeetCode 362 is to understand how the solution changes when the interviewer changes one assumption.

The original problem has three important properties:

1. Timestamps arrive in non-decreasing order.
2. The window is fixed at 300 seconds.
3. Every hit counts, including multiple hits at the same timestamp.

Change any of these properties, and the best data structure may change.

We'll use modern Java and build from the original queue solution toward more advanced designs. All implementations below are independent alternatives, not classes that need to be combined.

## 1. Quick decision guide

| Interview scenario                         | Suitable approach                    | Query complexity                      |
| ------------------------------------------ | ------------------------------------ | ------------------------------------- |
| Original problem, chronological timestamps | Queue of timestamps                  | O(1) amortized                        |
| Huge hit volume, fixed 300-second window   | Circular array of counts             | O(1)                                  |
| Huge hit volume, variable window size      | Queue of timestamp/count pairs       | O(k) amortized per hit/query sequence |
| Need O(1) query even after time jumps      | Circular buckets with running total  | O(1)                                  |
| Out-of-order events, arbitrary timestamps  | Ordered map or time buckets          | Depends on operations                 |
| Need historical queries at arbitrary times | Prefix sums / ordered event history  | O(log n) or O(1) after preprocessing  |
| Multiple concurrent callers                | Lock-protected or concurrent design  | Depends on synchronization            |
| Distributed service across many servers    | Partitioned counters and aggregation | Depends on consistency requirements   |

Here, `k` denotes the number of expired entries processed, and `n` denotes the number of stored events or time buckets.

## 2. Follow-up A: What if hits arrive in chronological order, but traffic is enormous?

Use a circular array with counts.

This is the standard optimization when the time resolution is one second and the window is fixed.

The queue stores each event individually. But if a server receives 100,000 hits during the same second, storing 100,000 timestamps is unnecessary. We can store one count for that second.

```
Individual events:
[10, 10, 10, 10, 10, 11, 11, 12]

Aggregated events:
Second:      10   11   12
Hit count:    5    2    1
```

The circular array has 300 buckets. Each bucket stores its actual timestamp and the number of hits for that second.

```
class HitCounterFixedWindow {

    private static final int WINDOW = 300;

    // Bucket i represents the second timestamps[i], not every second forever.
    private final int[] timestamps = new int[WINDOW];
    private final int[] counts = new int[WINDOW];

    public void hit(int timestamp) {
        int index = timestamp % WINDOW;

        // A different timestamp means this circular bucket has been reused.
        if (timestamps[index] != timestamp) {
            timestamps[index] = timestamp;
            counts[index] = 1;
        } else {
            // Multiple hits during the same second share one bucket.
            counts[index]++;
        }
    }

    public int getHits(int timestamp) {
        int total = 0;
        int firstValidSecond = timestamp - WINDOW + 1;

        for (int i = 0; i < WINDOW; i++) {
            // Validate the actual timestamp to avoid counting stale buckets.
            if (timestamps[i] >= firstValidSecond
                    && timestamps[i] <= timestamp) {
                total += counts[i];
            }
        }

        return total;
    }

    /*
     * hit(): O(1) time.
     * getHits(): O(300) = O(1) time for the fixed window.
     * Space: O(300) = O(1).
     *
     * Best when:
     * - Timestamps have one-second resolution.
     * - The window is fixed.
     * - Hit volume is high.
     *
     * Limitation:
     * - If timestamps can jump backward, bucket overwriting can destroy
     *   information needed for an older query.
     * - Counts can overflow int under sufficiently high traffic.
     */
}
```

Interview takeaway: Aggregate events at the granularity of the query. If you only need counts per second, individual events are often unnecessary.

## 3. Follow-up B: Can both `hit()` and `getHits()` be O(1) without scanning all 300 buckets?

Yes. Maintain a running total alongside the circular array.

The previous circular-array solution scans 300 buckets for every query. Although that is O(1) asymptotically for a fixed window, we can avoid that scan.

### The mental model

Maintain this invariant:

```
runningTotal = sum of hits in the current 300-second window
```

Whenever time advances:

1. Identify buckets that have expired.
2. Subtract their counts from `runningTotal`.
3. Clear those buckets.
4. Record new hits by incrementing the relevant bucket and `runningTotal`.

There is a subtlety: time may jump from `10` to `1_000_000`. We must not loop through every second in that gap. Instead, inspect the 300 buckets and expire any that are stale.

```
class HitCounterRunningTotal {

    private static final int WINDOW = 300;

    // -1 means that the bucket has not yet been assigned a timestamp.
    private final int[] timestamps = new int[WINDOW];
    private final long[] counts = new long[WINDOW];

    // Sum of counts in the most recently advanced window.
    private long runningTotal;

    public HitCounterRunningTotal() {
        java.util.Arrays.fill(timestamps, -1);
    }

    public void hit(int timestamp) {
        advanceTo(timestamp);

        int index = timestamp % WINDOW;

        // If this slot represents another second, its previous count is stale.
        if (timestamps[index] != timestamp) {
            timestamps[index] = timestamp;
            counts[index] = 0;
        }

        counts[index]++;
        runningTotal++;
    }

    public long getHits(int timestamp) {
        advanceTo(timestamp);
        return runningTotal;
    }

    private void advanceTo(int timestamp) {
        int earliestValidSecond = timestamp - WINDOW + 1;

        // Inspect every bucket to handle both ordinary progression and
        // large jumps in time without iterating through every missing second.
        for (int i = 0; i < WINDOW; i++) {
            if (timestamps[i] != -1
                    && timestamps[i] < earliestValidSecond) {
                runningTotal -= counts[i];
                counts[i] = 0;
                timestamps[i] = -1;
            }
        }
    }

    /*
     * hit(): O(300) = O(1) for the fixed window.
     * getHits(): O(300) = O(1) for the fixed window.
     * Space: O(300) = O(1).
     *
     * The actual query result is returned in O(1) after maintenance.
     * Overall query time remains O(1) because maintenance checks a fixed
     * number of buckets.
     *
     * Why the invariant holds:
     * - Expiring a bucket subtracts its contribution exactly once.
     * - Adding a hit increments both its bucket and the total.
     * - Therefore, runningTotal always equals the current window's count
     *   after advanceTo(timestamp) completes.
     *
     * Assumption:
     * - Calls are chronological.
     * - The current window is defined by the latest supplied timestamp.
     */
}
```

Why is the expiration comparison `< earliestValidSecond` rather than `<= timestamp - 300`? They are equivalent because `earliestValidSecond = timestamp - 299`.

For example, at time `301`, the earliest valid second is `2`. A bucket for second `1` expires; a bucket for second `2` remains.

Interview takeaway: When a query repeatedly asks for a sum over a moving window, consider maintaining the sum incrementally rather than recomputing it.

## 4. Follow-up C: What if the window duration is configurable?

Suppose the interviewer changes the API to:

```
hit(timestamp);
getHits(timestamp, windowSeconds);
```

Now the window might be 60 seconds for one query and 300 seconds for another.

A circular array sized to 300 is no longer automatically sufficient. More importantly, you must not permanently discard hits just because they are too old for a short query: a later query might request a wider window.

### Approach: Store timestamp/count pairs

Aggregate hits sharing a timestamp, and retain a configured maximum history. For queries, sum the buckets that fall within the requested window.

The constructor below specifies the largest supported window. Every query must request a window no larger than that limit.

```
import java.util.ArrayDeque;
import java.util.Deque;

class HitCounterVariableWindow {

    // One entry stores all hits recorded during one second.
    private record HitBucket(int timestamp, long count) {}

    private final int maxWindowSeconds;
    private final Deque<HitBucket> buckets = new ArrayDeque<>();

    public HitCounterVariableWindow(int maxWindowSeconds) {
        if (maxWindowSeconds <= 0) {
            throw new IllegalArgumentException(
                    "Maximum window must be positive");
        }

        this.maxWindowSeconds = maxWindowSeconds;
    }

    public void hit(int timestamp) {
        // Remove history older than the largest window we promise to support.
        expireBefore(timestamp - maxWindowSeconds + 1);

        HitBucket latest = buckets.peekLast();

        if (latest != null && latest.timestamp() == timestamp) {
            // Aggregate another hit in the same second.
            buckets.removeLast();
            buckets.addLast(
                    new HitBucket(timestamp, latest.count() + 1));
        } else {
            buckets.addLast(new HitBucket(timestamp, 1));
        }
    }

    public long getHits(int timestamp, int windowSeconds) {
        if (windowSeconds <= 0 || windowSeconds > maxWindowSeconds) {
            throw new IllegalArgumentException(
                    "Window must be between 1 and maxWindowSeconds");
        }

        // This method assumes chronological calls, as in the original problem.
        expireBefore(timestamp - maxWindowSeconds + 1);

        int earliestValidSecond = timestamp - windowSeconds + 1;
        long total = 0;

        // Iterate from newest to oldest. Once a timestamp is too old,
        // all entries before it are also too old, so stop immediately.
        for (var iterator = buckets.descendingIterator();
             iterator.hasNext();) {
            HitBucket bucket = iterator.next();

            if (bucket.timestamp() < earliestValidSecond) {
                break;
            }

            if (bucket.timestamp() <= timestamp) {
                total += bucket.count();
            }
        }

        return total;
    }

    private void expireBefore(int earliestRetainedSecond) {
        // Because calls are chronological, expired buckets form a prefix.
        while (!buckets.isEmpty()
                && buckets.peekFirst().timestamp() < earliestRetainedSecond) {
            buckets.removeFirst();
        }
    }

    /*
     * hit(): O(1) amortized, excluding any cleanup; each bucket is removed
     * at most once over the lifetime of the structure.
     *
     * getHits(): O(b), where b is the number of retained per-second buckets
     * inspected for that query.
     *
     * Space: O(m), where m is the number of distinct hit seconds retained
     * within the maximum supported window.
     *
     * Why the maximum window matters:
     * - A short query must not destroy history needed by a wider query.
     * - Retaining the maximum supported window makes permanent expiration safe.
     *
     * Why aggregate by second:
     * - Many hits at the same timestamp use one queue entry.
     */
}
```

For a query at second `1000`:

```
getHits(1000, 60)   -> count seconds 941 through 1000
getHits(1000, 300) -> count seconds 701 through 1000
```

If the API instead allows arbitrary window sizes with no upper bound, you cannot safely discard history based on a fixed maximum. You would need a different retention policy or explicitly define how much historical data is kept.

## 5. Follow-up D: What if hits arrive out of order?

The original queue solution depends on chronological timestamps. If the interviewer removes that guarantee, a hit at time `10` might arrive after a hit at time `100`.

Consider:

```
Arrival order: 100, 105, 10
Timestamp order: 10, 100, 105
```

The queue is no longer sorted by timestamp. The oldest event may not be at the front, so removing entries from the front becomes incorrect.

### Approach: `TreeMap` keyed by timestamp

Use a sorted map to aggregate hits by timestamp.

```
import java.util.NavigableMap;
import java.util.TreeMap;

class HitCounterOutOfOrder {

    // Key = event timestamp; value = number of hits at that timestamp.
    private final NavigableMap<Integer, Long> hitsByTimestamp =
            new TreeMap<>();

    public void hit(int timestamp) {
        // merge handles duplicate timestamps and out-of-order arrivals.
        hitsByTimestamp.merge(timestamp, 1L, Long::sum);
    }

    public long getHits(int timestamp) {
        int earliestValidSecond = timestamp - 299;

        // Obtain only timestamps in the inclusive interval
        // [timestamp - 299, timestamp].
        var relevantHits = hitsByTimestamp.subMap(
                earliestValidSecond, true,
                timestamp, true);

        long total = 0;

        for (long count : relevantHits.values()) {
            total += count;
        }

        return total;
    }

    /*
     * hit(): O(log n), where n is the number of distinct stored timestamps.
     *
     * getHits(): O(log n + k), where k is the number of distinct timestamps
     * in the requested interval.
     *
     * Space: O(n), because this version retains the entire timestamp history.
     *
     * Advantages:
     * - Hits can arrive in arbitrary timestamp order.
     * - Duplicate timestamps are aggregated.
     * - Queries can target a timestamp earlier than the latest arrival.
     *
     * Limitation:
     * - This simple version never deletes old history.
     * - It can support arbitrary historical queries only while that history
     *   is retained.
     */
}
```

### Why not just use a `HashMap`?

A `HashMap` can aggregate counts by timestamp, but it does not keep keys sorted. A query would need to scan all stored timestamps to determine which are in the window.

A `TreeMap` is appropriate when the timestamps themselves must be ordered.

Important distinction: Handling out-of-order arrivals is not the same as supporting arbitrary historical queries. If you discard old data to save memory, you can no longer answer every past query.

## 6. Follow-up E: What if the interviewer asks for historical queries?

Suppose the service must answer:

```
getHits(100);
getHits(500);
getHits(100);
```

The query timestamp can move backward. A destructive sliding-window queue is unsuitable because it permanently removes old hits.

There are two common scenarios.

### Scenario 1: Events are known in advance

If all events are available before queries begin, sort them and build prefix sums.

The prefix sum tells us how many hits occurred up to a particular timestamp. We can calculate a window count by subtracting the prefix sum before the window from the prefix sum at the window's end.

```
import java.util.Arrays;

class HistoricalHitCounter {

    private final int[] times;
    private final long[] prefix;

    public HistoricalHitCounter(int[] eventTimestamps) {
        // Clone so sorting doesn't unexpectedly mutate the caller's array.
        times = eventTimestamps.clone();
        Arrays.sort(times);

        // prefix[i] counts events in times[0..i-1].
        // prefix[0] = 0 represents an empty prefix.
        prefix = new long[times.length + 1];

        for (int i = 0; i < times.length; i++) {
            prefix[i + 1] = prefix[i] + 1;
        }
    }

    public long getHits(int timestamp) {
        int earliestValidSecond = timestamp - 299;

        // First index whose timestamp is >= earliestValidSecond.
        int left = lowerBound(times, earliestValidSecond);

        // First index whose timestamp is > timestamp.
        int right = upperBound(times, timestamp);

        // Number of events in the half-open array range [left, right).
        return prefix[right] - prefix[left];
    }

    private static int lowerBound(int[] values, int target) {
        int left = 0;
        int right = values.length;

        while (left < right) {
            int middle = left + (right - left) / 2;

            if (values[middle] < target) {
                left = middle + 1;
            } else {
                right = middle;
            }
        }

        return left;
    }

    private static int upperBound(int[] values, int target) {
        int left = 0;
        int right = values.length;

        while (left < right) {
            int middle = left + (right - left) / 2;

            if (values[middle] <= target) {
                left = middle + 1;
            } else {
                right = middle;
            }
        }

        return left;
    }

    /*
     * Preprocessing:
     * - O(n log n) to sort.
     * - O(n) to build prefix sums.
     *
     * getHits(): O(log n), because two binary searches find the range.
     *
     * Space: O(n) for sorted timestamps and prefix sums.
     *
     * Best when:
     * - The event history is known or finalized before querying.
     * - Many queries need different historical windows.
     *
     * Limitation:
     * - This implementation does not support inserting new events after
     *   construction. Adding events would require rebuilding or a different
     *   dynamic data structure.
     */
}
```

Why does subtraction work?

```
Sorted events:  [1, 2, 2, 5, 8, 10, 10, 20]
Prefix counts:  [0, 1, 2, 3, 4, 5,  6,  7,  8]
```

If the desired timestamp range corresponds to array indices `[left, right)`, then:

```
hits in range = prefix[right] - prefix[left]
```

The prefix sum includes all earlier events, so subtracting the earlier prefix removes everything before the window.

### Scenario 2: Events continue arriving and historical queries remain possible

Use an ordered event store or a time-series database that retains sufficient history. An augmented balanced search tree can support dynamic range sums more efficiently than scanning every timestamp, but the implementation is more complex.

The interviewer should clarify how far back queries may go and how long events must be retained. Without a retention limit, memory usage grows with the history.

## 7. Follow-up F: What if `getHits()` is called concurrently?

Suppose multiple threads call `hit()` and `getHits()` on the same counter.

The queue and array solutions above are not thread-safe. A race condition could occur when one thread removes an expired hit while another thread inserts or counts hits.

For an interview, a straightforward solution is to synchronize access to the shared state.

```
import java.util.ArrayDeque;
import java.util.Deque;

class ThreadSafeHitCounter {

    private final Deque<Integer> hitTimestamps = new ArrayDeque<>();

    public synchronized void hit(int timestamp) {
        hitTimestamps.offerLast(timestamp);
    }

    public synchronized int getHits(int timestamp) {
        int expirationBoundary = timestamp - 300;

        while (!hitTimestamps.isEmpty()
                && hitTimestamps.peekFirst() <= expirationBoundary) {
            hitTimestamps.pollFirst();
        }

        return hitTimestamps.size();
    }

    /*
     * Why synchronized:
     * - Only one thread can execute a synchronized instance method on this
     *   object at a time.
     * - Insertion, expiration, and counting therefore cannot interleave
     *   in a way that corrupts the queue.
     *
     * Complexity:
     * - Same algorithmic costs as the ordinary queue implementation.
     * - Contention can increase actual latency because callers may wait.
     *
     * Important:
     * - This preserves thread safety, but timestamps must still arrive
     *   in non-decreasing order across all threads.
     * - If different threads submit events with arbitrary timestamps,
     *   synchronization alone does not make the FIFO algorithm correct.
     */
}
```

For production systems, one might instead use a lock, a single-writer event processor, or a partitioned aggregation design. The right choice depends on throughput, contention, and consistency requirements.

## 8. Follow-up G: What if the hit counter is distributed across multiple servers?

Imagine an API running on four servers:

```
             Incoming requests
                     |
          +----------+----------+
          |          |          |
       Server A   Server B   Server C ... Server D
          |          |          |
          +----------+----------+
                     |
              Aggregate counts
```

A counter stored in one server's memory sees only the hits recorded by that server. To return a global count, the system must aggregate hits from every server.

A common design is:

1. Each server maintains local per-second counts.
2. Each server periodically publishes its counts to a shared aggregation layer.
3. The aggregation layer combines counts for the requested time window.
4. Expired buckets are discarded according to the retention policy.

### What must the interviewer clarify?

- Is the result required to be exact or approximately correct?
- How quickly must a new hit become visible globally?
- Can messages be duplicated, delayed, or lost?
- What happens if one server goes down?
- Is the count per user, API key, endpoint, or globally?

These details determine whether the design uses a shared database, an event stream, a distributed cache, or a dedicated stream-processing system.

### Important distinction: counting versus rate limiting

A hit counter answers:

> How many hits occurred in the last five minutes?

A rate limiter answers:

> Should this request be allowed?

They are related, but they have different correctness requirements. A rate limiter may need atomic check-and-increment behavior to prevent concurrent requests from exceeding a limit.

For example, if the maximum is 100 requests and two servers simultaneously see a count of 99, both must not independently approve the next request if the limit must be strictly enforced globally.

## 9. Follow-up H: What if we need a rate limiter instead of just a counter?

A common extension is:

```
boolean allowRequest(int timestamp);
```

Assume the limit is 100 requests in any rolling 300-second window.

The simplest implementation reuses the queue but makes the decision before recording the new request.

```
import java.util.ArrayDeque;
import java.util.Deque;

class SlidingWindowRateLimiter {

    private final int maxRequests;
    private final int windowSeconds;
    private final Deque<Integer> acceptedRequests = new ArrayDeque<>();

    public SlidingWindowRateLimiter(int maxRequests, int windowSeconds) {
        if (maxRequests <= 0 || windowSeconds <= 0) {
            throw new IllegalArgumentException(
                    "Limits must be positive");
        }

        this.maxRequests = maxRequests;
        this.windowSeconds = windowSeconds;
    }

    public synchronized boolean allowRequest(int timestamp) {
        int expirationBoundary = timestamp - windowSeconds;

        // Discard requests outside the rolling window.
        while (!acceptedRequests.isEmpty()
                && acceptedRequests.peekFirst() <= expirationBoundary) {
            acceptedRequests.pollFirst();
        }

        // Reject if the number of accepted requests has reached the limit.
        if (acceptedRequests.size() >= maxRequests) {
            return false;
        }

        // Only accepted requests consume capacity.
        acceptedRequests.offerLast(timestamp);
        return true;
    }

    /*
     * TIME:
     * - O(1) amortized per request over a sequence of calls.
     * - Each accepted request enters and leaves the queue at most once.
     *
     * SPACE:
     * - O(maxRequests), since the queue cannot retain more than the
     *   configured number of unexpired accepted requests.
     *
     * WHY THIS IS A RATE LIMITER:
     * - The counter only measures traffic.
     * - The limiter makes an allow/reject decision and records only
     *   requests that were accepted.
     *
     * ASSUMPTION:
     * - Calls arrive in non-decreasing timestamp order.
     * - Synchronization protects this instance in a single JVM only;
     *   a distributed limiter needs shared atomic coordination.
     */
}
```

This is a basic sliding-window log rate limiter. Other common designs include a fixed-window counter, a sliding-window counter, and a token bucket.

One trade-off is that the sliding-window log stores individual accepted requests, whereas a bucket-based limiter can use less memory at the cost of different precision or behavior.

## 10. Follow-up I: What if timestamps can be the same, but the window is measured in milliseconds?

The algorithm doesn't fundamentally change. The time unit is a modeling decision.

For a five-minute window:

```
private static final long WINDOW_MILLIS = 5 * 60 * 1_000L;
```

Use `long` timestamps if epoch milliseconds are possible, and compare against the correct inclusive or exclusive boundary.

For a query at time `t`, if the intended interval is `(t - W, t]`, expire entries whose timestamps satisfy:

```
hitTimestamp <= t - W
```

If the intended interval is `[t - W, t]`, that boundary changes: entries exactly `W` units old must be retained.

Interview lesson: Always define the window's boundary semantics before implementing the expiration condition. Time units and boundary inclusivity are separate decisions.

| "Multiple threads will call it."    | Synchronize shared state or use a concurrency-aware design |
| "We run on many servers."           | Distributed aggregation and consistency guarantees         |
| "Reject requests above a limit."    | Rate limiter, not merely a counter                         |

The most valuable insight from this problem is that the data structure follows from the guarantees and the information the system must retain. Start by identifying those constraints, then choose the simplest data structure that satisfies them.
