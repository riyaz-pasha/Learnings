# 1396. Design Underground System — Java 24

Difficulty: Medium Core data structures: `HashMap` + `record` + running aggregate Optimal complexity: \\(O(1)\\) average time per operation and \\(O(C+R)\\) space, where \\(C\\) is the number of currently checked-in customers and \\(R\\) is the number of distinct station-to-station routes recorded.

## 0. Simplify the problem

Imagine a railway system with three operations:

1. Check in: Remember which station a customer entered and at what time.
2. Check out: Calculate the duration of that journey and add it to the statistics for that route.
3. Get average: Return the average journey duration for a particular direction of travel.

For example:

```
Customer 45: Leyton at time 3
Customer 45: Waterloo at time 15

Journey duration = 15 - 3 = 12
```

Suppose two customers travel from Leyton to Waterloo:

```
Customer 45: 3  -> 15  = 12 minutes
Customer 27: 10 -> 20  = 10 minutes
```

Then:

\\[ \text{Average}=\frac{12+10}{2}=11 \\]

The key insight is that we don't need to remember every completed journey. We only need the total journey time and the number of journeys for each route.

## 1. Clarifying questions to ask the interviewer

The problem already specifies most assumptions, but these are useful questions to ask in a real interview.

| Question                                                  | Why it matters                                                                                       |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Can a customer have multiple active check-ins?            | Determines whether one entry per customer ID is sufficient. Here, only one is allowed.               |
| Are events chronological?                                 | Out-of-order events might require more sophisticated event handling. Here, events are chronological. |
| Is the route directional?                                 | Leyton → Waterloo and Waterloo → Leyton must be treated separately.                                  |
| Do we need individual trip histories?                     | If not, storing only a sum and count saves memory.                                                   |
| Can `getAverageTime` be called for a route with no trips? | Here, at least one trip is guaranteed before querying.                                               |
| Can station names contain spaces or special characters?   | This affects how we represent a route key. Here, station names contain only letters and digits.      |

Interview conclusion: We can safely use two hash maps, with no database, sorting, or historical trip list required.

## 2. Core idea: Think in terms of two questions

When designing this class, separate the information you need into two independent categories.

- Customer state: Where is this customer currently checked in, and when did they enter?
- Route statistics: How many completed journeys exist for a route, and what is their total duration?

These are different kinds of information, so use two maps.

```
                         UndergroundSystem
                                 |
                  +--------------+--------------+
                  |                             |
                  v                             v
          Active customers               Route statistics
          Map<CustomerId, Trip>          Map<Route, Stats>
                  |                             |
          Customer 45:                       Leyton -> Waterloo
          Leyton, time 3                     total = 22
                                             count = 2
                                             average = 11
```

### Why this is the optimal mental model

Ask yourself: What information must I preserve so that I can answer every future query correctly?

- For an active customer, we need their check-in station and timestamp.
- For a completed route, we need the sum and count of all completed journey durations.
- We don't need the identities of customers who have already completed their trips.
- We don't need to store every journey duration to calculate an average.

The average formula is:

\\[ \text{average}=\frac{\text{total journey duration}}{\text{number of journeys}} \\]

This transforms the problem from storing and processing a history of journeys into maintaining a small, incremental summary.

### What happens during each operation?

```

checkIn(id, station, time)
    activeTrips[id] = (station, time)

checkOut(id, station, time)
    trip = activeTrips[id]
    duration = time - trip.checkInTime
    route = (trip.checkInStation, station)
    routeStats[route].total += duration
    routeStats[route].count += 1
    remove activeTrips[id]

getAverageTime(start, end)
    stats = routeStats[(start, end)]
    return stats.total / stats.count

```

The most important transition happens in `checkOut`: we convert one active trip into a completed journey and update the corresponding route aggregate.

## 3. Edge cases to watch out for

- Repeated journeys on the same route: Accumulate both duration and count; don't overwrite previous statistics.
- Reverse direction: `(A, B)` and `(B, A)` are different routes.
- Same station name: A trip from a station back to itself is still a valid route if the input permits it.
- Customer checks in again after checking out: The previous trip must have been removed so the new check-in replaces no valid active trip.
- Integer division: Cast to `double` before dividing; otherwise, a duration average such as \\(11/2\\) could incorrectly become `5`.
- No completed trips for a queried route: The problem guarantees this won't happen, so the optimal implementation doesn't need a fallback policy.
- Large cumulative duration: Store the total in a `long`, even though individual timestamps fit in an `int`.
- Same timestamp for different events: The input guarantees a valid check-in precedes its corresponding check-out, so no special timestamp handling is required.

## 4. All solutions — brute force to optimal

### Approach 1: Store every completed journey

Mental model: Keep a history of all completed journeys. Whenever someone asks for an average, scan the history and select journeys matching the requested route.

This is the easiest approach to invent during an interview. It works, but every average query may need to examine the entire journey history.

```java
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

class UndergroundSystemBruteForce {

    // A record makes the check-in information immutable and concise.
    private record CheckIn(String station, int time) {}

    // Store a completed journey's origin, destination and duration.
    private record Journey(String start, String end, int duration) {}

    private final Map<Integer, CheckIn> activeTrips = new HashMap<>();
    private final List<Journey> journeyHistory = new ArrayList<>();

    public void checkIn(int id, String stationName, int t) {
        // Remember the customer's current trip.
        // HashMap get/put operations take O(1) average time.
        activeTrips.put(id, new CheckIn(stationName, t));
    }

    public void checkOut(int id, String stationName, int t) {
        // Retrieve the original check-in to determine the route and duration.
        CheckIn checkIn = activeTrips.remove(id);

        int duration = t - checkIn.time();

        // Preserve every completed journey because this approach calculates
        // averages later by scanning the full history.
        journeyHistory.add(
            new Journey(checkIn.station(), stationName, duration)
        );
    }

    public double getAverageTime(String startStation, String endStation) {
        long totalDuration = 0;
        int count = 0;

        // BRUTE FORCE: inspect every completed journey for every query.
        // Only journeys matching BOTH endpoints and the correct direction count.
        for (Journey journey : journeyHistory) {
            if (journey.start().equals(startStation)
                    && journey.end().equals(endStation)) {
                totalDuration += journey.duration();
                count++;
            }
        }

        // The problem guarantees count > 0 for every query.
        // Cast before division to preserve fractional averages.
        return (double) totalDuration / count;
    }

    /*
     * Let:
     *   C = number of currently checked-in customers.
     *   J = number of completed journeys.
     *
     * checkIn:  O(1) average time.
     * checkOut: O(1) average time, excluding amortized list growth.
     * getAverageTime: O(J), because every stored journey may be examined.
     *
     * Space: O(C + J), because we retain active trips and the entire history.
     *
     * Interview takeaway:
     * This is a correct baseline. The expensive operation is repeatedly
     * recalculating an average from historical data.
     */
}
```

### Approach 2: Group journeys by route, but keep every duration

Improvement: Instead of scanning journeys from unrelated routes, organize them by `(startStation, endStation)`. Each route owns a list of its completed durations.

For example:

```
Leyton -> Waterloo : [12, 10, 14]
Paradise -> Cambridge: [14]
```

A query for Leyton → Waterloo now scans only `[12, 10, 14]`.

```java
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

class UndergroundSystemPerRoute {

    private record CheckIn(String station, int time) {}

    // Records provide value-based equality and hashing.
    // Therefore, two Route instances with equal station names are equal keys.
    private record Route(String start, String end) {}

    private final Map<Integer, CheckIn> activeTrips = new HashMap<>();

    // Each route keeps its own duration history.
    private final Map<Route, List<Integer>> durationsByRoute = new HashMap<>();

    public void checkIn(int id, String stationName, int t) {
        activeTrips.put(id, new CheckIn(stationName, t));
    }

    public void checkOut(int id, String stationName, int t) {
        CheckIn checkIn = activeTrips.remove(id);

        Route route = new Route(checkIn.station(), stationName);
        int duration = t - checkIn.time();

        // computeIfAbsent creates the list only when this route is first seen.
        durationsByRoute
            .computeIfAbsent(route, ignored -> new ArrayList<>())
            .add(duration);
    }

    public double getAverageTime(String startStation, String endStation) {
        Route route = new Route(startStation, endStation);
        List<Integer> durations = durationsByRoute.get(route);

        long totalDuration = 0;

        // We only scan durations for the requested route, not all journeys.
        for (int duration : durations) {
            totalDuration += duration;
        }

        return (double) totalDuration / durations.size();
    }

    /*
     * Let:
     *   C = active customers.
     *   R = distinct routes.
     *   J_r = completed journeys for the queried route r.
     *
     * checkIn:  O(1) average.
     * checkOut: O(1) average.
     * getAverageTime: O(J_r), because it scans that route's duration list.
     *
     * Space: O(C + R + J), where J is the total number of completed journeys.
     *
     * Why this is better than Approach 1:
     * Route grouping avoids scanning irrelevant journeys.
     *
     * Why it is still not optimal:
     * The average only requires a sum and a count. Keeping every individual
     * duration uses extra memory and requires repeated summation.
     */
}
```

### Approach 3: Store only the sum and count — optimal

This is the preferred interview solution.

Replace each route's list of durations with two numbers:

```
Route: Leyton -> Waterloo

Instead of storing:
[12, 10, 14]

Store:
totalDuration = 36
journeyCount  = 3

Average = 36 / 3 = 12
```

When a new journey completes, update those two numbers. No history scan is needed.

```java
import java.util.HashMap;
import java.util.Map;

class UndergroundSystem {

    /*
     * Immutable check-in data.
     *
     * A Java record provides:
     * - A compact constructor declaration.
     * - Final record components.
     * - Accessors such as station() and time().
     *
     * A customer can have at most one active trip, so customer ID is the key.
     */
    private record CheckIn(String station, int time) {}

    /*
     * A route is directional.
     *
     * Route("Leyton", "Waterloo") is NOT equal to
     * Route("Waterloo", "Leyton").
     *
     * Records automatically implement value-based equals() and hashCode(),
     * making them convenient and safe HashMap keys.
     */
    private record Route(String start, String end) {}

    /*
     * A completed route needs only:
     * 1. The sum of all journey durations.
     * 2. The number of completed journeys.
     *
     * This is deliberately a class rather than a record because its fields
     * are updated incrementally whenever a new trip completes.
     */
    private static final class RouteStats {
        private long totalDuration;
        private long journeyCount;

        private void addJourney(int duration) {
            totalDuration += duration;
            journeyCount++;
        }

        private double average() {
            // Cast before division to ensure floating-point division.
            return (double) totalDuration / journeyCount;
        }
    }

    /*
     * Map 1: Customer ID -> currently active trip.
     *
     * Contains only customers who have checked in but have not checked out.
     *
     * Map 2: Directed route -> aggregate statistics.
     *
     * Contains only routes for which at least one journey has completed.
     */
    private final Map<Integer, CheckIn> activeTrips = new HashMap<>();
    private final Map<Route, RouteStats> statsByRoute = new HashMap<>();

    public UndergroundSystem() {
        // HashMap fields are initialized above; no additional setup is needed.
    }

    public void checkIn(int id, String stationName, int t) {
        /*
         * Save the customer's origin and entry time.
         *
         * Time: O(1) average for HashMap.put().
         * Space: O(1) additional space for this active trip.
         *
         * The problem guarantees consistent calls, so this customer does not
         * already have another active check-in that needs special handling.
         */
        activeTrips.put(id, new CheckIn(stationName, t));
    }

    public void checkOut(int id, String stationName, int t) {
        /*
         * Step 1: Retrieve and remove the active trip.
         *
         * remove() both retrieves the original check-in and ensures the
         * completed customer is no longer counted as active.
         *
         * Time: O(1) average.
         */
        CheckIn checkIn = activeTrips.remove(id);

        /*
         * Step 2: Calculate the duration.
         *
         * Since the events are valid and chronological, t > checkIn.time().
         */
        int duration = t - checkIn.time();

        /*
         * Step 3: Identify the directed route.
         *
         * The origin comes from the customer's check-in, not from the
         * destination or from any global station state.
         */
        Route route = new Route(checkIn.station(), stationName);

        /*
         * Step 4: Find or create the route aggregate.
         *
         * computeIfAbsent creates RouteStats the first time this route occurs.
         * Every later journey for the same route updates the same aggregate.
         */
        RouteStats stats = statsByRoute.computeIfAbsent(
            route,
            ignored -> new RouteStats()
        );

        /*
         * Step 5: Incorporate this journey exactly once.
         *
         * totalDuration += duration
         * journeyCount  += 1
         *
         * We never need to retain this individual duration afterward.
         *
         * Time: O(1) average for the map operations and aggregate update.
         */
        stats.addJourney(duration);
    }

    public double getAverageTime(String startStation, String endStation) {
        /*
         * Constructing the key from the two requested stations retrieves
         * exactly the matching direction of travel.
         *
         * The problem guarantees at least one completed journey for the route,
         * so statsByRoute.get(route) will not return null.
         */
        Route route = new Route(startStation, endStation);
        RouteStats stats = statsByRoute.get(route);

        /*
         * The average is already represented by the running sum and count.
         * No loop, sorting, or historical journey retrieval is required.
         *
         * Time: O(1) average.
         */
        return stats.average();
    }

    /*
     * FINAL COMPLEXITY ANALYSIS
     *
     * Let:
     *   C = maximum/current number of active customers being stored.
     *   R = number of distinct routes that have completed journeys.
     *
     * checkIn:
     *   O(1) average time.
     *   O(1) additional space per newly active customer.
     *
     * checkOut:
     *   O(1) average time.
     *   O(1) additional space when a new route first appears.
     *
     * getAverageTime:
     *   O(1) average time because it performs a constant number of hash-map
     *   operations and reads two numeric fields.
     *
     * Total space:
     *   O(C + R).
     *
     * Why the HashMap complexity is described as average:
     *   HashMap lookups and updates are O(1) on average under normal hashing
     *   behavior; pathological collision scenarios can have higher costs.
     *
     * Why this is optimal:
     *   Each operation processes a constant amount of information, and an
     *   average query reads the already-maintained aggregate. We do not retain
     *   the completed journey history, so memory does not grow with every trip.
     */
}
```

## 5. Walk through the example

Consider the following operations:

```
undergroundSystem.checkIn(45, "Leyton", 3);
undergroundSystem.checkOut(45, "Waterloo", 15);

undergroundSystem.checkIn(27, "Leyton", 10);
undergroundSystem.checkOut(27, "Waterloo", 20);

double average =
    undergroundSystem.getAverageTime("Leyton", "Waterloo");
```

The internal state evolves as follows.

Step 1 — First check-in

`activeTrips`:

```
45 -> (Leyton, 3)
```

No completed route statistics exist yet.

Step 2 — First check-out

Duration = `15 - 3 = 12`.

```
activeTrips: empty

Leyton -> Waterloo
  total = 12
  count = 1
```

Step 3 — Second check-out

Duration = `20 - 10 = 10`.

```
Leyton -> Waterloo
  total = 12 + 10 = 22
  count = 2
```

Step 4 — Average query

```
average = 22 / 2 = 11.0
```

The answer is returned without examining either journey individually.

## 6. Interview follow-up questions and answers

Q1. Why use two hash maps instead of one?

Because active customer information and completed route statistics have different lifecycles. A check-out removes a customer from the active map but updates the route aggregate. Separating them makes the state transitions straightforward.

Q2. Why use a `Route` record instead of concatenating station names?

A record gives us a structured, immutable key with correct value-based equality and hashing. Concatenating strings can introduce ambiguity if separators appear in station names, and it obscures the route's meaning.

Q3. Why not store the average directly?

You can maintain a running average, but the sum-and-count representation is easier to reason about and avoids repeated floating-point updates. The average is calculated only when requested.

Q4. Can we use `int` for `totalDuration`?

Using `long` is safer for cumulative values. Even if each individual duration fits in an `int`, the sum of many durations can exceed the `int` range.

Q5. What if the interviewer asks for the median travel time?

Sum and count are no longer sufficient to compute an exact median. You would need to retain duration information or use an appropriate ordered data structure, depending on the update and query requirements.

Q6. What if the interviewer asks for the average over only the last 24 hours?

The current aggregate cannot answer that because it does not retain individual journey timestamps. You would need timestamped journey records and a strategy to expire old journeys, while keeping sums and counts consistent.

Q7. What if check-in and check-out events arrive out of order?

The current solution assumes chronological events. Out-of-order processing may require buffering, event-time processing, or corrections to previously computed aggregates.

Q8. What if the system must support millions of stations and customers across multiple servers?

The same logical model still applies, but the implementation would need distributed state management. Active trips could be partitioned by customer ID, and route aggregates by route key, with care taken to prevent duplicate or lost updates.

## 7. Final interview summary

The thought process to remember is:

1. Identify the information required to answer each operation.
2. Separate active state from historical aggregates.
3. Recognize that an average needs only a sum and a count.
4. Represent the directed route as a structured key.
5. Update aggregates when a journey completes rather than recomputing them on demand.

The most important optimization is not a clever algorithm; it is recognizing that the full history of completed journeys is unnecessary.

| Operation        | Optimal average time |
| ---------------- | -------------------- |
| `checkIn`        | \\(O(1)\\)           |
| `checkOut`       | \\(O(1)\\)           |
| `getAverageTime` | \\(O(1)\\)           |
| Total space      | \\(O(C+R)\\)         |

This is a classic example of incremental aggregation: maintain a compact summary as events arrive, allowing future queries to be answered efficiently.
