# LeetCode 635: Design Log Storage System

Difficulty: Medium

Main concepts: Design a data structure, `TreeMap`, `HashMap`, timestamp parsing, range filtering, and lexicographical ordering.

Problem link: [Design Log Storage System — LeetCode](https://leetcode.com/problems/design-log-storage-system/description/?utm_source=chatgpt.com)

## 0. Simplify the problem statement

You need to design a system that stores logs. Each log has:

- A unique integer `id`.
- A timestamp in the format `Year:Month:Day:Hour:Minute:Second`.

For example:

```
2017:01:01:23:59:59
2017:01:02:00:00:00
2018:01:01:00:00:00
```

The system supports two operations:

1. `put(id, timestamp)` — store a log.
2. `retrieve(start, end, granularity)` — return the IDs of logs whose timestamps fall between `start` and `end`, inclusive, considering only the specified granularity.

The granularity can be one of:

`Year`, `Month`, `Day`, `Hour`, `Minute`, or `Second`.

### What does granularity mean?

Suppose the query is:

```
start       = 2017:01:01:00:00:00
end         = 2017:12:31:23:59:59
granularity = Month
```

We only care about the year and month. The query effectively covers every log from January through December 2017, regardless of its day or time.

A useful mental model is to expand the start and end timestamps to the boundaries of the requested granularity.

For example, a query at `Month` granularity can be converted into a range beginning at the first second of the start month and ending at the last second of the end month.

## 1. Clarifying questions to ask the interviewer

Before coding, these are the useful questions to ask and why they matter.

1. Are timestamps always in the fixed-width, zero-padded format? This matters because lexicographical string comparison is chronologically correct only when the format is consistent.
2. Is the range inclusive at both ends? Yes, the problem specifies an inclusive interval. Both boundary timestamps must be considered.
3. Can multiple logs have the same timestamp? Yes, IDs are unique, but timestamps need not be. Our data structure must retain every log at the same timestamp.
4. Does the returned list need to be sorted? No particular order is required by the problem. If sorted output were required, we'd need to account for that explicitly.
5. How many logs and operations can there be? The constraints allow at most 500 calls to `put` and `retrieve`, so a linear scan is entirely reasonable. For a large-scale logging system, an ordered index would be more appropriate.&#x20;

## 2. Core intuition: reduce time to string comparison

The key observation is that timestamps are zero-padded and ordered from the largest time unit to the smallest:

```
YYYY:MM:DD:HH:MM:SS
```

Therefore:

```
"2016:12:31:23:59:59" < "2017:01:01:00:00:00"
```

This is true both chronologically and lexicographically.

Each granularity corresponds to a fixed prefix length:

| Granularity | Prefix length |
| ----------- | ------------- |
| Year        | 4             |
| Month       | 7             |
| Day         | 10            |
| Hour        | 13            |
| Minute      | 16            |
| Second      | 19            |

For example, at `Day` granularity:

```
2017:01:02:23:59:59
           ↓
2017:01:02
```

We can compare only the first 10 characters of each timestamp.

The condition becomes:

```
startPrefix.compareTo(logPrefix) <= 0
    && logPrefix.compareTo(endPrefix) <= 0
```

This is the central trick: we don't need to parse dates or calculate time differences at all.

## 3. Approaches from brute force to an indexed solution

### Approach A — Brute force: inspect every log

Store logs in a list. For every retrieval, visit each log, extract the relevant timestamp prefix, and check whether it falls within the query range.

- `put`: \\(O(1)\\)
- `retrieve`: \\(O(n)\\)
- Space: \\(O(n)\\)

This is simple and appropriate for the given constraints.

### Approach B — Normalize the boundaries

Instead of truncating every log's timestamp, expand the query boundaries to the beginning and end of their respective granularity units.

For a `Month` query:

```
Start: 2017:03:15:12:30:00
End:   2017:06:10:08:00:00

Lower: 2017:03:00:00:00:00  // Conceptually: first instant of March
Upper: 2017:06:99:99:99:99  // Lexicographic upper bound, not a real date
```

The normalized string boundaries are:

```
Lower: 2017:03:00:00:00:00
Upper: 2017:06:99:99:99:99
```

The upper boundary is a comparison sentinel, not a valid timestamp. All timestamps in June sort before it.

Then scan the logs and compare each complete timestamp against these bounds.

- `put`: \\(O(1)\\)
- `retrieve`: \\(O(n)\\)
- Space: \\(O(n)\\)

This is an equivalent linear-scan approach. It avoids truncating each log's timestamp during retrieval, but boundary construction requires care.

### Approach C — Use a `TreeMap` for indexed range queries

A `TreeMap` maintains timestamps in sorted order. We can normalize the query boundaries and use `subMap` to visit only the entries inside the requested range.

- `put`: \\(O(\log n)\\), excluding the small cost of appending to a timestamp's ID list.
- `retrieve`: \\(O(\log n + k)\\), where \\(k\\) is the number of distinct timestamps visited, plus the cost of returning the matching IDs.
- Space: \\(O(n)\\)

This is a better choice when retrieval performance matters and the number of stored logs is large.

## 4. Java 24 solutions

### Solution 1: Linear scan using timestamp prefixes

This is the solution I'd recommend implementing first in an interview. It is short, readable, and directly expresses the problem's requirements.

```java
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

class LogSystem {

    // A record gives each stored log a compact, immutable representation.
    // The timestamp remains a string because its fixed-width format is useful.
    private record Log(int id, String timestamp) {}

    private final List<Log> logs = new ArrayList<>();

    // Map each granularity to the number of timestamp characters we care about.
    // These lengths include the separators between the date/time components.
    private static final Map<String, Integer> PREFIX_LENGTHS = Map.of(
        "Year", 4,
        "Month", 7,
        "Day", 10,
        "Hour", 13,
        "Minute", 16,
        "Second", 19
    );

    public LogSystem() {
        // ArrayList starts empty; no additional initialization is required.
    }

    public void put(int id, String timestamp) {
        // Store every log, even when several logs share the same timestamp.
        // Appending to an ArrayList takes amortized O(1) time.
        logs.add(new Log(id, timestamp));
    }

    public List<Integer> retrieve(
            String start,
            String end,
            String granularity) {

        // Determine which timestamp prefix defines the requested precision.
        // The problem guarantees that granularity is valid.
        int length = PREFIX_LENGTHS.get(granularity);

        // Ignore all components finer than the requested granularity.
        String startPrefix = start.substring(0, length);
        String endPrefix = end.substring(0, length);

        List<Integer> result = new ArrayList<>();

        // Brute-force scan: every stored log must be checked because the list
        // is not sorted or indexed by timestamp.
        for (Log log : logs) {
            String logPrefix = log.timestamp().substring(0, length);

            // String.compareTo follows chronological order here because all
            // timestamp fields are fixed-width and zero-padded.
            // Both inequalities are inclusive, as required by the problem.
            if (logPrefix.compareTo(startPrefix) >= 0
                    && logPrefix.compareTo(endPrefix) <= 0) {
                result.add(log.id());
            }
        }

        // IDs can appear in any order; the problem does not require sorting.
        return result;
    }

    /*
     * COMPLEXITY
     *
     * Let:
     *   n = number of stored logs
     *   L = 19, the maximum timestamp length
     *   r = number of matching logs
     *
     * put:
     *   Amortized O(1), since appending one record to the list is amortized O(1).
     *
     * retrieve:
     *   O(n * L) in a character-level analysis, because each timestamp prefix
     *   is extracted and compared. Since L <= 19 is constant, this simplifies
     *   to O(n). Constructing and returning the result additionally costs O(r).
     *
     * Auxiliary space per retrieval:
     *   O(r) for the result list. The stored logs consume O(n) persistent space.
     *
     * Why this is a good interview answer:
     *   The constraints are small, the code is easy to verify, and the solution
     *   exploits the timestamp format instead of introducing needless date logic.
     */
}
```

### Solution 2: Linear scan with normalized boundaries

This approach is useful when you want to compare complete timestamps instead of extracting a prefix from every stored log.

```java
import java.util.ArrayList;
import java.util.List;
import java.util.Map;

class LogSystem {

    private record Log(int id, String timestamp) {}

    private final List<Log> logs = new ArrayList<>();

    // Number of characters representing each granularity.
    private static final Map<String, Integer> PREFIX_LENGTHS = Map.of(
        "Year", 4,
        "Month", 7,
        "Day", 10,
        "Hour", 13,
        "Minute", 16,
        "Second", 19
    );

    public LogSystem() {}

    public void put(int id, String timestamp) {
        // Keep the original timestamp; normalization happens only at query time.
        logs.add(new Log(id, timestamp));
    }

    public List<Integer> retrieve(
            String start,
            String end,
            String granularity) {

        int length = PREFIX_LENGTHS.get(granularity);

        // Make the lower bound the earliest timestamp with the same prefix.
        // For example, a Month lower bound ends with :00:00:00.
        String lower = start.substring(0, length)
                + "0".repeat(19 - length);

        // Make the upper bound the lexicographically greatest possible
        // timestamp with the end prefix. '9' is a sentinel, not a date value.
        // For example, a Month upper bound ends with :99:99:99.
        String upper = end.substring(0, length)
                + "9".repeat(19 - length);

        List<Integer> result = new ArrayList<>();

        for (Log log : logs) {
            String timestamp = log.timestamp();

            // Compare the complete timestamp against the expanded interval.
            // The bounds include every timestamp at the requested granularity.
            if (timestamp.compareTo(lower) >= 0
                    && timestamp.compareTo(upper) <= 0) {
                result.add(log.id());
            }
        }

        return result;
    }

    /*
     * COMPLEXITY
     *
     * put:
     *   Amortized O(1).
     *
     * retrieve:
     *   O(n * L + L), or O(n) because L = 19 is constant.
     *   Every log is examined once, and creating the two bounds is O(L).
     *
     * Persistent space:
     *   O(n) for stored logs.
     *
     * Additional retrieval space:
     *   O(r) for r returned IDs, plus O(L) for the normalized boundaries.
     *
     * IMPORTANT:
     *   The sentinel suffix must not be interpreted as an actual calendar date.
     *   It works because the comparison is lexicographical and the timestamp
     *   format is fixed-width. This approach assumes valid input timestamps
     *   with the exact format guaranteed by the problem.
     */
}
```

### Solution 3: Indexed retrieval using `TreeMap`

This approach is preferable if we expect many logs and need to retrieve small subsets repeatedly.

The key idea is to maintain timestamps in sorted order. Because multiple logs can share a timestamp, each timestamp maps to a list of IDs rather than a single ID.

```java
import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.NavigableMap;
import java.util.TreeMap;

class LogSystem {

    // TreeMap orders timestamp strings chronologically because their format
    // is fixed-width and zero-padded.
    //
    // The list preserves all IDs when multiple logs share one timestamp.
    private final NavigableMap<String, List<Integer>> logs = new TreeMap<>();

    private static final Map<String, Integer> PREFIX_LENGTHS = Map.of(
        "Year", 4,
        "Month", 7,
        "Day", 10,
        "Hour", 13,
        "Minute", 16,
        "Second", 19
    );

    public LogSystem() {}

    public void put(int id, String timestamp) {
        // computeIfAbsent creates a bucket only when this timestamp is new.
        // Otherwise, append to the existing bucket instead of overwriting IDs.
        logs.computeIfAbsent(timestamp, ignored -> new ArrayList<>())
                .add(id);

        // TreeMap insertion costs O(log m), where m is the number of distinct
        // timestamps. Appending to the existing ID list is amortized O(1).
    }

    public List<Integer> retrieve(
            String start,
            String end,
            String granularity) {

        int length = PREFIX_LENGTHS.get(granularity);

        // Normalize to inclusive lower and upper bounds.
        String lower = start.substring(0, length)
                + "0".repeat(19 - length);
        String upper = end.substring(0, length)
                + "9".repeat(19 - length);

        List<Integer> result = new ArrayList<>();

        // subMap(lower, true, upper, true) selects the inclusive timestamp
        // interval. TreeMap can seek to the lower bound rather than scanning
        // every timestamp that precedes it.
        //
        // Iteration visits only entries in the selected range.
        for (List<Integer> ids :
                logs.subMap(lower, true, upper, true).values()) {

            // Return every ID associated with each matching timestamp.
            // Do not assume one timestamp corresponds to exactly one log.
            result.addAll(ids);
        }

        return result;
    }

    /*
     * COMPLEXITY
     *
     * Let:
     *   n = number of logs
     *   m = number of distinct timestamps, with m <= n
     *   k = number of distinct timestamps inside the query range
     *   r = number of returned log IDs
     *
     * put:
     *   O(log m) for a TreeMap insertion, plus amortized O(1) to append an ID.
     *
     * retrieve:
     *   O(log m + k + r).
     *   O(log m) locates the range boundary, O(k) visits matching timestamp
     *   entries, and O(r) copies their IDs into the result.
     *
     * Persistent space:
     *   O(n + m) = O(n), including timestamp keys, tree nodes, and ID lists.
     *
     * Additional retrieval space:
     *   O(r) for the returned IDs, plus O(L) for the two boundaries.
     *
     * Why it scales better:
     *   The linear solutions inspect every log. This version skips timestamps
     *   outside the requested range, making retrieval more efficient when
     *   the matching range is much smaller than the entire log collection.
     *
     * Trade-off:
     *   Insertion is slower and the implementation is more complex. With the
     *   problem's small constraints, Solution 1 is usually the best choice.
     */
}
```

## 5. Dry run: understand the granularity

Suppose we store these logs:

```
put(1, "2017:01:01:23:59:59");
put(2, "2017:01:02:00:00:00");
put(3, "2017:02:01:12:00:00");
put(4, "2018:01:01:00:00:00");
```

Query:

```
retrieve(
    "2017:01:01:23:00:00",
    "2017:01:02:01:00:00",
    "Day"
);
```

At `Day` granularity, we use the first 10 characters.

| ID | Timestamp prefix | Within range? |
| -- | ---------------- | ------------- |
| 1  | `2017:01:01`     | Yes           |
| 2  | `2017:01:02`     | Yes           |
| 3  | `2017:02:01`     | No            |
| 4  | `2018:01:01`     | No            |

Result:

```
[1, 2]
```

Notice that log 2 is included even though its timestamp is after the start timestamp's time of day. We are considering the entire day, not the exact time.

## 6. Edge cases to watch out for

1. Same start and end timestamp: At `Second` granularity, only logs matching that exact timestamp should be returned.
2. Same timestamp, different IDs: All corresponding IDs must be retained. This is especially important for the `TreeMap` solution.
3. Year granularity: Ignore month, day, hour, minute, and second.
4. Second granularity: Compare the entire 19-character timestamp.
5. Inclusive endpoints: A log exactly at either normalized boundary must be included.
6. No matching logs: Return an empty list, not `null`.
7. End-of-month and leap years: No special calendar calculations are needed because the problem guarantees valid timestamps and the solutions compare strings.
8. Invalid granularity or malformed timestamps: These are outside the stated constraints. Production code would typically validate them.

## 7. Interviewer follow-up questions and answers

Q1. Why does lexicographical ordering work for timestamps?

Because the year appears first, followed by increasingly smaller time units, and every component has a fixed width. Numeric ordering of each component is therefore preserved by string ordering.

Q2. Why not use `LocalDateTime`?

You could, but it introduces parsing and date-time boundary calculations that are unnecessary here. String prefixes solve the problem directly and with less code.

Q3. Why can't a `TreeMap<String, Integer>` store the logs directly?

Two different IDs may share a timestamp. A map with a single integer value would overwrite one ID with another. Mapping each timestamp to `List<Integer>` avoids losing logs.

Q4. Is `TreeMap` always better than the linear scan?

No. It offers better range-query performance as the dataset grows, but its insertions cost more and it requires additional implementation complexity. With at most 500 operations, the linear solution is sufficient.

Q5. Could we use a `HashMap` instead?

A `HashMap` provides efficient exact-key lookup but does not maintain timestamp order. Since the operation asks for a range of timestamps, we would still need to scan the entries unless we built additional indexes.

Q6. How would you handle millions of logs in a real logging system?

I would consider an ordered index or a database index on a native timestamp column. For distributed systems, I would also consider time partitioning, retention policies, and indexing by common query dimensions.

## 8. How to recognize this pattern in future interviews

When a problem gives you timestamps or other fixed-format, sortable strings and asks for range filtering, ask yourself:

1. Can the string's natural order match the actual chronological or numeric order?
2. Does the query care about the entire value, or only a prefix?
3. Are there enough records to justify an ordered data structure?
4. Can I transform a complex query into a simple inclusive range comparison?

For this problem, the key observation is the combination of fixed-width timestamps, prefix-based granularity, and inclusive range queries.

My recommendation: start with Solution 1 in an interview. It is the simplest correct solution. Then explain how Solution 3 uses `TreeMap` to improve range retrieval when the dataset grows.

Let's forget the code for a moment and build the idea from scratch. The tricky part of this problem is not Java or `TreeMap`. It's understanding what granularity means and how we can turn a date-time range into a simple comparison.

# 1. Understand the problem with a real example

Imagine a logging system that stores events:

| ID | Timestamp             | Event           |
| -- | --------------------- | --------------- |
| 1  | `2017:01:01:08:30:00` | User logged in  |
| 2  | `2017:01:01:15:45:00` | User logged out |
| 3  | `2017:01:02:09:00:00` | User logged in  |
| 4  | `2017:02:10:12:00:00` | File uploaded   |
| 5  | `2018:01:01:00:00:00` | User logged in  |

We need to support two operations:

```
put(id, timestamp);
retrieve(start, end, granularity);
```

`put` simply stores a log. The interesting operation is `retrieve`.

Suppose I ask:

> Give me all logs from January 1, 2017, through January 1, 2017, considering only the day.

What should the answer be?

IDs `1`, `2`, and `3` are not all on the same day: ID 3 is on January 2. So the answer is IDs `1` and `2`.

Now consider this query:

```
retrieve(
    "2017:01:01:00:00:00",
    "2017:01:01:23:59:59",
    "Day"
);
```

We are asking for the entire day of January 1. The logs at 8:30 AM and 3:45 PM should both match.

The important question is: How do we express “the entire day” without writing complicated date-time logic?

# 2. The breakthrough: granularity means ignoring the smaller units

A timestamp has six components:

Year

## 2017

Month

## 01

Day

## 01

Hour

## 08

Minute

## 30

Second

## 00

Example timestamp: 2017:01:01:08:30:00

If the granularity is `Year`, we care only about the year.

If the granularity is `Month`, we care about the year and month.

If the granularity is `Day`, we care about the year, month, and day.

And so on.

| Granularity | What we compare    | Prefix                |
| ----------- | ------------------ | --------------------- |
| Year        | Year               | `2017`                |
| Month       | Year + month       | `2017:01`             |
| Day         | Year + month + day | `2017:01:01`          |
| Hour        | Through hour       | `2017:01:01:08`       |
| Minute      | Through minute     | `2017:01:01:08:30`    |
| Second      | Entire timestamp   | `2017:01:01:08:30:00` |

Notice that we are not rounding a number. We are simply ignoring everything after the requested level of detail.

For example, these timestamps all have the same `Day` prefix:

```
2017:01:01:08:30:00
2017:01:01:15:45:00
2017:01:01:23:59:59
```

Their prefixes are all:

```
2017:01:01
```

That is the first major insight.

# 3. The second breakthrough: timestamps can be compared like strings

Look at these two timestamps:

```
2017:01:01:08:30:00
2017:01:02:09:00:00
```

Which comes first?

The first one. We can determine that by comparing from left to right:

```
2017:01:01
2017:01:02
         ^
         First difference: 01 comes before 02
```

Java's `String.compareTo()` follows this ordering.

```
"2017:01:01".compareTo("2017:01:02") < 0  // true
"2017:01:02".compareTo("2017:01:02") == 0 // true
"2017:01:03".compareTo("2017:01:02") > 0  // true
```

Why does this work? Because the timestamp format is always zero-padded:

- January is `01`, not `1`.
- February is `02`, not `2`.
- The year comes before the month, and the month before the day.

Important: This trick depends on the fixed-width format. It would not be safe for arbitrary date strings such as `2017:1:2` and `2017:10:1`.

# 4. Now combine both ideas

We know two things:

1. Granularity tells us how much of a timestamp to consider.
2. String comparison tells us whether one timestamp prefix comes before another.

Let's use both.

Suppose we have these logs:

```
ID 1: 2017:01:01:08:30:00
ID 2: 2017:01:01:15:45:00
ID 3: 2017:01:02:09:00:00
ID 4: 2017:02:10:12:00:00
ID 5: 2018:01:01:00:00:00
```

And this query:

```
retrieve(
    "2017:01:01:12:00:00",
    "2017:01:02:08:00:00",
    "Day"
);
```

## Step 1: Find the prefix length

`Day` means we care about the year, month, and day.

The prefix is 10 characters long:

```
2017:01:01:12:00:00
          |
          First 10 characters = 2017:01:01
```

So:

```
startPrefix = 2017:01:01
endPrefix   = 2017:01:02
```

## Step 2: Check each log

| ID | Original timestamp    | Prefix       | Decision |
| -- | --------------------- | ------------ | -------- |
| 1  | `2017:01:01:08:30:00` | `2017:01:01` | Include  |
| 2  | `2017:01:01:15:45:00` | `2017:01:01` | Include  |
| 3  | `2017:01:02:09:00:00` | `2017:01:02` | Include  |
| 4  | `2017:02:10:12:00:00` | `2017:02:10` | Exclude  |
| 5  | `2018:01:01:00:00:00` | `2018:01:01` | Exclude  |

Why include ID 3 even though its time is 9 AM and the end time says 8 AM? Because we selected `Day` granularity. The end prefix is January 2, and the entire day is included.

Why include ID 1 even though its time is before noon? For the same reason: at `Day` granularity, the time is irrelevant.

The result is:

```
[1, 2, 3]
```

## Step 3: Write the condition in Java

A log matches if its prefix is greater than or equal to the start prefix and less than or equal to the end prefix.

```
logPrefix.compareTo(startPrefix) >= 0
        && logPrefix.compareTo(endPrefix) <= 0
```

Think of this as:

```
startPrefix <= logPrefix <= endPrefix
```

Both boundaries are inclusive.

This is the entire algorithm. The remaining work is simply to implement it cleanly.

# 5. Complete Java 24 solution with detailed comments

This is the solution I recommend learning first. It uses a simple list because the problem's constraints are small.

```java
import java.util.ArrayList;
import java.util.List;
import java.util.Map;

class LogSystem {

    /*
     * STEP 1: Choose a simple representation for each log.
     *
     * Each log consists of:
     *   - its unique ID
     *   - its timestamp
     *
     * A record is convenient in modern Java because it gives us an immutable
     * data carrier with an ID accessor and a timestamp accessor.
     *
     * We keep timestamps as Strings. There is no need to parse them into
     * date-time objects because the problem guarantees a fixed-width format.
     */
    private record Log(int id, String timestamp) {}

    /*
     * STEP 2: Store all logs.
     *
     * An ArrayList is sufficient because:
     *   - put() only needs to append a log.
     *   - retrieve() can inspect every log.
     *
     * We do not need sorting, a tree, or a hash map for the basic solution.
     */
    private final List<Log> logs = new ArrayList<>();

    /*
     * STEP 3: Convert granularity into a prefix length.
     *
     * Timestamp format:
     *
     *   YYYY:MM:DD:HH:MM:SS
     *   0123456789012345678  <- character positions
     *
     * Prefix lengths:
     *
     *   Year   ->  4 characters: YYYY
     *   Month  ->  7 characters: YYYY:MM
     *   Day    -> 10 characters: YYYY:MM:DD
     *   Hour   -> 13 characters: YYYY:MM:DD:HH
     *   Minute -> 16 characters: YYYY:MM:DD:HH:MM
     *   Second -> 19 characters: YYYY:MM:DD:HH:MM:SS
     *
     * We include the colons that occur between the components.
     *
     * Example:
     *   "2017:01:02:09:30:00".substring(0, 10)
     *   returns "2017:01:02".
     */
    private static final Map<String, Integer> PREFIX_LENGTHS = Map.of(
        "Year", 4,
        "Month", 7,
        "Day", 10,
        "Hour", 13,
        "Minute", 16,
        "Second", 19
    );

    /*
     * STEP 4: Initialize an empty logging system.
     *
     * ArrayList is already initialized when the object is constructed.
     */
    public LogSystem() {
    }

    /*
     * STEP 5: Insert a log.
     *
     * We do not need to sort the list or compare the timestamp here.
     * Simply retain the ID and its original timestamp.
     *
     * Time complexity: O(1) amortized.
     * Space complexity: O(1) additional space per inserted log.
     */
    public void put(int id, String timestamp) {
        logs.add(new Log(id, timestamp));
    }

    /*
     * STEP 6: Retrieve all logs within the requested range.
     *
     * The main idea:
     *
     *   A. Determine how many timestamp characters matter.
     *   B. Extract that prefix from start and end.
     *   C. Extract the same prefix from every stored log.
     *   D. Include a log if its prefix lies between the two boundaries.
     */
    public List<Integer> retrieve(
            String start,
            String end,
            String granularity) {

        /*
         * A. Find the required precision.
         *
         * If granularity is "Day", length is 10.
         * If granularity is "Month", length is 7.
         *
         * The problem guarantees a valid granularity.
         */
        int length = PREFIX_LENGTHS.get(granularity);

        /*
         * B. Reduce the query boundaries to the requested precision.
         *
         * Example:
         *
         * start = "2017:01:01:12:00:00"
         * end   = "2017:01:03:08:00:00"
         * granularity = "Day"
         *
         * We get:
         *
         * startPrefix = "2017:01:01"
         * endPrefix   = "2017:01:03"
         *
         * Notice that the hours, minutes, and seconds are discarded.
         */
        String startPrefix = start.substring(0, length);
        String endPrefix = end.substring(0, length);

        /*
         * C. Create a list for the matching IDs.
         *
         * It is initially empty. We append IDs only when their logs match.
         */
        List<Integer> result = new ArrayList<>();

        /*
         * D. Examine every stored log.
         *
         * This is a linear scan. We deliberately choose the simplest
         * implementation first rather than adding an index prematurely.
         */
        for (Log log : logs) {

            /*
             * Extract the same part of this log's timestamp.
             *
             * If granularity is Day, the comparison ignores the time of day.
             */
            String logPrefix = log.timestamp().substring(0, length);

            /*
             * Check the inclusive range:
             *
             *   logPrefix >= startPrefix
             *   AND
             *   logPrefix <= endPrefix
             *
             * String.compareTo() is suitable because the timestamp fields
             * are fixed-width, zero-padded, and arranged from largest unit
             * (year) to smallest unit (second).
             *
             * compareTo() returns:
             *   a negative number if the left string comes before the right
             *   zero if the strings are equal
             *   a positive number if the left string comes after the right
             *
             * Both comparisons include equality, so logs at either endpoint
             * are included.
             */
            boolean isAfterOrAtStart =
                    logPrefix.compareTo(startPrefix) >= 0;

            boolean isBeforeOrAtEnd =
                    logPrefix.compareTo(endPrefix) <= 0;

            /*
             * Only logs satisfying BOTH conditions belong to the answer.
             *
             * Example:
             *   startPrefix = "2017:01:01"
             *   logPrefix   = "2017:01:02"
             *   endPrefix   = "2017:01:03"
             *
             * Both conditions are true, so the ID is included.
             */
            if (isAfterOrAtStart && isBeforeOrAtEnd) {
                result.add(log.id());
            }
        }

        /*
         * Return every matching ID.
         *
         * The problem does not require a particular order, so there is no
         * need to sort the result.
         */
        return result;
    }

    /*
     * COMPLEXITY ANALYSIS
     *
     * Let:
     *   n = number of stored logs
     *   r = number of matching logs
     *   L = maximum timestamp length, which is 19
     *
     * put():
     *   Amortized O(1) time per insertion.
     *
     * retrieve():
     *   O(n * L) when counting character operations, because we examine each
     *   log and extract/compare prefixes of at most 19 characters.
     *   Since L is a fixed constant, this simplifies to O(n).
     *
     *   Constructing the returned list takes O(r) additional time.
     *   The full time bound remains O(n), because r <= n.
     *
     * Persistent storage:
     *   O(n) for all stored logs.
     *
     * Additional space per retrieve():
     *   O(r) for the returned IDs.
     *   The two boundary prefixes require O(L) space, which is constant.
     *
     * WHY THIS SOLUTION IS A GOOD START:
     *   It directly expresses the problem's requirements, handles all
     *   granularities uniformly, and avoids unnecessary date calculations.
     */
}
```

# 7. What about the `TreeMap` solution?

Once the simple solution makes sense, the optimization becomes easier to understand.

The list solution examines all five logs, even though only three match. With a million logs, this could be expensive.

A `TreeMap` keeps timestamps sorted:

```
2017:01:01:08:30:00  -> [1]
2017:01:01:15:45:00  -> [2]
2017:01:02:09:00:00  -> [3]
2017:02:10:12:00:00  -> [4]
2018:01:01:00:00:00  -> [5]
```

We can then ask Java for only the entries within the required range using `subMap()`.

One important correction to my earlier answer: simply appending zeros or nines to a prefix is not enough because the timestamp's colon separators must be preserved. Here is the correct boundary construction:

```java
import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.NavigableMap;
import java.util.TreeMap;

class LogSystem {

    // A timestamp may have several IDs, so retain a list for each key.
    private final NavigableMap<String, List<Integer>> logs = new TreeMap<>();

    // Number of timestamp components that matter at each granularity.
    private static final Map<String, Integer> COMPONENTS = Map.of(
        "Year", 1,
        "Month", 2,
        "Day", 3,
        "Hour", 4,
        "Minute", 5,
        "Second", 6
    );

    public LogSystem() {}

    public void put(int id, String timestamp) {
        // Preserve all IDs when multiple logs have the same timestamp.
        logs.computeIfAbsent(timestamp, key -> new ArrayList<>()).add(id);
    }

    public List<Integer> retrieve(
            String start,
            String end,
            String granularity) {

        int components = COMPONENTS.get(granularity);

        // Keep the meaningful prefix and fill every smaller component with 00.
        // Example at Month granularity:
        // 2017:03 becomes 2017:03:00:00:00:00.
        String lower = start.substring(0, prefixLength(components))
                + ":00".repeat(6 - components);

        // Fill smaller components with 99 to include every possible timestamp
        // in the ending unit. These are lexicographical sentinels, not dates.
        // Example at Month granularity:
        // 2017:06 becomes 2017:06:99:99:99:99.
        String upper = end.substring(0, prefixLength(components))
                + ":99".repeat(6 - components);

        List<Integer> result = new ArrayList<>();

        // TreeMap locates the range and iterates only matching timestamp keys.
        // Both bounds are inclusive.
        for (List<Integer> ids : logs.subMap(lower, true, upper, true).values()) {
            result.addAll(ids);
        }

        return result;
    }

    private static int prefixLength(int components) {
        // Each component contributes two colons except the first component,
        // the year. For six components, the length is 19.
        return components * 3 + 1;
    }

    /*
     * Time complexity:
     *
     * put:
     *   O(log m) to insert into the TreeMap, plus amortized O(1) to append
     *   an ID to its list, where m is the number of distinct timestamps.
     *
     * retrieve:
     *   O(log m + k + r), where k is the number of matching timestamp keys
     *   and r is the total number of IDs returned.
     *
     * Space:
     *   O(n) for stored logs and O(r) for the returned list.
     *
     * The prefix-scan solution is simpler and sufficient for the original
     * constraints. This version is useful when range queries become frequent.
     */
}
```

# 8. The interview thought process to remember

When you see this problem, think through these questions in order:

1. What does granularity mean? It means ignoring the smaller time units.
2. Can the timestamp be compared as a string? Yes, because it is fixed-width and zero-padded.
3. How do I check the range? Compare the relevant prefixes against the inclusive start and end prefixes.
4. Do I need a more advanced data structure? Only if the number of logs or retrieval frequency makes scanning expensive.

The most important thing to understand is this line:

```
String logPrefix = log.timestamp().substring(0, length);
```

It removes the information we don't care about. After that, the problem is just an ordinary range check.

My advice: Make sure you can explain and trace the linear-scan solution before memorizing `TreeMap`. Once the prefix idea clicks, the rest of the problem becomes straightforward.
