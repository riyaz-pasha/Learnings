# 355. Design Twitter — Java 24 Interview Guide

The key to solving this problem is to recognize that a news feed is a merge of multiple users' timelines, ordered by recency.

We need to design five operations:

- `postTweet(userId, tweetId)` — store a tweet.
- `getNewsFeed(userId)` — return the 10 newest tweets from the user and everyone they follow.
- `follow(followerId, followeeId)` — establish a following relationship.
- `unfollow(followerId, followeeId)` — remove that relationship.
- `Twitter()` — initialize the data structure.

The most important interview insight is that we don't need to sort every tweet in the entire system whenever someone requests a feed. We can store tweets in chronological order and efficiently merge only the timelines relevant to that user.

## 1. Simplify the problem

Imagine the following users and tweets:

User 1's timeline

User 1

Tweets: 5, 8

Oldest → Newest

User 2

Tweets: 6, 9

Oldest → Newest

User 3

Tweets: 7, 10

Oldest → Newest

Assume User 1 follows User 2 and User 3.

User 1's feed must combine all three timelines and return the newest tweets first:

`[10, 9, 8, 7, 6, 5]`

Notice that the tweet IDs themselves do not tell us their posting order in a general implementation. We should maintain a separate timestamp or sequence number.

Our design challenge: How can we retrieve the newest 10 tweets without unnecessarily examining every tweet ever posted?

## 2. Clarifying questions to ask the interviewer

These questions establish the constraints that determine the data structures and algorithm.

1. Are tweet IDs unique? The problem guarantees unique IDs, so we don't need to handle duplicate tweet identifiers.
2. Can users follow themselves? We should always include the user's own tweets, regardless of their follow relationships. We can also prevent self-following explicitly.
3. Can someone follow the same user multiple times? Following should behave like a set relationship. Repeated calls must not create duplicate feed entries.
4. Can a user unfollow someone they aren't following? The operation should safely do nothing.
5. Can tweets arrive out of chronological order? The standard problem treats each posting call as a new event. We can assign a monotonically increasing sequence number to each post.
6. Must the feed contain exactly 10 tweets? No. It contains up to 10 tweets, depending on how many eligible tweets exist.
7. Are we optimizing for posting or feed retrieval? The problem doesn't mandate a particular trade-off. A good solution keeps posting inexpensive and uses a heap to retrieve the newest 10 tweets efficiently.

## 3. Core idea: timelines plus a k-way merge

Think of each user's tweets as a separate, chronological list. The news feed is the result of merging those lists in reverse chronological order.

### Data structures

| Data structure               | Responsibility                                      |
| ---------------------------- | --------------------------------------------------- |
| `Map<Integer, Set<Integer>>` | Stores who each user follows                        |
| `Map<Integer, List<Tweet>>`  | Stores each user's tweets in posting order          |
| Global sequence counter      | Establishes the recency of every tweet              |
| `PriorityQueue<TweetCursor>` | Selects the newest available tweet across timelines |

A tweet can be represented with a Java `record`, which is a good fit for immutable data:

```
record Tweet(int id, long sequence) {}
```

The `sequence` increases on every post. A larger value means a newer tweet.

### Mental model: merge sorted lists

Suppose the eligible timelines are:

```
User 1:  [5, 8, 12]
User 2:  [6, 9, 11]
User 3:  [7, 10, 13]
```

Each list is stored oldest to newest. We begin at the end of each list, where its newest tweet is located.

```
                    Max-Heap
                (newest tweet first)
                   /     |     \
                  12     11     13
                   |      |      |
User 1:          5 → 8 → 12
User 2:          6 → 9 → 11
User 3:          7 → 10 → 13
```

The heap first selects `13`. Then we move backward in User 3's timeline and insert `10`. The heap selects the next-newest candidate, `12`, and we continue.

The output becomes:

`[13, 12, 11, 10, 9, 8, 7, 6, 5]`

We stop after 10 tweets or when the heap becomes empty.

Why this is optimal for feed retrieval: If a user follows \\(F\\) other users, there are only \\(F+1\\) relevant timelines. We initially put at most one tweet from each timeline into the heap. Each extraction reveals the next tweet from that same timeline.

This is called a k-way merge, a standard algorithmic pattern used for merging sorted lists and streams.

## 4. All solutions: brute force to optimal

We can derive three solutions by progressively improving how `getNewsFeed()` retrieves tweets.

- Solution 1 — Brute force: Keep every tweet in a global list, filter eligible tweets, sort them, and return the newest 10.
- Solution 2 — Per-user timelines: Store tweets separately for each author, collect tweets from relevant authors, and sort the candidates.
- Solution 3 — Optimal k-way merge: Store per-user timelines and use a max-heap to retrieve only the newest 10 tweets.

The first two solutions are useful interview stepping stones. The third is the recommended solution.

### Solution 1: Brute force

```
import java.util.ArrayList;
import java.util.Comparator;
import java.util.HashMap;
import java.util.HashSet;
import java.util.List;
import java.util.Map;
import java.util.Set;

class TwitterBruteForce {

    /*
     * WHAT WE STORE
     *
     * Tweet:
     *   - authorId identifies who posted the tweet.
     *   - id is the externally visible tweet ID.
     *   - sequence establishes chronological order.
     *
     * A global list makes posting straightforward, but every feed
     * request must inspect the complete tweet history.
     */
    private record Tweet(int authorId, int id, long sequence) {}

    private final List<Tweet> allTweets = new ArrayList<>();

    /*
     * followerId -> users followed by followerId.
     *
     * A Set prevents duplicate following relationships.
     */
    private final Map<Integer, Set<Integer>> following = new HashMap<>();

    private long nextSequence = 0;

    public void postTweet(int userId, int tweetId) {
        /*
         * Each call receives a strictly increasing sequence number.
         * Therefore, larger sequence means more recent, independently
         * of the tweet ID.
         *
         * Time: O(1) amortized for appending to ArrayList.
         * Space: O(1) per posted tweet, excluding list growth overhead.
         */
        allTweets.add(new Tweet(userId, tweetId, nextSequence++));
    }

    public List<Integer> getNewsFeed(int userId) {
        /*
         * Step 1: Build the set of eligible authors.
         *
         * The user must always see their own tweets, so we explicitly
         * add userId even if they follow nobody.
         *
         * Time: O(F + 1), where F is the number of followed users.
         * Space: O(F + 1) for this temporary set.
         */
        Set<Integer> eligibleAuthors = new HashSet<>(
                following.getOrDefault(userId, Set.of())
        );
        eligibleAuthors.add(userId);

        /*
         * Step 2: Scan the complete history and retain eligible tweets.
         *
         * We cannot skip old tweets because we have no per-user index.
         *
         * Time: O(T), where T is the total number of tweets ever posted.
         * Space: O(M), where M is the number of eligible tweets.
         */
        List<Tweet> candidates = new ArrayList<>();

        for (Tweet tweet : allTweets) {
            if (eligibleAuthors.contains(tweet.authorId())) {
                candidates.add(tweet);
            }
        }

        /*
         * Step 3: Sort candidates newest first.
         *
         * A descending sequence comparator guarantees chronological
         * ordering without relying on tweet IDs.
         *
         * Time: O(M log M).
         * Space: O(M) for candidates; sorting uses implementation-
         * dependent additional workspace.
         */
        candidates.sort(
                Comparator.comparingLong(Tweet::sequence).reversed()
        );

        /*
         * Step 4: Return at most 10 tweet IDs.
         *
         * Time: O(min(10, M)), which is O(1) for this fixed limit.
         * Space: O(min(10, M)) for the returned list.
         */
        List<Integer> feed = new ArrayList<>(10);

        for (int i = 0; i < Math.min(10, candidates.size()); i++) {
            feed.add(candidates.get(i).id());
        }

        return feed;
    }

    public void follow(int followerId, int followeeId) {
        /*
         * Set.add is idempotent: following the same user repeatedly
         * does not create duplicate feed entries.
         *
         * Time: O(1) expected.
         * Space: O(1) expected per new relationship.
         */
        following.computeIfAbsent(
                followerId, ignored -> new HashSet<>()
        ).add(followeeId);
    }

    public void unfollow(int followerId, int followeeId) {
        /*
         * Removing a nonexistent relationship safely does nothing.
         *
         * Time: O(1) expected.
         * Space: O(1) auxiliary.
         */
        following.getOrDefault(followerId, Set.of()).remove(followeeId);
    }
}
```

One important correction is needed in the brute-force implementation above: `Set.of()` is immutable, so calling `remove()` on it can throw `UnsupportedOperationException` if the follower has no entry. Use the following safe implementation instead:

```
public void unfollow(int followerId, int followeeId) {
    Set<Integer> followees = following.get(followerId);

    if (followees != null) {
        followees.remove(followeeId);
    }
}
```

Complexity summary

Let:

- \\(T\\) = total tweets in the system.
- \\(M\\) = tweets authored by the user and their followees.
- \\(F\\) = number of users followed by the requesting user.

| Operation     | Time                     |
| ------------- | ------------------------ |
| `postTweet`   | \\(O(1)\\) amortized     |
| `follow`      | \\(O(1)\\) expected      |
| `unfollow`    | \\(O(1)\\) expected      |
| `getNewsFeed` | \\(O(T + M\log M + F)\\) |

This solution is easy to reason about but inefficient for feed retrieval because it scans the entire system's tweet history, even when the requesting user follows only a few people.

### Solution 2: Store tweets per user, then sort candidates

The first improvement is to index tweets by their author. This avoids scanning unrelated users' tweets.

```
import java.util.ArrayList;
import java.util.Comparator;
import java.util.HashMap;
import java.util.HashSet;
import java.util.List;
import java.util.Map;
import java.util.Set;

class TwitterSortCandidates {

    /*
     * Each author's timeline is stored oldest to newest.
     * The sequence number globally orders tweets across authors.
     */
    private record Tweet(int id, long sequence) {}

    private final Map<Integer, List<Tweet>> tweetsByUser =
            new HashMap<>();

    private final Map<Integer, Set<Integer>> following =
            new HashMap<>();

    private long nextSequence = 0;

    public void postTweet(int userId, int tweetId) {
        /*
         * Appending to an author's timeline keeps that timeline
         * chronological and lets us retrieve it directly.
         *
         * Time: O(1) amortized.
         * Space: O(1) per tweet.
         */
        tweetsByUser.computeIfAbsent(
                userId, ignored -> new ArrayList<>()
        ).add(new Tweet(tweetId, nextSequence++));
    }

    public List<Integer> getNewsFeed(int userId) {
        /*
         * Step 1: Find the relevant authors.
         *
         * Adding the requesting user ensures self-authored tweets
         * always appear, without requiring a self-follow relationship.
         *
         * Time: O(F + 1).
         * Space: O(F + 1).
         */
        Set<Integer> authors = new HashSet<>(
                following.getOrDefault(userId, Set.of())
        );
        authors.add(userId);

        /*
         * Step 2: Gather tweets from relevant timelines only.
         *
         * Let M be the total number of tweets in these timelines.
         * We no longer pay for tweets authored by unrelated users.
         *
         * Time: O(F + M).
         * Space: O(M) for the candidate list.
         */
        List<Tweet> candidates = new ArrayList<>();

        for (int authorId : authors) {
            List<Tweet> timeline = tweetsByUser.get(authorId);

            if (timeline != null) {
                candidates.addAll(timeline);
            }
        }

        /*
         * Step 3: Sort all relevant tweets by descending sequence.
         *
         * Time: O(M log M).
         * Space: O(M) for the gathered candidates; sorting workspace
         * depends on the Java sorting implementation.
         */
        candidates.sort(
                Comparator.comparingLong(Tweet::sequence).reversed()
        );

        /*
         * Step 4: Extract only the first 10 IDs.
         *
         * Time: O(min(10, M)).
         * Space: O(min(10, M)) for the returned feed.
         */
        List<Integer> feed = new ArrayList<>(10);

        for (int i = 0; i < Math.min(10, candidates.size()); i++) {
            feed.add(candidates.get(i).id());
        }

        return feed;
    }

    public void follow(int followerId, int followeeId) {
        /*
         * HashSet makes the relationship unique.
         * Time: O(1) expected; O(1) expected space for a new edge.
         */
        following.computeIfAbsent(
                followerId, ignored -> new HashSet<>()
        ).add(followeeId);
    }

    public void unfollow(int followerId, int followeeId) {
        /*
         * Time: O(1) expected; a missing relationship is a no-op.
         */
        Set<Integer> followees = following.get(followerId);

        if (followees != null) {
            followees.remove(followeeId);
        }
    }
}
```

This version is a meaningful improvement because feed retrieval depends on the user's social graph rather than every user in the system.

However, it still gathers and sorts every eligible tweet even though we need only 10.

If the user follows 100 people and those people have collectively posted millions of tweets, sorting every candidate is unnecessary.

That observation leads to the optimal solution.

### Solution 3: Optimal approach using a max-heap

This is the solution I would recommend presenting in an interview.

The central improvement is: instead of gathering all eligible tweets and sorting them, maintain only the newest unprocessed tweet from each relevant timeline.

```
import java.util.ArrayList;
import java.util.Comparator;
import java.util.HashMap;
import java.util.HashSet;
import java.util.List;
import java.util.Map;
import java.util.PriorityQueue;
import java.util.Set;

class Twitter {

    /*
     * A tweet's ID is what the API returns.
     * Its sequence number establishes when it was posted.
     *
     * Java record components are final, making Tweet a suitable
     * immutable value object.
     *
     * We use long for sequence because the number of posting events
     * may exceed the range of an int in a long-running system.
     */
    private record Tweet(int id, long sequence) {}

    /*
     * A cursor points to one tweet in one author's timeline.
     *
     * timelineIndex is the position of the tweet in that author's
     * ArrayList. Because timelines are oldest-to-newest, decrementing
     * this index moves to an older tweet.
     *
     * Keeping the author ID lets us retrieve the corresponding
     * timeline after removing a cursor from the heap.
     */
    private record TweetCursor(
            int authorId,
            int timelineIndex,
            Tweet tweet
    ) {}

    /*
     * FOLLOW GRAPH
     *
     * Key: follower ID.
     * Value: set of users followed by that user.
     *
     * HashSet ensures that repeated follow calls do not duplicate
     * an author's timeline in the news feed.
     *
     * Expected lookup, insertion, and removal: O(1).
     */
    private final Map<Integer, Set<Integer>> following = new HashMap<>();

    /*
     * TIMELINES
     *
     * Key: author ID.
     * Value: tweets posted by that author, oldest to newest.
     *
     * ArrayList is suitable because:
     * 1. Posting appends at the end.
     * 2. The newest tweet is at size - 1.
     * 3. We can move backward by decrementing an index.
     *
     * Each post costs O(1) amortized.
     */
    private final Map<Integer, List<Tweet>> tweetsByUser = new HashMap<>();

    /*
     * Globally increasing posting sequence.
     *
     * We must not compare tweet IDs because IDs are identifiers,
     * not guaranteed timestamps.
     */
    private long nextSequence = 0;

    public Twitter() {
        /*
         * No preallocation is needed.
         * Users and timelines are created lazily as operations occur.
         *
         * Time: O(1).
         * Space: O(1) initially.
         */
    }

    public void postTweet(int userId, int tweetId) {
        /*
         * Create the user's timeline on their first post.
         * computeIfAbsent avoids a separate containsKey/get/put sequence.
         *
         * Appending preserves chronological order because each call
         * receives a newer sequence number.
         *
         * Time: O(1) amortized.
         * Space: O(1) additional per tweet, excluding ArrayList growth.
         */
        List<Tweet> timeline = tweetsByUser.computeIfAbsent(
                userId,
                ignored -> new ArrayList<>()
        );

        timeline.add(new Tweet(tweetId, nextSequence++));
    }

    public List<Integer> getNewsFeed(int userId) {
        /*
         * STEP 1: Identify all relevant authors.
         *
         * A user's own tweets must appear even when they follow nobody.
         * Adding userId explicitly handles this without relying on
         * the user following themselves.
         *
         * A Set also protects against duplicate authors.
         *
         * Let F = number of followees and A = F + 1.
         * Time: O(A) expected.
         * Auxiliary space: O(A).
         */
        Set<Integer> authors = new HashSet<>(
                following.getOrDefault(userId, Set.of())
        );
        authors.add(userId);

        /*
         * STEP 2: Initialize a max-heap.
         *
         * Java PriorityQueue is a min-heap by default, so reverse the
         * sequence comparator. The greatest sequence is removed first.
         *
         * We keep only one cursor per nonempty timeline.
         * Therefore, heap size never exceeds A.
         *
         * Time to initialize the empty heap: O(1).
         */
        PriorityQueue<TweetCursor> newestFirst = new PriorityQueue<>(
                Comparator.comparingLong(
                        (TweetCursor cursor) -> cursor.tweet().sequence()
                ).reversed()
        );

        /*
         * Insert the newest tweet from each relevant author's timeline.
         *
         * The last index is timeline.size() - 1, NOT size().
         * Lists use zero-based indexing, so size() itself is out of bounds.
         *
         * Why only one tweet per author?
         *
         * Every older tweet in the same timeline has a smaller sequence.
         * Until the newest tweet is removed, none of those older tweets
         * can be the newest remaining tweet from that timeline.
         *
         * If author i has n_i tweets, retrieving their newest tweet
         * takes O(1), while inserting it into the heap takes O(log A).
         *
         * Total initialization time: O(A log A).
         * Heap space: O(A).
         */
        for (int authorId : authors) {
            List<Tweet> timeline = tweetsByUser.get(authorId);

            if (timeline == null || timeline.isEmpty()) {
                continue;
            }

            int newestIndex = timeline.size() - 1;
            Tweet newestTweet = timeline.get(newestIndex);

            newestFirst.offer(
                    new TweetCursor(authorId, newestIndex, newestTweet)
            );
        }

        /*
         * STEP 3: Repeatedly select the globally newest available tweet.
         *
         * Each poll removes the newest tweet among the current candidates.
         * Its author's next older tweet becomes the next candidate.
         *
         * This is the k-way merge pattern:
         *
         *       Author A timeline ----\
         *       Author B timeline -----+--> max-heap --> feed
         *       Author C timeline ----/
         *
         * The heap always exposes the newest unprocessed tweet from
         * each timeline. Thus its maximum is the next correct feed item.
         *
         * Poll: O(log A).
         * Optional insertion of the next older tweet: O(log A).
         *
         * At most 10 tweets are emitted, so the merge takes O(10 log A).
         * More generally, for a feed limit L, it takes O(L log A).
         */
        List<Integer> feed = new ArrayList<>(10);

        while (!newestFirst.isEmpty() && feed.size() < 10) {
            /*
             * The heap's root is the newest tweet across all current
             * timeline candidates.
             */
            TweetCursor newestCursor = newestFirst.poll();

            feed.add(newestCursor.tweet().id());

            /*
             * Move one position backward in the SAME author's timeline.
             *
             * If the current index is 4, the next index is 3.
             * Index -1 means there are no older tweets remaining.
             */
            int olderIndex = newestCursor.timelineIndex() - 1;

            if (olderIndex >= 0) {
                List<Tweet> authorTimeline =
                        tweetsByUser.get(newestCursor.authorId());

                Tweet olderTweet = authorTimeline.get(olderIndex);

                newestFirst.offer(
                        new TweetCursor(
                                newestCursor.authorId(),
                                olderIndex,
                                olderTweet
                        )
                );
            }
        }

        /*
         * The feed contains at most 10 tweet IDs, ordered newest first.
         *
         * Time: O(min(10, M) * log A) for the merge,
         * plus O(A log A) for initialization.
         *
         * The result uses O(min(10, M)) space.
         */
        return feed;
    }

    public void follow(int followerId, int followeeId) {
        /*
         * Store the relationship in a set.
         *
         * Repeated calls are harmless because Set.add does not create
         * duplicate relationships.
         *
         * Self-following is harmless too: getNewsFeed uses a Set and
         * adds the requesting user exactly once.
         *
         * Time: O(1) expected.
         * Space: O(1) expected for a new relationship.
         */
        following.computeIfAbsent(
                followerId,
                ignored -> new HashSet<>()
        ).add(followeeId);
    }

    public void unfollow(int followerId, int followeeId) {
        /*
         * A missing follower entry or missing relationship is a no-op.
         *
         * Do not remove the user's own tweets or timeline.
         * The user's own timeline is added independently in getNewsFeed.
         *
         * Time: O(1) expected.
         * Auxiliary space: O(1).
         */
        Set<Integer> followees = following.get(followerId);

        if (followees != null) {
            followees.remove(followeeId);
        }
    }
}
```

## 5. Walk through the heap algorithm

Suppose the user follows two people, and the three timelines are:

```
User 1: [5, 8]
User 2: [6, 9]
User 3: [7, 10]
```

The timelines are stored oldest to newest. Assume the global posting sequence increases in the same order shown.

Initially, we put the newest tweet from each timeline into the max-heap:

```
Heap candidates: [8, 9, 10]

Newest = 10
```

The algorithm works as follows:

| Step | Tweet selected | Next tweet inserted from the same author | Feed so far           |
| ---- | -------------- | ---------------------------------------- | --------------------- |
| 1    | 10             | 7                                        | `[10]`                |
| 2    | 9              | 6                                        | `[10, 9]`             |
| 3    | 8              | 5                                        | `[10, 9, 8]`          |
| 4    | 7              | None                                     | `[10, 9, 8, 7]`       |
| 5    | 6              | None                                     | `[10, 9, 8, 7, 6]`    |
| 6    | 5              | None                                     | `[10, 9, 8, 7, 6, 5]` |

We stop when the heap is empty, because there are no more eligible tweets.

In a real example with more than 10 tweets, we stop as soon as the feed reaches 10 items.

### Why does the algorithm never miss a newer tweet?

This is the most important correctness argument to explain in an interview.

Consider any timeline. Its tweets are ordered chronologically:

```
Older --------------------------> Newer
  5          8          12
```

The heap initially contains `12`, the newest tweet from that timeline.

As long as `12` remains unprocessed, neither `8` nor `5` can be newer than it. Therefore, hiding the older tweets temporarily is safe.

When `12` is selected, we reveal `8`. When `8` is selected, we reveal `5`.

At every step, the heap contains the newest unprocessed tweet from every timeline that still has tweets. The maximum among these candidates is consequently the globally newest unprocessed tweet.

By induction, every selected tweet is the correct next item in the feed.

## 6. Time and space complexity comparison

Define:

- \\(F\\): number of users followed by the requesting user.
- \\(A = F + 1\\): maximum number of relevant timelines, including the requesting user.
- \\(M\\): total tweets in those timelines.
- \\(T\\): total tweets across the entire system.
- \\(L\\): requested feed limit, which is 10 in this problem.

| Operation                     | Brute force              | Sort candidates      | Heap merge                 |
| ----------------------------- | ------------------------ | -------------------- | -------------------------- |
| Post                          | \\(O(1)\\) amortized     | \\(O(1)\\) amortized | \\(O(1)\\) amortized       |
| Follow                        | \\(O(1)\\) expected      | \\(O(1)\\) expected  | \\(O(1)\\) expected        |
| Unfollow                      | \\(O(1)\\) expected      | \\(O(1)\\) expected  | \\(O(1)\\) expected        |
| Feed retrieval                | \\(O(T + M\log M + F)\\) | \\(O(F + M\log M)\\) | \\(O(A\log A + L\log A)\\) |
| Feed-specific auxiliary space | \\(O(M+F)\\)             | \\(O(M+F)\\)         | \\(O(A+L)\\)               |

For the heap approach, the full expression is:

\\[ O(A\log A + L\log A) \\]

The first term initializes the heap with at most one tweet per author. The second term performs up to \\(L\\) extractions and up to \\(L\\) insertions.

Since \\(L=10\\) is fixed, we commonly express the feed complexity as:

\\[ O(A\log A) \\]

This is the important improvement: the number of historical tweets \\(M\\) no longer determines feed retrieval time, because each timeline is traversed only as far as necessary to return the newest 10 tweets.

The heap solution is especially beneficial when users have long posting histories but follow relatively few people.

## 7. Edge cases to test

| Scenario                               | Expected behavior                                      |
| -------------------------------------- | ------------------------------------------------------ |
| User has never posted                  | Empty feed                                             |
| User has no followees                  | Their own newest tweets only                           |
| User has fewer than 10 eligible tweets | Return all eligible tweets                             |
| User has more than 10 eligible tweets  | Return only the newest 10                              |
| Followee has no tweets                 | Ignore that empty timeline                             |
| Follow is called twice                 | No duplicate tweets in the feed                        |
| Unfollow is called twice               | Second call does nothing                               |
| User unfollows a followee              | That followee's tweets disappear from subsequent feeds |
| User follows themselves                | No duplicate timeline; their tweets appear once        |
| Tweet IDs are not chronological        | Correct ordering using sequence numbers                |
| Several users post interleaved tweets  | Merge by global sequence, not by author or tweet ID    |

One particularly useful test is the following:

```
Twitter twitter = new Twitter();

twitter.postTweet(1, 100);
twitter.postTweet(2, 5);
twitter.follow(1, 2);

System.out.println(twitter.getNewsFeed(1));
// [5, 100]

twitter.unfollow(1, 2);

System.out.println(twitter.getNewsFeed(1));
// [100]
```

Even though tweet `100` has a larger ID, tweet `5` appears first because it was posted later. The sequence number, not the ID, determines recency.

## 8. Interviewer follow-up questions and answers

Q1. Why not just use a `PriorityQueue` containing every tweet in the system?

That would require considering tweets unrelated to the requesting user. We need only the tweets from the requesting user and their followees. The k-way merge uses one initial heap entry per relevant timeline, making the heap size proportional to the number of relevant authors rather than the number of historical tweets.

Q2. Why do we store tweets in a list instead of a linked list?

An `ArrayList` provides constant-time indexed access and efficient appends. Our cursor stores an index and moves backward, so a linked list's sequential traversal overhead would not help. We do not need to insert tweets in the middle because posting events are processed in sequence.

Q3. Why is a `Set` needed for follow relationships?

A set enforces uniqueness. Without it, repeated `follow()` calls could add the same author's timeline multiple times, causing duplicate tweet IDs in the feed.

Q4. Why use a global sequence number instead of timestamps?

For this problem, a counter is enough to establish posting order. It avoids clock precision, clock skew, and equal-timestamp concerns. In a distributed production system, a global counter may be difficult to maintain, so systems often use timestamps combined with tie-breakers or other ordering mechanisms.

Q5. What happens when a user unfollows someone while a feed is being generated?

The standard coding problem assumes sequential method calls, so the feed uses the current follow graph when it begins. A production implementation would need concurrency controls, consistent snapshots, or an appropriate consistency model to handle concurrent posting and follow changes safely.

Q6. Can we optimize initialization further by reading only 10 tweets from each timeline?

Yes. Since the feed limit is 10, no author can contribute more than 10 tweets to the final feed. We could seed the heap with the newest \\(\min(10,n_i)\\) tweets per author and use a different merge strategy, but inserting every one of those candidates increases initialization work. The one-cursor-per-author approach is simpler and already gives excellent performance when the number of followed users is modest.

Q7. What would change if the feed limit were configurable?

Replace the hardcoded `10` with a limit parameter \\(L\\). The merge complexity becomes \\(O(A\log A + L\log A)\\), and result space becomes \\(O(L)\\).

Q8. What are the limitations of this design at production scale?

The in-memory design assumes all timelines and relationships fit in memory and that method calls are appropriately coordinated. A production system may need persistent storage, distributed timeline services, caching, pagination, deletion support, and a strategy for very large accounts. The same k-way merge idea remains useful when reading ordered tweet streams from storage.

## 9. How to recognize this pattern in interviews

When you see a problem that asks you to combine the newest items from multiple independently ordered sources, think of a heap-based k-way merge.

A useful thought process is:

1. Identify the independent sorted sequences.
2. Determine the next candidate from each sequence.
3. Ask which candidate should be selected globally.
4. Use a heap to efficiently select the best candidate.
5. After selecting one item, advance only the sequence that produced it.
6. Stop once the required number of results is reached.

This pattern applies beyond Twitter: merging logs, combining event streams, aggregating recent messages, and retrieving the top results from multiple ordered feeds.

Final interview recommendation: Start by proposing the per-user timeline design. Explain that sorting every relevant tweet wastes work because only 10 results are required. Then introduce the max-heap and the invariant that each timeline contributes only its newest unprocessed tweet. That reasoning demonstrates not just knowledge of `PriorityQueue`, but why the algorithm is correct and efficient.
