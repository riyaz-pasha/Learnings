# 1670. Design Front Middle Back Queue — Java 24

The key to solving this problem is understanding how to represent the middle of a queue efficiently.

A normal queue supports operations at the front and back. This problem also lets us insert and remove elements from the middle. We need a design that keeps all six operations simple and efficient.

The best approach is to use two `ArrayDeque<Integer>` instances:

- `left` stores the front half of the queue.
- `right` stores the back half of the queue.

We maintain one important invariant:

\\[ \boxed{\text{left.size()}=\text{right.size()} \quad \text{or} \quad \text{left.size()}=\text{right.size()}+1} \\]

In other words, `left` always contains either the same number of elements as `right`, or exactly one more.

This makes the middle easy to locate without searching through the queue.

## 0. Understand the problem in simple terms

Imagine a queue of people standing in a line:

```
Front                              Back
  ↓                                  ↓
[ 1, 2, 3, 4, 5 ]
```

You can perform six operations:

| Operation        | Meaning                                         |
| ---------------- | ----------------------------------------------- |
| `pushFront(10)`  | Add `10` at the beginning.                      |
| `pushMiddle(10)` | Insert `10` at the middle position.             |
| `pushBack(10)`   | Add `10` at the end.                            |
| `popFront()`     | Remove and return the first element.            |
| `popMiddle()`    | Remove and return the frontmost middle element. |
| `popBack()`      | Remove and return the last element.             |

If a removal is attempted on an empty queue, return `-1`.

### What does “frontmost middle” mean?

This is the most important detail in the problem.

For an odd-sized queue:

```
[1, 2, 3, 4, 5]
       ↑
     middle
```

The middle element is `3`.

For an even-sized queue:

```
[1, 2, 3, 4, 5, 6]
       ↑  ↑
       3  4
```

There are two central elements: `3` and `4`. The problem asks us to use the frontmost one, which is `3`.

Therefore:

- `pushMiddle` inserts immediately before the current middle element for odd-sized queues.
- `pushMiddle` inserts between the two halves for even-sized queues.
- `popMiddle` removes the frontmost middle element.

Let's derive a design that handles these rules naturally instead of memorizing separate index formulas.

## 1. Clarifying questions to ask the interviewer

Before coding, I would confirm these details:

1. Which middle element should be removed when the queue has an even number of elements? The statement specifies the frontmost middle element. This determines whether `popMiddle()` removes the last element of the front half or the first element of the back half.
2. What should removal return when the queue is empty? The required answer is `-1`. This matters because our implementation must check emptiness before removing an element.
3. Are all operations required to be constant time? The problem does not explicitly state this requirement, but an efficient design should aim for \\(O(1)\\) per operation. This leads us to a two-deque solution instead of an array-backed list.
4. Can the queue contain duplicate values? Yes, there is no uniqueness requirement. Our design stores values directly and does not rely on them being unique.

## 2. Core intuition: Split the queue into two halves

Instead of maintaining one queue and repeatedly searching for its middle, split it into two deques.

```
Complete queue = left + right

left                         right
Front                        Back
  ↓                            ↓
[ 1, 2, 3 ]                 [ 4, 5 ]

                ↑
        boundary between halves
```

Here, `left` contains the first three elements, and `right` contains the remaining two.

We use these rules:

- The front of the complete queue is the front of `left`.
- The back of the complete queue is the back of `right`, unless `right` is empty.
- The middle element we need to remove is always the last element of `left`.
- Inserting in the middle means inserting at the back of `left`, after ensuring the halves are balanced.

Why is the last element of `left` always the correct middle element?

Because we maintain this invariant:

```
left.size() == right.size()
             OR
left.size() == right.size() + 1
```

## 3. How do we keep the two halves balanced?

We'll use one helper method, `rebalance()`.

It restores the invariant after every operation:

```
If left has more than one extra element:
    Move left's last element to right's front.

If right has more elements than left:
    Move right's first element to left's back.
```

For example, suppose we have:

```
left = [1, 2, 3, 4]
right = [5, 6]
```

The left side has two extra elements, so the first move gives:

```
left = [1, 2, 3]
right = [4, 5, 6]
```

Now the halves are equal.

In our implementation, each operation changes the size by at most one, and the invariant held before that operation. Therefore, one balancing move is sufficient. We don't need a loop.

This is the central mental model: let the deques handle their respective ends, then move at most one boundary element to restore the correct split.

## 4. Solution 1 — Brute force using `ArrayList`

The simplest solution is to store the entire queue in an `ArrayList<Integer>`.

Why start here? It lets us express the problem directly using indices, making it an excellent correctness baseline before optimizing.

```
import java.util.ArrayList;
import java.util.List;

class FrontMiddleBackQueueBruteForce {

    // Stores the queue from front to back.
    private final List<Integer> elements = new ArrayList<>();

    public FrontMiddleBackQueueBruteForce() {
        // ArrayList starts empty.
    }

    public void pushFront(int val) {
        // Index 0 represents the front.
        // Inserting here shifts every existing element one position right.
        elements.add(0, val);
    }

    public void pushMiddle(int val) {
        // Integer division rounds down.
        //
        // n = 5: index 2 -> [1, 2, val, 3, 4, 5]
        // n = 4: index 2 -> [1, 2, val, 3, 4]
        //
        // In both cases, inserting at n / 2 gives the required middle position.
        elements.add(elements.size() / 2, val);
    }

    public void pushBack(int val) {
        // Appending at the end is amortized O(1).
        elements.add(val);
    }

    public int popFront() {
        // Removing from an empty queue must return -1.
        if (elements.isEmpty()) {
            return -1;
        }

        // Index 0 is the front. The remaining elements shift left.
        return elements.remove(0);
    }

    public int popMiddle() {
        if (elements.isEmpty()) {
            return -1;
        }

        // (n - 1) / 2 selects the frontmost middle:
        //
        // n = 5 -> index 2 -> element 3
        // n = 6 -> index 2 -> element 3, not element 4
        //
        // The subtraction is important: n / 2 would select index 3
        // when n = 6, which is the backmost of the two middle elements.
        int middleIndex = (elements.size() - 1) / 2;

        // Removing this index shifts all subsequent elements left.
        return elements.remove(middleIndex);
    }

    public int popBack() {
        if (elements.isEmpty()) {
            return -1;
        }

        // The last index is size - 1.
        // Removing the last element does not shift any remaining elements.
        return elements.remove(elements.size() - 1);
    }

    /*
     * Time complexity:
     * - pushFront: O(n), because existing elements shift right.
     * - pushMiddle: O(n), because elements after the insertion shift right.
     * - pushBack: amortized O(1).
     * - popFront: O(n), because remaining elements shift left.
     * - popMiddle: O(n), because subsequent elements shift left.
     * - popBack: O(1).
     *
     * Space complexity: O(n) for n stored elements.
     *
     * This solution is simple and correct, but five of the six operations
     * can require linear time. We can do better with two deques.
     */
}
```

### Why is `popMiddle()` different from `pushMiddle()`?

This is a common source of confusion.

- `pushMiddle()` uses `n / 2`.
- `popMiddle()` uses `(n - 1) / 2`.

For a queue of six elements:

```
Indices:  0  1  2  3  4  5
Values:   1  2  3  4  5  6
```

Inserting at index `6 / 2 = 3` would insert after the first three existing elements. That's the required insertion position.

But removing at index `(6 - 1) / 2 = 2` removes `3`, the frontmost middle.

Insertion and removal have different index formulas because they must preserve different positions relative to the existing elements.

## 5. Solution 2 — Optimal using two `ArrayDeque` instances

Now we replace index-based movement with operations at deque ends.

The implementation maintains the following invariant at all times:

```
left.size() == right.size()
OR
left.size() == right.size() + 1
```

`ArrayDeque` provides efficient insertion and removal at both ends, so each queue operation takes \\(O(1)\\) time.

```
import java.util.ArrayDeque;
import java.util.Deque;

class FrontMiddleBackQueue {

    /*
     * The complete queue is always:
     *
     *     left followed by right
     *
     * Example:
     *
     *     left = [1, 2, 3]
     *     right = [4, 5]
     *
     *     Complete queue = [1, 2, 3, 4, 5]
     *
     * Why use two deques?
     *
     * A single deque cannot directly access its middle in O(1).
     * By maintaining the split at the middle, the middle element we need
     * is always the last element of left.
     *
     * INVARIANT:
     *
     *     left.size() == right.size()
     *     OR
     *     left.size() == right.size() + 1
     *
     * Thus, left contains either the same number of elements as right
     * or exactly one extra element.
     *
     * Consequently:
     * - Front       = left.peekFirst()
     * - Middle      = left.peekLast()
     * - Back        = right.peekLast(), if right is nonempty;
     *                 otherwise left.peekLast()
     */
    private final Deque<Integer> left = new ArrayDeque<>();
    private final Deque<Integer> right = new ArrayDeque<>();

    public FrontMiddleBackQueue() {
        // Both deques start empty.
    }

    public void pushFront(int val) {
        // The new element belongs at the very front of the complete queue.
        left.addFirst(val);

        // Adding to left may make it too large.
        // Move at most one boundary element if needed.
        rebalance();
    }

    public void pushMiddle(int val) {
        /*
         * We want to insert at index floor(n / 2).
         *
         * Case 1: Both halves have equal size.
         *
         *     left  = [1, 2]
         *     right = [3, 4]
         *
         *     Add 5 to the end of left:
         *
         *     left  = [1, 2, 5]
         *     right = [3, 4]
         *
         *     Result = [1, 2, 5, 3, 4]
         *
         * This is the correct middle insertion.
         *
         * Case 2: Left has one extra element.
         *
         *     left  = [1, 2, 3]
         *     right = [4, 5]
         *
         *     First move 3, the last element of left, to the front of right:
         *
         *     left  = [1, 2]
         *     right = [3, 4, 5]
         *
         *     Then append the new value 6 to left:
         *
         *     left  = [1, 2, 6]
         *     right = [3, 4, 5]
         *
         *     Result = [1, 2, 6, 3, 4, 5]
         *
         * Both cases leave the halves balanced.
         */
        if (left.size() > right.size()) {
            right.addFirst(left.removeLast());
        }

        // Inserting at the end of left places val at index floor(n / 2).
        left.addLast(val);
    }

    public void pushBack(int val) {
        // Append to the end of the complete queue.
        right.addLast(val);

        // If right becomes larger than left, transfer its first element
        // to the end of left so the invariant is restored.
        rebalance();
    }

    public int popFront() {
        if (left.isEmpty()) {
            // Both halves are empty, so the complete queue is empty.
            return -1;
        }

        // The first element of left is the first element of the full queue.
        int value = left.removeFirst();

        // Removing from left might make right larger than left.
        // If so, move the first element of right to the end of left.
        rebalance();

        return value;
    }

    public int popMiddle() {
        if (left.isEmpty()) {
            // An empty queue has no middle element.
            return -1;
        }

        /*
         * The last element of left is always the frontmost middle element.
         *
         * Odd size:
         *     left  = [1, 2, 3]
         *     right = [4, 5]
         *     Remove 3, the unique middle.
         *
         * Even size:
         *     left  = [1, 2, 3]
         *     right = [4, 5, 6]
         *     Remove 3, the frontmost of the two middle elements.
         *
         * Since left has either the same size as right or one extra element,
         * removing its last element always implements the required rule.
         *
         * No rebalance is necessary:
         * - If the sizes were equal, left becomes one smaller.
         * - If left had one extra element, the sizes become equal.
         *
         * Wait: in the equal-size case, removing from left leaves right
         * larger by one, which is allowed only after balancing. Therefore
         * we must rebalance after removal.
         */
        int value = left.removeLast();

        rebalance();

        return value;
    }

    public int popBack() {
        if (left.isEmpty()) {
            // Both halves are empty.
            return -1;
        }

        /*
         * The last element of right is the back of the complete queue
         * whenever right is nonempty.
         *
         * If right is empty, the queue contains only left, so its last
         * element is also the back of the complete queue.
         */
        int value;

        if (!right.isEmpty()) {
            value = right.removeLast();
        } else {
            value = left.removeLast();
        }

        // Removing from right may leave left too large.
        // Move one element from left to right if necessary.
        rebalance();

        return value;
    }

    private void rebalance() {
        /*
         * Restore the invariant:
         *
         *     left.size() == right.size()
         *     OR
         *     left.size() == right.size() + 1
         *
         * If left is too large, move its last element to right's front.
         *
         *     left  = [1, 2, 3, 4]
         *     right = [5, 6]
         *
         *     Becomes:
         *
         *     left  = [1, 2, 3]
         *     right = [4, 5, 6]
         *
         * If right is larger, move its first element to left's back.
         *
         *     left  = [1, 2]
         *     right = [3, 4, 5]
         *
         *     Becomes:
         *
         *     left  = [1, 2, 3]
         *     right = [4, 5]
         *
         * Why are two independent if statements sufficient?
         *
         * Every public operation changes the total size by at most one,
         * and the invariant was true before that operation.
         * Therefore, the sizes can become unbalanced by at most one element.
         * At most one transfer restores the invariant.
         *
         * The second if checks the current sizes after the first possible
         * transfer, keeping the method robust and easy to reason about.
         */
        if (left.size() > right.size() + 1) {
            right.addFirst(left.removeLast());
        }

        if (left.size() < right.size()) {
            left.addLast(right.removeFirst());
        }
    }

    /*
     * TIME COMPLEXITY:
     *
     * Every public operation performs a constant number of deque operations.
     * ArrayDeque.addFirst, addLast, removeFirst, and removeLast are O(1)
     * amortized operations.
     *
     * pushFront:  O(1)
     * pushMiddle: O(1)
     * pushBack:   O(1)
     * popFront:   O(1)
     * popMiddle:  O(1)
     * popBack:    O(1)
     *
     * rebalance: O(1), because at most one element moves between the deques.
     *
     * SPACE COMPLEXITY:
     *
     * O(n), where n is the number of elements currently stored.
     * Each element belongs to exactly one of the two deques.
     */
}
```

## 6. Walk through the example step by step

Let's simulate the problem's example using the two-deque implementation.

| Operation       | `left`      | `right` | Result         |
| --------------- | ----------- | ------- | -------------- |
| Initialize      | `[]`        | `[]`    | Queue is empty |
| `pushFront(1)`  | `[1]`       | `[]`    | `[1]`          |
| `pushBack(2)`   | `[1]`       | `[2]`   | `[1, 2]`       |
| `pushMiddle(3)` | `[1, 3]`    | `[2]`   | `[1, 3, 2]`    |
| `pushMiddle(4)` | `[1, 4, 3]` | `[2]`   | `[1, 4, 3, 2]` |
| `popFront()`    | `[4, 3]`    | `[2]`   | Returns `1`    |
| `popMiddle()`   | `[4]`       | `[2]`   | Returns `3`    |
| `popMiddle()`   | `[2]`       | `[]`    | Returns `4`    |
| `popBack()`     | `[]`        | `[]`    | Returns `2`    |
| `popFront()`    | `[]`        | `[]`    | Returns `-1`   |

Let's examine the trickiest operations more carefully.

### Step A: `pushMiddle(3)`

Before the operation:

```
left  = [1]
right = [2]
```

Both halves have equal size, so we append `3` to the end of `left`.

```
left  = [1, 3]
right = [2]

Queue = [1, 3, 2]
```

### Step B: `pushMiddle(4)`

Before the operation:

```
left  = [1, 3]
right = [2]
```

`left` is larger by one. We first move its last element, `3`, to the front of `right`.

```
left  = [1]
right = [3, 2]
```

Now append `4` to the end of `left`.

```
left  = [1, 4]
right = [3, 2]
```

Correction: the resulting complete queue is `[1, 4, 3, 2]`, and the split must have `left = [1, 4]`, `right = [3, 2]`. The sizes are equal, as required.

### Step C: `popMiddle()`

After `popFront()`, the queue is:

```
left  = [4, 3]
right = [2]

Queue = [4, 3, 2]
```

The last element of `left` is `3`. Remove it:

```
left  = [4]
right = [2]

Queue = [4, 2]
```

The next `popMiddle()` removes `4`, leaving `[2]`.

The important point is that we never calculate a middle index or scan the queue. The invariant tells us where the middle is.

## 9. Interviewer follow-up questions and answers

### Q1. Why use two deques instead of one deque?

A single deque supports constant-time operations at its two ends, but it cannot directly access its middle in constant time.

With two deques, the middle is always at `left.removeLast()`. This avoids searching, shifting, or calculating indices.

### Q2. Why must `left` contain either the same number of elements as `right` or one extra?

Because we want the last element of `left` to always be the frontmost middle.

If `right` had more elements than `left`, the split would be too far toward the front. If `left` had two extra elements, the split would be too far toward the back.

The invariant ensures that the split is always at the correct position.

### Q3. Why does `pushMiddle()` move an element before inserting?

When `left` has one extra element, its last element currently occupies the middle position.

Moving that element to the front of `right` creates room for the new value at the end of `left`. The new value then occupies the required middle insertion position.

When both halves are already equal, no move is necessary.

### Q4. Can `rebalance()` use `while` instead of `if`?

Yes, but it is unnecessary here.

Since every public operation changes the size by at most one, and the invariant holds before each operation, the imbalance can never exceed one element. A single transfer is sufficient.

If the implementation later changes to support batch insertion or deletion, a loop could become useful.

### Q5. Why is the last element of `left` the frontmost middle for both odd and even sizes?

Let the total number of elements be \\(n\\).

- If \\(n=2k\\), both halves have \\(k\\) elements. The last element of `left` has index \\(k-1\\), which is the frontmost middle.
- If \\(n=2k+1\\), `left` has \\(k+1\\) elements. Its last element has index \\(k\\), which is the unique middle.

Thus, `left.removeLast()` implements the required behavior for both cases.

### Q6. Why not use a linked list?

A linked list can insert or remove at known nodes in constant time, but finding the middle still takes \\(O(n)\\) unless we maintain additional structure. Two deques provide a simpler design with constant-time operations and less bookkeeping.

### Q7. Is the two-deque solution always preferable?

For this problem, yes, when constant-time operations are the goal. However, the `ArrayList` solution is simpler and perfectly reasonable when the queue is small or performance is not important. The constraints allow only 1,000 operations, so both solutions would likely pass.

## 10. Final mental model

Remember these three rules rather than memorizing six separate implementations:

1. Split the queue into two halves. `left` stores the front half, and `right` stores the back half.
2. Keep the left half equal in size to the right half or one element larger. This makes the last element of `left` the frontmost middle.
3. Perform the operation at the appropriate deque end, then rebalance if necessary.

```
                  Complete queue
             ┌───────────────────────┐
             │         left + right  │
             └───────────────────────┘
                       │
              ┌────────┴────────┐
              │                 │
           left deque        right deque
              │                 │
         Front: first       Back: last
         Middle: last
              │                 │
              └────────┬────────┘
                       │
                 Rebalance
                       │
          left == right OR left == right + 1
```

The essential insight is that we make the middle easy to access by maintaining the correct split, instead of trying to find the middle each time an operation is called.

# 1670. Design Front Middle Back Queue — How to Discover the Solution in an Interview

The most important thing to learn from this problem is not the code. It's how to recognize that two deques can make middle operations as cheap as front and back operations.

Let's rebuild the solution from scratch, as if you're sitting in an interview and have never seen this problem before.

## 1. Start by translating the problem into operations

You are given a sequence of elements, for example:

```
[10, 20, 30, 40, 50]
```

You need to support three kinds of insertion and three kinds of removal:

- Front: the beginning of the sequence.
- Middle: the center of the sequence.
- Back: the end of the sequence.

The first thing I'd ask myself in an interview is:

Which operations are easy with a data structure I already know, and which operations are difficult?

Let's compare the usual candidates.

| Data structure | Front operations     | Back operations | Middle operations                 |
| -------------- | -------------------- | --------------- | --------------------------------- |
| ArrayList      | Slow: elements shift | Fast            | Slow: elements shift              |
| LinkedList     | Fast                 | Fast            | Slow: must traverse to the middle |
| ArrayDeque     | Fast                 | Fast            | Slow: no direct middle access     |
| Two deques     | Fast                 | Fast            | Potentially fast                  |

The problem is not that a middle element is impossible to find. The problem is that finding or modifying the middle usually requires work proportional to the number of elements.

That is the performance problem we need to solve.

## 2. Ask: what makes the middle expensive?

Consider this queue:

```
[10, 20, 30, 40, 50, 60, 70]
```

Suppose we use a linked list.

To remove `40`, we must walk through the list until we reach the middle. That takes \\(O(n)\\) time.

With an `ArrayList`, we can calculate the middle index in \\(O(1)\\), but removing the element shifts all subsequent elements. That also takes \\(O(n)\\) time.

Notice an important distinction:

- Finding an index can be constant time.
- Modifying a data structure at that index may still be linear time.

So our objective is not merely to calculate the middle. We need to represent the queue so that its middle is always at a position where insertion and removal are cheap.

That leads to the first major interview insight:

> If an operation is expensive because we repeatedly search for or shift elements around a position, consider maintaining that position as a boundary in your data structure.

## 3. The key question: can we stop the middle from moving?

Imagine dividing the queue into two parts:

```
Queue:
[10, 20, 30, 40, 50, 60, 70]

Split:
[10, 20, 30, 40] | [50, 60, 70]
```

Why choose two parts?

Because the existing data structures already give us efficient operations at their ends. If the boundary between the two parts represents the middle, we can access that boundary without traversing the entire sequence.

Our target is:

```
left deque                right deque
Front                      Back
  ↓                          ↓
[10, 20, 30, 40] | [50, 60, 70]
                 ↑
          Middle boundary
```

Now the key observation is:

- The front of the entire queue is the front of `left`.
- The back of the entire queue is the back of `right`, when `right` is nonempty.
- The middle is at the boundary between the two deques.

We have transformed a difficult middle operation into an operation at the end of a deque.

This is the real reason the two-deque solution works.

## 4. How do you discover the balancing rule?

This is the part I want you to be able to derive independently in an interview.

Don't start by memorizing:

```
left.size() == right.size()
    || left.size() == right.size() + 1
```

Instead, derive it from the problem.

### Step 1: Try a queue with an odd number of elements

```
[10, 20, 30, 40, 50]
```

The middle is `30`.

To make the middle the last element of `left`, split the queue like this:

```
left                 right
[10, 20, 30] | [40, 50]
          ↑
        middle
```

The left half has one extra element.

### Step 2: Try a queue with an even number of elements

```
[10, 20, 30, 40, 50, 60]
```

The frontmost middle is `30`, not `40`.

So split it like this:

```
left                 right
[10, 20, 30] | [40, 50, 60]
          ↑
        middle
```

The halves have equal sizes, and the last element of `left` is the frontmost middle.

### Step 3: Combine the two observations

For odd sizes, `left` has one extra element.

For even sizes, both halves have equal sizes.

Therefore, the only two valid size relationships are:

```
left.size() == right.size()
OR
left.size() == right.size() + 1
```

We didn't invent this invariant. We derived it from where the middle must be.

That is exactly how you should approach invariants in interviews: start with the behavior the problem requires, construct a representation that supports it, and then derive the rule that keeps that representation correct.

## 5. How do we derive each operation?

Once the representation is chosen, don't invent six independent algorithms. Derive each operation from the same invariant.

Assume we have:

```
left  = [10, 20, 30]
right = [40, 50]

Complete queue = [10, 20, 30, 40, 50]
```

### A. `pushFront(val)`

Ask: where does the new element belong?

At the front of the entire queue, so it belongs at the front of `left`.

```
left.addFirst(val);
```

But adding an element might make `left` too large. Therefore, restore the invariant afterward.

### B. `pushBack(val)`

The new element belongs at the back of the entire queue, so append it to the back of `right`.

```
right.addLast(val);
```

Again, rebalance afterward if necessary.

### C. `popFront()`

The first element of the complete queue is the first element of `left`.

```
left.removeFirst();
```

Then rebalance, because removing from `left` might make `right` larger.

### D. `popBack()`

If `right` is nonempty, remove its last element. If `right` is empty, the entire queue is in `left`, so remove the last element of `left`.

Then rebalance.

### E. `popMiddle()`

This is now easy. We deliberately designed the representation so that the frontmost middle is always the last element of `left`.

```
left.removeLast();
```

Rebalance afterward.

### F. `pushMiddle(val)`

This operation requires a little more reasoning.

There are two possible situations.

Situation 1: Both halves have equal sizes.

```
left  = [10, 20]
right = [30, 40]
```

The queue is even-sized. Inserting at the middle means inserting between `20` and `30`.

```
left  = [10, 20, 25]
right = [30, 40]

Result = [10, 20, 25, 30, 40]
```

So we append to `left`.

Situation 2: `left` has one extra element.

```
left  = [10, 20, 30]
right = [40, 50]
```

The queue is odd-sized. The insertion position is immediately before the existing middle element `30`.

We must move `30` to the front of `right`, then insert the new value at the end of `left`.

```
Before:
left  = [10, 20, 30]
right = [40, 50]

Move 30 across the boundary:
left  = [10, 20]
right = [30, 40, 50]

Insert 25:
left  = [10, 20, 25]
right = [30, 40, 50]

Result:
[10, 20, 25, 30, 40, 50]
```

The insertion rules follow directly from the desired position and the invariant.

## 6. The interview thought process, from naive to optimal

Here is how I'd expect a strong candidate to approach the problem aloud.

```

1. Understand the required operations.
   The queue supports front, middle, and back insertion/removal.

2. Identify the expensive operation.
   Middle insertion/removal is expensive with ordinary lists and deques.

3. Establish a performance goal.
   Aim for O(1) per operation, if possible.

4. Change the representation.
   Split the queue into a front half and a back half.

5. Define the invariant.
   The left half has the same number of elements as the right half,
   or one extra element.

6. Prove the middle is accessible.
   The last element of the left half is the frontmost middle.

7. Derive each operation.
   Use deque ends instead of searching for an index.

8. Restore the invariant after updates.
   Move at most one element across the boundary.

9. Verify odd/even sizes and empty-queue behavior.

10. Analyze complexity.
    Each operation performs a constant number of deque operations,
    so each is O(1) amortized.

```

Notice that the data structure comes only after identifying the bottleneck and deciding what property must remain true.

That sequence is much more reusable than memorizing the solution.

## 7. How to turn this reasoning into code

Once the reasoning is complete, the implementation becomes relatively small. Here is the version I'd recommend practicing for interviews.

```
import java.util.ArrayDeque;
import java.util.Deque;

class FrontMiddleBackQueue {

    /*
     * Representation:
     *
     * The complete queue is left followed by right.
     *
     * Invariant:
     *     left.size() == right.size()
     *     OR
     *     left.size() == right.size() + 1
     *
     * This means the last element of left is always the frontmost middle.
     *
     * Time: O(1) amortized per operation.
     * Space: O(n) for n stored elements.
     */
    private final Deque<Integer> left = new ArrayDeque<>();
    private final Deque<Integer> right = new ArrayDeque<>();

    public void pushFront(int val) {
        left.addFirst(val);
        rebalance();
    }

    public void pushMiddle(int val) {
        /*
         * If left has one extra element, move its last element across
         * the boundary first. This creates the correct middle position.
         *
         * Then append val to left.
         */
        if (left.size() > right.size()) {
            right.addFirst(left.removeLast());
        }

        left.addLast(val);
    }

    public void pushBack(int val) {
        right.addLast(val);
        rebalance();
    }

    public int popFront() {
        if (left.isEmpty()) {
            return -1;
        }

        int value = left.removeFirst();
        rebalance();
        return value;
    }

    public int popMiddle() {
        if (left.isEmpty()) {
            return -1;
        }

        // By our invariant, the last element of left is the frontmost middle.
        int value = left.removeLast();
        rebalance();
        return value;
    }

    public int popBack() {
        if (left.isEmpty()) {
            return -1;
        }

        // The complete queue's last element is in right if it is nonempty.
        int value = right.isEmpty()
                ? left.removeLast()
                : right.removeLast();

        rebalance();
        return value;
    }

    private void rebalance() {
        /*
         * The only allowed size relationships are:
         * left == right, or left == right + 1.
         *
         * Every public operation changes the total size by at most one,
         * so at most one transfer is needed to restore the invariant.
         */
        if (left.size() > right.size() + 1) {
            right.addFirst(left.removeLast());
        } else if (left.size() < right.size()) {
            left.addLast(right.removeFirst());
        }
    }
}
```

One subtle point worth remembering: `pushMiddle()` handles the balancing directly, so it does not need to call `rebalance()` afterward. Its two cases both leave the halves balanced.

## 9. How to recognize this pattern in other interview problems

The broader pattern is maintaining a useful boundary between two data structures.

Whenever you see a problem involving a middle, a median, a rank, or two sides of a sequence, ask these questions:

1. Can I split the data into two parts?
2. Can each part support the operations I need at its ends?
3. What size relationship must hold between the parts?
4. Can I restore that relationship with only a constant number of moves?
5. Does the boundary identify the element I need?

This pattern appears in several other problems:

| Problem                        | Similar idea                                                            |
| ------------------------------ | ----------------------------------------------------------------------- |
| Find Median from Data Stream   | Two heaps; the heap boundary identifies the median.                     |
| Design Front Middle Back Queue | Two deques; the boundary identifies the middle.                         |
| MKAverage                      | Three ordered partitions; the boundaries isolate the values to average. |
| Sliding Window Median          | Maintain lower and upper partitions while the window changes.           |

The implementations differ, but the underlying thinking is similar: maintain a partition so that an expensive query becomes a cheap operation on the boundary.

## 10. Interviewer follow-up questions

Q: How do you prove that `popMiddle()` is correct?

The invariant guarantees that `left` has either the same number of elements as `right` or one extra. For an even-sized queue, the two middle elements straddle the boundary, so the last element of `left` is the frontmost one. For an odd-sized queue, that same element is the unique middle. Therefore, removing the last element of `left` is correct in both cases.

Q: Why is rebalancing constant time?

Each public operation changes the total number of elements by at most one. Before the operation, the sizes satisfy the invariant. Consequently, after the operation, at most one element needs to cross the boundary to restore the invariant.

Q: What if we allowed inserting or removing several elements in a single operation?

Then the size difference could grow by more than one. A single transfer might not be sufficient; we'd use a loop to restore the invariant. The total cost would depend on how many elements were transferred.

Q: What is the most important correctness condition?

The size invariant. If it is maintained, the middle operation is easy to implement correctly. If it is violated, `left.removeLast()` might no longer remove the required middle element.

## Final takeaway

When you encounter a difficult operation in an interview, don't immediately search for a clever formula.

Instead, think in this order:

Bottleneck → Representation → Invariant → Operations → Proof → Complexity.

For this problem:

- Bottleneck: accessing the middle efficiently.
- Representation: two deques.
- Invariant: the left half is equal in size to the right half or one element larger.
- Operations: work at deque ends.
- Proof: the last element of `left` is always the frontmost middle.
- Complexity: \\(O(1)\\) amortized time per operation and \\(O(n)\\) space.

If you can derive those six points yourself, you genuinely understand the solution rather than simply remembering the code.
