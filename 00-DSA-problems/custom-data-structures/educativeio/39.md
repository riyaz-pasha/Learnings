# LeetCode 1188 — Design Bounded Blocking Queue

Problem: [Design Bounded Blocking Queue](https://leetcode.com/problems/design-bounded-blocking-queue/description/?utm_source=chatgpt.com)

Difficulty: Medium

The key interview concept here is concurrency, thread coordination, and producer-consumer synchronization. Unlike ordinary queue design problems, this problem requires multiple threads to wait when an operation cannot proceed and wake up when another thread changes the queue's state.

## 0. Simplify the problem statement

Imagine a queue that can hold at most `capacity` elements.

Two kinds of threads use this queue:

- Producer: calls `enqueue(element)` to add an element.
- Consumer: calls `dequeue()` to remove and retrieve an element.

The queue has two important rules:

1. If the queue is full, a producer must wait until a consumer removes an element.
2. If the queue is empty, a consumer must wait until a producer adds an element.

The word blocking is crucial: the operation waits rather than throwing an exception or returning immediately.

For example, suppose the capacity is `2`.

| Operation             | Queue state | What happens?                   |
| --------------------- | ----------- | ------------------------------- |
| `enqueue(10)`         | `[10]`      | Adds 10                         |
| `enqueue(20)`         | `[10, 20]`  | Adds 20; queue is full          |
| `enqueue(30)`         | `[10, 20]`  | Producer blocks                 |
| `dequeue()`           | `[20]`      | Removes 10; producer can resume |
| `enqueue(30)` resumes | `[20, 30]`  | Adds 30                         |

The queue must also support multiple producers and consumers running concurrently. That means we must protect shared state against race conditions.

## 1. Clarifying questions to ask the interviewer

These questions help determine the correct concurrency guarantees and avoid solving a simpler problem than the one requested.

1. Can multiple producers and consumers execute concurrently? Yes, that is the purpose of the problem. We must synchronize access to the queue.
2. Should `enqueue` wait indefinitely if the queue is full? Yes. It should wait until capacity becomes available, assuming the thread is not interrupted.
3. Should `dequeue` wait indefinitely if the queue is empty? Yes. It should wait until an element is available.
4. Can we use Java's built-in `BlockingQueue`? For this LeetCode design exercise, no. We need to implement the blocking behavior ourselves.
5. What should happen if a waiting thread is interrupted? Java's `wait()` can throw `InterruptedException`. We should preserve the problem's required method signatures and follow its expected interruption handling. In production code, interruption should generally be propagated or the interrupt status restored.
6. Does `size()` need to be thread-safe? Yes. It must return a consistent queue size even when other threads are adding or removing elements.

## 2. Core intuition: think in terms of permissions

The easiest way to recognize this problem in an interview is to ask:

What exactly prevents an enqueue or dequeue from proceeding?

- Enqueue is blocked because there are no empty slots.
- Dequeue is blocked because there are no available elements.

This leads to two possible implementation strategies:

1. Use a lock and condition variables (`synchronized`, `wait()`, `notifyAll()`).
2. Use semaphores to count available slots and available elements.

Both approaches can solve the problem correctly. We'll derive both rather than treating either as magic.

### Approach A: lock + `wait()` + `notifyAll()`

Maintain three things:

- A FIFO queue.
- A maximum capacity.
- A monitor lock protecting every read and write of the queue.

The queue's state determines whether an operation can proceed.

| Queue condition | Producer    | Consumer    |
| --------------- | ----------- | ----------- |
| Empty           | Can enqueue | Must wait   |
| Partially full  | Can enqueue | Can dequeue |
| Full            | Must wait   | Can dequeue |

When a producer adds an element, consumers may now be able to proceed.

When a consumer removes an element, producers may now be able to proceed.

### Why `while`, not `if`?

This is one of the most important interview details.

```
while (queue.size() == capacity) {
    wait();
}
```

A thread may wake up even though the condition it needs is still false. This can happen because of spurious wakeups or because another thread wins the race to consume the available space.

For example, capacity is `1`, and the queue is full.

1. Producers P1 and P2 are waiting.
2. A consumer removes the element and wakes waiting threads.
3. P1 acquires the lock first and inserts a new element.
4. P2 acquires the lock afterward.
5. P2 must check the condition again because the queue is full once more.

An `if` statement would let P2 continue incorrectly. A `while` loop forces it to wait again.

The important guarantee is that checking the condition and modifying the queue happen while holding the same lock. This prevents race conditions.

## 3. Solution 1 — Brute-force approach and why it fails

A normal queue with no synchronization might look like this:

```
class NaiveBoundedQueue {
    private final int capacity;
    private final Deque<Integer> queue = new ArrayDeque<>();

    NaiveBoundedQueue(int capacity) {
        this.capacity = capacity;
    }

    void enqueue(int element) {
        if (queue.size() < capacity) {
            queue.offerLast(element);
        }
    }

    int dequeue() {
        return queue.isEmpty() ? -1 : queue.pollFirst();
    }

    int size() {
        return queue.size();
    }
}
```

This code is deliberately incorrect for the problem.

- It silently drops elements when the queue is full rather than blocking.
- It returns `-1` when the queue is empty rather than waiting.
- Multiple threads can concurrently observe or modify the queue without synchronization.
- `ArrayDeque` is not thread-safe.

Interview lesson: thread safety is not simply about choosing a queue data structure. You must coordinate both the state transitions and the waiting behavior.

## 4. Solution 2 — Optimal interview solution using `synchronized` and `wait()`

This is my recommended first solution in an interview because it directly expresses the queue's rules.

```
import java.util.ArrayDeque;
import java.util.Deque;

class BoundedBlockingQueue {
    private final int capacity;
    private final Deque<Integer> queue;

    public BoundedBlockingQueue(int capacity) {
        // Store the maximum number of elements the queue may contain.
        this.capacity = capacity;
        this.queue = new ArrayDeque<>(capacity);
    }

    public synchronized void enqueue(int element)
            throws InterruptedException {

        // WHY while?
        // The queue might still be full after this thread wakes up:
        // another producer may have inserted first, or this may be
        // a spurious wakeup. Always recheck the actual condition.
        while (queue.size() == capacity) {
            // wait() releases this object's monitor while blocking.
            // That allows a consumer to enter dequeue(), remove an
            // element, and notify waiting producers.
            wait();
        }

        // We own the monitor and know there is space.
        // offerLast() inserts at the tail, preserving FIFO order.
        queue.offerLast(element);

        // A consumer may be waiting because the queue was empty.
        // Wake waiting threads so they can recheck their conditions.
        // notifyAll() is used because both producers and consumers
        // wait on this same monitor; notify() could wake the wrong kind.
        notifyAll();
    }

    public synchronized int dequeue() throws InterruptedException {
        // WHY while?
        // The queue may be empty again when this thread reacquires
        // the monitor, even if it was non-empty when notified.
        while (queue.isEmpty()) {
            // Release the monitor and wait for a producer to enqueue.
            wait();
        }

        // Remove the oldest element from the head.
        int element = queue.removeFirst();

        // Removing an element creates capacity.
        // Wake waiting producers so they can recheck whether space exists.
        notifyAll();

        return element;
    }

    public synchronized int size() {
        // The monitor guarantees a consistent snapshot of the size.
        return queue.size();
    }
}
```

### Walk through a concrete example

Let `capacity = 2`.

| Step | Action           | Queue      | Result                 |
| ---- | ---------------- | ---------- | ---------------------- |
| 1    | `enqueue(10)`    | `[10]`     | Completes              |
| 2    | `enqueue(20)`    | `[10, 20]` | Completes              |
| 3    | `enqueue(30)`    | `[10, 20]` | Producer waits         |
| 4    | `dequeue()`      | `[20]`     | Returns `10`; notifies |
| 5    | Producer resumes | `[20, 30]` | Adds `30`              |
| 6    | `dequeue()`      | `[30]`     | Returns `20`           |

Notice that the waiting producer does not need to poll the queue repeatedly. `wait()` suspends it until a notification or spurious wakeup, avoiding wasteful busy-waiting.

### Why `notifyAll()` instead of `notify()`?

All threads wait on the same monitor, but they may be waiting for different conditions:

- Producers wait for `queue.size() < capacity`.
- Consumers wait for `!queue.isEmpty()`.

Suppose the queue is full and multiple producers are waiting. A consumer removes an element and calls `notify()`. The JVM could wake another consumer instead of a producer. That consumer sees a non-empty queue, removes an element, and proceeds; the producer remains asleep despite space being available.

The system may still make progress later, but `notify()` can create avoidable delays and complicate liveness reasoning. With `notifyAll()`, all waiting threads get a chance to recheck their conditions. Threads whose conditions remain false simply wait again.

This implementation is straightforward and correct, although waking every waiter can add overhead when there are many threads.

### Complexity analysis

- `enqueue`: \\(O(1)\\) for the queue insertion, excluding time spent waiting and lock contention.
- `dequeue`: \\(O(1)\\) for the queue removal, excluding time spent waiting and lock contention.
- `size`: \\(O(1)\\).
- Space: \\(O(C)\\), where \\(C\\) is the configured capacity.

`notifyAll()` can wake \\(O(T)\\) waiting threads, where \\(T\\) is the number of waiters. Therefore, the total synchronization overhead is not strictly constant in the number of threads, even though the queue operation itself is \\(O(1)\\).

## 5. Solution 3 — Semaphores (an alternative optimal approach)

The second optimal approach is to use semaphores to track resources.

The mental model is different:

- `availableSlots` counts how many more elements can be inserted.
- `availableItems` counts how many elements can be removed.
- A mutex protects the actual queue because a semaphore alone does not make `ArrayDeque` thread-safe.

Initially, if capacity is `3`:

```
availableSlots = 3
availableItems = 0
queue          = []
```

After `enqueue(10)`:

```
availableSlots = 2
availableItems = 1
queue          = [10]
```

After `dequeue()`:

```
availableSlots = 3
availableItems = 0
queue          = []
```

A semaphore's `acquire()` blocks if no permit is available. `release()` adds a permit and can allow a waiting thread to proceed.

```
import java.util.ArrayDeque;
import java.util.Deque;
import java.util.concurrent.Semaphore;
import java.util.concurrent.locks.ReentrantLock;

class BoundedBlockingQueue {
    private final Deque<Integer> queue = new ArrayDeque<>();

    // One permit represents one empty slot.
    // Initially, all capacity slots are available.
    private final Semaphore availableSlots;

    // One permit represents one queued element.
    // Initially, there are no elements to consume.
    private final Semaphore availableItems = new Semaphore(0);

    // Semaphores count permissions, but do not serialize operations
    // on ArrayDeque. The mutex protects the queue itself.
    private final ReentrantLock mutex = new ReentrantLock();

    public BoundedBlockingQueue(int capacity) {
        availableSlots = new Semaphore(capacity);
    }

    public void enqueue(int element) throws InterruptedException {
        // Wait until a free slot exists. If the queue is full,
        // acquire() blocks without occupying the queue mutex.
        availableSlots.acquire();

        // Multiple producers may own different slot permits at once,
        // so serialize their actual modifications to ArrayDeque.
        mutex.lock();
        try {
            queue.offerLast(element);
        } finally {
            // Always unlock, even if an unexpected exception occurs.
            mutex.unlock();
        }

        // Publish one additional consumable item.
        // Do this after insertion, so a consumer cannot consume
        // a permit for an element that has not yet been inserted.
        availableItems.release();
    }

    public int dequeue() throws InterruptedException {
        // Wait until an element exists. If the queue is empty,
        // acquire() blocks without occupying the queue mutex.
        availableItems.acquire();

        mutex.lock();
        try {
            // The acquired item permit guarantees an element is
            // available for this consumer, barring invariant violations.
            return queue.removeFirst();
        } finally {
            mutex.unlock();

            // A removed element frees one capacity slot.
            // Release a slot permit even as the method returns.
            availableSlots.release();
        }
    }

    public int size() {
        mutex.lock();
        try {
            // Read the queue size under the same mutex used by
            // enqueue/dequeue, providing a consistent snapshot.
            return queue.size();
        } finally {
            mutex.unlock();
        }
    }
}
```

### Why do we need all three synchronization mechanisms?

| Mechanism        | Responsibility                                           |
| ---------------- | -------------------------------------------------------- |
| `availableSlots` | Blocks producers when the queue has no free slots        |
| `availableItems` | Blocks consumers when there are no elements              |
| `mutex`          | Prevents concurrent modification of the underlying queue |

One subtle detail: the semaphores represent available resources, while the mutex protects the data structure. They solve related but distinct problems.

### Complexity

- `enqueue`: \\(O(1)\\) queue insertion, plus semaphore and lock overhead.
- `dequeue`: \\(O(1)\\) queue removal, plus semaphore and lock overhead.
- `size`: \\(O(1)\\).
- Space: \\(O(C)\\) for the queue, plus constant synchronization state.

These complexity bounds exclude waiting time, which depends on other threads' progress.

Interview recommendation: Start with the `synchronized` solution. It is easier to explain and reason about. Introduce semaphores when the interviewer asks for a resource-counting approach or wants to explore producer-consumer synchronization more deeply.

## 6. Edge cases to watch out for

| Edge case                  | Expected behavior                                        |
| -------------------------- | -------------------------------------------------------- |
| Capacity is `1`            | Only one element may be stored at a time                 |
| Enqueue on a full queue    | Producer blocks until space becomes available            |
| Dequeue on an empty queue  | Consumer blocks until an element is available            |
| Multiple producers         | No element is inserted beyond capacity                   |
| Multiple consumers         | No element is removed more than once                     |
| Spurious wakeup            | The thread rechecks its condition in a `while` loop      |
| Concurrent `size()`        | Returns a consistent snapshot                            |
| Element value is `0`       | It is a valid element, not an empty-queue marker         |
| Interrupted waiting thread | Interruption is handled according to the method contract |

A useful concurrency invariant is:

\\[ 0 \leq \text{queue.size()} \leq \text{capacity} \\]

For the semaphore implementation, another invariant is:

\\[ \text{availableSlots} + \text{queue.size()} = C \\]

and

\\[ \text{availableItems} = \text{queue.size()} \\]

These semaphore relationships hold when operations are observed after their respective enqueue/dequeue transitions have completed. During an operation, a permit can temporarily be acquired before the corresponding queue mutation or released afterward.

## 7. Interviewer follow-up questions and answers

Q1. Why can't we just use `synchronized` without `wait()`?

A synchronized method prevents concurrent execution, but it does not automatically wait for a queue to become non-full or non-empty. Without `wait()`, we'd have to return an error or repeatedly check the condition.

Q2. Does `wait()` release the lock?

Yes. `wait()` releases the object's monitor while the thread waits, allowing other threads to enter synchronized methods. When the thread wakes, it must reacquire that monitor before continuing.

Q3. Why not use `Thread.sleep()` in a loop?

That approach is polling or busy-waiting with delays. It wastes CPU time, introduces arbitrary latency, and does not provide the synchronization guarantees needed to safely access the queue.

Q4. Why use `ArrayDeque` rather than `LinkedList`?

Both support FIFO operations. `ArrayDeque` generally offers lower memory overhead and efficient operations at both ends. Because we only insert at the tail and remove from the head, we don't need indexed access.

Q5. Can we replace this implementation with Java's `ArrayBlockingQueue`?

In production, yes. `ArrayBlockingQueue` already provides a thread-safe bounded FIFO queue with blocking `put()` and `take()` methods. The LeetCode problem explicitly asks us to implement the behavior ourselves.

Q6. Is `notifyAll()` always better than `notify()`?

Not always. If producers and consumers have separate condition variables, signaling one appropriate waiter is often more efficient. With one shared monitor and two different wait conditions, `notifyAll()` is the simpler, safer choice.

Q7. Is the solution fair?

Not necessarily. Java monitor scheduling does not guarantee that the longest-waiting thread proceeds first. The semaphore solution also does not guarantee fairness unless fair semaphores are explicitly configured. Fairness can reduce starvation risk but may reduce throughput.

Q8. How would you improve the production design?

Use `ArrayBlockingQueue` or `LinkedBlockingQueue` unless custom behavior is necessary. These existing implementations handle coordination, blocking, interruption, and concurrency edge cases that are easy to get wrong in custom code.

## 8. Final interview thought process

When you see a problem involving producers, consumers, bounded capacity, and blocking operations, follow this reasoning:

1. Identify the shared state: a FIFO queue and its capacity.
2. Identify the conditions that prevent progress: full for producers, empty for consumers.
3. Protect the shared state with a common synchronization mechanism.
4. Make threads wait when their conditions are false.
5. Signal waiting threads after state changes.
6. Recheck conditions after waking up.
7. Verify that the capacity invariant and FIFO order always hold.

That thought process is more important than memorizing the implementation. It generalizes to worker pools, task buffers, pipelines, message queues, and many other producer-consumer systems.
