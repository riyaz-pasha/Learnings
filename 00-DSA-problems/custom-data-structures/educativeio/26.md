# 588. Design In-Memory File System — Java 24

The key to solving this problem in an interview is to recognize that we are implementing a miniature file system, not simply storing strings in a map.

We need to represent directories, files, their relationships, file contents, and the rules governing operations such as listing, creating directories, and appending to files.

## 0. Understand the problem in simple terms

Imagine a computer with an initially empty file system containing only the root directory `/`.

We need to implement these four operations:

| Operation                             | What it does                                               | Example                   |
| ------------------------------------- | ---------------------------------------------------------- | ------------------------- |
| `ls(path)`                            | Lists a file's name or the sorted names inside a directory | `ls("/a")` → `["b", "c"]` |
| `mkdir(path)`                         | Creates a directory and any missing parent directories     | `mkdir("/a/b/c")`         |
| `addContentToFile(filePath, content)` | Creates a file if needed, then appends content             | Add `"hello"` to `/a.txt` |
| `readContentFromFile(filePath)`       | Returns the entire file content                            | `/a.txt` → `"hello"`      |

There are some important rules:

- The root directory `/` always exists.
- Directory listings must be returned in lexicographical order.
- Listing a file returns a list containing only its filename, not its contents.
- Adding content to a file appends to existing content rather than replacing it.
- Paths may contain multiple nested directories.
- `mkdir` must create missing intermediate directories.

For example, suppose we execute:

```
mkdir("/company/engineering/backend")
addContentToFile("/company/engineering/backend/notes.txt", "Hello")
addContentToFile("/company/engineering/backend/notes.txt", " World")

ls("/")
ls("/company/engineering/backend")
readContentFromFile("/company/engineering/backend/notes.txt")
```

Expected results:

```
ls("/")                                      -> ["company"]
ls("/company/engineering/backend")           -> ["notes.txt"]
readContentFromFile("/company/engineering/backend/notes.txt")
                                               -> "Hello World"
```

Notice that `mkdir` created all the missing directories, and the second write appended to the first.

## 1. Clarifying questions to ask the interviewer

The problem statement already defines most of the rules, so we should avoid asking questions whose answers are explicitly given. Instead, we can confirm the assumptions that affect our implementation.

1. Can a path refer to either a file or a directory? Why: `ls()` behaves differently depending on the target type.
2. Should `mkdir()` create all missing intermediate directories? Why: This determines whether we create only the final node or traverse the entire path while creating missing nodes. The problem confirms that intermediate directories must be created.
3. Should repeated writes append or overwrite? Why: This determines how file content is stored. The required behavior is append.
4. Must directory listings be sorted? Why: An ordinary hash map does not guarantee lexicographical iteration order. The answer is yes.
5. Can we assume paths and operations are valid? Why: This tells us whether we need error handling for nonexistent files, invalid paths, or attempts to treat a file as a directory. LeetCode explicitly permits these assumptions.

In an interview, after confirming these constraints, move directly to the data structure.

## 2. Core idea: Model the file system as a tree

Think of every directory as a container that can hold more directories and files.

A file holds content, while a directory holds named child nodes.

For example, after:

```
mkdir("/a/b");
addContentToFile("/a/b/x.txt", "hello");
```

the structure looks like this:

```
root "/"
└── a/                     Directory
    └── b/                 Directory
        └── x.txt          File: "hello"
```

This immediately suggests a tree, because every path component leads from a parent to a child.

### Why a tree instead of one big map?

We could store everything in a flat map:

```
"/a"       -> directory
"/a/b"     -> directory
"/a/b/x.txt" -> "hello"
```

This works for direct lookups, but listing `/a/b` requires finding every key with the correct prefix, extracting immediate children, and sorting them. Prefix matching also risks confusing direct children with deeper descendants.

A tree stores each directory's direct children together. Therefore, listing a directory requires inspecting only that directory's children.

### The optimal node design

We have two reasonable designs:

- Separate `Directory` and `File` classes.
- One unified `Node` class that represents either a directory or a file.

For this problem, I recommend the unified node because it simplifies path traversal and keeps the implementation compact.

Each node stores:

- `isFile`: distinguishes files from directories.
- `children`: maps a child name to its node.
- `content`: stores the file's content.

A directory has children; a file has content.

```
Node
├── isFile
├── children: Map<String, Node>
└── content: StringBuilder
```

We use a `HashMap` for children and sort names when `ls()` is called. This makes creating and looking up children efficient without maintaining sorted order after every insertion.

## 3. How to think about path traversal

Consider this path:

```
/a/b/c
```

Splitting on `/` gives:

```
["", "a", "b", "c"]
```

The first element is empty because the path begins with `/`. We can simply ignore it.

Then we traverse:

```
root -> a -> b -> c
```

The important interview insight is that every operation is either traversal, traversal plus creation, or traversal plus a local action.

| Operation                         | Traversal strategy                           |
| --------------------------------- | -------------------------------------------- |
| `ls(path)`                        | Traverse to the existing target              |
| `mkdir(path)`                     | Traverse and create missing directory nodes  |
| `addContentToFile(path, content)` | Traverse to the file, creating it if missing |
| `readContentFromFile(path)`       | Traverse to the existing file                |

Let's examine the tricky part: `ls()`.

If the path is `/a/b`, we traverse to node `b`. If it is a directory, we return the names of its children sorted alphabetically.

If the path is `/a/b/x.txt`, we traverse to the file node. Instead of listing its children, we return just `["x.txt"]`.

The path's target type changes the behavior, so our node must remember whether it is a file.

## 4. All approaches: brute force to optimal

### Approach 1: Flat map of complete paths

Store complete paths in a map:

```
Map<String, String> files;
Set<String> directories;
```

For example:

```
directories = ["/", "/a", "/a/b"]
files       = {"/a/b/x.txt" -> "hello"}
```

Why is this not optimal?

- Looking up a file by its full path is efficient.
- Creating nested directories requires tracking parent paths.
- Listing a directory requires scanning stored paths to identify its direct children.
- Prefix matching must distinguish `/a/b` from `/a/bc`.

If there are \\(N\\) stored paths and the target path has length \\(L\\), a straightforward implementation can take \\(O(NL)\\) time for a directory listing because each path may need to be examined and compared.

This approach is reasonable as a baseline but makes hierarchical operations awkward.

### Approach 2: Tree with a `HashMap` — recommended

Each directory has a map of child names to nodes. We traverse one path component at a time and create nodes when needed.

For `ls()`, we sort the child names before returning them.

Advantages:

- Natural representation of directories and files.
- Efficient path traversal.
- Simple implementation.
- No repeated scanning of unrelated paths.

This is the solution I recommend for the interview.

### Approach 3: Tree with a `TreeMap`

Replace the child `HashMap` with a `TreeMap`.

```
Map<String, Node> children = new TreeMap<>();
```

Now children remain sorted automatically, so `ls()` does not need to sort them on every call.

The trade-off is that insertion and lookup take \\(O(\log C)\\), where \\(C\\) is the number of children, rather than expected \\(O(1)\\) with a hash map.

Use this when sorted directory listings are frequent enough that maintaining order continuously is worthwhile.

## 5. Optimal Java 24 implementation

The following implementation uses a single node type, a `HashMap` for child lookup, and `StringBuilder` for efficient file-content appends.

Every important design choice, reasoning step, and complexity analysis is explained in the code comments.

```
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

class FileSystem {

    /*
     * Each node represents exactly one filesystem entry:
     * either a directory or a file.
     *
     * Directory node:
     *   - isFile == false
     *   - children contains its immediate entries
     *
     * File node:
     *   - isFile == true
     *   - content contains its data
     *
     * Why use a unified Node?
     * Both files and directories are reached by following the same
     * path-traversal logic. A boolean distinguishes their behavior,
     * avoiding duplicated traversal code across two separate classes.
     *
     * Why use HashMap for children?
     * We need efficient lookup by a child name. Expected O(1) lookup
     * and insertion are appropriate here. Sorting is performed only
     * when ls() actually needs an ordered result.
     */
    private static final class Node {

        private boolean isFile = false;

        private final Map<String, Node> children = new HashMap<>();

        /*
         * StringBuilder is preferable to repeated immutable String
         * concatenation because addContentToFile() may append many
         * chunks. StringBuilder avoids creating a new String for every
         * append, although growing its internal buffer can occasionally
         * require copying existing characters.
         */
        private final StringBuilder content = new StringBuilder();
    }

    /*
     * The root always exists and represents "/".
     *
     * Every other node is reachable by following child-name mappings
     * from this root. This is the central tree invariant.
     */
    private final Node root = new Node();

    /*
     * Resolve an absolute path to its corresponding node.
     *
     * Example:
     *   "/a/b/c" -> root -> a -> b -> c
     *
     * The leading slash creates an empty component when split using
     * "/". split("/") also discards trailing empty components by
     * default, which is compatible with the problem's path constraints.
     *
     * We skip the leading empty component and follow the remaining names.
     *
     * Preconditions:
     * The requested path exists, and the path is valid, as guaranteed
     * by the problem.
     *
     * Let L be the path length and D its number of components.
     *
     * Time: O(L) expected, because every component is looked up once.
     * Auxiliary space: O(D) for the split array.
     */
    private Node resolve(String path) {
        Node current = root;

        for (String component : path.split("/")) {
            if (component.isEmpty()) {
                continue;
            }

            current = current.children.get(component);
        }

        return current;
    }

    /*
     * Return the final component of a non-root absolute path.
     *
     * Examples:
     *   "/a/b/file.txt" -> "file.txt"
     *   "/a"            -> "a"
     *
     * This helper is used only when ls() targets a file. We cannot
     * return the file's children because files are not directories.
     *
     * Time: O(L) for substring extraction in the worst case.
     * Auxiliary space: O(L) for the resulting String.
     */
    private String fileName(String path) {
        return path.substring(path.lastIndexOf('/') + 1);
    }

    /*
     * List the requested path.
     *
     * Case 1: The target is a file.
     * Return only its own name, e.g. ls("/a/x.txt") -> ["x.txt"].
     *
     * Case 2: The target is a directory.
     * Return its immediate child names, sorted lexicographically.
     *
     * We sort a new list rather than sorting the underlying HashMap:
     * the map has no meaningful iteration order, and the contract
     * requires the returned list to be sorted.
     *
     * Let:
     *   L = path length
     *   C = number of immediate children in the target directory
     *
     * Time:
     *   O(L + C log C) expected.
     *   O(L) resolves the path; O(C) collects names; O(C log C)
     *   sorts them.
     *
     * Auxiliary space: O(L + C), including path parsing and output.
     */
    public List<String> ls(String path) {
        Node target = resolve(path);

        if (target.isFile) {
            return List.of(fileName(path));
        }

        List<String> names = new ArrayList<>(target.children.keySet());
        names.sort(String::compareTo);

        return names;
    }

    /*
     * Create the requested directory and any missing ancestors.
     *
     * Example:
     *   mkdir("/a/b/c")
     *
     * If only "/" exists, this creates a, then b, then c.
     * If a or b already exists, we reuse the existing node.
     *
     * Why computeIfAbsent?
     * It combines "look up the child; create it if missing" into
     * one clear operation. Existing nodes are never replaced.
     *
     * Each newly created node defaults to isFile == false, so it
     * represents a directory.
     *
     * Let D be the number of path components and L the path length.
     *
     * Time: O(L) expected, including path parsing and traversal.
     * Auxiliary space: O(D) for parsing, plus O(D) new nodes in
     * the worst case when the entire directory chain is missing.
     */
    public void mkdir(String path) {
        Node current = root;

        for (String component : path.split("/")) {
            if (component.isEmpty()) {
                continue;
            }

            current = current.children.computeIfAbsent(
                component,
                ignored -> new Node()
            );
        }
    }

    /*
     * Create a file if needed and append the supplied content.
     *
     * The problem guarantees that the parent directory exists.
     * Therefore, we resolve the parent and handle only the final
     * component as a file.
     *
     * Example:
     *   addContentToFile("/a/x.txt", "hello")
     *   addContentToFile("/a/x.txt", " world")
     *
     * The final content becomes "hello world", not " world".
     *
     * Why mark isFile explicitly?
     * A newly created Node defaults to a directory. Setting this flag
     * distinguishes the file from a directory with the same node shape.
     *
     * Why not use String concatenation?
     * Repeated immutable concatenation can copy all existing content
     * on every write. StringBuilder is designed for mutable appends.
     *
     * Let:
     *   L = file path length
     *   A = number of characters appended in this call
     *
     * Time: O(L + A) amortized, including traversal and append.
     * Auxiliary space: O(L) for path parsing, plus O(A) additional
     * content capacity amortized; a buffer resize may temporarily
     * require copying existing file content.
     */
    public void addContentToFile(String filePath, String content) {
        int lastSlash = filePath.lastIndexOf('/');

        String parentPath = filePath.substring(0, lastSlash);
        String name = filePath.substring(lastSlash + 1);

        /*
         * For a root-level file such as "/notes.txt", parentPath
         * is the empty string. Resolve the root explicitly.
         */
        Node parent = parentPath.isEmpty()
            ? root
            : resolve(parentPath);

        /*
         * Reuse the file node if it already exists; otherwise create it.
         */
        Node file = parent.children.computeIfAbsent(
            name,
            ignored -> new Node()
        );

        file.isFile = true;
        file.content.append(content);
    }

    /*
     * Return the complete content of an existing file.
     *
     * resolve() navigates to the file node, and StringBuilder.toString()
     * creates the immutable String required by the method signature.
     *
     * Let:
     *   L = file path length
     *   S = total number of characters stored in the file
     *
     * Time: O(L + S), because converting the builder to a String
     * requires copying its characters.
     * Auxiliary space: O(L + S), including path parsing and the
     * returned String.
     */
    public String readContentFromFile(String filePath) {
        return resolve(filePath).content.toString();
    }
}
```

### Why this implementation is clean

- `resolve()` centralizes existing-path traversal.
- `Node` encapsulates the state of each filesystem entry.
- `mkdir()` and file creation reuse existing nodes rather than overwriting them.
- `StringBuilder` avoids repeatedly rebuilding the entire file string on each append.
- `ls()` handles files and directories separately.
- The root is a permanent node, so `/` requires no special tree structure.

One assumption worth noting: the LeetCode constraints guarantee valid operations and that a file's parent exists. This implementation follows those constraints rather than adding extra validation for invalid paths.

## 6. Edge cases to test

| Scenario                  | Expected behavior                                                     |
| ------------------------- | --------------------------------------------------------------------- |
| Empty root                | `ls("/")` returns `[]`                                                |
| Nested directory creation | `mkdir("/a/b/c")` creates all missing ancestors                       |
| File listing              | `ls("/a/x.txt")` returns `["x.txt"]`                                  |
| Repeated writes           | `"hello"` then `" world"` returns `"hello world"`                     |
| Alphabetical listing      | Creating `z` before `a` still returns `["a", "z"]`                    |
| Root-level file           | `addContentToFile("/x.txt", "data")` works                            |
| Existing directory        | Calling `mkdir()` on an existing directory leaves its contents intact |
| Mixed children            | Files and directories appear together in sorted order                 |

A particularly useful test is:

```
FileSystem fs = new FileSystem();

fs.mkdir("/docs/java");
fs.addContentToFile("/docs/java/notes.txt", "Java");
fs.addContentToFile("/docs/java/notes.txt", " 24");

assert fs.ls("/").equals(List.of("docs"));
assert fs.ls("/docs/java").equals(List.of("notes.txt"));
assert fs.ls("/docs/java/notes.txt").equals(List.of("notes.txt"));
assert fs.readContentFromFile("/docs/java/notes.txt")
         .equals("Java 24");
```

Remember that Java assertions are disabled by default unless enabled with `-ea`. For a quick standalone test, ordinary `if` statements or a unit-test framework are also suitable.

## 7. Follow-up interview questions and answers

Q1. Why use a trie-like tree instead of a flat map?

A tree naturally models parent-child relationships. Listing a directory examines only its direct children rather than scanning all stored paths.

Q2. Why use `HashMap` rather than `TreeMap`?

A `HashMap` gives expected constant-time child lookup and insertion. We pay the sorting cost only during `ls()`. A `TreeMap` is a valid alternative when sorted iteration is needed frequently.

Q3. Can we optimize directory listing further?

Yes. Using `TreeMap` for every directory maintains sorted children continuously. Then listing a directory takes \\(O(C)\\) to collect the names after traversal, instead of \\(O(C \log C)\\) to sort them. The trade-off is \\(O(\log C)\\) child lookup and insertion.

Q4. Why use `StringBuilder` instead of `String`?

Repeated immutable string concatenation can repeatedly copy existing file content. `StringBuilder` makes appending amortized efficient, though reading still requires producing a `String`.

Q5. What is the total space complexity?

Let \\(V\\) be the number of filesystem nodes, \\(P\\) the total number of characters in stored path components, and \\(S\\) the total number of file-content characters.

The tree uses \\(O(V + P + S)\\) space, with map entries and node objects contributing to the structural overhead. Temporary path arrays and `ls()` output use additional space during operations.

Q6. How would you support deleting or moving files?

Add operations that resolve the parent directory and final name. Deletion removes the relevant child mapping. Moving requires validating the destination and updating the appropriate parent-child mappings; moving a directory into its own descendant must be rejected to prevent cycles.

Q7. What changes would be required for a production filesystem?

A real system would need decisions about permissions, concurrent access, persistence, path normalization, symbolic links, failure recovery, and potentially very large files. The LeetCode implementation deliberately excludes these concerns.

Q8. What is the central invariant of this solution?

Every path component maps to exactly one child node under its parent, and every node is reachable from the root. A file node stores content; a directory node stores child entries. Preserving this invariant makes all four operations straightforward.
