# 729. My Calendar I — Interval / Sweep Line / Binary Search / TreeMap

The most important thing to understand about this problem is:

We are not trying to merge overlapping intervals. We are trying to maintain a collection of non-overlapping intervals and reject any new interval that conflicts with an existing one.

There are multiple ways to solve this problem:

1. Brute force using a list.
2. Sorting-based approach (not ideal because insertion requires maintaining order).
3. Binary Search using a sorted list.
4. `TreeMap` using a balanced BST — optimal for larger numbers of bookings.

Since the constraint allows at most 1000 calls, even brute force is sufficient. However, let's understand the approaches and their trade-offs.

## 0. Simplify the problem

Suppose our calendar currently contains:

```
[10, 20)
[25, 35)
[40, 50)
```

Now someone wants to book:

```
[15, 30)
```

Should we accept it?

No, because it overlaps with both `[10, 20)` and `[25, 35)`.

Now consider:

```
[20, 25)
```

Should we accept it?

Yes!

Why?

Because intervals are half-open:

```
[10, 20) means 10 <= time < 20
[20, 25) means 20 <= time < 25
```

The first event does not include time `20`, so the two events do not overlap.

### The most important formula

Two intervals:

```
A = [start1, end1)
B = [start2, end2)
```

Overlap if and only if:

```
start1 < end2 && start2 < end1
```

They do NOT overlap if:

```
end1 <= start2 || end2 <= start1
```

Memorize this condition. It is fundamental to interval problems.

## 1. Clarifying questions to ask the interviewer

Before implementing, clarify:

Q1. Are intervals half-open or closed?

Why?

Because `[10, 20)` and `[20, 30)` do not overlap, whereas closed intervals `[10, 20]` and `[20, 30]` do overlap at `20`.

Here, the problem explicitly specifies half-open intervals.

Q2. Can we modify previously accepted bookings?

Why?

This determines whether we need to support deletion or modification operations.

Here, we only support booking. Existing events never change.

Q3. What is the maximum number of booking calls?

Why?

It determines whether a linear scan is sufficient or whether we should use an ordered data structure.

Here, at most 1000 calls are made, so brute force is perfectly acceptable.

Q4. Can startTime or endTime be negative?

Why?

It determines whether special handling is necessary for coordinate boundaries.

Here, `0 <= start < end <= 10^9`.

# 2. Core intuition: Why checking only neighboring intervals works

This is the most important observation behind the optimal solution.

Imagine that all accepted bookings are sorted by their start times.

```
[10, 20)
[25, 35)
[40, 50)
[60, 70)
```

Suppose we want to insert:

```
[22, 28)
```

We only need to inspect its neighboring intervals:

```
Previous: [10, 20)
New:      [22, 28)
Next:     [25, 35)
```

The previous interval is fine:

```
20 <= 22
```

But the next interval overlaps:

```
28 > 25
```

Therefore, reject the booking.

### Why don't we need to check every interval?

Because all existing intervals are already non-overlapping.

Let's say we want to insert a new interval `[S, E)`.

Find the interval with the greatest start time that is less than or equal to `S`.

Call it `previous`.

Also find the interval with the smallest start time greater than `S`.

Call it `next`.

The new interval is valid if:

```
previous.end <= S
```

AND

```
E <= next.start
```

Why is this sufficient?

- Every interval before `previous` ends before `previous` starts.
- Since `previous` ends before or at `S`, all earlier intervals also end before or at `S`.
- Every interval after `next` starts after `next` starts.
- Since `E` is before or equal to `next.start`, all later intervals are also safe.

Therefore, checking only the immediate neighbors is sufficient.

This is the mental model to remember:

Maintain sorted, non-overlapping intervals. To insert a new interval, check only its predecessor and successor.

# 3. Solution 1: Brute Force — Linear Scan

The simplest solution is to store all accepted intervals in a list.

For every new booking:

1. Iterate over all existing bookings.
2. Check whether the new interval overlaps any existing interval.
3. If an overlap exists, return `false`.
4. Otherwise, add the interval and return `true`.

### Java 24 code

```java
import java.util.ArrayList;
import java.util.List;

class MyCalendar {

    // Represents one accepted calendar booking.
    // Records provide immutable data carriers in modern Java.
    private record Interval(int start, int end) {}

    // Stores all successfully accepted bookings.
    private final List<Interval> bookings;

    public MyCalendar() {
        bookings = new ArrayList<>();
    }

    public boolean book(int startTime, int endTime) {

        /*
         * STEP 1: Check the new interval against every existing interval.
         *
         * WHY?
         * A booking is valid only if it does not overlap with ANY
         * previously accepted booking.
         *
         * Existing intervals are not necessarily sorted, so we simply
         * inspect every booking.
         */
        for (Interval current : bookings) {

            /*
             * Two half-open intervals [a, b) and [c, d) overlap when:
             *
             * a < d AND c < b
             *
             * Equivalent non-overlapping condition:
             *
             * b <= c OR d <= a
             *
             * Here:
             * current.end <= startTime
             *     means existing booking finishes before new booking starts.
             *
             * endTime <= current.start
             *     means new booking finishes before existing booking starts.
             *
             * If neither condition is true, the intervals overlap.
             */
            boolean doesNotOverlap =
                    current.end() <= startTime ||
                    endTime <= current.start();

            if (!doesNotOverlap) {
                /*
                 * At least one existing booking conflicts with the new one.
                 *
                 * IMPORTANT:
                 * We return immediately without adding the new booking.
                 */
                return false;
            }
        }

        /*
         * STEP 2: No existing booking overlaps.
         *
         * Therefore, the new booking is safe to accept.
         */
        bookings.add(new Interval(startTime, endTime));

        return true;
    }
}
```

### Complexity analysis

Let `N` be the number of accepted bookings.

| Operation   | Complexity |
| ----------- | ---------- |
| Constructor | O(1)       |
| One booking | O(N)       |
| Space       | O(N)       |

For `N` booking calls, total worst-case time is:

\\[ O(N^2) \\]

Advantages:

- Extremely simple.
- Easy to implement and explain.
- Perfectly sufficient for 1000 calls.

Disadvantage:

\- Every new booking may need to inspect all existing bookings.

# 4. Solution 2: Binary Search using a Sorted ArrayList

We can improve the search for conflicting intervals by maintaining bookings sorted by their start times.

Instead of checking every interval, use binary search to find where the new interval belongs.

Remember our key observation:

Only the predecessor and successor need to be checked.

### Example

Existing bookings:

```
Index:    0         1         2
       [10,20)   [30,40)   [50,60)
```

New booking:

```
[25, 35)
```

Binary search tells us that the new interval belongs at index `1`.

Therefore:

```
Previous = [10,20)
Next     = [30,40)
```

Check:

```
Previous.end <= new.start
20 <= 25  => true

New.end <= Next.start
35 <= 30  => false
```

Reject.

### Java 24 code

```java
import java.util.ArrayList;
import java.util.List;

class MyCalendar {

    private record Interval(int start, int end) {}

    // Always maintained in ascending order of start time.
    private final List<Interval> bookings;

    public MyCalendar() {
        bookings = new ArrayList<>();
    }

    public boolean book(int startTime, int endTime) {

        /*
         * STEP 1: Find the insertion position using binary search.
         *
         * We want the first index whose interval.start >= startTime.
         *
         * This is called lower bound.
         *
         * At the end:
         * - left is the insertion position.
         * - left - 1 is the predecessor, if it exists.
         * - left is the successor, if it exists.
         */
        int left = 0;
        int right = bookings.size();

        while (left < right) {

            int mid = left + (right - left) / 2;

            if (bookings.get(mid).start() < startTime) {
                /*
                 * Current interval starts before the new interval.
                 *
                 * Therefore, the insertion position must be to the right.
                 */
                left = mid + 1;
            } else {
                /*
                 * Current interval starts at or after the new interval.
                 *
                 * It could be the insertion position.
                 * Continue searching on the left.
                 */
                right = mid;
            }
        }

        // First index whose start >= startTime.
        int insertionIndex = left;

        /*
         * STEP 2: Check the predecessor.
         *
         * The predecessor is the interval immediately before the
         * insertion position.
         *
         * It must finish before or exactly when our new booking starts.
         */
        if (insertionIndex > 0) {

            Interval previous = bookings.get(insertionIndex - 1);

            if (previous.end() > startTime) {
                /*
                 * Previous interval extends into our new interval.
                 *
                 * Overlap exists, so reject.
                 */
                return false;
            }
        }

        /*
         * STEP 3: Check the successor.
         *
         * The successor is the interval immediately after the
         * insertion position.
         *
         * Our new booking must finish before or exactly when
         * the successor starts.
         */
        if (insertionIndex < bookings.size()) {

            Interval next = bookings.get(insertionIndex);

            if (endTime > next.start()) {
                /*
                 * Our new interval extends into the next booking.
                 *
                 * Overlap exists, so reject.
                 */
                return false;
            }
        }

        /*
         * STEP 4: Both neighbors are safe.
         *
         * Insert at the correct sorted position.
         *
         * ArrayList insertion shifts subsequent elements to the right.
         * This operation takes O(N) time in the worst case.
         */
        bookings.add(
                insertionIndex,
                new Interval(startTime, endTime)
        );

        return true;
    }
}
```

### Complexity analysis

| Operation           | Complexity |
| ------------------- | ---------- |
| Binary search       | O(log N)   |
| Check predecessor   | O(1)       |
| Check successor     | O(1)       |
| ArrayList insertion | O(N)       |
| Space               | O(N)       |

Overall booking complexity:

\\[ O(N) \\]

Important interviewer observation:

Although binary search takes `O(log N)`, the overall operation is still `O(N)` because inserting into an `ArrayList` requires shifting elements.

This is a common interview trap.

# 5. Solution 3: Optimal — TreeMap (Balanced Binary Search Tree)

This is the approach I would recommend when discussing an efficient ordered-data-structure solution.

Java's `TreeMap` internally uses a Red-Black Tree.

It maintains keys in sorted order and supports:

- `floorEntry(key)` — greatest key less than or equal to the given key.
- `ceilingEntry(key)` — smallest key greater than or equal to the given key.

These two operations are exactly what we need!

## Understanding the mental model

We store bookings like this:

```
TreeMap<Integer, Integer> calendar;
```

Where:

```
Key   = startTime
Value = endTime
```

Example:

```
TreeMap:

10 -> 20
30 -> 40
50 -> 60
```

This represents:

```
[10,20)
[30,40)
[50,60)
```

Now suppose we want to book:

```
[25, 35)
```

We perform two operations.

1\. Find the previous booking

```
calendar.floorEntry(25);
```

Returns:

```
10 -> 20
```

Check:

```
20 <= 25
```

Valid.

2\. Find the next booking

```
calendar.ceilingEntry(25);
```

Returns:

```
30 -> 40
```

Check:

```
35 <= 30
```

Invalid.

Therefore, reject the booking.

## Java 24 optimal code

```java
import java.util.Map;
import java.util.TreeMap;

class MyCalendar {

    /*
     * TreeMap maintains all booking start times in sorted order.
     *
     * KEY:
     *     Booking start time.
     *
     * VALUE:
     *     Booking end time.
     *
     * Example:
     *
     * 10 -> 20
     * 30 -> 40
     * 50 -> 60
     *
     * Represents:
     *
     * [10,20), [30,40), [50,60)
     *
     * WHY TREEMAP?
     *
     * We need to efficiently find:
     * 1. The previous booking.
     * 2. The next booking.
     *
     * TreeMap is backed by a Red-Black Tree and provides
     * O(log N) lookup and insertion.
     */
    private final TreeMap<Integer, Integer> calendar;

    public MyCalendar() {
        calendar = new TreeMap<>();
    }

    public boolean book(int startTime, int endTime) {

        /*
         * STEP 1: Find the previous booking.
         *
         * floorEntry(startTime) returns the entry with the
         * greatest key <= startTime.
         *
         * In other words:
         * Find the booking whose start time is closest to
         * startTime from the left, including equality.
         *
         * Example:
         *
         * Existing:
         * 10 -> 20
         * 30 -> 40
         * 50 -> 60
         *
         * New booking starts at 35.
         *
         * floorEntry(35) returns:
         * 30 -> 40
         */
        Map.Entry<Integer, Integer> previous =
                calendar.floorEntry(startTime);

        /*
         * STEP 2: Check whether the previous booking overlaps.
         *
         * Previous booking:
         * [previous.start, previous.end)
         *
         * New booking:
         * [startTime, endTime)
         *
         * They overlap if:
         *
         * previous.end > startTime
         *
         * WHY STRICTLY GREATER?
         *
         * If previous.end == startTime:
         *
         * Previous: [10,20)
         * New:      [20,30)
         *
         * They do not overlap because 20 is excluded
         * from the previous half-open interval.
         */
        if (previous != null && previous.getValue() > startTime) {
            return false;
        }

        /*
         * STEP 3: Find the next booking.
         *
         * ceilingEntry(startTime) returns the entry with
         * the smallest key >= startTime.
         *
         * Example:
         *
         * Existing:
         * 10 -> 20
         * 30 -> 40
         * 50 -> 60
         *
         * New booking starts at 25.
         *
         * ceilingEntry(25) returns:
         * 30 -> 40
         */
        Map.Entry<Integer, Integer> next =
                calendar.ceilingEntry(startTime);

        /*
         * STEP 4: Check whether the next booking overlaps.
         *
         * Next booking:
         * [next.start, next.end)
         *
         * New booking:
         * [startTime, endTime)
         *
         * They overlap if:
         *
         * endTime > next.start
         *
         * If endTime == next.start, the intervals are adjacent,
         * which is perfectly valid for half-open intervals.
         */
        if (next != null && endTime > next.getKey()) {
            return false;
        }

        /*
         * STEP 5: Both neighboring bookings are safe.
         *
         * Therefore, accept the booking.
         *
         * Store:
         * startTime -> endTime
         *
         * TreeMap automatically maintains sorted key order.
         */
        calendar.put(startTime, endTime);

        return true;
    }
}
```

### Complexity analysis

Let `N` be the number of accepted bookings.

| Operation               | Complexity |
| ----------------------- | ---------- |
| `floorEntry()`          | O(log N)   |
| `ceilingEntry()`        | O(log N)   |
| `put()`                 | O(log N)   |
| Total booking operation | O(log N)   |
| Space                   | O(N)       |

For `B` booking calls, total worst-case time is:

\\[ O(B\log B) \\]

This is substantially better than the brute-force approach for large inputs.

# 8. Interviewer follow-up questions

### Q1. Why does checking only the previous and next intervals work?

Because we maintain the invariant that all accepted intervals are non-overlapping and sorted by their start times.

Every interval before the predecessor ends before or at the predecessor's start. Every interval after the successor starts after or at the successor's start.

Therefore, if the immediate neighbors do not overlap the new interval, no other interval can overlap it.

### Q2. Why use `floorEntry()` instead of `lowerEntry()`?

`floorEntry(key)` finds the greatest key less than or equal to the given key.

`lowerEntry(key)` finds the greatest key strictly less than the given key.

In our implementation, we use `floorEntry()` because it also handles an existing booking with exactly the same start time.

For example:

```
Existing: [10,20)
New:      [10,15)
```

`floorEntry(10)` finds the existing booking, and we correctly reject the new one.

Using `lowerEntry()` alone would miss it.

### Q3. Why is `ceilingEntry()` necessary?

It finds the next booking whose start time is greater than or equal to the new booking's start time.

We must ensure our new interval finishes before or exactly when this next booking starts.

### Q4. What if two bookings have the same start time?

The `TreeMap` uses start time as the unique key.

However, the existing booking is detected using `floorEntry()`, and the new booking is rejected before calling `put()`.

Therefore, an existing booking is never accidentally overwritten.

### Q5. Can we solve this using a PriorityQueue?

A priority queue can efficiently find the earliest-ending booking, but it does not efficiently provide both the predecessor and successor of an arbitrary start time.

We need an ordered structure, making `TreeMap` more suitable.

### Q6. What if we need to support cancellation?

We can introduce:

```java
public void cancel(int startTime) {
    calendar.remove(startTime);
}
```

This takes `O(log N)` time.

This assumes each booking can be uniquely identified by its start time, which is guaranteed by the no-overlap constraint for accepted bookings.

### Q7. What if double booking is allowed, but triple booking is prohibited?

That is a different problem: LeetCode 731, My Calendar II.

We would need to track overlapping regions as well as original bookings.

A simple predecessor/successor check would no longer be sufficient.

| Approach                  | Booking time | Space | When to use                           |
| ------------------------- | ------------ | ----- | ------------------------------------- |
| Brute force               | O(N)         | O(N)  | Small constraints                     |
| Binary Search + ArrayList | O(N)         | O(N)  | Sorted storage, simple implementation |
| TreeMap                   | O(log N)     | O(N)  | Efficient ordered insertion           |

My recommendation for an interview:

1. Start with brute force. Explain the interval-overlap condition.
2. Recognize that accepted intervals never overlap.
3. Maintain intervals sorted by start time.
4. Observe that only the predecessor and successor need checking.
5. Use `TreeMap.floorEntry()` and `TreeMap.ceilingEntry()` to get both neighbors efficiently.

The key insight to remember is:

> When maintaining non-overlapping intervals sorted by their start times, inserting a new interval only requires checking its immediate predecessor and successor.

That observation is much more important than memorizing the `TreeMap` APIs.








































Your solution uses a Binary Search Tree (BST) to store non-overlapping intervals. This is a very good approach for My Calendar I because it uses the same predecessor/successor idea as `TreeMap`, but implements the tree manually.

Let's improve your implementation with detailed comments and understand the reasoning behind every operation.

# 1. Core intuition: BST of intervals

Each BST node represents one accepted booking.

```
Node:
    start
    end
    left
    right
```

We maintain the following BST property:

- Left subtree: All intervals end before or exactly when the current interval starts.
- Right subtree: All intervals start after or exactly when the current interval ends.

For example, suppose we book:

```
book(20, 30);
book(10, 15);
book(40, 50);
book(15, 20);
```

The resulting BST looks like:

```
                 [20, 30)
                 /      \
          [10, 15)     [40, 50)
               \
              [15, 20)
```

Notice something important:

`[15, 20)` belongs in the right subtree of `[10, 15)` because:

```
15 >= 15
```

But it belongs in the left subtree of `[20, 30)` because:

```
20 <= 20
```

This is valid because adjacent half-open intervals do not overlap.

# 2. The most important decision-making logic

Suppose the current BST node represents:

```
Current interval = [node.start, node.end)
New interval     = [startTime, endTime)
```

There are exactly three possibilities.

Case 1: New interval belongs to the left subtree

```
endTime <= node.start
```

Example:

```
Current: [20, 30)
New:     [10, 20)
```

The new interval ends before or exactly when the current interval starts.

No overlap.

Move left.

Case 2: New interval belongs to the right subtree

```
startTime >= node.end
```

Example:

```
Current: [20, 30)
New:     [30, 40)
```

The new interval starts after or exactly when the current interval ends.

No overlap.

Move right.

Case 3: Overlap

If neither condition is true, the intervals overlap.

Example:

```
Current: [20, 30)
New:     [25, 35)
```

Neither condition holds:

```
35 <= 20  // false
25 >= 30  // false
```

Therefore, reject the booking.

The key observation:

```java
if (endTime <= node.start) {
    // Go LEFT
} else if (startTime >= node.end) {
    // Go RIGHT
} else {
    // OVERLAP: Reject
}
```

# 3. Improved Java 24 solution — Detailed comments

I recommend keeping your two-phase design:

1. `canInsert()` checks whether the booking is valid.
2. `insert()` actually inserts the booking.

This separation is useful because we never modify the tree until we know the booking can be accepted.

Recommended BST implementation

```java
class MyCalendar {

    /*
     * ROOT represents the root of our Binary Search Tree.
     *
     * Every node represents one successfully accepted booking.
     *
     * IMPORTANT INVARIANT:
     *
     * No two intervals stored in this BST overlap.
     *
     * BST ordering:
     *
     * LEFT SUBTREE:
     * Every interval lies completely before or adjacent to
     * the current interval.
     *
     * RIGHT SUBTREE:
     * Every interval lies completely after or adjacent to
     * the current interval.
     *
     * Example:
     *
     *                  [20, 30)
     *                  /      \
     *             [10, 15)  [40, 50)
     *
     * This is an ordinary, unbalanced BST.
     */
    private Node root;

    public MyCalendar() {
        root = null;
    }

    public boolean book(int startTime, int endTime) {

        /*
         * PHASE 1: VALIDATE THE BOOKING.
         *
         * canInsert() traverses the BST and checks whether
         * the new interval conflicts with any existing interval.
         *
         * WHY SEPARATE VALIDATION FROM INSERTION?
         *
         * If we insert while checking, we might modify the tree
         * before discovering a conflict.
         *
         * By checking first, the tree remains unchanged when
         * a booking is rejected.
         */
        if (!canInsert(root, startTime, endTime)) {
            return false;
        }

        /*
         * PHASE 2: INSERT THE BOOKING.
         *
         * We reach this point only if the new interval does not
         * overlap with any existing interval.
         *
         * insert() follows the same BST navigation rules and
         * creates a new node at the appropriate position.
         *
         * IMPORTANT:
         * We must assign the returned node to root because
         * the tree might initially be empty.
         */
        root = insert(root, startTime, endTime);

        return true;
    }

    /*
     * Checks whether [startTime, endTime) can be inserted
     * into the subtree rooted at 'node'.
     *
     * This is a recursive BST search.
     *
     * We do NOT need to inspect every node.
     * We only follow one root-to-leaf path.
     */
    private boolean canInsert(
            Node node,
            int startTime,
            int endTime
    ) {

        /*
         * BASE CASE:
         *
         * We reached an empty position.
         *
         * This means no existing interval along the search path
         * conflicts with our new interval.
         *
         * Since the BST invariant guarantees that intervals
         * in the other branches are also ordered and non-overlapping,
         * the booking is valid.
         */
        if (node == null) {
            return true;
        }

        /*
         * CASE 1: NEW INTERVAL BELONGS TO THE LEFT SUBTREE.
         *
         * Existing interval: [node.start, node.end)
         * New interval:      [startTime, endTime)
         *
         * Condition:
         *
         * endTime <= node.start
         *
         * Example:
         *
         * Existing: [20, 30)
         * New:      [10, 20)
         *
         * The new interval ends exactly when the existing interval
         * starts.
         *
         * Because intervals are HALF-OPEN, they do not overlap.
         *
         * Therefore, search the left subtree.
         */
        if (endTime <= node.start) {

            return canInsert(
                    node.left,
                    startTime,
                    endTime
            );
        }

        /*
         * CASE 2: NEW INTERVAL BELONGS TO THE RIGHT SUBTREE.
         *
         * Condition:
         *
         * startTime >= node.end
         *
         * Example:
         *
         * Existing: [20, 30)
         * New:      [30, 40)
         *
         * The new interval starts exactly when the existing
         * interval ends.
         *
         * Again, they do not overlap.
         *
         * Therefore, search the right subtree.
         */
        else if (startTime >= node.end) {

            return canInsert(
                    node.right,
                    startTime,
                    endTime
            );
        }

        /*
         * CASE 3: OVERLAP FOUND.
         *
         * Neither of the two non-overlapping conditions holds.
         *
         * Therefore:
         *
         * startTime < node.end
         * AND
         * node.start < endTime
         *
         * This is precisely the interval-overlap condition.
         *
         * Example:
         *
         * Existing: [20, 30)
         * New:      [25, 35)
         *
         * Both intervals share the time range [25, 30).
         *
         * Reject immediately.
         */
        else {

            return false;
        }
    }

    /*
     * Inserts a previously validated interval into the BST.
     *
     * IMPORTANT:
     * This method assumes the interval has already been validated
     * using canInsert().
     *
     * Therefore, we do not need to check for overlap again.
     *
     * The method returns the root of the updated subtree.
     */
    private Node insert(
            Node node,
            int startTime,
            int endTime
    ) {

        /*
         * BASE CASE:
         *
         * We found an empty position.
         *
         * Create a new node representing the accepted booking.
         */
        if (node == null) {
            return new Node(startTime, endTime);
        }

        /*
         * CASE 1: Insert into the left subtree.
         *
         * The new interval finishes before or exactly when
         * the current interval starts.
         *
         * This is the same navigation rule used in canInsert().
         */
        if (endTime <= node.start) {

            /*
             * Recursively insert into the left subtree.
             *
             * Assign the returned subtree root to node.left.
             *
             * This assignment is important because recursion
             * may create a completely new node.
             */
            node.left = insert(
                    node.left,
                    startTime,
                    endTime
            );
        }

        /*
         * CASE 2: Insert into the right subtree.
         *
         * Because canInsert() already validated the booking,
         * the new interval must belong on the right whenever
         * it does not belong on the left.
         *
         * This means:
         *
         * startTime >= node.end
         */
        else {

            node.right = insert(
                    node.right,
                    startTime,
                    endTime
            );
        }

        /*
         * Return the current node.
         *
         * This preserves the root of the current subtree
         * while allowing recursive calls to update child pointers.
         */
        return node;
    }

    /*
     * Represents one calendar booking.
     *
     * Each node stores:
     *
     * start = booking start time
     * end   = booking end time
     *
     * left  = earlier non-overlapping bookings
     * right = later non-overlapping bookings
     */
    private static class Node {

        final int start;
        final int end;

        Node left;
        Node right;

        Node(int start, int end) {
            this.start = start;
            this.end = end;
        }
    }
}
```

# 5. Complexity analysis — Important interview discussion

Let `N` represent the number of successfully accepted bookings.

The BST has one node per accepted booking.

### Time complexity

`canInsert()`:

- Best case: `O(1)` if the first comparison finds a conflict or the tree is empty.
- Average case: `O(log N)` if the tree is reasonably balanced.
- Worst case: `O(N)` if the tree becomes skewed.

`insert()`:

- Best case: `O(1)` for an empty tree.
- Average case: `O(log N)`.
- Worst case: `O(N)`.

Therefore:

| Scenario     | Booking complexity |
| ------------ | ------------------ |
| Balanced BST | O(log N)           |
| Skewed BST   | O(N)               |

Important: Your implementation is an ordinary BST, not a self-balancing BST.

Consider inserting bookings in ascending order:

```
[10, 20)
[30, 40)
[50, 60)
[70, 80)
```

The tree becomes:

```
[10, 20)
      \
      [30, 40)
            \
            [50, 60)
                  \
                  [70, 80)
```

This is effectively a linked list!

Every subsequent booking may require traversing all previous nodes.

### Space complexity

- BST storage: `O(N)`.
- Recursive call stack: `O(H)`, where `H` is the tree height.
- Overall: `O(N)`.

# 6. Important improvement: Can we combine validation and insertion?

Yes!

Your current implementation traverses the tree twice:

1. `canInsert()` searches for the insertion position.
2. `insert()` searches again to reach the same position.

We can improve this by combining both operations into one recursive method.

This is a cleaner implementation because:

- We traverse the tree only once.
- We immediately reject on overlap.
- We insert when we find an empty position.
- We don't need a separate validation pass.

## Single-pass BST solution

```java
class MyCalendar {

    private Node root;

    public MyCalendar() {
        root = null;
    }

    public boolean book(int startTime, int endTime) {

        /*
         * insert() returns:
         *
         * - Updated subtree root when insertion succeeds.
         * - null when insertion fails.
         *
         * However, null is ambiguous if the original root is null.
         *
         * Therefore, we use a small result wrapper to explicitly
         * distinguish success from failure.
         */
        InsertResult result = insert(root, startTime, endTime);

        if (!result.inserted()) {
            return false;
        }

        root = result.node();

        return true;
    }

    private InsertResult insert(
            Node node,
            int startTime,
            int endTime
    ) {

        /*
         * Found an empty position.
         *
         * Create and return a new node.
         */
        if (node == null) {
            return new InsertResult(
                    new Node(startTime, endTime),
                    true
            );
        }

        /*
         * New interval belongs to the left subtree.
         *
         * Its end is <= current.start, so there is no overlap.
         */
        if (endTime <= node.start) {

            InsertResult result = insert(
                    node.left,
                    startTime,
                    endTime
            );

            /*
             * If insertion failed deeper in the tree,
             * propagate the failure without modifying this node.
             */
            if (!result.inserted()) {
                return result;
            }

            /*
             * Insertion succeeded.
             * Update the left child.
             */
            node.left = result.node();

            return new InsertResult(node, true);
        }

        /*
         * New interval belongs to the right subtree.
         *
         * Its start is >= current.end, so there is no overlap.
         */
        if (startTime >= node.end) {

            InsertResult result = insert(
                    node.right,
                    startTime,
                    endTime
            );

            if (!result.inserted()) {
                return result;
            }

            node.right = result.node();

            return new InsertResult(node, true);
        }

        /*
         * Neither condition holds.
         *
         * The new interval overlaps the current interval.
         *
         * Return failure without changing the tree.
         */
        return new InsertResult(node, false);
    }

    /*
     * Immutable result returned by recursive insertion.
     *
     * inserted = whether insertion succeeded.
     * node     = updated subtree root.
     */
    private record InsertResult(Node node, boolean inserted) {}

    private static class Node {

        final int start;
        final int end;

        Node left;
        Node right;

        Node(int start, int end) {
            this.start = start;
            this.end = end;
        }
    }
}
```

This version traverses only one path and avoids the separate validation traversal.

# 7. Final comparison of BST vs TreeMap vs Sweep Line

| Approach                         | Booking time     | Main idea                            |
| -------------------------------- | ---------------- | ------------------------------------ |
| Brute force                      | O(N)             | Check every interval                 |
| Sorted ArrayList + Binary Search | O(N)             | Find position, shift elements        |
| Manual ordinary BST              | O(H), worst O(N) | Navigate interval tree               |
| TreeMap                          | O(log N)         | Balanced BST + predecessor/successor |
| Sweep Line + TreeMap             | O(N)             | Recalculate active bookings          |

My recommendation for interviews:

- If asked to implement a BST yourself, your original approach is correct and demonstrates good understanding of interval ordering.
- If asked for the most efficient practical Java solution, use `TreeMap`.
- If asked specifically about sweep line, explain event deltas and active booking counts.

One final insight worth remembering:

Your manual BST is essentially implementing the same fundamental idea as TreeMap. The difference is that Java's `TreeMap` automatically balances its Red-Black Tree, while your custom BST does not.
