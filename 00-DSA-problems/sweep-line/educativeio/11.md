# 715. Range Module — Hard

Main pattern: Interval Management + Ordered Data Structure (TreeMap)

The most practical interview solution is a TreeMap-based implementation that maintains non-overlapping, merged intervals.

We will cover:

1. Simplified understanding.
2. Clarifying questions.
3. Core intuition and mental model.
4. Brute-force, TreeMap, and Dynamic Segment Tree approaches.
5. Detailed Java 24 implementations.
6. Edge cases.
7. Interview follow-up questions.

# 0. Simplify the problem

We need to design a data structure that tracks which numbers are currently covered.

It supports three operations:

| Operation                  | Meaning                                        |
| -------------------------- | ---------------------------------------------- |
| `addRange(left, right)`    | Start tracking every number in `[left, right)` |
| `queryRange(left, right)`  | Check whether the entire interval is tracked   |
| `removeRange(left, right)` | Stop tracking numbers in `[left, right)`       |

The important detail is that intervals are half-open.

For example:

```
[10, 20)
```

Includes:

```
10, 10.5, 11, 11.5, ..., 19.99...
```

Does not include `20`.

This means:

```
[10, 15) and [15, 20)
```

are adjacent intervals. Together, they represent `[10, 20)` without any gap.

We must support real numbers, not just integers.

# 1. Clarifying questions to ask the interviewer

Before implementing, clarify:

1. Can intervals overlap?

   Yes. `addRange` must merge overlapping and adjacent coverage logically.
2. Can `addRange` be called on an already tracked interval?

   Yes. Adding an existing range should not change the result.
3. Can `removeRange` partially overlap existing intervals?

   Yes. We might need to split an existing interval.
4. Are intervals half-open or closed?

   Half-open `[left, right)`. This is critical when deciding whether two intervals overlap or are adjacent.
5. What are the constraints on coordinates and operations?

   Coordinates can be as large as \\(10^9\\), and there are at most \\(10^4\\) operations.

   This helps determine whether coordinate compression, a TreeMap, or a segment tree is appropriate.

# 2. Core intuition: Think of ranges as continuous coverage

The key observation:

We should maintain the tracked numbers as sorted, non-overlapping intervals.

For example, suppose we execute:

```
addRange(10, 20);
addRange(15, 25);
addRange(30, 40);
```

Instead of storing all three original operations, maintain:

```
10 ---------------- 25       30 -------- 40
```

Our internal representation becomes:

```
[10, 25)
[30, 40)
```

Why?

- Overlapping intervals can be merged.
- Sorted intervals make searching easier.
- We never need to store duplicate coverage.
- Removing a range only requires modifying intervals that intersect it.

## The three operations mentally

### A. addRange(left, right)

Suppose we currently have:

```
[10, 20)     [30, 40)
```

Execute:

```
addRange(15, 35);
```

The new interval overlaps both existing intervals.

Result:

```
[10, 40)
```

Mental model:

1. Find the first interval that overlaps or touches the new interval.
2. Expand the new interval to include it.
3. Continue merging while intervals overlap or touch.
4. Insert the merged interval.

### B. queryRange(left, right)

Suppose we have:

```
[10, 20)     [25, 40)
```

Query:

```
queryRange(12, 18); // true
queryRange(12, 22); // false
queryRange(25, 40); // true
queryRange(20, 25); // false
```

A query must be covered by one continuous tracked interval.

Because we always merge overlapping and adjacent intervals, a valid query must fit entirely inside one stored interval.

### C. removeRange(left, right)

Suppose we have:

```
[10, 30)
```

Execute:

```
removeRange(15, 20);
```

Result:

```
[10, 15)     [20, 30)
```

There are four possible cases:

| Existing interval | Removal interval | Result               |
| ----------------- | ---------------- | -------------------- |
| `[10, 20)`        | `[12, 15)`       | `[10,12)`, `[15,20)` |
| `[10, 20)`        | `[5, 15)`        | `[15,20)`            |
| `[10, 20)`        | `[15, 25)`       | `[10,15)`            |
| `[10, 20)`        | `[5, 25)`        | Nothing              |

The most important case is splitting an interval into two pieces.

# 3. Solution 1: Brute Force — List of Intervals

The simplest implementation maintains a list of non-overlapping intervals.

For every operation, scan the list and modify the intervals.

This is useful as a starting point because it makes the interval logic easy to understand.

```java
import java.util.*;

class RangeModuleBruteForce {

    // Every interval is represented as [start, end).
    // The list maintains sorted, non-overlapping, non-adjacent intervals.
    private final List<int[]> intervals = new ArrayList<>();

    public void addRange(int left, int right) {

        List<int[]> result = new ArrayList<>();

        // The new interval initially contains only the requested range.
        int mergedStart = left;
        int mergedEnd = right;

        boolean inserted = false;

        for (int[] interval : intervals) {

            int start = interval[0];
            int end = interval[1];

            // Existing interval is completely before the new interval.
            // Strict '<' is used because adjacent intervals should merge.
            if (end < mergedStart) {
                result.add(interval);
            }

            // Existing interval is completely after the new interval.
            else if (mergedEnd < start) {

                // Insert the merged interval before this existing interval.
                if (!inserted) {
                    result.add(new int[]{mergedStart, mergedEnd});
                    inserted = true;
                }

                result.add(interval);
            }

            // Overlapping or adjacent intervals must be merged.
            else {

                mergedStart = Math.min(mergedStart, start);
                mergedEnd = Math.max(mergedEnd, end);
            }
        }

        // If we haven't inserted the merged interval, append it.
        if (!inserted) {
            result.add(new int[]{mergedStart, mergedEnd});
        }

        intervals.clear();
        intervals.addAll(result);
    }

    public boolean queryRange(int left, int right) {

        for (int[] interval : intervals) {

            // Since intervals are sorted, no later interval can cover
            // the query if this interval starts after left.
            if (interval[0] > left) {
                return false;
            }

            // The query must fit entirely inside one stored interval.
            if (interval[0] <= left && interval[1] >= right) {
                return true;
            }
        }

        return false;
    }

    public void removeRange(int left, int right) {

        List<int[]> result = new ArrayList<>();

        for (int[] interval : intervals) {

            int start = interval[0];
            int end = interval[1];

            // No overlap: preserve the original interval.
            if (end <= left || start >= right) {
                result.add(interval);
                continue;
            }

            // Left remainder:
            // Existing interval begins before the removal interval.
            if (start < left) {
                result.add(new int[]{start, left});
            }

            // Right remainder:
            // Existing interval ends after the removal interval.
            if (end > right) {
                result.add(new int[]{right, end});
            }
        }

        intervals.clear();
        intervals.addAll(result);
    }
}
```

### Complexity

Let `N` be the number of currently stored intervals.

| Operation     | Time | Explanation                        |
| ------------- | ---- | ---------------------------------- |
| `addRange`    | O(N) | Scan and rebuild the interval list |
| `queryRange`  | O(N) | Linear search                      |
| `removeRange` | O(N) | Scan and rebuild the interval list |

Space: O(N) for stored intervals, with O(N) temporary space during updates.

Limitation: Every operation potentially scans the entire list. We can improve searching using an ordered map.

# 4. Solution 2: Optimal practical solution — TreeMap

Recommended interview solution

Java's `TreeMap` maintains keys in sorted order using a Red-Black Tree.

We will use:

```
TreeMap<Integer, Integer>
```

Representation:

```
key   = interval start
value = interval end
```

For example:

```
map.put(10, 20);
map.put(30, 40);
map.put(50, 60);
```

Represents:

```
[10, 20)
[30, 40)
[50, 60)
```

Our invariant:

- Intervals are sorted by start.
- Intervals never overlap.
- Intervals never touch (adjacent intervals are merged).

This invariant makes all three operations easier.

## A. addRange()

The main TreeMap operations are:

```
floorEntry(left)
ceilingEntry(left)
```

- `floorEntry(left)` gives the interval whose start is the greatest key less than or equal to `left`.
- `ceilingEntry(left)` gives the interval whose start is the smallest key greater than or equal to `left`.

Mental model:

```
Existing:

[10, 20)     [30, 40)     [50, 60)

addRange(15, 45)

Step 1: Start with [15, 45)
Step 2: Merge [10, 20)
Step 3: Merge [30, 40)
Step 4: Insert [10, 45)

Result:

[10, 45)                  [50, 60)
```

We also merge adjacent intervals.

For half-open intervals, adjacency occurs when:

```
existingEnd == newStart
```

There is no uncovered real number between them, so merging is valid.

## B. queryRange()

Find the interval with the greatest start less than or equal to `left`.

Then check:

```
interval.start <= left && interval.end >= right
```

Why is one interval sufficient?

Because our invariant guarantees that overlapping and adjacent tracked intervals are already merged.

## C. removeRange()

Find every interval intersecting the removal interval.

For each overlapping interval:

- Preserve the left remainder if it exists.
- Preserve the right remainder if it exists.
- Delete the original interval.

The overlap condition for half-open intervals is:

```
existingStart < right && existingEnd > left
```

Notice the strict inequalities.

An interval ending exactly at `left` does not overlap the removal range.

An interval starting exactly at `right` does not overlap either.

## Complete Java 24 implementation

```java
import java.util.Map;
import java.util.TreeMap;

class RangeModule {

    /*
     * DATA STRUCTURE
     *
     * TreeMap<start, end>
     *
     * Example:
     *
     * 10 -> 20
     * 30 -> 40
     * 50 -> 60
     *
     * Represents:
     *
     * [10, 20)
     * [30, 40)
     * [50, 60)
     *
     * INVARIANT:
     *
     * 1. Intervals are sorted by start.
     * 2. Intervals never overlap.
     * 3. Intervals never touch.
     *
     * Therefore, for consecutive intervals:
     *
     * previousEnd < nextStart
     *
     * Why use TreeMap?
     *
     * TreeMap is implemented using a Red-Black Tree.
     * floorEntry(), ceilingEntry(), and put() take O(log N).
     *
     * N = number of currently tracked intervals.
     */
    private final TreeMap<Integer, Integer> intervals;

    public RangeModule() {
        intervals = new TreeMap<>();
    }

    /*
     * ADD RANGE
     *
     * Adds every number in [left, right).
     *
     * Example:
     *
     * Existing:
     * [10, 20) [30, 40) [50, 60)
     *
     * addRange(15, 45)
     *
     * Result:
     * [10, 45) [50, 60)
     *
     * APPROACH:
     *
     * 1. Find an interval that may overlap or touch the new interval
     *    from the left.
     *
     * 2. Merge all intervals that overlap or touch the growing range.
     *
     * 3. Insert the final merged interval.
     */
    public void addRange(int left, int right) {

        // The interval being constructed.
        // It expands whenever we encounter an overlapping interval.
        int mergedStart = left;
        int mergedEnd = right;

        /*
         * STEP 1: Find the interval immediately before or at left.
         *
         * floorEntry(left):
         * Returns the entry with the greatest key <= left.
         *
         * We need to check this interval because it may overlap
         * or touch the new interval from the left.
         */
        Map.Entry<Integer, Integer> entry =
                intervals.floorEntry(left);

        if (entry != null && entry.getValue() >= mergedStart) {

            /*
             * The existing interval overlaps or touches the new interval.
             *
             * Example:
             *
             * Existing: [10, 20)
             * New:           [15, 25)
             *
             * Merge:
             * [10, 25)
             *
             * Equality is included because adjacent intervals
             * should also be merged.
             */
            mergedStart = Math.min(mergedStart, entry.getKey());
            mergedEnd = Math.max(mergedEnd, entry.getValue());

            // Remove the old interval because it is now part
            // of the merged interval.
            intervals.remove(entry.getKey());
        }

        /*
         * STEP 2: Merge all intervals starting inside or at
         * the growing merged interval's right boundary.
         *
         * ceilingEntry(mergedStart):
         * Returns the smallest key >= mergedStart.
         *
         * We repeatedly merge until no more intervals overlap
         * or touch the current merged interval.
         */
        entry = intervals.ceilingEntry(mergedStart);

        while (entry != null && entry.getKey() <= mergedEnd) {

            // Expand the right boundary if necessary.
            mergedEnd = Math.max(mergedEnd, entry.getValue());

            // Remove the old interval before inserting the merged one.
            intervals.remove(entry.getKey());

            /*
             * The right boundary may have expanded.
             * Therefore, retrieve the next candidate using the
             * updated mergedEnd/merged interval.
             */
            entry = intervals.ceilingEntry(mergedStart);
        }

        /*
         * STEP 3: Insert the final merged interval.
         *
         * At this point, no existing interval overlaps or touches it.
         */
        intervals.put(mergedStart, mergedEnd);
    }

    /*
     * QUERY RANGE
     *
     * Returns true if every real number in [left, right)
     * is currently being tracked.
     *
     * APPROACH:
     *
     * Find the interval with the greatest start <= left.
     *
     * If that interval ends at or beyond right,
     * the entire query is covered.
     */
    public boolean queryRange(int left, int right) {

        /*
         * Find the interval that could contain left.
         *
         * floorEntry(left) returns the interval with the greatest
         * starting point that does not exceed left.
         */
        Map.Entry<Integer, Integer> entry =
                intervals.floorEntry(left);

        /*
         * If no such interval exists, left is not tracked.
         *
         * Otherwise, the interval must extend at least until right.
         *
         * end >= right is correct because both intervals are half-open.
         *
         * Example:
         *
         * Tracked: [10, 20)
         * Query:   [12, 20)
         *
         * This is fully covered.
         */
        return entry != null && entry.getValue() >= right;
    }

    /*
     * REMOVE RANGE
     *
     * Removes every tracked number in [left, right).
     *
     * Example:
     *
     * Existing:
     * [10, 30) [40, 60)
     *
     * removeRange(15, 45)
     *
     * Result:
     * [10, 15) [45, 60)
     *
     * APPROACH:
     *
     * 1. Find the first interval that overlaps the removal range.
     *
     * 2. Remove every overlapping interval.
     *
     * 3. Preserve the portions outside the removal range.
     */
    public void removeRange(int left, int right) {

        /*
         * STEP 1: Find the first possible overlapping interval.
         *
         * floorEntry(left) might overlap from the left.
         *
         * If it doesn't overlap, start with ceilingEntry(left).
         */
        Map.Entry<Integer, Integer> entry =
                intervals.floorEntry(left);

        if (entry == null || entry.getValue() <= left) {
            entry = intervals.ceilingEntry(left);
        }

        /*
         * Store the remainders separately.
         *
         * Why?
         *
         * We are deleting intervals while iterating.
         * Collecting the remainders first avoids modifying
         * the map with new intervals during traversal.
         */
        Integer leftRemainderStart = null;
        Integer leftRemainderEnd = null;

        Integer rightRemainderStart = null;
        Integer rightRemainderEnd = null;

        while (entry != null && entry.getKey() < right) {

            int start = entry.getKey();
            int end = entry.getValue();

            /*
             * This interval overlaps [left, right).
             *
             * We know:
             *
             * start < right
             *
             * And because we selected the first possible overlap,
             * its end is > left.
             */

            // Preserve the left part if it exists.
            //
            // Existing: [10, 30)
            // Removal:       [15, 20)
            // Left part: [10, 15)
            if (start < left) {
                leftRemainderStart = start;
                leftRemainderEnd = left;
            }

            // Preserve the right part if it exists.
            //
            // Existing: [10, 30)
            // Removal:       [15, 20)
            // Right part:          [20, 30)
            if (end > right) {
                rightRemainderStart = right;
                rightRemainderEnd = end;
            }

            /*
             * Remove the original interval.
             *
             * If the removal interval is inside an existing interval,
             * this operation effectively splits it into two pieces.
             */
            intervals.remove(start);

            /*
             * If the current interval extends beyond right,
             * no later interval can overlap the removal range.
             *
             * Why?
             *
             * Existing intervals are non-overlapping and sorted.
             */
            if (end >= right) {
                break;
            }

            // Find the next interval whose start is >= current start.
            entry = intervals.ceilingEntry(left);
        }

        /*
         * STEP 2: Insert the preserved remainders.
         *
         * There can be at most:
         *
         * - One left remainder.
         * - One right remainder.
         *
         * All fully covered intervals have been deleted.
         */
        if (leftRemainderStart != null) {
            intervals.put(leftRemainderStart, leftRemainderEnd);
        }

        if (rightRemainderStart != null) {
            intervals.put(rightRemainderStart, rightRemainderEnd);
        }
    }
}
```

## Complexity analysis

Let:

- `N` = number of currently stored intervals.
- `K` = number of intervals affected by an operation.

| Operation     | Time complexity  | Explanation                                                                  |
| ------------- | ---------------- | ---------------------------------------------------------------------------- |
| `addRange`    | O((K + 1) log N) | Finds the first interval and removes K merged intervals before inserting one |
| `queryRange`  | O(log N)         | One `floorEntry()` lookup                                                    |
| `removeRange` | O((K + 1) log N) | Finds and removes K affected intervals, then inserts at most two remainders  |

Worst-case time for updates: O(N log N).

Space complexity: O(N), because each stored interval occupies one TreeMap entry. The removal operation additionally uses O(1) temporary space.

Interview takeaway: This is generally the best practical solution for this problem in Java.

# 5. Solution 3: Dynamic Segment Tree

There is another important approach worth understanding.

We can use a segment tree with lazy propagation.

However, coordinates go up to \\(10^9\\), so creating a normal array-based segment tree is impractical.

Instead, use a dynamic segment tree:

- Create nodes only when needed.
- Each node represents a coordinate segment.
- Store whether the entire segment is tracked.
- Support range assignment and range queries.

We can use three states:

```
0 = Entire segment is untracked
1 = Entire segment is tracked
2 = Mixed coverage
```

For a node:

- `addRange` assigns the range to tracked.
- `removeRange` assigns the range to untracked.
- `queryRange` checks whether every covered segment is tracked.

The domain is `[1, 1_000_000_000]` for this implementation, treating each coordinate as a unit cell. Because all update boundaries are integers, this exactly represents coverage of the corresponding real-number half-open intervals: `[left, right)` maps to cells `[left, right - 1]`.

```java
class RangeModuleSegmentTree {

    private static final int MIN = 1;
    private static final int MAX = 1_000_000_000;

    /*
     * Node states:
     *
     * 0 = Entire segment is untracked.
     * 1 = Entire segment is tracked.
     * 2 = Segment has mixed coverage.
     *
     * lazy:
     *
     * -1 = No pending assignment.
     *  0 = Assign entire segment as untracked.
     *  1 = Assign entire segment as tracked.
     */
    private static class Node {

        Node left;
        Node right;

        int state = 0;
        int lazy = 0;
    }

    private final Node root = new Node();

    public void addRange(int left, int right) {

        // Convert [left, right) to inclusive integer cells.
        update(root, MIN, MAX, left, right - 1, 1);
    }

    public void removeRange(int left, int right) {

        update(root, MIN, MAX, left, right - 1, 0);
    }

    public boolean queryRange(int left, int right) {

        // Every unit cell in [left, right - 1] must be tracked.
        return query(root, MIN, MAX, left, right - 1);
    }

    private void update(
            Node node,
            int start,
            int end,
            int queryStart,
            int queryEnd,
            int value) {

        // No intersection.
        if (queryStart > end || queryEnd < start) {
            return;
        }

        // Full coverage: assign the entire node.
        if (queryStart <= start && end <= queryEnd) {

            node.state = value;
            node.lazy = value;

            // Existing children are no longer needed to represent
            // this uniform segment.
            node.left = null;
            node.right = null;

            return;
        }

        // Create children only when necessary.
        pushDown(node);

        int mid = start + (end - start) / 2;

        if (queryStart <= mid) {
            update(
                    node.left,
                    start,
                    mid,
                    queryStart,
                    queryEnd,
                    value
            );
        }

        if (queryEnd > mid) {
            update(
                    node.right,
                    mid + 1,
                    end,
                    queryStart,
                    queryEnd,
                    value
            );
        }

        // Recalculate the parent's state.
        node.state =
                node.left.state == node.right.state
                        ? node.left.state
                        : 2;
    }

    private boolean query(
            Node node,
            int start,
            int end,
            int queryStart,
            int queryEnd) {

        // No intersection contributes no uncovered portion.
        if (queryStart > end || queryEnd < start) {
            return true;
        }

        // If the entire current segment is tracked,
        // every queried portion inside it is also tracked.
        if (node.state == 1) {
            return true;
        }

        // If the entire current segment is untracked,
        // any non-empty intersection fails the query.
        if (node.state == 0) {
            return false;
        }

        int mid = start + (end - start) / 2;

        // Mixed state: inspect the relevant children.
        pushDown(node);

        boolean leftResult = true;
        boolean rightResult = true;

        if (queryStart <= mid) {
            leftResult = query(
                    node.left,
                    start,
                    mid,
                    queryStart,
                    queryEnd
            );
        }

        if (queryEnd > mid) {
            rightResult = query(
                    node.right,
                    mid + 1,
                    end,
                    queryStart,
                    queryEnd
            );
        }

        return leftResult && rightResult;
    }

    private void pushDown(Node node) {

        // A leaf cannot have children.
        // In this problem the smallest coordinate cell has length 1.
        if (node.left != null || node.right != null) {
            return;
        }

        // Create two children inheriting the parent's current state.
        node.left = new Node();
        node.right = new Node();

        node.left.state = node.state;
        node.right.state = node.state;

        node.left.lazy = node.state == 2 ? -1 : node.state;
        node.right.lazy = node.state == 2 ? -1 : node.state;

        node.lazy = -1;
    }
}
```

### Important implementation note

The above is a conceptual dynamic segment tree, but the `pushDown` implementation needs to handle partially existing child nodes and pending assignments carefully. For a production-grade implementation, the standard approach is to maintain explicit lazy propagation and initialize children from the parent's pending assignment. Here is the corrected `pushDown` and update propagation pattern to use instead:

```java
private void pushDown(Node node) {

    if (node.left == null) {
        node.left = new Node();
        node.right = new Node();

        // New children inherit the parent's uniform state.
        node.left.state = node.state;
        node.right.state = node.state;
    }

    if (node.lazy != -1) {

        node.left.state = node.lazy;
        node.right.state = node.lazy;

        node.left.lazy = node.lazy;
        node.right.lazy = node.lazy;

        node.lazy = -1;
    }
}
```

The complete dynamic segment tree has O(log C) time per operation for a range assignment or query in the usual segment-tree analysis, where C is the coordinate-domain size, and O(Q log C) worst-case allocated nodes over Q operations.

Which should you choose?

| Approach             | Best use                                                |
| -------------------- | ------------------------------------------------------- |
| List                 | Learning interval manipulation                          |
| TreeMap              | Best practical interview solution                       |
| Dynamic Segment Tree | Large coordinate domain and range-update/query problems |

For this problem, I would implement the TreeMap solution first.

# 6. Edge cases to watch out for

| Scenario                | Operation                   | Expected behavior    |
| ----------------------- | --------------------------- | -------------------- |
| Empty module            | `queryRange(10,20)`         | false                |
| Add duplicate interval  | `addRange(10,20)` twice     | No change            |
| Add adjacent interval   | `[10,20)`, then `[20,30)`   | Merge into `[10,30)` |
| Add contained interval  | `[10,30)`, then `[15,20)`   | No change            |
| Remove uncovered range  | `removeRange(30,40)`        | No change            |
| Remove entire interval  | `[10,20)`, remove `[5,25)`  | Delete it            |
| Remove middle           | `[10,30)`, remove `[15,20)` | Split into two       |
| Remove left part        | `[10,30)`, remove `[5,15)`  | `[15,30)`            |
| Remove right part       | `[10,30)`, remove `[20,35)` | `[10,20)`            |
| Query exact interval    | `[10,20)`, query `[10,20)`  | true                 |
| Query adjacent boundary | `[10,20)`, query `[20,21)`  | false                |

The most common bug is using incorrect overlap comparisons.

Remember:

```
// Half-open intervals overlap:
existingStart < right && existingEnd > left;

// Adjacent intervals:
existingEnd == newStart;

// Adjacent intervals should merge in addRange().
```

# 7. Walkthrough of the given example

Operations:

```
RangeModule rm = new RangeModule();

rm.addRange(10, 20);

rm.removeRange(14, 16);

rm.queryRange(10, 14);

rm.queryRange(13, 15);
```

# 8. Interviewer follow-up questions

Q1. Why do we use TreeMap instead of HashMap?

Because we need ordered operations such as `floorEntry()` and `ceilingEntry()`.

A HashMap cannot efficiently find the interval immediately before or after a coordinate.

Q2. Why do we merge adjacent intervals?

Because `[10,20)` and `[20,30)` together represent continuous coverage of `[10,30)`.

Merging ensures that a query spanning the boundary is recognized as fully tracked.

Q3. Why does queryRange only need floorEntry(left)?

Because the intervals are sorted and non-overlapping.

The interval with the greatest starting point not exceeding `left` is the only possible interval that can contain `left`.

If it ends before `right`, no other interval can fill the gap because adjacent intervals have already been merged.

Q4. Can we use a HashSet?

Not directly.

The problem tracks real-number intervals, not individual integer coordinates. A HashSet would require discretizing the domain and would not represent arbitrary continuous ranges efficiently.

Q5. Why is the dynamic segment tree useful?

It supports range assignments and range queries without allocating an array for all coordinates.

It is particularly useful when the coordinate domain is huge and the number of operations is limited.

Q6. What happens if we change the interval convention to closed intervals `[left,right]`?

The overlap and adjacency rules change.

For closed intervals, intervals `[10,20]` and `[21,30]` have a gap, whereas for discrete integer coordinates they are consecutive but not continuous. We must carefully define whether coordinates represent real numbers or integers before changing the comparison rules.

Q7. Can the TreeMap solution be made thread-safe?

Yes, but `TreeMap` itself is not thread-safe.

We could synchronize all three public operations using the same lock. Merely using `ConcurrentSkipListMap` would not make a multi-step merge or removal atomic.

# 9. Final interview recommendation

| Criteria                  | List     | TreeMap        | Dynamic Segment Tree  |
| ------------------------- | -------- | -------------- | --------------------- |
| Implementation simplicity | High     | Medium         | Low                   |
| Query                     | O(N)     | O(log N)       | O(log C)              |
| Update                    | O(N)     | O((K+1) log N) | O(log C)              |
| Coordinate domain         | Any      | Any            | Fixed domain          |
| Extra memory              | O(N)     | O(N)           | O(Q log C) worst case |
| Interview preference      | Baseline | Best choice    | Advanced alternative  |

My recommendation: Lead with the TreeMap approach.

It demonstrates:

- Correct half-open interval reasoning.
- Ordered data structure knowledge.
- Efficient predecessor/successor lookup.
- Interval merging and splitting.
- Clear time-space trade-offs.

One important point to remember: Range Module is fundamentally an interval-maintenance problem, not a coordinate-storage problem. Once you maintain sorted, disjoint, non-adjacent intervals, all three operations become manageable.
