# 732. My Calendar III — Hard

Pattern: Sweep Line / Ordered Events (TreeMap) / Segment Tree

The most important observation is that My Calendar III is a maximum-overlap problem.

Unlike My Calendar I and II:

- My Calendar I: Prevent any overlapping bookings.
- My Calendar II: Prevent triple bookings.
- My Calendar III: Allow all bookings and return the maximum number of overlapping events after every booking.

There are multiple ways to solve this problem. Since there are at most 400 booking operations, the TreeMap Sweep Line solution is the simplest optimal choice for this problem's constraints.

## 0. Simplify the problem

Suppose we receive these bookings:

```
[10, 20)
[50, 60)
[10, 40)
[5, 15)
[5, 10)
[25, 55)
```

We need to return the maximum number of events active at the same time after each booking.

For example:

```
Time:       5   10   15   20   25   40   50   55   60
            |----|----|----|----|----|----|----|----|

Booking 1:      [----------]
Booking 2:                              [----------]
Booking 3:      [----------------------]
Booking 4:  [----------]
Booking 5:  [----]
Booking 6:                      [----------------------]
```

The maximum overlaps after each booking are:

```
Booking 1 -> 1
Booking 2 -> 1
Booking 3 -> 2
Booking 4 -> 3
Booking 5 -> 3
Booking 6 -> 3
```

Output:

```
[1, 1, 2, 3, 3, 3]
```

Notice that we don't need to know which events overlap with which other events.

We only need to know:

At every point in time, how many events are active?

## 1. Clarifying questions to ask the interviewer

| Question                                              | Why clarify?                                                                      |
| ----------------------------------------------------- | --------------------------------------------------------------------------------- |
| Are intervals half-open `[start, end)`?               | Determines whether an event ending at time `t` overlaps an event starting at `t`. |
| Are all bookings accepted?                            | My Calendar III accepts every valid booking.                                      |
| Do we need the maximum overlap after every insertion? | Determines whether we need to maintain the answer dynamically.                    |
| Are coordinates bounded?                              | Helps decide between TreeMap, coordinate compression, and segment trees.          |
| How many booking operations are expected?             | Determines which data structure is appropriate.                                   |

For this problem, the constraints establish:

- `0 <= startTime < endTime <= 10^9`
- At most `400` calls to `book()`.

The coordinate range is huge, but the number of bookings is small.

This makes a TreeMap particularly attractive.

# 2. Core intuition — Sweep Line Algorithm

The key mental model:

Instead of storing intervals, store the changes in the number of active intervals.

For every booking:

```
[startTime, endTime)
```

We create two events:

```
startTime -> +1
endTime   -> -1
```

Why?

- When an event starts, the number of active events increases by one.
- When an event ends, the number of active events decreases by one.

For example:

```
Booking: [10, 20)

10 -> +1
20 -> -1
```

Suppose we book:

```
[10, 20)
[15, 25)
```

Our event map becomes:

```
Time    Change
----------------
10      +1
15      +1
20      -1
25      -1
```

Now sweep through the events in sorted order.

| Time | Change | Active bookings | Maximum |
| ---- | ------ | --------------- | ------- |
| 10   | +1     | 1               | 1       |
| 15   | +1     | 2               | 2       |
| 20   | -1     | 1               | 2       |
| 25   | -1     | 0               | 2       |

Answer = `2`.

## Why does this correctly handle half-open intervals?

Consider:

```
[10, 20)
[20, 30)
```

These intervals do not overlap.

Our event changes are:

```
10 -> +1
20 -> -1 + 1 = 0
30 -> -1
```

At time `20`, the first interval ends and the second starts.

Because we aggregate both changes at the same coordinate, the active count never incorrectly becomes 2.

This is an important detail of sweep-line algorithms.

# 3. Solution 1 — TreeMap + Sweep Line (Recommended)

Recommended for these constraints

```java
import java.util.Map;
import java.util.TreeMap;

class MyCalendarThree {

    /*
     * TreeMap maintains all event coordinates in sorted order.
     *
     * Key   = timestamp
     * Value = net change in active bookings at that timestamp.
     *
     * Example:
     *
     * [10, 20) produces:
     *
     * 10 -> +1
     * 20 -> -1
     *
     * Multiple bookings can modify the same timestamp.
     */
    private final TreeMap<Integer, Integer> events;

    public MyCalendarThree() {
        events = new TreeMap<>();
    }

    public int book(int startTime, int endTime) {

        /*
         * STEP 1: Record the starting event.
         *
         * WHY +1?
         * A booking becomes active at startTime.
         */
        events.merge(startTime, 1, Integer::sum);

        /*
         * STEP 2: Record the ending event.
         *
         * WHY -1?
         * The booking is no longer active at endTime.
         *
         * This correctly models [startTime, endTime).
         */
        events.merge(endTime, -1, Integer::sum);

        /*
         * STEP 3: Sweep through all event coordinates.
         *
         * WHY?
         * The number of active bookings changes only at event
         * coordinates.
         *
         * Between two consecutive coordinates, the number of
         * active bookings remains constant.
         */
        int activeBookings = 0;

        /*
         * This stores the maximum number of simultaneous bookings
         * encountered during the sweep.
         */
        int maximumBookings = 0;

        /*
         * TreeMap.values() iterates in ascending key order.
         *
         * Therefore, we process all time changes chronologically.
         */
        for (int change : events.values()) {

            /*
             * Apply the net change at the current timestamp.
             */
            activeBookings += change;

            /*
             * Update the maximum overlap.
             */
            maximumBookings = Math.max(
                    maximumBookings,
                    activeBookings
            );
        }

        /*
         * Return the maximum overlap after this booking.
         */
        return maximumBookings;
    }
}
```

## Complexity analysis

Let:

- `n` = number of bookings made so far.
- `m` = number of distinct timestamps in the TreeMap.

Each booking introduces at most two timestamps.

Therefore:

\\[ m \leq 2n \\]

Time complexity per `book()` call:

1. Insert/update start timestamp: `O(log m)`.
2. Insert/update end timestamp: `O(log m)`.
3. Traverse all timestamps: `O(m)`.

Total:

\\[ O(\log m + \log m + m) \\]

\\[ \boxed{O(n)} \\]

Space complexity:

At most two distinct timestamps per booking:

\\[ \boxed{O(n)} \\]

For 400 bookings, this is extremely efficient and simple to implement.

# 4. Solution 2 — Brute Force: Store Intervals and Recalculate

This is the most straightforward solution.

The mental model is:

1. Store every booking.
2. Whenever a new booking arrives, collect all start and end coordinates.
3. Sort the coordinates.
4. Check how many intervals overlap at each coordinate.
5. Return the maximum.

```java
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

class MyCalendarThreeBruteForce {

    private record Interval(int start, int end) {}

    private final List<Interval> bookings = new ArrayList<>();

    public int book(int startTime, int endTime) {

        /*
         * STEP 1: Accept the booking.
         *
         * Unlike My Calendar I and II, we never reject a booking.
         */
        bookings.add(new Interval(startTime, endTime));

        /*
         * STEP 2: Generate all start and end events.
         *
         * We use a local record to represent a coordinate and
         * the corresponding change in active bookings.
         */
        record Event(int time, int delta) {}

        List<Event> events = new ArrayList<>();

        for (Interval booking : bookings) {
            events.add(new Event(booking.start(), 1));
            events.add(new Event(booking.end(), -1));
        }

        /*
         * STEP 3: Sort events by timestamp.
         *
         * For equal timestamps, aggregate their changes before
         * checking the active count.
         *
         * This ensures correct half-open interval behavior.
         */
        events.sort(Comparator.comparingInt(Event::time));

        /*
         * STEP 4: Sweep through sorted events.
         */
        int active = 0;
        int maximum = 0;

        int i = 0;

        while (i < events.size()) {

            int currentTime = events.get(i).time();
            int netChange = 0;

            /*
             * Combine all changes occurring at the same timestamp.
             */
            while (i < events.size()
                    && events.get(i).time() == currentTime) {

                netChange += events.get(i).delta();
                i++;
            }

            active += netChange;
            maximum = Math.max(maximum, active);
        }

        return maximum;
    }
}
```

### Complexity

Let `n` be the number of bookings so far.

- Generating events: `O(n)`.
- Sorting `2n` events: `O(n log n)`.
- Sweeping: `O(n)`.

Therefore:

\\[ \boxed{O(n\log n)\text{ per booking}} \\]

Space:

\\[ \boxed{O(n)} \\]

This solution is correct but does unnecessary sorting on every booking.

The TreeMap solution avoids sorting from scratch because it maintains sorted timestamps incrementally.

# 5. Solution 3 — Dynamic Segment Tree (Advanced)

This is an important alternative because it introduces a more advanced way to maintain maximum overlap.

The coordinate range is:

\\[ [0, 10^9] \\]

We cannot build a normal segment tree over this entire range because it would require too much memory.

Instead, we use a dynamic segment tree.

A dynamic segment tree creates nodes only when needed.

## Core idea

We maintain two values at every segment-tree node:

- `max`: Maximum prefix sum in this segment.
- `sum`: Total sum of all changes in this segment.

Why are these sufficient?

Suppose the left segment has:

```
sum = 2
max = 3
```

And the right segment has:

```
sum = -1
max = 2
```

The maximum prefix sum across the combined segment is:

\\[ \max(left.max,\ left.sum + right.max) \\]

Why?

A prefix of the combined segment is either:

1. Completely inside the left segment.
2. Includes the entire left segment and part of the right segment.

Therefore:

\\[ \boxed{max = \max(left.max,\ left.sum + right.max)} \\]

The total sum is:

\\[ \boxed{sum = left.sum + right.sum} \\]

These two equations let us maintain the global maximum overlap efficiently.

## Java implementation

```java
class MyCalendarThreeSegmentTree {

    /*
     * Coordinate boundaries.
     *
     * The original problem guarantees:
     * 0 <= startTime < endTime <= 10^9.
     *
     * We model the event coordinates using [0, 10^9].
     */
    private static final int MIN = 0;
    private static final int MAX = 1_000_000_000;

    private static class Node {

        /*
         * Maximum prefix sum in this segment.
         *
         * This represents the maximum overlap contribution
         * encountered while sweeping through this segment,
         * assuming the count before the segment is zero.
         */
        int max;

        /*
         * Sum of all event deltas in this segment.
         *
         * This is the net change contributed by the segment.
         */
        int sum;

        Node left;
        Node right;
    }

    private final Node root = new Node();

    public int book(int startTime, int endTime) {

        /*
         * Add +1 at startTime.
         *
         * A booking becomes active at its starting coordinate.
         */
        update(root, MIN, MAX, startTime, 1);

        /*
         * Add -1 at endTime.
         *
         * A booking is no longer active at its ending coordinate.
         */
        update(root, MIN, MAX, endTime, -1);

        /*
         * The root's maximum prefix sum represents the maximum
         * number of simultaneously active bookings.
         */
        return root.max;
    }

    private void update(
            Node node,
            int low,
            int high,
            int index,
            int delta
    ) {

        /*
         * BASE CASE:
         *
         * We have reached the leaf corresponding to index.
         * Apply the event delta.
         */
        if (low == high) {
            node.sum += delta;
            node.max = Math.max(0, node.sum);
            return;
        }

        /*
         * Find the midpoint safely.
         *
         * Using low + (high - low) / 2 avoids integer overflow.
         */
        int mid = low + (high - low) / 2;

        /*
         * Recursively update only the child containing index.
         *
         * Dynamic allocation:
         * We create a node only when an update needs that branch.
         */
        if (index <= mid) {

            if (node.left == null) {
                node.left = new Node();
            }

            update(node.left, low, mid, index, delta);

        } else {

            if (node.right == null) {
                node.right = new Node();
            }

            update(node.right, mid + 1, high, index, delta);
        }

        /*
         * STEP 1: Calculate the total sum of this segment.
         *
         * Missing children represent segments with no event
         * changes, so their sum is zero.
         */
        int leftSum = node.left == null ? 0 : node.left.sum;
        int rightSum = node.right == null ? 0 : node.right.sum;

        node.sum = leftSum + rightSum;

        /*
         * STEP 2: Calculate maximum prefix sum.
         *
         * A maximum prefix is either:
         *
         * 1. Entirely within the left segment.
         * 2. Entire left segment + a prefix of the right segment.
         *
         * Missing children contribute zero.
         */
        int leftMax = node.left == null ? 0 : node.left.max;
        int rightMax = node.right == null ? 0 : node.right.max;

        node.max = Math.max(
                leftMax,
                leftSum + rightMax
        );
    }
}
```

### Complexity

The coordinate range is approximately \\(10^9\\).

Its binary tree height is:

\\[ \log_2(10^9) \approx 30 \\]

Each booking performs two point updates.

Each update visits at most 31 nodes.

Therefore:

\\[ \boxed{O(\log C)\text{ per booking}} \\]

Where `C` is the coordinate range.

More specifically:

\\[ O(2\log C)=O(\log C) \\]

Space complexity:

Each point update creates at most `O(log C)` new nodes.

For `n` bookings:

\\[ \boxed{O(n\log C)} \\]

This is a much more scalable approach when the number of bookings becomes very large.

# 6. Comparing all solutions

| Approach              | Time per booking | Space      | When to use                |
| --------------------- | ---------------- | ---------- | -------------------------- |
| Brute force + sorting | O(n log n)       | O(n)       | Understanding the problem  |
| TreeMap + sweep line  | O(n)             | O(n)       | Best for given constraints |
| Dynamic segment tree  | O(log C)         | O(n log C) | Large number of bookings   |

Here, `n` is the number of bookings and `C` is the coordinate range.

My recommendation in an interview:

Start with the TreeMap sweep-line solution.

It is:

- Easy to explain.
- Easy to implement.
- Efficient for 400 booking operations.
- Naturally handles large coordinates.
- A direct application of the sweep-line pattern.

Then discuss the dynamic segment tree if the interviewer asks how to improve the per-booking complexity for a much larger number of bookings.

# 8. Interviewer follow-up questions

Q1. Why do we use TreeMap instead of HashMap?

Because we need timestamps in sorted order to perform a chronological sweep.

HashMap does not guarantee sorted iteration.

Q2. Why don't we compare every new interval against existing intervals?

Because the answer is not about individual interval pairs.

We need the maximum number of intervals overlapping at any point. Sweep line directly computes this global maximum.

Q3. Why do we add `+1` at the start and `-1` at the end?

Because these represent the changes in the active interval count.

The prefix sum of these changes gives the number of active intervals.

Q4. Why is the TreeMap solution O(n) per booking?

Because there are at most `2n` distinct timestamps after `n` bookings.

We update two TreeMap entries in `O(log n)` each and scan all timestamps in `O(n)`.

Q5. Can we avoid scanning the entire TreeMap after every booking?

Yes.

A segment tree can maintain:

- Total sum of a segment.
- Maximum prefix sum of a segment.

This allows the answer to be retrieved from the root in `O(1)` after each `O(log C)` update.

Q6. Why is coordinate compression not necessary for TreeMap?

TreeMap stores only coordinates that actually occur.

It does not allocate memory proportional to the coordinate range.

Q7. Can we use a PriorityQueue?

A priority queue can help find the maximum number of simultaneous intervals when processing a static collection of intervals sorted by start time.

However, My Calendar III is an online problem: we receive one booking at a time and need an answer immediately after every insertion.

A TreeMap or dynamic segment tree is more suitable.

Q8. What is the relationship between My Calendar I, II, and III?

| Problem         | Main technique                |
| --------------- | ----------------------------- |
| My Calendar I   | BST / interval insertion      |
| My Calendar II  | Overlap tracking / sweep line |
| My Calendar III | Sweep line / segment tree     |

The progression is from preventing overlaps to measuring the maximum overlap.

# 9. Final interview takeaway

Remember this mental model:

```
Interval:
[start, end)

Convert into events:
start -> +1
end   -> -1

Sort timestamps.

Prefix sum:
Active bookings at each timestamp.

Maximum prefix sum:
Maximum simultaneous bookings.
```

The key mathematical relationship is:

\\[ \boxed{ \text{Maximum K-booking} = \max_t \left(\sum\_{x \leq t}\text{delta}(x)\right) } \\]

For this particular problem, I would confidently implement TreeMap + Sweep Line in the interview.

It gives a clean `O(n)` booking operation, uses `O(n)` space, and is more than sufficient for the maximum of 400 calls.
