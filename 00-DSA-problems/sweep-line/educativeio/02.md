# LeetCode 253: Meeting Rooms II — Java 24

Difficulty: Medium Core concepts: Sorting, intervals, sweep line, min-heap (PriorityQueue)

Problem: [Meeting Rooms II on LeetCode](https://leetcode.com/problems/meeting-rooms-ii/description/?utm_source=chatgpt.com)

## 0. Understand the problem in simple terms

You are given an array of meeting intervals. Each interval is represented as:

`[start, end]`

You need to determine the minimum number of meeting rooms required to accommodate every meeting without conflicts.

For example:

```
meetings = [[0, 30], [5, 10], [15, 20]]
```

Visualize the meetings on a timeline:

```
Time:  0     5    10    15    20              30
       |-----Meeting 1-------------------------|
             |Meeting 2|
                        |Meeting 3|
```

- Meeting 1 runs from 0 to 30.
- Meeting 2 runs from 5 to 10.
- Meeting 3 runs from 15 to 20.

Meeting 2 overlaps with Meeting 1, so they need separate rooms. Meeting 3 also overlaps with Meeting 1, but Meeting 2 has already finished.

Therefore, we need 2 meeting rooms.

The key observation is that we don't need to assign a specific room to every meeting. We only need to determine the maximum number of meetings happening simultaneously.

## 1. Clarifying questions to ask the interviewer

1. Can meetings have the same start or end time? Why: This determines how we handle ties when sorting intervals.
2. Can one meeting start exactly when another meeting ends? Why: Under the usual LeetCode convention, a meeting ending at time 10 frees its room for a meeting starting at time 10. We use `end <= start` to recognize that room as available.
3. Can the input be empty? Why: We should know whether to return zero or rely on a non-empty-input constraint.
4. Are the intervals valid, with `start < end`? Why: Zero-length or invalid intervals could require additional rules.
5. Do we need to return only the number of rooms, or the room assignment too? Why: Returning a count is simpler than tracking the actual room assigned to each meeting.

For the solutions below, we assume standard LeetCode constraints: valid intervals, an empty input returns zero, and meetings that touch at an endpoint do not overlap.

## 2. Core intuition: What are we really counting?

Imagine that every meeting occupies one room from its start time until its end time.

If four meetings overlap at the same moment, we need at least four rooms. Conversely, if no more than four meetings ever overlap, four rooms are sufficient.

Thus:

Minimum rooms required = Maximum number of simultaneous meetings.

There are several ways to calculate this:

- Brute force: Count overlaps for each meeting.
- Sweep line: Process all start and end events in chronological order.
- Min-heap: Track the earliest-ending meeting so we can reuse its room as soon as possible.

The min-heap approach is particularly intuitive because it simulates how we would allocate rooms in real life.

## 3. Solution 1 — Brute force

### Idea

For every meeting, count how many meetings overlap it. The largest overlap count gives the number of rooms needed.

Two meetings overlap if:

```
a.start < b.end && b.start < a.end
```

However, there is a subtle issue: simply counting all meetings that overlap a particular meeting does not necessarily find the maximum number of meetings overlapping at the same instant. Two meetings can overlap the target meeting at different times without overlapping each other.

Therefore, a correct brute-force baseline is to examine each distinct meeting start time and count how many meetings are active then.

```java
class Solution {

    public int minMeetingRooms(int[][] intervals) {
        // No meetings means no rooms are required.
        if (intervals == null || intervals.length == 0) {
            return 0;
        }

        int maxRooms = 0;

        // Any maximum number of simultaneous meetings can be observed
        // immediately after one or more meetings start.
        // Therefore, each meeting start is a candidate time to examine.
        for (int[] candidate : intervals) {
            int time = candidate[0];
            int activeRooms = 0;

            for (int[] meeting : intervals) {
                // Meetings are treated as half-open intervals [start, end).
                // A meeting is active at 'time' exactly when:
                // start <= time < end.
                if (meeting[0] <= time && time < meeting[1]) {
                    activeRooms++;
                }
            }

            maxRooms = Math.max(maxRooms, activeRooms);
        }

        return maxRooms;
    }
}
```

Complexity

- Time: \\(O(n^2)\\). There are \\(n\\) candidate start times, and each requires scanning all \\(n\\) meetings.
- Auxiliary space: \\(O(1)\\). We only use a few counters and references; the input is not copied.

This is a correct baseline, but it repeats work for many meetings. We can do much better by processing meetings in chronological order.

## 4. Solution 2 — Sweep line using sorted start and end times

### Core intuition

Instead of examining every meeting separately, track how the number of active meetings changes over time.

- A meeting starting increases the room count by one.
- A meeting ending frees a room.
- The maximum count reached is the answer.

We can sort all start times and all end times independently. We do not need to preserve which start belongs to which end because we only care about the number of occupied rooms.

### Example

```
Meetings: [[0, 30], [5, 10], [15, 20]]

Sorted starts: [0, 5, 15]
Sorted ends:   [10, 20, 30]
```

Process the timeline:

| Event       | Active rooms | Maximum |
| ----------- | ------------ | ------- |
| Start at 0  | 1            | 1       |
| Start at 5  | 2            | 2       |
| End at 10   | 1            | 2       |
| Start at 15 | 2            | 2       |
| End at 20   | 1            | 2       |
| End at 30   | 0            | 2       |

The answer is `2`.

### Java 24 implementation

```java
import java.util.Arrays;

class Solution {

    public int minMeetingRooms(int[][] intervals) {
        if (intervals == null || intervals.length == 0) {
            return 0;
        }

        int n = intervals.length;

        // Separate starts and ends. Once sorted, the two arrays tell us
        // when rooms become occupied and when they become available.
        int[] starts = new int[n];
        int[] ends = new int[n];

        for (int i = 0; i < n; i++) {
            starts[i] = intervals[i][0];
            ends[i] = intervals[i][1];
        }

        Arrays.sort(starts);
        Arrays.sort(ends);

        int startIndex = 0;
        int endIndex = 0;

        int activeRooms = 0;
        int maxRooms = 0;

        // Visit meeting starts in chronological order.
        while (startIndex < n) {

            // If the earliest unfinished meeting ends at or before the
            // next start, its room can be reused.
            //
            // IMPORTANT: <= handles back-to-back meetings correctly.
            // A meeting ending at 10 frees its room for a meeting
            // starting at 10.
            if (starts[startIndex] >= ends[endIndex]) {
                activeRooms--;
                endIndex++;
            } else {
                // The next meeting starts before any remaining meeting
                // ends, so an additional room is necessary.
                activeRooms++;
                maxRooms = Math.max(maxRooms, activeRooms);
                startIndex++;
            }
        }

        return maxRooms;
    }
}
```

### Why does this work?

At each step, we compare the next meeting start with the earliest remaining end time.

- If `start < end`, no meeting has finished yet to free a room, so we need another room.
- If `start >= end`, at least one room is available, so we account for that ending before proceeding.

Complexity

- Time: \\(O(n \log n)\\) because sorting the two arrays dominates the linear sweep.
- Auxiliary space: \\(O(n)\\) for the copied start and end arrays.

This approach is excellent when we care only about the count. The next solution directly models room allocation using a min-heap.

## 5. Solution 3 — Min-heap (priority queue)

This is the approach I would recommend explaining in a coding interview because the data structure maps naturally to the real-world problem.

### Mental model: Always know which room becomes free first

Imagine that each occupied room has a meeting scheduled to finish at some time.

Suppose the current room end times are:

```
Room A: ends at 30
Room B: ends at 10
```

The next meeting starts at time `15`.

Which room should we try to reuse? Room B, because it becomes available first, at time `10`.

A min-heap gives us the earliest end time in \\(O(1)\\) peek time and \\(O(\log n)\\) insertion/removal time.

We don't need to remember the full meeting in the heap; the end time alone is sufficient to determine whether a room is available.

### Step-by-step example

Input:

```
[[0, 30], [5, 10], [15, 20]]
```

First, sort by start time. These meetings are already sorted.

Meeting 1: [0, 30]

Heap before: `[]`

No room is available, so allocate one.

Heap after: `[30]`

Rooms in use: 1

Meeting 2: [5, 10]

Heap before: `[30]`

The earliest end is `30`, which is later than `5`. The existing room is busy, so allocate another.

Heap after: `[10, 30]`

Rooms in use: 2

Meeting 3: [15, 20]

Heap before: `[10, 30]`

The earliest end is `10`, which is less than or equal to `15`. Reuse that room.

Remove `10`, then insert `20`.

Heap after: `[20, 30]`

Rooms in use: 2

The maximum number of rooms needed is `2`.

### Java 24 implementation

```java
import java.util.Arrays;
import java.util.PriorityQueue;

class Solution {

    public int minMeetingRooms(int[][] intervals) {
        if (intervals == null || intervals.length == 0) {
            return 0;
        }

        // Process meetings chronologically. This ensures that, when we
        // encounter a meeting, every earlier-starting meeting is already
        // accounted for in the heap.
        Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0]));

        // The smallest element is always the earliest meeting end.
        // Each heap entry represents one room currently assigned to a
        // meeting; its value is the time when that room becomes free.
        PriorityQueue<Integer> roomEndTimes = new PriorityQueue<>();

        int maxRooms = 0;

        for (int[] meeting : intervals) {
            int start = meeting[0];
            int end = meeting[1];

            // Release rooms that are free by this meeting's start time.
            //
            // Why a while loop?
            // Multiple meetings may have finished before this start.
            // Each of their rooms can be reused, so remove all such
            // end times before deciding whether another room is needed.
            while (!roomEndTimes.isEmpty()
                    && roomEndTimes.peek() <= start) {
                roomEndTimes.poll();
            }

            // The remaining heap entries represent meetings that are
            // still active. If every existing room is busy, inserting
            // this meeting increases the number of rooms required.
            roomEndTimes.offer(end);

            // The heap size is the number of rooms currently occupied.
            // Its maximum over all iterations is the answer.
            maxRooms = Math.max(maxRooms, roomEndTimes.size());
        }

        return maxRooms;
    }
}
```

### Why is the greedy decision correct?

We sort by start time, so every meeting we have already processed starts no later than the current meeting.

Among the meetings occupying rooms, the earliest end time is the first opportunity to reuse a room.

- If that end time is at most the current start, the room is free and can be reused.
- If the earliest end time is later than the current start, every currently occupied room is still busy. The current meeting therefore needs a new room.

Removing all finished meetings before inserting the new one keeps the heap equal to the set of rooms currently occupied.

The maximum heap size is the minimum number of rooms required: whenever the heap reaches size \\(k\\), there are \\(k\\) simultaneous meetings requiring \\(k\\) distinct rooms. Conversely, the algorithm reuses every room that is available, so it does not create unnecessary rooms.

### Complexity analysis

Let \\(n\\) be the number of meetings.

- Sorting: \\(O(n \log n)\\).
- Heap operations: Each meeting is inserted once and removed at most once, giving \\(O(n \log n)\\) total heap work.
- Total time: \\(O(n \log n)\\).
- Auxiliary space: \\(O(n)\\) for the heap in the worst case. Java's object-array sorting may also use temporary storage; the interval array itself is sorted in place.

One subtle advantage: the heap solution can be extended to return actual room assignments, while the two-pointer solution only calculates the required count.

## 6. Solution 4 — Sweep line using events

This is another way to implement the same maximum-overlap idea.

For every meeting `[start, end]`, create two events:

- `(start, +1)`: a meeting begins.
- `(end, -1)`: a meeting ends.

Sort the events by time. If events share a timestamp, process end events before start events because a room can be reused at the exact ending time.

### Java 24 implementation

```java
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

class Solution {

    // A record is a concise, immutable data carrier in modern Java.
    private record Event(int time, int delta) {}

    public int minMeetingRooms(int[][] intervals) {
        if (intervals == null || intervals.length == 0) {
            return 0;
        }

        List<Event> events = new ArrayList<>(2 * intervals.length);

        for (int[] meeting : intervals) {
            // Starting a meeting occupies one additional room.
            events.add(new Event(meeting[0], +1));

            // Ending a meeting frees one room.
            events.add(new Event(meeting[1], -1));
        }

        // Sort chronologically. At equal timestamps, -1 comes before +1
        // so a meeting ending at t releases its room before another
        // meeting starting at t needs it.
        events.sort(
            Comparator.comparingInt(Event::time)
                      .thenComparingInt(Event::delta)
        );

        int activeRooms = 0;
        int maxRooms = 0;

        for (Event event : events) {
            activeRooms += event.delta();

            // The highest occupancy at any point is the answer.
            maxRooms = Math.max(maxRooms, activeRooms);
        }

        return maxRooms;
    }
}
```

Complexity

- Time: \\(O(n \log n)\\) for sorting \\(2n\\) events.
- Auxiliary space: \\(O(n)\\) for the event list.

This approach is useful when you want to understand the sweep-line pattern for other interval problems, such as maximum concurrent users or peak resource usage.

## 7. Comparison of all approaches

| Approach                         | Time              | Auxiliary space | Best use                          |
| -------------------------------- | ----------------- | --------------- | --------------------------------- |
| Brute force                      | \\(O(n^2)\\)      | \\(O(1)\\)      | Understanding the problem         |
| Two sorted arrays / two pointers | \\(O(n \log n)\\) | \\(O(n)\\)      | Efficient count only              |
| Min-heap                         | \\(O(n \log n)\\) | \\(O(n)\\)      | Room allocation and extensions    |
| Sweep-line events                | \\(O(n \log n)\\) | \\(O(n)\\)      | General event-processing problems |

For this problem, I would choose the min-heap solution in an interview. It directly represents occupied rooms and is easy to extend if the interviewer asks you to assign actual room numbers.

## 8. Edge cases to test

| Input                        | Expected | Reason                                       |
| ---------------------------- | -------- | -------------------------------------------- |
| `[]`                         | `0`      | No meetings                                  |
| `[[1, 5]]`                   | `1`      | A single meeting                             |
| `[[1, 5], [5, 8]]`           | `1`      | Back-to-back meetings                        |
| `[[1, 10], [2, 3], [4, 5]]`  | `2`      | One long meeting overlaps each short meeting |
| `[[1, 5], [1, 5], [1, 5]]`   | `3`      | Three identical overlapping meetings         |
| `[[2, 4], [7, 9], [12, 15]]` | `1`      | Completely separate meetings                 |

The most important boundary condition is:

```
roomEndTimes.peek() <= start
```

Using `<` instead of `<=` would incorrectly treat back-to-back meetings as overlapping.

Also, do not compare only the current meeting with the immediately preceding meeting. For example, `[1, 10]`, `[2, 3]`, and `[4, 5]` require two rooms even though the last two short meetings do not overlap each other.

## 9. Interviewer follow-up questions

Q1. Why use a min-heap rather than a max-heap?

We need the room that becomes available earliest. A min-heap exposes the smallest end time at its root. A max-heap would give the latest end time, which does not help us reuse rooms efficiently.

Q2. Why do we sort meetings by start time?

It guarantees that we process meetings in chronological order. Without this, a later meeting might be processed before an earlier one, making room-reuse decisions unreliable.

Q3. Can we solve this without a heap?

Yes. Sort the start times and end times independently and use two pointers. This gives \\(O(n \log n)\\) time and \\(O(n)\\) auxiliary space, and is often the simplest solution when only the count is required.

Q4. Can we return the room assigned to every meeting?

Yes. Store `(endTime, roomId)` pairs in a min-heap. Maintain another min-heap of available room IDs, or use a reusable room ID when a meeting finishes. When processing each meeting, release rooms whose end times are at most its start time, assign an available room if possible, and otherwise allocate a new room. Record the assigned room against the meeting's original index.

Q5. What if the meetings arrive in real time rather than as a complete array?

If meetings arrive in arbitrary order, you cannot finalize the optimal room count without knowing whether earlier-starting meetings will arrive later. If meetings arrive in nondecreasing start-time order, the min-heap approach can process them incrementally, maintaining the current occupancy and maximum room count.

Q6. Why is the answer the maximum heap size, not the sum of heap sizes?

The heap represents rooms occupied at one point in the iteration. Each meeting is inserted once, and rooms are removed when their meetings finish. The maximum occupancy is the number of rooms needed concurrently; adding heap sizes would count the same room repeatedly across different times.

## 10. Final interview takeaway

Remember this mental model:

1. Sort meetings by start time.
2. Track the earliest room availability using a min-heap of end times.
3. Free every room whose meeting ends at or before the next meeting's start.
4. Add the new meeting's end time.
5. Keep the maximum heap size.

The central insight is that the number of rooms needed is determined by peak simultaneous occupancy, not by the total number of meetings. The min-heap makes that peak easy to track while naturally modeling room reuse.&#x20;

# Meeting Rooms II — Clean Java 24 Solutions Using Records

Both approaches use the same core idea: the minimum number of meeting rooms equals the maximum number of meetings happening simultaneously.

Below are two clean implementations with meaningful names, Java records, and detailed inline comments explaining the reasoning, correctness, edge cases, and complexity.

## 1. Sweep line using `Event` record

This approach represents every meeting as two events:

- Meeting starts → `+1` active meeting.
- Meeting ends → `-1` active meeting.

Sort the events by time. When two events occur at the same time, process the ending event first, because its room can be reused immediately.

```
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

class Solution {

    /*
     * Each event represents a change in the number of active meetings.
     *
     * time:
     *   The timestamp at which the event occurs.
     *
     * roomChange:
     *   +1 means a meeting starts and occupies a room.
     *   -1 means a meeting ends and frees a room.
     *
     * A record is appropriate here because an event is a simple,
     * immutable data carrier. Java automatically provides its
     * constructor, accessors, equals(), hashCode(), and toString().
     */
    private record Event(int time, int roomChange) {}

    public int minMeetingRooms(int[][] intervals) {

        // An empty schedule needs no meeting rooms.
        // This guard also prevents accessing intervals[0] unnecessarily.
        if (intervals == null || intervals.length == 0) {
            return 0;
        }

        /*
         * Every meeting contributes exactly two events:
         *   1. One start event.
         *   2. One end event.
         *
         * Therefore, there will be exactly 2 * n events for n meetings.
         * Providing the initial capacity avoids unnecessary list resizing.
         */
        List<Event> events = new ArrayList<>(2 * intervals.length);

        for (int[] interval : intervals) {
            int startTime = interval[0];
            int endTime = interval[1];

            // A meeting starting increases simultaneous room usage by one.
            events.add(new Event(startTime, +1));

            // A meeting ending decreases simultaneous room usage by one.
            events.add(new Event(endTime, -1));
        }

        /*
         * Sort events chronologically.
         *
         * First comparator:
         *   Earlier timestamps must be processed first.
         *
         * Second comparator:
         *   When timestamps are equal, sort by roomChange ascending.
         *   Since -1 < +1, ending events are processed before starting
         *   events at the same timestamp.
         *
         * Example:
         *   Meetings [1, 5] and [5, 8] need only ONE room.
         *   At time 5, the first meeting ends before the second begins.
         *
         * This tie-breaking rule implements the half-open interval
         * convention [startTime, endTime).
         */
        events.sort(
            Comparator.comparingInt(Event::time)
                      .thenComparingInt(Event::roomChange)
        );

        // Number of meetings currently occupying rooms as we sweep time.
        int activeMeetings = 0;

        // Maximum simultaneous meetings observed so far.
        // This is the minimum number of rooms needed for the full schedule.
        int maximumRoomsRequired = 0;

        /*
         * Process every event in chronological order.
         *
         * We do not need to assign actual room IDs. We only track how
         * many meetings are active at each event.
         */
        for (Event event : events) {

            // Apply the event:
            // +1 for a start, -1 for an end.
            activeMeetings += event.roomChange();

            /*
             * Every active meeting needs a separate room.
             *
             * If four meetings are simultaneously active, at least four
             * rooms are necessary. Conversely, if the active count never
             * exceeds four, four rooms are sufficient.
             */
            maximumRoomsRequired = Math.max(
                maximumRoomsRequired,
                activeMeetings
            );
        }

        return maximumRoomsRequired;
    }
}
```

### Example walkthrough

Input:

```
intervals = [[0, 30], [5, 10], [15, 20]]
```

Sorted events:

```
(0,  +1)
(5,  +1)
(10, -1)
(15, +1)
(20, -1)
(30, -1)
```

| Event      | Active meetings | Maximum rooms |
| ---------- | --------------- | ------------- |
| `(0, +1)`  | 1               | 1             |
| `(5, +1)`  | 2               | 2             |
| `(10, -1)` | 1               | 2             |
| `(15, +1)` | 2               | 2             |
| `(20, -1)` | 1               | 2             |
| `(30, -1)` | 0               | 2             |

The result is `2`.

### Complexity

- Time: \\(O(n\log n)\\). We create \\(2n\\) events and sort them, taking \\(O(n\log n)\\) time. Processing the events takes \\(O(n)\\).
- Auxiliary space: \\(O(n)\\). The event list stores \\(2n\\) records.

## 2. Min-heap using `Meeting` and `Room` records

This approach models room allocation more directly.

The key idea is to maintain a min-heap of meeting end times. The earliest-ending meeting is always at the top, so we can quickly determine whether a room is available.

We can use records for both the meeting representation and the room's availability information.

```
import java.util.Arrays;
import java.util.PriorityQueue;

class Solution {

    /*
     * Represents one meeting with its start and end timestamps.
     *
     * Keeping these values together makes the code more readable than
     * repeatedly accessing interval[0] and interval[1].
     */
    private record Meeting(int startTime, int endTime) {}

    /*
     * Represents the time at which an allocated room becomes available.
     *
     * We store one Room record for each currently occupied room.
     * The record contains the end time of the meeting using that room.
     *
     * A record is useful because this value is immutable: once inserted,
     * the room's availability time does not change.
     */
    private record Room(int availableAt) {}

    public int minMeetingRooms(int[][] intervals) {

        // No meetings means no rooms are needed.
        if (intervals == null || intervals.length == 0) {
            return 0;
        }

        /*
         * Convert the input arrays into meaningful Meeting records.
         *
         * We create a separate array instead of sorting the caller's
         * input directly, so the original intervals remain unchanged.
         *
         * The conversion takes O(n) time and O(n) additional space.
         */
        Meeting[] meetings = Arrays.stream(intervals)
            .map(interval -> new Meeting(interval[0], interval[1]))
            .toArray(Meeting[]::new);

        /*
         * Meetings must be processed in nondecreasing start-time order.
         *
         * Why?
         * When processing a meeting, all meetings that start earlier
         * have already been considered. This makes it safe to reuse a
         * room whose previous meeting has already ended.
         *
         * Integer.compare avoids the potential integer overflow that
         * can occur with subtraction-based comparators.
         */
        Arrays.sort(
            meetings,
            Comparator.comparingInt(Meeting::startTime)
        );

        /*
         * The priority queue is a min-heap ordered by availability time.
         *
         * roomAvailability.peek() returns the room that becomes free
         * earliest.
         *
         * Invariant:
         * Every entry represents a room currently assigned to a meeting
         * that has not yet been released while processing the current
         * meeting.
         */
        PriorityQueue<Room> roomAvailability = new PriorityQueue<>(
            Comparator.comparingInt(Room::availableAt)
        );

        // Track the maximum number of simultaneously occupied rooms.
        int maximumRoomsRequired = 0;

        for (Meeting meeting : meetings) {
            int startTime = meeting.startTime();
            int endTime = meeting.endTime();

            /*
             * Release all rooms whose meetings have ended by this
             * meeting's start time.
             *
             * Why <= instead of <?
             * A room becomes reusable at the exact moment its meeting
             * ends. For example, [1, 5] and [5, 8] can share one room.
             *
             * Why while instead of if?
             * Several meetings may have ended before this meeting starts.
             * We must remove every finished meeting, not just one.
             */
            while (!roomAvailability.isEmpty()
                    && roomAvailability.peek().availableAt() <= startTime) {
                roomAvailability.poll();
            }

            /*
             * Now every room remaining in the heap is occupied by a
             * meeting that overlaps the current meeting's start.
             *
             * Insert the current meeting's end time to reserve a room
             * until this meeting finishes.
             *
             * If a room was freed above, its heap entry was removed and
             * this insertion represents reusing that room. We only need
             * the number of rooms, not their actual identities.
             */
            roomAvailability.offer(new Room(endTime));

            /*
             * The heap size now equals the number of rooms required by
             * the meetings processed so far at this point in time.
             *
             * Its maximum is the answer.
             *
             * We do not simply return the final heap size because rooms
             * may become free later. The maximum heap size records the
             * peak occupancy across the entire schedule.
             */
            maximumRoomsRequired = Math.max(
                maximumRoomsRequired,
                roomAvailability.size()
            );
        }

        return maximumRoomsRequired;
    }
}
```

### Why the heap approach works

Consider:

```
Meetings = [[0, 30], [5, 10], [15, 20]]
```

| Meeting processed | Rooms released    | Heap after insertion | Maximum |
| ----------------- | ----------------- | -------------------- | ------- |
| `[0, 30]`         | None              | `[30]`               | 1       |
| `[5, 10]`         | None              | `[10, 30]`           | 2       |
| `[15, 20]`        | Room ending at 10 | `[20, 30]`           | 2       |

When `[15, 20]` begins, the earliest-ending room is available at time `10`. We remove it and reuse the room for the new meeting.

The heap stores only the meetings still occupying rooms, not every meeting that has ever been processed.

### Complexity

- Time: \\(O(n\log n)\\). Sorting takes \\(O(n\log n)\\), and each meeting is inserted once and removed at most once from the heap. Each heap operation takes \\(O(\log n)\\).
- Auxiliary space: \\(O(n)\\) for the `Meeting` array and the priority queue in the worst case.

## 3. Which version should you use?

| Consideration                 | Sweep line                    | Min-heap                       |
| ----------------------------- | ----------------------------- | ------------------------------ |
| Main idea                     | Count start/end events        | Reuse the earliest-ending room |
| Records used                  | `Event`                       | `Meeting`, `Room`              |
| Tracks actual room allocation | No                            | Not in this version            |
| Time complexity               | \\(O(n\log n)\\)              | \\(O(n\log n)\\)               |
| Best conceptual fit           | Maximum simultaneous meetings | Room scheduling and reuse      |

Interview recommendation: Present the min-heap approach first if the interviewer emphasizes room allocation. Present the sweep-line approach if the interviewer asks for the maximum number of overlapping intervals or simultaneous resources.

One final Java detail: each implementation must be submitted as its own `Solution` class. You cannot put both classes named `Solution` in the same Java source file.
