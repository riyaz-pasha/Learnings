# LeetCode 2021 — Brightest Position on Street

Difficulty: Medium Pattern: Sweep Line + Difference Events + Prefix Sum

The key insight is that we do not need to calculate the brightness at every integer position on the street. Instead, we only need to examine positions where the brightness can change.

## 0. Simplify the problem statement

You are given an array `lights`, where each light is represented as:

`lights[i] = [position, range]`

- `position` is where the light is installed.
- `range` is how far the light shines in both directions.
- Every position within that range, including both endpoints, receives brightness `1` from that light.

For each light, the illuminated interval is:

\\[ [\text{position}-\text{range},\ \text{position}+\text{range}] \\]

Your task is to return the smallest position with the maximum total brightness.

### Example

Input:

```
int[][] lights = {
    {2, 1},
    {5, 1},
    {4, 1}
};
```

The lights cover these intervals:

- Light 1: `[1, 3]`
- Light 2: `[4, 6]`
- Light 3: `[3, 5]`

Brightness at each relevant position:

| Position | Active lights | Brightness |
| -------- | ------------- | ---------- |
| 1        | Light 1       | 1          |
| 2        | Light 1       | 1          |
| 3        | Lights 1, 3   | 2          |
| 4        | Lights 2, 3   | 2          |
| 5        | Lights 2, 3   | 2          |
| 6        | Light 2       | 1          |

The maximum brightness is `2`, achieved at positions `3`, `4`, and `5`.

The answer is `3`, because we must return the smallest position among those with maximum brightness.

## 1. Clarifying questions to ask the interviewer

These questions help establish the exact behavior before choosing the algorithm.

1. Are the light intervals inclusive? The statement says yes: both `position - range` and `position + range` are illuminated. This matters when two lights meet at an endpoint.
2. What should happen when multiple positions have equal maximum brightness? Return the smallest coordinate, so we must process coordinates in ascending order and update our answer only when brightness strictly increases.
3. Can coordinates be negative, and how large can they be? Yes, coordinates may be negative and large. We should use `long` for intermediate calculations such as `position - range` and `position + range + 1` to avoid integer overflow.
4. Can the input be empty? The standard LeetCode constraints guarantee at least one light. If we want a defensive implementation, we should agree on what to return for empty input.

## 2. Core intuition: Sweep Line

Imagine walking along the street from left to right. Instead of repeatedly counting every light at every position, keep track of how many lights are currently illuminating the street.

A light covering `[left, right]` causes two changes:

- At `left`, brightness increases by `1`.
- At `right + 1`, brightness decreases by `1`.

Why `right + 1`? Because the right endpoint is illuminated, and the decrease must happen only after that endpoint. This converts an inclusive interval into two difference events.&#x20;

Consider one light covering `[1, 3]`.

```

Brightness:     0   1   1   1   0   0
                    +1          -1
Event:              start       end + 1
```

Now add a second light covering `[3, 5]`.

```
Coordinate:     0   1   2   3   4   5   6
Brightness:     0   1   1   2   1   1   0
                    +1      +1          -1
                                -1
```

At coordinate `3`, both lights illuminate the street, so the brightness is `2`.

The running brightness is simply the sum of all event changes encountered so far.

### Why this works

Between two consecutive event coordinates, no light starts or stops. Therefore, brightness remains constant throughout that segment.

We only need to evaluate the brightness at each event coordinate, rather than iterate over every possible integer coordinate. Since there are at most two events per light, sorting and processing the events takes \\(O(n\log n)\\) time.

### Solution 1: Brute force — check every candidate left endpoint

A straightforward approach is to try the left endpoint of every light's interval as a candidate answer.

Why is this sufficient? Brightness can increase only when a light starts illuminating a position. Therefore, the leftmost position attaining the global maximum must be a left endpoint of at least one light.

For each candidate, count how many lights cover it. Keep the candidate with the highest brightness, breaking ties by choosing the smaller coordinate.

```java
class Solution {

    public int brightestPosition(int[][] lights) {
        // Every left endpoint is a candidate for the leftmost maximum.
        // Why? Brightness can only increase when a light starts.
        // If the maximum starts on a plateau, its first coordinate is
        // the left endpoint where the brightness increased to that maximum.

        long bestPosition = 0;
        int maxBrightness = -1;

        for (int[] candidateLight : lights) {
            // Use long for safe endpoint arithmetic.
            long candidate = (long) candidateLight[0]
                           - candidateLight[1];

            int brightness = 0;

            // Count every light illuminating this candidate coordinate.
            for (int[] light : lights) {
                long left = (long) light[0] - light[1];
                long right = (long) light[0] + light[1];

                if (left <= candidate && candidate <= right) {
                    brightness++;
                }
            }

            // Strictly greater preserves the earliest candidate on ties
            // only if candidates are visited in ascending order.
            // Here they are NOT guaranteed to be sorted, so explicitly
            // compare positions when brightness is equal.
            if (brightness > maxBrightness
                    || (brightness == maxBrightness
                        && candidate < bestPosition)) {
                maxBrightness = brightness;
                bestPosition = candidate;
            }
        }

        // Under the stated LeetCode constraints, the answer fits in int.
        return (int) bestPosition;
    }
}
```

Complexity analysis

- Time: \\(O(n^2)\\). We evaluate at most \\(n\\) candidate endpoints and scan all \\(n\\) lights for each candidate.
- Auxiliary space: \\(O(1)\\). We only maintain a few variables.
- Limitation: This is a useful starting point for understanding the problem, but it is too slow for \\(n=10^5\\).

### Solution 2: Sweep line using a `TreeMap` — optimal

The brute-force approach repeatedly recounts the same lights. We can avoid that by recording only where brightness changes.

For every light `[position, range]`, calculate:

\\[ left = position - range \\]

\\[ right = position + range \\]

Store two events:

\\[ events[left] \mathrel{+}=1 \\]

\\[ events[right+1] \mathrel{-}=1 \\]

A `TreeMap` automatically stores event coordinates in ascending order. If several lights produce events at the same coordinate, their deltas are combined.

```java
import java.util.TreeMap;

class Solution {

    public int brightestPosition(int[][] lights) {
        // Key   = street coordinate where brightness changes.
        // Value = net brightness change at that coordinate.
        //
        // TreeMap keeps keys sorted, allowing us to sweep from left to right.
        // Combining equal coordinates is important: multiple lights may
        // start or end at exactly the same coordinate.
        TreeMap<Long, Integer> events = new TreeMap<>();

        for (int[] light : lights) {
            long position = light[0];
            long range = light[1];

            long left = position - range;
            long afterRight = position + range + 1L;

            // The light begins contributing at its inclusive left endpoint.
            events.merge(left, 1, Integer::sum);

            // The light stops contributing immediately AFTER its inclusive
            // right endpoint. The +1 is correct because coordinates are
            // integers and both original interval endpoints are illuminated.
            events.merge(afterRight, -1, Integer::sum);
        }

        int currentBrightness = 0;
        int maxBrightness = -1;
        long answer = 0;

        // Entries are visited in ascending coordinate order.
        for (var event : events.entrySet()) {
            long coordinate = event.getKey();
            int delta = event.getValue();

            // Apply all net changes at this coordinate.
            // The resulting count is the brightness at this coordinate.
            currentBrightness += delta;

            // Update only when brightness strictly increases.
            // Since coordinates are processed from left to right, the first
            // position reaching a brightness level is the smallest one.
            // Keeping the existing answer on ties gives the leftmost maximum.
            if (currentBrightness > maxBrightness) {
                maxBrightness = currentBrightness;
                answer = coordinate;
            }
        }

        // The official constraints guarantee that the answer fits in int.
        return (int) answer;
    }
}
```

Complexity analysis

Let \\(n\\) be the number of lights and \\(m\\) the number of distinct event coordinates, where \\(m \leq 2n\\).

- Building the map: Each of the \\(2n\\) event insertions or updates takes \\(O(\log m)\\), so this phase takes \\(O(n\log n)\\).
- Sweeping the events: There are \\(m\\) distinct coordinates, and each map entry is visited once. This takes \\(O(m)\\), or \\(O(n)\\).
- Total time: \\(O(n\log n)\\), dominated by ordered-map operations.
- Auxiliary space: \\(O(n)\\), since there are at most \\(2n\\) distinct event coordinates.

The `TreeMap` solution is optimal in asymptotic time for this general comparison-based event-sorting approach.

### Solution 3: Sweep line using an event array and sorting

Instead of a `TreeMap`, we can store all \\(2n\\) events in an array and sort them. This avoids the per-insertion tree overhead and is often the preferred interview implementation.

```java
import java.util.Arrays;
import java.util.Comparator;

class Solution {

    // Immutable event: coordinate where brightness changes and its delta.
    private record Event(long coordinate, int delta) {}

    public int brightestPosition(int[][] lights) {
        int n = lights.length;

        Event[] events = new Event[2 * n];

        for (int i = 0; i < n; i++) {
            long position = lights[i][0];
            long range = lights[i][1];

            long left = position - range;
            long afterRight = position + range + 1L;

            // Inclusive interval [left, right] becomes:
            // +1 at left and -1 at right + 1.
            events[2 * i] = new Event(left, 1);
            events[2 * i + 1] = new Event(afterRight, -1);
        }

        // Sorting by coordinate places all events at a shared coordinate
        // next to each other. Their deltas can then be accumulated together.
        Arrays.sort(events, Comparator.comparingLong(Event::coordinate));

        int currentBrightness = 0;
        int maxBrightness = -1;
        long answer = 0;

        int i = 0;

        while (i < events.length) {
            long coordinate = events[i].coordinate();

            // Combine ALL events at this coordinate before measuring
            // brightness. This handles simultaneous starts and endings.
            //
            // Because we used right + 1 for endings, a light ending at
            // coordinate x contributes through x - 1, not at x.
            while (i < events.length
                    && events[i].coordinate() == coordinate) {
                currentBrightness += events[i].delta();
                i++;
            }

            // Brightness is constant from this event coordinate until the
            // next event coordinate - 1. Therefore, this coordinate is the
            // earliest position in that segment and is the only one we need
            // to consider when looking for the leftmost maximum.
            if (currentBrightness > maxBrightness) {
                maxBrightness = currentBrightness;
                answer = coordinate;
            }
        }

        return (int) answer;
    }
}
```

Complexity analysis

- Building events: \\(O(n)\\), creating exactly two events per light.
- Sorting: \\(O(n\log n)\\), sorting \\(2n\\) events.
- Sweeping: \\(O(n)\\), since each event is processed once.
- Total time: \\(O(n\log n)\\).
- Auxiliary space: \\(O(n)\\) for the event array, excluding implementation-dependent sorting workspace.

Recommendation: Use Solution 3 in an interview. It expresses the sweep-line idea directly, uses modern Java records for event modeling, and has a predictable \\(O(n\log n)\\) time bound.

## 5. Edge cases to watch out for

| Case                              | Example                    | Expected result | Why it matters                                                      |
| --------------------------------- | -------------------------- | --------------- | ------------------------------------------------------------------- |
| One light                         | `[[1, 2]]`                 | `-1`            | The leftmost illuminated point is the interval's left endpoint.     |
| Zero range                        | `[[5, 0]]`                 | `5`             | A light illuminates exactly one coordinate.                         |
| Negative coordinates              | `[[-3, 2]]`                | `-5`            | Coordinates can be negative.                                        |
| Overlapping intervals             | `[[1, 1], [3, 2]]`         | `1`             | Positions `1` and `2` both have brightness `2`; return the smaller. |
| Equal maximum over a long segment | `[[1, 3]]`                 | `-2`            | Every point from `-2` to `4` has brightness `1`.                    |
| Identical lights                  | `[[2, 1], [2, 1]]`         | `1`             | Both lights contribute to the same interval.                        |
| Intervals touching at one point   | `[[1, 2], [5, 2]]`         | `3`             | Both lights illuminate coordinate `3`.                              |
| Large coordinates                 | `[[100000000, 100000000]]` | `0`             | Intermediate arithmetic should use `long`.                          |

One important correction to remember: in the sweep-line solutions, we use `right + 1` rather than `right` for the ending event. That means all lights covering an integer coordinate are counted correctly, including at the inclusive right endpoint.

## 6. Interviewer follow-up questions and answers

### Q1. Why is the left endpoint enough in the brute-force solution?

Brightness changes only when an interval starts or ends. Using the difference-event representation, a positive increase can occur only at a left endpoint. The earliest coordinate where the global maximum is achieved must therefore be among the light start coordinates.

### Q2. Why not simply use an array as a difference array?

The coordinates may be negative and have a very large range. Allocating an array indexed by the entire coordinate range could require billions of entries. An ordered map or a sorted event array stores only the \\(O(n)\\) coordinates where brightness changes.

### Q3. Why do we combine events at the same coordinate?

Several lights may start or stop contributing at the same coordinate. We must apply all their changes before evaluating brightness at that coordinate. Otherwise, the intermediate count could incorrectly represent the number of active lights.

### Q4. Can we remove the `+1` from the right endpoint?

Yes, but we would need to change how simultaneous starts and endings are processed. With inclusive intervals, starts must be counted before ends at the same coordinate. Using `right + 1` simplifies the implementation because every event is a change to the brightness beginning at that integer coordinate.

### Q5. What if coordinates and ranges are floating-point values?

The `right + 1` trick no longer applies. We would instead use events at the exact left and right endpoints and carefully process starts before endings at the same coordinate, respecting the inclusive interval semantics. Exact comparisons may require special consideration if coordinates are floating-point values.

### Q6. What if the interviewer asks for the entire brightest segment?

Keep track of each constant-brightness segment between consecutive event coordinates. When a segment has brightness equal to the maximum, record its start and end; if a later segment exceeds the previous maximum, discard the earlier segments and begin a new collection. Adjacent segments with the same maximum brightness can be merged.

### Q7. What if lights are added or removed dynamically?

A basic sweep-line solution must be rebuilt after updates. For frequent online updates and queries, consider a segment tree with lazy propagation if the coordinate domain can be compressed or otherwise represented efficiently. The right design depends on whether queries ask for the global maximum, a point's brightness, or a range's brightness.

## Final interview summary

- Brute force: Check each light's left endpoint against every light. \\(O(n^2)\\) time, \\(O(1)\\) auxiliary space.
- Ordered map: Aggregate brightness changes by coordinate and sweep in sorted order. \\(O(n\log n)\\) time, \\(O(n)\\) space.
- Sorted event array: Create two events per light, sort, aggregate changes at equal coordinates, and sweep. \\(O(n\log n)\\) time, \\(O(n)\\) space.

The main insight is to convert every light interval into two events and track cumulative brightness. The `right + 1` convention handles inclusive endpoints cleanly, while updating the answer only when brightness strictly increases guarantees the smallest coordinate wins ties.

# LeetCode 2021 — Brightest Position on Street

Both implementations use the sweep-line algorithm. The difference is how they maintain events in sorted order:

- Solution 1: `Event[]` + sorting. We explicitly create events and sort them.
- Solution 2: `TreeMap`. The map automatically sorts coordinates and combines changes at identical coordinates.

The following versions include the intuition, correctness reasoning, edge cases, and detailed time and space complexity directly in the code comments.

## Solution 1: Event array + sorting

```java
import java.util.Arrays;
import java.util.Comparator;

class Solution {

    /*
     * CORE IDEA: SWEEP LINE + DIFFERENCE EVENTS
     *
     * Each light is represented by:
     *     lights[i] = [position, range]
     *
     * It illuminates the inclusive interval:
     *     [position - range, position + range]
     *
     * A naive solution would calculate the brightness at every street
     * coordinate. That is inefficient because coordinates can be very large.
     *
     * Instead, brightness changes only at specific coordinates:
     *
     *     left       -> brightness increases by 1
     *     right + 1  -> brightness decreases by 1
     *
     * Why right + 1?
     * The interval is inclusive, so the light must illuminate `right`.
     * Its contribution must disappear only at the next integer coordinate.
     *
     * Example:
     *     Light interval = [2, 5]
     *
     *     Event at 2:  +1
     *     Event at 6:  -1
     *
     *     Coordinates 2, 3, 4 and 5 receive this light's contribution.
     *
     * Once all events are sorted, we sweep from left to right and maintain
     * the cumulative brightness. This cumulative sum equals the number of
     * lights illuminating the current coordinate.
     *
     * WHY USE A RECORD?
     * Event is an immutable data carrier. It keeps the coordinate and its
     * brightness change together, making the event array easy to understand.
     */
    private record Event(long coordinate, int delta) {}

    public int brightestPosition(int[][] lights) {

        int n = lights.length;

        /*
         * Every light creates exactly two events:
         *
         *     1. Start event: left endpoint, delta = +1
         *     2. End event:   right endpoint + 1, delta = -1
         *
         * Therefore, for n lights, we need exactly 2 * n events.
         *
         * We use long for event coordinates because calculating
         * position + range + 1 can exceed the int range in general.
         *
         * The problem's final answer fits in int, but intermediate
         * calculations should still use long to prevent overflow.
         */
        Event[] events = new Event[2 * n];

        for (int i = 0; i < n; i++) {

            // Convert the input values to long BEFORE arithmetic.
            // This ensures subtraction and addition use 64-bit arithmetic.
            long position = lights[i][0];
            long range = lights[i][1];

            long left = position - range;
            long right = position + range;

            /*
             * Convert this inclusive interval into two events.
             *
             * Example: position = 4, range = 2
             *
             *     left  = 2
             *     right = 6
             *
             *     Event(2, +1)
             *     Event(7, -1)
             *
             * The running brightness increases at 2 and decreases at 7.
             * Therefore, this light contributes at coordinates 2 through 6.
             */
            events[2 * i] = new Event(left, +1);
            events[2 * i + 1] = new Event(right + 1L, -1);
        }

        /*
         * Sort all events by their coordinate in ascending order.
         *
         * Why?
         * We must process brightness changes in the order in which we
         * encounter them while moving from left to right along the street.
         *
         * Events with the same coordinate become adjacent after sorting.
         * We will process all such events together before measuring brightness.
         *
         * Comparator.comparingLong avoids narrowing coordinates to int.
         */
        Arrays.sort(
            events,
            Comparator.comparingLong(Event::coordinate)
        );

        /*
         * currentBrightness:
         *     The total number of active lights at the coordinate currently
         *     being processed.
         *
         * maxBrightness:
         *     The greatest brightness seen so far.
         *
         * answer:
         *     The leftmost coordinate at which maxBrightness is achieved.
         *
         * Initially, maxBrightness = -1 because brightness cannot be negative.
         * This ensures that the first valid event coordinate establishes
         * the initial answer, even if there is only one light.
         */
        int currentBrightness = 0;
        int maxBrightness = -1;
        long answer = 0;

        int i = 0;

        while (i < events.length) {

            // The next coordinate at which at least one brightness change
            // occurs. Since events are sorted, coordinates never decrease.
            long coordinate = events[i].coordinate();

            /*
             * IMPORTANT: PROCESS ALL EVENTS AT THE SAME COORDINATE.
             *
             * Multiple lights may start or stop contributing at the same
             * coordinate. Their net effect must be applied before we inspect
             * the brightness at that coordinate.
             *
             * Example:
             *     Event(5, +1)
             *     Event(5, +1)
             *     Event(5, -1)
             *
             * Net change at coordinate 5 = +1.
             *
             * We accumulate all three deltas, so the brightness measured
             * at 5 is the correct total.
             */
            while (i < events.length
                    && events[i].coordinate() == coordinate) {

                currentBrightness += events[i].delta();
                i++;
            }

            /*
             * WHY IS currentBrightness CORRECT HERE?
             *
             * We have processed every event at this coordinate.
             * Each light contributes +1 at its left endpoint and -1 just
             * after its right endpoint.
             *
             * Consequently, the cumulative sum equals the number of lights
             * illuminating this coordinate.
             *
             * Brightness remains constant until the next event coordinate.
             * Therefore, checking the current coordinate is enough: if this
             * segment has the maximum brightness, its leftmost coordinate
             * is the first event coordinate of that segment.
             */

            /*
             * WHY USE STRICTLY GREATER THAN (>) INSTEAD OF >=?
             *
             * We process coordinates in ascending order.
             *
             * If a coordinate has brightness greater than every previous
             * coordinate, it becomes the new answer.
             *
             * If a later coordinate has the SAME maximum brightness, we
             * must preserve the earlier answer because the problem requests
             * the smallest coordinate among all maximum-brightness positions.
             *
             * Example:
             *     Position 3 -> brightness 4
             *     Position 5 -> brightness 4
             *
             * The answer must remain 3.
             */
            if (currentBrightness > maxBrightness) {
                maxBrightness = currentBrightness;
                answer = coordinate;
            }
        }

        /*
         * The official problem constraints guarantee that the answer fits
         * in int, which is the required return type.
         *
         * If a generalized version allowed answers outside the int range,
         * the method's return type would need to be long.
         */
        return (int) answer;
    }

    /*
     * CORRECTNESS ARGUMENT
     *
     * 1. Every light contributes +1 at its left endpoint and -1 immediately
     *    after its inclusive right endpoint.
     *
     * 2. Thus, after processing all events at coordinate x, the cumulative
     *    sum equals the true brightness at x.
     *
     * 3. Brightness cannot change between consecutive event coordinates,
     *    so no unprocessed coordinate can introduce a new brightness value.
     *
     * 4. Since we visit event coordinates in ascending order and update the
     *    answer only on a STRICT increase, the final answer is the smallest
     *    coordinate attaining the global maximum brightness.
     *
     * TIME COMPLEXITY:
     *     Creating events: O(n)
     *     Sorting 2n events: O(n log n)
     *     Sweeping all events: O(n)
     *
     *     Total: O(n log n)
     *
     * AUXILIARY SPACE:
     *     The event array contains exactly 2n entries.
     *     Total: O(n), excluding sorting implementation workspace.
     *
     *     The record objects are also O(n) in number.
     */
}
```

## Solution 2: `TreeMap` + sweep line

```java
import java.util.TreeMap;

class Solution {

    public int brightestPosition(int[][] lights) {

        /*
         * CORE IDEA: STORE BRIGHTNESS CHANGES IN A SORTED MAP
         *
         * We use a TreeMap where:
         *
         *     key   = street coordinate
         *     value = net brightness change at that coordinate
         *
         * Example:
         *     events[2] = +2
         *     events[5] = -1
         *     events[8] = -1
         *
         * This means:
         *     At coordinate 2, brightness increases by 2.
         *     At coordinate 5, brightness decreases by 1.
         *     At coordinate 8, brightness decreases by 1.
         *
         * WHY TREEMAP?
         *
         * 1. Its keys are automatically maintained in ascending order.
         * 2. We do not need to create a separate event array and sort it.
         * 3. If multiple lights produce events at the same coordinate,
         *    merge() combines their deltas into a single net change.
         *
         * TreeMap uses a balanced search tree, so inserting or updating
         * an event takes O(log m), where m is the number of distinct keys.
         */
        TreeMap<Long, Integer> events = new TreeMap<>();

        for (int[] light : lights) {

            // Convert to long before performing endpoint arithmetic.
            long position = light[0];
            long range = light[1];

            long left = position - range;
            long right = position + range;

            /*
             * A light illuminates every integer coordinate in [left, right].
             *
             * At left:
             *     Add 1 because this light begins contributing.
             *
             * At right + 1:
             *     Subtract 1 because this light no longer contributes.
             *
             * Example:
             *     Interval = [3, 7]
             *
             *     events[3] += 1
             *     events[8] -= 1
             *
             * This ensures the light contributes at 3, 4, 5, 6 and 7,
             * but not at 8.
             */

            /*
             * merge(key, value, Integer::sum):
             *
             * If the coordinate does not exist, insert the supplied delta.
             * If it already exists, add the new delta to its existing value.
             *
             * For example, if three lights start at coordinate 4:
             *     events[4] becomes +3.
             *
             * If one light ends immediately before coordinate 4:
             *     its -1 event is also combined at coordinate 4.
             *
             * The resulting map value is the NET change at that coordinate.
             */
            events.merge(left, +1, Integer::sum);
            events.merge(right + 1L, -1, Integer::sum);
        }

        /*
         * Initialize the sweep state.
         *
         * currentBrightness:
         *     Running sum of all event deltas processed so far.
         *
         * maxBrightness:
         *     Largest brightness observed at an event coordinate.
         *
         * answer:
         *     Leftmost coordinate at which that maximum occurs.
         *
         * We initialize maxBrightness to -1 so that the first event
         * establishes the answer. Every actual brightness is nonnegative.
         */
        int currentBrightness = 0;
        int maxBrightness = -1;
        long answer = 0;

        /*
         * TreeMap.entrySet() iterates over entries in ascending key order.
         *
         * This gives us the same left-to-right sweep as the sorted-array
         * solution without explicitly sorting an event array.
         */
        for (var event : events.entrySet()) {

            long coordinate = event.getKey();
            int delta = event.getValue();

            /*
             * Apply the NET brightness change at this coordinate.
             *
             * Because merge() combined all events at a coordinate,
             * a single addition is sufficient.
             *
             * Example:
             *     events[10] = +2
             *
             * If currentBrightness was 3 before coordinate 10:
             *     currentBrightness becomes 5.
             *
             * The result is the actual brightness at coordinate 10.
             */
            currentBrightness += delta;

            /*
             * WHY IS THE CUMULATIVE SUM THE BRIGHTNESS?
             *
             * Every light contributes exactly:
             *     +1 when its interval begins
             *     -1 immediately after its interval ends
             *
             * Before the first event, no light contributes.
             * Every subsequent event adjusts the number of active lights.
             *
             * Therefore, after applying the net delta at coordinate x,
             * currentBrightness equals the number of lights covering x.
             */

            /*
             * UPDATE THE ANSWER ONLY ON A STRICT INCREASE.
             *
             * Since TreeMap visits coordinates in ascending order,
             * the first coordinate that achieves a particular maximum
             * is necessarily the smallest coordinate achieving it.
             *
             * If a later coordinate has the same brightness, do nothing:
             * the earlier coordinate is already the correct answer.
             *
             * Using >= here would be WRONG because it could replace the
             * leftmost answer with a later coordinate having equal brightness.
             */
            if (currentBrightness > maxBrightness) {
                maxBrightness = currentBrightness;
                answer = coordinate;
            }
        }

        /*
         * Return the leftmost position with the highest brightness.
         * The problem guarantees that this coordinate fits in int.
         */
        return (int) answer;
    }

    /*
     * CORRECTNESS ARGUMENT
     *
     * 1. Every light is translated into the correct pair of difference events.
     *
     * 2. TreeMap stores each coordinate's net change and visits coordinates
     *    in increasing order.
     *
     * 3. The cumulative sum after applying each net change is the true
     *    brightness at that coordinate.
     *
     * 4. Brightness stays constant between event coordinates. Therefore,
     *    the global maximum must be observable at one of the event coordinates.
     *
     * 5. The answer changes only when brightness strictly increases.
     *    Because coordinates are processed from smallest to largest, ties
     *    retain the smallest coordinate.
     *
     * TIME COMPLEXITY:
     *     There are 2n event insertions or updates.
     *     Each TreeMap operation costs O(log m), where m <= 2n.
     *     Building the map: O(n log n).
     *     Iterating through its m entries: O(n).
     *
     *     Total: O(n log n).
     *
     * AUXILIARY SPACE:
     *     At most 2n distinct event coordinates are stored.
     *     Total: O(n).
     */
}
```

## Which implementation should you use in an interview?

| Aspect                | Event array                             | `TreeMap`                           |
| --------------------- | --------------------------------------- | ----------------------------------- |
| Sorting               | Explicitly sorts events                 | Maintains sorted keys automatically |
| Duplicate coordinates | Processed together in a loop            | Combined by `merge()`               |
| Main data structure   | `Event[]`                               | `TreeMap<Long, Integer>`            |
| Time complexity       | \\(O(n\log n)\\)                        | \\(O(n\log n)\\)                    |
| Auxiliary space       | \\(O(n)\\)                              | \\(O(n)\\)                          |
| Main advantage        | Makes the sweep-line algorithm explicit | Concise event aggregation           |

My recommendation: Explain the event-array solution first. It makes the core algorithm visible: create two events per light, sort them, calculate the prefix sum, and preserve the leftmost maximum. Then show the `TreeMap` solution as an alternative that combines equal-coordinate events automatically.

One rule to remember above everything else: add at `left`, subtract at `right + 1`, and update the answer only when brightness strictly increases.
