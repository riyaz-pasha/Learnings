# 731. My Calendar II — Java 24 Solutions

The key idea behind this problem is we can allow an interval to be booked twice, but never three times.

This is a natural extension of LeetCode 729 (My Calendar I).

We will explore four approaches:

1. Brute Force — Store all events and check every pair.
2. Better — Maintain single-booked and double-booked intervals.
3. Optimal for this problem — Sweep Line using `TreeMap`.
4. Advanced — Dynamic Segment Tree with lazy propagation.

Given that there are at most 1000 booking operations, the `TreeMap` sweep-line solution is particularly elegant and practical.

# 0. Simplifying the problem

We receive booking requests:

```
book(startTime, endTime)
```

Each event represents a half-open interval:

\\[ [startTime, endTime) \\]

Our job is to accept a booking only if no point in time becomes covered by three events.

There are three possible situations:

| Existing bookings           | New booking    | Result |
| --------------------------- | -------------- | ------ |
| No overlap                  | Single booking | Accept |
| One existing event overlaps | Double booking | Accept |
| Two existing events overlap | Triple booking | Reject |

Important: Half-open intervals

For intervals `[10, 20)` and `[20, 30)`:

- The first interval includes 10 but excludes 20.
- The second interval includes 20.
- Therefore, they do not overlap.

This boundary condition is extremely important when implementing interval algorithms.

# 1. Clarifying questions to ask the interviewer

Before coding, clarify the following:

Q1. Are intervals half-open or closed?

Why ask?

Because `[10, 20)` and `[20, 30)` do not overlap, whereas closed intervals would overlap at 20.

The problem explicitly specifies half-open intervals.

Q2. Can the same event be booked multiple times?

Why ask?

Because duplicate bookings count as separate events and can create a triple booking.

Q3. Should a rejected booking modify the calendar?

Why ask?

Because we must ensure that a failed booking does not partially modify our data structures.

The answer is no. A rejected booking must leave the calendar unchanged.

Q4. What are the maximum number of booking operations?

Why ask?

Because this determines whether an \\(O(n)\\), \\(O(n\log n)\\), or more sophisticated solution is appropriate.

Here, at most 1000 calls are made, making the `TreeMap` solution very suitable.

# 2. Core intuition — Think in terms of booking counts

Imagine that we already have these bookings:

```
Event A: [10, 20)
Event B: [15, 25)
```

Their combined timeline looks like this:

```
Time:     10    15    20    25
          |-----|-----|-----|

Event A:  [================)
Event B:        [================)

Bookings:
          1     2     1
```

The interval `[15, 20)` is already double-booked.

Now consider a new booking:

```
Event C: [18, 22)
```

This would create:

```
Time:     10    15    18    20    22    25
          |-----|-----|-----|-----|-----|

Event A:  [================)
Event B:        [======================)
Event C:              [================)

Bookings:
          1     2     3     2     1
```

The region `[18, 20)` would have three simultaneous bookings.

Therefore, reject the new event.

The central observation:

We only need to detect whether the requested interval intersects an already double-booked region.

This observation leads to our first optimized solution.

# 3. Solution 1 — Brute Force

## Mental model

Store every accepted event.

Whenever a new event arrives:

1. Compare it with every previously accepted event.
2. Find all existing events that overlap the new event.
3. For every overlapping event, compare it against all other existing events.
4. If two existing events overlap each other inside the new event, reject.
5. Otherwise, accept.

Why does this work?

A triple booking occurs precisely when the new event overlaps two existing events at a common point.

We can detect that by checking whether the intersection of three intervals is non-empty.

For three half-open intervals:

\\[ [\max(s_1,s_2,s_3),\min(e_1,e_2,e_3)) \\]

The intersection is non-empty when:

\\[ \max(s_1,s_2,s_3)<\min(e_1,e_2,e_3) \\]

## Java 24 implementation

```
import java.util.*;

class MyCalendarTwo {

    // Store all successfully accepted bookings.
    private final List<int[]> bookings = new ArrayList<>();

    public boolean book(int startTime, int endTime) {

        /*
         * STEP 1: Compare the new booking against every pair
         * of previously accepted bookings.
         *
         * WHY?
         * A triple booking can only occur when:
         *
         * 1. The new interval overlaps an existing interval A.
         * 2. The new interval overlaps another existing interval B.
         * 3. A and B overlap at a common point inside the new interval.
         *
         * Checking the intersection of all three intervals
         * detects exactly this situation.
         */

        for (int i = 0; i < bookings.size(); i++) {

            int[] first = bookings.get(i);

            for (int j = i + 1; j < bookings.size(); j++) {

                int[] second = bookings.get(j);

                /*
                 * Calculate the intersection of:
                 *
                 * New booking: [startTime, endTime)
                 * First:       [first[0], first[1])
                 * Second:      [second[0], second[1])
                 *
                 * Intersection start = maximum of all starts.
                 * Intersection end   = minimum of all ends.
                 */

                int intersectionStart = Math.max(
                    startTime,
                    Math.max(first[0], second[0])
                );

                int intersectionEnd = Math.min(
                    endTime,
                    Math.min(first[1], second[1])
                );

                /*
                 * If start < end, all three intervals share
                 * at least one non-empty time range.
                 *
                 * Therefore, accepting this booking would
                 * create a triple booking.
                 */

                if (intersectionStart < intersectionEnd) {
                    return false;
                }
            }
        }

        /*
         * STEP 2: No triple booking was found.
         *
         * Only now modify the calendar.
         *
         * This guarantees that rejected bookings do not
         * modify the existing calendar.
         */

        bookings.add(new int[]{startTime, endTime});

        return true;
    }
}
```

## Complexity analysis

Let \\(n\\) be the number of previously accepted bookings.

- Time: \\(O(n^2)\\) per booking because we examine every pair of existing bookings.
- Space: \\(O(n)\\) for storing accepted bookings.

For \\(m\\) total booking operations, worst-case total time is:

\\[ O(m^3) \\]

This is acceptable for small inputs but we can do better.

# 4. Solution 2 — Maintain Single and Double Booked Intervals

This is a much more intuitive solution.

## Mental model

Instead of repeatedly checking every pair of existing bookings, explicitly maintain two collections:

- `bookings`: all accepted original intervals.
- `overlaps`: all regions that are already double-booked.

Whenever a new event arrives:

Step 1: Check whether it intersects any existing double-booked interval.

If yes, reject immediately.

Step 2: Find intersections between the new event and all existing bookings.

These intersections become newly double-booked regions.

Step 3: Add the new event to the original bookings.

Let's understand this with an example.

Initially:

```
bookings = []
overlaps = []
```

Book `[10, 20)`:

```
bookings = [[10, 20)]
overlaps = []
```

Book `[15, 25)`:

The intersection is:

\\[ [\max(10,15),\min(20,25)) \\]

\\[ =[15,20) \\]

Therefore:

```
bookings = [[10,20), [15,25)]
overlaps = [[15,20)]
```

Now try `[18, 22)`.

It intersects the already double-booked interval `[15,20)`.

Therefore, reject.

## Java 24 implementation

```
import java.util.*;

class MyCalendarTwo {

    // All successfully accepted original bookings.
    private final List<int[]> bookings = new ArrayList<>();

    // Regions that are already double-booked.
    private final List<int[]> overlaps = new ArrayList<>();

    public boolean book(int startTime, int endTime) {

        /*
         * STEP 1: Check whether the new booking intersects
         * any region that is already double-booked.
         *
         * WHY?
         * Adding another event to an already double-booked
         * region would create a triple booking.
         */

        for (int[] overlap : overlaps) {

            int intersectionStart = Math.max(
                startTime,
                overlap[0]
            );

            int intersectionEnd = Math.min(
                endTime,
                overlap[1]
            );

            /*
             * Half-open interval intersection:
             *
             * start < end means a non-empty intersection.
             *
             * If start == end, the intervals only touch
             * at a boundary and do not overlap.
             */

            if (intersectionStart < intersectionEnd) {
                return false;
            }
        }

        /*
         * STEP 2: Find every intersection between the new
         * booking and previously accepted original bookings.
         *
         * WHY?
         * Every such intersection represents a region
         * that will become double-booked after accepting
         * the new event.
         *
         * We must compare against ORIGINAL bookings,
         * not against the overlaps list.
         */

        for (int[] booking : bookings) {

            int intersectionStart = Math.max(
                startTime,
                booking[0]
            );

            int intersectionEnd = Math.min(
                endTime,
                booking[1]
            );

            if (intersectionStart < intersectionEnd) {

                overlaps.add(new int[]{
                    intersectionStart,
                    intersectionEnd
                });
            }
        }

        /*
         * STEP 3: Accept the new booking.
         *
         * IMPORTANT:
         * We add the original booking only after checking
         * that no triple booking would be created.
         */

        bookings.add(new int[]{startTime, endTime});

        return true;
    }
}
```

## Why is this solution correct?

We maintain the following invariant:

> `overlaps` contains every region covered by at least two accepted events.

When a new event arrives:

- If it intersects `overlaps`, it would create a third booking, so we reject.
- Otherwise, its intersections with original bookings become double-booked regions.
- We add the new booking.

Therefore, the invariant remains true after every successful operation.

## Complexity analysis

Let \\(n\\) be the number of accepted bookings.

Each booking operation performs:

- One traversal of `overlaps`.
- One traversal of `bookings`.

Since there can be at most \\(n\\) overlap intervals per accepted booking, both traversals take \\(O(n)\\).

| Complexity                      | Value                   |
| ------------------------------- | ----------------------- |
| Time per booking                | \\(O(n)\\)              |
| Space                           | \\(O(n^2)\\) worst case |
| Total time for \\(m\\) bookings | \\(O(m^2)\\)            |

Why can space become \\(O(n^2)\\)?

Because every newly accepted booking can intersect many existing bookings, and we store each resulting intersection separately.

This is a very good interview solution.

# 5. Solution 3 — Sweep Line using TreeMap

Recommended solution

This is my preferred solution to explain the underlying sweep-line concept.

## Core intuition

Instead of storing intervals directly, store only the points where the booking count changes.

For every interval:

\\[ [start,end) \\]

We create two events:

- At `start`, booking count increases by 1.
- At `end`, booking count decreases by 1.

We maintain these changes in a sorted `TreeMap`.

Why?

Because a sorted map allows us to process all booking changes in chronological order.

### Example

Suppose we book:

```
[10, 20)
[15, 25)
```

The event map becomes:

| Time | Change |
| ---- | ------ |
| 10   | +1     |
| 15   | +1     |
| 20   | -1     |
| 25   | -1     |

Sweep through the events:

```
Time:          10    15    20    25
               |-----|-----|-----|

Changes:       +1    +1    -1    -1

Active count:   1     2     1     0
```

The maximum active count is 2.

Now consider booking `[18, 22)`.

Temporarily add its events:

| Time | Change |
| ---- | ------ |
| 10   | +1     |
| 15   | +1     |
| 18   | +1     |
| 20   | -1     |
| 22   | -1     |
| 25   | -1     |

Sweep:

```
Time:          10    15    18    20    22    25
               |-----|-----|-----|-----|-----|

Active count:   1     2     3     2     1     0
```

The active count reaches 3.

Therefore, reject the booking and undo its changes.

## Java 24 implementation

```
import java.util.*;

class MyCalendarTwo {

    /*
     * TreeMap maintains timestamps in sorted order.
     *
     * Key   = timestamp
     * Value = change in active booking count at that timestamp.
     *
     * Positive value means bookings start.
     * Negative value means bookings end.
     *
     * WHY TreeMap?
     * We need chronological processing of all events.
     * TreeMap maintains sorted keys automatically.
     */
    private final TreeMap<Integer, Integer> timeline = new TreeMap<>();

    public boolean book(int startTime, int endTime) {

        /*
         * STEP 1: Temporarily add the new booking.
         *
         * At startTime:
         *     Active bookings increase by 1.
         *
         * At endTime:
         *     Active bookings decrease by 1.
         *
         * merge() combines changes if multiple events
         * happen at the same timestamp.
         */

        timeline.merge(startTime, 1, Integer::sum);
        timeline.merge(endTime, -1, Integer::sum);

        /*
         * STEP 2: Sweep through all timestamps.
         *
         * activeBookings represents how many events
         * are active immediately after processing
         * the current timestamp.
         *
         * WHY?
         * For half-open intervals [start, end):
         *
         * - A booking starting at time t is active from t.
         * - A booking ending at time t is no longer active
         *   from t onwards.
         *
         * Combining both changes at the same timestamp
         * gives the correct count for the interval after t.
         */

        int activeBookings = 0;

        for (int change : timeline.values()) {

            activeBookings += change;

            /*
             * STEP 3: Detect triple booking.
             *
             * If three or more bookings are simultaneously
             * active, the new event must be rejected.
             */

            if (activeBookings >= 3) {

                /*
                 * STEP 4: Roll back the temporary booking.
                 *
                 * Undo the +1 at startTime.
                 * Undo the -1 at endTime.
                 *
                 * This restores the exact previous timeline.
                 */

                timeline.merge(startTime, -1, Integer::sum);
                timeline.merge(endTime, 1, Integer::sum);

                /*
                 * Remove timestamps whose net change
                 * has become zero.
                 *
                 * This is important because zero-valued
                 * entries have no effect on the sweep.
                 */

                if (timeline.get(startTime) == 0) {
                    timeline.remove(startTime);
                }

                if (timeline.get(endTime) == 0) {
                    timeline.remove(endTime);
                }

                return false;
            }
        }

        /*
         * STEP 5: No triple booking was found.
         *
         * Keep the temporary changes permanently.
         * The new event is successfully booked.
         */

        return true;
    }
}
```

## Complexity analysis

Let \\(n\\) be the number of distinct timestamps in the TreeMap.

There are at most \\(2m\\) timestamps after \\(m\\) booking operations.

For each booking:

1. Two `TreeMap.merge()` operations: \\(O(\log n)\\).
2. Sweep through all timestamps: \\(O(n)\\).
3. If rejected, two rollback operations: \\(O(\log n)\\).

Therefore:

| Complexity                      | Value        |
| ------------------------------- | ------------ |
| Time per booking                | \\(O(n)\\)   |
| Space                           | \\(O(n)\\)   |
| Total time for \\(m\\) bookings | \\(O(m^2)\\) |

Important interviewer observation:

Although we use `TreeMap`, this implementation is not \\(O(\log n)\\) per booking.

Why?

Because we traverse the entire timeline after every booking.

The TreeMap gives us sorted ordering, but it does not automatically give us a fast maximum-prefix-sum query.

# 6. Solution 4 — Dynamic Segment Tree with Lazy Propagation

This is the advanced solution.

If the interviewer asks:

"Can you achieve approximately \\(O(\log C)\\) per booking?"

This is where a dynamic segment tree becomes useful.

Here:

\\[ C=10^9 \\]

The coordinate range is extremely large, so building a normal segment tree with an array of size \\(10^9\\) is impractical.

Instead, create nodes dynamically only when needed.

## Core intuition

We want to support two operations:

1. Range increment: increase the booking count by 1 over `[startTime, endTime)`.
2. Range maximum: find the maximum booking count over that range.

If the maximum would exceed 2, reject the booking and undo the increment.

A lazy segment tree supports these operations efficiently.

### Mental model

Each segment-tree node represents a time range.

For example:

```
                  [0, 16)
                 /       \
            [0, 8)       [8, 16)
            /   \         /    \
         ...    ...     ...    ...
```

Each node stores:

- `max`: maximum booking count within its range, including its own lazy increment.
- `lazy`: increment that has been applied to the entire node range but not yet propagated to its children.
- `left`, `right`: dynamically created child nodes.

When a booking covers an entire node range, we update that node directly without visiting its descendants.

When a booking covers only part of the node range, we recurse into the appropriate children.

## Java 24 implementation

```
class MyCalendarTwo {

    /*
     * Dynamic segment-tree node.
     *
     * Every node represents some coordinate interval [left, right).
     *
     * max:
     *     Maximum booking count anywhere inside this node's range.
     *
     * lazy:
     *     A pending increment applied to the entire node range.
     *     It has not necessarily been pushed to its children.
     *
     * left / right:
     *     Dynamically allocated children.
     */
    private static class Node {

        int max;
        int lazy;

        Node left;
        Node right;
    }

    /*
     * Root represents the complete coordinate domain.
     *
     * Constraints:
     * 0 <= startTime < endTime <= 10^9
     *
     * We use [0, 1_000_000_000).
     */
    private final Node root = new Node();

    public boolean book(int startTime, int endTime) {

        /*
         * STEP 1: Temporarily increase booking counts
         * over the requested interval.
         *
         * We query the maximum after applying the update.
         */

        update(
            root,
            0,
            1_000_000_000,
            startTime,
            endTime,
            1
        );

        /*
         * STEP 2: Check whether any point has three bookings.
         *
         * root.max represents the maximum booking count
         * anywhere in the entire coordinate domain.
         */

        if (root.max >= 3) {

            /*
             * STEP 3: Roll back the rejected booking.
             *
             * Decrease the same interval by 1.
             *
             * This restores the previous calendar state.
             */

            update(
                root,
                0,
                1_000_000_000,
                startTime,
                endTime,
                -1
            );

            return false;
        }

        return true;
    }

    private void update(
        Node node,
        int left,
        int right,
        int queryLeft,
        int queryRight,
        int value
    ) {

        /*
         * CASE 1: Complete coverage.
         *
         * The requested interval completely covers
         * this segment-tree node.
         *
         * We can update the entire node in O(1).
         *
         * lazy records the pending update for descendants.
         */

        if (queryLeft <= left && right <= queryRight) {

            node.max += value;
            node.lazy += value;

            return;
        }

        /*
         * CASE 2: Partial coverage.
         *
         * Push any pending lazy update to the children
         * before recursively updating them.
         */

        int mid = left + (right - left) / 2;

        pushDown(node);

        /*
         * Recurse left if the query intersects the left child.
         *
         * Left child range:
         * [left, mid)
         */

        if (queryLeft < mid) {

            if (node.left == null) {
                node.left = new Node();
            }

            update(
                node.left,
                left,
                mid,
                queryLeft,
                queryRight,
                value
            );
        }

        /*
         * Recurse right if the query intersects the right child.
         *
         * Right child range:
         * [mid, right)
         */

        if (queryRight > mid) {

            if (node.right == null) {
                node.right = new Node();
            }

            update(
                node.right,
                mid,
                right,
                queryLeft,
                queryRight,
                value
            );
        }

        /*
         * STEP 3: Recalculate this node's maximum.
         *
         * WHY?
         * The maximum booking count in this range is the
         * maximum of its children's maximum values,
         * plus this node's own lazy increment.
         *
         * Null children represent untouched ranges
         * with a maximum booking count of zero.
         */

        int leftMax = node.left == null ? 0 : node.left.max;

        int rightMax = node.right == null ? 0 : node.right.max;

        node.max = node.lazy + Math.max(leftMax, rightMax);
    }

    private void pushDown(Node node) {

        /*
         * No pending update exists.
         * Nothing needs to be propagated.
         */

        if (node.lazy == 0) {
            return;
        }

        /*
         * Create children only when required.
         */

        if (node.left == null) {
            node.left = new Node();
        }

        if (node.right == null) {
            node.right = new Node();
        }

        /*
         * Propagate the parent's pending increment
         * to both children.
         *
         * Because the parent increment applies to its
         * entire range, both children receive it.
         */

        node.left.max += node.lazy;
        node.left.lazy += node.lazy;

        node.right.max += node.lazy;
        node.right.lazy += node.lazy;

        /*
         * The update has now been propagated.
         * Clear the parent's lazy value.
         */

        node.lazy = 0;
    }
}
```

## Complexity analysis

Let \\(C=10^9\\) be the coordinate domain.

The height of the segment tree is:

\\[ O(\log C) \\]

A range update visits at most \\(O(\log C)\\) nodes for an interval update in this one-dimensional segment tree.

Therefore:

| Complexity        | Value                                                         |
| ----------------- | ------------------------------------------------------------- |
| Time per booking  | \\(O(\log C)\\)                                               |
| Space per booking | \\(O(\log C)\\) new nodes in the usual range-update traversal |
| Total space       | \\(O(m\log C)\\)                                              |
| Total time        | \\(O(m\log C)\\)                                              |

This is considerably more scalable than sweeping the entire TreeMap for every booking.

The dynamic tree avoids allocating nodes for untouched portions of the coordinate domain.

# 7. Comparing all approaches

Let \\(m\\) be the total number of booking operations and \\(C=10^9\\).

| Approach                    | Time per booking | Space            |
| --------------------------- | ---------------- | ---------------- |
| Brute force (pair checking) | \\(O(n^2)\\)     | \\(O(n)\\)       |
| Single + double intervals   | \\(O(n)\\)       | \\(O(n^2)\\)     |
| TreeMap sweep line          | \\(O(n)\\)       | \\(O(n)\\)       |
| Dynamic segment tree        | \\(O(\log C)\\)  | \\(O(m\log C)\\) |

Here, \\(n\\) is the number of accepted bookings or distinct timeline entries, depending on the approach.

Which solution should you use in an interview?

- Start with brute force to establish correctness.
- Explain the single/double interval approach as the natural optimization.
- Present `TreeMap` sweep line as a clean and efficient solution for the given constraints.
- Discuss the dynamic segment tree if the interviewer asks for better scalability.

For this problem's constraint of at most 1000 calls, I would generally implement Solution 2 (single and double intervals) or Solution 3 (TreeMap).

# 8. Important edge cases

Let's walk through the cases an interviewer may test.

### Case 1: Adjacent intervals

```
book(10, 20); // true
book(20, 30); // true
```

Why?

`[10,20)` does not include 20.

Therefore, there is no overlap.

### Case 2: Identical intervals

```
book(10, 20); // true
book(10, 20); // true
book(10, 20); // false
```

Why?

Two identical intervals create double booking.

The third identical interval creates triple booking.

### Case 3: Completely nested intervals

```
book(10, 100); // true
book(20, 80);  // true
book(30, 50);  // false
```

Why?

The third interval is entirely inside the region already covered by two events.

### Case 4: Partial overlap

```
book(10, 30); // true
book(20, 40); // true
book(25, 35); // false
```

Why?

The third event overlaps the already double-booked region `[20,30)`.

### Case 5: Rejected booking followed by a valid booking

```
book(10, 20); // true
book(15, 25); // true
book(18, 22); // false
book(20, 30); // true
```

Why?

The rejected booking must not corrupt the calendar.

`[20,30)` is valid because the previously double-booked region ends at 20.

### Case 6: Booking at the maximum boundary

```
book(999_999_999, 1_000_000_000); // true
```

Why?

The constraint permits an end time of \\(10^9\\).

The segment-tree implementation uses `[0, 1_000_000_000)` as its domain, so this is handled correctly.

# 9. Interviewer follow-up questions

Q1. Why do we use `start < end` instead of `start <= end` to detect overlap?

Because intervals are half-open.

Two intervals touching at a boundary do not share any point.

For example:

```
[10, 20)
[20, 30)
```

Their intersection is empty.

Q2. Why does the TreeMap solution process both events at the same timestamp together?

Because the map stores the net change at each timestamp.

For half-open intervals, all bookings ending at time `t` stop being active at `t`, while bookings starting at `t` become active at `t`.

The net change correctly represents the active count immediately after `t`.

Q3. Why do we need rollback in the TreeMap solution?

Because we temporarily insert the new booking before validating it.

If the sweep detects three active bookings, we must undo both endpoint changes.

Otherwise, the rejected booking would incorrectly remain in the calendar.

Q4. Can we solve this using a priority queue?

A priority queue can help track interval endings, but by itself it does not maintain the full booking-count information needed to detect triple booking efficiently.

A min-heap can track active interval endings, but we still need to manage overlapping intervals and their counts.

The double-booked interval list or sweep-line approach is more straightforward.

Q5. What changes if we want to allow at most K simultaneous bookings?

The same logic generalizes.

For the single/double interval solution, we would need to maintain regions covered by up to \\(K-1\\) bookings, which becomes increasingly complicated.

For the sweep-line solution, simply change:

```
if (activeBookings >= 3)
```

to:

```
if (activeBookings >= K + 1)
```

For the segment tree, similarly change the rejection threshold from 3 to `K + 1`.

Q6. Can we avoid rollback in the TreeMap solution?

Yes.

We can first calculate the maximum booking count that would result from the proposed booking without modifying the TreeMap.

Q7. How is My Calendar II different from My Calendar I?

| Problem         | Allowed maximum overlap           |

My Calendar I rejects any overlap.

My Calendar II rejects only triple bookings.

My Calendar III accepts every booking and returns the maximum number of simultaneous events.

# 10. Final interview recommendation

I would present the solutions in this order:

1. Brute force: Establish the correctness condition using three-interval intersection.
2. Double-booked interval list: Show that we only need to check whether a new booking intersects an already double-booked region.
3. TreeMap sweep line: Demonstrate the general sweep-line pattern and chronological booking-count changes.
4. Dynamic segment tree: Discuss when the coordinate range and operation count justify a more advanced data structure.

The most important mental model to remember:

> A new booking is valid if and only if it does not intersect any time region that is already occupied by two bookings.

That single observation is the foundation of My Calendar II.
