Good instinct — the trickiest part of Morris traversal isn't the code, it's *seeing* the threading happen. Let me trace it on a concrete tree, step by step, showing exactly when a link is created and when it's torn down.

## The example tree

```
        1
       / \
      2   3
     / \
    4   5
```

Expected preorder: `1, 2, 4, 5, 3` — that's what we're racing to reproduce, but with O(1) space instead of a stack.

## The core idea, in one sentence

For any node with a left child, its **inorder predecessor** (rightmost node of the left subtree) has a `null` right pointer just sitting there unused — Morris traversal temporarily repurposes that `null` as a "come back to me" thread, so we never need a stack to remember how to return to `current` after finishing its left subtree.

## Full trace

| Step | `current` | `current.left`? | predecessor found | Action | Thread op | `result` |
|---|---|---|---|---|---|---|
| 1 | 1 | 2 (not null) | 5 (rightmost of subtree rooted at 2) | 1st visit → **process 1** | **ADD**: `5.right = 1` | `[1]` |
| 2 | 2 (via `1.left`) | 4 (not null) | 4 (no right child, so it *is* its own predecessor) | 1st visit → **process 2** | **ADD**: `4.right = 2` | `[1,2]` |
| 3 | 4 (via `2.left`) | null | — | leaf → **process 4** | move via `4.right` (the thread!) | `[1,2,4]` |
| 4 | 2 (arrived via thread) | 4 (not null) | 4, and `4.right == current(2)` → we're seeing our own thread | 2nd visit → subtree done | **REMOVE**: `4.right = null` | `[1,2,4]` (unchanged) |
| 5 | 5 (via `2.right`, untouched) | null | — | leaf → **process 5** | move via `5.right` (the thread!) | `[1,2,4,5]` |
| 6 | 1 (arrived via thread) | 2 (not null) | 5, and `5.right == current(1)` → our own thread | 2nd visit → subtree done | **REMOVE**: `5.right = null` | `[1,2,4,5]` (unchanged) |
| 7 | 3 (via `1.right`, untouched) | null | — | leaf → **process 3** | `current = null` → done | `[1,2,4,5,3]` |

Final: `[1, 2, 4, 5, 3]` ✅

## Watching the tree shape-shift

**After step 1** — we haven't lost anything, we've just borrowed `5`'s empty `right` slot:
```
        1  ←──────────┐
       / \             ┊ (thread)
      2   3            ┊
     / \                ┊
    4   5 ┈┈┈┈┈┈┈┈┈┈┈┈┈┈┘
```
This is *why* we go left immediately after — the thread guarantees we can get back to `1` once the left subtree is exhausted, so it's safe to "lose" our reference to `1` for a while.

**After step 2** — same trick, one level down:
```
        1  ←──────────┐
       / \             ┊
      2   3            ┊
     / \                ┊
    4   5 ┈┈┈┈┈┈┈┈┈┈┈┈┈┈┘
    │
    └┈┈┈> back to 2   (4.right = 2)
```

**Step 3→4** — we hit leaf `4`, process it, then walk `4.right`. That pointer isn't `null` anymore — it's the thread — so it silently teleports us back to `2`. We arrive at `2` a second time, and the tell-tale sign is `predecessor.right == current`. That's the "I've already been down this road" signal. We **remove** the thread (put the tree back the way it was) and move on to `2.right`:
```
        1  ←──────────┐
       / \             ┊
      2   3            ┊
     / \                ┊
    4   5 ┈┈┈┈┈┈┈┈┈┈┈┈┈┈┘
   (thread to 2 erased — 4.right is null again)
```

**Step 5→6** — same story one level up: leaf `5` processed, walk `5.right`, land back on `1`, recognize the thread (`predecessor.right == current`), erase it, move to `1.right`:
```
        1
       / \
      2   3
     / \
    4   5
   (both threads gone — tree fully restored to original shape)
```

**Step 7** — `3` is a leaf, process it, `current.right` is genuinely `null`, loop ends.

## Why "add before going left, remove before going right"

- We **add** the thread the *first* time we visit a node with a left child — right when we've just processed it (preorder!) and are about to dive into the left subtree and (temporarily) lose our way back.
- We **remove** the thread the *second* time we arrive at that same node — via the thread itself — because at that point the left subtree is fully drained and we're about to move to `current.right`. If we didn't remove it, `current.right` would still be pointing at the thread instead of the real right subtree, and we'd loop forever.

The `predecessor.right != current` check in the inner `while` is what stops us from re-threading a link that already exists — without it, on the second visit we'd walk all the way down to the thread, see it's not `null`, and try to walk *through* it into an infinite loop.

## The code, annotated with this exact trace

```java
public List<Integer> preorderTraversal(TreeNode<Integer> root) {
    List<Integer> result = new ArrayList<>();
    TreeNode<Integer> current = root;

    while (current != null) {
        if (current.left == null) {
            // No left subtree to detour through — e.g. current = 4, or current = 5, or current = 3.
            // Nothing to thread. Just visit and step right.
            // (For 4 and 5, "right" turns out to be a thread we planted earlier — that's the magic.)
            result.add(current.data);
            current = current.right;
        } else {
            // e.g. current = 1: walk into the left subtree (rooted at 2) to find its
            // rightmost node — that's 5, the inorder predecessor of 1.
            TreeNode predecessor = current.left;
            while (predecessor.right != null && predecessor.right != current) {
                predecessor = predecessor.right;
            }

            if (predecessor.right == null) {
                // FIRST arrival at `current`. predecessor (5) has a free right pointer —
                // borrow it. This is the ADD step: 5.right = 1.
                // Preorder means we record `current` right now, before descending,
                // since we may not cleanly "come back" to visit it in the usual recursive sense.
                result.add(current.data);
                predecessor.right = current;
                current = current.left;   // dive into the left subtree (2)
            } else {
                // SECOND arrival at `current`, reached via the thread we planted.
                // predecessor.right == current confirms: "this is my own thread, not a real edge."
                // Left subtree is fully processed — REMOVE the thread to restore the tree,
                // then proceed to the right subtree as normal.
                predecessor.right = null;
                current = current.right;
            }
        }
    }
    return result;
}
```

**The one-line mental model:** every node with a left child gets visited twice — once to process it and drop a breadcrumb (thread) at the end of its left subtree, and once (arriving via that very breadcrumb) to pick up the breadcrumb and continue right. Leaves and nodes with no left child are visited exactly once, straight through.
