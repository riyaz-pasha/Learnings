# **901. Online Stock Span — Medium**

**Pattern: Monotonic Stack | Data Stream | Previous Greater Element**

The optimal solution uses a **Monotonic Decreasing Stack** with a small optimization called **Span Compression**.

Let's understand it from an interview perspective.

## **0. Simplify the problem**

We receive stock prices one day at a time.

For each new day's price, we need to calculate how many consecutive days, including today and moving backward, had prices less than or equal to today's price.

In other words:

> Starting from today, keep moving backward until you encounter a day whose stock price is strictly greater than today's price. The number of days visited is the span.

### **Example**

Suppose the stock prices are:

```
Day:     1   2   3   4   5   6   7
Price: 100  80  60  70  60  75  85
```

For day 6, price = 75:

```
Day:     3   4   5   6
Price:  60  70  60  75
                  ^
                Today
```

Moving backward:

\- Day 6: 75  75 ✗ Stop.

Therefore, span = **4**.

For day 7, price = 85:

```
Day:     1   2   3   4   5   6   7
Price: 100  80  60  70  60  75  85
```

The previous greater price is 100.

Everything after day 1 is less than or equal to 85.

Therefore, span = **6**.

## **1. Clarifying questions to ask the interviewer**

Before implementing, clarify:

**Q1. Are prices guaranteed to arrive in chronological order?**

Why: The problem describes an online stream. We process each price in arrival order, and we cannot assume future prices are available.

**Q2. Should equal prices be included in the span?**

Why: This determines our stack comparison.

Yes. The definition explicitly says less than or equal to today's price.

Therefore, we must pop previous prices that are **less than or equal to** the current price.

**Q3. Can we store previously received prices?**

Why: This determines whether we can use a stack to maintain historical information.

Yes. We can store the necessary information from previous days.

**Q4. What are the expected constraints?**

Why: This helps determine whether an O(n) or O(n²) solution is appropriate.

At most 10⁴ calls are made, so an O(n) total-time solution is easily sufficient.

## **2. Core intuition — Monotonic Stack**

### **First, understand the brute-force approach**

For every new price:

1. Start from today's price.
2. Move backward through previous prices.
3. Continue while previous prices are less than or equal to today's price.
4. Stop when a greater price is found.
5. Return the number of visited days.

But there is a problem.

We repeatedly examine historical prices.

Can we avoid checking the same historical prices multiple times?

**Yes! Using a Monotonic Stack.**

### **The key observation**

Consider:

```
Prices = [100, 80, 60, 70, 60, 75]
```

When today's price is 75:

- 60 is smaller than 75.
- 70 is smaller than 75.
- 60 is smaller than 75.

All these days can be combined into today's span.

We don't need to remember each of those days separately.

We only need to remember:

- The price of a day.
- The total span represented by that day.

This is the key optimization.

### **Stack representation**

Instead of storing just prices, store:

```
record Entry(int price, int span) {}
```

Each stack entry represents a group of consecutive days.

For example:

```
Price = 75
Span  = 4
```

means that the current day and the three days immediately preceding it all have prices less than or equal to 75.

### **Why do we pop elements?**

Suppose our stack contains:

```
Bottom                         Top

[100, 1] [80, 1] [70, 2] [60, 1]
```

Now today's price is 75.

We inspect the top:

```
60 <= 75  → Pop, add span 1
70 <= 75  → Pop, add span 2
```

Our accumulated span becomes:

```
1 + 2 = 3
```

Now the top is 80.

```
80 > 75 → Stop
```

Push:

```
[100, 1] [80, 1] [75, 3]
```

The new entry represents today's price and the previous two days represented by the popped entries.

### **The most important mental model**

**Every stack entry represents a compressed block of consecutive days.**

When a new price arrives:

- Pop every block whose price is less than or equal to today's price.
- Add their spans to today's span.
- Stop at the first greater price.
- Push today's price and its accumulated span.

This is called a **Monotonic Decreasing Stack** because prices from bottom to top are strictly decreasing.

# **4. All possible solutions in Java 24**

## **Approach 1: Brute Force — Scan Previous Prices**

### **Idea**

Maintain all previous prices in an array/list.

For each incoming price, scan backward until we find a greater price.

```java

import java.util.ArrayList;
import java.util.List;

class StockSpanner {

    private final List<Integer> prices = new ArrayList<>();

    public int next(int price) {

        // Store today's price.
        prices.add(price);

        // Every day includes itself in its span.
        int span = 1;

        // Start from the previous day.
        int index = prices.size() - 2;

        // Move backward while previous prices are
        // less than or equal to today's price.
        while (index >= 0 && prices.get(index) <= price) {

            span++;
            index--;
        }

        return span;
    }
}

/*
TIME COMPLEXITY:

next():
    O(n) worst case.

    In the worst case, prices arrive in increasing order:
    [10, 20, 30, 40, 50]

    For every new price, we scan all previous prices.

    Total time for n calls:
    O(n^2).

SPACE COMPLEXITY:

O(n) for storing all historical prices.

WHY THIS IS NOT OPTIMAL:

The same historical prices may be examined repeatedly.
We need to avoid redundant backward scanning.
*/

```

**Verdict:** Correct, but inefficient.

## **Approach 2: Optimal — Monotonic Stack with Span Compression**

This is the standard interview solution.

### **Java 24 implementation**

```java

import java.util.ArrayDeque;
import java.util.Deque;

class StockSpanner {

    // Each entry represents a compressed block of days.
    //
    // price = price of the representative day.
    // span  = number of consecutive days represented.
    //
    // A record is useful because these two values
    // logically belong together and are immutable.
    private record Entry(int price, int span) {}

    // Maintains prices in strictly decreasing order
    // from bottom to top.
    private final Deque<Entry> stack = new ArrayDeque<>();

    public int next(int price) {

        // Today's price always contributes one day.
        int span = 1;

        // Remove all previous blocks whose prices are
        // less than or equal to today's price.
        //
        // Why <= and not < ?
        // Because the problem explicitly includes equal
        // prices in the stock span.
        while (!stack.isEmpty() &&
               stack.peek().price() <= price) {

            // The popped block consists entirely of days
            // that are less than or equal to today's price.
            //
            // Therefore, we can safely include its entire
            // span without examining individual days.
            Entry previous = stack.pop();

            span += previous.span();
        }

        // Push today's price together with its accumulated
        // span. This entry now represents all the days
        // compressed during the current operation.
        stack.push(new Entry(price, span));

        // Return the number of consecutive qualifying days.
        return span;
    }
}

/*
TIME COMPLEXITY:

For one next() call:

    Worst case: O(n)

    A single call might pop every element currently
    present in the stack.

    However, this is NOT the overall complexity.

For n calls:

    Every entry is pushed exactly once.

    Every entry can be popped at most once.

    Therefore:
        Total pushes = n
        Total pops   <= n

    Total stack operations = O(n).

    Amortized time per next() = O(1).

    Total time for n calls = O(n).

SPACE COMPLEXITY:

    O(n) worst case.

    Consider strictly decreasing prices:
        [100, 90, 80, 70, 60]

    No previous entry gets popped, so the stack
    contains all n entries.

WHY THIS IS OPTIMAL:

    We never revisit a compressed block after removing it.

    Every historical block is processed at most twice:
        1. Once when pushed.
        2. Once when popped.

    This eliminates repeated backward scanning.
*/

```

### **Why is the complexity amortized O(1)?**

This is an important interview question.

Consider:

```
[100, 80, 60, 70, 60, 75, 85]
```

When 85 arrives, it might pop several elements.

That individual operation can take O(n).

But each popped element was previously pushed exactly once.

It can never be popped again because it has been permanently removed.

For n incoming prices:

| Operation | Maximum total |
| --------- | ------------- |
| Push      | n             |
| Pop       | n             |
| Total     | 2n            |

Therefore:

\\[ T(n)=O(2n)=O(n) \\]

Amortized complexity:

\\[ \frac{O(n)}{n}=O(1) \\]

**Remember:** Individual operations can be O(n), but the average cost across the entire sequence is O(1).

## **Approach 3: Monotonic Stack with Day Indices**

There is another elegant implementation.

Instead of storing `(price, span)`, store the indices of previous greater prices.

### **Idea**

Maintain an array of historical prices and a stack of indices.

For today's index `i`:

1. Pop indices whose prices are less than or equal to today's price.
2. The remaining stack top represents the nearest previous greater price.
3. Calculate the distance between today and that previous greater price.

If no previous greater price exists, the span is `i + 1`.

```java

import java.util.ArrayDeque;
import java.util.Deque;
import java.util.ArrayList;
import java.util.List;

class StockSpanner {

    private final List<Integer> prices = new ArrayList<>();

    // Stores indices of previous greater prices.
    private final Deque<Integer> stack = new ArrayDeque<>();

    public int next(int price) {

        int currentIndex = prices.size();

        // Store today's price.
        prices.add(price);

        // Remove all previous prices <= today's price.
        while (!stack.isEmpty() &&
               prices.get(stack.peek()) <= price) {

            stack.pop();
        }

        // If no greater previous price exists,
        // the span includes every day so far.
        //
        // Otherwise, the nearest previous greater price
        // acts as the boundary of today's span.
        int span = stack.isEmpty()
                ? currentIndex + 1
                : currentIndex - stack.peek();

        // Store today's index for future queries.
        stack.push(currentIndex);

        return span;
    }
}

/*
TIME COMPLEXITY:

next():
    O(n) worst case for an individual call.

Across n calls:
    Every index is pushed exactly once.
    Every index is popped at most once.

    Total = O(n).

    Amortized next() = O(1).

SPACE COMPLEXITY:

    O(n) for the historical prices.
    O(n) for the index stack.

    Total = O(n).

WHY THIS WORKS:

    The stack maintains indices of previous
    strictly greater elements.

    The nearest previous greater element determines
    where the backward span must stop.

    If its index is j and today's index is i:

        span = i - j

    If no such element exists:

        span = i + 1
*/

```

## **5. Edge cases to watch out for**

| Input prices        | Expected spans    | Reason                            |
| ------------------- | ----------------- | --------------------------------- |
| `[100]`             | `[1]`             | First day always has span 1       |
| `[10, 20, 30]`      | `[1, 2, 3]`       | Increasing prices pop everything  |
| `[30, 20, 10]`      | `[1, 1, 1]`       | Decreasing prices never pop       |
| `[10, 10, 10]`      | `[1, 2, 3]`       | Equal prices must be included     |
| `[100, 80, 60, 70]` | `[1, 1, 1, 2]`    | Previous greater price stops span |
| `[5, 4, 3, 4, 5]`   | `[1, 1, 1, 3, 5]` | Multiple blocks get compressed    |

**Most common bug:**

Using:

```
stack.peek().price() < price
```

instead of:

```
stack.peek().price() <= price
```

This incorrectly excludes equal prices.

## **6. Interviewer follow-up questions**

### **Q1. Why do we use a monotonic decreasing stack?**

Because we need to efficiently find the nearest previous element that is strictly greater than today's price.

The stack maintains decreasing prices, so all smaller or equal prices can be removed immediately.

### **Q2. Why do we add the popped element's span instead of incrementing by one?**

Because an entry represents multiple historical days.

For example:

```
(70, 3)
```

represents three consecutive days.

When that entry is popped, all three days qualify for today's span.

Therefore:

```
span += previous.span();
```

### **Q3. Why is the stack strictly decreasing?**

Whenever a new price arrives, we remove all elements whose prices are less than or equal to it.

Therefore, after insertion:

```
100 > 85 > 75 > 60
```

All remaining prices are strictly decreasing from bottom to top.

### **Q4. Can we use a Queue instead?**

A normal FIFO queue is not suitable because we need to remove previous prices from the most recent day backward.

A stack naturally supports this LIFO behavior.

### **Q5. Is O(1) guaranteed for every next() call?**

No.

A single call can pop O(n) elements.

O(1) is the **amortized time complexity**, not the worst-case complexity of an individual call.

### **Q6. What happens if prices are strictly increasing?**

Example:

```
[10, 20, 30, 40, 50]
```

Each new price removes all previous entries.

The stack always contains one element.

The spans are:

```
[1, 2, 3, 4, 5]
```

Total time is still O(n).

### **Q7. What happens if prices are strictly decreasing?**

Example:

```
[50, 40, 30, 20, 10]
```

Nothing gets popped.

The stack contains all five entries.

Every span is 1.

This is the worst-case O(n) space scenario.

### **Q8. Why can't we discard all previous prices immediately?**

Because a future price may be smaller than some historical prices.

For example:

```
[100, 80, 60, 70, 65]
```

When 65 arrives, the previous price 70 must stop the span.

We need to preserve the relevant historical boundaries.

The monotonic stack retains exactly the information needed.

### **Q9. What is the relationship between this problem and Next Greater Element?**

They are closely related.

Online Stock Span finds the **Previous Greater Element** for each new price.

The span is calculated as:

\\[ span = currentIndex - previousGreaterIndex \\]

If no previous greater element exists:

\\[ span = currentIndex + 1 \\]

### **Q10. Can we implement this without storing individual prices?**

Yes.

That is exactly what the span-compression solution does.

Each stack entry stores only:

```
(price, span)
```

It doesn't need to retain the complete price history.

## **7. Final interview comparison**

| Approach                  | Individual `next()` | Total time for n calls | Space |
| ------------------------- | ------------------- | ---------------------- | ----- |
| Brute force               | O(n)                | O(n²)                  | O(n)  |
| Monotonic stack + span    | O(n) worst case     | O(n)                   | O(n)  |
| Monotonic stack + indices | O(n) worst case     | O(n)                   | O(n)  |

**My recommendation in an interview:**

Use **Approach 2 — Monotonic Stack with Span Compression**.

Why?

1. It directly models the problem.
2. It avoids storing the entire historical price array.
3. It uses a clean `(price, span)` representation.
4. It achieves O(1) amortized time per operation.
5. It is easy to explain and prove correct.

### **Pattern recognition to remember**

Whenever you see problems involving:

- Previous greater or smaller elements.
- Next greater or smaller elements.
- Consecutive ranges.
- Finding boundaries in historical data.
- Processing elements in a stream.

Think about **Monotonic Stack**.

And remember this particularly useful pattern:

> If a newly arriving element makes several previous elements irrelevant, pop those elements and combine the information they represent.

That is the central idea behind Online Stock Span.
