# **LeetCode 359. Logger Rate Limiter**

**Difficulty:** Easy\
**Topics:** Hash Table, Design, Data Stream\
**Primary data structure:** `HashMap`

Problem: [359. Logger Rate Limiter – LeetCode](https://leetcode.com/problems/logger-rate-limiter/description/?utm_source=chatgpt.com)

## **0. Simplify the problem statement**

Imagine you are building a logging system.

Messages arrive with timestamps, and you need to decide whether each message should be printed.

**Rule:** The same message can be printed only once every 10 seconds.

For a given message:

- If it has never been printed before, print it.
- If it was printed previously, print it only if at least 10 seconds have passed since its previous printed occurrence.
- Otherwise, suppress it.

Importantly, different messages have independent rate limits.

### **Example**

Input:

```
(1, "foo")
(2, "bar")
(3, "foo")
(8, "bar")
(10, "foo")
(11, "foo")
```

Output:

```
true
true
false
false
false
true
```

Explanation:

| Timestamp | Message | Decision | Reason                    |
| --------- | ------- | -------- | ------------------------- |
| 1         | foo     | true     | First occurrence          |
| 2         | bar     | true     | First occurrence          |
| 3         | foo     | false    | Only 2 seconds passed     |
| 8         | bar     | false    | Only 6 seconds passed     |
| 10        | foo     | false    | Only 9 seconds passed     |
| 11        | foo     | true     | Exactly 10 seconds passed |

Notice that the condition is:

\\[ currentTime - previousTime \geq 10 \\]

The boundary is important: **exactly 10 seconds is allowed.**

## **1. Clarifying questions to ask the interviewer**

Before implementing, clarify these assumptions:

1. **Are timestamps guaranteed to arrive in non-decreasing order?**
   - Why: If timestamps can arrive out of order, the standard HashMap solution needs additional consideration.
2. **Is the restriction applied independently to each message?**
   - Why: We need to maintain a separate timestamp for every unique message.
3. **Does exactly 10 seconds count as eligible?**
   - Why: Determines whether we use `>= 10` or `> 10`.
4. **Can messages contain arbitrary strings?**
   - Why: Helps determine whether a String-based HashMap is appropriate.

For the LeetCode problem, timestamps are guaranteed to be non-decreasing, and the restriction is independently applied to each message.

## **2. Core intuition – Remember the last accepted timestamp**

The key observation:

**We don't need to remember every occurrence of a message. We only need to remember the timestamp when it was last printed.**

Think of a dictionary:

```
Message -> Last printed timestamp

foo -> 1
bar -> 2
```

When a new message arrives:

1. Check whether the message exists in the HashMap.
2. If it doesn't exist, accept it and store its timestamp.
3. If it exists, calculate the difference between the current timestamp and its last accepted timestamp.
4. If the difference is at least 10:
   - Accept the message.
   - Update its timestamp.
5. Otherwise:
   - Reject the message.
   - Do not update its timestamp.

### **Mental model**

```
              New message arrives
                       |
                       v
              Is message present?
                 /          \
               No            Yes
               |              |
               v              v
            Accept       Current time -
               |         Last accepted time
               |              |
               |              v
               |          Difference >= 10?
               |           /          \
               |         Yes           No
               |          |             |
               |          v             v
               |        Accept        Reject
               |          |             |
               v          v             |
           Store/update timestamp       |
               |                        |
               +------------------------+
```

## **3. Edge cases to watch out for**

| Scenario                              | Expected behavior                       |
| ------------------------------------- | --------------------------------------- |
| First occurrence of a message         | Accept                                  |
| Same message after 1 second           | Reject                                  |
| Same message after 9 seconds          | Reject                                  |
| Same message after exactly 10 seconds | Accept                                  |
| Same message after 11 seconds         | Accept                                  |
| Different messages at same timestamp  | Both accepted                           |
| Rejected message appears again        | Compare against last accepted timestamp |
| Multiple messages interleaved         | Maintain independent timestamps         |

**Important trap:**

Consider:

```
(1, "foo")  -> true
(5, "foo")  -> false
(10, "foo") -> false
(11, "foo") -> true
```

At timestamp 10, only 9 seconds have passed since the last accepted occurrence at timestamp 1.

A rejected message must NOT update the timestamp.

## **4. All possible solutions**

### **Approach 1: Brute Force – Store all accepted messages**

**Idea:** Maintain a list of previously accepted messages and their timestamps.

For every incoming message, scan the list backward to find its most recent accepted occurrence.

```java

import java.util.*;

class LoggerBruteForce {

    record LogEntry(int timestamp, String message) {}

    private final List<LogEntry> acceptedLogs = new ArrayList<>();

    public boolean shouldPrintMessage(int timestamp, String message) {

        // WHY: Search backward because the most recent accepted
        // occurrence is the only timestamp that matters.
        for (int i = acceptedLogs.size() - 1; i >= 0; i--) {

            LogEntry previous = acceptedLogs.get(i);

            // WHY: Messages have independent rate limits.
            if (previous.message().equals(message)) {

                // WHY: Exactly 10 seconds is allowed.
                if (timestamp - previous.timestamp() >= 10) {

                    // WHY: Only accepted messages should be stored.
                    acceptedLogs.add(new LogEntry(timestamp, message));
                    return true;
                }

                // WHY: The most recent accepted occurrence is
                // too recent, so this message must be rejected.
                return false;
            }
        }

        // WHY: No previous accepted occurrence exists.
        // This is the first time we are printing this message.
        acceptedLogs.add(new LogEntry(timestamp, message));
        return true;
    }
}

```

**Complexity analysis:**

- Time: O(N) per operation in the worst case, because we might scan all previously accepted logs.
- Space: O(N), because we store all accepted log entries.
- N = number of accepted messages.

**Limitation:** We repeatedly scan historical data, even though we only need the latest timestamp for each message.

### **Approach 2: Optimal – HashMap**

This is the expected interview solution.

**Idea:** Replace the historical list with a HashMap.

```
HashMap<String, Integer>

foo -> 1
bar -> 2
```

Instead of searching through all historical entries, directly access the last accepted timestamp using the message as the key.

```java

import java.util.*;

class Logger {

    // WHY: Each message has an independent rate limit.
    // Store only the timestamp of its last accepted occurrence.
    //
    // Key   = Message
    // Value = Last accepted timestamp
    //
    // We do not need to store rejected occurrences.
    private final Map<String, Integer> lastPrinted = new HashMap<>();

    public Logger() {
    }

    public boolean shouldPrintMessage(int timestamp, String message) {

        // WHY: HashMap.get() returns null when the message
        // has never been accepted before.
        Integer previousTimestamp = lastPrinted.get(message);

        // CASE 1: First occurrence of this message.
        if (previousTimestamp == null) {

            // WHY: First occurrence is always eligible.
            // Record its accepted timestamp.
            lastPrinted.put(message, timestamp);

            return true;
        }

        // CASE 2: Message was accepted previously.
        //
        // WHY: At least 10 seconds must have elapsed
        // since the last ACCEPTED occurrence.
        //
        // Use >= because exactly 10 seconds is allowed.
        if (timestamp - previousTimestamp >= 10) {

            // WHY: Update only when accepting the message.
            // Rejected messages must not reset the rate limit.
            lastPrinted.put(message, timestamp);

            return true;
        }

        // CASE 3: Less than 10 seconds have elapsed.
        //
        // WHY: Reject without updating the timestamp.
        return false;
    }
}

```

**Complexity analysis:**

Let:

- N = total number of incoming messages.
- U = number of distinct messages accepted.

| Operation                | Time complexity |
| ------------------------ | --------------- |
| HashMap lookup           | O(1) average    |
| HashMap insertion/update | O(1) average    |
| `shouldPrintMessage()`   | O(1) average    |
| Constructor              | O(1)            |

**Overall:**

- Time: O(1) average per message.
- Space: O(U), where U is the number of distinct accepted messages.

In the worst case, HashMap operations can degrade due to collisions, but Java HashMap provides efficient average-case performance.

## **6. Interviewer follow-up questions**

### **Q1. Why do we update the timestamp only when a message is accepted?**

Because the restriction is based on the last time the message was actually printed, not the last time it was received.

Consider:

```
(1, "foo")  -> true
(5, "foo")  -> false
(9, "foo")  -> false
(11, "foo") -> true
```

If we updated the timestamp on rejection at time 5, the message at time 11 would incorrectly be rejected.

### **Q2. Why use HashMap instead of HashSet?**

A HashSet can tell us whether a message has appeared, but cannot tell us when it was last printed.

We need both:

- Message identity.
- Last accepted timestamp.

Therefore, HashMap is appropriate.

### **Q3. Can we optimize the space complexity further?**

The current implementation stores one entry per distinct accepted message.

If the system has millions of unique messages, memory usage can grow significantly.

One optimization is to expire old entries.

However, this requires careful consideration:

- Timestamps are guaranteed to be non-decreasing.
- An entry can be removed when its last accepted timestamp is more than or equal to 10 seconds behind the current timestamp.
- A queue can track expiration order.

For example:

```
Current timestamp = 20

Any entry with:
lastAcceptedTimestamp <= 10

Can be removed.
```

Why is this safe? A message last accepted at timestamp 10 or earlier is eligible again at timestamp 20, so forgetting its old timestamp does not change the next decision.

A queue can support this cleanup efficiently, provided expiration ordering is maintained.

### **Q4. What if timestamps arrive out of order?**

The standard solution relies on non-decreasing timestamps.

If timestamps arrive out of order, a previous timestamp could be greater than the current timestamp, making the subtraction invalid for the intended chronological interpretation.

We would need to clarify the event-time semantics and potentially maintain more historical information.

### **Q5. What if the rate limit changes from 10 seconds to 60 seconds?**

Make the rate limit configurable:

```java
private final int rateLimitSeconds;

public Logger(int rateLimitSeconds) {
    this.rateLimitSeconds = rateLimitSeconds;
}
```

Then replace:

```java
timestamp - previousTimestamp >= 10
```

with:

```java
timestamp - previousTimestamp >= rateLimitSeconds
```

### **Q6. What if this logger is distributed across multiple servers?**

A local HashMap is insufficient because different servers would maintain different timestamps.

A distributed solution could use Redis:

- Store the message as the key.
- Use an atomic operation such as `SET key value NX EX 10`.
- If the operation succeeds, allow the message.
- Otherwise, reject it.

The atomic operation ensures concurrent requests across servers cannot both bypass the rate limit.

## **7. Final interview takeaway**

| Approach                  | Time per operation | Space | Recommendation |
| ------------------------- | ------------------ | ----- | -------------- |
| ArrayList + backward scan | O(N)               | O(N)  | Brute force    |
| HashMap                   | O(1) average       | O(U)  | Optimal        |

**The key pattern to remember:**

Whenever a problem asks you to enforce a rule based on the *last occurrence of an item*, think about:

```java
HashMap<Item, LastOccurrence>
```

This pattern is useful in:

- Rate limiters
- Duplicate detection
- Event processing
- Session tracking
- API throttling
- Recent activity tracking

**Interview recommendation:** Start with the brute-force approach to establish correctness, identify that historical scanning is unnecessary, and then derive the HashMap solution. The HashMap implementation is the one you should submit to LeetCode.
