# **LeetCode 1429 — First Unique Number**

**Difficulty:** Medium\
**Topics:** Design, Hash Table, Queue, Linked List, Ordered Set

Problem: [1429. First Unique Number](https://leetcode.com/problems/first-unique-number/description/?utm_source=chatgpt.com)

## **0. Simplify the problem**

You are given a stream of integers and need to design a data structure that efficiently finds the **first number that has appeared exactly once**.

Implement:

```
FirstUnique(int[] nums)
int showFirstUnique()
void add(int value)
```

- `FirstUnique(nums)`: Initialize the data structure with the given numbers.
- `showFirstUnique()`: Return the first number that currently appears exactly once. Return `-1` if no such number exists.
- `add(value)`: Add a new number to the stream.

### **Example**

```
Initial numbers: [2, 3, 5]

showFirstUnique() -> 2

add(5)
Numbers: [2, 3, 5, 5]

showFirstUnique() -> 2

add(2)
Numbers: [2, 3, 5, 5, 2]

showFirstUnique() -> 3

add(3)
Numbers: [2, 3, 5, 5, 2, 3]

showFirstUnique() -> -1
```

Notice something important:

- `2` is initially unique.
- When `5` appears again, it stops being unique.
- When `2` appears again, `3` becomes the first unique number.
- Eventually, all numbers become duplicates.

**The challenge:** We need to support insertion and finding the first unique number efficiently.

## **1. Clarifying questions to ask the interviewer**

Before implementing, clarify these details:

1. **Does unique mean frequency exactly one?**\
   Yes. A number appearing once is unique; appearing twice or more is not.
2. **Does&#x20;**`showFirstUnique()`**&#x20;remove the returned element?**\
   No. It only returns the first unique number. Subsequent calls should return the same number unless an `add()` changes its frequency.
3. **Can a duplicate become unique again?**\
   No. Since this is an append-only stream, frequencies never decrease.
4. **Can numbers be negative or zero?**\
   The published constraints specify positive integers, so `-1` is a safe sentinel.
5. **What are the expected operation complexities?**\
   Ideally, `add()` and `showFirstUnique()` should both take O(1) time on average or amortized.

## **2. Core intuition and mental model**

The problem has two independent requirements:

- **Frequency tracking:** Know whether a number appears exactly once.
- **Insertion-order tracking:** Know which unique number appeared earliest.

A single data structure does not naturally solve both requirements efficiently.

We combine a HashMap and an ordered collection.

### **Approach A: HashMap + Queue (Lazy Deletion)**

This is the easiest optimal approach to understand.

Maintain:

```
frequency: HashMap<Integer, Integer>
queue:     Queue<Integer>
```

The HashMap tracks frequencies, while the queue tracks insertion order.

**Important trick: Lazy deletion**

Instead of removing duplicates from the middle of the queue, leave them there.

Whenever `showFirstUnique()` is called:

1. Inspect the queue's front.
2. If its frequency is greater than one, remove it.
3. Repeat until the front is unique or the queue becomes empty.
4. Return the front or `-1`.

Why does this work?

Once a number becomes a duplicate, it can never become unique again. Therefore, removing it permanently from the front is safe.

**Key observation:** Each queue element is removed at most once. Therefore, although one query might remove many elements, the total work across all queries is linear.

### **Approach B: HashMap + LinkedHashSet**

We can improve the queue approach by keeping only currently unique numbers.

A `LinkedHashSet` provides:

- Hash-based lookup.
- Insertion-order preservation.
- Average O(1) insertion.
- Average O(1) removal.
- Access to the first element through an iterator.

When a number appears:

| Frequency transition | Action                    |
| -------------------- | ------------------------- |
| 0 → 1                | Add to LinkedHashSet      |
| 1 → 2                | Remove from LinkedHashSet |
| 2 → 3                | Do nothing                |
| 3 → 4                | Do nothing                |

Now `showFirstUnique()` simply returns the first element of the set.

This is particularly elegant because the set always contains exactly the currently unique numbers, in their original insertion order.

## **3. Edge cases to watch out for**

| Edge case                                                     | Expected behavior                                |
| ------------------------------------------------------------- | ------------------------------------------------ |
| All numbers are duplicates                                    | Return `-1`                                      |
| Only one number exists                                        | Return that number                               |
| Duplicate appears immediately                                 | Return `-1` if no other unique exists            |
| Duplicate of the first unique number                          | Move to the next unique number                   |
| Several consecutive duplicates                                | Skip all of them                                 |
| New number added after all existing numbers become duplicates | Return the newly added number                    |
| Multiple consecutive `showFirstUnique()` calls                | Return the same value                            |
| Many additions without queries                                | Maintain correct frequencies and insertion order |

## **4. All solutions in Java 24**

### **Solution 1: Brute Force — ArrayList + Frequency Scan**

**Mental model:** Store the entire stream. Whenever asked for the first unique number, scan the stream from beginning to end and count how many times each candidate appears.

```java

import java.util.*;

class FirstUniqueBruteForce {

    private final List<Integer> stream = new ArrayList<>();

    public FirstUniqueBruteForce(int[] nums) {
        // Store every number in its original insertion order.
        for (int num : nums) {
            stream.add(num);
        }
    }

    public void add(int value) {
        // Appending to an ArrayList is O(1) amortized.
        stream.add(value);
    }

    public int showFirstUnique() {

        // Examine candidates in insertion order.
        for (int i = 0; i < stream.size(); i++) {

            int candidate = stream.get(i);
            int frequency = 0;

            // Count how many times this candidate appears.
            // This nested scan makes the approach expensive.
            for (int j = 0; j < stream.size(); j++) {
                if (stream.get(j) == candidate) {
                    frequency++;
                }
            }

            // The first candidate with frequency exactly 1
            // is the earliest unique number.
            if (frequency == 1) {
                return candidate;
            }
        }

        return -1;
    }

    /*
     * TIME COMPLEXITY:
     *
     * Constructor: O(n)
     * add():       O(1) amortized
     * show():      O(n^2) worst case
     *
     * Why O(n^2)?
     * For every element, we potentially scan the entire
     * stream to count its occurrences.
     *
     * SPACE COMPLEXITY:
     *
     * O(n) for storing the complete stream.
     *
     * This solution is correct but inefficient for
     * repeated showFirstUnique() operations.
     */
}

```

### **Solution 2: HashMap + Queue — Lazy Deletion**

This is my recommended interview solution because the reasoning is simple and the complexity is excellent.

```java

import java.util.*;

class FirstUnique {

    private final Map<Integer, Integer> frequency = new HashMap<>();

    private final Queue<Integer> queue = new ArrayDeque<>();

    public FirstUnique(int[] nums) {

        // Reuse add() to ensure initialization and subsequent
        // insertions follow exactly the same frequency logic.
        for (int num : nums) {
            add(num);
        }
    }

    public void add(int value) {

        // Every occurrence is recorded in the frequency map.
        frequency.merge(value, 1, Integer::sum);

        // Preserve the original insertion order.
        // We intentionally do NOT remove duplicates here.
        // They will be removed lazily when they reach the front.
        queue.offer(value);
    }

    public int showFirstUnique() {

        // Keep removing elements from the front while they
        // are no longer unique.
        //
        // Why is this safe?
        // The stream only supports additions. Once a number
        // becomes duplicated, it can NEVER become unique again.
        while (!queue.isEmpty()
                && frequency.get(queue.peek()) > 1) {

            queue.poll();
        }

        // The front is guaranteed to be the earliest number
        // whose frequency is exactly one.
        return queue.isEmpty() ? -1 : queue.peek();
    }

    /*
     * TIME COMPLEXITY:
     *
     * Constructor: O(n) average.
     *
     * add(): O(1) average.
     *
     * showFirstUnique():
     *     O(1) worst case if no elements need removal.
     *     O(n) worst case for a single call.
     *     O(1) amortized across all calls.
     *
     * Why amortized O(1)?
     *
     * Every element is inserted into the queue exactly once.
     * Every element can be removed from the queue at most once.
     *
     * Therefore, across m insertions and queries, the total
     * number of queue removals cannot exceed m.
     *
     * Total queue work = O(m).
     * Amortized work per operation = O(1).
     *
     * SPACE COMPLEXITY:
     *
     * O(n + m), where:
     * n = initial number of elements.
     * m = number of subsequent additions.
     *
     * The frequency map stores distinct values.
     * The queue can retain duplicate/stale entries until
     * showFirstUnique() removes them.
     *
     * This is an optimal asymptotic solution.
     */
}

```

### **Solution 3: HashMap + LinkedHashSet — Maintain Only Unique Numbers**

This is another excellent solution, and it gives worst-case O(1) structural operations under the usual HashMap assumptions.

Instead of storing every occurrence in a queue, maintain only numbers whose frequency is exactly one.

```java

import java.util.*;

class FirstUnique {

    private final Map<Integer, Integer> frequency = new HashMap<>();

    // LinkedHashSet preserves insertion order while allowing
    // average O(1) insertion and removal.
    private final LinkedHashSet<Integer> unique = new LinkedHashSet<>();

    public FirstUnique(int[] nums) {

        // Process the initial stream exactly like future additions.
        for (int num : nums) {
            add(num);
        }
    }

    public void add(int value) {

        // Obtain the previous frequency.
        int oldFrequency = frequency.getOrDefault(value, 0);

        // Record the new frequency.
        frequency.put(value, oldFrequency + 1);

        if (oldFrequency == 0) {

            // Case 1: First occurrence.
            // The number becomes unique, so append it to the set.
            unique.add(value);

        } else if (oldFrequency == 1) {

            // Case 2: Second occurrence.
            // The number is no longer unique.
            // Remove it even if it is somewhere in the middle.
            unique.remove(value);

        } else {

            // Case 3: Third or subsequent occurrence.
            // It is already non-unique, so nothing else is needed.
        }
    }

    public int showFirstUnique() {

        // The first element of LinkedHashSet is always
        // the earliest number that currently occurs exactly once.
        //
        // iterator().next() does not remove the element.
        Iterator<Integer> iterator = unique.iterator();

        return iterator.hasNext() ? iterator.next() : -1;
    }

    /*
     * TIME COMPLEXITY:
     *
     * Constructor: O(n) average.
     *
     * add(): O(1) average.
     *
     * showFirstUnique(): O(1) average.
     *
     * Why?
     *
     * HashMap provides average O(1) frequency lookup/update.
     * LinkedHashSet provides average O(1) insertion/removal.
     * Its iterator can retrieve the first element in O(1).
     *
     * Unlike the lazy queue, showFirstUnique() never needs
     * to remove stale elements.
     *
     * SPACE COMPLEXITY:
     *
     * O(d), where d is the number of distinct values ever seen.
     *
     * HashMap stores each distinct number once.
     * LinkedHashSet stores only currently unique numbers.
     *
     * This avoids retaining duplicate occurrences in the
     * ordering structure.
     */
}

```

### **Comparison of all approaches**

| Approach                | Constructor | add()          | showFirstUnique() | Extra space |
| ----------------------- | ----------- | -------------- | ----------------- | ----------- |
| Brute force             | O(n)        | O(1) amortized | O(n²)             | O(n)        |
| HashMap + Queue         | O(n)        | O(1) average   | O(1) amortized    | O(n + m)    |
| HashMap + LinkedHashSet | O(n)        | O(1) average   | O(1) average      | O(d)        |

Where:

- `n` = initial array length.
- `m` = subsequent additions.
- `d` = distinct numbers encountered.

**My interview recommendation:**

- Explain HashMap + Queue first because lazy deletion demonstrates amortized analysis.
- Present HashMap + LinkedHashSet as an alternative when the interviewer wants to maintain only currently unique elements.

Both are excellent solutions.

## **5. Why not use a PriorityQueue (Min Heap)?**

A common question is whether a heap can solve this.

A min heap orders elements by their numerical values, not by insertion time.

But this problem requires the earliest inserted unique number, not the smallest unique number.

For example:

```
Stream: [50, 10, 30]

First unique = 50
Smallest unique = 10
```

A normal min heap would return the wrong answer.

We could store `(insertionIndex, value)` pairs, but removing arbitrary duplicates efficiently becomes complicated. A HashMap with an ordered collection is simpler.

## **6. Interviewer follow-up questions and answers**

### **Q1. Why can't we use only a HashMap?**

A HashMap tracks frequencies but does not preserve insertion order.

For example:

```
Stream: [50, 10, 30]

Frequency:
50 -> 1
10 -> 1
30 -> 1
```

We need `50`, not `10`.

A separate ordered data structure is necessary.

### **Q2. Why can't we use only a Queue?**

A queue preserves insertion order but cannot efficiently determine whether an element is duplicated.

We need frequency information, which is why we combine it with a HashMap.

### **Q3. Why is lazy deletion safe?**

Because the stream only grows.

Once a number's frequency becomes greater than one, its frequency can never decrease.

Therefore, it can never become unique again.

Removing it permanently is safe.

### **Q4. Is&#x20;**`showFirstUnique()`**&#x20;really O(1) in the queue solution?**

Not necessarily for an individual call.

Consider:

```
Queue: [1, 2, 3, 4, 5]
Frequency:
1 -> 2
2 -> 2
3 -> 2
4 -> 2
5 -> 1
```

One call removes four elements.

Its worst-case time is O(n).

However, each element can be removed only once throughout the lifetime of the data structure.

Therefore, the amortized complexity is O(1).

### **Q5. Can we use a normal HashSet instead of LinkedHashSet?**

No.

A normal HashSet does not guarantee insertion order.

We need the first inserted unique number, so insertion order matters.

### **Q6. Can a number become unique again?**

No, because this is an append-only stream.

For example:

```
[5]       -> unique
[5, 5]    -> duplicate
[5, 5, 5] -> still duplicate
```

There is no removal operation that could decrease its frequency.

### **Q7. What if the interviewer adds a remove operation?**

Now the problem changes significantly.

A number could transition:

```
Frequency 1 -> 2 -> 1
```

The simple lazy-deletion approach no longer works.

We would need a more sophisticated ordered structure that supports moving elements into and out of the unique collection while preserving the appropriate order.

A HashMap + LinkedHashSet can still work if the semantics are carefully defined and we maintain the frequency transitions.

### **Q8. Can we achieve worst-case O(1) for all operations?**

With a doubly linked list and a HashMap mapping each currently unique value to its linked-list node, we can achieve O(1) pointer operations:

- First occurrence: append a node.
- Second occurrence: remove its node.
- Third or later occurrence: do nothing.
- Query: return the head.

HashMap operations are still generally considered O(1) average, not guaranteed O(1) worst-case.

## **7. Optimal approach — Doubly Linked List + HashMap (Advanced)**

This is worth knowing for senior-level interviews.

Instead of using `LinkedHashSet`, explicitly maintain:

```
HashMap<Integer, Node>
Doubly Linked List
```

The linked list contains only currently unique numbers.

The HashMap maps each unique number to its corresponding node.

When a number appears for the first time, create a node and append it.

When it appears for the second time, remove its node in O(1), using the HashMap reference.

The list's head always contains the first unique number.

```
                 HashMap
             +-------------+
             | 10 -> Node  |
             | 20 -> Node  |
             | 30 -> Node  |
             +-------------+
                    |
                    v

HEAD <-> [10] <-> [20] <-> [30] <-> TAIL
           ^
           |
      First unique
```

Java implementation:

```java

import java.util.*;

class FirstUnique {

    private static class Node {
        int value;
        Node prev;
        Node next;

        Node(int value) {
            this.value = value;
        }
    }

    private final Map<Integer, Node> uniqueNodes = new HashMap<>();

    private final Map<Integer, Integer> frequency = new HashMap<>();

    // Dummy nodes eliminate special cases when inserting
    // or removing the first and last real nodes.
    private final Node head = new Node(-1);
    private final Node tail = new Node(-1);

    public FirstUnique(int[] nums) {

        head.next = tail;
        tail.prev = head;

        for (int num : nums) {
            add(num);
        }
    }

    public void add(int value) {

        int oldFrequency = frequency.getOrDefault(value, 0);
        frequency.put(value, oldFrequency + 1);

        if (oldFrequency == 0) {

            // First occurrence: create and append a node.
            Node node = new Node(value);

            uniqueNodes.put(value, node);
            insertAtTail(node);

        } else if (oldFrequency == 1) {

            // Second occurrence: this value is no longer unique.
            // The HashMap gives us direct access to its node.
            Node node = uniqueNodes.remove(value);

            removeNode(node);
        }

        // Further occurrences do not change the unique list.
    }

    private void insertAtTail(Node node) {

        // Insert immediately before the dummy tail.
        Node previous = tail.prev;

        previous.next = node;
        node.prev = previous;

        node.next = tail;
        tail.prev = node;
    }

    private void removeNode(Node node) {

        // Remove a node in O(1) using its previous and next links.
        node.prev.next = node.next;
        node.next.prev = node.prev;

        // Disconnect references for clarity.
        node.prev = null;
        node.next = null;
    }

    public int showFirstUnique() {

        // An empty list contains only the two dummy nodes.
        return head.next == tail ? -1 : head.next.value;
    }

    /*
     * TIME COMPLEXITY:
     *
     * Constructor: O(n) average.
     * add():       O(1) average.
     * show():      O(1).
     *
     * SPACE COMPLEXITY:
     *
     * O(d), where d is the number of distinct values.
     *
     * WHY THIS WORKS:
     *
     * The doubly linked list preserves insertion order.
     * The HashMap provides direct access to unique nodes.
     *
     * Consequently, we can remove a duplicated value
     * from anywhere in the list without scanning.
     *
     * This is the classic HashMap + Doubly Linked List
     * design pattern.
     */
}

```

## **8. Final interview takeaway**

Remember this problem as a combination of two fundamental patterns:

| Requirement                           | Data structure                             |
| ------------------------------------- | ------------------------------------------ |
| Track occurrences                     | HashMap                                    |
| Preserve insertion order              | Queue / LinkedHashSet / Doubly Linked List |
| Remove invalid candidates efficiently | Lazy deletion or direct node removal       |
| Retrieve earliest valid candidate     | Front / first iterator element / head      |

**Three important concepts to take away:**

1. **HashMap + Queue:** Lazy deletion and amortized O(1) complexity.
2. **HashMap + LinkedHashSet:** Maintain only currently unique elements.
3. **HashMap + Doubly Linked List:** Direct removal of arbitrary unique elements in O(1).

For LeetCode 1429, I would submit **Solution 2 (HashMap + Queue)**. It is concise, easy to explain, and comfortably satisfies the constraints.
