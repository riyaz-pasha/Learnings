# **295. Find Median from Data Stream**

**Difficulty:** Hard\
**Pattern:** Two Heaps / Priority Queue / Data Stream

## **0. Understand the problem**

We need to design a data structure that continuously receives integers and can return the median of all numbers received so far.

Unlike a normal array problem:

- We don't know all elements in advance.
- New elements arrive one at a time.
- We must efficiently maintain the median after every insertion.
- We should avoid sorting the entire collection every time `findMedian()` is called.

**Example:**

```
addNum(1)
Stream: [1]
Median = 1

addNum(2)
Stream: [1, 2]
Median = (1 + 2) / 2 = 1.5

addNum(3)
Stream: [1, 2, 3]
Median = 2

addNum(4)
Stream: [1, 2, 3, 4]
Median = (2 + 3) / 2 = 2.5
```

The challenge is to efficiently maintain the middle element(s) while numbers keep arriving.

## **1. Clarifying questions to ask the interviewer**

| Question                                                                | Why clarify?                                        |
| ----------------------------------------------------------------------- | --------------------------------------------------- |
| Can duplicate numbers occur?                                            | Our data structure must support duplicates.         |
| Can negative numbers occur?                                             | We must not assume non-negative values.             |
| Is the stream unbounded?                                                | Determines whether we need memory optimizations.    |
| Can `findMedian()` be called multiple times without insertion?          | The median should remain unchanged.                 |
| Is insertion more frequent than median retrieval?                       | Helps choose the appropriate data structure.        |
| Is the input guaranteed to contain at least one number before querying? | Determines whether empty-stream handling is needed. |

For this problem, LeetCode guarantees:

- Duplicates are allowed.
- Numbers can be negative.
- At least one number exists before `findMedian()`.
- At most 50,000 operations occur.

## **2. Core idea: Two Heaps**

The key observation:

**We don't need to sort the entire stream. We only need to maintain the middle of the sorted stream.**

We can divide all numbers into two halves:

1. Left half: Contains the smaller numbers.
2. Right half: Contains the larger numbers.

We maintain these two halves using two heaps.

### **Heap 1: Max Heap (Left Half)**

Stores the smaller half of the numbers.

The largest element in the smaller half should be accessible immediately.

```
PriorityQueue<Integer> maxHeap =
    new PriorityQueue<>(Comparator.reverseOrder());
```

### **Heap 2: Min Heap (Right Half)**

Stores the larger half of the numbers.

The smallest element in the larger half should be accessible immediately.

```
PriorityQueue<Integer> minHeap =
    new PriorityQueue<>();
```

### **Important invariants**

We maintain two rules throughout the algorithm.

**Rule 1: Ordering invariant**

Every element in the left half must be less than or equal to every element in the right half.

```
maxHeap.peek() <= minHeap.peek()
```

**Rule 2: Size invariant**

The sizes of the heaps can differ by at most one.

```
maxHeap.size() == minHeap.size()

OR

maxHeap.size() == minHeap.size() + 1
```

We intentionally allow the left heap to contain one extra element.

Why?

Because when the total number of elements is odd, the median will be the largest element in the left half.

### **Visual representation**

Suppose the stream is:

```
[5, 2, 8, 1, 9, 3]
```

After sorting:

```
[1, 2, 3, 5, 8, 9]
```

We divide it into two halves:

```
        LEFT HALF              RIGHT HALF

          Max Heap              Min Heap

             3                     5
            / \                   / \
           1   2                 8   9

      maxHeap.peek()         minHeap.peek()
             3                     5
```

Therefore:

```
Median = (3 + 5) / 2 = 4.0
```

Notice that we never sorted the entire stream. We only maintained the two heaps.

## **3. Optimal approach: Step-by-step insertion**

Let's understand how `addNum()` works.

Suppose the stream is:

```
[5, 2, 8, 1]
```

After processing these numbers:

```
maxHeap = [2, 1]
minHeap = [5, 8]
```

Now insert `3`.

### **Step 1: Insert into maxHeap**

We initially insert the new number into the max heap.

```
maxHeap = [3, 2, 1]
minHeap = [5, 8]
```

### **Step 2: Balance the heaps**

Our invariant requires:

```
maxHeap.size() == minHeap.size()

OR

maxHeap.size() == minHeap.size() + 1
```

Currently:

```
maxHeap.size() = 3
minHeap.size() = 2
```

This is valid.

The resulting heaps are:

```
maxHeap = [3, 2, 1]
minHeap = [5, 8]
```

Median:

```
maxHeap.peek() = 3
```

Therefore, median = `3`.

### **What happens when the right heap becomes larger?**

Suppose we insert `4`.

After inserting into max heap:

```
maxHeap = [4, 3, 2, 1]
minHeap = [5, 8]
```

Now the left heap has two extra elements.

Move the largest element from max heap to min heap.

```
minHeap.offer(maxHeap.poll());
```

Result:

```
maxHeap = [3, 2, 1]
minHeap = [4, 5, 8]
```

Now the size difference is one, and the ordering invariant is preserved.

# **4. All possible solutions**

## **Approach 1: Brute Force — Store and Sort**

### **Idea**

Store all incoming numbers in an ArrayList.

Whenever `findMedian()` is called:

1. Sort the entire list.
2. Find the middle element(s).
3. Return the median.

```
import java.util.*;

class MedianFinder {

    private final List<Integer> numbers = new ArrayList<>();

    public void addNum(int num) {

        /*
         * Simply append the incoming number.
         *
         * Time Complexity: O(1) amortized.
         */
        numbers.add(num);
    }

    public double findMedian() {

        /*
         * Sort all elements every time we need the median.
         *
         * Why?
         * The median is determined by the middle position
         * in the sorted sequence.
         *
         * Time Complexity: O(n log n).
         */
        Collections.sort(numbers);

        int n = numbers.size();

        /*
         * Odd number of elements:
         * The middle element is the median.
         */
        if (n % 2 == 1) {
            return numbers.get(n / 2);
        }

        /*
         * Even number of elements:
         * Average the two middle elements.
         *
         * Convert to long before addition to avoid integer overflow
         * for unrestricted integer inputs.
         */
        return ((long) numbers.get(n / 2 - 1)
                + numbers.get(n / 2)) / 2.0;
    }
}

/*
 * COMPLEXITY:
 *
 * addNum():
 * O(1) amortized.
 *
 * findMedian():
 * O(n log n) because we sort the entire list.
 *
 * Space:
 * O(n) for storing all incoming elements.
 *
 * Problem:
 * Repeated median queries become expensive.
 */
```

**Why is this inefficient?**

Suppose we receive 50,000 numbers and call `findMedian()` after every insertion.

We repeatedly sort almost the same elements.

We are doing unnecessary work.

## **Approach 2: Maintain a Sorted ArrayList**

### **Idea**

Instead of sorting during every median query, maintain the list in sorted order during insertion.

For each new number:

1. Use binary search to find its correct insertion position.
2. Insert the number at that position.
3. Retrieve the median directly.

Binary search finds the insertion position in `O(log n)`.

However, inserting into an ArrayList requires shifting elements.

Therefore, actual insertion takes `O(n)`.

```
import java.util.*;

class MedianFinder {

    private final List<Integer> numbers = new ArrayList<>();

    public void addNum(int num) {

        /*
         * Binary search finds the insertion position.
         *
         * If the number exists multiple times, any valid
         * insertion position among equal values is acceptable.
         */
        int index = Collections.binarySearch(numbers, num);

        /*
         * A negative result means the element does not exist.
         *
         * Convert the encoded insertion point into an index.
         */
        if (index < 0) {
            index = -index - 1;
        }

        /*
         * Insert while preserving sorted order.
         *
         * ArrayList shifts subsequent elements to the right.
         *
         * Time Complexity: O(n).
         */
        numbers.add(index, num);
    }

    public double findMedian() {

        /*
         * Since the list is always sorted,
         * no additional sorting is required.
         */
        int n = numbers.size();

        if (n % 2 == 1) {
            return numbers.get(n / 2);
        }

        return ((long) numbers.get(n / 2 - 1)
                + numbers.get(n / 2)) / 2.0;
    }
}

/*
 * COMPLEXITY:
 *
 * addNum():
 * O(log n) for binary search + O(n) for shifting.
 * Overall O(n).
 *
 * findMedian():
 * O(1), because ArrayList supports random access.
 *
 * Space:
 * O(n).
 *
 * Trade-off:
 * We make insertion expensive to make median retrieval cheap.
 */
```

**When is this useful?**

When median queries are extremely frequent and insertions are relatively infrequent.

However, for a continuous stream, `O(n)` insertion is not ideal.

## **Approach 3: Optimal — Two Heaps**

This is the expected solution for the interview.

### **Java 24 implementation**

```
import java.util.*;

class MedianFinder {

    /*
     * MAX HEAP:
     *
     * Stores the smaller half of all incoming numbers.
     *
     * The largest element of the smaller half is always
     * available at the root.
     *
     * This element is one of the two possible median candidates.
     */
    private final PriorityQueue<Integer> maxHeap =
            new PriorityQueue<>(Comparator.reverseOrder());

    /*
     * MIN HEAP:
     *
     * Stores the larger half of all incoming numbers.
     *
     * The smallest element of the larger half is always
     * available at the root.
     *
     * This element is the other possible median candidate.
     */
    private final PriorityQueue<Integer> minHeap =
            new PriorityQueue<>();

    public MedianFinder() {

        /*
         * Initially, both heaps are empty.
         *
         * We maintain two invariants throughout the algorithm:
         *
         * 1. ORDERING INVARIANT:
         *
         *    Every element in maxHeap must be <= every element
         *    in minHeap.
         *
         *    Therefore:
         *
         *    maxHeap.peek() <= minHeap.peek()
         *
         *    whenever both heaps are non-empty.
         *
         * 2. SIZE INVARIANT:
         *
         *    maxHeap.size() == minHeap.size()
         *
         *    OR
         *
         *    maxHeap.size() == minHeap.size() + 1
         *
         *    We intentionally keep the extra element in maxHeap.
         */
    }

    public void addNum(int num) {

        /*
         * STEP 1: Insert the incoming number into maxHeap.
         *
         * Why maxHeap?
         *
         * We want maxHeap to contain the smaller half.
         * Its root should represent the largest element
         * among the smaller numbers.
         */
        maxHeap.offer(num);

        /*
         * STEP 2: Restore the ordering invariant.
         *
         * Consider:
         *
         * maxHeap = [10, 5, 3]
         * minHeap = [7, 12]
         *
         * Here:
         *
         * maxHeap.peek() = 10
         * minHeap.peek() = 7
         *
         * This violates our ordering invariant.
         *
         * We move the largest element of maxHeap into minHeap.
         *
         * After moving:
         *
         * maxHeap = [7, 5, 3]
         * minHeap = [10, 12]
         *
         * Now every element in maxHeap is <= every element
         * in minHeap.
         *
         * Notice that moving the root is sufficient because
         * the heaps already maintain their internal ordering.
         */
        if (!minHeap.isEmpty()
                && maxHeap.peek() > minHeap.peek()) {

            minHeap.offer(maxHeap.poll());
        }

        /*
         * STEP 3: Restore the size invariant.
         *
         * Our desired condition is:
         *
         * maxHeap.size() == minHeap.size()
         *
         * OR
         *
         * maxHeap.size() == minHeap.size() + 1
         *
         * If minHeap becomes larger, move its smallest
         * element into maxHeap.
         *
         * This ensures that:
         *
         * - Both heaps have equal sizes, OR
         * - maxHeap has exactly one extra element.
         */
        if (maxHeap.size() < minHeap.size()) {

            maxHeap.offer(minHeap.poll());
        }
    }

    public double findMedian() {

        /*
         * CASE 1: Odd number of elements.
         *
         * Since maxHeap is allowed to contain one extra element,
         * its root represents the middle element.
         *
         * Example:
         *
         * Sorted: [1, 2, 3, 4, 5]
         *
         * maxHeap: [3, 2, 1]
         * minHeap: [4, 5]
         *
         * Median = maxHeap.peek() = 3.
         */
        if (maxHeap.size() > minHeap.size()) {

            return maxHeap.peek();
        }

        /*
         * CASE 2: Even number of elements.
         *
         * Both heaps contain the same number of elements.
         *
         * The two middle elements are:
         *
         * maxHeap.peek() -> Largest element in smaller half.
         * minHeap.peek() -> Smallest element in larger half.
         *
         * Median = Average of these two elements.
         *
         * Cast to long BEFORE addition to prevent integer overflow.
         *
         * Example:
         *
         * maxHeap.peek() = 3
         * minHeap.peek() = 4
         *
         * Median = (3 + 4) / 2.0 = 3.5.
         */
        return ((long) maxHeap.peek()
                + minHeap.peek()) / 2.0;
    }
}

/*
 * ==========================================
 * COMPLEXITY ANALYSIS
 * ==========================================
 *
 * Let n = number of elements currently in the stream.
 *
 * addNum():
 *
 * 1. maxHeap.offer(num):
 *    O(log n).
 *
 * 2. maxHeap.poll() / minHeap.offer():
 *    O(log n) in the worst case.
 *
 * 3. minHeap.poll() / maxHeap.offer():
 *    O(log n) in the worst case.
 *
 * There are only a constant number of heap operations.
 *
 * Overall: O(log n).
 *
 *
 * findMedian():
 *
 * Only accesses the roots and compares heap sizes.
 *
 * PriorityQueue.peek() = O(1).
 *
 * Overall: O(1).
 *
 *
 * SPACE:
 *
 * Every incoming number is stored in exactly one heap.
 *
 * maxHeap + minHeap = n elements.
 *
 * Overall: O(n).
 *
 *
 * FINAL:
 *
 * addNum()     -> O(log n)
 * findMedian() -> O(1)
 * Space        -> O(n)
 */
```

### **Why does this algorithm work?**

Let's prove the two invariants.

**1. Ordering invariant**

Initially, both heaps are empty.

When inserting a number:

- We first insert it into maxHeap.
- If its value is greater than the smallest element in minHeap, we move the maximum element from maxHeap into minHeap.

This restores the ordering between the two halves.

**2. Size invariant**

After insertion and ordering correction, the heaps can differ in size by at most two.

If minHeap becomes larger, we move one element from minHeap to maxHeap.

Consequently:

```
maxHeap.size() == minHeap.size()

OR

maxHeap.size() == minHeap.size() + 1
```

Both invariants are maintained after every insertion.

Therefore, the roots always represent the middle element(s).

# **6. Follow-up questions**

## **Follow-up 1: What if all integers are in the range [0, 100]?**

We can optimize using a frequency array instead of heaps.

Since there are only 101 possible values, maintain:

```
int[] frequency = new int[101];
int size = 0;
```

Every incoming number increments its frequency.

To find the median:

1. Determine the middle position(s).
2. Traverse the frequency array from 0 to 100.
3. Accumulate frequencies until we reach the required position(s).

### **Java implementation**

```
class MedianFinder {

    /*
     * frequency[i] represents the number of occurrences of i.
     *
     * Since values are restricted to [0, 100],
     * only 101 counters are required.
     */
    private final int[] frequency = new int[101];

    /*
     * Total number of elements inserted so far.
     */
    private int size = 0;

    public void addNum(int num) {

        /*
         * Increment the frequency of the incoming number.
         *
         * Time Complexity: O(1).
         */
        frequency[num]++;
        size++;
    }

    public double findMedian() {

        /*
         * For an odd number of elements:
         * We need the element at zero-based index size / 2.
         *
         * For an even number of elements:
         * We need elements at indexes size / 2 - 1
         * and size / 2.
         */
        int leftPosition = (size - 1) / 2;
        int rightPosition = size / 2;

        int cumulativeCount = 0;

        int leftValue = -1;
        int rightValue = -1;

        /*
         * Traverse the frequency array.
         *
         * cumulativeCount tells us how many elements
         * we have encountered in sorted order.
         *
         * Example:
         *
         * frequency[2] = 2
         * frequency[5] = 1
         * frequency[8] = 1
         *
         * Sorted stream = [2, 2, 5, 8]
         */
        for (int value = 0; value <= 100; value++) {

            cumulativeCount += frequency[value];

            /*
             * Capture the element at the left median position.
             */
            if (leftValue == -1
                    && cumulativeCount > leftPosition) {

                leftValue = value;
            }

            /*
             * Capture the element at the right median position.
             */
            if (cumulativeCount > rightPosition) {

                rightValue = value;
                break;
            }
        }

        /*
         * For odd size, both positions are identical.
         *
         * For even size, average the two middle values.
         */
        return (leftValue + rightValue) / 2.0;
    }
}

/*
 * COMPLEXITY:
 *
 * addNum():
 * O(1).
 *
 * findMedian():
 * O(101) = O(1), because the range is fixed.
 *
 * Space:
 * O(101) = O(1).
 *
 * This is an example of using a bounded value domain
 * to replace a comparison-based data structure.
 */
```

**Interview insight:** This solution is particularly efficient because the input domain is fixed and very small.

## **Follow-up 2: What if 99% of numbers are in [0, 100]?**

This is more interesting.

We cannot simply use a frequency array because the remaining 1% can contain values outside the range.

We need to support arbitrary integers while optimizing the common case.

### **Idea: Hybrid Frequency Array + Two Heaps**

Maintain:

1. A frequency array for values in `[0, 100]`.
2. A max heap for values smaller than `0`.
3. A min heap for values greater than `100`.

```
           Negative values
                |
              Max Heap
                |
                v

       [0, 1, 2, ... 100]
          Frequency Array

                |
                v
           Min Heap
                |
           Values > 100
```

However, there is an important subtlety:

**We cannot independently find the median of these three structures and combine their medians.**

We need to locate the global middle position.

One way is to calculate the rank of each value using:

- Negative heap elements.
- Frequency counts.
- Positive heap elements.

For an interview implementation, an easier general-purpose hybrid is to maintain a frequency array for `[0, 100]` and two heaps for out-of-range values, then use rank selection across the three partitions.

### **Java implementation**

```
import java.util.*;

class MedianFinder {

    /*
     * Values in [0, 100].
     *
     * Each index stores the frequency of that value.
     */
    private final int[] frequency = new int[101];

    /*
     * Values smaller than 0.
     *
     * We need the largest negative value first because
     * it is closest to the frequency-array partition.
     */
    private final PriorityQueue<Integer> negative =
            new PriorityQueue<>(Comparator.reverseOrder());

    /*
     * Values greater than 100.
     *
     * We need the smallest positive-outlier value first.
     */
    private final PriorityQueue<Integer> positive =
            new PriorityQueue<>();

    private int totalSize = 0;

    public void addNum(int num) {

        /*
         * Common case:
         * Values in [0, 100] are handled in O(1).
         */
        if (num >= 0 && num <= 100) {

            frequency[num]++;

        } else if (num < 0) {

            /*
             * Outliers below the supported frequency range.
             */
            negative.offer(num);

        } else {

            /*
             * Outliers above the supported frequency range.
             */
            positive.offer(num);
        }

        totalSize++;
    }

    public double findMedian() {

        /*
         * Find the two middle zero-based positions.
         */
        int leftPosition = (totalSize - 1) / 2;
        int rightPosition = totalSize / 2;

        /*
         * Select the values at the required ranks.
         *
         * select() traverses the negative values in sorted order,
         * then the frequency array, then positive outliers.
         *
         * The traversal is valid because the three partitions
         * are globally ordered:
         *
         * negative < [0, 100] < positive.
         */
        int left = select(leftPosition);
        int right = select(rightPosition);

        return ((long) left + right) / 2.0;
    }

    private int select(int rank) {

        /*
         * PART 1: Negative values.
         *
         * We need ascending order.
         *
         * Since negative is a max heap, repeatedly poll into
         * a temporary list to enumerate its elements in ascending
         * order.
         *
         * This implementation is correct but temporarily modifies
         * and restores the heap.
         */
        List<Integer> negativeValues = new ArrayList<>();

        while (!negative.isEmpty()) {
            negativeValues.add(negative.poll());
        }

        /*
         * The max heap produces descending order.
         * Reverse it to obtain ascending order.
         */
        Collections.reverse(negativeValues);

        int position = 0;

        for (int value : negativeValues) {

            if (position == rank) {

                /*
                 * Restore the heap before returning.
                 */
                negative.addAll(negativeValues);
                return value;
            }

            position++;
        }

        /*
         * Restore the negative heap after consuming its elements.
         */
        negative.addAll(negativeValues);

        /*
         * PART 2: Frequency array.
         *
         * Values are already naturally sorted by array index.
         */
        for (int value = 0; value <= 100; value++) {

            if (frequency[value] == 0) {
                continue;
            }

            int nextPosition = position + frequency[value];

            if (rank < nextPosition) {
                return value;
            }

            position = nextPosition;
        }

        /*
         * PART 3: Positive outliers.
         *
         * Min heap provides ascending order.
         *
         * As with negative values, temporarily extract and restore.
         */
        List<Integer> positiveValues = new ArrayList<>();

        while (!positive.isEmpty()) {
            positiveValues.add(positive.poll());
        }

        for (int value : positiveValues) {

            if (position == rank) {

                positive.addAll(positiveValues);
                return value;
            }

            position++;
        }

        positive.addAll(positiveValues);

        throw new IllegalStateException("Invalid median rank");
    }
}

/*
 * COMPLEXITY:
 *
 * addNum():
 *
 * In-range values:
 * O(1).
 *
 * Out-of-range values:
 * O(log k), where k is the number of outliers.
 *
 * findMedian():
 *
 * O(k log k + 101), because this illustrative implementation
 * extracts and restores the outlier heaps.
 *
 * Space:
 * O(n).
 *
 * IMPORTANT:
 *
 * This is a hybrid illustration, not the optimal implementation
 * for the 99% follow-up.
 *
 * Its median-query implementation is expensive because it
 * temporarily enumerates outliers.
 *
 * A production-quality solution can maintain an ordered structure
 * for outliers and perform rank selection without extracting
 * the entire heap.
 */
```

### **A more important interview observation**

For the 99% follow-up, the exact distribution matters.

If the 1% outliers are rare but can occur anywhere, a frequency array alone cannot maintain the global median.

The hybrid approach is useful when the common range is fixed, but the data structure must still correctly account for outliers.

An alternative is to maintain the original two heaps and optimize the common-case insertion path using additional counts. However, this adds complexity and should only be done if profiling demonstrates a meaningful benefit.

# **7. Interviewer follow-up questions**

### **Q1. Why do we need two heaps instead of one heap?**

A single min heap or max heap only exposes one extreme element.

The median requires access to the boundary between the smaller and larger halves.

Two heaps expose both boundaries:

- Max heap gives the largest element in the smaller half.
- Min heap gives the smallest element in the larger half.

Together, they provide the median in `O(1)`.

### **Q2. Why do we use a max heap for the left half?**

Because we need the largest element among the smaller values.

That element is the left-middle candidate.

### **Q3. Why do we use a min heap for the right half?**

Because we need the smallest element among the larger values.

That element is the right-middle candidate.

### **Q4. Why do we insert into maxHeap first?**

It establishes the convention that maxHeap contains either the same number of elements as minHeap or one additional element.

We could design the algorithm with the opposite convention, but then we would need to adjust the insertion and median logic accordingly.

### **Q5. Why do we compare heap roots?**

Because the roots represent the boundary between the two halves.

If:

```
maxHeap.peek() > minHeap.peek()
```

the ordering invariant is violated.

Swapping the boundary elements restores it.

### **Q6. Can we use TreeMap instead?**

Yes.

A TreeMap can maintain value frequencies in sorted order.

However, Java's standard TreeMap does not provide direct indexed access to the kth element.

Finding the median by traversing its entries would take `O(n)` in the worst case.

An augmented balanced BST with subtree sizes can support median selection in `O(log n)`.

### **Q7. What if duplicate numbers exist?**

No problem.

PriorityQueue supports duplicates.

For example:

```
[2, 2, 2, 2]
```

The median is still:

```
2
```

### **Q8. Why cast to long before calculating the average?**

Consider:

```
int a = Integer.MAX_VALUE;
int b = Integer.MAX_VALUE;
```

This expression can overflow:

```
(a + b) / 2.0
```

Instead:

```
((long) a + b) / 2.0
```

The addition happens using `long`, preventing integer overflow.

### **Q9. What if we need to remove numbers from the stream?**

We would need to extend the data structure to support deletions.

One common approach is **lazy deletion**:

- Maintain a frequency map of elements marked for deletion.
- When an element reaches the top of a heap, remove it if it is marked.
- Maintain valid heap sizes separately from physical heap sizes.

This is useful for sliding-window median problems.

"I would solve this using two priority queues.

The max heap maintains the smaller half of the numbers, while the min heap maintains the larger half.

I maintain two invariants:

All three implementations solve **LeetCode 295 – Find Median from Data Stream** using two heaps.

However, they use slightly different insertion strategies.

The important distinction is:

- **Approach 1:** Decide which heap receives the number, then rebalance.
- **Approach 2:** Always insert into the max heap, correct ordering if necessary, then rebalance.
- **Approach 3:** Always move the max element from the left heap to the right heap, then move the min element back if necessary.

| Operation      | Time Complexity |
| -------------- | --------------- |
| `addNum()`     | O(log n)        |

# **1. First understand the two invariants**

Regardless of the implementation, we must maintain two invariants.

**Invariant 1: Ordering**

The left heap contains the smaller half, and the right heap contains the larger half.

Therefore:

```
left.peek() <= right.peek()
```

Whenever both heaps are non-empty.

**Invariant 2: Size**

The left heap is allowed to have one extra element.

```
left.size() == right.size()

OR

left.size() == right.size() + 1
```

Why do we maintain these invariants?

Because they make finding the median extremely simple.

```
                    ALL ELEMENTS
                         |
             +-----------+-----------+
             |                       |
             v                       v
        LEFT HALF               RIGHT HALF
         MAX HEAP                 MIN HEAP

       Largest smaller          Smallest larger
          element                  element
             |                       |
             +-----------+-----------+
                         |
                       MEDIAN
```

- Odd elements: `left.peek()`
- Even elements: `(left.peek() + right.peek()) / 2.0`

Now let's compare the implementations.

# **2. Approach 1: Conditional insertion + rebalance**

Your first implementation:

```
import java.util.*;

class MedianFinder {

    private final PriorityQueue<Integer> left, right;

    public MedianFinder() {
        left = new PriorityQueue<>(Collections.reverseOrder());
        right = new PriorityQueue<>();
    }

    public void addNum(int num) {

        /*
         * STEP 1: Decide which heap should receive the new number.
         *
         * left is a MAX HEAP containing the smaller half.
         * right is a MIN HEAP containing the larger half.
         *
         * If left is empty, insert into left.
         *
         * Otherwise:
         *
         * If num <= left.peek():
         *     num belongs to the smaller half.
         *     Insert into left.
         *
         * Else:
         *     num belongs to the larger half.
         *     Insert into right.
         *
         * Why compare with left.peek()?
         *
         * left.peek() is the largest element in the smaller half.
         *
         * Therefore, it represents the boundary between
         * the smaller and larger halves.
         */
        if (left.isEmpty() || num <= left.peek()) {
            left.offer(num);
        } else {
            right.offer(num);
        }

        /*
         * STEP 2: Restore the SIZE invariant.
         *
         * We want:
         *
         * left.size() == right.size()
         *
         * OR
         *
         * left.size() == right.size() + 1
         *
         * The ordering invariant is already maintained
         * by our conditional insertion.
         */
        rebalance();
    }

    private void rebalance() {

        /*
         * CASE 1:
         *
         * left has more than one extra element.
         *
         * Example:
         *
         * left  = [5, 3, 2, 1]
         * right = [8, 9]
         *
         * Sizes:
         * left  = 4
         * right = 2
         *
         * Difference = 2.
         *
         * Move the largest element from left to right.
         *
         * left.poll() returns the largest element because
         * left is a max heap.
         */
        if (left.size() > right.size() + 1) {

            right.offer(left.poll());
        }

        /*
         * CASE 2:
         *
         * right has more elements than left.
         *
         * Example:
         *
         * left  = [3, 2]
         * right = [5, 8, 9]
         *
         * Move the smallest element from right to left.
         *
         * right.poll() returns the smallest element because
         * right is a min heap.
         *
         * Notice that we use else-if.
         *
         * After moving one element, the size difference
         * is guaranteed to satisfy our invariant.
         */
        else if (right.size() > left.size()) {

            left.offer(right.poll());
        }
    }

    public double findMedian() {

        /*
         * ODD NUMBER OF ELEMENTS:
         *
         * left has one extra element.
         *
         * Therefore, the root of left is the middle element.
         */
        if (left.size() > right.size()) {
            return left.peek();
        }

        /*
         * EVEN NUMBER OF ELEMENTS:
         *
         * Both heaps contain equal numbers of elements.
         *
         * The two middle elements are:
         *
         * left.peek()  -> Largest element in smaller half.
         * right.peek() -> Smallest element in larger half.
         *
         * Cast to long before addition to prevent overflow.
         */
        return ((long) left.peek() + right.peek()) / 2.0;
    }
}
```

### **Why does conditional insertion work?**

Suppose we have:

```
left  = [5, 3, 2]
right = [8, 9]
```

The boundary is:

```
left.peek() = 5
right.peek() = 8
```

Now insert `4`.

Since:

```
4 <= 5
```

We insert into left.

```
left  = [5, 4, 3, 2]
right = [8, 9]
```

Now left has one extra element. Everything is valid.

Now insert `10`.

Since:

```
10 > 5
```

We insert into right.

```
left  = [5, 4, 3, 2]
right = [8, 9, 10]
```

Left has one extra element, so we move the largest element from left to right.

```
left  = [4, 3, 2]
right = [5, 8, 9, 10]
```

Now right has one extra element, so we move its smallest element back to left.

```
left  = [5, 4, 3, 2]
right = [8, 9, 10]
```

Both invariants are restored.

**Important observation:** Conditional insertion maintains the ordering invariant from the beginning. Rebalancing only needs to fix the sizes.

# **3. Approach 2: Always insert into max heap + conditional ordering correction**

This is the second implementation you provided.

The insertion process is different.

Instead of deciding which heap should receive the number, we always insert into the max heap.

Then we check whether the ordering invariant is violated.

```
import java.util.*;

class MedianFinder {

    /*
     * MAX HEAP:
     *
     * Stores the smaller half of the stream.
     *
     * The largest element of the smaller half is at the root.
     *
     * Example:
     *
     * Elements: [1, 2, 3]
     *
     * maxHeap:
     *
     *          3
     *         / \
     *        1   2
     *
     * peek() = 3
     */
    private final PriorityQueue<Integer> maxHeap =
            new PriorityQueue<>(Comparator.reverseOrder());

    /*
     * MIN HEAP:
     *
     * Stores the larger half of the stream.
     *
     * The smallest element of the larger half is at the root.
     *
     * Example:
     *
     * Elements: [5, 8, 9]
     *
     * minHeap:
     *
     *          5
     *         / \
     *        8   9
     *
     * peek() = 5
     */
    private final PriorityQueue<Integer> minHeap =
            new PriorityQueue<>();

    public void addNum(int num) {

        /*
         * STEP 1: Always insert into maxHeap.
         *
         * We are not deciding whether num belongs to the
         * smaller or larger half at this stage.
         *
         * We temporarily put it into the smaller half.
         */
        maxHeap.offer(num);

        /*
         * STEP 2: Restore the ORDERING invariant.
         *
         * Required:
         *
         * maxHeap.peek() <= minHeap.peek()
         *
         * Consider:
         *
         * maxHeap = [10, 5, 3]
         * minHeap = [7, 12]
         *
         * maxHeap.peek() = 10
         * minHeap.peek() = 7
         *
         * Ordering is violated because 10 > 7.
         *
         * Therefore, move the largest element from maxHeap
         * into minHeap.
         *
         * After moving:
         *
         * maxHeap = [7, 5, 3]
         * minHeap = [10, 12]
         *
         * Now:
         *
         * maxHeap.peek() <= minHeap.peek()
         *
         * The ordering invariant is restored.
         *
         * Why is moving only the root sufficient?
         *
         * Because the only possible violation is at the
         * boundary between the two heaps.
         *
         * The internal ordering of both heaps is already valid.
         *
         * Also, if minHeap is empty, there is no ordering
         * violation to correct.
         */
        if (!minHeap.isEmpty()
                && maxHeap.peek() > minHeap.peek()) {

            minHeap.offer(maxHeap.poll());
        }

        /*
         * STEP 3: Restore the SIZE invariant.
         *
         * Required:
         *
         * maxHeap.size() == minHeap.size()
         *
         * OR
         *
         * maxHeap.size() == minHeap.size() + 1
         *
         * If minHeap has more elements, move its smallest
         * element back to maxHeap.
         *
         * Example:
         *
         * maxHeap = [3, 2]
         * minHeap = [5, 8, 9]
         *
         * Move 5 from minHeap to maxHeap.
         *
         * Result:
         *
         * maxHeap = [5, 3, 2]
         * minHeap = [8, 9]
         *
         * Now maxHeap has exactly one extra element.
         */
        if (maxHeap.size() < minHeap.size()) {

            maxHeap.offer(minHeap.poll());
        }
    }

    public double findMedian() {

        /*
         * ODD NUMBER OF ELEMENTS:
         *
         * maxHeap contains one extra element.
         *
         * Its root is the middle element.
         */
        if (maxHeap.size() > minHeap.size()) {
            return maxHeap.peek();
        }

        /*
         * EVEN NUMBER OF ELEMENTS:
         *
         * Both heaps have equal sizes.
         *
         * The median is the average of their roots.
         *
         * Cast to long before addition to avoid overflow.
         */
        return ((long) maxHeap.peek() + minHeap.peek()) / 2.0;
    }
}
```

### **Why do we need the ordering correction before size correction?**

Because we first establish which elements belong to the smaller and larger halves.

Then we balance their sizes.

The two operations have different responsibilities:

| Operation           | Responsibility                                                            |
| ------------------- | ------------------------------------------------------------------------- |
| Ordering correction | Ensure smaller elements are in maxHeap and larger elements are in minHeap |
| Size correction     | Ensure the heaps differ by at most one                                    |

This separation makes the implementation easy to reason about.

# **4. Approach 3: Always move maxHeap root to minHeap, then move back if necessary**

This is your third implementation.

This is a particularly interesting approach because it removes the explicit ordering comparison.

Instead, it uses heap operations themselves to guarantee the ordering.

### **Code with detailed comments**

```
import java.util.*;

class MedianFinder {

    /*
     * LEFT HALF: MAX HEAP
     *
     * Stores the smaller half of all numbers.
     *
     * The largest number among the smaller half is always
     * available at the root.
     *
     * Example:
     *
     * Stream: [0, 2, 5, 6, 6, 10]
     *
     * lowerHalf:
     *
     *           5
     *          / \
     *         2   0
     *
     * peek() = 5
     *
     * This is the left-middle candidate.
     */
    private final PriorityQueue<Integer> lowerHalf =
            new PriorityQueue<>(Collections.reverseOrder());

    /*
     * RIGHT HALF: MIN HEAP
     *
     * Stores the larger half of all numbers.
     *
     * The smallest number among the larger half is always
     * available at the root.
     *
     * Example:
     *
     * Stream: [0, 2, 5, 6, 6, 10]
     *
     * upperHalf:
     *
     *           6
     *          / \
     *         6   10
     *
     * peek() = 6
     *
     * This is the right-middle candidate.
     */
    private final PriorityQueue<Integer> upperHalf =
            new PriorityQueue<>();

    public void addNum(int num) {

        /*
         * STEP 1: Always insert the incoming number into lowerHalf.
         *
         * We temporarily assume that the incoming number
         * belongs to the smaller half.
         *
         * We do not need to compare num with either heap root.
         *
         * The following steps will automatically correct
         * its position.
         */
        lowerHalf.offer(num);

        /*
         * STEP 2: ALWAYS move the largest element of lowerHalf
         * into upperHalf.
         *
         * This is the most important step in this approach.
         *
         * lowerHalf is a MAX HEAP.
         *
         * Therefore:
         *
         * lowerHalf.poll() returns the largest element.
         *
         * We insert that element into upperHalf.
         *
         * Why does this guarantee ordering?
         *
         * Consider:
         *
         * lowerHalf = [10, 5, 3]
         * upperHalf = [7, 12]
         *
         * The largest element of lowerHalf is 10.
         *
         * Moving 10 to upperHalf:
         *
         * lowerHalf = [5, 3]
         * upperHalf = [7, 10, 12]
         *
         * Now:
         *
         * Every element remaining in lowerHalf is <= 10.
         *
         * Every element in upperHalf is >= 7.
         *
         * More importantly, the maximum remaining in lowerHalf
         * is no greater than the minimum in upperHalf.
         *
         * Thus:
         *
         * lowerHalf.peek() <= upperHalf.peek()
         *
         * The ordering invariant is restored automatically.
         *
         * Notice:
         *
         * We do this EVEN IF the ordering was already valid.
         *
         * That is why this approach is slightly different
         * from Approach 2.
         */
        upperHalf.offer(lowerHalf.poll());

        /*
         * STEP 3: Restore the SIZE invariant.
         *
         * After STEP 2, upperHalf can have one more element
         * than lowerHalf.
         *
         * But our convention is:
         *
         * lowerHalf.size() == upperHalf.size()
         *
         * OR
         *
         * lowerHalf.size() == upperHalf.size() + 1
         *
         * If upperHalf is larger, move its smallest element
         * back to lowerHalf.
         *
         * Because upperHalf is a MIN HEAP,
         * poll() returns its smallest element.
         *
         * This makes lowerHalf contain either:
         *
         * - The same number of elements, or
         * - Exactly one extra element.
         */
        if (lowerHalf.size() < upperHalf.size()) {

            lowerHalf.offer(upperHalf.poll());
        }
    }

    public double findMedian() {

        /*
         * ODD NUMBER OF ELEMENTS:
         *
         * lowerHalf has one extra element.
         *
         * Therefore, its root is the median.
         */
        if (lowerHalf.size() > upperHalf.size()) {

            return lowerHalf.peek();
        }

        /*
         * EVEN NUMBER OF ELEMENTS:
         *
         * Both heaps have equal sizes.
         *
         * The middle elements are:
         *
         * lowerHalf.peek() -> Largest element in smaller half.
         * upperHalf.peek() -> Smallest element in larger half.
         *
         * Convert to double before addition.
         *
         * This also avoids integer overflow.
         */
        return ((double) lowerHalf.peek()
                + upperHalf.peek()) / 2.0;
    }
}
```

# **9. Final recommendation: Code to remember**

For interviews, I would memorize Approach 3 because its three-step insertion process is consistent and easy to reproduce.

```
import java.util.*;

class MedianFinder {

    // Max heap: stores the smaller half.
    // Root = largest element in the smaller half.
    private final PriorityQueue<Integer> left =
            new PriorityQueue<>(Collections.reverseOrder());

    // Min heap: stores the larger half.
    // Root = smallest element in the larger half.
    private final PriorityQueue<Integer> right =
            new PriorityQueue<>();

    public void addNum(int num) {

        /*
         * STEP 1:
         * Insert into left (max heap).
         *
         * We temporarily assume that the new number
         * belongs to the smaller half.
         */
        left.offer(num);

        /*
         * STEP 2:
         * Move the largest element of left into right.
         *
         * This restores the ordering invariant:
         *
         * Every element in left <= every element in right.
         *
         * Why?
         * We move the maximum of left across the boundary.
         */
        right.offer(left.poll());

        /*
         * STEP 3:
         * Restore the size invariant.
         *
         * left must have either:
         *
         * - Equal number of elements as right, OR
         * - Exactly one extra element.
         *
         * If right is larger, move its smallest element
         * back to left.
         */
        if (left.size() < right.size()) {
            left.offer(right.poll());
        }
    }

    public double findMedian() {

        /*
         * Odd count:
         * left contains one extra element.
         * Its root is the median.
         */
        if (left.size() > right.size()) {
            return left.peek();
        }

        /*
         * Even count:
         * Average the two boundary elements.
         *
         * Cast before addition to avoid integer overflow.
         */
        return ((long) left.peek() + right.peek()) / 2.0;
    }
}

/*
 * TIME COMPLEXITY:
 *
 * addNum():
 * O(log n)
 *
 * At most two poll operations and two offer operations
 * are performed. Each heap operation takes O(log n).
 *
 * findMedian():
 * O(1)
 *
 * Only heap roots and sizes are accessed.
 *
 * SPACE COMPLEXITY:
 * O(n)
 *
 * Every inserted number is stored in exactly one heap.
 */
```

**One-line mental model to remember:**

`Insert into left → Move max(left) to right → If right is bigger, move min(right) back to left.`

This is the complete two-heaps pattern.
