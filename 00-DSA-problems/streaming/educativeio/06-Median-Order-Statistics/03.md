# **3369. Design an Array Statistics Tracker**

**Difficulty:** Hard\
**Topics:** Design, Queue, HashMap, Heap, PriorityQueue, Ordered Set, Data Stream

Problem: [LeetCode – Design an Array Statistics Tracker](https://leetcode.com/problems/design-an-array-statistics-tracker/description/?utm_source=chatgpt.com).

The problem tests whether you can maintain multiple statistics of a dynamically changing collection without recomputing everything after every operation.

The three statistics are:

1. **Mean:** Average of all currently stored numbers.
2. **Median:** Middle element after sorting. If there are two middle elements, return the larger one.
3. **Mode:** Most frequently occurring number. If multiple numbers have the same frequency, return the smallest one.

## **0. Simplify the problem**

We need to implement a class called `StatisticsTracker` supporting five operations.

| Operation                  | Meaning                           |
| -------------------------- | --------------------------------- |
| `StatisticsTracker()`      | Initialize an empty tracker       |
| `addNumber(number)`        | Add a number                      |
| `removeFirstAddedNumber()` | Remove the oldest inserted number |
| `getMean()`                | Return the floored average        |
| `getMedian()`              | Return the middle element         |
| `getMode()`                | Return the most frequent element  |

Consider this sequence:

```
StatisticsTracker tracker = new StatisticsTracker();

tracker.addNumber(4);
tracker.addNumber(2);
tracker.addNumber(5);
tracker.addNumber(2);
tracker.addNumber(3);
```

Current insertion order:

```
[4, 2, 5, 2, 3]
```

Sorted order:

```
[2, 2, 3, 4, 5]
```

Statistics:

**Mean:**

\\[ \frac{4+2+5+2+3}{5}=3.2 \\]

Return `3` (floor).

**Median:**

```
[2, 2, 3, 4, 5]
       ^
```

Return `3`.

**Mode:**

```
2 -> 2 occurrences
3 -> 1 occurrence
4 -> 1 occurrence
5 -> 1 occurrence
```

Return `2`.

Now execute:

```
tracker.removeFirstAddedNumber();
```

The oldest inserted number, `4`, is removed.

Current insertion order:

```
[2, 5, 2, 3]
```

Sorted order:

```
[2, 2, 3, 5]
```

Now:

- Mean = `3`
- Median = `3` (larger of 2 and 3)
- Mode = `2`

**The important observation:** We need to maintain insertion order, sorted order, frequencies, and the sum simultaneously.

## **1. Clarifying questions to ask the interviewer**

Before designing the data structure, clarify these details.

**Q1. Can numbers be negative or zero?**

Why?

This affects how we implement the floored mean.

For example:

\\[ \lfloor -1.5 \rfloor = -2 \\]

Java integer division returns `-1` for `-3 / 2`, because it truncates toward zero.

The given LeetCode constraints specify positive integers, so ordinary integer division is sufficient.

**Q2. What should happen when the collection contains an even number of elements?**

Why?

There are two possible middle elements.

The problem explicitly specifies that we must return the larger one.

**Q3. How should ties be handled when calculating the mode?**

Why?

Multiple numbers can have the same maximum frequency.

The problem specifies that we return the smallest number.

**Q4. Can removal happen when the collection is empty?**

Why?

We need to know whether empty-state validation is required.

The problem guarantees that removal and statistical queries happen only when the collection is non-empty.

**Q5. What are the constraints?**

Why?

With up to \\(10^5\\) operations, recomputing statistics on every query is too expensive.

We should aim for logarithmic update operations and constant-time queries.

# **2. Core intuition and mental model**

The trick is to recognize that each statistic needs a different data structure.

| Requirement           | Data structure     | Why?                               |
| --------------------- | ------------------ | ---------------------------------- |
| Remove oldest element | Queue              | FIFO ordering                      |
| Calculate mean        | Running sum + size | Avoid repeated summation           |
| Calculate median      | Two heaps          | Maintain the middle element        |
| Calculate mode        | HashMap + TreeSet  | Track frequencies and resolve ties |

Our optimal solution combines these structures into one class.

Let's understand each independently.

## **2.1 Mean: Running sum**

The mean is:

\\[ Mean = \left\lfloor \frac{Sum}{Count} \right\rfloor \\]

Instead of calculating the sum every time `getMean()` is called, maintain it during updates.

When adding:

```
sum += number;
```

When removing:

```
sum -= number;
```

Query:

```
return (int) (sum / size);
```

Complexities:

- Add: O(1)
- Remove: O(1)
- Get mean: O(1)

We use `long` for the sum to avoid integer overflow.

## **2.2 Median: Two heaps**

This is the most interesting part.

We need the middle element of a dynamically changing sorted collection.

We can solve this using two heaps.

**Heap 1: Max Heap (**`lower`**)**

Stores the smaller half of the numbers.

**Heap 2: Min Heap (**`upper`**)**

Stores the larger half of the numbers.

Example:

```
Numbers: [1, 3, 5, 7, 9]

                 5
                / \
               3   7
              /     \
             1       9
```

Our actual heap representation is:

```
LOWER (Max Heap)       UPPER (Min Heap)

       3                      5
      /                      / \
     1                      7   9
```

Notice:

- `lower.peek()` gives the largest element in the smaller half.
- `upper.peek()` gives the smallest element in the larger half.

The important invariant:

\\[ lower.size() \le upper.size() \\]

\\[ upper.size() - lower.size() \le 1 \\]

In other words, `upper` contains either the same number of elements as `lower` or exactly one more.

Therefore:

```
upper.peek()
```

always gives us the required median.

Why?

**Odd number of elements:**

```
[1, 3, 5, 7, 9]

LOWER             UPPER
[3, 1]            [5, 7, 9]

Median = 5
```

**Even number of elements:**

```
[1, 3, 5, 7]

LOWER             UPPER
[3, 1]            [5, 7]

Median = 5
```

We return the larger middle element.

This is exactly why we maintain the extra element in `upper`.

### **Adding an element**

Suppose we insert `4`.

```
if (lower.isEmpty() || number <= lower.peek()) {
    lower.offer(number);
} else {
    upper.offer(number);
}
```

Then rebalance the heaps.

### **Removing an element**

Here is the challenge.

We must remove the oldest inserted number, but that number could exist anywhere inside either heap.

Java's `PriorityQueue.remove(value)` takes O(n), because it needs to search for the element.

We need something better.

The solution is **Lazy Deletion**.

Instead of immediately removing an element from a heap, we:

1. Record that the element has been deleted.
2. Decrease the logical size of the appropriate heap.
3. Physically remove it when it reaches the heap's root.

We maintain:

```
Map<Integer, Integer> delayed;
```

For example:

```
LOWER:

       8
      / \
     5   7
    /
   2
```

Suppose `2` is removed.

We don't search for `2`.

Instead:

```
delayed.merge(2, 1, Integer::sum);
```

The element stays physically inside the heap.

When `2` eventually reaches the root, we remove it.

This is lazy deletion.

### **Why do we need logical sizes?**

Because the heaps may temporarily contain deleted elements.

For example:

```
Physical lower heap size = 4
Deleted elements         = 1

Logical lower size       = 3
```

Therefore, we maintain:

```
int lowerSize;
int upperSize;
```

These represent the number of valid elements, not the physical heap sizes.

This distinction is essential.

## **2.3 Mode: HashMap + TreeSet**

The mode is the most frequently occurring number.

We maintain:

```
Map<Integer, Integer> frequency;
```

Example:

```
Number     Frequency

2          3
5          2
7          1
9          1
```

But how do we efficiently retrieve the number with the highest frequency?

We could iterate over the entire HashMap, but that takes O(n).

Instead, maintain a `TreeSet` containing entries ordered by:

1. Frequency descending.
2. Number ascending.

For example:

```
(frequency, number)

(3, 2)
(2, 5)
(1, 7)
(1, 9)
```

The first entry always represents the mode.

We define a record:

```
record ModeEntry(int number, int frequency) {}
```

And a comparator:

```
private static final Comparator<ModeEntry> MODE_ORDER =
        Comparator.comparingInt(ModeEntry::frequency)
                .reversed()
                .thenComparingInt(ModeEntry::number);
```

Now:

```
modeSet.first()
```

returns the mode.

### **Updating the mode**

Suppose the frequency of `5` changes from 2 to 3.

We must:

1. Remove `(5, 2)` from the TreeSet.
2. Update its frequency in the HashMap.
3. Insert `(5, 3)` into the TreeSet.

Why remove the old entry first?

Because the TreeSet comparator depends on frequency.

Changing a field used by the comparator without removing the old entry can break the TreeSet's ordering.

This is an important interview detail.

# **4. All possible approaches**

## **Approach 1: Brute Force**

The simplest implementation maintains a queue of numbers.

For every query:

- Mean: Iterate over all numbers and calculate the sum.
- Median: Copy the elements, sort them, and return the middle element.
- Mode: Build a frequency map and find the most frequent number.

```java
import java.util.*;

class StatisticsTracker {

    private final Queue<Integer> numbers = new ArrayDeque<>();

    public void addNumber(int number) {
        // Add the new number at the end.
        numbers.offer(number);
    }

    public void removeFirstAddedNumber() {
        // FIFO removal.
        numbers.poll();
    }

    public int getMean() {

        // Recalculate the sum every time.
        long sum = 0;

        for (int number : numbers) {
            sum += number;
        }

        return (int) (sum / numbers.size());
    }

    public int getMedian() {

        // Copy the current elements.
        List<Integer> sorted = new ArrayList<>(numbers);

        // Sorting costs O(n log n).
        Collections.sort(sorted);

        // Return the larger middle element.
        return sorted.get(sorted.size() / 2);
    }

    public int getMode() {

        Map<Integer, Integer> frequency = new HashMap<>();

        // Recalculate all frequencies.
        for (int number : numbers) {
            frequency.merge(number, 1, Integer::sum);
        }

        int mode = Integer.MAX_VALUE;
        int maxFrequency = 0;

        for (var entry : frequency.entrySet()) {

            int number = entry.getKey();
            int count = entry.getValue();

            // Higher frequency wins.
            // Smaller number wins when frequencies tie.
            if (count > maxFrequency ||
                (count == maxFrequency && number < mode)) {

                maxFrequency = count;
                mode = number;
            }
        }

        return mode;
    }
}
```

**Complexity analysis**

Let n be the current number of elements.

| Operation              | Time       |
| ---------------------- | ---------- |
| addNumber              | O(1)       |
| removeFirstAddedNumber | O(1)       |
| getMean                | O(n)       |
| getMedian              | O(n log n) |
| getMode                | O(n)       |

Space complexity: O(n).

**Why is this inefficient?**

Every query recalculates information that we could have maintained incrementally.

With \\(10^5\\) operations, this approach can result in TLE.

## **Approach 2: Queue + TreeMap + Frequency TreeSet**

Before jumping into two heaps, there is another useful approach.

We can maintain:

- Queue: Insertion order.
- Running sum: Mean.
- `TreeMap<Integer, Integer>`: Sorted multiset.
- `HashMap<Integer, Integer>`: Frequencies.
- `TreeSet<ModeEntry>`: Mode.

The `TreeMap` stores:

```
Number -> Frequency

2 -> 2
3 -> 1
5 -> 1
```

This allows us to maintain sorted values.

However, Java's `TreeMap` does not support retrieving the kth element in O(log n).

To find the median, we must iterate through its entries until reaching the middle position.

Consequently:

| Operation              | Time     |
| ---------------------- | -------- |
| addNumber              | O(log n) |
| removeFirstAddedNumber | O(log n) |
| getMean                | O(1)     |
| getMedian              | O(d)     |
| getMode                | O(1)     |

Here, d is the number of distinct values.

This is a reasonable intermediate approach, but we can do better for median queries.

# **5. Optimal Java 24 Solution**

We will combine:

- `ArrayDeque` for FIFO ordering.
- `HashMap` for frequencies and lazy deletion.
- Two `PriorityQueue` instances for median.
- `TreeSet` for mode.
- `long` for running sum.

One important detail: the median heaps use lazy deletion, so their physical sizes can grow beyond the number of active elements. However, every stale entry is eventually removed when it reaches a heap root.

```java

import java.util.*;

class StatisticsTracker {

    /*
     * Stores numbers in insertion order.
     *
     * Required for removeFirstAddedNumber().
     */
    private final Deque<Integer> queue = new ArrayDeque<>();

    /*
     * Running sum of all currently active numbers.
     *
     * long avoids integer overflow.
     */
    private long sum = 0;


    /*
     * Frequency of every currently active number.
     *
     * Example:
     *
     * 2 -> 3
     * 5 -> 2
     * 7 -> 1
     */
    private final Map<Integer, Integer> frequency = new HashMap<>();


    /*
     * Median data structures.
     *
     * LOWER:
     * Max heap containing the smaller half.
     *
     * UPPER:
     * Min heap containing the larger half.
     *
     * UPPER always contains either:
     * - The same number of valid elements as LOWER.
     * - One more valid element than LOWER.
     *
     * Therefore, upper.peek() is always the required median.
     */
    private final PriorityQueue<Integer> lower =
            new PriorityQueue<>(Comparator.reverseOrder());

    private final PriorityQueue<Integer> upper =
            new PriorityQueue<>();


    /*
     * Numbers marked for lazy deletion.
     *
     * Example:
     *
     * 5 -> 2
     *
     * Means two occurrences of 5 have been logically removed
     * but have not yet been physically removed from their heaps.
     */
    private final Map<Integer, Integer> delayed = new HashMap<>();


    /*
     * Logical sizes of the heaps.
     *
     * IMPORTANT:
     * These are not necessarily equal to lower.size()
     * and upper.size(), because those heaps may contain
     * stale elements.
     */
    private int lowerSize = 0;
    private int upperSize = 0;


    /*
     * ModeEntry represents:
     *
     * number    -> actual number
     * frequency -> its current frequency
     */
    private record ModeEntry(int number, int frequency) {}


    /*
     * Mode ordering:
     *
     * 1. Higher frequency first.
     * 2. Smaller number first when frequencies are equal.
     *
     * Therefore, modeSet.first() always gives the mode.
     */
    private static final Comparator<ModeEntry> MODE_ORDER =
            Comparator.comparingInt(ModeEntry::frequency)
                    .reversed()
                    .thenComparingInt(ModeEntry::number);


    /*
     * Ordered set containing one entry per active distinct number.
     */
    private final TreeSet<ModeEntry> modeSet =
            new TreeSet<>(MODE_ORDER);


    /*
     * ---------------------------------------------------------
     * ADD NUMBER
     * ---------------------------------------------------------
     *
     * Time Complexity: O(log n)
     *
     * Queue insertion: O(1)
     * HashMap operations: O(1) expected
     * Heap insertion: O(log n)
     * Heap balancing: O(log n)
     * TreeSet updates: O(log d)
     *
     * Overall: O(log n)
     */
    public void addNumber(int number) {

        // 1. Maintain insertion order.
        queue.offerLast(number);

        // 2. Maintain running sum.
        sum += number;


        // 3. Update the frequency and mode set.
        updateFrequency(number, 1);


        // 4. Insert the number into the correct median heap.
        //
        // If it belongs to the smaller half, insert into LOWER.
        // Otherwise, insert into UPPER.
        if (lower.isEmpty() || number <= lower.peek()) {

            lower.offer(number);
            lowerSize++;

        } else {

            upper.offer(number);
            upperSize++;
        }


        // 5. Restore the median heap invariants.
        rebalance();
    }


    /*
     * ---------------------------------------------------------
     * REMOVE FIRST ADDED NUMBER
     * ---------------------------------------------------------
     *
     * Time Complexity: O(log n) amortized
     *
     * We do not search inside either heap.
     * Instead, we use lazy deletion.
     */
    public void removeFirstAddedNumber() {

        // 1. Remove the oldest inserted number.
        int number = queue.pollFirst();


        // 2. Update running sum.
        sum -= number;


        // 3. Update the frequency and mode set.
        updateFrequency(number, -1);


        // 4. Mark this number for lazy deletion.
        delayed.merge(number, 1, Integer::sum);


        /*
         * 5. Decide which heap's logical size to decrease.
         *
         * If number <= lower.peek(), logically remove it
         * from LOWER.
         *
         * Otherwise, logically remove it from UPPER.
         *
         * When duplicate values exist at the boundary,
         * their instances are interchangeable.
         */
        prune(lower);

        if (!lower.isEmpty() && number <= lower.peek()) {

            lowerSize--;

        } else {

            upperSize--;
        }


        /*
         * 6. Remove stale elements if they appear at heap tops.
         *
         * This is necessary before moving elements between heaps.
         */
        prune(lower);
        prune(upper);


        // 7. Restore the heap size invariant.
        rebalance();
    }


    /*
     * ---------------------------------------------------------
     * UPDATE FREQUENCY AND MODE
     * ---------------------------------------------------------
     *
     * delta = +1 -> insertion
     * delta = -1 -> deletion
     *
     * Time Complexity: O(log d)
     *
     * We remove the previous entry before inserting the updated
     * frequency because TreeSet ordering depends on frequency.
     */
    private void updateFrequency(int number, int delta) {

        int oldFrequency = frequency.getOrDefault(number, 0);


        // Remove the old mode entry if this number already exists.
        if (oldFrequency > 0) {

            modeSet.remove(new ModeEntry(number, oldFrequency));
        }


        // Calculate the updated frequency.
        int newFrequency = oldFrequency + delta;


        if (newFrequency == 0) {

            // The number no longer exists in our collection.
            frequency.remove(number);

        } else {

            // Store its new frequency.
            frequency.put(number, newFrequency);

            // Insert the updated entry into the ordered set.
            modeSet.add(new ModeEntry(number, newFrequency));
        }
    }


    /*
     * ---------------------------------------------------------
     * PRUNE STALE ELEMENTS
     * ---------------------------------------------------------
     *
     * Time Complexity: O(k log n)
     *
     * k = number of stale elements removed in this invocation.
     *
     * Each stale element is physically removed only once
     * throughout its lifetime.
     */
    private void prune(PriorityQueue<Integer> heap) {

        while (!heap.isEmpty()) {

            int number = heap.peek();

            int count = delayed.getOrDefault(number, 0);


            // The heap top is valid.
            if (count == 0) {
                break;
            }


            // Physically remove the stale element.
            heap.poll();


            // Update the delayed deletion count.
            if (count == 1) {

                delayed.remove(number);

            } else {

                delayed.put(number, count - 1);
            }
        }
    }


    /*
     * ---------------------------------------------------------
     * REBALANCE MEDIAN HEAPS
     * ---------------------------------------------------------
     *
     * Invariants:
     *
     * 1. lowerSize <= upperSize
     *
     * 2. upperSize <= lowerSize + 1
     *
     * 3. Every valid element in LOWER <= every valid element
     *    in UPPER.
     *
     * After balancing:
     *
     * upper.peek() = required median.
     *
     * Time Complexity: O(log n)
     */
    private void rebalance() {

        // Remove stale elements before accessing heap tops.
        prune(lower);
        prune(upper);


        /*
         * Case 1:
         *
         * LOWER has more elements than UPPER.
         *
         * Move the maximum element from LOWER to UPPER.
         */
        if (lowerSize > upperSize) {

            upper.offer(lower.poll());

            lowerSize--;
            upperSize++;
        }


        /*
         * Case 2:
         *
         * UPPER has more than one extra element.
         *
         * Move the minimum element from UPPER to LOWER.
         */
        else if (upperSize > lowerSize + 1) {

            lower.offer(upper.poll());

            upperSize--;
            lowerSize++;
        }


        // Clean any stale elements exposed after moving.
        prune(lower);
        prune(upper);
    }


    /*
     * ---------------------------------------------------------
     * GET MEAN
     * ---------------------------------------------------------
     *
     * Time Complexity: O(1)
     *
     * We maintain the sum incrementally.
     * No iteration is necessary.
     */
    public int getMean() {

        return (int) (sum / queue.size());
    }


    /*
     * ---------------------------------------------------------
     * GET MEDIAN
     * ---------------------------------------------------------
     *
     * Time Complexity: O(log n) worst case for pruning,
     * amortized O(1) over the sequence of operations.
     *
     * The median is the minimum element of UPPER.
     *
     * When the collection has an even number of elements,
     * UPPER contains the larger middle element at its root.
     */
    public int getMedian() {

        // Ensure the root is not a stale element.
        prune(lower);
        prune(upper);

        return upper.peek();
    }


    /*
     * ---------------------------------------------------------
     * GET MODE
     * ---------------------------------------------------------
     *
     * Time Complexity: O(1)
     *
     * TreeSet.first() directly provides:
     *
     * 1. Maximum frequency.
     * 2. Smallest number when frequencies tie.
     */
    public int getMode() {

        return modeSet.first().number();
    }
}
```

# **6. Important dry run**

Let's understand how the optimal implementation behaves.

Operations:

```
addNumber(4);
addNumber(2);
addNumber(5);
addNumber(2);
addNumber(3);
```

### **Step 1: Insert 4**

```
LOWER: []
UPPER: [4]
```

Median = 4.

### **Step 2: Insert 2**

Since `2 <= lower.peek()` is not applicable because lower is empty, insert into upper.

```
LOWER: []
UPPER: [2, 4]
```

Rebalance:

```
LOWER: [2]
UPPER: [4]
```

Median = 4.

### **Step 3: Insert 5**

```
LOWER: [2]
UPPER: [4, 5]
```

Median = 4.

### **Step 4: Insert 2**

```
LOWER: [2, 2]
UPPER: [4, 5]
```

Median = 4.

### **Step 5: Insert 3**

```
LOWER: [3, 2, 2]
UPPER: [4, 5]
```

After rebalancing:

```
LOWER: [2, 2]
UPPER: [3, 4, 5]
```

Median = 3.

Mode:

```
2 -> 2
3 -> 1
4 -> 1
5 -> 1
```

Mode = 2.

### **Step 6: Remove oldest element**

```
removeFirstAddedNumber();
```

The oldest element is `4`.

We mark `4` for lazy deletion.

We do not search for it inside the heap.

Current valid collection:

```
[2, 5, 2, 3]
```

The median heaps might temporarily contain stale elements.

After pruning and rebalancing, their logical contents are:

```
LOWER: [2, 2]
UPPER: [3, 5]
```

Median = 3.

Mean = 3.

Mode = 2.

# **7. Edge cases to watch out for**

| Edge case                                | Expected behavior                                    |
| ---------------------------------------- | ---------------------------------------------------- |
| Only one element                         | That element is mean, median and mode                |
| All elements identical                   | Return that element for all statistics               |
| Two elements                             | Median is the larger element                         |
| Multiple numbers have the same frequency | Return the smallest                                  |
| Remove the current median                | Correctly rebalance heaps                            |
| Remove an element buried inside a heap   | Lazy deletion handles it                             |
| Repeated insertions and removals         | Frequency and delayed counts remain correct          |
| Large values                             | Use `long` for sum                                   |
| Empty collection                         | Queries are not called under the problem constraints |

**One particularly important edge case:**

```
[5, 5, 5, 5]
```

Remove the oldest `5`.

The frequency changes:

```
5 -> 3
```

All four occurrences have the same value, but we must still correctly update the logical heap sizes and delayed deletion counts.

This is why the `delayed` map and logical heap sizes are important.

# **8. Complexity comparison**

Let:

- n = total active elements.
- d = distinct active elements.

| Operation              | Brute force | TreeMap approach | Optimal                             |
| ---------------------- | ----------- | ---------------- | ----------------------------------- |
| addNumber              | O(1)        | O(log n)         | O(log n)                            |
| removeFirstAddedNumber | O(1)        | O(log n)         | O(log n) amortized                  |
| getMean                | O(n)        | O(1)             | O(1)                                |
| getMedian              | O(n log n)  | O(d)             | O(log n) worst case, O(1) amortized |
| getMode                | O(n)        | O(1)             | O(1)                                |
| Space                  | O(n)        | O(n)             | O(n) amortized                      |

**Why is the median query O(1) amortized rather than strictly O(1)?**

Because `getMedian()` calls `prune()`, which might remove several stale elements from a heap.

However, each stale element is inserted once and physically removed at most once.

Across the entire sequence of operations, the total pruning work is O(n log n).

Thus, the amortized pruning cost per operation is O(log n), and median retrieval is O(1) amortized when considering the heap maintenance across operations.

The overall auxiliary space is O(n) amortized, including lazy-deletion entries.

# **9. Interviewer follow-up questions**

### **Q1. Why use two heaps instead of a single PriorityQueue?**

A single heap only gives us access to one extreme element.

The median requires access to the middle of the sorted collection.

Two heaps divide the collection into smaller and larger halves, allowing us to retrieve the middle element efficiently.

### **Q2. Why not use&#x20;**`PriorityQueue.remove(number)`**?**

Java's `PriorityQueue.remove(Object)` requires a linear search.

Its complexity is O(n).

Lazy deletion avoids searching the heap and provides amortized logarithmic update operations.

### **Q3. Why maintain logical sizes separately?**

Because lazy deletion means that deleted elements can remain physically inside the heaps.

The physical size does not represent the number of active elements.

Logical sizes are necessary for maintaining the median partition correctly.

### **Q4. Why do we use a TreeSet for the mode?**

A HashMap efficiently tracks frequencies but does not maintain ordering.

A TreeSet maintains entries in the required order:

```
Highest frequency
       |
       v
Smallest number
```

Therefore, retrieving the mode takes O(1) using `first()`.

Updates take O(log d).

### **Q5. Can we use a PriorityQueue instead of TreeSet for the mode?**

Yes.

We can use a max heap storing:

```
record ModeEntry(int number, int frequency) {}
```

Every frequency update inserts a new entry.

When querying the mode, discard stale entries until the top entry matches the current frequency in the HashMap.

This uses lazy deletion, just like our median implementation.

The trade-off is that the heap can accumulate stale entries, whereas the TreeSet maintains only current entries.

### **Q6. Can we implement the median using a TreeMap?**

Yes.

A TreeMap can maintain frequencies of sorted values.

However, Java's TreeMap does not provide kth-element access.

We would need to iterate over the sorted entries to locate the median.

An augmented balanced BST (such as an order-statistics tree) could support kth-element retrieval in O(log n).

### **Q7. What if the interviewer allows negative numbers?**

The mean implementation needs special attention.

Java integer division truncates toward zero rather than flooring.

For example:

```
-3 / 2 = -1
```

But:

\\[ \lfloor -3/2 \rfloor = -2 \\]

We can use:

```
return (int) Math.floorDiv(sum, queue.size());
```

### **Q8. What if the interviewer asks for the average of the two middle elements instead?**

We simply change the median query:

```
if (lowerSize == upperSize) {
    return ((long) lower.peek() + upper.peek()) / 2;
}

return upper.peek();
```

The exact return type and rounding behavior should be clarified.

## **10. What to remember for interviews**

This problem is essentially a combination of three previously useful patterns:

| Pattern                   | Used for              |
| ------------------------- | --------------------- |
| Queue + Running Sum       | FIFO removal and mean |
| Two Heaps + Lazy Deletion | Sliding window median |
| HashMap + Ordered Set     | Frequency and mode    |

The most important insights are:

1. **Don't recalculate statistics.** Maintain them incrementally.
2. **Two heaps** maintain the median efficiently.
3. **Lazy deletion** avoids O(n) removal from Java PriorityQueues.
4. **Logical heap sizes** are essential when using lazy deletion.
5. **TreeSet with a custom comparator** handles mode and tie-breaking elegantly.
6. Always remove the old TreeSet entry before inserting an updated frequency entry.

**My recommendation for an interview:** Explain the running sum first, then the mode structure, and spend most of your time explaining the two heaps and lazy deletion. That is where the majority of the algorithmic complexity lies.
