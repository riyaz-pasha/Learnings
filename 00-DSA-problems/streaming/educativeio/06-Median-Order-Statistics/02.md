# **480. Sliding Window Median — Hard**

## **0. Simplify the problem statement**

We are given:

- An integer array `nums`.
- A sliding window of size `k`.
- We need to calculate the **median of every window** as it moves from left to right.

The window moves one position at a time:

1. Add the next element entering the window.
2. Remove the element leaving the window.
3. Calculate the median of the current window.

**Median calculation:**

- Odd number of elements: return the middle element after sorting.
- Even number of elements: return the average of the two middle elements.

### **Example**

```
nums = [1, 3, -1, -3, 5, 3, 6, 7]
k = 3
```

The windows are:

```
[1, 3, -1]  -> sorted [-1, 1, 3]  -> median = 1

[3, -1, -3] -> sorted [-3, -1, 3] -> median = -1

[-1, -3, 5] -> sorted [-3, -1, 5] -> median = -1

[-3, 5, 3]  -> sorted [-3, 3, 5]  -> median = 3

[5, 3, 6]   -> sorted [3, 5, 6]   -> median = 5

[3, 6, 7]   -> sorted [3, 6, 7]   -> median = 6
```

Output:

```
[1.0, -1.0, -1.0, 3.0, 5.0, 6.0]
```

## **1. Clarifying questions to ask the interviewer**

| Question                                                              | Why clarify?                                                    |
| --------------------------------------------------------------------- | --------------------------------------------------------------- |
| Can the array contain negative numbers?                               | We must handle negative values correctly.                       |
| Can duplicate values exist?                                           | Yes, duplicates affect removal logic in heaps.                  |
| Can `k` be even?                                                      | We must calculate the average of two middle elements.           |
| Can values be as large as `Integer.MIN_VALUE` or `Integer.MAX_VALUE`? | We must avoid integer overflow while calculating the average.   |
| What is the maximum array length?                                     | With `n <= 10^5`, an \\(O(n \log k)\\) solution is appropriate. |
| Is the input mutable?                                                 | Helps determine whether modifying the array is acceptable.      |

We will assume:

- Duplicates are allowed.
- Negative numbers are allowed.
- The input array should not be modified.
- `1 <= k <= nums.length`.
- We need an efficient solution for `n <= 100,000`.

## **2. Core intuition — Two Heaps**

This problem is closely related to **295. Find Median from Data Stream**.

Remember the two-heap approach:

- Max heap: stores the smaller half of the numbers.
- Min heap: stores the larger half of the numbers.

The difference here is that the window is sliding, meaning we must support three operations:

1. Insert an element.
2. Remove an element.
3. Find the median.

A normal Java `PriorityQueue` supports insertion and removal of the root efficiently, but removing an arbitrary element takes \\(O(k)\\).

We need to solve that problem.

There are two important approaches:

1. Two heaps with lazy deletion.
2. Two balanced ordered multisets (using `TreeMap` frequency counting).

The first is a popular heap-based interview solution. The second is particularly clean in Java because Java does not provide a built-in multiset.

### **2.1 Visualizing the two heaps**

Suppose:

```
window = [1, 3, -1]
```

After inserting all elements:

```
             Smaller half         Larger half

Max Heap:       [1]                Min Heap: [-1, 3]
```

More precisely:

```
        Max Heap                 Min Heap

           1                        -1
                                     |
                                     3
```

The max heap's root represents the largest element in the smaller half.

The min heap's root represents the smallest element in the larger half.

For an odd-sized window:

```
maxHeap.size() = minHeap.size() + 1
```

Median:

```
maxHeap.peek()
```

For an even-sized window:

```
maxHeap.size() = minHeap.size()
```

Median:

```
(maxHeap.peek() + minHeap.peek()) / 2.0
```

**Important:** These are logical heap sizes, excluding elements that have been marked for deletion.

### **2.2 The sliding window challenge**

Consider:

```
nums = [1, 3, -1, -3, 5, 3]
k = 3
```

Initially:

```
[1, 3, -1]
```

Next window:

```
[3, -1, -3]
```

We must:

- Insert `-3`.
- Remove `1`.
- Rebalance the heaps.
- Calculate the new median.

But what if `1` is buried somewhere inside a heap?

We cannot efficiently remove it from a normal priority queue.

### **2.3 Lazy deletion — The key optimization**

Instead of immediately removing an element from a heap, we mark it as deleted.

We maintain:

```
Map<Integer, Integer> delayed = new HashMap<>();
```

This map stores the frequency of elements that should be removed when they reach the top of a heap.

For example:

```
delayed = {
    1 -> 1
}
```

This means one occurrence of `1` should be discarded.

Whenever we inspect the root of a heap:

1. Check whether the root exists in `delayed`.
2. If yes, remove it from the heap.
3. Decrease its delayed-deletion frequency.
4. Continue until the root is valid.

This is called **lazy deletion** because physical deletion is postponed until the element becomes accessible at the heap's root.

## **3. Edge cases to watch out for**

| Edge case                       | Input                         | Expected behavior |
| ------------------------------- | ----------------------------- | ----------------- |
| Window size is 1                | `[5, 2, 8], k=1`              | `[5, 2, 8]`       |
| Window size equals array size   | `[1, 2, 3], k=3`              | `[2]`             |
| Even window size                | `[1, 2, 3, 4], k=2`           | `[1.5, 2.5, 3.5]` |
| Negative numbers                | `[-5, -2, -8], k=2`           | `[-3.5, -5.0]`    |
| All elements equal              | `[2, 2, 2, 2], k=2`           | `[2, 2, 2]`       |
| Integer overflow                | `[MAX_VALUE, MAX_VALUE], k=2` | `2147483647.0`    |
| Duplicate values during removal | `[1, 2, 2, 3], k=3`           | `[2, 2]`          |

**Particularly important:** Avoid this:

```
return (a + b) / 2.0;
```

The addition `a + b` happens using integer arithmetic and can overflow.

Instead, use:

```
return ((double) a + b) / 2.0;
```

# **4. All possible solutions**

## **Approach 1: Brute Force — Sort every window**

### **Mental model**

For every window:

1. Copy its `k` elements into a temporary array.
2. Sort the temporary array.
3. Calculate the median.
4. Move to the next window.

This is the most straightforward approach.

```java

import java.util.Arrays;

class Solution {

    public double[] medianSlidingWindow(int[] nums, int k) {

        int n = nums.length;

        // There are exactly n - k + 1 windows.
        double[] result = new double[n - k + 1];

        for (int left = 0; left <= n - k; left++) {

            // Extract the current window.
            int[] window = Arrays.copyOfRange(
                nums,
                left,
                left + k
            );

            // Sorting allows us to access the middle element(s).
            Arrays.sort(window);

            // Odd window: exactly one middle element.
            if (k % 2 == 1) {

                result[left] = window[k / 2];

            } else {

                // Even window: average of two middle elements.
                // Cast before addition to prevent integer overflow.
                result[left] =
                    ((double) window[k / 2 - 1]
                    + window[k / 2]) / 2.0;
            }
        }

        return result;
    }
}

/*
 * TIME COMPLEXITY:
 *
 * Number of windows = n - k + 1.
 *
 * For every window:
 * 1. Copying k elements: O(k).
 * 2. Sorting k elements: O(k log k).
 * 3. Calculating median: O(1).
 *
 * Total:
 * O((n - k + 1) * k log k)
 *
 * SPACE COMPLEXITY:
 *
 * Temporary window array: O(k).
 * Result array: O(n - k + 1).
 *
 * Auxiliary space excluding output: O(k).
 *
 * Problem:
 * We repeatedly sort almost identical windows.
 * This wastes a lot of work.
 */

```

**Why is this inefficient?**

When the window moves one position, only two things change:

- One element enters.
- One element leaves.

But we sort all `k` elements again.

We should reuse the ordering information instead.

## **Approach 2: Optimal — Two Heaps with Lazy Deletion**

This is the classic heap-based solution.

### **2.1 Data structures**

We maintain:

```
PriorityQueue<Integer> small;
PriorityQueue<Integer> large;
Map<Integer, Integer> delayed;
```

Their responsibilities:

| Data structure | Responsibility                                   |
| -------------- | ------------------------------------------------ |
| `small`        | Max heap containing the smaller half             |
| `large`        | Min heap containing the larger half              |
| `delayed`      | Tracks elements waiting to be physically removed |

We also maintain:

```
int smallSize;
int largeSize;
```

These represent the number of **valid elements**, not the physical heap sizes.

### **2.2 Heap invariants**

We always maintain:

**Invariant 1: Ordering**

```
Every valid element in small <= every valid element in large.
```

**Invariant 2: Balance**

```
smallSize == largeSize

OR

smallSize == largeSize + 1
```

Therefore:

```
Odd k:

small has one additional valid element.

Median = small.peek()


Even k:

Both heaps have equal valid elements.

Median = average(small.peek(), large.peek())
```

### **2.3 Visual example**

Consider:

```
nums = [1, 3, -1]
k = 3
```

After insertion:

```
                Window
              [1, 3, -1]

          SMALL                 LARGE
          Max Heap              Min Heap

             1                    -1
                                  |
                                   3
```

Conceptually, the sorted values are:

```
[-1, 1, 3]
      ^
    Median
```

Now the window slides:

```
[1, 3, -1] -> [3, -1, -3]
```

Operations:

```
1. Insert -3.
2. Mark 1 for deletion.
3. Prune invalid heap roots.
4. Rebalance the heaps.
5. Read the median.
```

### **2.4 Complete Java 24 implementation**

```java

import java.util.*;

class Solution {

    /*
     * SMALL:
     *
     * Max heap containing the smaller half of the values.
     * Its root is the largest element in the smaller half.
     */
    private final PriorityQueue<Integer> small =
        new PriorityQueue<>(Comparator.reverseOrder());

    /*
     * LARGE:
     *
     * Min heap containing the larger half of the values.
     * Its root is the smallest element in the larger half.
     */
    private final PriorityQueue<Integer> large =
        new PriorityQueue<>();

    /*
     * DELAYED:
     *
     * Tracks values that must eventually be removed.
     *
     * Example:
     * {5 -> 2} means two occurrences of 5
     * should be discarded when they reach a heap root.
     *
     * Frequencies are necessary because duplicates are allowed.
     */
    private final Map<Integer, Integer> delayed =
        new HashMap<>();

    /*
     * Logical sizes:
     *
     * These count only valid elements.
     *
     * They are deliberately different from small.size()
     * and large.size(), because physical heaps may contain
     * elements waiting for lazy deletion.
     */
    private int smallSize = 0;
    private int largeSize = 0;

    public double[] medianSlidingWindow(int[] nums, int k) {

        int n = nums.length;

        double[] result = new double[n - k + 1];

        /*
         * Initialize the first window.
         */
        for (int i = 0; i < k; i++) {
            addNum(nums[i]);
        }

        result[0] = getMedian(k);

        /*
         * Slide the window.
         *
         * At each step:
         * 1. Add the incoming element.
         * 2. Remove the outgoing element.
         * 3. Calculate the new median.
         */
        for (int right = k; right < n; right++) {

            int incoming = nums[right];
            int outgoing = nums[right - k];

            addNum(incoming);

            removeNum(outgoing);

            result[right - k + 1] = getMedian(k);
        }

        return result;
    }

    /*
     * INSERT OPERATION
     *
     * Insert into the appropriate heap based on the
     * maximum element of the smaller half.
     */
    private void addNum(int num) {

        /*
         * Clean stale elements before comparing against
         * the root of the smaller heap.
         */
        prune(small);

        if (small.isEmpty() || num <= small.peek()) {

            small.offer(num);
            smallSize++;

        } else {

            large.offer(num);
            largeSize++;
        }

        rebalance();
    }

    /*
     * REMOVE OPERATION
     *
     * We cannot efficiently remove an arbitrary element
     * from PriorityQueue.
     *
     * Therefore, we:
     * 1. Mark the element in delayed.
     * 2. Decrease the logical size of its heap.
     * 3. Physically remove it later when it reaches the root.
     */
    private void removeNum(int num) {

        prune(small);

        /*
         * Determine which logical heap owns this occurrence.
         *
         * If num <= small.peek(), classify it as belonging
         * to small. Otherwise, it belongs to large.
         *
         * This classification works with duplicates because
         * equal values can safely belong to either side.
         */
        delayed.merge(num, 1, Integer::sum);

        if (!small.isEmpty() && num <= small.peek()) {

            smallSize--;

            /*
             * If the element is already at the root,
             * remove it immediately.
             */
            if (num == small.peek()) {
                prune(small);
            }

        } else {

            largeSize--;

            /*
             * Similarly, remove immediately if it is at
             * the root of the larger heap.
             */
            if (!large.isEmpty() && num == large.peek()) {
                prune(large);
            }
        }

        /*
         * Removing an element can break the size invariant.
         */
        rebalance();
    }

    /*
     * LAZY DELETION
     *
     * Physically remove invalid elements from the heap root.
     *
     * Why only the root?
     *
     * PriorityQueue exposes its highest-priority element
     * efficiently, but does not expose arbitrary elements
     * efficiently.
     *
     * An invalid element buried inside the heap does not
     * affect the median until it reaches the root.
     */
    private void prune(PriorityQueue<Integer> heap) {

        while (!heap.isEmpty()) {

            int num = heap.peek();

            Integer count = delayed.get(num);

            /*
             * No pending deletion for this root.
             * Therefore, it is valid.
             */
            if (count == null) {
                break;
            }

            /*
             * Remove the invalid root physically.
             */
            heap.poll();

            /*
             * Consume exactly one pending deletion.
             */
            if (count == 1) {

                delayed.remove(num);

            } else {

                delayed.put(num, count - 1);
            }
        }
    }

    /*
     * REBALANCING
     *
     * Required invariant:
     *
     * smallSize == largeSize
     *
     * OR
     *
     * smallSize == largeSize + 1
     *
     * Therefore, the smaller heap can contain at most
     * one additional valid element.
     */
    private void rebalance() {

        /*
         * Too many valid elements in small.
         *
         * Move its largest element into large.
         */
        if (smallSize > largeSize + 1) {

            prune(small);

            large.offer(small.poll());

            smallSize--;
            largeSize++;

            /*
             * The moved element might be a stale entry
             * only if pruning was insufficient, but pruning
             * above guarantees the root is valid.
             */
            prune(small);
        }

        /*
         * Too many valid elements in large.
         *
         * Move its smallest element into small.
         */
        else if (smallSize < largeSize) {

            prune(large);

            small.offer(large.poll());

            largeSize--;
            smallSize++;

            prune(large);
        }
    }

    /*
     * MEDIAN OPERATION
     *
     * Odd k:
     * The smaller heap has one extra valid element.
     * Its root is the median.
     *
     * Even k:
     * Both heaps have equal valid elements.
     * Their roots are the two middle values.
     */
    private double getMedian(int k) {

        prune(small);
        prune(large);

        if (k % 2 == 1) {

            return small.peek();

        }

        return ((double) small.peek() + large.peek()) / 2.0;
    }
}

```

### **2.5 Complexity analysis**

Let:

- `n` = number of elements.
- `k` = sliding window size.

| Operation             | Complexity                          |
| --------------------- | ----------------------------------- |
| Insert                | \\(O(\log n)\\) worst case          |
| Lazy deletion marking | \\(O(1)\\) average                  |
| Physical pruning      | \\(O(\log n)\\) per removed element |
| Rebalancing           | \\(O(\log n)\\)                     |
| Median lookup         | \\(O(1)\\), excluding pruning       |

**Overall time complexity:**

\\[ O(n\log n) \\]

Why not automatically claim \\(O(n\log k)\\)?

Because stale elements buried inside the heaps can remain there for many iterations. The physical heaps can grow to \\(O(n)\\), even though there are only `k` valid elements.

Each element is inserted once and physically removed at most once, so the amortized bound is \\(O(n\log n)\\).

**Space complexity:**

\\[ O(n) \\]

The heaps and delayed-deletion map can collectively retain \\(O(n)\\) entries in the worst case.

This is an important subtlety when discussing lazy deletion in interviews.

## **Approach 3: Two balanced multisets using TreeMap**

This is another excellent Java solution.

In Java, `TreeMap` is a balanced red-black tree.

It provides:

- \\(O(\log k)\\) insertion.
- \\(O(\log k)\\) deletion.
- \\(O(\log k)\\) lookup.

However, Java's `TreeMap` is not a multiset: it cannot directly store duplicate keys.

We solve that by storing frequencies:

```
TreeMap<Integer, Integer>
```

Example:

```
Values: [1, 2, 2, 3, 3, 3]

TreeMap:

1 -> 1
2 -> 2
3 -> 3
```

We maintain two such maps:

```
TreeMap<Integer, Integer> small;
TreeMap<Integer, Integer> large;
```

### **3.1 Mental model**

Same two-partition idea:

```
SMALL                         LARGE

Smaller half                  Larger half

1 -> 1                        3 -> 2
2 -> 2                        4 -> 1

             ^
          Boundary
```

The important difference:

Instead of heaps, we use ordered maps.

We can directly access:

```
small.lastKey(); // Largest value in smaller half

large.firstKey(); // Smallest value in larger half
```

We can also remove an arbitrary value in \\(O(\log k)\\).

No lazy deletion is required.

### **3.2 Complete Java 24 implementation**

```java

import java.util.*;

class Solution {

    /*
     * SMALL:
     *
     * Stores the smaller half of the window.
     *
     * lastKey() gives the largest value in this partition.
     */
    private final TreeMap<Integer, Integer> small =
        new TreeMap<>();

    /*
     * LARGE:
     *
     * Stores the larger half of the window.
     *
     * firstKey() gives the smallest value in this partition.
     */
    private final TreeMap<Integer, Integer> large =
        new TreeMap<>();

    /*
     * Logical sizes count total occurrences, not distinct keys.
     *
     * For example:
     * {2 -> 3, 5 -> 1} has size 4, not 2.
     */
    private int smallSize = 0;
    private int largeSize = 0;

    public double[] medianSlidingWindow(int[] nums, int k) {

        int n = nums.length;

        double[] result = new double[n - k + 1];

        // Build the initial window.
        for (int i = 0; i < k; i++) {
            addNum(nums[i]);
        }

        result[0] = getMedian(k);

        // Slide the window one position at a time.
        for (int right = k; right < n; right++) {

            int incoming = nums[right];
            int outgoing = nums[right - k];

            // Insert the new element.
            addNum(incoming);

            // Remove the element leaving the window.
            removeNum(outgoing);

            // Calculate the median of the updated window.
            result[right - k + 1] = getMedian(k);
        }

        return result;
    }

    /*
     * INSERT
     *
     * Insert into the appropriate partition.
     *
     * Every value in small must be <= every value in large.
     */
    private void addNum(int num) {

        if (small.isEmpty() || num <= small.lastKey()) {

            add(small, num);
            smallSize++;

        } else {

            add(large, num);
            largeSize++;
        }

        rebalance();
    }

    /*
     * REMOVE
     *
     * Unlike PriorityQueue, TreeMap supports direct key removal
     * in O(log k).
     *
     * Since duplicates are interchangeable, if num equals the
     * boundary, we can safely remove one occurrence from small.
     */
    private void removeNum(int num) {

        if (!small.isEmpty() && num <= small.lastKey()) {

            remove(small, num);
            smallSize--;

        } else {

            remove(large, num);
            largeSize--;
        }

        rebalance();
    }

    /*
     * ADD ONE OCCURRENCE
     *
     * merge handles duplicate values by incrementing frequency.
     */
    private void add(TreeMap<Integer, Integer> map, int num) {

        map.merge(num, 1, Integer::sum);
    }

    /*
     * REMOVE ONE OCCURRENCE
     *
     * If frequency is greater than one, decrement it.
     * Otherwise, remove the key completely.
     */
    private void remove(TreeMap<Integer, Integer> map, int num) {

        int count = map.get(num);

        if (count == 1) {

            map.remove(num);

        } else {

            map.put(num, count - 1);
        }
    }

    /*
     * REBALANCE
     *
     * Invariant:
     *
     * smallSize == largeSize
     *
     * OR
     *
     * smallSize == largeSize + 1
     *
     * Move the boundary element between partitions when needed.
     */
    private void rebalance() {

        // SMALL has more than one extra element.
        if (smallSize > largeSize + 1) {

            int value = small.lastKey();

            remove(small, value);
            add(large, value);

            smallSize--;
            largeSize++;
        }

        // LARGE has more elements than SMALL.
        else if (smallSize < largeSize) {

            int value = large.firstKey();

            remove(large, value);
            add(small, value);

            largeSize--;
            smallSize++;
        }
    }

    /*
     * MEDIAN
     *
     * Odd k:
     * The largest value in small is the middle element.
     *
     * Even k:
     * The largest value in small and smallest value in large
     * are the two middle elements.
     */
    private double getMedian(int k) {

        if (k % 2 == 1) {

            return small.lastKey();

        }

        return ((double) small.lastKey() + large.firstKey()) / 2.0;
    }
}

/*
 * TIME COMPLEXITY:
 *
 * addNum:
 * O(log k)
 *
 * removeNum:
 * O(log k)
 *
 * rebalance:
 * O(log k), because at most one element is transferred.
 *
 * getMedian:
 * O(log k) for TreeMap key access in Java.
 *
 * Number of windows:
 * n - k + 1.
 *
 * Overall:
 * O(n log k)
 *
 * SPACE COMPLEXITY:
 *
 * Both TreeMaps together contain exactly k valid elements
 * after every completed window update.
 *
 * Therefore:
 * O(k) auxiliary space.
 *
 * No lazy-deletion entries accumulate.
 */

```

### **3.3 Why this solution is particularly attractive in Java**

Let's compare the two approaches:

| Feature                    | Two heaps + lazy deletion   | Two TreeMaps     |
| -------------------------- | --------------------------- | ---------------- |
| Insert                     | Heap insertion              | Map insertion    |
| Arbitrary deletion         | Lazy deletion               | Direct deletion  |
| Duplicate support          | Frequency map               | Frequency map    |
| Median access              | Heap roots                  | First/last keys  |
| Logical sizes needed       | Yes                         | Yes              |
| Lazy deletion needed       | Yes                         | No               |
| Worst-case auxiliary space | \\(O(n)\\)                  | \\(O(k)\\)       |
| Overall time               | \\(O(n\log n)\\) worst case | \\(O(n\log k)\\) |
| Implementation complexity  | Higher                      | Lower            |

**My recommendation in a Java interview:** Present the two-heap solution first because it demonstrates heap-based median maintenance and lazy deletion. Then present the `TreeMap` solution as a particularly clean Java alternative with a stronger worst-case space guarantee.

## **5. Which approach should you choose?**

| Approach                  | Time complexity             | Auxiliary space | Recommendation        |
| ------------------------- | --------------------------- | --------------- | --------------------- |
| Sort every window         | \\(O(nk\log k)\\)           | \\(O(k)\\)      | Brute force           |
| Two heaps + lazy deletion | \\(O(n\log n)\\) worst case | \\(O(n)\\)      | Classic heap solution |
| Two TreeMaps              | \\(O(n\log k)\\)            | \\(O(k)\\)      | Strong Java solution  |

There is also a useful distinction:

- If the interviewer specifically asks for a heap-based approach, use two heaps with lazy deletion.
- If the interviewer emphasizes strict \\(O(n\log k)\\) time and \\(O(k)\\) space in Java, the two-`TreeMap` implementation is a strong choice.

# **6. Interviewer follow-up questions and answers**

### **Q1. Why can't we simply remove an element from PriorityQueue?**

Java's `PriorityQueue.remove(Object)` takes \\(O(k)\\) time in the worst case.

It must search for the element before removing it and restoring the heap property.

That's why we use lazy deletion:

- Mark the element for deletion.
- Remove it when it reaches the heap root.

This avoids searching the entire heap.

### **Q2. Why do we maintain&#x20;**`smallSize`**&#x20;and&#x20;**`largeSize`**&#x20;instead of using&#x20;**`small.size()`**&#x20;and&#x20;**`large.size()`**?**

Because physical heap sizes include stale elements.

Consider:

```
small physical elements = [5, 3, 1]
```

Suppose `1` has been marked for deletion but is buried inside the heap.

Then:

```
small.size() = 3

smallSize = 2
```

The logical size must be used for balancing and median calculation.

### **Q3. Why do we use a frequency map for lazy deletion?**

Because duplicates are allowed.

Consider:

```
window = [2, 2, 3]
```

If we remove one occurrence of `2`, we cannot mark the value itself as completely deleted.

We need to track how many occurrences are pending deletion.

Hence:

```
delayed.merge(num, 1, Integer::sum);
```

### **Q4. Why do we use&#x20;**`num <= small.peek()`**&#x20;when deciding which heap to remove from?**

Because `small.peek()` represents the maximum element in the smaller partition.

Therefore:

```
num <= small.peek()
```

indicates that the value can belong to the smaller partition.

For equal values appearing in both heaps, either identical occurrence can be removed. Their values are interchangeable, so the logical partition sizes remain correct.

### **Q5. Why do we rebalance after both insertion and deletion?**

Both operations can violate the size invariant.

For example:

```
smallSize = 2
largeSize = 1
```

If we insert into `large`:

```
smallSize = 2
largeSize = 2
```

This is valid.

But if we insert into `large` again:

```
smallSize = 2
largeSize = 3
```

This is invalid.

Rebalancing restores:

```
smallSize == largeSize

OR

smallSize == largeSize + 1
```

### **Q6. Why is one&#x20;**`if`**&#x20;sufficient instead of a&#x20;**`while`**&#x20;loop in&#x20;**`rebalance()`**?**

Because before each insertion or deletion, the heaps already satisfy the balance invariant.

Each operation changes the logical size of exactly one heap by one.

Therefore, the imbalance can increase by at most one element.

Moving one element from one heap to the other is sufficient to restore the invariant.

This assumes we rebalance after every individual insertion or deletion, as in our implementation.

### **Q7. Can we solve this using a single TreeMap?**

Yes, but finding the middle element would require traversing the ordered entries or maintaining additional indexing information.

Using two TreeMaps is simpler because the median is always at the boundary between the two partitions.

### **Q8. Can we use a balanced BST with order statistics?**

Yes.

An augmented balanced BST can maintain subtree sizes.

It supports:

- Insert: \\(O(\log k)\\).
- Delete: \\(O(\log k)\\).
- Find kth smallest: \\(O(\log k)\\).

This is a general solution for dynamic order-statistics problems.

However, Java does not provide a built-in order-statistics tree.

### **Q9. What happens when&#x20;**`k = 1`**?**

Every window contains exactly one element.

The median is simply that element.

Both implementations handle this without special-case logic.

### **Q10. Why do we cast to double before calculating the average?**

Consider:

```
int a = Integer.MAX_VALUE;
int b = Integer.MAX_VALUE;
```

This can overflow:

```
(a + b) / 2.0;
```

Correct:

```
((double) a + b) / 2.0;
```

The addition now happens using double precision.

# **7. Dry run — Two heaps**

Let's walk through the first example.

```
nums = [1, 3, -1, -3, 5, 3, 6, 7]
k = 3
```

We maintain:

- `small`: max heap.
- `large`: min heap.
- `delayed`: pending deletions.

| Window        | Sorted window | Small (valid) | Large (valid) | Median |
| ------------- | ------------- | ------------- | ------------- | ------ |
| `[1, 3, -1]`  | `[-1, 1, 3]`  | `[1, -1]`     | `[3]`         | 1      |
| `[3, -1, -3]` | `[-3, -1, 3]` | `[-1, -3]`    | `[3]`         | -1     |
| `[-1, -3, 5]` | `[-3, -1, 5]` | `[-1, -3]`    | `[5]`         | -1     |


# **8. Important concepts to remember**

This problem tests several important DSA concepts together.

| Concept           | What you should remember                       |
| ----------------- | ---------------------------------------------- |
| Two heaps         | Maintain the smaller and larger halves         |
| Max heap          | Access the largest element of the smaller half |
| Min heap          | Access the smallest element of the larger half |
| Lazy deletion     | Defer arbitrary heap deletion                  |
| HashMap frequency | Handle duplicate values                        |
| Logical heap size | Ignore stale elements while balancing          |
| Rebalancing       | Maintain the median partition invariant        |
| TreeMap           | Alternative for ordered insertion and deletion |

**My interview recommendation:**

Understand these three problems together:

1. **295. Find Median from Data Stream** — Learn two heaps.
2. **480. Sliding Window Median** — Extend two heaps with lazy deletion.
3. **1825. Finding MK Average** — Extend ordered partitions to maintain more than just the median.

The central mental model is:

**Maintain an ordered partition, efficiently insert and remove elements, and keep the boundary balanced.**

Once you understand that, these problems become variations of the same underlying technique.
