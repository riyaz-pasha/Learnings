# **1348. Tweet Counts Per Frequency**

**Difficulty:** Medium\
**Pattern:** HashMap + Binary Search / Sorting / Bucket Counting\
**Data Structure:** `HashMap<String, List<Integer>>`

## **0. Simplifying the problem**

We need to design a data structure that supports two operations:

1. `recordTweet(tweetName, time)` – Store the timestamp of a tweet.
2. `getTweetCountsPerFrequency(freq, tweetName, startTime, endTime)` – Count how many tweets occurred in each time interval.

There are three possible frequencies:

| Frequency | Chunk size     |
| --------- | -------------- |
| minute    | 60 seconds     |
| hour      | 3,600 seconds  |
| day       | 86,400 seconds |

**Important:** The intervals are inclusive, and the final interval can be shorter than the requested frequency.

For example:

```
startTime = 0
endTime   = 210
freq      = minute
```

The intervals are:

```
[0, 59]
[60, 119]
[120, 179]
[180, 210]
```

We need to return the number of tweets in each interval.

## **1. Clarifying questions to ask the interviewer**

| Question                                                               | Why clarify?                                                               |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Can tweets arrive out of chronological order?                          | Determines whether we need sorting or an ordered data structure.           |
| Can multiple tweets have the same timestamp?                           | Determines whether timestamps should be stored individually or aggregated. |
| Are startTime and endTime inclusive?                                   | Determines interval boundary handling.                                     |
| Can we receive queries for timestamps before the first recorded tweet? | Helps ensure empty intervals return zero.                                  |
| Can tweet names be arbitrary strings?                                  | Determines how we organize tweets by name.                                 |

Based on the problem statement:

- Tweets can arrive out of order.
- Multiple tweets can share a timestamp.
- Both interval boundaries are inclusive.
- Empty intervals must return zero.
- We have at most \\(10^4\\) operations.

# **2. Core intuition**

The central observation is:

**Tweets belonging to different tweet names should be stored independently.**

For example:

```
tweet3 -> [0, 60, 10, 120]
tweet5 -> [10, 30, 90]
tweet7 -> [100, 200]
```

We can use:

```
Map<String, List<Integer>>
```

The key is the tweet name, and the value is the list of timestamps.

When a query arrives:

1. Find the timestamps belonging to the requested tweet name.
2. Calculate how many chunks are required.
3. Create an integer array initialized with zeros.
4. Iterate through the timestamps.
5. Ignore timestamps outside the requested range.
6. Calculate the appropriate chunk index.
7. Increment the corresponding bucket.

### **The most important formula**

For a timestamp `time`, its bucket index is:

\\[ \boxed{\text{bucketIndex} = \frac{time-startTime}{chunkSize}} \\]

Integer division automatically assigns the timestamp to the correct chunk.

Example:

```
startTime = 0
chunkSize = 60

time = 0   -> (0 - 0) / 60 = 0
time = 10  -> (10 - 0) / 60 = 0
time = 59  -> (59 - 0) / 60 = 0
time = 60  -> (60 - 0) / 60 = 1
time = 120 -> (120 - 0) / 60 = 2
```

Therefore:

```
Bucket 0 -> [0, 59]
Bucket 1 -> [60, 119]
Bucket 2 -> [120, 179]
```

# **3. All possible solutions**

## **Approach 1: Brute Force — Scan every timestamp for every bucket**

### **Idea**

For every interval, iterate through all recorded timestamps and count the timestamps that belong to that interval.

This is straightforward but repeatedly scans the same timestamps.

```java
import java.util.*;

class TweetCounts {

    // Stores all timestamps grouped by tweet name.
    private final Map<String, List<Integer>> tweets = new HashMap<>();

    public void recordTweet(String tweetName, int time) {

        // Create a list if this tweet name has never been recorded.
        tweets.computeIfAbsent(tweetName, key -> new ArrayList<>())
              .add(time);
    }

    public List<Integer> getTweetCountsPerFrequency(
            String freq,
            String tweetName,
            int startTime,
            int endTime) {

        // Map frequency to its corresponding chunk size.
        int chunkSize = switch (freq) {
            case "minute" -> 60;
            case "hour" -> 3600;
            case "day" -> 86400;
            default -> throw new IllegalArgumentException("Invalid frequency");
        };

        // Number of inclusive intervals.
        // Example: start=0, end=60, chunkSize=60 => 2 buckets.
        int bucketCount = (endTime - startTime) / chunkSize + 1;

        List<Integer> result = new ArrayList<>();

        // Fetch timestamps for the requested tweet name.
        List<Integer> timestamps = tweets.getOrDefault(
                tweetName, Collections.emptyList()
        );

        // Process each bucket independently.
        for (int bucket = 0; bucket < bucketCount; bucket++) {

            int bucketStart = startTime + bucket * chunkSize;

            // The final bucket may be shorter.
            int bucketEnd = Math.min(
                    endTime,
                    bucketStart + chunkSize - 1
            );

            int count = 0;

            // Scan every timestamp for this bucket.
            for (int timestamp : timestamps) {

                // Both boundaries are inclusive.
                if (timestamp >= bucketStart && timestamp <= bucketEnd) {
                    count++;
                }
            }

            result.add(count);
        }

        return result;
    }
}
```

### **Complexity analysis**

Let:

- \\(N\\) = number of timestamps for the requested tweet name.
- \\(B\\) = number of buckets.

| Operation                      | Complexity     |
| ------------------------------ | -------------- |
| `recordTweet()`                | O(1) amortized |
| `getTweetCountsPerFrequency()` | O(N × B)       |
| Storage                        | O(N)           |

**Why is querying O(N × B)?**

We scan all N timestamps separately for each of the B buckets.

This repeats unnecessary work.

## **Approach 2: Optimal for the given constraints — HashMap + Bucket Counting**

This is the approach I would recommend implementing in an interview.

### **Idea**

Instead of scanning timestamps separately for each bucket, scan them only once.

For each timestamp:

1. Check whether it belongs to the requested range.
2. Calculate its bucket index.
3. Increment that bucket.

### **Java 24 implementation**

```java
import java.util.*;

class TweetCounts {

    // Each tweet name maps to its recorded timestamps.
    //
    // Example:
    // {
    //     "tweet3" -> [0, 60, 10, 120],
    //     "tweet5" -> [10, 30, 90]
    // }
    //
    // HashMap provides O(1) average lookup by tweet name.
    private final Map<String, List<Integer>> tweets = new HashMap<>();

    public TweetCounts() {
        // No initialization is necessary.
    }

    public void recordTweet(String tweetName, int time) {

        // If the tweet name does not exist, create its timestamp list.
        // Otherwise, retrieve the existing list.
        //
        // Append the timestamp in O(1) amortized time.
        //
        // We intentionally do not maintain sorted order because
        // timestamps can arrive out of chronological order.
        tweets.computeIfAbsent(tweetName, key -> new ArrayList<>())
              .add(time);
    }

    public List<Integer> getTweetCountsPerFrequency(
            String freq,
            String tweetName,
            int startTime,
            int endTime) {

        // Convert frequency into seconds.
        //
        // switch expression is available in modern Java.
        int chunkSize = switch (freq) {
            case "minute" -> 60;
            case "hour" -> 3600;
            case "day" -> 86400;
            default -> throw new IllegalArgumentException(
                    "Unsupported frequency: " + freq
            );
        };

        // Calculate how many buckets are needed.
        //
        // Formula:
        // bucketCount = (endTime - startTime) / chunkSize + 1
        //
        // Why +1?
        // Because both startTime and endTime are inclusive.
        //
        // Example:
        // startTime = 0, endTime = 60, chunkSize = 60
        //
        // Bucket 0: [0, 59]
        // Bucket 1: [60, 60]
        //
        // Therefore, we need 2 buckets.
        int bucketCount = (endTime - startTime) / chunkSize + 1;

        // Initialize all buckets to zero.
        //
        // This is important because some intervals may not contain tweets.
        // We must still return zero for those intervals.
        int[] buckets = new int[bucketCount];

        // Retrieve timestamps for the requested tweet name.
        //
        // If no tweets exist for this name, return all-zero buckets.
        List<Integer> timestamps = tweets.get(tweetName);

        if (timestamps == null) {

            // Arrays.stream(...).boxed() converts int[] into Stream<Integer>.
            // The returned list contains one zero for every bucket.
            return Arrays.stream(buckets)
                         .boxed()
                         .toList();
        }

        // Process every recorded timestamp exactly once.
        for (int timestamp : timestamps) {

            // Ignore tweets outside the requested inclusive range.
            if (timestamp < startTime || timestamp > endTime) {
                continue;
            }

            // Calculate which bucket contains this timestamp.
            //
            // Integer division automatically maps timestamps to chunks.
            //
            // Example:
            // startTime = 0, chunkSize = 60
            //
            // timestamp = 10  => bucket 0
            // timestamp = 59  => bucket 0
            // timestamp = 60  => bucket 1
            // timestamp = 120 => bucket 2
            //
            // Subtracting startTime is essential because buckets
            // are relative to the query's starting timestamp.
            int bucketIndex = (timestamp - startTime) / chunkSize;

            // Increment the corresponding bucket.
            buckets[bucketIndex]++;
        }

        // Convert int[] into List<Integer>.
        //
        // toList() returns an unmodifiable list, which is perfectly
        // acceptable because the problem only requires returning counts.
        return Arrays.stream(buckets)
                     .boxed()
                     .toList();
    }
}
```


**Step 2: Calculate bucket count**

\\[ B = \frac{120-0}{60}+1 = 3 \\]

Initialize:

```
buckets = [0, 0, 0]
```

**Step 3: Process timestamps**

| Timestamp | Bucket calculation | Updated buckets |
| --------- | ------------------ | --------------- |
| 0         | (0 - 0) / 60 = 0   | [1, 0, 0]       |
| 60        | (60 - 0) / 60 = 1  | [1, 1, 0]       |

### **Complexity analysis**

Let:

- \\(N\\) = total timestamps recorded for the requested tweet name.
- \\(B\\) = number of buckets.
- \\(T\\) = total number of recorded tweets across all names.

| Operation                      | Time complexity |
| ------------------------------ | --------------- |
| Constructor                    | O(1)            |
| `recordTweet()`                | O(1) amortized  |
| `getTweetCountsPerFrequency()` | O(N + B)        |
| Total storage                  | O(T)            |
| Query auxiliary space          | O(B)            |

**Why O(N + B)?**

- We iterate through N timestamps exactly once: O(N).
- We initialize B buckets: O(B).
- We convert B integers into a list: O(B).

Therefore:

\\[ \boxed{O(N+B)} \\]

This is significantly better than the brute-force O(N × B).

## **Approach 3: HashMap + Sorted Timestamps + Binary Search**

This approach is useful when the system receives many queries over previously recorded data.

### **Idea**

The previous approach scans every timestamp, even if most timestamps are outside the requested range.

We can improve this by maintaining timestamps in sorted order.

For every query:

1. Find the first timestamp greater than or equal to `startTime` using lower bound.
2. Find the first timestamp greater than `endTime` using upper bound.
3. Iterate only through timestamps inside the requested range.
4. Calculate the corresponding bucket and increment it.

This avoids scanning timestamps outside the requested range.

### **Java implementation**

```java
import java.util.*;

class TweetCounts {

    // TreeMap keeps timestamps sorted automatically.
    //
    // timestamp -> number of tweets at that timestamp
    //
    // Example:
    // {
    //     0   -> 1,
    //     10  -> 1,
    //     60  -> 2,
    //     120 -> 1
    // }
    //
    // The count handles multiple tweets at the same timestamp.
    private final Map<String, NavigableMap<Integer, Integer>> tweets =
            new HashMap<>();

    public TweetCounts() {
    }

    public void recordTweet(String tweetName, int time) {

        // Create a TreeMap for a new tweet name.
        NavigableMap<Integer, Integer> timeline =
                tweets.computeIfAbsent(
                        tweetName,
                        key -> new TreeMap<>()
                );

        // Increment the frequency of the timestamp.
        //
        // TreeMap insertion/update takes O(log M),
        // where M is the number of distinct timestamps for this name.
        timeline.merge(time, 1, Integer::sum);
    }

    public List<Integer> getTweetCountsPerFrequency(
            String freq,
            String tweetName,
            int startTime,
            int endTime) {

        int chunkSize = switch (freq) {
            case "minute" -> 60;
            case "hour" -> 3600;
            case "day" -> 86400;
            default -> throw new IllegalArgumentException(
                    "Unsupported frequency: " + freq
            );
        };

        int bucketCount = (endTime - startTime) / chunkSize + 1;

        int[] buckets = new int[bucketCount];

        NavigableMap<Integer, Integer> timeline = tweets.get(tweetName);

        if (timeline == null) {
            return Arrays.stream(buckets).boxed().toList();
        }

        // subMap includes both startTime and endTime.
        //
        // TreeMap navigates to the requested range efficiently.
        //
        // Its range view contains only timestamps:
        // startTime <= timestamp <= endTime.
        NavigableMap<Integer, Integer> range =
                timeline.subMap(startTime, true, endTime, true);

        // Iterate only through timestamps inside the requested range.
        for (Map.Entry<Integer, Integer> entry : range.entrySet()) {

            int timestamp = entry.getKey();

            // Number of tweets at this exact timestamp.
            int count = entry.getValue();

            // Calculate the appropriate bucket.
            int bucketIndex = (timestamp - startTime) / chunkSize;

            // Add all tweets recorded at this timestamp.
            buckets[bucketIndex] += count;
        }

        return Arrays.stream(buckets).boxed().toList();
    }
}
```

### **Complexity analysis**

Let:

- \\(M\\) = number of distinct timestamps for the requested tweet name.
- \\(K\\) = number of distinct timestamps inside the requested range.
- \\(B\\) = number of buckets.

| Operation                   | Time complexity  |
| --------------------------- | ---------------- |
| `recordTweet()`             | O(log M)         |
| Query range navigation      | O(log M)         |
| Iterate matching timestamps | O(K)             |
| Construct result            | O(B)             |
| Total query                 | O(log M + K + B) |
| Storage                     | O(T)             |

This approach is especially useful when:

- There are many historical timestamps.
- Queries frequently cover small time ranges.
- Most recorded timestamps are outside the requested range.

**Trade-off:** Recording tweets is more expensive because TreeMap maintains sorted order.

# **4. Comparing all approaches**

| Approach                  | Record         | Query            | Main disadvantage              |
| ------------------------- | -------------- | ---------------- | ------------------------------ |
| Brute force               | O(1)           | O(N × B)         | Repeated scanning              |
| HashMap + bucket counting | O(1) amortized | O(N + B)         | Scans timestamps outside range |
| TreeMap + range query     | O(log M)       | O(log M + K + B) | More expensive insertion       |

### **Which approach should we choose?**

For this problem, I would choose **HashMap + bucket counting**.

Why?

1. The maximum number of operations is only \\(10^4\\).
2. The query range is bounded by \\(10^4\\) seconds.
3. The bucket count is relatively small.
4. We don't need to maintain sorted timestamps.
5. Recording a tweet is O(1) amortized.
6. The implementation is simple and less error-prone.

The TreeMap approach becomes interesting when the dataset becomes significantly larger and queries usually cover small portions of the timeline.

# **5. Edge cases to consider**

| Scenario                          | Expected behavior  |
| --------------------------------- | ------------------ |
| No tweets for a name              | Return all zeros   |
| Tweet exactly at startTime        | Include it         |
| Tweet exactly at endTime          | Include it         |
| Multiple tweets at same timestamp | Count all of them  |
| Tweets arrive out of order        | Count correctly    |
| Only one timestamp in range       | Return one bucket  |
| Range shorter than frequency      | Return one bucket  |
| Range exactly equals frequency    | Return two buckets |
| Final bucket is incomplete        | Still include it   |
| Tweet outside requested range     | Ignore it          |

### **Important boundary example**

```
startTime = 0
endTime = 60
chunkSize = 60
```

The buckets are:

```
Bucket 0: [0, 59]
Bucket 1: [60, 60]
```

Result must contain two elements.

This is why we use:

```
int bucketCount = (endTime - startTime) / chunkSize + 1;
```

And not:

```
int bucketCount = (endTime - startTime) / chunkSize;
```

# **6. Interviewer follow-up questions**

### **Q1. Why don't we store tweets in a global list?**

Because each query asks for a particular `tweetName`.

Using:

```
Map<String, List<Integer>>
```

allows us to directly retrieve the relevant timestamps instead of scanning tweets belonging to unrelated names.

### **Q2. Why do we subtract startTime when calculating the bucket index?**

Because bucket boundaries are relative to the query's starting time.

Consider:

```
startTime = 100
chunkSize = 60
```

The buckets are:

```
[100, 159]
[160, 219]
[220, 279]
```

For timestamp 160:

```
(160 - 100) / 60 = 1
```

Without subtracting `startTime`:

```
160 / 60 = 2
```

That would assign the timestamp to the wrong bucket.

### **Q3. Can we use an array instead of a HashMap?**

Not directly for tweet names because names are strings and we need to maintain independent timelines.

We could use:

```
Map<String, int[]>
```

if the timestamp domain were small and bounded, but the constraints allow timestamps up to \\(10^9\\), making a full array impractical.

### **Q4. What if timestamps arrive in sorted order?**

We could use an ArrayList and binary search to find the requested range.

However, Java's ArrayList does not guarantee sorted insertion. If timestamps arrive sorted, appending is O(1) amortized.

### **Q5. What if we have millions of tweets and millions of queries?**

We should consider:

- Sorted timestamp storage.
- TreeMap-based range queries.
- Database indexes on `(tweetName, timestamp)`.
- Time-based aggregation.
- Precomputed counts for frequently requested intervals.

### **Q6. Can we use prefix sums?**

Yes.

If timestamps are stored in sorted order, we can build a prefix sum over their frequencies.

For each bucket:

\\[ count = upperBound(bucketEnd)-lowerBound(bucketStart) \\]

For compressed timestamp frequencies, prefix sums allow each bucket count to be calculated in O(log M) using binary search.

However, building or updating prefix sums dynamically is more complicated.

### **Q7. Why is bucket counting better than checking every bucket?**

Because each timestamp belongs to exactly one bucket.

Instead of asking:

```
Does this timestamp belong to bucket 0?
Does it belong to bucket 1?
Does it belong to bucket 2?
...
```

We directly calculate:

```java
int bucketIndex = (timestamp - startTime) / chunkSize;
```

This eliminates the additional bucket loop.

# **7. Final interview takeaway**

Remember this pattern:

**HashMap + Bucket Counting = Efficient time-window aggregation.**

Whenever a problem asks you to:

- Group events by some identifier.
- Retrieve events for a particular identifier.
- Divide a time range into fixed-size intervals.
- Count events in each interval.

Think about:

```
Map<String, List<Integer>>
```

And the key formula:

```
int bucketIndex = (timestamp - startTime) / chunkSize;
```

The optimal solution for the given constraints is:

\\[ \boxed{\text{Time: }O(N+B)\text{ per query}} \\]

\\[ \boxed{\text{Space: }O(T+B)} \\]

where N is the number of timestamps for the requested tweet name, B is the number of buckets, and T is the total number of recorded tweets.

**Senior interviewer tip:** The most important insight in this problem isn't HashMap itself. It's recognizing that integer division lets you map every timestamp directly to its corresponding time bucket in O(1).
