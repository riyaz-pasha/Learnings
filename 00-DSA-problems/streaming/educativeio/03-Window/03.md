# **362. Design Hit Counter**

**Difficulty:** Medium\
**Topics:** Hash Table, Design, Queue, Array, Binary Search

## **0. Simplifying the problem statement**

You need to design a `HitCounter` class that tracks the number of hits received over time.

Each hit occurs at a particular timestamp (in seconds).

Implement two methods:

1. `hit(timestamp)`: Record a hit at the given timestamp.
2. `getHits(timestamp)`: Return the total number of hits received during the **past 5 minutes (300 seconds)** from the given timestamp.

### **Important example**

```java
HitCounter counter = new HitCounter();

counter.hit(1);
counter.hit(2);
counter.hit(3);

counter.getHits(4);    // 3

counter.hit(300);

counter.getHits(300);  // 4

counter.getHits(301);  // 4
```

Why?

At timestamp `301`, the relevant interval is:

```
[2, 301]
```

Hits at timestamps `2`, `3`, and `300` are counted, but the hit at timestamp `1` is excluded.

**Key observation:** The time window is always 300 seconds, and we only care about hits inside that moving window.

## **1. Clarifying questions to ask the interviewer**

Before choosing a data structure, clarify:

1. **Are timestamps guaranteed to arrive in non-decreasing order?**
   - Why: A queue and circular-array implementation rely on chronological processing.
   - If hits can arrive out of order, a `HashMap` or `TreeMap` approach is safer.
2. **Can multiple hits occur at the same timestamp?**
   - Why: We must count every hit, not just unique timestamps.
   - Example: Three calls to `hit(10)` should contribute 3 hits.
3. **Is the time window exactly 300 seconds?**
   - Why: We can exploit the fixed window to achieve constant-time operations and fixed memory.
4. **Is the query timestamp also non-decreasing?**
   - Why: This determines whether we can permanently discard expired hits.

For the standard LeetCode problem, timestamps are non-decreasing, and multiple hits can occur at the same timestamp.

## **2. Core intuition: Three approaches**

We can solve this problem in three ways.

| Approach                     | `hit()`        | `getHits()`    | Space  |
| ---------------------------- | -------------- | -------------- | ------ |
| Brute force: store every hit | O(1)           | O(H)           | O(H)   |
| HashMap + fixed-window scan  | O(1) average   | O(300)         | O(U)   |
| Queue + lazy removal         | O(1) amortized | O(1) amortized | O(H)   |
| Circular array               | O(1)           | O(300)         | O(300) |

Here:

- `H` = number of hits stored.
- `U` = number of distinct timestamps stored.

Since 300 is a fixed constant, O(300) is effectively O(1).

### **The most important mental model**

Imagine a window that moves forward with time.

```
Time:  1   2   3   4   5 ... 300 301 302
       |-------------------|
           300 seconds

At timestamp 301:

           |-------------------|
           2                 301
```

Every hit outside the current window must be excluded.

The interesting question is: **How do we efficiently remember and remove expired hits?**

Let's explore each approach.

## **3. Solution 1: Brute force — Store every hit**

**Idea:** Store every timestamp in a list. Whenever `getHits(t)` is called, iterate through the list and count timestamps belonging to the current window.

This is the simplest solution and establishes the correct logic.

```java

import java.util.*;

class HitCounterBruteForce {

    // Store every individual hit.
    // Duplicate timestamps are intentionally allowed because
    // each hit must contribute independently to the answer.
    private final List<Integer> hits = new ArrayList<>();

    public void hit(int timestamp) {

        // Simply record the incoming hit.
        // No expiration or deletion is performed.
        hits.add(timestamp);
    }

    public int getHits(int timestamp) {

        // The current 300-second window is:
        // [timestamp - 299, timestamp]
        //
        // Both boundaries are inclusive.
        int lowerBound = timestamp - 299;

        int count = 0;

        // Examine every recorded hit.
        for (int hitTime : hits) {

            // Count only hits inside the current window.
            if (hitTime >= lowerBound && hitTime <= timestamp) {
                count++;
            }
        }

        return count;
    }

    /*
     * COMPLEXITY:
     *
     * hit():
     *   Time: O(1) amortized.
     *   ArrayList insertion is O(1) amortized because occasional
     *   resizing requires copying existing elements.
     *
     * getHits():
     *   Time: O(H), where H is the total number of recorded hits.
     *   We scan the entire list, including expired hits.
     *
     * Space: O(H).
     *   Every hit is retained forever.
     *
     * DRAWBACK:
     *   Expired hits waste memory, and every query scans all hits.
     */
}

```

**Why is this not optimal?**

Suppose we have received 10 million hits, but only the last 300 seconds matter.

We are still scanning all 10 million hits!

We need a way to discard expired information.

## **4. Solution 2: HashMap + Fixed Window**

**Idea:** Instead of storing every hit individually, maintain:

```
timestamp -> number of hits at that timestamp
```

For example:

```
timestamp    hit count
----------------------
1            2
2            1
3            4
300          1
```

When `getHits(t)` is called, inspect only the 300 possible timestamps in the current window.

```java

import java.util.*;

class HitCounterHashMap {

    // Maps each timestamp to the number of hits received at that second.
    private final Map<Integer, Integer> frequency = new HashMap<>();

    public void hit(int timestamp) {

        // If this timestamp already exists, increment its count.
        // Otherwise, initialize its count to 1.
        //
        // merge() handles both cases.
        frequency.merge(timestamp, 1, Integer::sum);
    }

    public int getHits(int timestamp) {

        // The 300-second interval includes:
        // timestamp, timestamp - 1, ..., timestamp - 299.
        int lowerBound = timestamp - 299;

        int totalHits = 0;

        // Only 300 possible timestamp values can contribute.
        for (int time = lowerBound; time <= timestamp; time++) {

            // If no hit occurred at this timestamp,
            // getOrDefault() contributes zero.
            totalHits += frequency.getOrDefault(time, 0);
        }

        return totalHits;
    }

    /*
     * COMPLEXITY:
     *
     * hit():
     *   Time: O(1) average.
     *   HashMap insertion/update is O(1) average.
     *
     * getHits():
     *   Time: O(300) = O(1).
     *   We inspect exactly 300 possible timestamps.
     *
     * Space: O(U).
     *   U is the number of distinct timestamps ever recorded.
     *
     * ADVANTAGES:
     *   - Multiple hits at the same timestamp are handled naturally.
     *   - Queries take constant time because the window is fixed.
     *   - Unlike the queue and circular-array approaches, this
     *     implementation can handle out-of-order hit timestamps.
     *
     * DRAWBACK:
     *   - Old timestamps are never removed.
     *   - Memory grows as more distinct timestamps arrive.
     *
     * OPTIMIZATION:
     *   If query timestamps are guaranteed to be non-decreasing,
     *   we can remove expired entries to prevent unbounded growth.
     */
}

```

This is already a significant improvement.

However, we can avoid even scanning the entire 300-second interval by maintaining a queue of hits.

## **5. Solution 3: Queue + Lazy Removal (Optimal General Approach)**

**This is an excellent interview solution.**

### **Mental model**

Since timestamps arrive in non-decreasing order, hits also enter the queue chronologically.

Therefore:

- The oldest hit is always at the front.
- If the oldest hit has expired, all earlier hits have expired too.
- We only need to remove expired hits from the front.

We use a queue to maintain the active hits.

### **Example walkthrough**

Suppose the queue contains:

```
[1, 2, 2, 3, 5, 300]
```

Now call:

```
getHits(301);
```

The valid window is:

```
[2, 301]
```

Remove expired timestamps:

```
Before:

[1, 2, 2, 3, 5, 300]

Remove 1:

[2, 2, 3, 5, 300]

After cleanup:

[2, 2, 3, 5, 300]
```

The queue size is 5, so return 5.

### **Java 24 implementation**

```java

import java.util.*;

class HitCounterQueue {

    // Queue stores every individual hit in chronological order.
    //
    // ArrayDeque is preferred over LinkedList for queue operations
    // because it provides efficient operations at both ends.
    private final Deque<Integer> hits = new ArrayDeque<>();

    public void hit(int timestamp) {

        // Add the new hit at the rear.
        //
        // Since timestamps arrive in non-decreasing order,
        // the queue remains chronologically sorted.
        hits.offerLast(timestamp);
    }

    public int getHits(int timestamp) {

        // Current valid window:
        // [timestamp - 299, timestamp]
        //
        // A hit expires when:
        // timestamp - hitTime >= 300.
        //
        // Equivalently:
        // hitTime <= timestamp - 300.
        //
        // Therefore, remove all expired hits from the front.

        while (!hits.isEmpty()
                && timestamp - hits.peekFirst() >= 300) {

            // The oldest hit has expired.
            // Remove it permanently because timestamps are ordered.
            hits.pollFirst();
        }

        // Every remaining hit belongs to the current window.
        return hits.size();
    }

    /*
     * COMPLEXITY:
     *
     * hit():
     *   Time: O(1).
     *   Adding an element to the rear of ArrayDeque is O(1)
     *   amortized.
     *
     * getHits():
     *   Time: O(1) amortized.
     *
     *   Important distinction:
     *   A single getHits() call might remove many expired hits,
     *   making that individual call O(H).
     *
     *   However, every hit is inserted exactly once and removed
     *   at most once.
     *
     *   Across N operations, the total number of removals cannot
     *   exceed the total number of insertions.
     *
     *   Therefore, the amortized cost per operation is O(1).
     *
     * Space: O(H).
     *
     *   In the worst case, many hits can occur within 300 seconds.
     *   We store every individual hit that has not yet expired.
     *
     * ADVANTAGES:
     *   - No scanning of the 300-second interval.
     *   - Expired hits are removed efficiently.
     *   - Supports multiple hits at the same timestamp.
     *
     * IMPORTANT ASSUMPTION:
     *   Hit timestamps and query timestamps must follow
     *   non-decreasing chronological order.
     */
}

```

### **Why is the queue solution amortized O(1)?**

Consider 1 million calls to `hit()`.

Every hit:

- Is inserted exactly once.
- Can be removed at most once.
- Is never reinserted.

Even if one query removes 100,000 expired hits, those removals will never happen again.

Therefore, total queue work over N operations is O(N).

This is the key amortized-analysis argument interviewers expect.

## **6. Solution 4: Circular Array (Best Space Optimization)**

**This is the most interesting optimization for this problem.**

The time window is fixed at exactly 300 seconds.

Instead of storing timestamps in a queue, we can use a circular array of size 300.

### **Mental model: Clock with 300 slots**

Imagine a clock with 300 slots.

Each timestamp maps to a slot using:

```
int index = timestamp % 300;
```

For example:

| Timestamp | Index |
| --------- | ----- |
| 1         | 1     |
| 2         | 2     |
| 299       | 299   |
| 300       | 0     |
| 301       | 1     |
| 302       | 2     |
| 600       | 0     |

Notice that timestamp `1` and timestamp `301` share the same slot.

This is intentional!

Why is this safe?

Because they are exactly 300 seconds apart.

At timestamp `301`, timestamp `1` is already expired.

Therefore, we can overwrite its slot with timestamp `301`.

### **What should each slot store?**

We need two arrays:

```
times[300]  -> actual timestamp stored in each slot
hits[300]   -> number of hits at that timestamp
```

Why do we need the `times` array?

Because multiple timestamps map to the same circular-array index.

For example:

```
timestamp 1   -> index 1
timestamp 301 -> index 1
```

We must distinguish between them.

The actual timestamp acts as a validation mechanism.

### **Java 24 implementation**

```java

import java.util.Arrays;

class HitCounterCircularArray {

    private static final int WINDOW = 300;

    // Each index represents one second in the circular window.
    private final int[] times = new int[WINDOW];

    // Number of hits recorded at the corresponding timestamp.
    private final int[] hits = new int[WINDOW];

    public HitCounterCircularArray() {

        // Initialize every slot with -1.
        //
        // This distinguishes an unused slot from a valid timestamp.
        Arrays.fill(times, -1);
    }

    public void hit(int timestamp) {

        // Map the timestamp to one of the 300 circular slots.
        int index = timestamp % WINDOW;

        // Check whether this slot belongs to the current timestamp.
        //
        // If not, it contains either:
        // 1. An unused slot, or
        // 2. An older timestamp that has expired.
        //
        // Reset the slot before recording the new timestamp.
        if (times[index] != timestamp) {

            // Associate this slot with the new timestamp.
            times[index] = timestamp;

            // Reset the previous timestamp's hit count.
            hits[index] = 0;
        }

        // Record this hit.
        //
        // If multiple hits occur at the same timestamp,
        // the count is incremented instead of overwritten.
        hits[index]++;
    }

    public int getHits(int timestamp) {

        // Current valid interval:
        // [timestamp - 299, timestamp]
        int lowerBound = timestamp - WINDOW + 1;

        int totalHits = 0;

        // Inspect all 300 circular slots.
        for (int i = 0; i < WINDOW; i++) {

            // A slot contributes only when its actual timestamp
            // belongs to the current 300-second window.
            //
            // Checking the actual timestamp is essential:
            // index equality alone cannot distinguish timestamps
            // separated by multiples of 300.
            if (times[i] >= lowerBound
                    && times[i] <= timestamp) {

                totalHits += hits[i];
            }
        }

        return totalHits;
    }

    /*
     * COMPLEXITY:
     *
     * hit():
     *   Time: O(1).
     *   One modulo operation, one slot validation, and one increment.
     *
     * getHits():
     *   Time: O(300) = O(1).
     *   We inspect exactly 300 array positions.
     *
     * Space: O(300) = O(1).
     *   Two arrays of fixed size 300.
     *
     * ADVANTAGES:
     *   - Constant-time hit recording.
     *   - Constant-time hit counting.
     *   - Fixed memory regardless of the total number of hits.
     *   - No queue or dynamic collection is required.
     *
     * IMPORTANT:
     *   This implementation assumes timestamps arrive in
     *   non-decreasing order and queries follow chronological order.
     *
     * WHY DOES CIRCULAR OVERWRITING WORK?
     *
     *   Two timestamps map to the same index only when their
     *   difference is a multiple of 300.
     *
     *   For a monotonically advancing stream, an older timestamp
     *   occupying that slot has already expired when a newer
     *   timestamp 300 seconds later replaces it.
     *
     *   The times[] array prevents stale values from being
     *   mistakenly counted during getHits().
     */
}

```

### **Visualizing the circular array**

Suppose we receive:

```
hit(1)
hit(2)
hit(3)
hit(301)
```

The array changes conceptually as follows:

**After&#x20;**`hit(1)`**:**

```
index = 1 % 300 = 1

times[1] = 1
hits[1]  = 1
```

**After&#x20;**`hit(301)`**:**

```
index = 301 % 300 = 1

times[1] != 301

Reset the slot:

times[1] = 301
hits[1]  = 1
```

The old hit at timestamp `1` is replaced.

Now:

```
getHits(301);
```

The valid interval is `[2, 301]`.

The hit at timestamp `1` is no longer counted.

### **Queue vs Circular Array**

| Property            | Queue          | Circular Array        |
| ------------------- | -------------- | --------------------- |
| `hit()`             | O(1)           | O(1)                  |
| `getHits()`         | O(1) amortized | O(300) = O(1)         |
| Space               | O(H)           | O(300) = O(1)         |
| Dynamic memory      | Yes            | No                    |
| Implementation      | Simple         | Slightly more complex |
| Expired-hit removal | Explicit       | Overwriting           |

**My interview recommendation:**

- Start with the HashMap approach to establish the fixed-window idea.
- Move to the Queue approach to demonstrate lazy deletion and amortized analysis.
- Present the Circular Array as the optimal fixed-memory solution.

The circular array is particularly attractive because the problem gives us a fixed window size of 300 seconds.

## **7. Edge cases to watch out for**

| Edge case                       | Example                    | Expected behavior                 |
| ------------------------------- | -------------------------- | --------------------------------- |
| No hits                         | `getHits(10)`              | `0`                               |
| Single hit                      | `hit(10)`, `getHits(10)`   | `1`                               |
| Multiple hits at same timestamp | Three calls to `hit(10)`   | `3`                               |
| Hit at lower boundary           | `hit(1)`, `getHits(300)`   | `1`                               |
| Hit just outside window         | `hit(1)`, `getHits(301)`   | `0`                               |
| Multiple timestamps             | Hits at 1, 2, 3            | Count all valid hits              |
| Circular collision              | `hit(1)`, `hit(301)`       | Old timestamp must not be counted |
| Large timestamp gaps            | `hit(1)`, `getHits(10000)` | `0`                               |

### **Most important off-by-one mistake**

The window is:

```
[timestamp - 299, timestamp]
```

NOT:

```
[timestamp - 300, timestamp]
```

Why?

Because the window contains exactly 300 integer-second timestamps.

For example, at timestamp `300`:

```
Valid timestamps:

1, 2, 3, ..., 299, 300

Total = 300 seconds
```

Therefore, timestamp `1` is still valid at `300`, but expires at `301`.

## **8. Interviewer follow-up questions**

**Q1. Why is the queue approach O(1) amortized rather than O(1) worst-case for&#x20;**`getHits()`**?**

Because a single query might remove many expired hits. However, each hit is inserted once and removed at most once. Across all operations, total removal work is O(N).

**Q2. Why does the circular array require two arrays?**

The index `timestamp % 300` can represent multiple timestamps. The `times` array identifies which timestamp currently owns a slot, while `hits` stores its frequency.

**Q3. Can we use a single array?**

Yes, if we store a packed representation of timestamp and frequency, but this adds encoding complexity. Two arrays are clearer and easier to maintain.

**Q4. What if timestamps arrive out of order?**

The queue and circular-array solutions are no longer generally safe.

A HashMap can store timestamp frequencies and scan the 300 valid timestamps during each query. For arbitrary historical queries, this is a straightforward solution.

**Q5. What if the window changes from 300 seconds to 1 hour?**

Change the window size to 3600 and use a circular array of size 3600. The same principle applies.

**Q6. What if we need to support multiple window sizes?**

A single circular array sized for one window may not be sufficient. We could maintain a timestamp-frequency map and calculate counts for each requested window, or use a prefix-sum-capable data structure depending on the query requirements.

**Q7. Can we optimize the circular-array&#x20;**`getHits()`**&#x20;beyond scanning 300 slots?**

For a fixed 300-second window, scanning 300 slots is already O(1) asymptotically. We could additionally maintain a running total and subtract expired bucket counts as time advances, but that requires careful handling of time jumps and slot reuse.

## **9. Which solution should you implement in an interview?**

My recommendation:

| Situation                      | Best choice    |
| ------------------------------ | -------------- |
| First explain the problem      | Brute force    |
| Need simple optimization       | HashMap        |
| Need efficient dynamic storage | Queue          |
| Need minimum fixed memory      | Circular Array |

### **The three patterns worth remembering**

This problem teaches three important data-structure patterns:

1. **Sliding Window + Queue:** Remove expired elements from the front.
2. **Frequency Map:** Aggregate multiple events occurring at the same timestamp.
3. **Circular Array:** Reuse fixed-size storage when the time window is bounded.

**Final takeaway:** The most important insight is that we don't need to remember the entire history. We only need information belonging to the most recent 300 seconds. The queue achieves efficient lazy deletion, while the circular array achieves constant auxiliary space.

For interview preparation, I would make sure you can implement both the Queue and Circular Array solutions without looking at the code.
