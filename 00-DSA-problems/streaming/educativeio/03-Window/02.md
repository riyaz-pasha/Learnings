# **LeetCode 346. Moving Average from Data Stream**

**Difficulty:** Easy\
**Topics:** Design, Queue, Array, Data Stream

## **0. Understand the problem**

We need to design a data structure that calculates the **average of the most recent&#x20;**`k`**&#x20;numbers** in a continuous stream of integers.

Implement the following class:

```
class MovingAverage {
    public MovingAverage(int size);

    public double next(int val);
}
```

- `MovingAverage(size)`: Initializes the data structure with a fixed window size.
- `next(val)`: Adds a new integer to the stream and returns the average of the most recent `size` integers.

**Important:** If fewer than `size` elements have been received, calculate the average using all elements received so far.

### **Example**

```
MovingAverage movingAverage = new MovingAverage(3);

movingAverage.next(1);  // 1.0
movingAverage.next(10); // 5.5
movingAverage.next(3);  // 4.66667
movingAverage.next(5);  // 6.0
```

Let's understand the window movement:

| Incoming value | Current window | Sum | Average |
| -------------- | -------------- | --- | ------- |
| 1              | [1]            | 1   | 1.0     |
| 10             | [1, 10]        | 11  | 5.5     |
| 3              | [1, 10, 3]     | 14  | 4.6667  |
| 5              | [10, 3, 5]     | 18  | 6.0     |

Notice what happens when `5` arrives:

- The window is already full.
- We remove the oldest element (`1`).
- We insert the new element (`5`).
- We calculate the average of `[10, 3, 5]`.

This is a classic **sliding window over a data stream** problem.

## **1. Clarifying questions to ask the interviewer**

1. **Is the window size fixed?**
   - Why: Determines whether we can use a fixed-size circular buffer.
   - LeetCode assumption: Yes.
2. **Should we calculate the average using fewer than&#x20;**`k`**&#x20;elements initially?**
   - Why: Determines the denominator before the window becomes full.
   - LeetCode assumption: Yes.
3. **Can the input contain negative numbers?**
   - Why: We should not assume all values are positive when maintaining the running sum.
   - LeetCode assumption: Values are non-negative.
4. **Can the stream contain a very large number of elements?**
   - Why: Determines whether storing the entire stream is practical.
   - LeetCode assumption: We only need the most recent `k` values.
5. **Can the running sum overflow an integer?**
   - Why: Determines whether to use `int` or `long`.
   - Interview recommendation: Use `long` for a robust implementation.

## **2. Core idea and intuition**

There are three approaches worth understanding.

### **Approach 1: Brute force — Store all elements and recalculate**

**Mental model:** Every time a new number arrives, look backward at the latest `k` numbers and calculate their sum from scratch.

For example:

```
Window size = 3
Stream      = 1, 10, 3, 5

next(1):
    [1]       -> 1 / 1 = 1.0

next(10):
    [1, 10]   -> 11 / 2 = 5.5

next(3):
    [1,10,3]  -> 14 / 3 = 4.6667

next(5):
    [10,3,5]  -> 18 / 3 = 6.0
```

Java implementation:

```java
import java.util.ArrayList;
import java.util.List;

class MovingAverageBruteForce {

    private final int size;
    private final List<Integer> stream;

    public MovingAverageBruteForce(int size) {
        this.size = size;
        this.stream = new ArrayList<>();
    }

    public double next(int val) {
        stream.add(val);

        // Calculate the starting index of the current window.
        int start = Math.max(0, stream.size() - size);

        long sum = 0;

        // Recalculate the sum of the entire current window.
        // This repeats work performed by previous calls.
        for (int i = start; i < stream.size(); i++) {
            sum += stream.get(i);
        }

        int windowSize = stream.size() - start;

        // Time Complexity: O(k) per next() call.
        // We iterate over at most k elements.
        //
        // Space Complexity: O(n).
        // We retain every element received, even though only
        // the latest k elements are needed.
        return (double) sum / windowSize;
    }
}
```

**Complexity:**

- Constructor: O(1)
- `next()`: O(k)
- Space: O(n), where n is the total number of incoming elements.

**Problem:** We repeatedly calculate sums of elements that were already processed.

Can we reuse the previous sum?

Absolutely!

### **Approach 2: Optimal using Queue + Running Sum**

**Mental model: Don't recalculate what you already know.**

Suppose our current window is:

```
[1, 10, 3]

sum = 14
```

A new number `5` arrives.

The new window becomes:

```
[10, 3, 5]
```

Instead of calculating:

```
10 + 3 + 5 = 18
```

from scratch, we already know the previous sum is `14`.

Simply:

```
New Sum = Previous Sum - Outgoing Element + Incoming Element

        = 14 - 1 + 5

        = 18
```

This is the key optimization!

We maintain two things:

1. A Queue containing the most recent `k` elements.
2. A running sum containing the sum of those elements.

**Algorithm:**

1. Check whether the queue has reached its maximum capacity.
2. If full:
   - Remove the oldest element.
   - Subtract it from the running sum.
3. Insert the new element.
4. Add it to the running sum.
5. Return `sum / queue.size()`.

Java 24 implementation:

```java
import java.util.ArrayDeque;
import java.util.Queue;

class MovingAverage {

    private final int size;
    private final Queue<Integer> window;
    private long sum;

    public MovingAverage(int size) {
        this.size = size;
        this.window = new ArrayDeque<>();
        this.sum = 0;
    }

    public double next(int val) {

        // STEP 1: If the window is full, remove the oldest element.
        if (window.size() == size) {

            // FIFO behavior ensures that the oldest element
            // leaves the window first.
            int removed = window.poll();

            // Maintain the running sum by removing its contribution.
            sum -= removed;
        }

        // STEP 2: Insert the incoming element.
        window.offer(val);

        // Update the running sum in O(1).
        sum += val;

        // STEP 3: Calculate the average.
        // window.size() automatically handles the initial phase
        // when fewer than 'size' elements have arrived.
        //
        // Casting to double is important:
        // Otherwise integer division would truncate decimal values.
        //
        // Time Complexity: O(1) per next() call.
        // Queue insertion, removal and size operations are O(1).
        //
        // Space Complexity: O(k).
        // The queue never contains more than k elements.
        return (double) sum / window.size();
    }
}
```

**Complexity:**

| Operation   | Time               | Space          |
| ----------- | ------------------ | -------------- |
| Constructor | O(1)               | O(k)           |
| `next()`    | O(1)               | O(1) auxiliary |
| Overall     | O(1) per insertion | O(k)           |

This is an optimal solution.

### **Approach 3: Optimal using Circular Array (Best interview implementation)**

Now let's improve the implementation further.

Do we really need a Queue?

Not necessarily!

A queue provides FIFO behavior, but we can achieve the same behavior using a fixed-size array and modular arithmetic.

This is called a **Circular Buffer** or **Ring Buffer**.

#### **Mental model**

Imagine an array of size 3:

```
Index:  0    1    2
       +----+----+----+
       |  1 | 10 |  3 |
       +----+----+----+
```

When `5` arrives, we overwrite the oldest element.

```
Before:

       +----+----+----+
       |  1 | 10 |  3 |
       +----+----+----+
          ^
       Oldest


After:

       +----+----+----+
       |  5 | 10 |  3 |
       +----+----+----+
```

We use an index to remember where the next incoming element should be inserted.

After reaching the last index, we wrap around to index zero.

```
nextIndex = (nextIndex + 1) % size;
```

For a window of size 3:

```
0 -> 1 -> 2 -> 0 -> 1 -> 2 -> ...
```

#### **Java 24 implementation**

```java
class MovingAverage {

    private final int[] window;

    // Points to the position where the next incoming value
    // should be inserted.
    private int nextIndex;

    // Number of elements currently stored in the window.
    // Never exceeds window.length.
    private int count;

    // Sum of all elements currently present in the window.
    private long sum;

    public MovingAverage(int size) {

        // Fixed-size array avoids dynamic allocation and
        // queue object overhead.
        this.window = new int[size];

        this.nextIndex = 0;
        this.count = 0;
        this.sum = 0;
    }

    public double next(int val) {

        // STEP 1: Remove the contribution of the element
        // that is about to be overwritten.
        //
        // Before the buffer becomes full, array positions
        // contain no valid elements, so we must not subtract
        // their default zero values as actual observations.
        if (count == window.length) {
            sum -= window[nextIndex];
        }

        // STEP 2: Insert the new value.
        window[nextIndex] = val;

        // Update the running sum.
        sum += val;

        // STEP 3: Update the number of valid elements.
        //
        // Once full, count remains equal to window.length.
        count = Math.min(count + 1, window.length);

        // STEP 4: Move the insertion pointer forward.
        //
        // Modulo ensures that we wrap around to index 0
        // after reaching the last array position.
        nextIndex = (nextIndex + 1) % window.length;

        // STEP 5: Calculate the moving average.
        //
        // During initialization, divide by the number of
        // elements actually received.
        // Once full, divide by the fixed window size.
        //
        // Time Complexity: O(1) per next() call.
        // Only a constant number of array operations occur.
        //
        // Space Complexity: O(k).
        // A fixed array of exactly k elements is maintained.
        return (double) sum / count;
    }
}
```

**Complexity:**

- Constructor: O(k) time to allocate the array.
- `next()`: O(1) time.
- Space: O(k).

This is my preferred implementation for an interview because it provides predictable memory usage and avoids unnecessary queue overhead.

## **3. Dry run of the optimal Circular Array approach**

Input:

```
size = 3
Stream = [1, 10, 3, 5, 7]
```

Initial state:

```
window = [0, 0, 0]
sum = 0
count = 0
nextIndex = 0
```

| Incoming | Array      | Sum | Count | Next index | Average |
| -------- | ---------- | --- | ----- | ---------- | ------- |
| 1        | [1, 0, 0]  | 1   | 1     | 1          | 1.0     |
| 10       | [1, 10, 0] | 11  | 2     | 2          | 5.5     |
| 3        | [1, 10, 3] | 14  | 3     | 0          | 4.6667  |
| 5        | [5, 10, 3] | 18  | 3     | 1          | 6.0     |
| 7        | [5, 7, 3]  | 15  | 3     | 2          | 5.0     |

Notice:

- When `5` arrives, index `0` is overwritten.
- When `7` arrives, index `1` is overwritten.
- The running sum always represents the current window.

The physical order of the circular array is not necessarily the chronological order. That's perfectly fine because we only need its sum.

## **4. Edge cases to watch out for**

| Edge case        | Input                          | Expected behavior                |
| ---------------- | ------------------------------ | -------------------------------- |
| Window size = 1  | `size=1`, values `[5,10]`      | `5.0`, `10.0`                    |
| Only one element | `size=3`, values `[5]`         | `5.0`                            |
| Window not full  | `size=5`, values `[1,2]`       | `1.0`, `1.5`                     |
| Negative values  | `size=2`, values `[-1,-5]`     | `-1.0`, `-3.0`                   |
| Mixed values     | `size=3`, values `[5,-5,10,0]` | `5.0`, `0.0`, `3.3333`, `1.6667` |
| Repeated values  | `size=3`, values `[7,7,7,7]`   | Always `7.0`                     |

**Important implementation pitfalls:**

1. Don't divide by the configured window size before the window is full.
2. Don't forget to subtract the outgoing element from the running sum.
3. Don't use integer division.
4. Don't shift an entire array when removing an element.
5. Use `long` for the running sum in production-quality implementations.
6. In circular arrays, subtract the old value only when the buffer is full.

## **5. Interviewer follow-up questions**

### **Q1. Why do we need a running sum?**

Without a running sum, every `next()` call requires traversing the current window.

That costs O(k).

With a running sum:

```
newSum = oldSum - outgoing + incoming
```

We perform constant-time updates, giving O(1) per call.

### **Q2. Why is a Queue a natural fit?**

A sliding window follows FIFO behavior:

- Oldest element leaves.
- Newest element enters.

A queue naturally supports these operations.

### **Q3. Why use a circular array instead of a regular array?**

A regular array would require shifting elements whenever the oldest element is removed.

That costs O(k).

A circular array overwrites the oldest position directly using modular arithmetic, giving O(1).

### **Q4. What happens if the window size is 1?**

Every incoming element replaces the previous element.

```
size = 1

next(5)  -> 5.0
next(10) -> 10.0
next(15) -> 15.0
```

The circular array handles this automatically.

### **Q5. Can we solve this without storing the elements?**

Not in general.

To remove the oldest element from the running sum, we need to know its value.

We therefore need to retain enough information to identify the outgoing element.

A circular buffer stores exactly the required `k` elements.

### **Q6. What if the window size changes dynamically?**

The current circular buffer is designed for a fixed window size.

If the window size changes, we need to resize the buffer and retain the appropriate most recent elements.

This can require O(k) time.

### **Q7. What if we want the moving average of the last&#x20;**`k`**&#x20;elements, but also need the moving maximum?**

Maintain two data structures:

- Running sum + circular buffer for the average.
- Monotonic deque for the maximum.

The maximum can also be maintained in amortized O(1) time per insertion.

### **Q8. What if we need the moving median instead?**

A running sum is insufficient for median calculations.

We can use two heaps:

- Max heap for the smaller half.
- Min heap for the larger half.

Maintain their sizes and remove expired elements using lazy deletion or indexed heaps.

Typical complexity: O(log k) per insertion.

## **6. Final comparison: Which approach should you choose?**

| Approach                     | `next()` time | Space | Recommendation                |
| ---------------------------- | ------------- | ----- | ----------------------------- |
| Store all + recalculate      | O(k)          | O(n)  | Understand brute force        |
| Queue + running sum          | O(1)          | O(k)  | Cleanest to explain           |
| Circular array + running sum | O(1)          | O(k)  | Best optimized implementation |

**My recommendation for interviews:**

Start with brute force to demonstrate understanding.

Then introduce the running sum optimization:

```
New Sum = Previous Sum - Outgoing Value + Incoming Value
```

Finally, replace the queue with a circular array if the interviewer wants better memory and implementation efficiency.

The most important takeaway is:

**Whenever a fixed-size sliding window moves forward by one position, investigate whether you can remove the outgoing element's contribution and add the incoming element's contribution instead of recalculating everything.**

This pattern appears in many streaming and sliding-window problems.
