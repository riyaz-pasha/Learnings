# **933. Number of Recent Calls**

**Difficulty:** Easy\
**Topics:** Queue, Sliding Window, Data Stream

## **0. Simplify the problem statement**

We need to design a class called `RecentCounter` that keeps track of incoming requests.

Every time `ping(t)` is called:

1. A new request arrives at timestamp `t`.
2. We need to count all requests that happened in the last **3000 milliseconds**, including the current request.
3. Return the count.

The time window is:

\\[ [t-3000,\ t] \\]

Both boundaries are inclusive.

**Important guarantee:** Timestamps are strictly increasing. This means requests always arrive in chronological order.

### **Example walkthrough**

Input:

```
RecentCounter()
ping(1)
ping(100)
ping(3001)
ping(3002)
```

| Call       | Current timestamp | Valid window | Requests inside window | Result |
| ---------- | ----------------- | ------------ | ---------------------- | ------ |
| ping(1)    | 1                 | [-2999, 1]   | [1]                    | 1      |
| ping(100)  | 100               | [-2900, 100] | [1, 100]               | 2      |
| ping(3001) | 3001              | [1, 3001]    | [1, 100, 3001]         | 3      |
| ping(3002) | 3002              | [2, 3002]    | [100, 3001, 3002]      | 3      |

Notice something interesting:

When `ping(3002)` happens, timestamp `1` becomes invalid because:

\\[ 1 < 3002 - 3000 = 2 \\]

Therefore, we remove it.

## **1. Clarifying questions to ask the interviewer**

Before implementing, clarify:

1. **Are timestamps guaranteed to arrive in increasing order?**
   - Why: If yes, we can efficiently remove expired requests from the front of a queue. Otherwise, we need a different approach.
2. **Is the time window inclusive?**
   - Why: We need to know whether a request exactly 3000 milliseconds old should count. Here, it is inclusive.
3. **Is the window always fixed at 3000 milliseconds?**
   - Why: A configurable window would slightly change the class design.
4. **Can multiple requests have the same timestamp?**
   - Why: This affects assumptions about timestamp ordering. The problem guarantees strictly increasing timestamps.

For this problem, all these details are already specified.

## **2. Core intuition: Sliding Window + Queue**

The key observation:

**We only care about requests within the most recent 3000 milliseconds.**

Since timestamps are strictly increasing:

- New requests always arrive at the back.
- Expired requests always exist at the front.
- Once a request expires, it will never become valid again.

This makes a **Queue (FIFO)** the natural data structure.

### **Mental model**

Imagine a queue containing timestamps:

```
Front                              Rear
  |                                  |
  v                                  v
[100] [3001] [3002] [3500] [4000]
```

When a new request arrives:

1. Add the new timestamp to the queue.
2. Calculate the earliest valid timestamp: `t - 3000`.
3. Remove timestamps smaller than that boundary.
4. Return the queue size.

## **3. Edge cases**

| Edge case                    | Expected behavior                  |
| ---------------------------- | ---------------------------------- |
| First request                | Return 1                           |
| Only one request             | Return 1                           |
| Request exactly 3000 ms old  | Include it                         |
| Request 3001 ms old          | Exclude it                         |
| Large timestamp gap          | Remove all expired requests        |
| Many requests within 3000 ms | Count all of them                  |
| Consecutive requests         | Maintain their timestamps in order |

**Most important edge case:**

Suppose:

```
ping(1)
ping(3001)
```

At `t = 3001`:

\\[ t-3000=1 \\]

Timestamp `1` must remain because the interval is inclusive.

Therefore, our removal condition must be:

```
queue.peek() < t - 3000
```

Not:

```
queue.peek() <= t - 3000
```

# **4. All possible solutions**

## **Solution 1: Brute Force — Store Every Timestamp**

### **Idea**

Store every request timestamp in a list.

For each `ping(t)`:

1. Add `t` to the list.
2. Iterate through all previously stored timestamps.
3. Count timestamps satisfying:

\\[ timestamp \geq t-3000 \\]

This works, but repeatedly scans old requests that might already be expired.

```java
import java.util.ArrayList;
import java.util.List;

class RecentCounter {

    private final List<Integer> requests = new ArrayList<>();

    public RecentCounter() {
        // No initialization required.
        // We store every request timestamp.
    }

    public int ping(int t) {

        // Step 1: Record the incoming request.
        requests.add(t);

        // Step 2: Calculate the earliest valid timestamp.
        int boundary = t - 3000;

        // Step 3: Count all timestamps inside the inclusive window.
        int count = 0;

        for (int timestamp : requests) {

            // The window is [t - 3000, t].
            // Since timestamps arrive in increasing order,
            // no stored timestamp can be greater than t.
            if (timestamp >= boundary) {
                count++;
            }
        }

        return count;
    }
}

/*
TIME COMPLEXITY:

Constructor:
O(1)

ping(t):
O(n), where n is the total number of requests received so far.

Why?
We iterate over the entire list for every ping(),
including requests that are already outside the valid window.

For N total requests:
O(N^2) overall in the worst case.

SPACE COMPLEXITY:
O(N)

Why?
We retain every timestamp, even if it is no longer relevant.
*/
```

**Problem:** We repeatedly examine timestamps that have already expired.

We can do much better.

## **Solution 2: Optimal — Queue + Sliding Window**

### **Idea**

Instead of retaining every timestamp forever, remove timestamps as soon as they expire.

Use:

```
Queue<Integer> queue = new ArrayDeque<>();
```

For every `ping(t)`:

```
1. Add t.
2. Remove timestamps < t - 3000.
3. Return queue.size().
```

### **Java 24 implementation**

```java
import java.util.ArrayDeque;
import java.util.Queue;

class RecentCounter {

    private final Queue<Integer> queue;

    public RecentCounter() {

        // ArrayDeque provides efficient FIFO queue operations.
        //
        // We use ArrayDeque instead of LinkedList because
        // it generally has better memory locality and less overhead.

        queue = new ArrayDeque<>();
    }

    public int ping(int t) {

        // STEP 1: Add the new incoming request.
        //
        // Since timestamps are strictly increasing,
        // the newest timestamp always belongs at the rear.

        queue.offer(t);

        // STEP 2: Calculate the earliest valid timestamp.
        //
        // Example:
        // t = 3002
        // boundary = 3002 - 3000 = 2
        //
        // We need requests in [2, 3002].

        int boundary = t - 3000;

        // STEP 3: Remove all expired requests.
        //
        // If the oldest timestamp is smaller than boundary,
        // it is outside the valid window.
        //
        // IMPORTANT:
        // Use '<', not '<='.
        //
        // A timestamp exactly equal to boundary is valid
        // because the problem specifies an inclusive interval.

        while (!queue.isEmpty() && queue.peek() < boundary) {

            // Remove the oldest expired request.
            queue.poll();
        }

        // STEP 4: Return the number of requests in the window.
        //
        // Every remaining timestamp belongs to [t - 3000, t].
        // Therefore, queue.size() is our answer.

        return queue.size();
    }
}

/*
TIME COMPLEXITY:

Constructor:
O(1)

ping(t):
Amortized O(1).

Why?

At first glance, the while loop might appear to take O(n)
because it could remove many expired timestamps in one call.

However, consider the entire sequence of N ping() operations.

1. Every timestamp is inserted exactly once.
2. Every timestamp is removed at most once.
3. A timestamp can never return after removal.

Therefore:
- Total insertions = N.
- Total removals <= N.
- Total queue operations = O(N).

For N operations:
Total time = O(N).

Amortized time per ping() = O(N) / N = O(1).

Worst-case individual ping():
O(N), if it removes many expired timestamps at once.

SPACE COMPLEXITY:

O(W), where W is the maximum number of requests
that can remain within any 3000-millisecond window.

In the worst case:
O(N), because all N requests could arrive within
a 3000-millisecond interval.

Important:
We do not retain expired timestamps.
*/
```

## **5. Alternative optimal implementation: ArrayDeque directly**

Java's `ArrayDeque` also provides `peekFirst()`, `removeFirst()` and `addLast()`.

This makes the FIFO behavior more explicit.

```java
import java.util.ArrayDeque;
import java.util.Deque;

class RecentCounter {

    private final Deque<Integer> timestamps = new ArrayDeque<>();

    public RecentCounter() {
        // ArrayDeque is used as a FIFO queue.
    }

    public int ping(int t) {

        // Add the newest request at the rear.
        timestamps.addLast(t);

        // Calculate the earliest valid timestamp.
        int boundary = t - 3000;

        // Remove expired timestamps from the front.
        while (!timestamps.isEmpty()
                && timestamps.peekFirst() < boundary) {

            timestamps.removeFirst();
        }

        // All remaining timestamps are valid.
        return timestamps.size();
    }
}

/*
TIME COMPLEXITY:
Constructor: O(1)
ping(): Amortized O(1).
Worst-case individual ping(): O(N).

SPACE COMPLEXITY:
O(W), where W is the maximum number of requests
within a 3000-millisecond window.
*/
```

This is functionally equivalent to Solution 2.

**Interview recommendation:** Use Solution 2 or Solution 5. Both are optimal. I would generally choose `ArrayDeque` because it explicitly communicates FIFO operations.

# **7. Interviewer follow-up questions**

### **Q1. Why do we use a queue instead of a stack?**

Because requests expire in chronological order.

The oldest request expires first, and the newest request expires last.

A queue supports exactly this behavior:

- FIFO: First In, First Out.
- Remove expired timestamps from the front.
- Insert new timestamps at the rear.

A stack is LIFO and does not naturally support this operation.

### **Q2. Why is the solution amortized O(1), even though there is a while loop?**

A single `ping()` can remove multiple timestamps.

However, every timestamp:

- Is inserted exactly once.
- Is removed at most once.

Across N operations, there can be at most N insertions and N removals.

Therefore, total work is O(N), giving amortized O(1) per operation.

### **Q3. What if timestamps are not strictly increasing?**

Our current solution would no longer be valid.

An incoming older timestamp might need to be inserted somewhere in the middle of the queue.

We would need a different data structure or an approach that supports out-of-order events, such as an ordered multiset or balanced search tree.

### **Q4. What if the window changes from 3000 milliseconds to a configurable duration?**

We can introduce a configurable field:

```
private final int windowSize;
```

Then use:

```
int boundary = t - windowSize;
```

The rest of the algorithm remains unchanged.

### **Q5. Can we solve this using a fixed-size circular array?**

Potentially, but it is unnecessary here.

A circular buffer would require careful capacity management because the problem does not guarantee a maximum number of requests within 3000 milliseconds.

`ArrayDeque` handles this more conveniently.

### **Q6. Why not use a HashMap?**

A HashMap can store timestamps, but it does not naturally maintain chronological ordering.

We need to efficiently identify and remove the oldest expired request.

A queue is a much better fit.

### **Q7. What is the difference between sliding window and fixed window?**

- **Sliding window:** The window moves with every incoming timestamp. Here, it is `[t - 3000, t]`.
- **Fixed window:** Time is divided into predefined intervals, such as 0–3000, 3001–6000, and so on.

This problem uses a sliding window.

### **Q8. What if we need to support multiple concurrent threads calling&#x20;**`ping()`**?**

The implementation is not thread-safe.

We would need synchronization around the entire `ping()` operation so that insertion, expiration, and counting happen atomically.

For example:

```
public synchronized int ping(int t) {
    // Same queue-based implementation.
}
```

However, synchronization alone does not solve the ordering guarantee: concurrent callers must still provide timestamps in strictly increasing order.

# **1. Core intuition: Circular Array**

The problem asks us to count requests in the inclusive time window:

\\[ [t-3000,t] \\]

The window contains at most **3001 distinct integer timestamps**:

\\[ t-3000,\ t-2999,\ \ldots,\ t \\]

Therefore, we can maintain a circular array of size 3001.

```
private final int[] window = new int[3001];
private final int[] timestamp = new int[3001];
```

Each array has a specific responsibility:

| Array         | Responsibility                                                             |
| ------------- | -------------------------------------------------------------------------- |
| `window[]`    | Stores the number of requests received at a particular timestamp           |
| `timestamp[]` | Identifies which actual timestamp currently occupies a circular-array slot |
| `count`       | Stores the total number of requests in the current 3001-timestamp window   |

The key idea:

**Map timestamps to array indices using modulo 3001.**

\\[ index = t \bmod 3001 \\]

Since the window contains 3001 possible integer timestamps, modulo 3001 allows us to reuse array positions safely.

# **2. Why do we need two arrays?**

This is the most important part of your implementation.

Consider:

```
int index = t % 3001;
```

Different timestamps can map to the same index.

For example:

```
t = 1       -> index = 1
t = 3002    -> index = 1
t = 6003    -> index = 1
```

Therefore, the index alone cannot tell us whether the slot contains data for the current timestamp.

That's why you maintain:

```
timestamp[index]
```

It validates whether the slot belongs to the current timestamp.

There are two possibilities.

### **Case 1: Same timestamp**

```
if (this.timestamp[index] == t)
```

The slot already represents timestamp `t`.

This means another request arrived at the same timestamp.

We increment:

```
this.window[index]++;
this.count++;
```

Why increment both?

- `window[index]` tracks requests at timestamp `t`.
- `count` tracks all valid requests in the current window.

### **Case 2: Different timestamp**

```
else {
    this.count -= this.window[index];

    this.window[index] = 1;
    this.timestamp[index] = t;
    this.count++;
}
```

The slot belongs to an older timestamp.

Since timestamps arrive in strictly increasing order, the old timestamp is now outside the current window.

Therefore:

1. Subtract its contribution from `count`.
2. Overwrite its frequency with `1`.
3. Update the slot's timestamp.
4. Add the new request to `count`.

This is the clever part: **Instead of explicitly removing expired timestamps one by one, you remove their contribution when their circular-array slot is reused.**

# **4. Why is modulo 3001 correct?**

Let's prove the important property.

The valid window is:

\\[ [t-3000,t] \\]

Its size, considering integer timestamps, is:

\\[ t-(t-3000)+1=3001 \\]

Therefore, no two distinct timestamps inside the current window can have the same modulo 3001 index.

Suppose two timestamps have the same index:

\\[ a \bmod 3001 = b \bmod 3001 \\]

Then:

\\[ |a-b|=k\times3001 \\]

for some positive integer \\(k\\).

Thus:

\\[ |a-b|\geq3001 \\]

But two timestamps inside the current window can differ by at most 3000.

Contradiction!

Therefore, **two different valid timestamps can never occupy the same circular-array slot.**

If a slot is reused, its previous timestamp must be expired.

# **5. Complexity analysis**

| Operation            | Complexity      |
| -------------------- | --------------- |
| Constructor          | O(1)            |
| `ping(t)`            | O(1) worst case |
| Total for N requests | O(N)            |
| Space                | O(3001) = O(1)  |

Unlike the queue solution:

- Queue solution: Amortized O(1) per request.
- Your circular-array solution: Worst-case O(1) per request.

Why worst-case O(1)?

Every `ping()` performs:

- One modulo operation.
- A constant number of array accesses.
- A constant number of comparisons and arithmetic operations.

There are no loops.

# **6. Important edge cases and potential improvements**

Your implementation is correct under the given constraints.

A few things worth understanding:

**1. Multiple requests at the same timestamp**

The problem guarantees strictly increasing timestamps, so this case cannot occur.

However, your implementation also handles repeated timestamps correctly because of:

```
if (timestamp[index] == t)
```

**2. Timestamp zero**

The constraints specify `t >= 1`, so the default timestamp value of zero cannot be confused with a valid timestamp.

If zero were allowed, initialization with a separate validity mechanism would be safer.

**3. Large timestamps**

`t` can be as large as \\(10^9\\), which is safe for Java `int`.

**4. Why not use an array of size 3000?**

Because the interval is inclusive.

For example:

```
[1, 3001]
```

contains 3001 integer timestamps, not 3000.

Therefore, the correct capacity is 3001.

# **7. Interview-ready implementation**

I would keep your implementation almost exactly as it is. Here is a slightly cleaner version with comments explaining the invariant.

```java
class RecentCounter {

    // The sliding window [t - 3000, t] contains 3001
    // possible integer timestamps.
    private static final int WINDOW_SIZE = 3001;

    // window[i] = number of requests at the timestamp
    // currently mapped to circular index i.
    private final int[] window;

    // timestamp[i] = actual timestamp represented by index i.
    // Needed because multiple timestamps can map to the same index.
    private final int[] timestamp;

    // Total requests inside the current sliding window.
    private int count;

    public RecentCounter() {
        window = new int[WINDOW_SIZE];
        timestamp = new int[WINDOW_SIZE];
        count = 0;
    }

    public int ping(int t) {

        // Map timestamp to its circular-array position.
        int index = t % WINDOW_SIZE;

        // Case 1: The slot already represents timestamp t.
        // (Useful if multiple requests share the same timestamp.)
        if (timestamp[index] == t) {

            window[index]++;
            count++;

        } else {

            // Case 2: The slot represents an older timestamp.
            //
            // Because requests arrive in strictly increasing order,
            // the old timestamp must be outside [t - 3000, t].
            //
            // Remove its contribution from the running count.
            count -= window[index];

            // Reuse this circular-array slot for timestamp t.
            window[index] = 1;
            timestamp[index] = t;

            // Include the newly arrived request.
            count++;
        }

        return count;
    }
}
```

# **8. Interviewer follow-up questions**

**Q1. Is this better than the queue solution?**

In terms of time complexity, yes, in the strict worst-case sense.

| Metric              | Queue   | Circular array |
| ------------------- | ------- | -------------- |
| Per-call worst case | O(N)    | O(1)           |
| Amortized per-call  | O(1)    | O(1)           |
| Space               | O(W)    | O(1)           |
| Implementation      | Simpler | More subtle    |

The queue is easier to explain and generalize. The circular array provides a stronger worst-case time guarantee.

**Q2. What if the window size becomes configurable?**

We can replace `3001` with `windowSize + 1`.

However, the circular array must have capacity at least `windowSize + 1` for integer timestamps.

**Q3. Can we use only one array?**

Yes, but not with this exact frequency-counting design.

You would need another way to distinguish valid timestamps from stale entries and maintain the total count. The second array makes timestamp validation straightforward.

**Q4. What is the key invariant of this implementation?**

At every completed `ping(t)`:

\\[ \boxed{ count=\sum\_{x=t-3000}^{t}\text{requests at timestamp }x } \\]

And every circular-array slot stores the frequency of the timestamp recorded in its corresponding `timestamp[]` entry.

## **Final verdict**

Your solution is an excellent optimization and demonstrates a deeper understanding of sliding windows.

The important conceptual difference is:

- **Queue:** Explicitly evicts expired requests.
- **Circular array:** Lazily evicts expired requests when their slots are reused, correcting the running count at that moment.

I would absolutely consider this an optimal interview solution. The key is being able to explain why modulo 3001 guarantees that overwriting a slot can never discard a still-valid timestamp.
