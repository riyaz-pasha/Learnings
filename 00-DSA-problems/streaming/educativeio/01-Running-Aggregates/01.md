# **346. Moving Average from Data Stream**

**Difficulty:** Easy\
**Topics:** Design, Queue, Array, Data Stream

## **0. Simplify the problem statement**

You are given a stream of integers, one number at a time.

Your task is to design a class that calculates the **average of the most recent&#x20;**`size`**&#x20;numbers**.

If fewer than `size` numbers have arrived, calculate the average using all available numbers.

Implement:

```
MovingAverage(int size)
double next(int val)
```

- `MovingAverage(size)`: Initializes the data structure with a maximum window size.
- `next(val)`: Receives a new number and returns the average of the most recent `size` numbers.

### **Example**

```
Input:
["MovingAverage", "next", "next", "next", "next"]
[[3], [1], [10], [3], [5]]

Output:
[null, 1.0, 5.5, 4.66667, 6.0]
```

Let's understand what happens:

| Incoming number | Current window | Sum | Average |
| --------------- | -------------- | --- | ------- |
| 1               | [1]            | 1   | 1.0     |
| 10              | [1, 10]        | 11  | 5.5     |
| 3               | [1, 10, 3]     | 14  | 4.6667  |
| 5               | [10, 3, 5]     | 18  | 6.0     |

Notice that when `5` arrives, the oldest element (`1`) is removed because the window size is `3`.

**The important observation:** We only care about the most recent `size` elements, not the entire history.

## **1. Clarifying questions to ask the interviewer**

Before implementing, I would clarify:

1. **Can the stream contain negative numbers?**

   Why: This determines whether we can make assumptions about the running sum. Our optimal approach works with positive, zero, and negative values.
2. **What happens when fewer than&#x20;**`size`**&#x20;elements have arrived?**

   Why: The problem expects us to calculate the average using all available elements, rather than dividing by the configured window size.
3. **Can&#x20;**`size`**&#x20;be zero or negative?**

   Why: A valid moving average requires a positive window size. We should establish the input constraints.
4. **Can the input contain very large integers?**

   Why: We should use `long` for the running sum to reduce the risk of integer overflow.
5. **Do we need to support multiple calls to&#x20;**`next()`**&#x20;over a long-running stream?**

   Why: If so, we should avoid storing the entire stream and maintain only the necessary window.

## **2. Core idea and intuition**

The key concept is a **Sliding Window**.

Imagine a window of fixed size moving from left to right over a stream.

For example, with `size = 3`:

```
Stream:  1, 10, 3, 5, 8

Step 1:  [1]
Step 2:  [1, 10]
Step 3:  [1, 10, 3]
Step 4:  [10, 3, 5]
Step 5:  [3, 5, 8]
```

Whenever a new number arrives:

1. Add the new number to the window.
2. Update the running sum.
3. If the window exceeds its capacity, remove the oldest number.
4. Subtract the removed number from the running sum.
5. Calculate the average using the current window size.

### **The most important optimization**

Instead of calculating the sum of the entire window every time, maintain a variable called `windowSum`.

Suppose:

```
Window = [1, 10, 3]
Sum    = 14
```

A new number `5` arrives.

Instead of recalculating:

```
1 + 10 + 3 + 5 = 19
```

We simply update:

```
New sum = Old sum + Incoming number - Outgoing number

        = 14 + 5 - 1

        = 18
```

This makes every `next()` operation constant time.

## **3. All possible solutions**

We will go from brute force to optimal.

### **Approach 1: Brute Force — Store all elements and recalculate the sum**

**Mental model:** Keep the entire stream in an `ArrayList`. Whenever a new number arrives, iterate over the most recent `size` elements and calculate their sum.

```java
import java.util.ArrayList;
import java.util.List;

class MovingAverageBruteForce {

    private final int size;
    private final List<Integer> stream;

    public MovingAverageBruteForce(int size) {
        // Store the configured window size.
        this.size = size;

        // Store every element received so far.
        // This is intentionally not space-efficient.
        this.stream = new ArrayList<>();
    }

    public double next(int val) {

        // Add the incoming element to the stream.
        stream.add(val);

        // Determine the beginning of the current window.
        // If fewer than 'size' elements exist, start at index 0.
        int start = Math.max(0, stream.size() - size);

        // Recalculate the sum from scratch on every invocation.
        long sum = 0;

        for (int i = start; i < stream.size(); i++) {
            sum += stream.get(i);
        }

        // Calculate the actual number of elements in the window.
        int windowCount = stream.size() - start;

        // Cast to double to avoid integer division.
        return (double) sum / windowCount;
    }
}

/*
TIME COMPLEXITY:

Constructor:
    O(1)

next():
    O(size)

    We iterate through at most 'size' elements to calculate
    the sum from scratch.

    If size = 1000, every call potentially performs 1000
    additions.

    Across q calls:
    O(q * size)

SPACE COMPLEXITY:

    O(q)

    We store every element received in the ArrayList.

    Even though we only need the latest 'size' elements,
    the list keeps growing indefinitely.

VERDICT:

    Correct, but inefficient in both time and space.
*/
```

**Can we improve it?**

Yes. We don't need to store the entire stream. We only need the latest `size` elements.

Also, we don't need to recalculate the sum every time.

### **Approach 2: Queue + Running Sum**

This is the most intuitive optimal solution.

**Mental model:**

A queue follows FIFO (First In, First Out).

- New elements enter from the rear.
- Oldest elements leave from the front.

This perfectly matches our sliding window.

We additionally maintain a running sum.

```java
import java.util.ArrayDeque;
import java.util.Deque;

class MovingAverage {

    private final int size;

    // Queue maintains only the latest 'size' elements.
    private final Deque<Integer> window;

    // Maintains the sum of all elements currently in the queue.
    private long windowSum;

    public MovingAverage(int size) {

        // Store the maximum window capacity.
        this.size = size;

        // ArrayDeque provides efficient insertion and removal
        // at both ends. We use it as a FIFO queue.
        this.window = new ArrayDeque<>();

        // Initially, the window is empty.
        this.windowSum = 0;
    }

    public double next(int val) {

        // STEP 1:
        // If the window is already full, remove its oldest element.
        //
        // Why remove BEFORE insertion?
        // Because the maximum allowed window size is 'size'.
        //
        // Example:
        // size = 3
        // window = [1, 10, 3]
        //
        // Incoming value = 5
        //
        // Remove 1 first:
        // window = [10, 3]
        // windowSum = 13
        if (window.size() == size) {

            // pollFirst() removes and returns the oldest element.
            int oldest = window.pollFirst();

            // Since that element is no longer part of the window,
            // subtract it from our running sum.
            windowSum -= oldest;
        }

        // STEP 2:
        // Add the incoming element to the rear of the queue.
        window.offerLast(val);

        // Update the running sum in O(1).
        windowSum += val;

        // STEP 3:
        // Calculate the average using the CURRENT window size.
        //
        // Important:
        // During the initial calls, the window might not be full.
        // Therefore, we must divide by window.size(),
        // NOT by the configured maximum capacity.
        //
        // Casting to double ensures floating-point division.
        return (double) windowSum / window.size();
    }
}

/*
TIME COMPLEXITY:

Constructor:
    O(1)

next():
    O(1)

    At most:
      1. Remove the oldest element: O(1).
      2. Insert the new element: O(1).
      3. Update the running sum: O(1).
      4. Calculate the average: O(1).

    Therefore, each next() call takes O(1).

    For q incoming elements:
    O(q) total processing time.

SPACE COMPLEXITY:

    O(size)

    The queue never contains more than 'size' elements.

    We additionally maintain one long variable for the sum.

WHY THIS IS OPTIMAL:

    We eliminate repeated summation.

    We also discard elements that are no longer relevant.

    Each incoming element enters the queue once and leaves
    the queue at most once.

    This is the standard sliding-window + running-sum pattern.
*/
```

### **Approach 3: Circular Array + Running Sum**

This is another optimal solution and arguably the most space-efficient implementation.

**Mental model:**

Instead of using a queue, allocate an array of exactly `size` elements.

Whenever a new number arrives:

1. Find the position where the oldest element is stored.
2. Subtract that old element from the running sum.
3. Replace it with the new element.
4. Add the new element to the running sum.
5. Move the pointer forward circularly.

We use modulo (`%`) to wrap around the array.

### **Visual understanding**

Suppose `size = 3`.

Initially:

```
Index:  0    1    2
       +----+----+----+
       |  1 | 10 |  3 |
       +----+----+----+
         ^
       nextIndex = 0
```

New element `5` arrives.

Index `0` contains the oldest element (`1`).

Replace it:

```
Index:  0    1    2
       +----+----+----+
       |  5 | 10 |  3 |
       +----+----+----+
              ^
           nextIndex = 1
```

The array has not grown or shifted.

The next insertion will overwrite index `1`.

### **Java 24 implementation**

```java
class MovingAverageCircularArray {

    private final int[] window;

    // Points to the next position that will be overwritten.
    private int nextIndex;

    // Number of elements currently stored.
    // Never exceeds window.length.
    private int count;

    // Sum of the elements currently stored in the array.
    private long windowSum;

    public MovingAverageCircularArray(int size) {

        // Allocate exactly the required window capacity.
        this.window = new int[size];

        this.nextIndex = 0;
        this.count = 0;
        this.windowSum = 0;
    }

    public double next(int val) {

        // STEP 1:
        // If the window is full, the element at nextIndex
        // is the oldest element and must be removed.
        //
        // If the window is not full, nextIndex points to
        // an unused array position (initially zero-filled).
        if (count == window.length) {

            // Remove the contribution of the overwritten element.
            windowSum -= window[nextIndex];

        } else {

            // The window is still growing.
            // Increase the actual number of stored elements.
            count++;
        }

        // STEP 2:
        // Store the new incoming value at nextIndex.
        window[nextIndex] = val;

        // Add the new value to the running sum.
        windowSum += val;

        // STEP 3:
        // Move to the next array position.
        //
        // Modulo ensures circular movement:
        //
        // For size = 3:
        // 0 -> 1 -> 2 -> 0 -> 1 -> ...
        nextIndex = (nextIndex + 1) % window.length;

        // STEP 4:
        // Divide by the actual number of stored elements.
        return (double) windowSum / count;
    }
}

/*
TIME COMPLEXITY:

Constructor:
    O(size)

    We allocate an integer array of length 'size'.
    Java initializes its elements to zero.

next():
    O(1)

    Every operation involves:
      - One array access.
      - One subtraction (when the window is full).
      - One array assignment.
      - One addition.
      - One modulo operation.
      - One division.

    No loops or shifting are required.

SPACE COMPLEXITY:

    O(size)

    We allocate exactly 'size' integer positions.

    No additional collection is required.

ADVANTAGES:

    1. Fixed memory allocation.
    2. No queue object or node management.
    3. No resizing.
    4. Constant-time insertion and eviction.
    5. Excellent for continuous streams.

VERDICT:

    This is the implementation I would choose when
    optimizing for predictable memory usage and minimal
    data-structure overhead.
*/
```

## **4. Comparing all approaches**

| Approach                     | `next()` time | Space   | Stores entire stream? |
| ---------------------------- | ------------- | ------- | --------------------- |
| Brute force + ArrayList      | O(size)       | O(q)    | Yes                   |
| Queue + running sum          | O(1)          | O(size) | No                    |
| Circular array + running sum | O(1)          | O(size) | No                    |

Where:

- `size` = moving window capacity.
- `q` = total number of incoming elements.

**My interview recommendation:**

Start with Queue + Running Sum.

It is easy to explain, easy to implement, and demonstrates that you understand the relationship between FIFO queues and sliding windows.

Then introduce Circular Array as an optimization that avoids the overhead of a general-purpose queue.

## **5. Edge cases to watch out for**

| Edge case               | Input                      | Expected output         |
| ----------------------- | -------------------------- | ----------------------- |
| Window size = 1         | size=1, values=[5,10]      | [5.0,10.0]              |
| Only one element        | size=3, values=[5]         | [5.0]                   |
| Negative numbers        | size=2, values=[-1,-5]     | [-1.0,-3.0]             |
| Mixed positive/negative | size=3, values=[5,-5,10,0] | [5.0,0.0,3.3333,1.6667] |
| Repeated elements       | size=2, values=[7,7,7]     | [7.0,7.0,7.0]           |
| Window not full         | size=5, values=[1,2,3]     | [1.0,1.5,2.0]           |

**Important implementation pitfalls:**

1. **Incorrect divisor:** Divide by the current number of elements, not always by `size`.
2. **Incorrect eviction:** Always remove the oldest element, not the newest.
3. **Incorrect running sum:** Whenever an element leaves the window, subtract it.
4. **Integer division:** Use `(double) windowSum / count`.
5. **Integer overflow:** Prefer `long` for the running sum, even though the given constraints fit in an `int`.

## **6. Interviewer follow-up questions**

### **Q1. Why do we need a queue?**

A queue naturally maintains insertion order.

We need to remove the oldest element whenever a new element arrives and the window is full.

FIFO gives us exactly this behavior.

### **Q2. Why maintain a running sum?**

Without a running sum, we would iterate over the entire window for every `next()` call.

That costs O(size).

With a running sum:

```
windowSum = windowSum + incoming - outgoing;
```

We can update the sum in O(1).

### **Q3. Why use&#x20;**`long`**&#x20;instead of&#x20;**`int`**?**

The running sum can exceed the range of an integer when the window size or incoming values become large.

Using `long` provides a much larger range and makes the implementation safer.

### **Q4. Why do we divide by&#x20;**`window.size()`**&#x20;instead of&#x20;**`size`**?**

Because initially, the window may not be full.

For example:

```
size = 3

Incoming values:
5

Current window:
[5]

Correct average:
5 / 1 = 5.0
```

Dividing by `3` would produce an incorrect result.

### **Q5. Can we solve this without a Queue?**

Yes. Use a circular array.

A circular array provides the same functionality with fixed memory allocation and O(1) insertion and eviction.

### **Q6. Why is a circular array better than an ArrayList?**

An ArrayList-based implementation that removes index `0` requires shifting remaining elements, costing O(size).

A circular array overwrites the oldest element directly without shifting.

### **Q7. Can this data structure handle negative numbers?**

Absolutely.

The running sum works with positive and negative integers.

For example:

```
Window = [-5, 10]

Sum = 5

Average = 5 / 2 = 2.5
```

### **Q8. What if the stream contains millions of elements?**

Our optimal implementations still use O(size) memory.

The amount of memory does not increase as the stream grows because we discard old elements.

### **Q9. Can this data structure support concurrent calls?**

The implementations shown are not thread-safe.

If multiple threads call `next()` concurrently, updates to the queue/array, count, and running sum could interleave and produce inconsistent results.

We could synchronize the `next()` method:

```
public synchronized double next(int val) {
    // Existing implementation.
}
```

This ensures that each operation executes atomically relative to other synchronized calls on the same instance.

### **Q10. What if we need the moving average of the last K elements, but also need to retrieve the minimum and maximum?**

We can maintain additional monotonic deques:

- One monotonic increasing deque for the minimum.
- One monotonic decreasing deque for the maximum.
- One FIFO queue or circular array for the window.
- One running sum for the average.

Each incoming element can be processed in amortized O(1) time.

### **Q11. Can we calculate a moving average without storing the elements?**

Not an exact sliding-window average for arbitrary incoming values.

We need to know which element is leaving the window so that we can subtract its contribution.

Without retaining the outgoing values (or equivalent information), we cannot generally maintain the exact sum of the latest K elements.

## **7. Final interview takeaway**

Remember this problem as a combination of three concepts:

1. **Sliding Window:** Only the latest K elements matter.
2. **Queue / Circular Buffer:** Efficiently remove the oldest element.
3. **Running Sum:** Avoid recalculating the sum every time.

The central invariant is:

> `windowSum` must always equal the sum of the elements currently inside the sliding window.

Once you maintain this invariant, the entire problem becomes straightforward.

**Optimal complexity:**

- Constructor: O(1) for the queue implementation; O(size) for the circular array.
- `next()`: O(1).
- Space: O(size).
