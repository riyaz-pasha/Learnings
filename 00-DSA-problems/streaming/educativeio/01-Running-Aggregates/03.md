# **2526. Find Consecutive Integers from a Data Stream**

**Difficulty:** Medium\
**Topics:** Data Stream, Design, Queue, Sliding Window

## **0. Simplify the problem statement**

We need to design a class that receives integers one at a time from a stream.

We are given two values:

- `value`: The integer we want to see repeatedly.
- `k`: The number of consecutive occurrences required.

Every time `consec(num)` is called:

1. Add `num` to the stream.
2. Check whether the last `k` integers are all equal to `value`.
3. Return `true` if they are; otherwise, return `false`.

**Important:** If fewer than `k` integers have arrived, always return `false`.

### **Example**

```
value = 4
k = 3

Stream input:  4, 4, 4, 3, 4, 4, 4
Output:        F, F, T, F, F, F, T
```

Why?

| Call | Incoming number | Last 3 numbers | Result |
| ---- | --------------- | -------------- | ------ |
| 1    | 4               | [4]            | false  |
| 2    | 4               | [4, 4]         | false  |
| 3    | 4               | [4, 4, 4]      | true   |
| 4    | 3               | [4, 4, 3]      | false  |
| 5    | 4               | [4, 3, 4]      | false  |
| 6    | 4               | [3, 4, 4]      | false  |
| 7    | 4               | [4, 4, 4]      | true   |

Notice that we only care about the **last k elements**, not the entire stream.

## **1. Clarifying questions to ask the interviewer**

Before implementing, clarify:

**Q1. Can the stream contain negative integers or zero?**

Why ask?

The current constraints specify positive integers, but a generalized implementation might need to handle any integer.

**Q2. Can&#x20;**`k`**&#x20;be equal to 1?**

Why ask?

This is an important boundary case. If `k = 1`, the answer is simply whether the current number equals `value`.

**Q3. Can we assume the number of calls is bounded?**

Why ask?

The constraints specify at most \\(10^5\\) calls. This helps us decide whether storing the entire stream is necessary.

**Q4. Do we need to support concurrent calls?**

Why ask?

The problem doesn't require thread safety, but a production implementation might need synchronization.

## **2. Core intuition and mental model**

The most important observation:

**We don't need to remember the entire stream. We only need to know how many consecutive occurrences of&#x20;**`value`**&#x20;have appeared at the end of the stream.**

Think about this:

```
value = 4
k = 3

Incoming numbers:

4 -> 4 -> 4 -> 3 -> 4 -> 4 -> 4
```

We can maintain one variable:

```java
int count;
```

This represents:

> The number of consecutive occurrences of `value` ending at the current position.

### **How should count change?**

There are only two possibilities.

**Case 1: Incoming number equals value**

```java
if (num == value) {
    count++;
}
```

We extend the current consecutive sequence.

**Case 2: Incoming number does not equal value**

```java
else {
    count = 0;
}
```

The consecutive sequence is broken, so reset the count.

### **When should we return true?**

Whenever:

```
count >= k
```

Why `>=` instead of `==`?

Suppose:

```
value = 4
k = 3

Input: 4, 4, 4, 4
```

The results should be:

```
false, false, true, true
```

Once we have three consecutive occurrences, every subsequent occurrence of `value` continues satisfying the condition.

## **4. All possible solutions**

### **Approach 1: Brute Force — Store the entire stream**

**Idea:**

Store every incoming number in a list.

Whenever `consec(num)` is called:

1. Append `num` to the list.
2. If fewer than `k` elements exist, return false.
3. Iterate over the last `k` elements.
4. Check whether every element equals `value`.

```java
import java.util.ArrayList;
import java.util.List;

class DataStream {

    private final int value;
    private final int k;

    // Stores the complete stream.
    private final List<Integer> stream = new ArrayList<>();

    public DataStream(int value, int k) {
        this.value = value;
        this.k = k;
    }

    public boolean consec(int num) {

        // Step 1: Append the incoming number.
        stream.add(num);

        // Step 2: We cannot have k consecutive numbers yet.
        if (stream.size() < k) {
            return false;
        }

        // Step 3: Calculate the starting index of the last k elements.
        int start = stream.size() - k;

        // Step 4: Verify that all last k elements equal value.
        for (int i = start; i < stream.size(); i++) {

            if (stream.get(i) != value) {
                return false;
            }
        }

        // Every one of the last k elements equals value.
        return true;
    }
}
```

**Complexity analysis:**

- Constructor:
  - Time: \\(O(1)\\)
  - Space: \\(O(1)\\), excluding the initially empty list.
- `consec()`:
  - Time: \\(O(k)\\) in the worst case because we inspect the last `k` elements.
  - Auxiliary space: \\(O(1)\\) per call.
  - Total space: \\(O(n)\\), where `n` is the number of stream elements received.

**Why is this inefficient?**

We repeatedly examine elements that we have already examined in previous calls.

For example:

```
value = 4
k = 100

Input: 4, 4, 4, 4, 4, ...
```

Every call might examine up to 100 elements.

We can avoid this repeated work.

### **Approach 2: Sliding Window using Queue**

**Idea:**

Instead of storing the entire stream, maintain only the last `k` elements.

Use a queue:

1. Insert the incoming number.
2. If queue size exceeds `k`, remove the oldest element.
3. If queue size is less than `k`, return false.
4. Check whether all elements in the queue equal `value`.

```java
import java.util.ArrayDeque;
import java.util.Deque;

class DataStream {

    private final int value;
    private final int k;

    // Maintains only the most recent k elements.
    private final Deque<Integer> window = new ArrayDeque<>();

    public DataStream(int value, int k) {
        this.value = value;
        this.k = k;
    }

    public boolean consec(int num) {

        // Add the newest number to the sliding window.
        window.offerLast(num);

        // Keep at most k elements.
        if (window.size() > k) {
            window.pollFirst();
        }

        // Not enough elements to form a complete window.
        if (window.size() < k) {
            return false;
        }

        // Check whether every element equals value.
        for (int number : window) {

            if (number != value) {
                return false;
            }
        }

        return true;
    }
}
```

**Complexity analysis:**

- `consec()`:
  - Queue insertion: \\(O(1)\\).
  - Queue removal: \\(O(1)\\).
  - Checking the window: \\(O(k)\\).
  - Overall: \\(O(k)\\).
- Space: \\(O(k)\\), because we maintain at most `k` elements.

**Why is this still not optimal?**

We have reduced storage from \\(O(n)\\) to \\(O(k)\\).

However, we still inspect all `k` elements on every call.

Can we avoid that?

Yes!

### **Approach 3: Optimal — Maintain a consecutive counter**

This is the best solution.

**Observation:**

We don't need to store the actual elements.

We only need to know how many consecutive occurrences of `value` have appeared.

Maintain:

```
private int count;
```

Whenever a number arrives:

- If it equals `value`, increment `count`.
- Otherwise, reset `count` to zero.
- Return whether `count >= k`.

```java
class DataStream {

    private final int value;
    private final int k;

    // Number of consecutive occurrences of value
    // ending at the current position in the stream.
    private int count;

    public DataStream(int value, int k) {

        this.value = value;
        this.k = k;

        // Initially, the stream is empty.
        this.count = 0;
    }

    public boolean consec(int num) {

        // Case 1:
        // The incoming number matches our target value.
        // Therefore, the current consecutive sequence extends.
        if (num == value) {
            count++;
        }

        // Case 2:
        // The incoming number is different from our target.
        // Therefore, the consecutive sequence is broken.
        // Reset the counter because no valid sequence can end here.
        else {
            count = 0;
        }

        // We need at least k consecutive occurrences of value.
        //
        // Use >= instead of == because once we have reached k,
        // additional occurrences of value must continue returning true.
        return count >= k;
    }
}
```

### **Complexity analysis**

Let `n` be the number of calls to `consec()`.

| Operation                | Time complexity | Space complexity |
| ------------------------ | --------------- | ---------------- |
| Constructor              | \\(O(1)\\)      | \\(O(1)\\)       |
| `consec()`               | \\(O(1)\\)      | \\(O(1)\\)       |
| Entire stream processing | \\(O(n)\\)      | \\(O(1)\\)       |

**Why is this optimal?**

- Every incoming number must be examined at least once: \\(\Omega(1)\\) per call.
- Our implementation processes each number in constant time.
- We maintain only three integer fields: `value`, `k`, and `count`.
- We don't store the stream or maintain a sliding window.

Therefore:

- Time per operation: \\(O(1)\\), optimal.
- Auxiliary space: \\(O(1)\\), optimal.

## **6. Edge cases to watch out for**

### **Case 1: k = 1**

```
value = 5
k = 1

Input: 5, 3, 5
Output: true, false, true
```

Our implementation handles this naturally.

### **Case 2: All numbers are different from value**

```
value = 4
k = 3

Input: 1, 2, 3, 5
Output: false, false, false, false
```

The counter always resets to zero.

### **Case 3: More than k consecutive occurrences**

```
value = 7
k = 2

Input: 7, 7, 7, 7
Output: false, true, true, true
```

This is why we use `count >= k`.

### **Case 4: A mismatch immediately after a valid sequence**

```
value = 4
k = 3

Input: 4, 4, 4, 2
Output: false, false, true, false
```

The mismatch must reset the counter.

### **Case 5: Large stream**

The constraints allow up to \\(10^5\\) calls.

Our implementation handles this efficiently because it doesn't retain historical stream elements.

## **7. Interviewer follow-up questions**

**Q1. Why don't we need a sliding window?**

Because we don't need to know the actual last `k` elements. We only need to know the length of the consecutive suffix containing `value`.

The counter captures exactly that information.

**Q2. Why do we reset the counter to zero instead of one when a mismatch occurs?**

Because the incoming number is not equal to `value`.

Therefore, there are zero consecutive occurrences of `value` ending at the current position.

**Q3. Why do we use&#x20;**`count >= k`**&#x20;rather than&#x20;**`count == k`**?**

Because once the counter reaches `k`, additional matching numbers keep the last `k` elements equal to `value`.

**Q4. Can we optimize the solution further?**

No asymptotic optimization is possible.

We already achieve:

- \\(O(1)\\) time per operation.
- \\(O(1)\\) auxiliary space.

Both are optimal.

**Q5. What if we want to check whether the last&#x20;**`k`**&#x20;numbers are all equal to an arbitrary target that changes over time?**

We would need to clarify how the target changes.

The current counter works because `value` is fixed throughout the lifetime of the `DataStream` object.

**Q6. What if we want to check whether the last&#x20;**`k`**&#x20;numbers are equal to each other, regardless of their actual value?**

We can maintain:

```java
private int count;
private int previous;
```

For each incoming number:

```java
if (num == previous) {
    count++;
} else {
    previous = num;
    count = 1;
}

return count >= k;
```

This checks whether the last `k` elements are identical, regardless of what that integer is.

## **8. Final interview takeaway**

Remember this problem as a **consecutive suffix tracking problem**.

The key distinction:

| Requirement                          | Appropriate approach |
| ------------------------------------ | -------------------- |
| Need actual last k elements          | Queue / Deque        |
| Need to inspect all last k elements  | Sliding window       |
| Need only consecutive matching count | Counter              |

**The most important lesson:**

Before choosing a sliding window or queue, ask yourself:

*Do I actually need to store the window, or can I maintain just enough information to answer the query?*

Here, a single counter is sufficient.

**Final recommendation:** In an interview, briefly mention the brute-force and queue approaches, explain why they perform unnecessary work, and then implement the counter-based solution.
