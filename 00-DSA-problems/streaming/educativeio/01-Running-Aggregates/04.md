# **2034. Stock Price Fluctuation**

**Difficulty:** Medium\
**Topics:** HashMap, TreeMap, Priority Queue, Lazy Deletion, Data Structure Design

## **0. Simplify the problem statement**

Imagine we are tracking the price of a stock throughout the day.

Each stock price is associated with a timestamp.

For example:

| Timestamp | Price |
| --------- | ----- |
| 1         | 10    |
| 2         | 5     |
| 3         | 15    |
| 4         | 8     |

We need to design a data structure that supports four operations:

1. `update(timestamp, price)` – Insert a new price or correct an existing price at a timestamp.
2. `current()` – Return the price corresponding to the largest timestamp.
3. `maximum()` – Return the highest price among all current records.
4. `minimum()` – Return the lowest price among all current records.

**The tricky part:**

Updates can arrive out of order, and the same timestamp can be updated multiple times.

For example:

```
update(1, 10)
update(2, 5)
update(3, 15)

update(1, 20)  // Correction!
```

Our records should now be:

```
Timestamp -> Price

1 -> 20
2 -> 5
3 -> 15
```

Notice that the old price `10` must no longer contribute to the minimum or maximum.

## **1. Clarifying questions to ask the interviewer**

Before implementing, clarify the following:

**Q1. Can timestamps arrive out of order?**

Yes. The problem explicitly allows out-of-order updates.

Why ask?

We cannot assume that the most recently received update corresponds to the latest timestamp.

**Q2. Can an existing timestamp be updated multiple times?**

Yes.

Why ask?

We need to overwrite the old price rather than treat every update as a separate record.

**Q3. Can multiple timestamps have the same price?**

Yes.

Why ask?

If we use a frequency map or TreeMap, we must account for duplicate prices. Removing one timestamp's price must not accidentally remove another timestamp's identical price.

**Q4. Are there any restrictions on the number of operations?**

At most \\(10^5\\) operations.

Why ask?

This makes an \\(O(n)\\) solution per query potentially too slow. We should aim for \\(O(\log n)\\) updates and constant-time or logarithmic queries.

**Q5. Can query methods be called before the first update?**

No. The constraints guarantee at least one update before `current()`, `maximum()`, or `minimum()`.

Why ask?

We do not need to define special behavior for an empty data structure.

## **2. Core intuition and mental model**

We need to maintain three different views of the same stock data.

| Requirement                      | What we need                 |
| -------------------------------- | ---------------------------- |
| Correct price for each timestamp | Timestamp → Price mapping    |
| Latest timestamp                 | Maximum timestamp            |
| Highest and lowest prices        | Ordered collection of prices |

The key observation:

**Timestamp ordering and price ordering are two completely different things.**

For example:

```
Timestamp -> Price

1 -> 100
2 -> 20
3 -> 50
4 -> 10
```

- Latest price = 10 (largest timestamp is 4).
- Maximum price = 100.
- Minimum price = 10.

We need to maintain both orderings independently.

There are two particularly good approaches:

1. HashMap + TreeMap (eager deletion).
2. HashMap + Two Priority Queues (lazy deletion).

Let's understand both.

# **3. Solution 1: HashMap + TreeMap (Optimal and clean)**

This is my preferred solution for an interview when using Java.

### **Mental model**

Use two data structures:

**1. HashMap**

```
Map<Integer, Integer> timestampToPrice;
```

Stores the latest valid price for every timestamp.

Example:

```
{
    1 -> 10,
    2 -> 5,
    3 -> 15
}
```

**2. TreeMap**

```
TreeMap<Integer, Integer> priceFrequency;
```

Stores each price and its frequency.

Example:

```
{
    5  -> 1,
    10 -> 1,
    15 -> 1
}
```

Why frequency?

Consider:

```
Timestamp -> Price

1 -> 10
2 -> 10
3 -> 20
```

Our price frequency map becomes:

```
Price -> Frequency

10 -> 2
20 -> 1
```

If timestamp 1 is corrected from 10 to 30:

```
Timestamp -> Price

1 -> 30
2 -> 10
3 -> 20
```

We must decrease the frequency of 10 from 2 to 1, not remove it completely.

TreeMap automatically maintains keys in sorted order.

Therefore:

```
priceFrequency.firstKey(); // Minimum price
priceFrequency.lastKey();  // Maximum price
```

For the latest timestamp:

```
timestampToPrice.get(Collections.max(timestampToPrice.keySet()));
```

However, repeatedly finding the maximum timestamp would take \\(O(n)\\).

Instead, maintain a separate variable:

```
int latestTimestamp;
```

Update it whenever we receive a larger timestamp.

### **Step-by-step example**

Operations:

```
update(1, 10)
update(2, 5)
update(1, 3)
update(4, 2)
```

**Step 1: update(1, 10)**

```
timestampToPrice = {1=10}
priceFrequency   = {10=1}
latestTimestamp = 1
```

**Step 2: update(2, 5)**

```
timestampToPrice = {1=10, 2=5}
priceFrequency   = {5=1, 10=1}
latestTimestamp = 2
```

**Step 3: update(1, 3)**

Timestamp 1 already exists.

First remove its old price (10) from the frequency map.

Then insert its new price (3).

```
timestampToPrice = {1=3, 2=5}
priceFrequency   = {3=1, 5=1}
latestTimestamp = 2
```

**Step 4: update(4, 2)**

```
timestampToPrice = {1=3, 2=5, 4=2}
priceFrequency   = {2=1, 3=1, 5=1}
latestTimestamp = 4
```

Now:

```java
current() = 2
maximum() = 5
minimum() = 2
```

### **Java 24 implementation**

```java

import java.util.HashMap;
import java.util.Map;
import java.util.TreeMap;

class StockPrice {

    /*
     * Maps each timestamp to its CURRENT valid price.
     *
     * This is the source of truth.
     *
     * If a timestamp gets corrected, its old price is replaced.
     *
     * HashMap operations:
     * get()    -> O(1) average
     * put()    -> O(1) average
     * contains -> O(1) average
     */
    private final Map<Integer, Integer> timestampToPrice;

    /*
     * Maintains:
     *
     * price -> number of timestamps currently having that price.
     *
     * TreeMap keeps prices sorted in ascending order.
     *
     * Example:
     * {
     *     5  -> 2,
     *     10 -> 1,
     *     20 -> 3
     * }
     *
     * firstKey() -> minimum price
     * lastKey()  -> maximum price
     *
     * TreeMap operations:
     * get()    -> O(log n)
     * put()    -> O(log n)
     * remove() -> O(log n)
     */
    private final TreeMap<Integer, Integer> priceFrequency;

    /*
     * Stores the largest timestamp encountered so far.
     *
     * We do not need a TreeMap for timestamps because:
     * - We only need the largest timestamp.
     * - A simple variable is sufficient.
     */
    private int latestTimestamp;

    public StockPrice() {

        timestampToPrice = new HashMap<>();
        priceFrequency = new TreeMap<>();

        latestTimestamp = 0;
    }

    public void update(int timestamp, int price) {

        /*
         * STEP 1: Check whether this timestamp already exists.
         *
         * If it exists, we must remove its previous price
         * from the frequency map.
         *
         * Why?
         *
         * Because the old price is no longer valid.
         * Keeping it would produce incorrect minimum/maximum values.
         */
        if (timestampToPrice.containsKey(timestamp)) {

            int oldPrice = timestampToPrice.get(timestamp);

            /*
             * Decrease the frequency of the old price.
             *
             * Example:
             * priceFrequency = {10=2, 20=1}
             *
             * If one timestamp changes from 10 to 30:
             * {10=1, 20=1}
             *
             * We must not blindly remove price 10 because
             * another timestamp might still have price 10.
             */
            int frequency = priceFrequency.get(oldPrice);

            if (frequency == 1) {

                /*
                 * No timestamp currently has this price.
                 *
                 * Removing the key also removes it from the
                 * ordered set maintained by TreeMap.
                 */
                priceFrequency.remove(oldPrice);

            } else {

                /*
                 * Other timestamps still have this price.
                 * Only decrement its frequency.
                 */
                priceFrequency.put(oldPrice, frequency - 1);
            }
        }

        /*
         * STEP 2: Store the new/corrected price.
         */
        timestampToPrice.put(timestamp, price);

        /*
         * STEP 3: Increase the frequency of the new price.
         *
         * If this price already exists, increment its count.
         * Otherwise, create a new entry with frequency 1.
         */
        priceFrequency.merge(price, 1, Integer::sum);

        /*
         * STEP 4: Update the latest timestamp.
         *
         * IMPORTANT:
         *
         * Do not simply assign:
         *
         * latestTimestamp = timestamp;
         *
         * Updates can arrive out of order.
         *
         * Example:
         * update(10, 100)
         * update(5, 50)
         *
         * The latest timestamp must remain 10.
         */
        latestTimestamp = Math.max(latestTimestamp, timestamp);
    }

    public int current() {

        /*
         * The latest stock price is the price associated
         * with the maximum timestamp.
         *
         * latestTimestamp is maintained during updates,
         * so this operation takes O(1) average time.
         */
        return timestampToPrice.get(latestTimestamp);
    }

    public int maximum() {

        /*
         * TreeMap stores keys in ascending order.
         *
         * The last key is the maximum currently valid price.
         *
         * O(log n) because TreeMap.firstKey()/lastKey()
         * have logarithmic navigation cost in Java's
         * NavigableMap interface.
         */
        return priceFrequency.lastKey();
    }

    public int minimum() {

        /*
         * The first key is the minimum currently valid price.
         */
        return priceFrequency.firstKey();
    }
}

/*
 * COMPLEXITY ANALYSIS
 *
 * Let n = number of distinct timestamps currently recorded.
 *
 * update(timestamp, price):
 *   HashMap containsKey()       -> O(1) average
 *   HashMap get()               -> O(1) average
 *   TreeMap get()/put()/remove()-> O(log n)
 *   HashMap put()               -> O(1) average
 *
 *   Overall: O(log n)
 *
 * current():
 *   One HashMap lookup.
 *   Overall: O(1) average.
 *
 * maximum():
 *   TreeMap.lastKey().
 *   Overall: O(log n).
 *
 * minimum():
 *   TreeMap.firstKey().
 *   Overall: O(log n).
 *
 * SPACE:
 *   HashMap stores at most n timestamp-price entries.
 *   TreeMap stores at most n distinct price-frequency entries.
 *
 *   Overall: O(n).
 *
 * This is an eager deletion approach:
 * whenever a timestamp is corrected, its old price
 * is immediately removed from the price frequency map.
 */

```

**Why this is a great solution:**

- No stale data.
- No complicated heap cleanup.
- Duplicate prices are handled correctly.
- All operations meet the required performance.

# **4. Solution 2: HashMap + Two Priority Queues (Lazy deletion)**

This is another very popular interview solution.

Instead of maintaining a sorted price-frequency map, we maintain:

1. A HashMap for the latest valid price per timestamp.
2. A Max Heap for maximum prices.
3. A Min Heap for minimum prices.
4. A variable for the latest timestamp.

### **Mental model**

The interesting idea is **lazy deletion**.

Java's PriorityQueue does not efficiently support removing an arbitrary element.

For example:

```
Max Heap:

       100
      /   \
     50    80
```

Suppose the price 100 gets corrected to 20.

Removing 100 from an arbitrary heap position is expensive.

Instead of removing it immediately, we leave it in the heap and use the HashMap to determine whether it is still valid.

We store both timestamp and price in each heap entry.

```
record PriceEntry(int timestamp, int price) {}
```

Suppose:

```java
update(1, 100)
update(2, 50)
update(1, 20)
```

HashMap:

```
1 -> 20
2 -> 50
```

Max Heap may contain:

```
100 (timestamp=1)
50  (timestamp=2)
20  (timestamp=1)
```

When `maximum()` is called:

- Peek at 100.
- Check HashMap: timestamp 1 currently has price 20.
- Therefore, 100 is stale.
- Remove it.
- Peek at 50.
- HashMap says timestamp 2 has price 50.
- Therefore, 50 is valid.

Return 50.

This is lazy deletion.

### **Why store timestamp along with price?**

Consider:

```
update(1, 10)
update(2, 10)
update(1, 20)
```

The heap contains two entries with price 10.

Only one of them is stale.

If we store only prices, we cannot determine which entry is outdated.

Storing both timestamp and price allows us to validate each heap entry against the HashMap.

### **Java 24 implementation**

```java

import java.util.HashMap;
import java.util.Map;
import java.util.PriorityQueue;

class StockPrice {

    /*
     * Immutable heap entry.
     *
     * A record is useful because each entry is just
     * an immutable pair of timestamp and price.
     *
     * We need timestamp to determine whether an entry
     * is stale after a correction.
     */
    private record PriceEntry(int timestamp, int price) {}

    /*
     * Source of truth:
     *
     * timestamp -> current valid price.
     */
    private final Map<Integer, Integer> timestampToPrice;

    /*
     * Max Heap:
     *
     * Highest price appears at the root.
     *
     * If prices are equal, timestamp is used as a
     * deterministic tie-breaker.
     */
    private final PriorityQueue<PriceEntry> maxHeap;

    /*
     * Min Heap:
     *
     * Lowest price appears at the root.
     */
    private final PriorityQueue<PriceEntry> minHeap;

    /*
     * Maximum timestamp encountered so far.
     */
    private int latestTimestamp;

    public StockPrice() {

        timestampToPrice = new HashMap<>();

        /*
         * Reverse price ordering creates a Max Heap.
         *
         * Comparator.comparingInt(...).reversed()
         * avoids integer subtraction overflow.
         */
        maxHeap = new PriorityQueue<>(
            java.util.Comparator
                .comparingInt(PriceEntry::price)
                .reversed()
                .thenComparingInt(PriceEntry::timestamp)
        );

        /*
         * Natural ascending price ordering creates a Min Heap.
         */
        minHeap = new PriorityQueue<>(
            java.util.Comparator
                .comparingInt(PriceEntry::price)
                .thenComparingInt(PriceEntry::timestamp)
        );

        latestTimestamp = 0;
    }

    public void update(int timestamp, int price) {

        /*
         * Update the source of truth.
         *
         * We do not remove old entries from either heap.
         * They will be cleaned up when they reach the root.
         */
        timestampToPrice.put(timestamp, price);

        /*
         * Insert the new entry into both heaps.
         *
         * Even if this timestamp already existed,
         * we simply insert its corrected version.
         */
        PriceEntry entry = new PriceEntry(timestamp, price);

        maxHeap.offer(entry);
        minHeap.offer(entry);

        /*
         * Maintain the largest timestamp.
         */
        latestTimestamp = Math.max(latestTimestamp, timestamp);
    }

    public int current() {

        /*
         * The HashMap contains the latest valid price
         * for every timestamp.
         *
         * The largest timestamp is tracked separately.
         */
        return timestampToPrice.get(latestTimestamp);
    }

    public int maximum() {

        /*
         * Remove stale entries from the Max Heap.
         *
         * An entry is stale if its price no longer matches
         * the current price recorded for its timestamp.
         *
         * We only need to clean the root because
         * non-root entries cannot affect the current answer.
         */
        while (!maxHeap.isEmpty()) {

            PriceEntry entry = maxHeap.peek();

            int currentPrice =
                timestampToPrice.get(entry.timestamp());

            /*
             * This entry is valid.
             *
             * Return its price without removing it.
             */
            if (currentPrice == entry.price()) {
                return entry.price();
            }

            /*
             * This entry represents an outdated price.
             * Remove it and inspect the next highest entry.
             */
            maxHeap.poll();
        }

        /*
         * This situation cannot happen under the problem's
         * constraints because maximum() is called only
         * after at least one update.
         */
        throw new IllegalStateException("No stock prices available");
    }

    public int minimum() {

        /*
         * Same lazy deletion technique as maximum(),
         * but applied to the Min Heap.
         */
        while (!minHeap.isEmpty()) {

            PriceEntry entry = minHeap.peek();

            int currentPrice =
                timestampToPrice.get(entry.timestamp());

            /*
             * Root is still valid.
             */
            if (currentPrice == entry.price()) {
                return entry.price();
            }

            /*
             * Root is stale.
             * Remove it and inspect the next smallest price.
             */
            minHeap.poll();
        }

        throw new IllegalStateException("No stock prices available");
    }
}

/*
 * COMPLEXITY ANALYSIS
 *
 * Let n = number of update operations.
 *
 * update():
 *   HashMap.put()          -> O(1) average
 *   MaxHeap.offer()        -> O(log n)
 *   MinHeap.offer()        -> O(log n)
 *
 *   Overall: O(log n)
 *
 * current():
 *   HashMap.get()          -> O(1) average
 *
 *   Overall: O(1) average
 *
 * maximum():
 *   Each stale entry is removed using poll().
 *   One poll() costs O(log n).
 *
 *   A single call can remove many stale entries.
 *   Therefore, worst-case time for one call is O(n log n).
 *
 *   However, each inserted heap entry is removed at most once.
 *   Across all operations, the total cleanup work is O(n log n).
 *
 *   Amortized: O(log n) per operation.
 *
 * minimum():
 *   Identical amortized analysis.
 *
 * SPACE:
 *   HashMap: O(n) entries.
 *   Max Heap: O(n) entries.
 *   Min Heap: O(n) entries.
 *
 *   Overall: O(n).
 *
 * IMPORTANT:
 *   This implementation can contain stale entries.
 *   Therefore, its heap sizes can grow with the total
 *   number of updates, not merely distinct timestamps.
 *
 *   At most 10^5 updates are allowed, so this is acceptable.
 */

```

### **Important subtlety: Why does lazy deletion work?**

Suppose the Max Heap contains:

```
100 (timestamp=1)
90  (timestamp=2)
80  (timestamp=3)
```

Timestamp 1 is corrected from 100 to 50.

The heap becomes logically:

```
100 (stale)
90  (valid)
80  (valid)
50  (valid)
```

The heap's root is 100, but it is stale.

We remove it.

Now 90 becomes the root, and it is valid.

We can safely return 90.

**Why don't we clean every element in the heap?**

Because we only need the root to answer a minimum or maximum query.

An outdated element buried somewhere in the heap cannot affect the answer until it reaches the root.

# **5. Solution 3: Brute Force (For completeness)**

Before jumping to optimal solutions, it is useful to understand the straightforward approach.

Maintain only:

```java
Map<Integer, Integer> timestampToPrice;
```

For every query:

- `current()`: Find the largest timestamp.
- `maximum()`: Scan all prices.
- `minimum()`: Scan all prices.

### **Java implementation**

```java

import java.util.HashMap;
import java.util.Map;

class StockPrice {

    private final Map<Integer, Integer> timestampToPrice;

    public StockPrice() {
        timestampToPrice = new HashMap<>();
    }

    public void update(int timestamp, int price) {

        /*
         * HashMap.put() automatically overwrites the old price
         * if the timestamp already exists.
         */
        timestampToPrice.put(timestamp, price);
    }

    public int current() {

        /*
         * Find the largest timestamp.
         *
         * This requires scanning all timestamps.
         */
        int latestTimestamp = Integer.MIN_VALUE;

        for (int timestamp : timestampToPrice.keySet()) {
            latestTimestamp = Math.max(
                latestTimestamp,
                timestamp
            );
        }

        return timestampToPrice.get(latestTimestamp);
    }

    public int maximum() {

        /*
         * Scan every currently valid price.
         */
        int maximumPrice = Integer.MIN_VALUE;

        for (int price : timestampToPrice.values()) {
            maximumPrice = Math.max(maximumPrice, price);
        }

        return maximumPrice;
    }

    public int minimum() {

        /*
         * Scan every currently valid price.
         */
        int minimumPrice = Integer.MAX_VALUE;

        for (int price : timestampToPrice.values()) {
            minimumPrice = Math.min(minimumPrice, price);
        }

        return minimumPrice;
    }
}

/*
 * COMPLEXITY ANALYSIS
 *
 * Let n = number of distinct timestamps.
 *
 * update()   -> O(1) average
 * current()  -> O(n)
 * maximum()  -> O(n)
 * minimum()  -> O(n)
 *
 * SPACE      -> O(n)
 *
 * This solution is simple and correct but inefficient
 * when many query operations are performed.
 */

```

# **6. Comparing all approaches**

| Operation | Brute Force | HashMap + TreeMap | HashMap + Heaps    |
| --------- | ----------- | ----------------- | ------------------ |
| update    | O(1) avg    | O(log n)          | O(log n)           |
| current   | O(n)        | O(1) avg          | O(1) avg           |
| maximum   | O(n)        | O(log n)          | O(log n) amortized |
| minimum   | O(n)        | O(log n)          | O(log n) amortized |
| Space     | O(n)        | O(n)              | O(U)               |

Here:

- \\(n\\) = number of distinct timestamps.
- \\(U\\) = number of update operations.

The heap solution's space is \\(O(U)\\) because stale entries are retained until they reach the heap root.

**My recommendation:**

Use **HashMap + TreeMap** as the primary interview solution.

It is straightforward, maintains only valid data, and has predictable complexity.

Use **HashMap + Two Heaps** when the interviewer specifically wants to explore lazy deletion or priority queues.

# **7. Edge cases to watch out for**

### **Case 1: Out-of-order timestamps**

```java
update(10, 100);
update(5, 50);

current(); // 100
```

Why?

The latest timestamp is 10, not the most recently received timestamp 5.

### **Case 2: Correcting the maximum price**

```java
update(1, 100);
update(2, 50);
update(1, 10);

maximum(); // 50
```

The old maximum 100 must no longer be considered.

### **Case 3: Correcting the minimum price**

```java
update(1, 5);
update(2, 20);
update(1, 100);

minimum(); // 20
```

The old minimum 5 must be removed.

### **Case 4: Duplicate prices**

```java
update(1, 10);
update(2, 10);
update(3, 20);

update(1, 30);

minimum(); // 10
```

The price 10 is still valid at timestamp 2.

This is why the TreeMap solution requires frequency counting.

### **Case 5: Updating the latest timestamp**

```java
update(1, 10);
update(5, 50);
update(3, 30);

current(); // 50
```

Updating an older timestamp must not change the latest timestamp.

### **Case 6: Updating the same timestamp repeatedly**

```java
update(1, 10);
update(1, 20);
update(1, 30);

current(); // 30
maximum(); // 30
minimum(); // 30
```

Only the most recent correction matters.

# **8. Interviewer follow-up questions**

### **Q1. Why can't we use only a HashMap?**

A HashMap provides efficient timestamp-to-price lookup, but it does not maintain sorted keys or values.

Finding the minimum or maximum would require scanning all prices.

We need an additional ordered data structure.

### **Q2. Why use TreeMap instead of TreeSet?**

TreeSet stores unique values.

But multiple timestamps can have the same price.

For example:

```
1 -> 10
2 -> 10
3 -> 20
```

If we remove price 10 after correcting timestamp 1, we would accidentally lose the valid price belonging to timestamp 2.

TreeMap with frequencies solves this problem.

### **Q3. Why not use TreeMap for timestamps too?**

We could.

For example:

```java
TreeMap<Integer, Integer> timestampToPrice;
```

Then:

```java
timestampToPrice.lastEntry().getValue();
```

would return the latest price.

However, we do not need the entire timestamp ordering. We only need the largest timestamp.

Maintaining `latestTimestamp` separately is simpler and allows constant-time `current()`.

### **Q4. Why not use a PriorityQueue alone?**

A PriorityQueue efficiently retrieves the minimum or maximum element.

However, it cannot efficiently remove an arbitrary old price when a timestamp gets corrected.

We need either:

- An ordered frequency map with eager deletion.
- Lazy deletion using a HashMap to validate heap entries.

### **Q5. What is the difference between eager and lazy deletion?**

| Eager deletion                | Lazy deletion                            |
| ----------------------------- | ---------------------------------------- |
| Remove old prices immediately | Keep old prices temporarily              |
| TreeMap approach              | Heap approach                            |
| Only valid data is maintained | Stale data may exist                     |
| Predictable query complexity  | Individual query can have cleanup spikes |
| Requires frequency tracking   | Requires timestamp validation            |

### **Q6. Can we optimize the TreeMap approach further?**

The current implementation already has efficient asymptotic complexity.

We could use a `TreeSet` of custom price-frequency entries, but we would need to remove and reinsert entries whenever their frequency changes.

That adds implementation complexity without improving the overall \\(O(\log n)\\) complexity.

### **Q7. What happens if two timestamps have the same price in the heap approach?**

Both entries are independently stored with their timestamps.

When checking whether an entry is stale, we compare its price against the current price for that specific timestamp.

Therefore, correcting one timestamp does not invalidate another timestamp with the same price.

### **Q8. Can the heap solution have&#x20;**\\(O(n)\\)**&#x20;time for one maximum query?**

Yes.

Imagine many timestamps have been corrected, leaving stale entries at the top of the heap.

A single `maximum()` call may remove many stale entries.

Its worst-case individual time is \\(O(U \log U)\\), but each stale entry is removed only once.

Thus, the amortized cleanup cost is \\(O(\log U)\\) per update/query operation over the complete sequence.

# **9. Final interview takeaway**

The central challenge is not finding a minimum or maximum. It is maintaining those values correctly when historical records can be overwritten.

Remember this mental model:

```
                  StockPrice
                      |
          +-----------+-----------+
          |           |           |
       Timestamp    Latest      Price
        Mapping    Timestamp   Ordering
          |           |           |
       HashMap      Integer     TreeMap
                                  |
                             Min / Max
```

**The most important design decision:**

- HashMap answers: What is the current price at this timestamp?
- `latestTimestamp` answers: Which timestamp is the latest?
- TreeMap answers: What are the minimum and maximum valid prices?

Once these three responsibilities are separated, the problem becomes straightforward.

**Best solution to present in an interview: HashMap + TreeMap, with O(log n) updates, O(1) average current, O(log n) min/max, and O(n) space.**
