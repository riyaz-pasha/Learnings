# **2102. Sequentially Ordinal Rank Tracker**

**Difficulty:** Hard\
**Pattern:** Two Heaps / Priority Queues / Dynamic Ranking\
**Optimal Time Complexity:** `O(log N)` for both `add()` and `get()`\
**Optimal Space Complexity:** `O(N)`

## **0. Simplify the problem statement**

Imagine we are building a system that maintains a leaderboard of scenic locations.

Each location has:

- `name`: A unique string.
- `score`: An integer attractiveness score.

We need to support two operations:

1. `add(name, score)` – Add a new location.
2. `get()` – Return the location at the current query rank.

The important twist is:

**The first&#x20;**`get()`**&#x20;returns the 1st best location, the second&#x20;**`get()`**&#x20;returns the 2nd best location, the third&#x20;**`get()`**&#x20;returns the 3rd best location, and so on.**

We don't pass the rank to `get()`. The system maintains it internally.

### **Ranking rules**

A location is better if:

1. It has a higher score.
2. If scores are equal, it has a lexicographically smaller name.

For example:

| Location | Score | Rank |
| -------- | ----- | ---- |
| branford | 3     | 1    |
| alps     | 2     | 2    |
| bradford | 2     | 3    |
| orland   | 2     | 4    |

Notice that `alps` comes before `bradford` because both have score 2, but `alps` is lexicographically smaller.

## **1. Clarifying questions to ask the interviewer**

Before implementing the solution, clarify:

**Q1. Are location names unique?**

Why: If names are unique, we don't need to handle duplicate locations or define how duplicate entries should be ranked.

The problem guarantees uniqueness.

**Q2. Can new locations be added after calling&#x20;**`get()`**?**

Why: This determines whether we need a static sorted collection or a dynamically maintained ranking.

Yes. New locations can be added at any time.

**Q3. Does every&#x20;**`get()`**&#x20;increase the requested rank by one?**

Why: This is the key requirement. We need to maintain the number of queries internally.

Yes. The first call requests rank 1, the second rank 2, etc.

**Q4. Can the number of queries exceed the number of additions?**

Why: We need to ensure the requested rank always exists.

No. The problem guarantees that the number of `get()` calls never exceeds the number of `add()` calls.

## **2. Core intuition: Two Heaps**

This is the most important part of the problem.

A straightforward approach would be:

- Store every location.
- Sort all locations whenever `get()` is called.
- Return the location at the current query index.

But sorting repeatedly is expensive.

Instead, we can divide all locations into two groups.

### **Mental model**

Maintain two priority queues:

**Heap 1:&#x20;**`best`

Contains the first `k` best locations, where `k` is the number of times `get()` has been called.

**Heap 2:&#x20;**`remaining`

Contains all other locations.

The key invariant is:

- `best` contains exactly the first `k` best locations.
- `remaining` contains everything else.
- The root of `best` is the worst location among the first `k` best locations.
- The root of `remaining` is the best location among the remaining locations.

Therefore, the root of `best` is exactly the answer to the next `get()` call.

### **Why does this work?**

Suppose the sorted ranking is:

```
Best                                      Worst

A          B          C          D          E
```

Initially, no queries have happened.

```
best      = []
remaining = [A, B, C, D, E]
```

After the first `get()`:

```
best      = [A]
remaining = [B, C, D, E]

Answer = A
```

After the second `get()`:

```
best      = [A, B]
remaining = [C, D, E]

Answer = B
```

After the third `get()`:

```
best      = [A, B, C]
remaining = [D, E]

Answer = C
```

Notice something important:

**Every&#x20;**`get()`**&#x20;moves exactly one location from&#x20;**`remaining`**&#x20;into&#x20;**`best`**.**

However, there is an interesting complication.

What happens if we add a new location after some queries have already happened?

Suppose:

```
best      = [A, B]
remaining = [C, D, E]
```

Now we add a new location `X` that is better than `B`.

The correct ranking becomes:

```
X, A, B, C, D, E
```

But `best` must still contain the first two best locations.

Therefore:

```
best      = [X, A]
remaining = [B, C, D, E]
```

We must rebalance the heaps.

This is exactly why two heaps are useful.

## **3. Comparator design**

Before implementing the heaps, we need to define the ranking order correctly.

We want:

1. Higher score first.
2. Smaller name first when scores are equal.

Let's create a `Location` record.

```
record Location(String name, int score) {}
```

Define a comparator representing **best-to-worst ordering**:

```java
Comparator<Location> BEST_FIRST = (a, b) -> {
    int scoreComparison = Integer.compare(b.score(), a.score());

    if (scoreComparison != 0) {
        return scoreComparison;
    }

    return a.name().compareTo(b.name());
};
```

Let's understand it.

| Location A | Location B    | Comparator result |
| ---------- | ------------- | ----------------- |
| (A, 10)    | (B, 5)        | A comes first     |
| (A, 5)     | (B, 10)       | B comes first     |
| (alps, 5)  | (bradford, 5) | alps comes first  |
| (zoo, 5)   | (apple, 5)    | apple comes first |

**Important PriorityQueue observation:**

Java's `PriorityQueue` always places the smallest element according to its comparator at the head.

Therefore:

- `remaining` needs `BEST_FIRST`, because we want its best element at the head.
- `best` needs `BEST_FIRST.reversed()`, because we want its worst element at the head.

This is the trickiest implementation detail.

# **4. All possible solutions**

## **Approach 1: Brute Force – Sort on every get()**

### **Intuition**

Maintain a list containing every location.

Whenever `get()` is called:

1. Sort all locations.
2. Return the location at index `queryCount - 1`.
3. Increment `queryCount`.

### **Java 24 implementation**

```java
import java.util.*;

class SORTrackerBruteForce {

    /*
     * Each location has a unique name and an attractiveness score.
     */
    record Location(String name, int score) {}

    /*
     * Comparator representing best-to-worst ordering:
     *
     * 1. Higher score comes first.
     * 2. If scores are equal, lexicographically smaller name comes first.
     *
     * Integer.compare() avoids integer overflow that could occur
     * if we used subtraction.
     */
    private static final Comparator<Location> BEST_FIRST =
            (a, b) -> {
                int comparison = Integer.compare(b.score(), a.score());

                if (comparison != 0) {
                    return comparison;
                }

                return a.name().compareTo(b.name());
            };

    /*
     * Stores every location added so far.
     */
    private final List<Location> locations = new ArrayList<>();

    /*
     * Number of get() calls made so far.
     *
     * If queryCount = 0, the next get() asks for rank 1.
     * If queryCount = 1, the next get() asks for rank 2.
     */
    private int queryCount = 0;

    public void add(String name, int score) {

        /*
         * Simply append the new location.
         *
         * We don't sort during add().
         */
        locations.add(new Location(name, score));
    }

    public String get() {

        /*
         * Sort all locations from best to worst.
         *
         * This is expensive because sorting takes O(N log N).
         */
        locations.sort(BEST_FIRST);

        /*
         * The next requested rank is queryCount + 1.
         *
         * Since Java arrays/lists are zero-indexed,
         * we access index queryCount.
         */
        String answer = locations.get(queryCount).name();

        /*
         * Every get() advances the requested rank.
         */
        queryCount++;

        return answer;
    }
}

/*
 * Complexity:
 *
 * add():
 * Time: O(1) amortized.
 * Reason: ArrayList insertion at the end is O(1) amortized.
 *
 * get():
 * Time: O(N log N).
 * Reason: We sort all N locations every time get() is called.
 *
 * Space:
 * O(N) for storing all locations.
 *
 * Main drawback:
 * Repeated sorting wastes considerable work because most locations
 * have not changed since the previous query.
 */
```

### **Complexity**

| Operation | Time           |
| --------- | -------------- |
| add()     | O(1) amortized |
| get()     | O(N log N)     |
| Space     | O(N)           |

This approach is simple but inefficient for up to 40,000 operations.

## **Approach 2: Single PriorityQueue + Lazy Sorting**

### **Intuition**

We can maintain all locations in a single priority queue.

The priority queue always exposes the best location.

However, we need the 1st, 2nd, 3rd, etc. best locations.

We could extract elements until reaching the requested rank, but we cannot permanently discard them because future operations may need the complete ranking.

One alternative is to maintain a separate list of extracted elements and restore them when necessary.

But this introduces unnecessary movement and complexity.

A more efficient solution is to maintain two heaps.

Before getting there, let's examine a single-heap approach that uses a sorted list of already extracted elements.

### **Java implementation**

```java
import java.util.*;

class SORTrackerSingleHeap {

    record Location(String name, int score) {}

    private static final Comparator<Location> BEST_FIRST =
            (a, b) -> {
                int comparison = Integer.compare(b.score(), a.score());

                if (comparison != 0) {
                    return comparison;
                }

                return a.name().compareTo(b.name());
            };

    /*
     * All locations are stored in a min-heap according to BEST_FIRST.
     * The best location is always available at the root.
     */
    private final PriorityQueue<Location> remaining =
            new PriorityQueue<>(BEST_FIRST);

    /*
     * Stores locations already returned by get().
     *
     * This list is maintained in best-to-worst order.
     */
    private final List<Location> extracted = new ArrayList<>();

    public void add(String name, int score) {

        remaining.offer(new Location(name, score));
    }

    public String get() {

        /*
         * The next requested location is the next best location
         * not returned previously.
         *
         * The priority queue gives us that location in O(log N).
         */
        Location next = remaining.poll();

        /*
         * Preserve the extracted location so that we don't lose it.
         */
        extracted.add(next);

        /*
         * Return the requested location.
         */
        return next.name();
    }
}

/*
 * Complexity:
 *
 * add(): O(log N)
 * get(): O(log N)
 * Space: O(N)
 *
 * This is actually a valid alternative because the problem never asks
 * us to query the same rank twice.
 *
 * Important:
 * The number of get() calls increases monotonically.
 * Therefore, permanently extracting the next best location is safe.
 *
 * The two-heap solution below is generally the more instructive
 * solution because it explicitly maintains the queried/unqueried
 * ranking boundary.
 */
```

**Observation:** This single-heap solution is already optimal!

Why, then, do we need two heaps?

We actually don't need two heaps for this particular problem.

Every `get()` asks for the next rank, never a previously requested rank. Therefore, extracting the best remaining element is sufficient.

The problem's guarantee that queries never exceed additions ensures that `poll()` always returns a location.

However, the two-heap approach is an excellent way to understand the dynamic ranking partition and is useful in related problems.

## **Approach 3: Optimal – Two PriorityQueues**

This is the standard two-heap solution.

### **Intuition**

We maintain:

- `best`: The first `k` best locations.
- `remaining`: All locations ranked after those `k` locations.

Where `k` is the number of `get()` calls.

The heap configurations are:

| Heap      | Root represents                    |
| --------- | ---------------------------------- |
| best      | Worst among the first k locations  |
| remaining | Best among the remaining locations |

### **Operations**

**add(name, score)**

1. Insert the new location into `remaining`.
2. Compare the best location in `remaining` with the worst location in `best`.
3. If the new partition ordering is violated, swap the roots.

**get()**

1. Move the best location from `remaining` into `best`.
2. Increment the query count.
3. Return the worst location in `best`.

Why return the worst location in `best`?

Because `best` contains exactly the first `k` best locations.

Its worst element is therefore the kth best element.

### **Java 24 implementation**

```java
import java.util.*;

class SORTracker {

    /*
     * Immutable representation of a scenic location.
     *
     * Records are useful here because:
     * 1. We only need to store name and score.
     * 2. Both fields are immutable.
     * 3. Records automatically provide accessors.
     */
    record Location(String name, int score) {}

    /*
     * Comparator representing best-to-worst ranking.
     *
     * Ranking rules:
     *
     * 1. Higher score is better.
     * 2. If scores are equal, lexicographically smaller name is better.
     *
     * Example:
     *
     * (branford, 3)
     * (alps, 2)
     * (bradford, 2)
     *
     * Ranking:
     * branford -> alps -> bradford
     *
     * Java PriorityQueue places the smallest element according
     * to the comparator at its head.
     *
     * Therefore, this comparator makes the BEST location the root.
     */
    private static final Comparator<Location> BEST_FIRST =
            (a, b) -> {

                /*
                 * Reverse score comparison:
                 * Higher score should come first.
                 *
                 * Use Integer.compare instead of subtraction
                 * to avoid potential integer overflow.
                 */
                int scoreComparison =
                        Integer.compare(b.score(), a.score());

                if (scoreComparison != 0) {
                    return scoreComparison;
                }

                /*
                 * Equal scores:
                 * Lexicographically smaller name comes first.
                 */
                return a.name().compareTo(b.name());
            };

    /*
     * HEAP 1: best
     *
     * Contains the first k best locations, where k is the number
     * of get() calls performed so far.
     *
     * We reverse BEST_FIRST because we want the WORST location
     * among these k locations at the root.
     *
     * Why?
     *
     * Suppose best contains:
     *
     * A -> B -> C
     *
     * where A is best and C is worst.
     *
     * We want C at the root because C represents the current
     * kth best location.
     *
     * This is effectively a max-heap with respect to BEST_FIRST.
     */
    private final PriorityQueue<Location> best =
            new PriorityQueue<>(BEST_FIRST.reversed());

    /*
     * HEAP 2: remaining
     *
     * Contains all locations ranked after the first k locations.
     *
     * BEST_FIRST ensures that the BEST remaining location
     * is always at the root.
     */
    private final PriorityQueue<Location> remaining =
            new PriorityQueue<>(BEST_FIRST);

    /*
     * Number of get() calls made so far.
     *
     * This is also the number of locations that must be stored
     * inside the best heap.
     */
    private int queryCount = 0;

    public SORTracker() {

        /*
         * Both priority queues are initially empty.
         *
         * Initially:
         * best      = []
         * remaining = []
         * queryCount = 0
         */
    }

    public void add(String name, int score) {

        /*
         * Step 1:
         *
         * Every newly added location initially goes into remaining.
         *
         * Why?
         *
         * We already have queryCount locations in best.
         * Those locations represent the first queryCount ranks.
         *
         * A new location may or may not belong to those ranks.
         * Therefore, insert it into remaining first.
         */
        remaining.offer(new Location(name, score));

        /*
         * Step 2:
         *
         * If best is empty, there is no partition boundary yet.
         * No rebalancing is required.
         */
        if (best.isEmpty()) {
            return;
        }

        /*
         * Step 3:
         *
         * Examine the two boundary elements.
         *
         * best.peek():
         * Worst location among the first queryCount locations.
         *
         * remaining.peek():
         * Best location among all remaining locations.
         *
         * If the best remaining location is better than
         * the worst selected location, our partition is invalid.
         *
         * Example:
         *
         * best      = [A, B]
         * remaining = [C, D]
         *
         * Suppose X is newly added and ranking becomes:
         *
         * X, A, B, C, D
         *
         * Correct partition:
         *
         * best      = [X, A]
         * remaining = [B, C, D]
         *
         * So we must swap the boundary elements.
         */
        if (BEST_FIRST.compare(
                remaining.peek(),
                best.peek()
        ) < 0) {

            /*
             * Remove the best element from remaining.
             */
            Location better = remaining.poll();

            /*
             * Remove the worst element from best.
             */
            Location worse = best.poll();

            /*
             * Move the better element into best.
             *
             * This restores the invariant that best contains
             * the first queryCount best locations.
             */
            best.offer(better);

            /*
             * Move the displaced worse element into remaining.
             */
            remaining.offer(worse);
        }

        /*
         * Why is only one swap necessary?
         *
         * Before add(), both heaps already satisfied the partition
         * invariant.
         *
         * We insert exactly one new location.
         *
         * Therefore, at most one new location can cross
         * the existing partition boundary.
         */
    }

    public String get() {

        /*
         * Step 1:
         *
         * The next requested rank is queryCount + 1.
         *
         * We need to move the best remaining location into best.
         *
         * remaining.peek() is exactly the best location
         * that has not yet been returned.
         */
        Location next = remaining.poll();

        /*
         * Step 2:
         *
         * Add the selected location to best.
         *
         * best now contains the first queryCount + 1 best locations.
         */
        best.offer(next);

        /*
         * Step 3:
         *
         * Increment the number of queries.
         */
        queryCount++;

        /*
         * Step 4:
         *
         * Return the worst element inside best.
         *
         * Since best contains exactly the first queryCount
         * best locations, its worst element is the
         * queryCount-th best location.
         *
         * Therefore, this is exactly the requested answer.
         */
        return best.peek().name();
    }
}

/*
 * ============================================================
 * COMPLEXITY ANALYSIS
 * ============================================================
 *
 * Let N = number of locations added so far.
 *
 * Let Q = number of get() calls so far.
 *
 * INVARIANTS:
 *
 * 1. best.size() == Q.
 *
 * 2. best contains the Q best locations overall.
 *
 * 3. remaining contains all other locations.
 *
 * 4. Every element in best is at least as good as every
 *    element in remaining.
 *
 * 5. best.peek() is the worst element in best.
 *
 * 6. remaining.peek() is the best element in remaining.
 *
 *
 * add():
 *
 * 1. remaining.offer():
 *    O(log N).
 *
 * 2. Comparing heap roots:
 *    O(1).
 *
 * 3. If rebalancing is necessary:
 *    Two poll() operations and two offer() operations.
 *    Each takes O(log N).
 *
 * Total: O(log N).
 *
 * Importantly, only one swap is required per add().
 *
 *
 * get():
 *
 * 1. remaining.poll():
 *    O(log N).
 *
 * 2. best.offer():
 *    O(log N).
 *
 * 3. best.peek():
 *    O(1).
 *
 * 4. Increment queryCount:
 *    O(1).
 *
 * Total: O(log N).
 *
 *
 * SPACE:
 *
 * Every location exists in exactly one of the two heaps.
 *
 * best.size() + remaining.size() == N.
 *
 * Therefore:
 *
 * Total auxiliary space = O(N).
 *
 *
 * FINAL COMPLEXITIES:
 *
 * add()  -> O(log N)
 * get()  -> O(log N)
 * Space  -> O(N)
 */
```

# **6. Edge cases to watch out for**

### **Case 1: Same score, different names**

```java
add("zoo", 10);
add("apple", 10);
add("mango", 10);
```

Expected ranking:

```
apple
mango
zoo
```

Why: Lexicographical ordering must be applied when scores are equal.

### **Case 2: New location is better than every existing location**

```java
add("apple", 5);
get();

add("best", 100);
```

Before adding:

```
best      = [apple]
remaining = []
```

After adding:

```
best      = [best]
remaining = [apple]
```

The new location must enter the already selected top-ranked group.

### **Case 3: New location is worse than every existing location**

```java
add("apple", 100);
get();

add("zoo", 1);
```

No swap is required.

### **Case 4: All locations have identical scores**

```java
add("c", 10);
add("a", 10);
add("b", 10);
```

Expected ranking:

```
a
b
c
```

The comparator must handle ties correctly.

### **Case 5: Multiple consecutive get() calls**

```java
add("a", 10);
add("b", 9);
add("c", 8);

get();
get();
get();
```

Expected:

```
a
b
c
```

Each query must advance the rank exactly once.

### **Case 6: Add after all currently added locations have been queried**

```java
add("a", 10);
get();

add("b", 20);
get();
```

Expected:

```
a
b
```

The new location may change the ranking of previously selected locations.

This is why rebalancing in `add()` is essential.

# **7. Interviewer follow-up questions**

### **Q1. Why do we need two heaps?**

We don't strictly need two heaps for this exact problem.

A single priority queue is sufficient because every query requests the next unreturned rank.

However, the two-heap solution explicitly maintains the queried and unqueried partitions.

It is a useful generalization for problems involving a dynamically maintained ranking boundary.

### **Q2. Why does&#x20;**`best`**&#x20;use a reversed comparator?**

Because Java's `PriorityQueue` places the smallest element according to its comparator at the root.

We want the worst element among the selected top `k` locations at the root.

Reversing the best-first comparator achieves that.

### **Q3. Why does&#x20;**`remaining`**&#x20;use the normal comparator?**

We want the best unselected location at the root so that `get()` can retrieve the next required rank efficiently.

### **Q4. Why do we need only one swap during&#x20;**`add()`**?**

Before insertion, both heaps already satisfy the partition invariant.

Only one new location is inserted.

That single location can violate the partition boundary, so at most one pair of roots needs to be exchanged.

### **Q5. Why not use an ArrayList and binary search?**

Binary search can locate the correct insertion position in `O(log N)`.

However, inserting into an ArrayList requires shifting elements, which takes `O(N)`.

The priority queues avoid this expensive shifting.

### **Q6. Can we use TreeSet instead?**

Yes.

A `TreeSet` can maintain all locations in sorted order.

However, Java's `TreeSet` does not support efficient retrieval by rank/index.

Retrieving the kth element requires iteration, which takes `O(N)` in the worst case.

We would need an order-statistics tree to support efficient rank queries.

### **Q7. What happens if we change the ranking rule to lower score being better?**

Change the comparator to:

```java
Comparator<Location> BEST_FIRST =
        Comparator.comparingInt(Location::score)
                  .thenComparing(Location::name);
```

The rest of the algorithm remains unchanged.

### **Q8. Can this solution support deletion of locations?**

Not directly.

Deletion introduces additional complications because removing a location may affect the partition boundary.

We would need to identify which heap contains the location and rebalance the heaps afterward.

An indexed heap or an ordered data structure could help.

### **Q9. What is the most important invariant in this problem?**

This one:

```
best contains exactly the first queryCount best locations.
```

Everything else follows from this invariant.

If we preserve it after every `add()` and `get()`, the answer is always available at:

```
best.peek()
```

## **8. Final interview takeaway**

There are two important observations to remember:

**Observation 1: Queries are sequential.**

The first query asks for rank 1, the second asks for rank 2, and so on.

We never need to retrieve an arbitrary rank.

This makes a single priority queue with extraction sufficient for the optimal solution.

**Observation 2: Dynamic additions can change previously established ranks.**

If we explicitly maintain the first `k` elements as one partition, we need to rebalance when a newly added element is better than the current kth element.

This gives us the two-heap solution.

### **Complexity comparison**

| Approach             | add()          | get()      | Space |
| -------------------- | -------------- | ---------- | ----- |
| Sort every query     | O(1) amortized | O(N log N) | O(N)  |
| Single PriorityQueue | O(log N)       | O(log N)   | O(N)  |
| Two PriorityQueues   | O(log N)       | O(log N)   | O(N)  |

**My recommendation in an interview:** Start with sorting to establish the baseline, recognize that queries are sequential, and derive the single-priority-queue solution as the simplest optimal approach. Then discuss the two-heap partition as a useful alternative for dynamic ranking problems.

Both priority-queue approaches achieve **O(log N) per operation and O(N) space**.










You can write the same comparator using `Comparator.comparingInt()`, `.reversed()`, and `.thenComparing()`:

```java
private static final Comparator<Location> BEST_FIRST =
        Comparator.comparingInt(Location::score)
                  .reversed()
                  .thenComparing(Location::name);
```

### **How it works**

1. `Comparator.comparingInt(Location::score)`
   - Sorts by score in ascending order.
   - Lower score comes first.
2. `.reversed()`
   - Reverses the ordering.
   - Higher score comes first.
3. `.thenComparing(Location::name)`
   - For equal scores, sorts names lexicographically in ascending order.
   - Smaller name comes first.

### **Example**

```
Location("branford", 3)
Location("alps", 2)
Location("bradford", 2)
```

Resulting order:

```
branford (3)
alps     (2)
bradford (2)
```

### **Using it in the two heaps**

```java
// Best location comes first.
private final PriorityQueue<Location> remaining =
        new PriorityQueue<>(BEST_FIRST);

// Worst location among the selected top k comes first.
private final PriorityQueue<Location> best =
        new PriorityQueue<>(BEST_FIRST.reversed());
```

**Interview tip:** This is the cleanest and most readable comparator for this problem. Be careful to apply `.reversed()` before `.thenComparing()`, not after it.

If you reverse the entire comparator after adding the name comparison, the tie-breaking order will also reverse, which is not what we want.
