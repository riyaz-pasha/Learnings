# **703. Kth Largest Element in a Stream**

**Difficulty:** Easy\
**Primary Pattern:** Heap / Priority Queue (Min Heap)\
**LeetCode:** [703. Kth Largest Element in a Stream](https://leetcode.com/problems/kth-largest-element-in-a-stream/?utm_source=chatgpt.com)

## **0. Simplify the problem statement**

We need to design a class that continuously tracks the **kth largest element** from a stream of integers.

There are two operations:

1. **Constructor:** Initialize the data structure with `k` and an initial array of numbers.
2. **add(val):** Add a new number and return the kth largest number among all numbers seen so far.

### **Example**

```
k = 3
nums = [4, 5, 8, 2]
```

Initially, sort the numbers in descending order:

```
[8, 5, 4, 2]
```

The 3rd largest element is `4`.

Now process incoming numbers:

| Incoming value | Sorted elements (descending) | 3rd largest |
| -------------- | ---------------------------- | ----------- |
| 3              | 8, 5, 4, 3, 2                | 4           |
| 5              | 8, 5, 5, 4, 3, 2             | 5           |
| 10             | 10, 8, 5, 5, 4, 3, 2         | 5           |
| 9              | 10, 9, 8, 5, 5, 4, 3, 2      | 8           |
| 4              | 10, 9, 8, 5, 5, 4, 4, 3, 2   | 8           |

Output:

```
[4, 5, 5, 8, 8]
```

**Important observation:** We don't actually need to maintain all elements in sorted order. We only need enough information to identify the kth largest element.

## **1. Clarifying questions to ask the interviewer**

| Question                                      | Why clarify?                                                                                                    |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Can duplicate numbers exist?                  | Yes, duplicates count as separate elements when determining the kth largest.                                    |
| Can numbers be negative?                      | Yes. We must not assume scores are positive.                                                                    |
| What happens if fewer than k elements exist?  | The constraints guarantee that `nums.length + 1 >= k`, but the number of elements can initially be less than k. |
| Do we need to retain all historical elements? | No, if we only need the kth largest element, we can discard elements that cannot affect the answer.             |
| Can `k` change during execution?              | The problem specifies a fixed k.                                                                                |

## **2. Core idea and intuition**

### **Optimal approach: Min Heap of size K**

The key insight:

**We only need to maintain the K largest elements seen so far.**

We don't need the remaining elements because they cannot affect the kth largest element.

Let's understand why a Min Heap is useful.

A Min Heap gives us:

- The smallest element at the root.
- Efficient insertion: `O(log K)`.
- Efficient removal of the smallest element: `O(log K)`.
- Efficient access to the smallest element: `O(1)`.

If we maintain exactly K largest elements, the smallest element among those K elements is precisely the kth largest element overall.

### **Visual intuition**

Suppose:

```
k = 3
nums = [4, 5, 8, 2]
```

We maintain a Min Heap of size at most 3.

After processing all initial elements:

```
       5
      / \
     8   4
```

The heap contains:

```
[4, 5, 8]
```

The root is `4`.

Why?

Because these are the three largest elements:

```
8, 5, 4
```

The smallest among them is `4`, which is the third largest overall.

Now add `10`.

Before insertion:

```
Heap = [4, 5, 8]
```

Insert `10`:

```
Heap temporarily contains [4, 5, 8, 10]
```

Remove the smallest element (`4`):

```
Heap = [5, 8, 10]
```

Now the root is `5`.

Therefore, the third largest element is `5`.

### **The invariant**

This is the most important thing to remember during the interview:

**At all times, the Min Heap contains the K largest elements encountered so far, or all elements if fewer than K have been encountered.**

Consequently:

```
minHeap.peek()
```

always gives us the kth largest element whenever at least K elements exist.

## **3. Edge cases to watch out for**

| Edge case                                | Expected behavior                                |
| ---------------------------------------- | ------------------------------------------------ |
| `nums` is empty                          | Heap starts empty.                               |
| Initially fewer than K elements          | Return the smallest element currently available. |
| Duplicate values                         | Count duplicates independently.                  |
| Negative values                          | Handle normally using natural integer ordering.  |
| Incoming value smaller than heap minimum | It should be discarded.                          |
| Incoming value greater than heap minimum | Replace the heap minimum.                        |
| Exactly K elements                       | Return the smallest among them.                  |

One important detail: The problem constraints guarantee that after the first `add()` operation, there are at least K elements.

This means `peek()` will not return `null` when the problem's valid operations are followed.

# **4. All possible solutions**

## **Solution 1: Brute Force — Store everything and sort**

### **Intuition**

Maintain all the elements in a list.

Whenever a new value arrives:

1. Insert it into the list.
2. Sort the entire list in descending order.
3. Return the element at index `k - 1`.

```java
import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;

class KthLargest {

    private final int k;
    private final List<Integer> numbers;

    public KthLargest(int k, int[] nums) {
        this.k = k;
        this.numbers = new ArrayList<>();

        for (int num : nums) {
            numbers.add(num);
        }
    }

    public int add(int val) {

        // Add the incoming element to our collection.
        numbers.add(val);

        /*
         * Sort everything in descending order.
         *
         * Why?
         * The kth largest element will be at index k - 1.
         *
         * This is simple but inefficient because we sort
         * all previously encountered elements after every add().
         *
         * Time: O(N log N), where N is the current number of elements.
         */
        numbers.sort((a, b) -> Integer.compare(b, a));

        /*
         * Return the kth largest element.
         *
         * Since the problem guarantees at least k elements
         * after every add(), this index is valid.
         *
         * Time: O(1).
         */
        return numbers.get(k - 1);
    }
}
```

### **Complexity analysis**

Let:

- `N` = total number of elements currently encountered.
- `M` = number of elements in the initial array.

| Operation   | Time complexity |
| ----------- | --------------- |
| Constructor | `O(M)`          |
| add()       | `O(N log N)`    |
| Space       | `O(N)`          |

**Disadvantage:** We repeatedly sort elements that were already sorted during previous operations.

We can do better.

## **Solution 2: Better — Maintain a Sorted List**

### **Intuition**

Instead of sorting the entire list after every insertion, maintain the list in descending order.

For every incoming value:

1. Find its correct position using binary search.
2. Insert it at that position.
3. Return the element at index `k - 1`.

Binary search finds the insertion position in `O(log N)`, but inserting into an ArrayList still takes `O(N)` because elements need to be shifted.

```java
import java.util.ArrayList;
import java.util.List;

class KthLargest {

    private final int k;
    private final List<Integer> numbers;

    public KthLargest(int k, int[] nums) {
        this.k = k;
        this.numbers = new ArrayList<>();

        for (int num : nums) {
            addSorted(num);
        }
    }

    private void addSorted(int val) {

        /*
         * Find the insertion position.
         *
         * The list is maintained in descending order.
         * We insert after existing equal elements.
         *
         * Binary search takes O(log N).
         */
        int left = 0;
        int right = numbers.size();

        while (left < right) {

            int mid = left + (right - left) / 2;

            if (numbers.get(mid) >= val) {
                left = mid + 1;
            } else {
                right = mid;
            }
        }

        /*
         * Insert at the correct position.
         *
         * ArrayList may shift O(N) elements.
         *
         * Therefore, insertion is O(N), despite binary search.
         */
        numbers.add(left, val);
    }

    public int add(int val) {

        addSorted(val);

        /*
         * Return the kth largest element.
         * Index k - 1 represents the kth largest value.
         */
        return numbers.get(k - 1);
    }
}
```

### **Complexity analysis**

| Operation   | Time complexity |
| ----------- | --------------- |
| Constructor | `O(M²)`         |
| add()       | `O(N)`          |
| Space       | `O(N)`          |

**Improvement:** We eliminated repeated sorting.

**Remaining problem:** We still maintain all elements, even though we only care about the K largest.

## **Solution 3: Optimal — Min Heap of Size K**

This is the solution I would recommend in an interview.

### **Java 24 implementation**

```java
import java.util.PriorityQueue;

class KthLargest {

    /*
     * We only maintain the K largest elements.
     *
     * Why PriorityQueue?
     * Java's PriorityQueue implements a Min Heap by default.
     *
     * The smallest element is always available at the root.
     *
     * Our invariant:
     * The heap contains at most K largest elements encountered so far.
     *
     * Therefore:
     * heap.peek() = kth largest element, when heap size >= K.
     */
    private final PriorityQueue<Integer> minHeap;

    /*
     * Fixed rank that we need to maintain.
     */
    private final int k;

    public KthLargest(int k, int[] nums) {

        this.k = k;

        /*
         * Create a Min Heap.
         *
         * We don't need to specify a custom comparator because
         * PriorityQueue<Integer> is already a Min Heap.
         *
         * Initial heap size = 0.
         */
        this.minHeap = new PriorityQueue<>();

        /*
         * Process all initial elements using the same add() logic.
         *
         * This is useful because we don't need separate initialization
         * logic and insertion logic.
         *
         * Every element is processed while preserving our invariant.
         */
        for (int num : nums) {
            add(num);
        }
    }

    public int add(int val) {

        /*
         * Step 1: Insert the incoming value.
         *
         * Insertion into a Min Heap takes O(log K)
         * when the heap contains at most K + 1 elements.
         */
        minHeap.offer(val);

        /*
         * Step 2: Ensure heap size does not exceed K.
         *
         * If heap size becomes K + 1:
         *
         * Remove the smallest element.
         *
         * Why?
         *
         * We only want the K largest elements.
         * The smallest among K + 1 elements cannot belong
         * to the K largest elements.
         *
         * poll() removes the root in O(log K).
         */
        if (minHeap.size() > k) {
            minHeap.poll();
        }

        /*
         * Step 3: Return the root.
         *
         * The heap contains:
         * - All elements, if fewer than K elements exist.
         * - Exactly K largest elements, otherwise.
         *
         * When the heap contains K elements,
         * its minimum is the kth largest element.
         *
         * peek() takes O(1).
         */
        return minHeap.peek();
    }
}
```

### **Dry run of the optimal solution**

Input:

```
k = 3
nums = [4, 5, 8, 2]
```

**Constructor execution**

| Incoming number | Heap after insertion | Action   | Result |
| --------------- | -------------------- | -------- | ------ |
| 4               | [4]                  | Nothing  | —      |
| 5               | [4, 5]               | Nothing  | —      |
| 8               | [4, 5, 8]            | Nothing  | —      |
| 2               | [2, 4, 8, 5]         | Remove 2 | —      |

Heap now contains:

```
[4, 5, 8]
```

**add() execution**

| Incoming | Heap before removal | Removed | Heap after removal | Return |
| -------- | ------------------- | ------- | ------------------ | ------ |
| 3        | [3, 4, 8, 5]        | 3       | [4, 5, 8]          | 4      |
| 5        | [4, 5, 8, 5]        | 4       | [5, 5, 8]          | 5      |
| 10       | [5, 5, 8, 10]       | 5       | [5, 8, 10]         | 5      |
| 9        | [5, 8, 10, 9]       | 5       | [8, 9, 10]         | 8      |
| 4        | [4, 8, 10, 9]       | 4       | [8, 9, 10]         | 8      |

Output:

```
[4, 5, 5, 8, 8]
```

### **Complexity analysis**

Let:

- `M` = initial number of elements.
- `K` = requested rank.
- `N` = total number of elements encountered.

**Constructor**

We process M elements using `add()`.

Each insertion and potential removal costs `O(log K)`.

Therefore:

- Time: `O(M log K)`
- Auxiliary space: `O(K)`

**add(val)**

| Operation                  | Complexity |
| -------------------------- | ---------- |
| Insert into Min Heap       | `O(log K)` |
| Check heap size            | `O(1)`     |
| Remove minimum if required | `O(log K)` |
| Retrieve minimum           | `O(1)`     |

Overall:

- Time: `O(log K)` per call.
- Auxiliary space: `O(K)`.

**Total space:** `O(K)` instead of `O(N)`.

This is the optimal approach for maintaining the kth largest element in a stream.

## **5. Why Min Heap and not Max Heap?**

This is a very common interviewer question.

Suppose:

```
k = 3

Numbers = [4, 5, 8, 2, 10, 9]
```

We only need:

```
[8, 9, 10]
```

The smallest element among these three is `8`.

Therefore, we want efficient access to the smallest element among the K largest elements.

A Min Heap provides exactly that.

| Property           | Min Heap                      | Max Heap                         |
| ------------------ | ----------------------------- | -------------------------------- |
| Root               | Smallest element              | Largest element                  |
| Access kth largest | Directly possible with size K | Requires removing k - 1 elements |
| Insertion          | `O(log K)`                    | `O(log N)` if storing everything |
| Space              | `O(K)`                        | `O(N)` if storing everything     |

**Remember this mental model:**

- kth largest → Min Heap of size K.
- kth smallest → Max Heap of size K.

## **6. Interviewer follow-up questions**

### **Q1. Why do we remove the smallest element when heap size exceeds K?**

Because we only want to retain the K largest elements.

If we have K + 1 elements, the smallest among them cannot be part of the K largest elements.

Removing it preserves our invariant.

### **Q2. What happens when duplicate values arrive?**

Duplicates are counted independently.

For example:

```
k = 3
nums = [5, 5, 5, 8]
```

The three largest elements are:

```
[8, 5, 5]
```

The answer is `5`.

Java's `PriorityQueue` supports duplicate values, so no special handling is required.

### **Q3. Why not use a Set?**

A Set removes duplicates.

But duplicates must count as separate elements when calculating the kth largest element.

Therefore, a Set would produce incorrect results.

### **Q4. Can we build the initial heap more efficiently?**

Yes.

Instead of inserting each initial element individually, we could:

1. Copy all initial elements into a collection.
2. Construct a PriorityQueue from that collection.
3. Remove elements until its size becomes K.

However, this initially constructs a heap of size M, requiring `O(M)` space.

The incremental approach in our solution keeps space at `O(K)` throughout initialization.

### **Q5. What if K is equal to 1?**

We need the largest element.

A Min Heap of size 1 maintains only the maximum element encountered so far.

For example:

```
k = 1
nums = [4, 5, 8, 2]

add(10) -> 10
add(3)  -> 10
add(15) -> 15
```

### **Q6. What if K is greater than the number of elements?**

The heap contains all available elements, and the solution returns the smallest available element.

The actual LeetCode constraints guarantee at least K elements after each `add()` operation, so the returned value is always valid.

### **Q7. Can we solve this using a Max Heap?**

Yes.

Maintain all elements in a Max Heap and remove the largest `k - 1` elements to obtain the kth largest.

However, this is less efficient:

- Space: `O(N)`.
- Insertion: `O(log N)`.
- Finding kth largest: `O(k log N)` if we use a temporary heap copy or destructive extraction.

The Min Heap of size K is preferable.

## **7. Final interview summary**

| Approach            | Constructor  | add()        | Space  |
| ------------------- | ------------ | ------------ | ------ |
| Brute force sorting | `O(M)`       | `O(N log N)` | `O(N)` |
| Sorted ArrayList    | `O(M²)`      | `O(N)`       | `O(N)` |
| Min Heap of size K  | `O(M log K)` | `O(log K)`   | `O(K)` |

### **What you should remember**

The entire problem boils down to one observation:

**To find the kth largest element, we don't need all N elements. We only need the K largest elements.**

Maintain those K elements in a Min Heap.

The root of that heap is always the kth largest element.

```java
minHeap.offer(val);

if (minHeap.size() > k) {
    minHeap.poll();
}

return minHeap.peek();
```

This three-step pattern is the core of the solution and is frequently useful in streaming problems involving kth largest elements, top K elements, and maintaining running rankings.
