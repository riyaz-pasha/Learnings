# Chapter 5 — System Design and Interview Preparation

This is the final chapter of the Message Outbox Pattern course. We'll bring together the database transaction, relay, Kafka, consumer idempotency, retry handling, ordering, and operational concerns into one production-oriented design.

We'll use an e-commerce order workflow as the running example and finish with interview questions covering common design trade-offs.

## 1. Design a production order-processing system

Suppose an e-commerce platform has these services:

- Order Service: Creates and manages orders.
- Inventory Service: Reserves products.
- Payment Service: Charges customers.
- Notification Service: Sends order confirmations.
- Kafka: Transports events between services.
- PostgreSQL: Stores the business data owned by each service.

The requirement is that an order must not be committed without a durable record of its creation event, even if Kafka is temporarily unavailable.

Each service owns its own business database. The Order Service does not directly modify the Inventory Service's database, and the Inventory Service does not depend on being called synchronously during the order-creation transaction.

### What happens when a customer creates an order?

1. The Order Service begins a PostgreSQL transaction.
2. It inserts the order in `orders`.
3. It inserts `OrderCreated` into `outbox_events`.
4. Both records commit together.
5. The API returns a successful response after that transaction commits.
6. The relay publishes the event to Kafka.
7. Downstream services consume the event and perform their own transactions.

The database commit is the point at which the order and its event record become durable, subject to the configured database durability guarantees.

Importantly, an HTTP success response at this point does not necessarily mean that inventory has been reserved or payment has completed. Those are separate asynchronous business steps.

## 4. Outbox pattern vs. Saga pattern

These patterns are often confused because both are used in distributed systems, but they solve different problems.

### Transactional Outbox

The outbox solves the problem of reliably publishing an event after a local database change.

For example:

```
Order Service:
    BEGIN
        Insert order
        Insert OrderCreated into outbox
    COMMIT

Later:
    Publish OrderCreated to Kafka
```

It does not coordinate all business operations across services.

### Saga

A Saga coordinates a business workflow that spans multiple services, using a sequence of local transactions and, when required, compensating actions.

Interview takeaway: The outbox improves reliable messaging. The Saga manages a multi-service business process. They are complementary patterns, not competing alternatives.

A Kafka transaction can atomically commit the relevant output records and input offsets according to Kafka's transaction semantics.

But the database outbox flow is different:

```
PostgreSQL transaction
        ↓
Kafka publication
        ↓
PostgreSQL published_at update
```

The PostgreSQL transaction and Kafka transaction are separate unless a supported distributed coordination mechanism explicitly spans those resources.

Kafka producer idempotence can reduce duplicate records caused by producer retries within its supported scope. Kafka transactions can provide atomic visibility for Kafka records and offsets. Neither feature automatically eliminates the outbox relay's crash window between publishing to Kafka and updating the PostgreSQL outbox row.

That is why an outbox consumer should still be prepared for duplicate events.

## 7. Event schema evolution: what changes when your application evolves?

Suppose version 1 of `OrderCreated` looks like this:

```
{
  "eventId": "evt-101",
  "orderId": "ord-101",
  "customerId": "cus-101",
  "totalAmount": 1250.00
}
```

Later, the business decides to support multiple currencies. Version 2 adds a `currency` field:

```
{
  "eventId": "evt-101",
  "orderId": "ord-101",
  "customerId": "cus-101",
  "totalAmount": 1250.00,
  "currency": "INR"
}
```

What happens when an older consumer receives the newer payload?

The answer depends on the serialization format, deserialization configuration, and consumer implementation.

An event contract should therefore be designed for compatibility.

Useful practices include:

- Add optional fields when older consumers can safely tolerate them.
- Give new fields sensible defaults where appropriate.
- Avoid changing the meaning or type of existing fields without a compatible migration.
- Version events or schemas when compatibility cannot be preserved.
- Use schema governance or a schema registry where it provides value.
- Retain enough information to replay old events using a compatible consumer.

A stored outbox payload is a historical event record, not simply a live serialization of the current entity. Avoid reconstructing old events from current database state during relay retries, because the entity may have changed since the event was created.

## 8. Observability: how do we know the system is healthy?

A message can be safely stored and still remain unpublished for hours if a relay is broken. Reliable design therefore needs clear operational signals.

### Important metrics

| Metric                                | What it tells you                                       |
| ------------------------------------- | ------------------------------------------------------- |
| Outbox backlog size                   | How many events still need publication                  |
| Oldest pending event age              | Whether messages are stuck                              |
| Publication success and failure rate  | Whether the relay is healthy                            |
| Retry count and rate                  | Whether transient or persistent failures are increasing |
| Kafka consumer lag                    | Whether downstream consumers are keeping up             |
| End-to-end business latency           | How long an order takes to reach the required state     |
| CDC connector health, when applicable | Whether change capture is progressing                   |

### What alerts matter most?

An increasing backlog alone may not be a failure if the system is processing a temporary burst. A more actionable signal is the age of the oldest pending event combined with the rate at which new events are produced and processed.

Alert thresholds should reflect business requirements. For example, a fulfillment service may require event delivery within seconds, while a reporting pipeline might tolerate delays of several minutes.

## 9. An end-to-end production design checklist

Before shipping an outbox implementation, work through each boundary.

### Database transaction

- Are the business record and outbox event written in the same local transaction?
- Do both repositories use the same transactional database and transaction manager?
- Is the event payload constructed from the correct business facts?
- Does the event have a stable, unique identifier?

### Relay or CDC

- Can pending events survive application and broker restarts?
- Can the relay safely handle multiple workers?
- Are retries bounded or scheduled according to an explicit policy?
- Can operators find and replay failed events?
- Is the outbox backlog monitored?
- Is there a retention policy that preserves recoverable work?

### Consumer

- Is the consumer idempotent?
- Does it commit its business change and deduplication record together?
- Does it acknowledge the message only after the business transaction succeeds?
- Does it have a strategy for poison events and out-of-order messages?

### Business workflow

- Is the API success response defined clearly?
- Does the system distinguish `ORDER_CREATED` from `ORDER_CONFIRMED`?
- Are compensation and cancellation rules defined where necessary?
- Are eventual consistency and user-visible delays acceptable?

## 10. Common interview questions and strong answers

### Q1. What problem does the Transactional Outbox Pattern solve?

It solves the dual-write problem. A service needs to persist business data and publish a corresponding event, but the database and message broker do not normally share one atomic transaction. The outbox writes the business change and event record in a single database transaction, then publishes the event asynchronously.

### Q2. Does the outbox guarantee that a message is published exactly once?

No. The relay can publish successfully and crash before recording the publication result. A retry may publish the same event again. The usual solution is reliable retries and idempotent consumers.

### Q3. Why not publish to Kafka first and then save the database record?

If Kafka accepts the message and the subsequent database transaction fails, consumers may process an event for a business record that does not exist. Reversing the order produces the opposite failure window. The outbox makes the business change and its event intent atomic.

### Q4. What happens when Kafka is down?

The business transaction can still commit the order and its outbox event, assuming PostgreSQL remains available and has sufficient capacity. The relay retries publication after Kafka recovers. The growing backlog must be monitored and managed.

### Q5. How do you implement a scalable outbox relay?

Start with indexed, bounded batches and short transactions. For concurrent polling workers, use atomic claims, such as PostgreSQL's `FOR UPDATE SKIP LOCKED`, combined with persistent leases if work needs to remain claimed after the transaction ends. Add backoff, recovery, metrics, and safe cleanup. Consider CDC when it better fits the workload.

### Q6. How would you prevent duplicate processing in a consumer?

Use the event ID as a stable idempotency key. In the same transaction as the consumer's business change, insert that ID into a table with a unique constraint. If the insert conflicts, skip the already-processed event. This protects database effects inside that transaction.

### Q7. When should you use CDC instead of polling?

Use CDC when its operational infrastructure is justified by the required latency, throughput, or database polling overhead. Debezium can capture committed PostgreSQL changes from the WAL and route outbox events to Kafka. CDC still requires connector monitoring, recovery, retention management, and duplicate-safe consumers.

### Q8. How does the outbox relate to the Saga pattern?

The outbox reliably publishes events associated with a local database transaction. A Saga coordinates a business workflow consisting of local transactions across multiple services and potentially compensating actions. A Saga can use the outbox at each service boundary.

### Q9. What if strict event ordering is required?

Assign reliable per-aggregate sequence numbers, prevent later events from being published before earlier required events, and use the aggregate ID as the Kafka key. Kafka preserves record order within a partition, but the relay itself must publish in the required order. Failed earlier events may block later events for the same aggregate.

### Q10. Can Kafka transactions solve the entire database-to-broker dual-write problem?

Not by themselves. Kafka transactions can atomically coordinate supported Kafka operations, such as output records and consumed offsets. They do not automatically include a PostgreSQL transaction in the same atomic commit. The outbox avoids requiring that cross-resource atomicity for the initial business change and event intent.

## 11. A final design exercise

Suppose you are asked this interview question:

> Design an order service that creates orders in PostgreSQL and publishes `OrderCreated` events to Kafka. The system must not lose events if Kafka is unavailable, must tolerate duplicate delivery, and should support multiple relay instances.

A strong solution is:

1. Use a PostgreSQL transaction to insert the order and its outbox event.
2. Use a polling relay with indexed pending-event queries and safe atomic claiming, or use CDC with Debezium.
3. Publish events to Kafka and record publication success only after successful broker acknowledgment.
4. Use retry policies and recovery mechanisms for failures.
5. Deduplicate events in each consumer using a unique event ID, committing the deduplication record with the consumer's business changes.
6. Monitor backlog age, retry rate, consumer lag, and publication failures.
7. Add explicit sequence enforcement if per-aggregate ordering is a requirement.
8. Document the recovery, replay, and retention procedures.

### How to handle the failure window in your answer

The interviewer may challenge you with:

“What if Kafka accepts the message, but the relay crashes before updating the outbox row?”

Your answer should be:

> The message may be published again after recovery because the database status does not prove whether Kafka accepted the previous attempt. We favor retryable, at-least-once publication, give the event a stable ID, and make consumers idempotent. This prevents a duplicate delivery from repeating the same database business effect. We do not claim exactly-once behavior across PostgreSQL, Kafka, and arbitrary external systems.

That answer demonstrates an understanding of the actual guarantee, rather than only the happy-path implementation.
