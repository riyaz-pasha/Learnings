# 2. Open/Closed Principle — OCP

**O = Open/Closed Principle**

The classic definition is:

> **Software entities should be open for extension but closed for modification.**

This is one of those SOLID definitions that sounds simple but is easy to misunderstand.

So let's build it from the problem first.

---

# 1. What problem does OCP solve?

Imagine you have this:

```java
public class PaymentService {

    public void processPayment(String type, double amount) {

        if (type.equals("CREDIT_CARD")) {
            // credit card payment
        } 
        else if (type.equals("PAYPAL")) {
            // PayPal payment
        }
    }
}
```

Today you support:

```text
CREDIT_CARD
PAYPAL
```

Tomorrow the business says:

> Add UPI.

So you modify:

```java
else if (type.equals("UPI")) {
    // UPI payment
}
```

Then:

> Add Apple Pay.

Modify the same class again.

Then:

> Add Google Pay.

Modify it again.

So every new payment type requires changing the existing code.

That's the problem OCP tries to address.

---

# 2. The key idea

Instead of writing:

```java
if (type == A)
    do A;
else if (type == B)
    do B;
else if (type == C)
    do C;
```

we want to design the system so that:

```text
Existing code
    ↓
doesn't need to change

New behavior
    ↓
can be added separately
```

That's:

```text
OPEN for extension
CLOSED for modification
```

Meaning:

### Open for extension

We should be able to introduce new behavior.

### Closed for modification

We should not have to keep changing stable, already-tested code every time new behavior is introduced.

---

# 3. First understand what “closed for modification” does NOT mean

This is important.

It does **not** mean:

> “Never modify existing code.”

Obviously existing requirements can change.

OCP means something more specific:

> **Design stable parts of the system so that common kinds of new behavior can be added without modifying those stable parts.**

That's much more realistic.

---

# 4. The classic bad example

Suppose we calculate discounts.

```java
public class DiscountCalculator {

    public double calculate(String customerType, double price) {

        if (customerType.equals("REGULAR")) {
            return price * 0.05;
        }

        if (customerType.equals("PREMIUM")) {
            return price * 0.10;
        }

        if (customerType.equals("VIP")) {
            return price * 0.20;
        }

        return 0;
    }
}
```

Looks fine initially.

But now:

```text
REGULAR
PREMIUM
VIP
```

are supported.

Business says:

> Add GOLD customers with 15% discount.

We modify:

```java
if (customerType.equals("GOLD")) {
    return price * 0.15;
}
```

Again:

> Add STUDENT.

Modify again.

Again:

> Add CORPORATE.

Modify again.

The class keeps growing.

---

# 5. Why is this dangerous?

Suppose:

```java
if (customerType.equals("PREMIUM")) {
    return price * 0.10;
}
```

has already been tested thoroughly.

Now you're asked to add:

```text
CORPORATE
```

You change the same class.

The more code you touch, the greater the chance of accidentally breaking existing functionality.

This gives us a major OCP benefit:

> **Reduce the regression risk caused by adding new behavior.**

---

# 6. Using abstraction

Let's define:

```java
public interface DiscountStrategy {

    double calculateDiscount(double price);
}
```

Now each discount type implements it.

```java
public class RegularDiscount implements DiscountStrategy {

    @Override
    public double calculateDiscount(double price) {
        return price * 0.05;
    }
}
```

```java
public class PremiumDiscount implements DiscountStrategy {

    @Override
    public double calculateDiscount(double price) {
        return price * 0.10;
    }
}
```

```java
public class VipDiscount implements DiscountStrategy {

    @Override
    public double calculateDiscount(double price) {
        return price * 0.20;
    }
}
```

And our calculator depends on the abstraction:

```java
public class DiscountCalculator {

    public double calculate(
            DiscountStrategy strategy,
            double price) {

        return strategy.calculateDiscount(price);
    }
}
```

Now we want:

```text
GOLD
```

We don't need to modify `DiscountCalculator`.

We simply add:

```java
public class GoldDiscount implements DiscountStrategy {

    @Override
    public double calculateDiscount(double price) {
        return price * 0.15;
    }
}
```

That's the essence of OCP.

# 7. Compare the two designs

## ❌ Before

```text
DiscountCalculator
        |
        +-- REGULAR
        +-- PREMIUM
        +-- VIP
        +-- GOLD
        +-- STUDENT
        +-- CORPORATE
```

Every new type modifies:

```text
DiscountCalculator
```

---

## ✅ After

```text
             DiscountStrategy
                    ↑
        -------------------------
        ↑        ↑       ↑      ↑
     Regular  Premium   VIP   Gold
```

The existing abstraction remains stable.

New implementations can be added.

This is:

```text
Extension
    ↓
new class
```

rather than:

```text
Extension
    ↓
modify old class
```

# 8. Why interfaces are commonly used for OCP

Java gives us:

```java
interface
abstract class
inheritance
polymorphism
composition
```

These mechanisms allow us to program against abstractions.

For example:

```java
public interface NotificationSender {

    void send(String message);
}
```

Implementations:

```java
public class EmailSender implements NotificationSender {

    @Override
    public void send(String message) {
        System.out.println("Sending email");
    }
}
```

```java
public class SmsSender implements NotificationSender {

    @Override
    public void send(String message) {
        System.out.println("Sending SMS");
    }
}
```

Then:

```java
public class NotificationService {

    private final NotificationSender sender;

    public NotificationService(NotificationSender sender) {
        this.sender = sender;
    }

    public void notify(String message) {
        sender.send(message);
    }
}
```

Tomorrow:

```java
public class PushNotificationSender implements NotificationSender {

    @Override
    public void send(String message) {
        System.out.println("Sending push notification");
    }
}
```

`NotificationService` doesn't need to know about it.

That's OCP through polymorphism.

---

# 9. A very important word: Polymorphism

OCP is closely associated with polymorphism.

Instead of:

```java
if (type.equals("EMAIL")) {
    sendEmail();
} else if (type.equals("SMS")) {
    sendSms();
}
```

we use:

```java
sender.send(message);
```

The object itself determines the behavior.

For example:

```text
sender
  |
  +-- EmailSender → send()
  |
  +-- SmsSender → send()
  |
  +-- PushSender → send()
```

Same interface.

Different behavior.

That's exactly what polymorphism gives us.


Then:

```text
Add Razorpay
```

Modify `PaymentService`.

```text

```

# 11. Apply OCP

Create abstraction:

```java
public interface PaymentProcessor {

    void pay(double amount);
}
```

Implementations:

```java
public class CardPaymentProcessor
        implements PaymentProcessor {

    @Override
    public void pay(double amount) {
        System.out.println("Processing card: " + amount);
    }
}
```

```java
public class UpiPaymentProcessor
        implements PaymentProcessor {

    @Override
    public void pay(double amount) {
        System.out.println("Processing UPI: " + amount);
    }
}
```

```java
public class PaypalPaymentProcessor
        implements PaymentProcessor {

    @Override
    public void pay(double amount) {
        System.out.println("Processing PayPal: " + amount);
    }
}
```

Service:

```java
public class PaymentService {

    private final PaymentProcessor processor;

    public PaymentService(PaymentProcessor processor) {
        this.processor = processor;
    }

    public void pay(double amount) {
        processor.pay(amount);
    }
}
```

Now add Stripe:

```java
public class StripePaymentProcessor
        implements PaymentProcessor {

    @Override
    public void pay(double amount) {
        System.out.println("Processing Stripe: " + amount);
    }
}
```

The core `PaymentService` remains unchanged.

---

# 12. “But something still has to change!”

Excellent observation.

You might say:

> “When I add `StripePaymentProcessor`, somewhere I still have to create it. So isn't something being modified?”

Yes.

OCP does **not** imply literally zero modifications anywhere.

The idea is to isolate **stable behavior** from **variable behavior**.

For example:

```java
PaymentProcessor processor =
        new StripePaymentProcessor();
```

is new wiring/configuration.

The existing payment-processing logic doesn't need modification.

This distinction is important.

# 13. OCP with Spring Boot

This is where OCP becomes very practical.

Suppose:

```java
public interface PaymentProcessor {

    void pay(double amount);
}
```

Spring implementations:

```java
@Component
public class CardPaymentProcessor
        implements PaymentProcessor {

    @Override
    public void pay(double amount) {
    }
}
```

```java
@Component
public class UpiPaymentProcessor
        implements PaymentProcessor {

    @Override
    public void pay(double amount) {
    }
}
```

Spring can inject implementations depending on your design.

For a larger system, you might have:

```java
public interface PaymentProcessor {

    boolean supports(String type);

    void pay(double amount);
}
```

Implementation:

```java
@Component
public class UpiPaymentProcessor
        implements PaymentProcessor {

    @Override
    public boolean supports(String type) {
        return "UPI".equals(type);
    }

    @Override
    public void pay(double amount) {
        System.out.println("UPI payment");
    }
}
```

Another:

```java
@Component
public class CardPaymentProcessor
        implements PaymentProcessor {

    @Override
    public boolean supports(String type) {
        return "CARD".equals(type);
    }

    @Override
    public void pay(double amount) {
        System.out.println("Card payment");
    }
}
```

And Spring can inject:

```java
List<PaymentProcessor>
```

into a service.

For example:

```java
@Service
public class PaymentService {

    private final List<PaymentProcessor> processors;

    public PaymentService(List<PaymentProcessor> processors) {
        this.processors = processors;
    }

    public void pay(
            String type,
            double amount) {

        PaymentProcessor processor =
                processors.stream()
                        .filter(p -> p.supports(type))
                        .findFirst()
                        .orElseThrow(
                                () -> new IllegalArgumentException(
                                        "Unsupported payment type"));

        processor.pay(amount);
    }
}
```

Now adding:

```java
@Component
public class PaypalPaymentProcessor
        implements PaymentProcessor {
    
    ...
}
```

doesn't require changing the service.

That's an extremely practical OCP pattern in Spring Boot.

# 14. Strategy Pattern and OCP

You will often see OCP implemented through the **Strategy Pattern**.

The general structure is:

```text
Context
   |
   ↓
Strategy interface
   ↑
   |
-------------------------
|          |            |
StrategyA StrategyB StrategyC
```

Example:

```java
public interface ShippingStrategy {

    double calculateCost(Order order);
}
```

Then:

```java
public class StandardShipping implements ShippingStrategy {
    public double calculateCost(Order order) {
        return 50;
    }
}
```

```java
public class ExpressShipping implements ShippingStrategy {
    public double calculateCost(Order order) {
        return 150;
    }
}
```

```java
public class InternationalShipping implements ShippingStrategy {
    public double calculateCost(Order order) {
        return 500;
    }
}
```

Your main logic works against:

```java
ShippingStrategy
```

rather than knowing every possible shipping type.

That makes adding strategies easy.

# 15. Example: Area calculation

Classic interview example.

## ❌ Bad design

```java
public class AreaCalculator {

    public double calculate(Object shape) {

        if (shape instanceof Circle) {

            Circle circle = (Circle) shape;

            return Math.PI *
                    circle.getRadius() *
                    circle.getRadius();
        }

        if (shape instanceof Rectangle) {

            Rectangle rectangle = (Rectangle) shape;

            return rectangle.getWidth() *
                    rectangle.getHeight();
        }

        return 0;
    }
}
```

Suppose we add:

```text
Triangle
Pentagon
Hexagon
```

We keep modifying:

```java
AreaCalculator
```

That's not scalable.

---

# 16. Better design

Define:

```java
public interface Shape {

    double area();
}
```

Circle:

```java
public class Circle implements Shape {

    private final double radius;

    public Circle(double radius) {
        this.radius = radius;
    }

    @Override
    public double area() {
        return Math.PI * radius * radius;
    }
}
```

Rectangle:

```java
public class Rectangle implements Shape {

    private final double width;
    private final double height;

    public Rectangle(double width, double height) {
        this.width = width;
        this.height = height;
    }

    @Override
    public double area() {
        return width * height;
    }
}
```

Calculator:

```java
public class AreaCalculator {

    public double calculate(Shape shape) {
        return shape.area();
    }
}
```

Now:

```java
public class Triangle implements Shape {

    private final double base;
    private final double height;

    public Triangle(double base, double height) {
        this.base = base;
        this.height = height;
    }

    @Override
    public double area() {
        return 0.5 * base * height;
    }
}
```

No changes to:

```java
AreaCalculator
```

This is the classic OCP example.

# 19. Is `if/else` always an OCP violation?

**No.**

This is very important.

Seeing:

```java
if (...)
```

doesn't automatically mean the code violates OCP.

For example:

```java
public class UserService {

    public void updateUser(User user) {

        if (user == null) {
            throw new IllegalArgumentException();
        }

        ...
    }
}
```

That's not an OCP problem.

The issue is typically a conditional that repeatedly grows as **new variants of behavior** are introduced.

For example:

```java
if (paymentType == CARD)
if (paymentType == UPI)
if (paymentType == PAYPAL)
if (paymentType == STRIPE)
if (paymentType == ...
```

That's a stronger OCP smell.

# 21. But don't use OCP everywhere

This is one of the most important practical lessons.

Suppose you have:

```java
public enum Direction {
    NORTH,
    SOUTH,
    EAST,
    WEST
}
```

and:

```java
switch (direction) {
    case NORTH:
        ...
        break;
    case SOUTH:
        ...
        break;
    ...
}
```

Maybe that's perfectly fine.

Why?

Because you know the set of cases is:

```text
closed and stable
```

You don't expect users to add arbitrary directions at runtime.

Creating:

```text
NorthStrategy
SouthStrategy
EastStrategy
WestStrategy
```

might simply create unnecessary complexity.

OCP is about identifying **where variation is expected**.

# 22. Expected variation is the key

This is a more advanced understanding of OCP.

Ask:

> **What part of my application is likely to change or have new variants?**

Suppose:

```text
Payment methods
```

change frequently.

Then create an abstraction:

```java
PaymentProcessor
```

Suppose:

```text
DayOfWeek
```

is stable.

You don't necessarily need six classes.

So:

> **Don't abstract everything. Abstract the things that are likely to vary.**

This is extremely important in real software development.

# 23. OCP and abstraction

You can think of the design like this:

```text
                Stable
                  ↑
             Abstraction
                  ↑
        ---------------------
        |         |         |
     Variant A Variant B Variant C
```

The abstraction represents the stable contract.

Concrete implementations represent the things that vary.

That's why you'll often hear:

> **“Identify what varies and encapsulate it.”**

That's a major object-oriented design idea.

# 26. OCP vs SRP

Since we just learned SRP, compare them.

### SRP asks:

> **How many reasons does this class have to change?**

### OCP asks:

> **When new behavior is needed, do we need to keep modifying existing stable code?**

Example:

```java
public class PaymentService {

    if (type == CARD) ...
    if (type == UPI) ...
    if (type == PAYPAL) ...
}
```

### SRP problem

The class may contain multiple responsibilities related to different payment behaviors.

### OCP problem

Adding another payment type forces us to modify the existing service.

The two principles are related, but they address different problems.

---

# 27. OCP vs polymorphism

These aren't synonyms.

### Polymorphism

A Java language/OOP mechanism.

For example:

```java
PaymentProcessor processor =
        new UpiPaymentProcessor();

processor.pay(100);
```

### OCP

A design principle saying:

> Design the system so new behavior can be added with minimal modification to stable existing code.

Polymorphism is **one of the major techniques used to achieve OCP**.

# 28. OCP with composition

You don't necessarily need inheritance.

This:

```java
public interface DiscountStrategy {
    double calculate(double amount);
}
```

and:

```java
public class DiscountService {

    private final DiscountStrategy strategy;

    public DiscountService(DiscountStrategy strategy) {
        this.strategy = strategy;
    }
}
```

uses **composition**.

This is often preferable to building deep inheritance hierarchies.

So in modern Java:

```text
OCP
   ↓
abstraction
   ↓
polymorphism
   ↓
often composition/Strategy
```

# 30. A warning: OCP can be over-engineered

Suppose you're asked to support:

```text
2 types
```

and those types will never change.

You might create:

```text
StrategyFactory
StrategyRegistry
AbstractStrategy
StrategyFactoryProvider
StrategyResolver
```

Now you've created 10 classes for a simple problem.

That's not good design.

OCP doesn't say:

> “Use interfaces everywhere.”

It says:

> **Design for extension where variation is meaningful and likely.**

# 31. The “switch vs polymorphism” interview discussion

Interviewer:

> “Would you always replace switch statements with polymorphism?”

Answer:

> **No.** A switch is perfectly appropriate when the set of cases is small, stable, and unlikely to change. Polymorphism is more useful when new variants of behavior are expected to be added frequently.

That's a very good answer.

# 32. Another interview question: “How do you achieve OCP in Java?”

A good answer:

> “I typically identify behavior that is likely to vary and place it behind an abstraction such as an interface or abstract class. Then the stable code depends on that abstraction, while new behavior is implemented as new classes. I commonly use polymorphism, composition, and patterns like Strategy to achieve this.”

That's better than simply saying:

> “Use interfaces.”

# 33. Interview example: Payment

A strong answer would look like:

**Open/Closed Principle says that software should be open for extension but closed for modification.**

The idea is that when a new variant of behavior is introduced, we should be able to add it without repeatedly modifying stable, existing code.

For example, suppose a `PaymentService` contains a large `if/else` or `switch` for CARD, UPI, PayPal, and other payment types. Every time a new payment method is introduced, we have to modify and retest the same service.

Instead, I would define a `PaymentProcessor` interface and create separate implementations such as `CardPaymentProcessor`, `UpiPaymentProcessor`, and `PaypalPaymentProcessor`. The service depends on the `PaymentProcessor` abstraction.

When a new payment method such as Stripe is introduced, I can add a `StripePaymentProcessor` without changing the core payment-processing logic.

In Java, I commonly achieve OCP using interfaces, polymorphism, composition, and the Strategy pattern.

The main benefits are easier extension, reduced regression risk, better testability, and better separation between stable and changing parts of the system.

```text
Easier maintenance
Better extensibility
Better testability
Lower coupling
```

# 35. Interview question: “Give me a bad code example”

Use this:

```java
public class PaymentService {

    public void process(String type, double amount) {

        if ("CARD".equals(type)) {
            // ...
        }
        else if ("UPI".equals(type)) {
            // ...
        }
        else if ("PAYPAL".equals(type)) {
            // ...
        }
    }
}
```

Then explain:

> “This becomes difficult to extend because every new payment type requires modifying the existing service.”

Then show:

```java
public interface PaymentProcessor {
    void process(double amount);
}
```

and implementations.

That is usually enough to demonstrate that you understand OCP.

# 36. The deeper idea behind OCP

This is perhaps the most important part.

OCP is not really about:

```text
adding classes
```

It's about recognizing that software has:

```text
STABLE PARTS
        +
CHANGING PARTS
```

For example:

```text
Stable:
PaymentService contract

Changing:
Card payment
UPI payment
PayPal payment
Stripe payment
```

We want:

```text
Stable part
     ↓
depends on abstraction
     ↓
Changing implementations
```

rather than:

```text
Stable part
     ↓
knows every current and future variant
```

That's the architectural thinking behind OCP.

---

# 37. A useful mental model

Whenever you see this:

```java
if (type == A) {
   ...
}
else if (type == B) {
   ...
}
else if (type == C) {
   ...
}
```

ask yourself:

> **“Is this conditional likely to grow because new variants of this behavior will keep being added?”**

If yes:

```text
Consider abstraction + polymorphism
```

If no:

```text
Simple conditional may be perfectly fine
```

That's a much more mature application of OCP.

# 38. SRP + OCP together

Let's combine what we've learned.

Suppose:

```java
public class PaymentService {

    public void process(String type) {

        if ("CARD".equals(type)) {
            // card logic
        }
        else if ("UPI".equals(type)) {
            // UPI logic
        }
    }

    public void sendEmail() {
    }

    public void saveToDatabase() {
    }
}
```

Problems:

### SRP

Too many unrelated responsibilities:

```text
payment
email
database
```

### OCP

New payment types require modifying the service.

After applying both:

```text
PaymentService
     |
     +-- PaymentProcessor abstraction
              |
        -------------------
        |        |        |
      Card      UPI     PayPal

EmailService
     ↓
email responsibility

PaymentRepository
     ↓
persistence responsibility
```

This is where SOLID principles start working together.

# 39. One important trap: “Closed for modification” can conflict with changing requirements

Suppose the business changes the fundamental payment process:

```text
Old:
Pay → Save

New:
Reserve → Fraud Check → Pay → Save → Settlement
```

Of course you may need to modify existing orchestration code.

That's okay.

OCP is not an absolute law saying:

```text
NEVER MODIFY OLD CODE
```

It's about designing likely extension points so that **new variations** don't force unnecessary modification of stable code.

---

# 40. OCP cheat sheet

```text
OPEN/CLOSED PRINCIPLE
        |
        +-- Open for extension
        |      ↓
        |   Add new behavior
        |
        +-- Closed for modification
               ↓
          Don't keep changing
          stable existing code
```

Typical tools:

```text
Interfaces
Abstract classes
Polymorphism
Composition
Strategy Pattern
Dependency Injection
```

Typical smells:

```text
Growing switch statements
Long if/else chains
Type checking
Adding new cases requires modifying old class
```

Main benefits:

```text
Extensibility
Lower regression risk
Maintainability
Testability
Lower coupling
```

# 41. SRP vs OCP — memorize this

| Principle | Main question                                                     |
| --------- | ----------------------------------------------------------------- |
| **SRP**   | “Does this class have more than one reason to change?”            |
| **OCP**   | “Can I add a new variant without modifying stable existing code?” |

So:

```text
SRP → responsibility
OCP → extensibility
```

---

# 42. One sentence to remember

For SRP, remember:

> **One reason to change.**

For OCP, remember:

> **Add new behavior by extending the system rather than repeatedly modifying stable existing code.**

# 43. Your interview-level understanding of OCP should reach this point

When an interviewer gives you:

```java
if (type.equals("A")) ...
else if (type.equals("B")) ...
else if (type.equals("C")) ...
```

you shouldn't automatically say:

> “OCP violation.”

Instead say:

> “I'd first determine whether these branches represent behavior that is expected to grow. If new variants are likely to be added frequently, I'd consider extracting the varying behavior behind an interface and use polymorphism or a Strategy-style design. That lets new implementations be added without modifying the stable core logic.”

**That sounds much more like someone who understands SOLID rather than someone who has memorized SOLID.**
