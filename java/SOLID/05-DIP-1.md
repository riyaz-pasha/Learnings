## What it says

> **A. High-level modules should not depend on low-level modules. Both should depend on abstractions.**
> **B. Abstractions should not depend on details. Details should depend on abstractions.** (Robert C. Martin)

Definitions:
- **High-level module:** business logic, the "what" and the "why" (`OrderService`, `CheckoutService`).
- **Low-level module:** implementation details, the "how" (MySQL access, SMTP email, file I/O, a specific payment gateway).
- **Abstraction:** an interface or abstract class.

Normally, the high-level code calls the low-level code directly, so the arrow of dependency points **down**, from policy to detail. DIP **inverts** that arrow: the high-level module *owns* an interface, and the low-level module *implements* it.

```
Before:   OrderService ───────────► MySqlOrderRepository
          (high-level)               (low-level)

After:    OrderService ──► OrderRepository (interface) ◄── MySqlOrderRepository
                           (owned by high-level side)       (low-level implements it)
```

The source-code dependency now points **up**, toward the abstraction, which is why it's called *inversion*.

---

## Important: DIP vs. DI vs. IoC (interviewers love this trap)

These three are related but **not the same thing**:

| Term | What it is |
|---|---|
| **DIP** (Dependency Inversion **Principle**) | A **design principle**: depend on abstractions, not concretions. |
| **DI** (Dependency **Injection**) | A **technique**: pass dependencies in from outside (constructor, setter) instead of creating them with `new` inside. It is one way to achieve DIP. |
| **IoC** (Inversion of Control) | A broader **idea**: a framework/container controls object creation and flow instead of your code. Spring is an IoC container that performs DI. |

Relationship: **IoC container (Spring) → does DI → which helps you follow DIP.** You can do DI without following DIP (injecting a concrete class), and you can follow DIP without a framework.

## 1. Why do we need it? (The problem)

When business logic does `new MySqlDatabase()` or `new SmtpEmailSender()` inside itself:

1. **Tight coupling:** business rules are welded to specific technologies. Switching MySQL to MongoDB means rewriting business logic.
2. **Untestable:** to unit test `OrderService`, you need a real database and real SMTP server. Tests become slow, flaky, and require infrastructure.
3. **Not reusable:** the business logic can't be used in another context (a batch job, a different app) without dragging its dependencies along.
4. **Ripple effects:** a change in a low-level detail (a new email API version) forces changes in high-level policy code.
5. **Blocks parallel work:** teams can't build the service until the database layer exists.
6. **Violates OCP:** to add a new implementation, you must edit the high-level class.

## 2. When do we need it?

- When a class **creates its own collaborators** with `new`.
- When business logic touches **I/O boundaries**: database, network, filesystem, clock, random numbers, external APIs.
- When you want to **swap implementations** (real vs. fake, MySQL vs. Postgres, SMTP vs. SendGrid).
- When you need **fast unit tests** without infrastructure.
- When you have **layers** (controller → service → repository) and don't want inner layers to know outer details.

## 3. How does it solve the problem?

Three steps:

1. **Define an interface** that expresses what the high-level module *needs* (in the high-level module's language).
2. **Make the low-level class implement** that interface.
3. **Pass the implementation in** from outside (constructor injection), so the high-level class never says `new ConcreteThing()`.

## Example 1: `OrderService` and the database (the classic)

### ❌ Violation

```java
public class MySqlOrderRepository {
    public void save(Order order) {
        System.out.println("Saving to MySQL: " + order);
    }
}

public class OrderService {
    // High-level class creates and depends on the concrete low-level class
    private final MySqlOrderRepository repository = new MySqlOrderRepository();

    public void placeOrder(Order order) {
        // business rules...
        repository.save(order);
    }
}
```

Problems:
- Switch to PostgreSQL or MongoDB? Edit `OrderService`.
- Unit test `placeOrder`? It hits the real MySQL code.
- `OrderService` is stuck with one technology forever.

### ✅ Fix

```java
// 1. Abstraction, owned by the high-level side
public interface OrderRepository {
    void save(Order order);
}

// 2. Low-level details implement the abstraction
public class MySqlOrderRepository implements OrderRepository {
    public void save(Order order) { System.out.println("Saving to MySQL: " + order); }
}

public class MongoOrderRepository implements OrderRepository {
    public void save(Order order) { System.out.println("Saving to Mongo: " + order); }
}

// 3. High-level class depends only on the abstraction, injected via constructor
public class OrderService {
    private final OrderRepository repository;

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }

    public void placeOrder(Order order) {
        // business rules...
        repository.save(order);
    }
}
```

Wiring (only in one place, the "composition root"):

```java
OrderService service = new OrderService(new MySqlOrderRepository());
// tomorrow: new OrderService(new MongoOrderRepository());  OrderService is untouched
```

### The testing payoff

```java
class InMemoryOrderRepository implements OrderRepository {
    final List<Order> saved = new ArrayList<>();
    public void save(Order order) { saved.add(order); }
}

@Test
void placeOrder_savesOrder() {
    InMemoryOrderRepository fake = new InMemoryOrderRepository();
    OrderService service = new OrderService(fake);

    service.placeOrder(new Order());

    assertEquals(1, fake.saved.size());   // fast, no DB, no setup
}
```

## Example 2: Notification service (multiple dependencies)

### ❌ Violation

```java
public class EmailSender {
    public void send(String to, String msg) { System.out.println("Email: " + msg); }
}

public class NotificationService {
    private EmailSender emailSender = new EmailSender();     // hard-wired

    public void notifyUser(String user, String message) {
        emailSender.send(user, message);
    }
}
```

The business asks for **SMS**, then **push notifications**, then **Slack**. Every request means editing `NotificationService`.

### ✅ Fix

```java
public interface MessageSender {
    void send(String to, String message);
}

public class EmailSender implements MessageSender {
    public void send(String to, String msg) { System.out.println("Email to " + to + ": " + msg); }
}
public class SmsSender implements MessageSender {
    public void send(String to, String msg) { System.out.println("SMS to " + to + ": " + msg); }
}

public class NotificationService {
    private final MessageSender sender;

    public NotificationService(MessageSender sender) { this.sender = sender; }

    public void notifyUser(String user, String message) {
        sender.send(user, message);
    }
}
```

```java
new NotificationService(new EmailSender());
new NotificationService(new SmsSender());
```

Notice how DIP is what makes **OCP** work here: the service is closed for modification because it depends on an abstraction.

## Example 3: Hidden dependencies (the clock, the randomizer)

Not all dependencies are "big" ones like databases. Time and randomness make code untestable too.

### ❌ Violation

```java
public class SubscriptionService {
    public boolean isExpired(Subscription s) {
        return LocalDate.now().isAfter(s.getEndDate());   // hidden dependency on the system clock
    }
}
```

How do you test "expired on Dec 31"? You can't control `now()`.

### ✅ Fix (Java already provides the abstraction: `java.time.Clock`)

```java
public class SubscriptionService {
    private final Clock clock;

    public SubscriptionService(Clock clock) { this.clock = clock; }

    public boolean isExpired(Subscription s) {
        return LocalDate.now(clock).isAfter(s.getEndDate());
    }
}
```

```java
// Production
new SubscriptionService(Clock.systemDefaultZone());

// Test: freeze time
Clock fixed = Clock.fixed(Instant.parse("2026-12-31T00:00:00Z"), ZoneOffset.UTC);
new SubscriptionService(fixed);
```

## Example 4: Spring Boot (the real-world form)

```java
public interface PaymentGateway {
    PaymentResult charge(String customerId, double amount);
}

@Component
public class StripeGateway implements PaymentGateway {
    public PaymentResult charge(String customerId, double amount) { /* call Stripe */ return null; }
}

@Service
public class CheckoutService {
    private final PaymentGateway gateway;             // abstraction

    public CheckoutService(PaymentGateway gateway) {  // Spring injects StripeGateway
        this.gateway = gateway;
    }
}
```

Spring's container finds a `PaymentGateway` implementation and injects it. To swap providers, you replace the bean (or use `@Profile` / `@Primary` / `@Qualifier`), and `CheckoutService` doesn't change.

**Prefer constructor injection** over field injection (`@Autowired` on a field):
- Dependencies are explicit and `final`.
- The class can be built in a plain unit test with no Spring.
- It can't be created in an invalid, half-wired state.

## Example 5: Layered architecture (where the interface lives matters)

A subtle but important point: **the abstraction should be owned by the high-level module**, not the low-level one.

```
com.shop.domain            (high-level: business rules)
   ├── Order
   ├── OrderService
   └── OrderRepository    ← interface lives HERE, with the business logic

com.shop.infrastructure    (low-level: details)
   └── JpaOrderRepository implements OrderRepository
```

Dependency direction: `infrastructure → domain`. The domain package has **zero imports** from `infrastructure`, JPA, or Spring Web. This is the heart of Clean/Hexagonal Architecture ("ports and adapters"): the domain defines ports (interfaces), and the infrastructure provides adapters.

If instead the interface sits in the infrastructure package and the domain imports it, you've added an interface but not truly inverted the dependency.

## DIP in the JDK and frameworks

- **JDBC:** your code depends on `Connection`, `Statement`, `ResultSet` (interfaces); MySQL, Postgres, and Oracle supply the implementations via drivers.
- **SLF4J:** code logs through the `Logger` interface, and Logback or Log4j2 plugs in underneath.
- **`java.util.Collection` types:** declaring `List<String> x = new ArrayList<>()` depends on the abstraction, not `ArrayList`.
- **`Clock`, `Executor`, `Comparator`:** the JDK hands you abstractions for time, threading, and ordering.
- **Servlet API:** containers (Tomcat, Jetty) implement it, and your code targets the interface.

## Smells that signal a DIP violation

- `new` keyword for collaborators inside business classes (`new MySqlDatabase()`, `new SmtpClient()`)
- Business classes importing `java.sql.*`, `javax.mail.*`, `org.apache.http.*`
- Static calls to singletons: `Database.getInstance()`, `EmailUtil.send(...)`
- Unit tests that need a DB, network, or filesystem
- Field declarations of concrete types: `private MySqlRepo repo;`
- `LocalDateTime.now()` or `new Random()` buried in business logic
- Changing a technology forces edits in domain code

## Don't over-apply it (interviewers love this)

- **Don't put an interface in front of everything.** Value objects, DTOs, `String`, `List`, simple utilities, and stable JDK classes don't need inversion.
- **Abstract volatile or external dependencies:** databases, network calls, third-party APIs, clocks, and anything you'd want to fake in tests.
- **Interface with exactly one implementation and no test/swap need** is often just noise. (Though "I need a fake in tests" *is* a valid second implementation.)
- **Beware of leaky abstractions:** an interface method like `executeSqlQuery(String sql)` names a detail. Design abstractions in **business terms** (`findOverdueOrders()`), not technology terms.
- **Too many layers of indirection** make code hard to trace.

## Common misconceptions

| Myth | Truth |
|---|---|
| "DIP = Dependency Injection" | DI is a technique to achieve DIP; DIP is the principle. |
| "DIP = Spring" | Spring helps, but plain constructors work fine. |
| "Injecting a concrete class satisfies DIP" | If the field type is a concrete class, you still depend on the detail. |
| "Interface in the same package as the implementation is enough" | Ownership matters: the high-level module should own the abstraction. |
| "Everything must be an interface" | Only volatile or boundary dependencies. |
| "Inversion means dependencies go from bottom to top" | It means source-code dependencies point toward abstractions, opposite to the runtime call flow. |

## How it ties all five principles together

| Principle | Role in the story |
|---|---|
| **SRP** | Gives you small, focused classes worth abstracting. |
| **OCP** | Goal: add behavior without editing. DIP is the *mechanism* that makes it possible. |
| **LSP** | Guarantees the implementations you plug in behave correctly. |
| **ISP** | Keeps the abstractions small and client-shaped. |
| **DIP** | Wires it together: high-level code depends on those abstractions, with details injected. |

One sentence to remember: **SRP splits the code, ISP shapes the interfaces, LSP keeps implementations honest, DIP wires them together, and OCP is the payoff.**

## How to explain DIP in an interview

**30-second answer:**

> "The Dependency Inversion Principle says high-level modules shouldn't depend on low-level modules; both should depend on abstractions. For example, if `OrderService` creates `new MySqlOrderRepository()` inside itself, business logic is tied to MySQL and I can't unit test it without a database. I define an `OrderRepository` interface owned by the business layer, make `MySqlOrderRepository` implement it, and inject it through the constructor. Now I can swap to Mongo without touching `OrderService`, and in tests I pass an in-memory fake. It's related to but different from Dependency Injection: DIP is the principle, DI is a technique to achieve it, and Spring's IoC container automates the injection. I'd apply it at boundaries like databases, external APIs, and time, not to every class."

**Order to follow:** Definition (both parts) → Violation (`new` inside a service) → Fix (interface + constructor injection) → Testing benefit → DIP vs DI vs IoC → Caveat (don't abstract everything).

**Likely follow-ups:**

1. **"DIP vs DI vs IoC?"** Principle vs. technique vs. broader control-flow idea (see the table above).
2. **"Why is it called 'inversion'?"** Without it, source dependencies follow the call flow (high → low). With it, the low-level module depends on an interface owned by the high level, so the dependency direction is inverted.
3. **"Constructor vs setter vs field injection?"** Constructor is preferred: immutability, mandatory dependencies, easy testing. Setter is for optional dependencies. Field injection hides dependencies and needs reflection or Spring to test.
4. **"How does DIP help testing?"** You inject fakes or mocks (Mockito), so unit tests are fast and isolated.
5. **"Who should own the interface?"** The high-level (client) module, not the implementation module.
6. **"Does DIP require a framework?"** No. Manual constructor injection in a `main` method (the composition root) works.
7. **"What's the composition root?"** The single place (usually `main` or a Spring config class) where concrete objects are created and wired.
8. **"Can DIP be overdone?"** Yes: interfaces for every class add noise. Abstract volatile boundaries only.
9. **"How does DIP relate to OCP?"** DIP is how you achieve OCP: depend on abstractions so new implementations plug in without edits.
10. **"How does Spring resolve multiple implementations of one interface?"** `@Primary`, `@Qualifier`, `@Profile`, or injecting a `List<T>` / `Map<String, T>` of all of them.

## 🎓 You've completed all five principles

**Master cheat sheet:**

| Principle | One-line rule | Smell | Main fix |
|---|---|---|---|
| **SRP** | One reason to change | God classes, "and" in descriptions | Split by actor/responsibility |
| **OCP** | Extend without editing | `switch`/`if-else`/`instanceof` on type | Interface + polymorphism (Strategy) |
| **LSP** | Subtypes must be substitutable | `UnsupportedOperationException`, `instanceof` | Fix hierarchy, composition, capability interfaces |
| **ISP** | No forced unused methods | Empty/throwing implementations | Small role interfaces |
| **DIP** | Depend on abstractions | `new Concrete()` in business logic | Interface owned by high-level + constructor injection |

**A closing interview tip:** if asked to explain SOLID as a whole, don't recite five definitions. Tell one story: *"I start with an `OrderService` that does everything (SRP violation). I split it into focused classes (SRP). I put interfaces between them so new payment types plug in without edits (OCP). I make sure every implementation honors the interface contract (LSP), keep those interfaces small (ISP), and inject the implementations rather than creating them (DIP)."* It shows you understand how the principles work *together*, which is what interviewers really want to see.
