## What it says

> **"Objects of a subclass should be usable anywhere the superclass is expected, without breaking the correctness of the program."** (Barbara Liskov, 1987)

If `B extends A`, then any code written for `A` must work correctly when handed a `B`, **without knowing it's a `B`**.

The key insight: **inheritance is not "is-a" in the real-world sense, it is "behaves-like-a".** A square *is a* rectangle in math, but a `Square` class may not *behave like* a `Rectangle` in code. LSP is about **behavior**, not just about compiling.

---

## 1. Why do we need it? (The problem)

Java's compiler only checks that method **signatures** match. It cannot check that the **behavior** matches. So you can write a subclass that compiles perfectly and still breaks every caller.

When LSP is violated:

1. **Polymorphism becomes unsafe:** code that takes `Base` must add `instanceof` checks or try/catch to survive certain subclasses.
2. **OCP collapses:** those `instanceof` checks are exactly the type-switching OCP told you to avoid.
3. **Surprise bugs at runtime:** `UnsupportedOperationException`, wrong results, or silent misbehavior appear far from the subclass that caused them.
4. **Tests lie:** tests pass for `Base` but fail for `Sub`, so you must test every subclass separately with special cases.

## 2. When do we need it?

- Any time you use **inheritance** (`extends`) or implement an **interface** and callers use the parent type.
- When designing **class hierarchies** and **library/framework extension points**.
- When you're tempted to override a method with an **empty body** or `throw new UnsupportedOperationException()`.
- When a subclass needs to **reject inputs** the parent accepted.

## 3. How does it solve the problem?

LSP is a **rule for designing hierarchies correctly**. A subclass must honor the parent's **contract**:

| Contract part | Rule for the subclass |
|---|---|
| **Preconditions** (what must be true before calling) | Cannot be **strengthened** (can't demand more) |
| **Postconditions** (what's guaranteed after) | Cannot be **weakened** (can't promise less) |
| **Invariants** (always-true facts about the object) | Must be **preserved** |
| **Exceptions** | Must not throw new unexpected exception types the parent didn't declare or imply |
| **History** | Must not make state changes the parent forbids (e.g., mutating an "immutable" parent) |

Easy memory trick: **a subclass may require less and promise more, never require more and promise less.**

When a subclass can't honor the contract, the fix is to **change the hierarchy**: separate abstractions, composition, or a smaller interface.

## Example 1: Rectangle and Square (the classic)

### ❌ Violation

```java
public class Rectangle {
    protected int width, height;

    public void setWidth(int width)   { this.width = width; }
    public void setHeight(int height) { this.height = height; }
    public int area()                 { return width * height; }
}

public class Square extends Rectangle {
    @Override public void setWidth(int w)  { this.width = w; this.height = w; }
    @Override public void setHeight(int h) { this.width = h; this.height = h; }
}
```

A client written against `Rectangle`:

```java
static void resize(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    System.out.println(r.area());   // Rectangle → 20 ✅
}

resize(new Rectangle());  // 20
resize(new Square());     // 16 ❌  (setHeight(4) overwrote width too)
```

**Why it breaks:** `Rectangle` has an implicit contract: *"setting width doesn't change height."* `Square` violates that postcondition. The client's reasonable assumption ("width=5, height=4, so area=20") fails.

### ✅ Fix: don't make one inherit from the other

```java
public interface Shape {
    int area();
}

public final class Rectangle implements Shape {
    private final int width, height;
    public Rectangle(int width, int height) { this.width = width; this.height = height; }
    public int area() { return width * height; }
}

public final class Square implements Shape {
    private final int side;
    public Square(int side) { this.side = side; }
    public int area() { return side * side; }
}
```

Both are `Shape`s and are substitutable **for what `Shape` promises**. Immutability removes the broken setters entirely.

> **Lesson:** "is-a" in the real world ≠ "is-a" in code. What matters is whether the subclass honors the **behavior** callers rely on.

## Example 2: Bird that can't fly

### ❌ Violation

```java
public class Bird {
    public void fly() { System.out.println("Flying..."); }
    public void eat() { System.out.println("Eating..."); }
}

public class Sparrow extends Bird { }

public class Penguin extends Bird {
    @Override
    public void fly() {
        throw new UnsupportedOperationException("Penguins can't fly!");
    }
}
```

```java
static void migrate(List<Bird> birds) {
    for (Bird b : birds) {
        b.fly();          // 💥 explodes on Penguin
    }
}
```

The "fix" people reach for is to patch the client: `if (!(b instanceof Penguin)) b.fly();`. That is an **LSP + OCP violation**, since every new flightless bird (Ostrich, Kiwi) needs another patch.

### ✅ Fix: model the capability honestly

```java
public abstract class Bird {
    public void eat() { System.out.println("Eating..."); }
}

public interface Flyable {
    void fly();
}

public class Sparrow extends Bird implements Flyable {
    public void fly() { System.out.println("Sparrow flying"); }
}

public class Penguin extends Bird {
    public void swim() { System.out.println("Penguin swimming"); }
}
```

```java
static void migrate(List<Flyable> flyers) {
    flyers.forEach(Flyable::fly);   // safe for everything in this list
}
```

Code that needs flying asks for `Flyable`, so a `Penguin` can never be passed in. **The compiler now enforces the contract.**

## Example 3: The "can't withdraw" account (`UnsupportedOperationException`)

### ❌ Violation

```java
public class BankAccount {
    protected double balance;

    public void deposit(double amount)  { balance += amount; }
    public void withdraw(double amount) { balance -= amount; }
}

public class FixedDepositAccount extends BankAccount {
    @Override
    public void withdraw(double amount) {
        throw new UnsupportedOperationException("Locked until maturity");
    }
}
```

```java
static void payBill(BankAccount account, double amount) {
    account.withdraw(amount);       // 💥 for FixedDepositAccount
}
```

**Red flag pattern:** a subclass that **removes** or **disables** a parent capability (empty body, or throws `UnsupportedOperationException`). Such a subclass is telling you the inheritance is wrong.

### ✅ Fix: split by capability

```java
public interface Account {
    void deposit(double amount);
    double getBalance();
}

public interface Withdrawable extends Account {
    void withdraw(double amount);
}

public class SavingsAccount implements Withdrawable {
    private double balance;
    public void deposit(double amount)  { balance += amount; }
    public void withdraw(double amount) {
        if (amount > balance) throw new IllegalArgumentException("Insufficient funds");
        balance -= amount;
    }
    public double getBalance() { return balance; }
}

public class FixedDepositAccount implements Account {
    private double balance;
    public void deposit(double amount) { balance += amount; }
    public double getBalance() { return balance; }
}
```

```java
static void payBill(Withdrawable account, double amount) {
    account.withdraw(amount);       // FixedDepositAccount can't even be passed
}
```

(This also previews **Interface Segregation**, our next lesson.)

## Example 4: Strengthening preconditions (subtle violation)

### ❌ Violation

```java
public interface NotificationSender {
    /** Sends any non-empty message. */
    void send(String message);
}

public class EmailSender implements NotificationSender {
    public void send(String message) {
        System.out.println("Email: " + message);
    }
}

public class SmsSender implements NotificationSender {
    public void send(String message) {
        if (message.length() > 160) {                      // ← stricter than the contract!
            throw new IllegalArgumentException("SMS too long");
        }
        System.out.println("SMS: " + message);
    }
}
```

A caller who reads the contract ("sends any non-empty message") passes a 500-character message. It works for email and crashes for SMS. `SmsSender` **strengthened the precondition**.

### ✅ Fix (two valid options)

**Option A: honor the contract by handling long messages internally:**

```java
public class SmsSender implements NotificationSender {
    public void send(String message) {
        for (int i = 0; i < message.length(); i += 160) {
            String part = message.substring(i, Math.min(i + 160, message.length()));
            System.out.println("SMS: " + part);
        }
    }
}
```

**Option B: make the limit part of the abstraction's contract**, so every implementation and caller knows about it:

```java
public interface NotificationSender {
    int maxLength();                 // callers can check this
    void send(String message);       // contract: message.length() <= maxLength()
}
```

Either way, no implementation surprises the caller.

## Example 5: Weakening postconditions

```java
public interface DiscountPolicy {
    /** Returns the price after discount: always between 0 and originalPrice. */
    double apply(double originalPrice);
}

// ❌ Breaks the postcondition: returns MORE than the original price
public class SurgeDiscount implements DiscountPolicy {
    public double apply(double originalPrice) {
        return originalPrice * 1.10;    // "discount" that raises price!
    }
}
```

Any checkout code that relies on "final price ≤ original price" is now wrong. The subclass **promised less** than the parent. A subclass may guarantee *more* (e.g., always at least 10% off), never less.

## LSP violations already in the JDK (great interview material)

- `Arrays.asList(...)` and `Collections.unmodifiableList(...)` return a `List`, but calling `add()` throws `UnsupportedOperationException`. Code written against `List` breaks. This is a well-known LSP compromise in the JDK.
- `java.util.Stack extends Vector`: a `Stack` lets you `insertElementAt(...)` in the middle, which breaks the LIFO invariant a stack promises. This is a classic bad-inheritance example (prefer `Deque`/`ArrayDeque`).
- `Properties extends Hashtable<Object,Object>`: you can `put(1, 2)` although `Properties` should hold only strings.

Saying "even the JDK has violations, and here's why" shows real depth.

## The compiler helps with signatures (but not behavior)

| Rule | Enforced by Java? |
|---|---|
| Parameter types can't be narrowed in override | ✅ (overload instead of override) |
| Return type may be narrower (covariant) | ✅ allowed |
| Can't throw broader **checked** exceptions | ✅ compile error |
| Can't throw new **unchecked** exceptions with different meaning | ❌ not enforced, this is where LSP bugs hide |
| Preconditions / postconditions / invariants | ❌ never enforced, it's on you |

---

## Smells that signal an LSP violation

- Overriding a method with an **empty body** or **`throw new UnsupportedOperationException()`**
- **`instanceof`** or `getClass()` checks on a parent-typed variable
- A subclass that **ignores** or **restricts** parameters the parent accepted
- Subclass tests need special-case logic that parent tests don't
- Javadoc like "*not supported in subclass X*"
- Deep inheritance hierarchies where subclasses override most parent methods

## How to design so you don't violate LSP

1. **Prefer composition over inheritance.** Use inheritance only for true behavioral substitutability.
2. **Keep base types small.** The fewer promises a parent makes, the easier it is for subclasses to keep them (leads into ISP).
3. **Write the contract down** (Javadoc for preconditions, postconditions, exceptions).
4. **Make classes `final` or immutable** where extension isn't designed for (Effective Java, Item 19).
5. **Ask "does it behave like it?"**, not "is it a kind of it?"
6. **Write a reusable contract test** that runs the same test suite against every implementation of an interface.

## Common misconceptions

| Myth | Truth |
|---|---|
| "LSP = inheritance must model real-world is-a" | It's about **behavioral** substitutability, not real-world taxonomy. |
| "If it compiles, it's fine" | The compiler can't check behavior. |
| "LSP only matters for classes" | It applies equally to **interface implementations**. |
| "Overriding is always OK" | Overriding is OK only if the contract is preserved. |
| "Throwing exceptions in subclasses is fine" | Only if the parent's contract allows those failures. |

---

## How does LSP relate to the earlier principles?

- **OCP depends on LSP.** OCP says "extend by adding new subclasses." That is only safe if those subclasses are truly substitutable. Break LSP and your "extension" breaks existing code.
- **LSP violations often cause SRP/ISP issues** too: fat base types force subclasses to implement things they can't support.

## How to explain LSP in an interview

**30-second answer:**

> "The Liskov Substitution Principle says that if `B` is a subtype of `A`, I should be able to use `B` anywhere I use `A` without breaking correctness. It's about behavior, not just method signatures: a subclass must honor the parent's contract, meaning it can't demand stricter preconditions, weaken postconditions, or break invariants. The classic example is `Square extends Rectangle`: `setWidth` on a square also changes height, so code that sets width 5 and height 4 expects area 20 but gets 16. Another is a `Penguin` extending `Bird` and throwing on `fly()`. The fix is to redesign the hierarchy, for example a `Shape` interface with immutable `Rectangle` and `Square`, or a separate `Flyable` interface. Red flags are `UnsupportedOperationException` overrides and `instanceof` checks."

**Order to follow:** Definition → "behavior, not just signature" → Classic example (Rectangle/Square) → Contract rules (pre/post/invariants) → Fix → Smells → OCP link.

**Likely follow-ups:**

1. **"How is LSP different from just polymorphism?"** Polymorphism is the language *mechanism*; LSP is the *discipline* that makes it safe to use.
2. **"What are the contract rules?"** Preconditions can't be strengthened, postconditions can't be weakened, invariants must hold, no unexpected exceptions.
3. **"How do you detect a violation?"** `UnsupportedOperationException`, empty overrides, `instanceof` checks in client code, subclass-specific test branches.
4. **"How would you fix it?"** Redesign: split interfaces by capability, use composition/delegation, or make types immutable.
5. **"Example in the JDK?"** `Collections.unmodifiableList().add()` throws; `Stack extends Vector`.
6. **"LSP vs OCP?"** OCP says extend via new subtypes; LSP guarantees those subtypes are safe to plug in.
7. **"Does covariant return violate LSP?"** No. Returning a more specific type is a *stronger* postcondition, which is allowed.
8. **"Composition or inheritance?"** Prefer composition; use inheritance only when substitutability truly holds.
