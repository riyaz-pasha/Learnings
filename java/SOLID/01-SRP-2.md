# 1. Single Responsibility Principle — SRP

**S = Single Responsibility Principle**

The classic definition is:

> **A class should have one reason to change.**

This is one of the most important definitions to understand for interviews.

A common but slightly misleading interpretation is:

> “A class should do only one thing.”

That is useful as a starting point, but **“one responsibility” does not necessarily mean “one method” or “one tiny operation.”**

The better question is:

> **Does this class have responsibilities that would change for different reasons?**

That is the heart of SRP.

---

# 1. Why do we need SRP?

Imagine this class:

```java
public class InvoiceService {

    public void createInvoice() {
        // create invoice
    }

    public void calculateTax() {
        // calculate tax
    }

    public void saveToDatabase() {
        // save invoice
    }

    public void generatePdf() {
        // generate PDF
    }

    public void sendEmail() {
        // send email
    }
}
```

At first glance, this may look convenient.

One class handles the entire invoice process.

But let's think about what can change.

The class could change because:

```text
Invoice creation rules changed
        ↓
Tax calculation changed
        ↓
Database implementation changed
        ↓
PDF format changed
        ↓
Email provider changed
```

These are **different reasons for change**.

That means this class has multiple responsibilities.

And that is exactly the problem SRP tries to prevent.

---

# 2. What is actually wrong with multiple responsibilities?

Suppose your application has:

```java
InvoiceService
```

and inside it:

```java
createInvoice()
calculateTax()
saveToDatabase()
generatePdf()
sendEmail()
```

Now the database team changes:

```text
MySQL → PostgreSQL
```

You modify the invoice class.

Then the company decides:

```text
PDF → HTML
```

Modify the same class again.

Then:

```text
Tax calculation changed
```

Modify the same class again.

Eventually this class becomes huge.

More importantly, changes become **coupled**.

A change in one area can accidentally affect another.

---

# 3. The main problem SRP solves

SRP tries to reduce:

### 1. Coupling

Unrelated responsibilities become dependent on one another.

### 2. Large classes

Classes become difficult to understand and maintain.

### 3. Difficult testing

Testing one responsibility requires dealing with many others.

### 4. Change impact

A change in one business area forces modifications elsewhere.

### 5. Merge conflicts

In a large team, many developers may modify the same class.

### 6. Reusability problems

A piece of functionality becomes difficult to reuse because it is trapped inside a large class.

---

# 4. The simplest way to understand SRP

Think about a restaurant.

Suppose one employee does:

```text
Take orders
Cook food
Wash dishes
Handle payments
Deliver food
Manage inventory
```

Technically, the restaurant could work.

But imagine the cooking rules change.

Why should the person responsible for payments need to change?

That's the same design problem in software.

We want related responsibilities together and unrelated responsibilities separated.

---

# 5. SRP example in Java

Let's start with a common bad design.

## ❌ Without SRP

```java
public class Employee {

    private String name;
    private double salary;

    public Employee(String name, double salary) {
        this.name = name;
        this.salary = salary;
    }

    public double calculateSalary() {
        return salary;
    }

    public void saveToDatabase() {
        System.out.println("Saving employee to database...");
    }

    public void generateReport() {
        System.out.println("Generating employee report...");
    }

    public void sendEmail() {
        System.out.println("Sending email...");
    }
}
```

What does `Employee` represent?

It represents:

```text
Employee data
Salary calculation
Database persistence
Report generation
Email communication
```

That's too much.

---

# 6. Applying SRP

We can split it.

```java
public class Employee {

    private String name;
    private double salary;

    public Employee(String name, double salary) {
        this.name = name;
        this.salary = salary;
    }

    public double calculateSalary() {
        return salary;
    }
}
```

Now `Employee` is responsible for employee-related business data/behavior.

Then:

```java
public class EmployeeRepository {

    public void save(Employee employee) {
        System.out.println("Saving employee to database...");
    }
}
```

Report:

```java
public class EmployeeReportGenerator {

    public void generate(Employee employee) {
        System.out.println("Generating employee report...");
    }
}
```

Email:

```java
public class EmployeeEmailService {

    public void send(Employee employee) {
        System.out.println("Sending employee email...");
    }
}
```

Now we have:

```text
Employee
    ↓
Employee business model

EmployeeRepository
    ↓
Persistence

EmployeeReportGenerator
    ↓
Reporting

EmployeeEmailService
    ↓
Email
```

Each has a much clearer reason to change.

# 7. Why “one responsibility” is NOT necessarily “one method”

Consider:

```java
public class OrderService {

    public void createOrder() {
        validate();
        calculateTotal();
        save();
    }

    private void validate() {
    }

    private void calculateTotal() {
    }

    private void save() {
    }
}
```

Some developers say:

> “This violates SRP because there are three methods.”

No.

The number of methods is not the point.

The question is whether these methods belong to the same responsibility.

For example:

```text
Order validation
Order total calculation
Order creation workflow
```

could reasonably belong to an order business service depending on your design.

SRP is about **responsibilities and reasons for change**, not method count.

---

# 8. “One reason to change” — understand this deeply

Let's take:

```java
public class InvoiceService {

    public Invoice createInvoice() {
        // business logic
    }

    public void sendInvoiceEmail() {
        // email logic
    }
}
```

There are two different stakeholders/business concerns.

```text
Business rules team
        ↓
Invoice creation

Infrastructure/communication concern
        ↓
Email
```

Suppose the invoice creation rules change.

You modify:

```java
InvoiceService
```

Suppose email provider changes:

```text
Gmail → SendGrid
```

You also modify:

```java
InvoiceService
```

So the same class changes for two unrelated reasons.

That is a strong signal that SRP is being violated.

---

# 9. A practical test for SRP

Whenever you see a class, ask:

### Question 1

> **What does this class do?**

Then list its responsibilities.

For example:

```text
UserService

- create user
- validate user
- save user
- send email
- generate PDF
- write audit log
```

That's suspicious.

Now ask:

### Question 2

> **Who would request changes to this class?**

Maybe:

```text
Business team
Database team
Email team
Reporting team
Security team
```

Multiple independent stakeholders are a very strong indication of multiple responsibilities.

This is sometimes called the **multiple actors** interpretation of SRP.

# 10. Real-world Java/Spring example

This comes up constantly in Spring Boot projects.

Suppose someone writes:

```java
@Service
public class UserService {

    public void registerUser(User user) {

        // validate user
        if (user.getEmail() == null) {
            throw new IllegalArgumentException("Email required");
        }

        // save
        userRepository.save(user);

        // send email
        emailClient.send(
            user.getEmail(),
            "Welcome!"
        );

        // generate audit log
        auditService.log("USER_CREATED");

        // generate PDF
        pdfService.generate(user);
    }
}
```

Is this necessarily terrible?

Not necessarily.

`UserService` may still be the **orchestrator** of the use case.

This is important for interviews.

SRP does **not** mean:

> “Every class must contain exactly one operation and never call anything else.”

Instead, the service can coordinate specialized components:

```java
@Service
public class UserService {

    private final UserRepository userRepository;
    private final EmailService emailService;
    private final AuditService auditService;

    public UserService(
            UserRepository userRepository,
            EmailService emailService,
            AuditService auditService) {

        this.userRepository = userRepository;
        this.emailService = emailService;
        this.auditService = auditService;
    }

    public void registerUser(User user) {

        validate(user);

        userRepository.save(user);

        emailService.sendWelcomeEmail(user);

        auditService.logUserCreated(user);
    }

    private void validate(User user) {
        if (user.getEmail() == null) {
            throw new IllegalArgumentException("Email required");
        }
    }
}
```

This can be perfectly reasonable.

Why?

Because the responsibility of `UserService` can be:

> **Coordinate the user registration use case.**

While:

```text
UserRepository
    → persistence

EmailService
    → email communication

AuditService
    → auditing
```

handle their own responsibilities.

# 11. Very important interview distinction

Interviewers may ask:

> “So should every class have only one method?”

Answer:

**No.**

A class can have multiple methods as long as they belong to a coherent responsibility and have a related reason to change.

For example:

```java
public class ShoppingCart {

    public void addItem(Product product) {
    }

    public void removeItem(Product product) {
    }

    public double calculateTotal() {
        return 0;
    }

    public int getItemCount() {
        return 0;
    }
}
```

This is fine.

All these methods relate to:

> **Managing the state and behavior of a shopping cart.**

```java
public class EmployeeReport {

    }
```

There are multiple concerns:

```text
Report formatting
File storage
Email delivery
```

Let's separate them.

```java
public class EmployeeReportGenerator {

    public String generate(Employee employee) {
        return employee.getName() + "," + employee.getSalary();

```

```java
public class ReportFileWriter {

    }

```

```java

    public void send(String report) {
        // send email
    }

```

Now consider:

```text
CSV format changes
```

Only:

```java
EmployeeReportGenerator
```

needs modification.

Or:

```text
File storage changes to S3
```

Only:

```java
ReportFileWriter
```

needs modification.

Or:

```text
Email provider changes
```

Only:

```java
ReportEmailSender
```

needs modification.

That's the real benefit.

# 13. Example: Payment system

Bad design:

```java
public class PaymentService {

    public void processPayment(double amount) {

        // validate card

        // call bank

        // store payment in database

        // generate receipt

        // send email

        // write audit log
    }
}
```

There are many responsibilities.

We could have:

```java
public class PaymentValidator {
}
```

```java
public class PaymentProcessor {
}
```

```java
public class PaymentRepository {
}
```

```java
public class ReceiptGenerator {
}
```

```java
public class PaymentEmailService {
}
```

```java
public class AuditLogger {
}
```

And then:

```java
public class PaymentService {

    private final PaymentValidator validator;
    private final PaymentProcessor processor;
    private final PaymentRepository repository;
    private final ReceiptGenerator receiptGenerator;
    private final PaymentEmailService emailService;

    public void processPayment(Payment payment) {

        validator.validate(payment);

        processor.process(payment);

        repository.save(payment);

        String receipt = receiptGenerator.generate(payment);

        emailService.send(receipt);
    }
}
```

Notice something subtle.

`PaymentService` still does several operations.

But its responsibility is:

> **Coordinate the payment use case.**

The details have been delegated.

That's good design.

# 15. SRP and maintainability

Consider two designs.

### Design A

```text
One huge class
    |
    +-- database
    +-- email
    +-- validation
    +-- reporting
    +-- calculations
    +-- logging
```

### Design B

```text
OrderService
    |
    +-- OrderValidator
    +-- OrderRepository
    +-- PricingService
    +-- EmailService
    +-- ReportGenerator
```

Now imagine:

```text
Pricing rules change
```

Design B makes the change much more localized.

That's what SRP gives us:

> **Change isolation.**

This is one of the most important benefits to mention in an interview.

# 17. SRP does NOT mean “make more classes everywhere”

This is another interview trap.

Suppose you have:

```java
public class UserName {

    private String value;

    public String getValue() {
        return value;
    }

    public String normalize() {
        return value.trim().toLowerCase();
    }
}
```

Someone might say:

> “SRP says `normalize()` must be moved to another class.”

No.

That's unnecessary decomposition.

Both operations are related to the responsibility represented by `UserName`.

SRP isn't about creating the maximum possible number of classes.

It is about creating **meaningful boundaries**.

# 18. The danger of over-applying SRP

Imagine:

```java

UserNameValidator
UserEmailValidator
UserAgeValidator
UserPhoneValidator
UserPersistence
UserEmailSender
UserMapper
UserFactory
UserService
UserResponseBuilder
```

For a tiny application, this could become ridiculous.

You now have 20 classes for simple behavior.

So SRP has to be applied with judgment.

The goal isn't:

```text

```

The goal is:

```text

+
low unnecessary coupling
+
easy change
+
maintainability
```

# 21. SRP and Spring Boot

You will see this constantly in real Spring applications.

A good separation might look like:

```text
Controller
   ↓
Service
   ↓
Repository
```

For example:

```java
@RestController
public class OrderController {

    private final OrderService orderService;

    @PostMapping("/orders")
    public OrderResponse createOrder(
            @RequestBody OrderRequest request) {

        return orderService.createOrder(request);
    }
}
```

The controller should primarily deal with:

```text
HTTP concerns
```

The service:

```text
Business/use-case concerns
```

The repository:

```text
Persistence concerns
```

This isn't a mechanical rule that every Spring project must use exactly these layers, but the separation often reflects SRP nicely.

# 22. SRP violation in a Controller

Suppose:

```java
@RestController
public class OrderController {

    @PostMapping("/orders")
    public String createOrder(OrderRequest request) {

        // validate request
        // calculate price
        // connect to database
        // generate PDF
        // send email
        // return response
    }
}
```

That's a bad design.

Why?

Because the controller has become responsible for:

```text
HTTP
validation
business logic
persistence
PDF generation
email
```

A better structure:

```text
OrderController
      ↓
OrderService
      ↓
OrderRepository
```

plus specialized collaborators where necessary.

This is where you should focus your thinking.

Suppose your old class is:

```java
public class InvoiceService {

    }

    public void saveInvoice() {
    }

    public void generatePdf() {
    }

    public void sendEmail() {
    }

```

Tomorrow:

```text
PDF library changes.
```

Because PDF logic is inside the same class, you modify `InvoiceService`.

Potentially you can break invoice creation or persistence.

With:

```java
}
```

```java

}
```

```java
}
```

the PDF library change is much more contained.

> **Making the software resilient to change.**

# 25. The “actor” approach

A more advanced way to understand SRP:

> **A class should have one group of actors/stakeholders that causes it to change.**

Imagine:

```java
public class EmployeeOperations {

    public void calculateSalary() {}

    public void saveEmployee() {}

    public void generateReport() {}
}
```

Potential stakeholders:

```text
HR/payroll
Database team
Management/reporting
```

Different groups want different changes.

So separating those concerns reduces the chance that one actor's changes affect another actor.

This is a more sophisticated explanation than simply saying:

> “One class should do one thing.”

# 27. How to identify an SRP violation in an existing project

During an interview, you can say you look for signals such as:

```text
1. Very large class
2. Too many unrelated methods
3. Multiple external dependencies
4. Multiple unrelated imports
5. Multiple business domains mixed together
6. Changes from unrelated requirements frequently hit same class
7. Difficult unit testing
8. Lots of if/else based on different concerns
```

For example:

```java
import java.sql.*;
import javax.mail.*;
import org.apache.pdfbox.*;
import org.json.*;
```

inside one business class isn't automatically wrong, but it can be a warning sign that several concerns are mixed together.

# 28. A refactoring example

Suppose we start with:

```java
public class OrderService {

    public void processOrder(Order order) {

        if (order.getItems().isEmpty()) {
            throw new IllegalArgumentException("Order is empty");
        }

        double total = 0;

        for (OrderItem item : order.getItems()) {
            total += item.getPrice() * item.getQuantity();
        }

        database.save(order);

        email.send(
            order.getCustomerEmail(),
            "Order placed"
        );
    }
}
```

We can refactor:

### Validation

```java
public class OrderValidator {

    public void validate(Order order) {
        if (order.getItems().isEmpty()) {
            throw new IllegalArgumentException("Order is empty");
        }
    }
}
```

### Pricing

```java
public class OrderPricingService {

    public double calculateTotal(Order order) {

        double total = 0;

        for (OrderItem item : order.getItems()) {
            total += item.getPrice() * item.getQuantity();
        }

        return total;
    }
}
```

### Persistence

```java
public class OrderRepository {

    public void save(Order order) {
        // database logic
    }
}
```

### Notification

```java
public class OrderNotificationService {

    public void sendConfirmation(Order order) {
        // email logic
    }
}
```

### Orchestration

```java
public class OrderService {

    private final OrderValidator validator;
    private final OrderPricingService pricingService;
    private final OrderRepository repository;
    private final OrderNotificationService notificationService;

    public void processOrder(Order order) {

        validator.validate(order);

        double total =
                pricingService.calculateTotal(order);

        order.setTotal(total);

        repository.save(order);

        notificationService.sendConfirmation(order);
    }
}
```

Now the architecture is much easier to reason about.

# 29. But here's an important subtlety

Don't blindly extract every private method into a new class.

For example:

```java
public class OrderService {

    public void createOrder(Order order) {
        validateCustomer(order);
        validateItems(order);
        calculateSomething(order);
        save(order);
    }

    private void validateCustomer(Order order) {}
    private void validateItems(Order order) {}
    private void calculateSomething(Order order) {}
    private void save(Order order) {}
}
```

This might still be completely reasonable.

We need to understand the **domain responsibility**.

If all those operations are part of:

> “Create an order”

then keeping them together can be appropriate.

SRP isn't:

```text
1 method → 1 class
```

It's:

```text
1 cohesive responsibility → 1 class
```

# 30. SRP vs separation of concerns

These terms are related but not identical.

### Separation of concerns

A broad software-design concept:

> Keep different concerns separated.

### SRP

A specific OO design principle:

> A class should have one reason to change.

For example:

```text
HTTP handling
Business logic
Database access
Email delivery
```

are different concerns.

SRP encourages us not to put all of those into one class.

# 32. What happens if we don't follow SRP?

Imagine a class:

```java
public class CustomerService {

    public void calculateDiscount() {}
    public void saveCustomer() {}
    public void sendEmail() {}
    public void generateInvoice() {}
    public void exportCsv() {}
```

Over time:

```text
                CustomerService
                       |
          ----------------------------
          |            |             |

```

Every new feature tends to increase the size of the same class.

Eventually:

```text
100 lines
   ↓
500 lines
   ↓
1000 lines
   ↓
2000 lines
```

Now developers become afraid to touch it.

That's exactly the kind of maintainability problem SOLID is intended to prevent.

# 34. Interview question: “Explain SRP”

A strong answer could be:

**Single Responsibility Principle says that a class should have one reason to change.**

It does not necessarily mean that a class can contain only one method. Instead, all the methods in a class should belong to one cohesive responsibility and be affected by the same kind of business or technical change.

For example, if an `Employee` class is responsible for employee data, database persistence, report generation, and email sending, it has multiple reasons to change. A database change, reporting change, or email-provider change could all require modifying the same class.

I would separate those concerns into classes such as `Employee`, `EmployeeRepository`, `EmployeeReportGenerator`, and `EmployeeEmailService`.

The main benefit is change isolation: when one responsibility changes, the impact is limited to the component responsible for that concern. It also improves testability, maintainability, and readability.

That is a good **60–90 second interview answer**.

```java
public class InvoiceService {
```

```java
    public void send(Invoice invoice) {
    }
}
```

Now each class has a clearer responsibility and a more focused reason to change.

---

# 36. Interview question: “When should you apply SRP?”

Don't answer:

> “Always create a separate class.”

A better answer:

> **Apply SRP when a class contains multiple independent responsibilities or when different kinds of changes repeatedly affect the same class.**

Typical signals:

```text
Large class
Unrelated methods
Multiple stakeholders
Hard-to-test code
Frequent unrelated changes
Many infrastructure concerns mixed with business logic
```

---

# 37. Interview question: “When shouldn't you split a class?”

This is an excellent senior-level discussion.

Don't split simply because:

```text
class is 100 lines
```

or:

```text
class has 10 methods
```

Instead consider:

```text
Are the methods cohesive?
Do they share the same reason to change?
Do they belong to the same domain concept?
Would splitting make the design clearer?
```

For example:

```java
public class ShoppingCart {

    addItem();
    removeItem();
    calculateTotal();
    clearCart();
    getItemCount();
}
```

These methods are strongly related.

Splitting them would probably make the design worse, not better.

---

# 38. A very important phrase: Cohesion

You will hear this term a lot in interviews.

### Cohesion

> How closely related the responsibilities inside a class are.

High cohesion:

```java
ShoppingCart

addItem()
removeItem()
calculateTotal()
clear()
```

All related.

Low cohesion:

```java
ShoppingCart

addItem()
sendEmail()
generatePdf()
connectToDatabase()
sendSms()
```

Not related.

So:

```text
SRP → encourages high cohesion
SRP → discourages unrelated responsibilities
```

---

# 39. SRP and coupling/cohesion

A good design generally tries to move toward:

```text
HIGH COHESION
+
LOW COUPLING
```

SRP primarily helps us improve cohesion by keeping related responsibilities together and helps reduce coupling by separating unrelated concerns.

You will see this concept repeatedly when learning SOLID.

---

# 40. One final example — the classic “God class”

Imagine:

```java
public class ApplicationManager {

    createUser();
    deleteUser();
    calculateSalary();
    generateInvoice();
    sendEmail();
    processPayment();
    connectDatabase();
    generatePdf();
    exportExcel();
}
```

This is often called a **God class** because it knows/does far too much.

A likely decomposition:

```text
UserService
PayrollService
InvoiceService
PaymentService
EmailService
PdfService
ExcelExporter
Repository layer
```

The point isn't the exact number of classes.

The point is that each class should own a coherent area of responsibility.

---

# 41. SRP cheat sheet

Remember this:

```text
SRP
│
├── What?
│   └── One responsibility per class
│
├── Better definition
│   └── One reason to change
│
├── Why?
│   ├── Maintainability
│   ├── Testability
│   ├── Lower coupling
│   └── Safer changes
│
├── Not this
│   └── One method per class
│
└── Look for
    ├── Large classes
    ├── Unrelated methods
    ├── Multiple stakeholders
    └── Multiple independent reasons to change
```

---

# 42. The easiest way to remember SRP

When you see a class, ask:

> **“If requirement A changes and requirement B changes, would I need to modify this same class for both?”**

If yes, investigate whether the class has multiple responsibilities.

And the most important interview sentence:

> **“SRP is about one reason to change, not one method.”**

That sentence is worth remembering.

```text
1. SRP ≠ one method per class

2. SRP = one reason to change

3. The goal is high cohesion and reduced impact of changes

4. A service can coordinate multiple operations without necessarily
   violating SRP, as long as those operations belong to one cohesive use case
```
