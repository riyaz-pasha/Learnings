# 3. Liskov Substitution Principle — LSP

**L = Liskov Substitution Principle**

The formal definition is:

> **Objects of a superclass should be replaceable with objects of its subclasses without breaking the correctness of the program.**

That's the definition to know.

But by itself, it can feel abstract.

The easiest way to understand LSP is:

> **If `B` is a subtype of `A`, then wherever the program expects an `A`, it should be safe to give it a `B`.**

Let's unpack that carefully.

---

# 1. Start with normal Java inheritance

Suppose we have:

```java
public class Bird {

    public void fly() {
        System.out.println("Flying");
    }
}
```

And:

```java
public class Sparrow extends Bird {
}
```

Then:

```java
Bird bird = new Sparrow();

bird.fly();
```

This works.

Why?

Because a `Sparrow` really behaves like a `Bird` in the context where `Bird` promises that it can `fly()`.

This is substitution.

```text
Bird reference
      ↓
Sparrow object
```

The caller doesn't need to care that the actual object is a `Sparrow`.

---

# 2. The classic LSP violation: Penguin

Now:

```java
public class Bird {

    public void fly() {
        System.out.println("Flying");
    }
}
```

Then:

```java
public class Penguin extends Bird {

    @Override
    public void fly() {
        throw new UnsupportedOperationException(
                "Penguins cannot fly"
        );
    }
}
```

Now:

```java
Bird bird = new Penguin();

bird.fly();
```

What happens?

```text
Runtime exception
```

The caller believed:

```text
Bird → can fly()
```

But `Penguin` cannot fulfill that behavior.

So although Java allows:

```java
Penguin extends Bird
```

the inheritance relationship is conceptually wrong.

This is the key idea of LSP.

---

# 3. Why is this a problem?

Consider:

```java
public void makeBirdFly(Bird bird) {
    bird.fly();
}
```

Now:

```java
makeBirdFly(new Sparrow());
```

works.

But:

```java
makeBirdFly(new Penguin());
```

breaks.

That means the subclass cannot safely replace the parent.

Therefore:

> **Penguin is not a valid subtype of this particular `Bird` abstraction.**

This is an important distinction.

It doesn't mean:

> “Penguin is not a bird.”

Of course it is.

It means:

> **Your `Bird` abstraction is poorly modeled because it promises a behavior that every bird does not support.**

---

# 4. The real problem is not inheritance itself

People often misunderstand LSP as:

> “Inheritance is dangerous.”

No.

Inheritance is perfectly valid when the subtype truly satisfies the contract of the parent.

For example:

```java
public class Animal {
    public void eat() {
        System.out.println("Eating");
    }
}
```

```java
public class Dog extends Animal {

    @Override
    public void eat() {
        System.out.println("Dog eating");
    }
}
```

This is fine.

```java
Animal animal = new Dog();

animal.eat();
```

The `Dog` fulfills the `Animal` contract.

So LSP is really about:

> **Behavioral correctness of subtypes.**

---

# 5. A better Bird design

Instead of:

```java
public class Bird {

    public void fly() {
    }
}
```

we could model:

```java
public class Bird {

    public void eat() {
        System.out.println("Eating");
    }
}
```

Then:

```java
public interface Flyable {

    void fly();
}
```

Sparrow:

```java
public class Sparrow extends Bird
        implements Flyable {

    @Override
    public void fly() {
        System.out.println("Sparrow flying");
    }
}
```

Penguin:

```java
public class Penguin extends Bird {
}
```

Now the model says:

```text
Bird
 |
 +-- Sparrow
 |      |
 |      +-- Flyable
 |
 +-- Penguin
```

That's much better.

The abstraction doesn't promise behavior that some subclasses can't provide.

---

# 6. LSP is about contracts

This is the deeper idea.

Suppose a parent class says:

```java
public class Account {

    public void withdraw(double amount) {
        // withdraw money
    }
}
```

The caller assumes:

```text
Account
    ↓
withdraw() is valid
```

Now imagine:

```java
public class FixedDepositAccount
        extends Account {

    @Override
    public void withdraw(double amount) {
        throw new UnsupportedOperationException();
    }
}
```

Again:

```java
Account account = new FixedDepositAccount();

account.withdraw(1000);
```

Breaks.

The subclass violates the contract expected by clients of `Account`.

That's an LSP violation.

---

# 7. “is-a” is not enough

This is one of the most important interview concepts.

People often say:

> “Inheritance represents an IS-A relationship.”

That's generally true, but incomplete.

For LSP, we need:

```text
B IS-A A
+
B can fulfill A's behavioral contract
```

Example:

```text
Penguin IS-A Bird
```

True biologically.

But:

```text
Penguin IS-A Bird-that-can-fly
```

False.

So if your `Bird` abstraction includes:

```java
fly()
```

you've made the abstraction too specific.

---

# 8. Another classic example: Rectangle and Square

This is one of the most famous LSP examples.

Suppose:

```java
public class Rectangle {

    protected int width;
    protected int height;

    public void setWidth(int width) {
        this.width = width;
    }

    public void setHeight(int height) {
        this.height = height;
    }

    public int getArea() {
        return width * height;
    }
}
```

Now:

```java
public class Square extends Rectangle {

    @Override
    public void setWidth(int width) {
        this.width = width;
        this.height = width;
    }

    @Override
    public void setHeight(int height) {
        this.width = height;
        this.height = height;
    }
}
```

Mathematically:

```text
Square is a Rectangle
```

But behaviorally this creates problems.

---

# 9. See the problem

Suppose the caller expects a `Rectangle`:

```java
public void resize(Rectangle rectangle) {

    rectangle.setWidth(5);
    rectangle.setHeight(10);

    System.out.println(
        rectangle.getArea()
    );
}
```

With a normal `Rectangle`:

```text
width = 5
height = 10

area = 50
```

Now:

```java
resize(new Square());
```

What happens?

```text
setWidth(5)
→ width = 5
→ height = 5

setHeight(10)
→ width = 10
→ height = 10

area = 100
```

The caller expected:

```text
Rectangle
5 × 10
= 50
```

but got:

```text
Square
10 × 10
= 100
```

The subclass changed the expected semantics.

So the `Square` cannot safely substitute for the `Rectangle` abstraction as designed.

That's LSP.

---

# 10. What went wrong?

The issue is not:

```text
Square
```

itself.

The problem is:

```text
Rectangle API allows width and height
to change independently.
```

But:

```text
Square requires width == height.
```

So the subclass cannot honor the parent's behavioral contract.

This is a very important interview insight:

> **A subtype must preserve the assumptions that clients are allowed to make about the parent type.**

---

# 11. Better design for Rectangle/Square

Instead of forcing inheritance, model shapes independently.

```java
public interface Shape {

    int getArea();
}
```

Rectangle:

```java
public class Rectangle implements Shape {

    private final int width;
    private final int height;

    public Rectangle(int width, int height) {
        this.width = width;
        this.height = height;
    }

    @Override
    public int getArea() {
        return width * height;
    }
}
```

Square:

```java
public class Square implements Shape {

    private final int side;

    public Square(int side) {
        this.side = side;
    }

    @Override
    public int getArea() {
        return side * side;
    }
}
```

Now both satisfy:

```java
Shape
```

without pretending they share the same mutable width/height behavior.

---

# 12. LSP isn't only about exceptions

This is extremely important.

A subclass doesn't have to literally throw an exception to violate LSP.

There are several ways.

For example:

### Parent

```java
public class FileStorage {

    public void save(String data) {
        // save data
    }
}
```

### Subclass

```java
public class ReadOnlyFileStorage
        extends FileStorage {

    @Override
    public void save(String data) {
        // silently do nothing
    }
}
```

This doesn't throw.

But the caller expects:

```java
storage.save(data);
```

to actually save the data.

The subclass violates that expectation.

Still LSP violation.

---

# 13. Subclass strengthening preconditions

This is a more advanced LSP concept.

Suppose parent says:

```java
public class PaymentProcessor {

    public void process(double amount) {

        if (amount <= 0) {
            throw new IllegalArgumentException();
        }

        // process
    }
}
```

The contract allows:

```text
amount > 0
```

Now subclass:

```java
public class PremiumPaymentProcessor
        extends PaymentProcessor {

    @Override
    public void process(double amount) {

        if (amount < 1000) {
            throw new IllegalArgumentException();
        }

        // process
    }
}
```

Parent accepted:

```text
100
```

Subclass rejects it.

Therefore the subclass has **strengthened the precondition**.

That's problematic for LSP.

The caller should not suddenly need additional restrictions just because a subtype was supplied.

---

# 14. Preconditions

A **precondition** is what must be true before an operation executes.

Example:

```java
withdraw(amount)
```

might require:

```text
amount > 0
```

Suppose parent allows:

```text
amount > 0
```

and subclass changes it to:

```text
amount >= 1000
```

The subclass has become more restrictive.

That's a contract violation.

A useful rule:

> **A subtype should not require more from the caller than the parent requires.**

---

# 15. Subclass weakening postconditions

Now the opposite.

A **postcondition** is what the method guarantees after execution.

Parent:

```java
public class OrderService {

    public Order createOrder(OrderRequest request) {

        Order order = new Order();

        repository.save(order);

        return order;
    }
}
```

The caller expects:

```text
createOrder()
→ returns a persisted Order
```

Subclass:

```java
public class SpecialOrderService
        extends OrderService {

    @Override
    public Order createOrder(OrderRequest request) {

        return new Order(); // not saved
    }
}
```

The subclass provides less than the parent promised.

That's also an LSP violation.

A useful rule:

> **A subtype should not provide weaker guarantees than the parent.**

---

# 16. Think in terms of contracts

This gives you a powerful mental model:

```text
Parent type defines contract
             ↓
       Subclass must honor
             ↓
      that same contract
```

The caller should be able to do:

```java
Parent p = new Child();
```

without needing:

```java
if (p instanceof Child) {
    // special rules
}
```

The moment clients need to know:

```text
“This implementation behaves differently, so be careful”
```

your abstraction may be violating LSP.

---

# 17. Another example: Bank accounts

Suppose:

```java
public class BankAccount {

    public void deposit(double amount) {
        // deposit
    }

    public void withdraw(double amount) {
        // withdraw
    }
}
```

Then:

```java
public class ReadOnlyAccount
        extends BankAccount {

    @Override
    public void withdraw(double amount) {
        throw new UnsupportedOperationException();
    }
}
```

Again:

```java
BankAccount account =
        new ReadOnlyAccount();

account.withdraw(500);
```

Breaks the contract.

So perhaps:

```java
public interface Depositable {
    void deposit(double amount);
}
```

and:

```java
public interface Withdrawable {
    void withdraw(double amount);
}
```

Then:

```text
SavingsAccount
    implements Depositable, Withdrawable

ReadOnlyAccount
    implements Depositable
```

This is interesting because you can see how **LSP and ISP** often interact.

We'll come back to that when we reach the Interface Segregation Principle.

---

# 18. LSP and method overriding

LSP is closely tied to overriding.

Suppose:

```java
public class Notification {

    public void send(String message) {
        System.out.println("Sending notification");
    }
}
```

Subclass:

```java
public class EmailNotification
        extends Notification {

    @Override
    public void send(String message) {
        System.out.println("Sending email");
    }
}
```

Perfectly fine.

The parent promises:

```text
send(message)
```

The child fulfills it:

```text
send(message)
```

with a specialized implementation.

That's exactly what inheritance/polymorphism are supposed to provide.

---

# 19. A good subclass

A good subtype should generally:

```text
preserve invariants
honor assumptions
honor method contracts
provide expected behavior
```

For example:

```java
List<String> list = new ArrayList<>();
```

You can substitute:

```java
List<String> list =
        new LinkedList<>();
```

The caller can still use the `List` contract.

That's good substitutability.

The caller doesn't need to know:

```text
ArrayList vs LinkedList
```

for normal `List` operations.

That's the spirit of LSP.

---

# 20. LSP and Java Collections

Here's a useful real-world perspective.

When you write:

```java
List<String> names;
```

Java allows:

```java
names = new ArrayList<>();
```

or:

```java
names = new LinkedList<>();
```

Your code uses:

```java
names.add("John");
names.remove("John");
names.get(0);
```

The implementations can differ internally.

But they honor the `List` abstraction.

This is a good example of substitutability.

---

# 21. A dangerous example: `UnsupportedOperationException`

Whenever you see:

```java
@Override
public void something() {
    throw new UnsupportedOperationException();
}
```

you should at least **investigate** LSP.

It isn't automatically a violation in every possible design, but often it means:

> “The parent abstraction promises behavior that this subtype cannot provide.”

For example:

```java
interface Vehicle {
    void drive();
}
```

and:

```java
class Car implements Vehicle {
    public void drive() {}
}
```

Fine.

But:

```java
class BrokenVehicle implements Vehicle {
    public void drive() {
        throw new UnsupportedOperationException();
    }
}
```

Why does this implementation exist?

Maybe the abstraction is wrong.

---

# 22. Example: Printer

Consider:

```java
public class Printer {

    public void print(Document document) {
    }

    public void scan(Document document) {
    }
}
```

Then:

```java
public class SimplePrinter
        extends Printer {

    @Override
    public void scan(Document document) {
        throw new UnsupportedOperationException();
    }
}
```

Now:

```java
Printer printer = new SimplePrinter();

printer.scan(document);
```

breaks.

This suggests that:

```java
Printer
```

is trying to represent two different capabilities.

A better design might eventually be:

```java
interface Printable {
    void print(Document document);
}
```

and:

```java
interface Scannable {
    void scan(Document document);
}
```

This is also leading us toward ISP.

---

# 23. LSP and abstraction quality

A big takeaway is:

> **LSP helps us discover bad abstractions.**

Suppose you write:

```java
abstract class Employee {

    abstract void work();

    abstract void drive();
}
```

Then:

```java
class OfficeEmployee extends Employee {
}
```

Maybe fine.

But:

```java
class RemoteEmployee extends Employee {
    
    @Override
    public void drive() {
        throw new UnsupportedOperationException();
    }
}
```

Now you're asking:

> Why does every employee need a `drive()` capability?

The abstraction is wrong.

LSP is telling you that your parent type is making promises that some subtypes can't fulfill.

---

# 24. LSP isn't “subclass must behave identically”

This is another common misunderstanding.

Suppose:

```java
Animal animal = new Dog();
```

The dog can make a different sound:

```java
@Override
public void makeSound() {
    System.out.println("Woof");
}
```

That's completely fine.

A subtype can have **different implementation**.

What matters is:

```text
same contract
+
valid specialized behavior
```

So LSP doesn't mean:

> Parent and child must have identical behavior.

It means:

> The child's behavior must remain valid wherever the parent's contract is expected.

---

# 25. Different behavior is okay

Consider:

```java
public interface PaymentMethod {

    void pay(double amount);
}
```

Card:

```java
public class CreditCardPayment
        implements PaymentMethod {

    @Override
    public void pay(double amount) {
        System.out.println(
            "Charging credit card"
        );
    }
}
```

UPI:

```java
public class UpiPayment
        implements PaymentMethod {

    @Override
    public void pay(double amount) {
        System.out.println(
            "Processing UPI"
        );
    }
}
```

Different implementations.

Same contract.

That's good polymorphism.

---

# 26. LSP and exception behavior

Suppose parent method:

```java
public void save(String data) {
    // save
}
```

The client assumes normal valid data will be saved.

Child:

```java
@Override
public void save(String data) {
    throw new RuntimeException();
}
```

for every input.

That's obviously not substitutable.

But a more subtle issue is when the child starts throwing exceptions for inputs the parent accepted.

Again:

```text
Parent contract
    ↓
accepted input
    ↓
Child rejects input
```

Potential LSP violation.

---

# 27. LSP and nulls

Here's a subtle example.

Parent:

```java
public class UserService {

    public String getDisplayName(User user) {

        if (user == null) {
            return "Unknown";
        }

        return user.getName();
    }
}
```

Suppose a subtype changes behavior:

```java
@Override
public String getDisplayName(User user) {

    Objects.requireNonNull(user);

    return user.getName();
}
```

Now:

```text
Parent accepts null
Child rejects null
```

The child has strengthened the precondition.

Potential LSP violation.

The broader lesson:

> **Subtypes shouldn't unexpectedly tighten the rules clients must follow.**

---

# 28. LSP with collections — mutable vs immutable

Consider:

```java
List<String> list = new ArrayList<>();
list.add("A");
```

Now someone gives you:

```java
List<String> list =
        Collections.unmodifiableList(...);
```

Calling:

```java
list.add("A");
```

throws an exception.

This is a useful discussion because it shows that substitutability depends on the **promised contract and context**.

An immutable view may satisfy many `List` operations but doesn't fulfill mutation expectations.

This is why understanding the actual API contract matters.

---

# 29. LSP is about the client

This point is extremely important.

Suppose:

```java
Bird bird = new Penguin();
```

The assignment itself isn't the problem.

The problem appears when the client does:

```java
bird.fly();
```

because the `Bird` abstraction promised it could.

So LSP asks:

> **Can existing client code continue to work when I replace the parent object with this subtype?**

That's the practical test.

---

# 30. A practical LSP test

When evaluating inheritance, ask:

### Test 1

Can I do:

```java
Parent p = new Child();
```

without changing client code?

### Test 2

Can the client invoke all operations promised by `Parent`?

### Test 3

Does `Child` preserve the expected outcomes?

### Test 4

Does `Child` introduce unexpected restrictions?

### Test 5

Does the client need:

```java
if (p instanceof Child)
```

to behave correctly?

If yes, investigate your abstraction.

---

# 31. The `instanceof` smell

Suppose:

```java
public void process(Employee employee) {

    if (employee instanceof Manager) {
        // special logic
    }

    if (employee instanceof Developer) {
        // different logic
    }
}
```

This isn't automatically an LSP violation.

But it can be a design smell.

Why?

Because it may indicate:

```text
The abstraction isn't powerful enough
```

and callers need to know concrete subtypes.

Good polymorphism usually lets us write:

```java
employee.work();
```

rather than:

```java
if (employee instanceof Manager) ...
else if (employee instanceof Developer) ...
```

This also connects LSP with OCP.

---

# 32. LSP + OCP

Remember OCP?

> Open for extension, closed for modification.

Imagine:

```java
public interface Notification {
    void send(String message);
}
```

Then:

```java
EmailNotification
SmsNotification
PushNotification
```

If all of them honor:

```java
send(message)
```

then:

```java
Notification notification =
        new EmailNotification();
```

or:

```java
Notification notification =
        new SmsNotification();
```

works without changing the caller.

So:

```text
OCP
   ↓
use abstraction for extension

LSP
   ↓
subtypes must genuinely honor abstraction
```

They work together.

---

# 33. LSP + SRP

We can also connect this to SRP.

Suppose:

```java
public class Bird {

    public void fly() {}
    public void swim() {}
    public void walk() {}
}
```

This class may already be mixing multiple capabilities.

When different birds can't honor all of them, LSP starts breaking.

Better separation of responsibility/capability often makes substitution easier.

Again, SOLID principles reinforce each other.

---

# 34. A very important misconception: “Every subclass must use every inherited method”

Not necessarily.

A subtype can inherit methods it doesn't directly override.

That's fine.

The problem is when inherited behavior **doesn't make sense** for the subtype.

For example:

```java
class Dog extends Animal
```

and:

```java
Animal.eat()
```

The dog doesn't need to override `eat()`.

It can simply inherit it.

That's perfectly valid.

---

# 35. Abstract classes and LSP

LSP applies to:

```text
class inheritance
abstract classes
interfaces
```

For example:

```java
abstract class Employee {
    abstract void work();
}
```

Then:

```java
class Developer extends Employee {
    @Override
    public void work() {
        System.out.println("Writing code");
    }
}
```

```java
class Tester extends Employee {
    @Override
    public void work() {
        System.out.println("Testing software");
    }
}
```

Both can substitute for:

```java
Employee
```

because both satisfy the contract:

```java
work()
```

---

# 36. LSP and default methods

Java interfaces can also create LSP issues.

Suppose:

```java
public interface Worker {

    void work();

    default void attendMeeting() {
        System.out.println("Meeting");
    }
}
```

Then a subtype may technically inherit:

```java
attendMeeting()
```

but whether it makes semantic sense depends on the abstraction.

The key question remains:

> **Does the subtype satisfy what clients reasonably expect from `Worker`?**

LSP is semantic, not merely syntactic.

---

# 37. An important distinction: Syntax vs semantics

Java compiler says:

```java
class Penguin extends Bird
```

is valid.

But LSP asks:

```text
Does Penguin semantically behave like
the Bird abstraction promises?
```

So:

```text
Java type system
    ≠
complete design correctness
```

The compiler can verify:

```text
method signatures
types
inheritance
```

It cannot fully verify:

```text
behavioral substitutability
```

That's why LSP is a design principle.

---

# 38. The classic formal interpretation

For interview purposes, there's a more formal way of expressing LSP.

A subtype should:

> **Accept at least what the parent accepts and guarantee at least what the parent guarantees.**

In simpler terms:

```text
Don't make preconditions stricter.
Don't make postconditions weaker.
Don't break invariants.
```

So:

### Preconditions

Subtype should not require **more**.

### Postconditions

Subtype should guarantee **at least as much**.

### Invariants

Subtype should preserve important properties expected by the parent.

You don't need to go extremely formal unless the interviewer wants deeper theory, but knowing these terms gives you an advantage.

---

# 39. Invariants

An invariant is a condition that should remain true.

For `BankAccount`:

```text
balance >= 0
```

Suppose parent guarantees:

```text
balance cannot become negative
```

and a subclass allows:

```java
balance = -1000;
```

The subclass may have violated the parent's invariant.

Therefore it may violate LSP.

Think:

```text
Parent promises:
    condition X always remains true

Child:
    allows X to become false
```

Problem.

---

# 40. Real-world REST/API analogy

LSP isn't limited to classes.

Imagine an abstraction:

```java
public interface OrderRepository {

    Order findById(Long id);
}
```

A caller assumes:

```java
Order order = repository.findById(id);
```

and perhaps the contract says:

```text
returns an Order if it exists
throws NotFoundException otherwise
```

Suppose one implementation instead:

```text
returns null
```

while another:

```text
throws IOException
```

If the caller depends on the original contract, implementations that violate it aren't safely substitutable.

So LSP also teaches us to keep **contracts consistent across implementations**.

# 41. Interview example — repository

Suppose:

```java
public interface UserRepository {

    User findById(Long id);
}
```

Implementation A:

```java
public class MySqlUserRepository
        implements UserRepository {

    public User findById(Long id) {
        // returns user or throws expected exception
    }
}
```

Implementation B:

```java
public class MongoUserRepository
        implements UserRepository {

    public User findById(Long id) {
        // returns user or throws expected exception
    }
}
```

Both should honor the same expectations.

That is LSP.

The implementation can differ internally.

The contract should remain substitutable.

# 42. When do we need LSP?

Whenever you're using:

```text
Inheritance
Interfaces
Polymorphism
Dependency injection
Plugin architectures
Strategy pattern
Multiple implementations
```

you should think about substitutability.

Especially ask:

> “Can I add another implementation without forcing callers to understand implementation-specific rules?”

---

# 43. Signs that LSP might be violated

These are excellent interview signals:

```text
1. Subclass throws UnsupportedOperationException
2. Subclass requires additional validation
3. Subclass rejects inputs accepted by parent
4. Subclass returns weaker/different results than expected
5. Parent methods don't make sense for some subclasses
6. Client uses instanceof to handle subclasses specially
7. Caller needs special-case logic for a particular implementation
8. Subclass breaks parent invariants
```

Not every one automatically proves an LSP violation, but they're strong warning signs.

---

# 44. A powerful example: Read-only collection

Imagine a class:

```java
public class Collection {

    public void add(String value) {
    }

    public void remove(String value) {
    }
}
```

Then:

```java
public class ReadOnlyCollection
        extends Collection {

    @Override
    public void add(String value) {
        throw new UnsupportedOperationException();
    }
}
```

A caller has:

```java
Collection collection =
        new ReadOnlyCollection();

collection.add("Java");
```

The caller cannot safely substitute the child.

The design might need different abstractions:

```java
interface ReadableCollection {
    String get(int index);
}

interface MutableCollection
        extends ReadableCollection {

    void add(String value);
    void remove(String value);
}
```

Now read-only collections only expose operations they support.

This example leads naturally into ISP.

# 45. LSP is not just “inheritance hierarchy correctness”

This is an important senior-level insight.

You can violate LSP even without explicit `extends`.

For example:

```java
public interface Storage {

    void save(String data);
}
```

Implementation:

```java
public class CloudStorage implements Storage {

    @Override
    public void save(String data) {
        // works
    }
}
```

Another implementation:

```java
public class TemporaryStorage implements Storage {

    @Override
    public void save(String data) {
        // only stores for 5 seconds
    }
}
```

Suppose the interface contract implies durable storage.

Then the second implementation doesn't satisfy the abstraction, even though it is perfectly valid Java.

So LSP is about **subtypes in the behavioral sense**, not only class inheritance syntax.

---

# 46. How to explain the Rectangle example in an interview

You can say:

> “A common example is Square extending Rectangle. Rectangle allows width and height to vary independently, but Square must keep them equal. If a caller expects a Rectangle and sets width to 5 and height to 10, substituting a Square changes the expected result because the Square modifies both dimensions. Therefore the Square cannot safely substitute for the Rectangle abstraction. The problem is the abstraction, not the mathematical relationship.”

That's a strong explanation.

# 47. Interview question: “How is LSP related to inheritance?”

A good answer:

> “LSP defines a behavioral requirement for inheritance and polymorphism. It's not enough for a subclass to satisfy the Java type system. The subclass must also honor the behavioral contract of its parent so that clients can replace the parent with the subclass without changing correctness.”

That's an excellent interview answer.

---

# 48. Interview question: “How do you detect LSP violations?”

You can answer:

> “I look for subclasses that throw `UnsupportedOperationException`, require stricter input validation, change expected output semantics, violate parent invariants, or force clients to use subtype-specific checks. Those are signs that the parent abstraction may be promising behavior the subtype cannot fulfill.”

# 49. Interview question: “How do you fix an LSP violation?”

Usually one of these approaches:

```text
1. Redesign the abstraction
2. Split a large interface into smaller capabilities
3. Prefer composition over inappropriate inheritance
4. Move behavior to a more appropriate abstraction
5. Remove inheritance when the subtype is not truly substitutable
```

For example:

```text
Bird
 ↓
FlyingBird
NonFlyingBird
```

or:

```text
Bird
 +
Flyable
```

depending on the domain.

# 50. LSP and composition

Sometimes the best solution is simply:

```text
Don't inherit.
Compose.
```

Suppose:

```java
public class Robot {

    private final Movement movement;

    public Robot(Movement movement) {
        this.movement = movement;
    }
}
```

Different movement implementations can be injected.

You don't need to force an inheritance relationship where the semantics don't fit.

This is why SOLID isn't about blindly using inheritance.

# 51. LSP and dependency injection

Suppose:

```java
@Service
public class CheckoutService {

    private final PaymentProcessor processor;

    public CheckoutService(
            PaymentProcessor processor) {
        this.processor = processor;

    public void checkout(double amount) {
        processor.process(amount);
```

Spring may inject:

```text

UpiProcessor
PaypalProcessor
```

For this architecture to work properly:

```text
Every processor
      ↓
must honor
      ↓
PaymentProcessor contract
```

That's LSP.

If one implementation behaves differently in a way the client cannot tolerate, the abstraction is broken.

```java
   ↑
 Child
```

# 55. SRP + OCP + LSP together

Let's connect all three.

Suppose we have:

```java
public class PaymentService {

    public void pay(String type) {

        if ("CARD".equals(type)) {
            ...
        }

            ...
        }
    }
```

### SRP

Payment behavior may be mixed together with other concerns.

### OCP

### LSP

After introducing:


```text
              PaymentProcessor
                  interface
                     |

        |             |            |
      Card           UPI         PayPal
```


# 56. The interview answer I'd memorize

**Liskov Substitution Principle says that objects of a subtype should be replaceable for objects of its parent type without breaking the correctness of the program.**

In Java, this means that if I have `Parent parent = new Child()`, client code should be able to use `parent` according to the parent's contract without needing special handling for `Child`.

A classic example is `Square` extending `Rectangle`. A rectangle allows width and height to be changed independently, but a square must keep them equal. If client code sets a rectangle's width to 5 and height to 10, substituting a `Square` changes the expected behavior. Therefore the subclass is not behaviorally substitutable.

Another example is a `Bird` class with a `fly()` method. A `Penguin` extending that class and throwing `UnsupportedOperationException` from `fly()` indicates that the abstraction is wrong because not every bird can satisfy the `fly()` contract.

LSP is therefore about behavioral contracts, not just whether Java allows the inheritance relationship. A subtype should not strengthen preconditions, weaken postconditions, or violate important invariants of the parent.

To fix LSP violations, I would usually redesign the abstraction, split capabilities into smaller interfaces, or use composition instead of inappropriate inheritance.
