# 4. Interface Segregation Principle — ISP

**I = Interface Segregation Principle**

The classic definition is:

> **Clients should not be forced to depend on methods they do not use.**

This is one of the most misunderstood SOLID principles.

The easiest way to understand it is:

> **Prefer small, focused interfaces over large, “do everything” interfaces.**

But there is a deeper idea behind it:

> **An interface should represent a meaningful capability, not a random collection of methods.**

Let's build this from the problem.

---

# 1. What problem does ISP solve?

Imagine we create this interface:

```java
public interface Machine {

    void print();

    void scan();

    void fax();
}
```

Now we have a normal printer:

```java
public class SimplePrinter implements Machine {

    @Override
    public void print() {
        System.out.println("Printing...");
    }

    @Override
    public void scan() {
        throw new UnsupportedOperationException();
    }

    @Override
    public void fax() {
        throw new UnsupportedOperationException();
    }
}
```

This is a major smell.

The printer only knows how to print, but the interface forces it to implement:

```text
scan()
fax()
```

which it doesn't support.

That's exactly what ISP tries to prevent.

---

# 2. Why is this a problem?

At first you might say:

> “It's just three methods. What's the big deal?”

The problem becomes much larger as the system grows.

Suppose:

```java
public interface Machine {

    void print();

    void scan();

    void fax();

    void staple();

    void copy();

    void email();

    void printColor();

    void printDuplex();
}
```

Now imagine:

```text
SimplePrinter
OfficePrinter
Scanner
FaxMachine
Photocopier
AllInOneMachine
```

Every implementation must deal with the entire interface.

Some methods will be irrelevant.

You start getting:

```java
throw new UnsupportedOperationException();
```

or:

```java
return null;
```

or:

```java
// Nothing to do
```

That's a strong indication that the interface is too large.

---

# 3. The fundamental idea

Instead of:

```java
public interface Machine {

    void print();
    void scan();
    void fax();
}
```

split the capabilities:

```java
public interface Printer {
    void print();
}
```

```java
public interface Scanner {
    void scan();
}
```

```java
public interface Fax {
    void fax();
}
```

Now:

```java
public class SimplePrinter
        implements Printer {

    @Override
    public void print() {
        System.out.println("Printing...");
    }
}
```

Multifunction machine:

```java
public class AllInOnePrinter
        implements Printer, Scanner, Fax {

    @Override
    public void print() {
        System.out.println("Printing...");
    }

    @Override
    public void scan() {
        System.out.println("Scanning...");
    }

    @Override
    public void fax() {
        System.out.println("Faxing...");
    }
}
```

Much cleaner.

---

# 4. The important phrase: “Clients”

The principle doesn't say:

> “Interfaces should always be small.”

It says:

> **Clients should not be forced to depend on methods they don't use.**

Suppose we have:

```java
public interface EmployeeOperations {

    void calculateSalary();

    void saveEmployee();

    void generateReport();

    void sendEmail();
}
```

Now a payroll client only needs:

```java
calculateSalary();
```

But because it depends on the entire interface, it's also coupled to:

```text
saveEmployee()
generateReport()
sendEmail()
```

even though it doesn't need them.

That's the problem.

---

# 5. Think about a remote control

Imagine a remote control with:

```text
Power
Volume
Channel
Brightness
AirConditioner
GarageDoor
Sprinkler
CoffeeMachine
```

You only want to control the TV.

Why should the TV client depend on all those unrelated controls?

A better design is:

```text
TVRemote
    |
    +-- Power
    +-- Volume
    +-- Channel
```

and separate controls for other devices.

That's essentially ISP.

# 6. Classic Java example: Worker

Suppose:

```java
public interface Worker {

    void work();

    void eat();

    void sleep();
}
```

Human:

```java
public class HumanWorker implements Worker {

    @Override
    public void work() {
        System.out.println("Human working");
    }

    @Override
    public void eat() {
        System.out.println("Human eating");
    }

    @Override
    public void sleep() {
        System.out.println("Human sleeping");
    }
}
```

Fine.

But now:

```java
public class RobotWorker implements Worker {

    @Override
    public void work() {
        System.out.println("Robot working");
    }

    @Override
    public void eat() {
        throw new UnsupportedOperationException();
    }

    @Override
    public void sleep() {
        throw new UnsupportedOperationException();
    }
}
```

Why does a robot need:

```text
eat()
sleep()
```

?

It doesn't.

The interface contains unrelated capabilities.

---

# 7. Applying ISP

Split it:

```java
public interface Workable {

    void work();
}
```

```java
public interface Eatable {

    void eat();
}
```

```java
public interface Sleepable {

    void sleep();
}
```

Human:

```java
public class HumanWorker
        implements Workable, Eatable, Sleepable {

    @Override
    public void work() {
        System.out.println("Human working");
    }

    @Override
    public void eat() {
        System.out.println("Human eating");
    }

    @Override
    public void sleep() {
        System.out.println("Human sleeping");
    }
}
```

Robot:

```java
public class RobotWorker
        implements Workable {

    @Override
    public void work() {
        System.out.println("Robot working");
    }
}
```

Now the design accurately represents capabilities.

---

# 8. Why smaller interfaces help

Suppose:

```java
public interface Worker {

    void work();
    void eat();
    void sleep();
}
```

and we modify:

```java
void eat();
```

Every implementation potentially needs recompilation/change.

For example:

```text
HumanWorker
RobotWorker
ContractorWorker
AIWorker
ExternalWorker
```

A change to the large interface affects all of them.

With segregated interfaces:

```text
Workable
Eatable
Sleepable
```

changes to `Eatable` primarily affect clients/implementations that actually depend on eating.

So ISP reduces:

> **Unnecessary coupling between clients and unrelated interface members.**

---

# 9. ISP and change impact

This is one of the most important benefits.

Suppose:

```java
public interface UserOperations {

    void createUser();

    void deleteUser();

    void resetPassword();

    void exportUsers();

    void sendEmail();
}
```

Now a reporting component only needs:

```java
exportUsers();
```

But it depends on the entire interface.

If someone adds:

```java
void archiveUser();
```

or changes:

```java
void sendEmail();
```

the reporting component is conceptually coupled to changes it doesn't care about.

This is exactly what ISP tries to eliminate.

---

# 10. ISP isn't merely “make interfaces tiny”

This is important.

Suppose:

```java
public interface UserService {

    void createUser();
    void findUser();
    void updateUser();
}
```

Would we split this into:

```text
UserCreator
UserFinder
UserUpdater
```

just because there are three methods?

Not necessarily.

These operations may all belong to a coherent client-facing abstraction.

ISP isn't about minimizing method count.

It's about:

> **Avoiding interfaces that force unrelated clients or implementations to depend on capabilities they don't need.**

That's the important distinction.

---

# 11. Cohesion again

Remember SRP?

We talked about **cohesion**.

ISP has a strong relationship with it.

A good interface should contain methods that are:

```text
closely related
meaningful together
used together by relevant clients
```

For example:

```java
public interface PaymentProcessor {

    PaymentResult authorize(Payment payment);

    PaymentResult capture(Payment payment);

    PaymentResult refund(Payment payment);
}
```

These may form a coherent payment-processing abstraction.

But this:

```java
public interface PaymentProcessor {

    PaymentResult authorize(Payment payment);

    void generatePdf();

    void sendEmail();

    void saveToDatabase();

    void generateAuditReport();
}
```

is clearly mixing unrelated concerns.

---

# 12. Another important example: Database repository

Suppose someone creates:

```java
public interface UserRepository {

    User findById(Long id);

    List<User> findAll();

    void save(User user);

    void delete(User user);

    void exportToCsv();

    void sendEmail(User user);

    void generateReport();
}
```

Now:

```text
CRUD/persistence
+
CSV
+
email
+
reporting
```

are mixed together.

This is a poor abstraction.

Better:

```java
public interface UserRepository {

    User findById(Long id);

    List<User> findAll();

    void save(User user);

    void delete(User user);
}
```

Then:

```java
public interface UserExporter {

    void exportToCsv(List<User> users);
}
```

```java
public interface UserNotificationService {

    void sendEmail(User user);
}
```

```java
public interface UserReportGenerator {

    byte[] generate(List<User> users);
}
```

Now each interface represents a clear capability.

# 13. Real Spring Boot example

This comes up frequently in enterprise Java.

Suppose:

```java
public interface UserService {

    User create(UserRequest request);

    User update(Long id, UserRequest request);

    void delete(Long id);

    void sendWelcomeEmail(User user);

    byte[] generateReport();

    void exportCsv();
}
```

Imagine three clients.

### REST API

Needs:

```text
create
update
delete
```

### Report module

Needs:

```text
generateReport
exportCsv
```

### Notification module

Needs:

```text
sendWelcomeEmail
```

The giant interface doesn't represent one coherent client need.

We could have:

```java
public interface UserCommandService {

    User create(UserRequest request);

    User update(Long id, UserRequest request);

    void delete(Long id);
}
```

```java
public interface UserReportingService {

    byte[] generateReport();

    void exportCsv();
}
```

```java
public interface UserNotificationService {

    void sendWelcomeEmail(User user);
}
```

Each client gets the contract it actually needs.

# 14. ISP and dependency injection

This is especially useful with Spring.

Suppose:

```java
@Service
public class OrderController {

    private final OrderOperations orderOperations;

    public OrderController(
            OrderOperations orderOperations) {
        this.orderOperations = orderOperations;
    }
}
```

If:

```java
OrderOperations
```

contains:

```text
create
update
delete
refund
generateInvoice
exportCsv
sendEmail
```

then the controller depends on a huge abstraction.

Instead, maybe the controller only needs:

```java
public interface OrderCommandService {

    Order create(OrderRequest request);

    Order update(Long id, OrderRequest request);

    void delete(Long id);
}
```

Now the controller depends only on what it actually needs.

That's clean dependency design.

# 15. ISP and APIs

Here's an important modern interpretation.

Suppose a class exposes:

```java
public interface CustomerService {

    Customer create(CustomerRequest request);

    Customer update(Long id, CustomerRequest request);

    void delete(Long id);

    List<Customer> findAll();

    void exportCsv();

    void exportPdf();

    void sendEmail();

    void sendSms();

    void resetPassword();

    void lockAccount();

    void unlockAccount();
}
```

This interface has a huge surface area.

Different consumers may need very different parts.

This makes the abstraction harder to understand, mock, implement, and evolve.

ISP says:

> **Give each client the smallest meaningful interface it needs.**

This is sometimes called **role-based interfaces**.

---

# 16. Role interfaces

Suppose:

```java
public interface CustomerReader {

    Customer findById(Long id);

    List<Customer> findAll();
}
```

```java
public interface CustomerWriter {

    Customer create(CustomerRequest request);

    Customer update(Long id, CustomerRequest request);
}
```

```java
public interface CustomerDeleter {

    void delete(Long id);
}
```

A component that only reads customers can depend on:

```java
CustomerReader
```

rather than the entire customer service API.

This is a very practical interpretation of ISP.

---

# 17. A common interview trap: “Many small interfaces are always better”

No.

Consider:

```java
public interface NameProvider {
    String getName();
}
```

```java
public interface AgeProvider {
    int getAge();
}
```

```java
public interface EmailProvider {
    String getEmail();
}
```

```java
public interface AddressProvider {
    String getAddress();
}
```

Maybe this is justified.

But maybe a `Customer` abstraction naturally and cohesively represents all these properties:

```java
public interface Customer {

    String getName();
    int getAge();
    String getEmail();
    String getAddress();
}
```

Splitting everything into microscopic interfaces can create unnecessary complexity.

So again:

> **Segregate interfaces based on meaningful client needs and cohesive capabilities, not simply method count.**

---

# 18. ISP vs SRP

These two are easy to confuse.

### SRP

Focuses primarily on:

> **classes/modules having one reason to change.**

### ISP

Focuses primarily on:

> **interfaces not forcing clients to depend on things they don't need.**

Example:

```java
public interface EmployeeOperations {

    void calculateSalary();

    void generateReport();

    void sendEmail();
}
```

SRP question:

> Does this abstraction represent one coherent responsibility?

ISP question:

> Does every client using this interface actually need all these methods?

They overlap, but the focus differs.

---

# 19. ISP vs LSP

This is even more interesting.

Remember our earlier example:

```java
public interface Worker {

    void work();

    void eat();

    void sleep();
}
```

Robot:

```java
public class RobotWorker implements Worker {

    @Override
    public void work() {
    }

    @Override
    public void eat() {
        throw new UnsupportedOperationException();
    }

    @Override
    public void sleep() {
        throw new UnsupportedOperationException();
    }
}
```

### ISP problem

Robot is forced to depend on methods it doesn't need.

### LSP problem

Robot cannot actually fulfill the contract represented by those methods.

So one bad abstraction can violate **both** ISP and LSP.

This is a very common SOLID connection.

# 20. ISP and the `UnsupportedOperationException` smell

Again:

```java
throw new UnsupportedOperationException();
```

doesn't automatically mean ISP.

But when you see:

```java
@Override
public void scan() {
    throw new UnsupportedOperationException();
}
```

inside an implementation of:

```java
Machine
```

you should ask:

> “Why is this implementation being forced to have `scan()`?”

That points toward ISP.

And potentially LSP.

# 21. ISP and abstract classes

ISP isn't limited to interfaces declared with:

```java
interface
```

The principle is about **contracts/abstractions**.

You can have a giant abstract class:

```java
public abstract class Employee {

    public abstract void calculateSalary();

    public abstract void generateReport();

    public abstract void sendEmail();

    public abstract void manageDatabase();
}
```

and subclasses that don't need all of these.

The same design problem exists.

So ISP is fundamentally about **client-specific contracts**, not merely the Java keyword `interface`.

```java

    void refund();

    void generateReceipt();

    void validateIdentity();

    void splitPayment();

    void chargeback();
}
```

Can every payment method realistically support all these?

Maybe not.

A better design could be:




This is much more expressive.

# 25. ISP and mocking in unit tests

This is a practical advantage.

Suppose:

```java
public interface UserService {

    void createUser();

    void deleteUser();

    void sendEmail();

    void generateReport();

    void exportCsv();

    void resetPassword();

    void lockAccount();
}
```

Now a class only needs:

```java
sendEmail()
```

When writing a unit test, the mock is conceptually representing an enormous dependency:

```text
UserService
```

Instead:

```java
public interface UserNotifier {

    void sendEmail(User user);
}
```

Now:

```java
@Mock
private UserNotifier userNotifier;
```

The test communicates exactly what the class depends on.

Smaller interfaces often make mocking and test setup easier.

# 26. ISP and maintenance

Suppose 15 classes implement:

```java
LargeInterface
```

and you add a method:

```java
void newMethod();
```

Now all 15 implementations may need changes.

You just caused a large change ripple.

With segregated interfaces:

```text
Reader
Writer
Notifier
Exporter
```

adding a method to `Notifier` primarily impacts notifier implementations and clients that use it.

This reduces the **blast radius** of changes.

That's an excellent phrase for interviews:

> **ISP reduces the blast radius of interface changes.**

---

# 27. ISP and compilation dependencies

There's also a deeper software-engineering reason.

If:

```java
Client
   ↓
HugeInterface
```

then the client is dependent on everything exposed by that interface.

Even if it only calls:

```java
getUser()
```

it's still conceptually coupled to the entire contract.

With:

```java
Client
   ↓
UserReader
```

the dependency surface is smaller.

So ISP helps reduce:

> **unnecessary compile-time and conceptual dependencies.**

# 28. ISP with Java 8+ default methods

Now an interesting question:

> “What if I solve the large-interface problem with default methods?”

For example:

```java
public interface Machine {

    void print();

    default void scan() {
        throw new UnsupportedOperationException();
    }

    default void fax() {
        throw new UnsupportedOperationException();
    }
}
```

Does that solve ISP?

**No.**

The implementation is still conceptually dependent on capabilities it doesn't need.

Default methods change the implementation burden, but they don't automatically make the interface segregated.

ISP is about the **design of dependencies**, not merely avoiding compiler errors.

---

# 29. ISP with Java 8 default methods — when they're useful

Default methods are excellent for:

```text
optional common behavior
backward-compatible interface evolution
shared small pieces of behavior
```

But they shouldn't be used as a way to hide a poorly designed interface.

This:

```java
default void scan() {
    throw new UnsupportedOperationException();
}
```

is basically saying:

> “I know some implementations don't support this, but I'm keeping it here anyway.”

That's often a sign that the abstraction should be reconsidered.

# 32. ISP and the Adapter pattern

Suppose you have a third-party library:

```java
ThirdPartyPaymentClient
```

with a huge API.

Your application doesn't need all of it.

Instead of injecting the entire third-party type throughout your application, define a focused interface:

```java
public interface PaymentGateway {

    PaymentResult charge(Payment payment);
}
```

Then adapt the third-party client:

```java
public class StripePaymentGateway
        implements PaymentGateway {

    private final ThirdPartyStripeClient client;

    @Override
    public PaymentResult charge(Payment payment) {
        // adapt application model to Stripe API
        return ...;
    }
}
```

Now your application depends on the small interface.

This is a very practical application of ISP.

# 35. What ISP doesn't mean

Don't say:

> “Interfaces should have as few methods as possible.”

Wrong.

Don't say:

> “Every method must have its own interface.”

Also wrong.

Don't say:

> “Always split large interfaces.”

Not necessarily.

Instead:

> **Clients should depend only on the cohesive set of operations they actually need.**

That's the correct idea.

---

# 36. How to identify ISP violations

Look for:

```text
1. Large interfaces
2. Implementations with many empty methods
3. UnsupportedOperationException
4. Clients using only a small subset of methods
5. Interfaces mixing unrelated capabilities
6. Changes to one interface affecting many unrelated clients
7. Classes implementing interfaces for only one or two methods
```

Again, these are **signals**, not automatic proof.

---

# 37. When do we need ISP?

ISP becomes especially valuable when:

```text
Large application
Multiple clients
Many implementations
Different teams consume different APIs
Interfaces evolve frequently
Plugin architecture
Spring dependency injection
Unit testing with mocks
External library integrations
```

For a tiny application with:

```java
interface Calculator {
    int add(int a, int b);
    int subtract(int a, int b);
}
```

there may be no meaningful reason to split it.

Don't engineer for problems you don't have.

# 38. ISP vs SRP vs LSP vs OCP

Now let's connect all four we've learned.

| Principle | Main question                                                       |
| --------- | ------------------------------------------------------------------- |
| **SRP**   | Does this class have one reason to change?                          |
| **OCP**   | Can new behavior be added without repeatedly modifying stable code? |
| **LSP**   | Can a subtype safely replace its parent?                            |
| **ISP**   | Are clients forced to depend on methods they don't need?            |

Or:

```text
SRP → Responsibility
OCP → Extension
LSP → Substitution
ISP → Interfaces
```

---

# 39. One example showing all four

Imagine:

```java
public interface EmployeeOperations {

    void calculateSalary();

    void generateReport();

    void save();

    void sendEmail();
}
```

And:

```java
public class EmployeeService
        implements EmployeeOperations {

    ...
}
```

Now look at the design.

### SRP

The class may have:

```text
salary
report
persistence
notification
```

multiple responsibilities.

### OCP

Adding another operation may require modifying the same interface/class.

### LSP

A subclass may be unable to meaningfully implement all operations.

### ISP

Clients that only need salary calculation are forced to depend on:

```text
report
save
email
```

One bad abstraction can create multiple SOLID problems.

# 40. How ISP can help LSP

This is one of the nicest relationships between the principles.

Earlier:

```java
public interface Machine {

    void print();
    void scan();
    void fax();
}
```

`SimplePrinter` had to implement unsupported operations.

Instead:

```java
public interface Printer {
    void print();
}
```

```java
public interface Scanner {
    void scan();
}
```

Now:

```java
SimplePrinter implements Printer
```

and:

```java
MultiFunctionPrinter
        implements Printer, Scanner, Fax
```

The smaller abstractions make it easier for each implementation to fulfill its contract.

So:

> **Good interface segregation often makes LSP easier to satisfy.**

# 41. How ISP can help OCP

Suppose we have:

```java
public interface Exporter {
    void export(Data data);
}
```

Different exporters implement it.

Now adding:

```text
PdfExporter
ExcelExporter
XmlExporter
```

is straightforward.

A small, focused abstraction becomes a clean extension point.

So:

```text
ISP
  ↓
focused interface
  ↓
clear abstraction
  ↓
easier OCP
```

Again, SOLID principles reinforce one another.

# 42. Interview question: “Explain ISP”

A strong answer:

**Interface Segregation Principle says that clients should not be forced to depend on methods they do not use.**

In practice, this means I prefer small, cohesive, role-based interfaces rather than large interfaces that contain many unrelated operations.

For example, if I have a `Machine` interface with `print()`, `scan()`, and `fax()`, a simple printer may be forced to implement `scan()` and `fax()` even though it doesn't support them. This often leads to empty methods or `UnsupportedOperationException`.

I would segregate the interface into capabilities such as `Printer`, `Scanner`, and `Fax`. A simple printer can implement only `Printer`, while a multifunction machine can implement all three.

The main benefits are reduced coupling, smaller dependency surfaces, easier testing, easier maintenance, and less impact when an interface changes.

---

# 43. Interview question: “Why is a fat interface bad?”

A good answer:

> “A fat interface forces implementations and clients to depend on methods that may be irrelevant to them. This creates unnecessary coupling. It also increases the impact of interface changes because adding or modifying one method may affect many unrelated implementations.”

That's a good concise answer.

---

# 44. Interview question: “What is a fat interface?”

A **fat interface** is an interface that exposes too many methods or unrelated capabilities such that many clients or implementations only need a small portion of it.

Example:

```java
public interface EmployeeService {

    void calculateSalary();
    void sendEmail();
    void generateReport();
    void save();
    void exportCsv();
}
```

Not every consumer needs all of that.

---

# 45. Interview question: “How would you fix a fat interface?”

Say:

> “I'd identify the different client needs or capabilities and split the interface into focused, cohesive interfaces. For example, I might have `EmployeeReader`, `EmployeeWriter`, `EmployeeReporter`, and `EmployeeNotifier`, depending on actual client requirements.”

Notice the important phrase:

> **depending on actual client requirements**

That's better than mechanically splitting based on method count.

---

# 46. A Spring Boot interview example

Interviewer:

> “You have a huge service interface. Would you split it?”

You can say:

> “I would first understand who consumes the interface and which methods they actually use. If different consumers depend on different subsets of the API, I'd introduce smaller role-specific interfaces and have an implementation provide multiple interfaces where appropriate.”

That's a strong answer.

For example:

```java
public interface OrderReader {
    Order findById(Long id);
}
```

```java
public interface OrderWriter {
    void save(Order order);
}
```

```java
public interface OrderCanceller {
    void cancel(Long id);
}
```

and a concrete service could implement several:

```java
@Service
public class OrderService
        implements OrderReader,
                   OrderWriter,
                   OrderCanceller {
}
```

Each client can depend on only the role it requires.

# 47. ISP and interfaces as contracts

Think about an interface as a promise:

```text
Interface
    ↓
"Here are the capabilities I promise."
```

A good interface says:

```text
Printer
    → I can print.
```

A bad interface says:

```text
Machine
    → I can print, scan, fax, email, copy,
      archive, stream, export...
```

When an implementation cannot honestly fulfill the whole contract, that's a warning that the contract is too broad.

# 48. The deepest mental model

Think about the flow:

```text
Large interface
      ↓
Many clients depend on it
      ↓
Each client uses different methods
      ↓
Unnecessary coupling
      ↓
Interface changes ripple everywhere
```

ISP changes the design to:

```text
Focused interfaces
      ↓
Clients depend on exactly what they need
      ↓
Less coupling
      ↓
Smaller change impact
```

That's the principle.

# 51. One final example to lock it in

Bad:

```java
public interface Vehicle {

    void drive();

    void fly();

    void sail();
}
```

Now:

```java
public class Car implements Vehicle {

    @Override
    public void drive() {
    }

    @Override
    public void fly() {
        throw new UnsupportedOperationException();
    }

    @Override
    public void sail() {
        throw new UnsupportedOperationException();
    }
}
```

The problem is obvious.

Instead:

```java
public interface Drivable {
    void drive();
}
```

```java
public interface Flyable {
    void fly();
}
```

```java
public interface Sailable {
    void sail();
}
```

Now:

```java
public class Car implements Drivable {
    
    @Override
    public void drive() {
        System.out.println("Driving");
    }
}
```

```java
public class FlyingCar
        implements Drivable, Flyable {
    
    @Override
    public void drive() {
    }

    @Override
    public void fly() {
    }
}
```

```java
public class Boat implements Sailable {
    
    @Override
    public void sail() {
        System.out.println("Sailing");
    }
}
```

This is a clean capability-based design.

## The one sentence I want you to remember

> **ISP means an object should not be forced to depend on a contract larger than the capabilities it actually needs or supports.**

And an interview-quality distinction:

> **SRP is primarily about responsibilities of classes/modules; ISP is about the size and shape of interfaces from the perspective of their clients.**

When you're comfortable with ISP, say **“next”** and we'll do the final SOLID principle: **D — Dependency Inversion Principle (DIP)**. That's the one that ties a lot of what we've discussed together, especially **interfaces, dependency injection, Spring Boot, loose coupling, and high-level vs low-level modules**.
