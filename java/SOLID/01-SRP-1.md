# S: Single Responsibility Principle (SRP)

> **"A class should have only one reason to change."** (Robert C. Martin)

A more precise version: **a class should be responsible to one actor (one stakeholder or group of people who'd request changes).**

"One responsibility" does **not** mean "one method." It means all the code in the class changes for the same reason, driven by the same source.

---

## 1. Why do we need it? (The problem)

Imagine a class that validates data, applies business rules, saves to the database, and sends emails. What goes wrong?

1. **Ripple effects:** Changing the email template forces you to touch, recompile, and retest a class that also holds payment logic. You might break something unrelated.
2. **Hard to test:** To test a discount calculation, you must set up a database and an email server.
3. **Merge conflicts:** Three developers working on three different features all edit the same file.
4. **Hard to reuse:** You want the validation logic elsewhere, but it's welded to the database code.
5. **Hard to read:** A 1,500-line "God class" that nobody fully understands.

## 2. When do we need it?

- When a class **changes for different reasons** at different times (e.g., business rule changes vs. UI format changes vs. DB changes).
- When you find yourself describing a class with **"and"**: "It calculates salary **and** saves to DB **and** prints reports."
- When unit tests need heavy setup or mocking of unrelated things.
- When one file keeps appearing in merge conflicts.

## 3. Example 1: The classic `Employee` (violation → fix)

### ❌ Violation

```java
public class Employee {
    private String name;
    private double hourlyRate;
    private int hoursWorked;

    // Used by the FINANCE department
    public double calculatePay() {
        return hourlyRate * hoursWorked;
    }

    // Used by the HR department
    public String generateHoursReport() {
        return name + " worked " + hoursWorked + " hours";
    }

    // Used by the IT/DB team
    public void save() {
        System.out.println("INSERT INTO employee ...");
    }
}
```

This class has **three reasons to change**, because it has three different actors:

| Method | Who requests changes |
|---|---|
| `calculatePay()` | Finance (overtime rules, tax) |
| `generateHoursReport()` | HR (report format) |
| `save()` | IT/DBA (switching from MySQL to Mongo) |

**A real bug this causes:** if `calculatePay()` and `generateHoursReport()` both call a shared helper `calculateRegularHours()`, then when Finance changes how "regular hours" are counted, HR's report silently changes too. Two actors, one shared code path, unintended breakage.

### ✅ Fix: split by actor

```java
// Pure data
public class Employee {
    private final String name;
    private final double hourlyRate;
    private final int hoursWorked;

    public Employee(String name, double hourlyRate, int hoursWorked) {
        this.name = name;
        this.hourlyRate = hourlyRate;
        this.hoursWorked = hoursWorked;
    }
    public String getName() { return name; }
    public double getHourlyRate() { return hourlyRate; }
    public int getHoursWorked() { return hoursWorked; }
}

// Finance's reason to change
public class PayCalculator {
    public double calculatePay(Employee e) {
        return e.getHourlyRate() * e.getHoursWorked();
    }
}

// HR's reason to change
public class HoursReporter {
    public String generateReport(Employee e) {
        return e.getName() + " worked " + e.getHoursWorked() + " hours";
    }
}

// IT's reason to change
public class EmployeeRepository {
    public void save(Employee e) {
        System.out.println("INSERT INTO employee ...");
    }
}
```

**How it solved the problem:** each class now has exactly one stakeholder. Finance changes only `PayCalculator`, so HR's report and the DB code cannot be affected.

## 4. Example 2: `UserService` doing everything (realistic backend code)

### ❌ Violation

```java
public class UserService {

    public void registerUser(String email, String password) {
        // 1. Validation
        if (email == null || !email.contains("@")) {
            throw new IllegalArgumentException("Invalid email");
        }
        if (password.length() < 8) {
            throw new IllegalArgumentException("Weak password");
        }

        // 2. Password hashing
        String hashed = Integer.toString(password.hashCode()); // simplified

        // 3. Persistence
        System.out.println("INSERT INTO users VALUES (" + email + "," + hashed + ")");

        // 4. Notification
        System.out.println("Sending welcome email to " + email);
    }
}
```

Four reasons to change: validation rules, hashing algorithm, database, email provider. Testing "weak password rejected" requires touching the DB and email code paths too.

### ✅ Fix

```java
public class UserValidator {
    public void validate(String email, String password) {
        if (email == null || !email.contains("@"))
            throw new IllegalArgumentException("Invalid email");
        if (password.length() < 8)
            throw new IllegalArgumentException("Weak password");
    }
}

public class PasswordHasher {
    public String hash(String password) {
        return Integer.toString(password.hashCode()); // swap for BCrypt later
    }
}

public class UserRepository {
    public void save(String email, String hashedPassword) {
        System.out.println("INSERT INTO users VALUES (" + email + "," + hashedPassword + ")");
    }
}

public class WelcomeEmailSender {
    public void send(String email) {
        System.out.println("Sending welcome email to " + email);
    }
}

// Orchestrator: its ONE job is coordinating the registration workflow
public class UserRegistrationService {
    private final UserValidator validator;
    private final PasswordHasher hasher;
    private final UserRepository repository;
    private final WelcomeEmailSender emailSender;

    public UserRegistrationService(UserValidator validator, PasswordHasher hasher,
                                   UserRepository repository, WelcomeEmailSender emailSender) {
        this.validator = validator;
        this.hasher = hasher;
        this.repository = repository;
        this.emailSender = emailSender;
    }

    public void registerUser(String email, String password) {
        validator.validate(email, password);
        String hashed = hasher.hash(password);
        repository.save(email, hashed);
        emailSender.send(email);
    }
}
```

**Benefits you can now claim:**
- Upgrade hashing to BCrypt → touch only `PasswordHasher`.
- Test `UserValidator` with plain unit tests, no DB or email needed.
- Reuse `UserValidator` in a "change password" flow.

> Note: `UserRegistrationService` is *not* a violation. Coordinating collaborators **is** a single responsibility (orchestration).

## 5. Example 3: `Invoice` (mixing business logic, printing, and storage)

### ❌ Violation

```java
public class Invoice {
    private double amount;
    private double taxRate;

    public double calculateTotal() { return amount + amount * taxRate; }

    public void printInvoice() {
        System.out.println("Invoice total: " + calculateTotal());
    }

    public void saveToFile(String path) {
        // writes invoice to a file
    }
}
```

Tomorrow the requirements say: *"Print as PDF"*, *"Save to a database instead of a file"*, *"Tax rules changed."* All three edit the same class.

### ✅ Fix

```java
public class Invoice {                       // business logic only
    private final double amount;
    private final double taxRate;

    public Invoice(double amount, double taxRate) {
        this.amount = amount;
        this.taxRate = taxRate;
    }
    public double calculateTotal() { return amount + amount * taxRate; }
}

public class InvoicePrinter {                // presentation only
    public void print(Invoice invoice) {
        System.out.println("Invoice total: " + invoice.calculateTotal());
    }
}

public class InvoiceFileStorage {            // persistence only
    public void save(Invoice invoice, String path) {
        // write to file
    }
}
```

Now "print as PDF" means adding a `PdfInvoicePrinter` or editing `InvoicePrinter`. `Invoice` is untouched. (This also sets you up nicely for the **Open/Closed** principle later.)

## 6. Example 4: SRP at the *method* level (mini example)

SRP applies to methods too, not just classes.

```java
// ❌ One method, three jobs
public void processOrder(Order order) {
    // validate
    // calculate price
    // print receipt
}

// ✅ Each method has one job
public void processOrder(Order order) {
    validate(order);
    double total = calculatePrice(order);
    printReceipt(order, total);
}
```

## 7. How to spot an SRP violation (smells)

- Class name contains **Manager, Helper, Util, Processor, Handler** with a vague scope (often God classes).
- Imports from unrelated layers in one file (`java.sql.*`, `javax.mail.*`, `java.io.*`).
- The constructor needs many unrelated dependencies.
- Test setup requires mocking half the application.
- You describe the class with "and".

## 8. Don't over-apply it (important, interviewers love this)

SRP taken to an extreme gives you 200 tiny classes that each do one trivial thing, making code harder to follow. That's **over-engineering**.

- Don't split based on hypothetical future changes. Split when you see **actual, different reasons to change**.
- A small class with 2 tightly related methods is fine.
- Rule of thumb: **group things that change together, separate things that change for different reasons.**

## 9. Common misconceptions

| Myth | Truth |
|---|---|
| "A class should have only one method" | No. It can have many methods, all serving one responsibility. |
| "A class should do only one small thing" | It's about *reasons to change* / *actors*, not size. |
| "POJOs/entities can't have any logic" | They can have logic that belongs to that entity's own domain. |

## 10. How to explain SRP in an interview

**30-second answer:**

> "SRP says a class should have only one reason to change, meaning it should be responsible to a single stakeholder or concern. For example, if an `Employee` class calculates pay, generates HR reports, and saves itself to the database, then Finance, HR, and the DBA can all force changes to it, and a change for one can accidentally break another. I'd split it into `PayCalculator`, `HoursReporter`, and `EmployeeRepository`. That makes each class easier to test, reuse, and change safely, and reduces merge conflicts."

**Structure to follow (say this order):** Definition → Problem (a violation example) → Fix → Benefits → Caveat about over-engineering.

**Likely follow-up questions:**

1. **"Is a class with multiple methods violating SRP?"** No. Multiple methods are fine if they serve the same responsibility.
2. **"How do you decide what a 'responsibility' is?"** By the *actor/reason to change*: who would ask me to modify this code?
3. **"Can SRP be overdone?"** Yes, too many tiny classes hurt readability. Split when there are real, different change drivers.
4. **"Where have you applied it?"** Use the layered structure: Controller → Service → Repository, where each layer has one job (a strong real-world answer). A Spring Boot `@RestController` handles HTTP, `@Service` handles business logic, `@Repository` handles persistence.
5. **"SRP vs. high cohesion?"** SRP is essentially a design rule for achieving high cohesion. Everything in the class belongs together.
