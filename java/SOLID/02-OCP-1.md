## What it says

> **"Software entities (classes, modules, methods) should be open for extension, but closed for modification."** (Bertrand Meyer; popularized by Robert C. Martin)

- **Open for extension:** you can add new behavior.
- **Closed for modification:** you add it *without editing existing, tested code*.

New features should arrive as **new code**, not as **edits to old code**.

---

## 1. Why do we need it? (The problem)

Picture a class with an `if/else if` chain on type. Every new requirement ("add a new customer type", "support a new payment method") means opening that class and adding another branch.

1. **Regression risk:** every edit to working, tested code can break what already works.
2. **Retesting:** you must retest *all* branches, not just the new one.
3. **Growing chains:** the `if/else` or `switch` grows forever and gets unreadable.
4. **Merge conflicts:** everyone adding a new type edits the same method.
5. **Shotgun surgery:** the same `switch` often gets copy-pasted in several places, and you must update them all.

## 2. When do we need it?

- When you see `if/else` or `switch` on a **type, enum, or string code** that decides behavior.
- When you expect **new variants** to keep coming (payment methods, discount rules, file formats, notification channels, tax rules).
- When a **stable, tested class** keeps being reopened for new cases.
- When you use `instanceof` checks to decide what to do.

## 3. How does it solve the problem?

The core trick: **depend on an abstraction (interface / abstract class), and let each variant be its own class.** Adding a variant means adding a class. The existing code that *uses* the abstraction never changes, because it doesn't know or care which implementation it gets. This works through **polymorphism**.

```
Before:  Client ──► [if type==A ... else if type==B ... else if type==C ...]
After:   Client ──► Interface ◄── A, B, C (add D later, nothing else changes)
```

## Example 1: Discount calculator

### ❌ Violation

```java
public class DiscountCalculator {
    public double calculate(String customerType, double amount) {
        if (customerType.equals("REGULAR")) {
            return amount * 0.95;
        } else if (customerType.equals("PREMIUM")) {
            return amount * 0.90;
        } else if (customerType.equals("VIP")) {
            return amount * 0.80;
        }
        return amount;
    }
}
```

The business says: *"Add a student discount."* You must **edit** `DiscountCalculator`, and retest REGULAR, PREMIUM, and VIP too.

### ✅ Fix

```java
public interface DiscountPolicy {
    double apply(double amount);
}

public class RegularDiscount implements DiscountPolicy {
    public double apply(double amount) { return amount * 0.95; }
}
public class PremiumDiscount implements DiscountPolicy {
    public double apply(double amount) { return amount * 0.90; }
}
public class VipDiscount implements DiscountPolicy {
    public double apply(double amount) { return amount * 0.80; }
}

public class DiscountCalculator {
    public double calculate(DiscountPolicy policy, double amount) {
        return policy.apply(amount);
    }
}
```

Now add the student discount:

```java
public class StudentDiscount implements DiscountPolicy {   // NEW file only
    public double apply(double amount) { return amount * 0.85; }
}
```

`DiscountCalculator`, `RegularDiscount`, `VipDiscount`, and every existing test are **untouched**. The system is *open* (new discount possible) and *closed* (old code not edited). This is the **Strategy pattern**.

## Example 2: Shapes and area (the classic)

### ❌ Violation

```java
class Circle    { double radius; }
class Rectangle { double width, height; }

public class AreaCalculator {
    public double area(Object shape) {
        if (shape instanceof Circle c) {
            return Math.PI * c.radius * c.radius;
        } else if (shape instanceof Rectangle r) {
            return r.width * r.height;
        }
        throw new IllegalArgumentException("Unknown shape");
    }
}
```

Add `Triangle`? Edit `AreaCalculator`. Add `Pentagon`? Edit it again.

### ✅ Fix

```java
public interface Shape {
    double area();
}

public class Circle implements Shape {
    private final double radius;
    public Circle(double radius) { this.radius = radius; }
    public double area() { return Math.PI * radius * radius; }
}

public class Rectangle implements Shape {
    private final double width, height;
    public Rectangle(double w, double h) { this.width = w; this.height = h; }
    public double area() { return width * height; }
}

public class AreaCalculator {
    public double totalArea(List<Shape> shapes) {
        return shapes.stream().mapToDouble(Shape::area).sum();
    }
}
```

```java
public class Triangle implements Shape {                  // NEW file only
    private final double base, height;
    public Triangle(double b, double h) { this.base = b; this.height = h; }
    public double area() { return 0.5 * base * height; }
}
```

`AreaCalculator` works with `Triangle` automatically, since it depends only on `Shape`.

**Key idea:** behavior moved *into* the type that owns it, so nobody outside needs to ask "what type are you?"

## Example 3: Payment processing (realistic backend)

### ❌ Violation

```java
public enum PaymentType { CREDIT_CARD, UPI, PAYPAL }

public class CheckoutService {
    public void checkout(PaymentType type, double amount) {
        switch (type) {
            case CREDIT_CARD -> System.out.println("Charging card: " + amount);
            case UPI         -> System.out.println("UPI payment: " + amount);
            case PAYPAL      -> System.out.println("PayPal payment: " + amount);
        }
    }
}
```

Adding `APPLE_PAY` means editing the enum **and** this switch **and** any other switch on `PaymentType` elsewhere in the codebase.

### ✅ Fix

```java
public interface PaymentProcessor {
    PaymentType type();
    void pay(double amount);
}

public class CardProcessor implements PaymentProcessor {
    public PaymentType type() { return PaymentType.CREDIT_CARD; }
    public void pay(double amount) { System.out.println("Charging card: " + amount); }
}
public class UpiProcessor implements PaymentProcessor {
    public PaymentType type() { return PaymentType.UPI; }
    public void pay(double amount) { System.out.println("UPI payment: " + amount); }
}

public class CheckoutService {
    private final Map<PaymentType, PaymentProcessor> processors;

    public CheckoutService(List<PaymentProcessor> processorList) {
        this.processors = processorList.stream()
            .collect(Collectors.toMap(PaymentProcessor::type, Function.identity()));
    }

    public void checkout(PaymentType type, double amount) {
        PaymentProcessor p = processors.get(type);
        if (p == null) throw new IllegalArgumentException("Unsupported: " + type);
        p.pay(amount);
    }
}
```

To add Apple Pay you create `ApplePayProcessor implements PaymentProcessor` (plus one new enum constant). In **Spring Boot**, mark each processor `@Component` and Spring injects the `List<PaymentProcessor>` automatically. `CheckoutService` is never edited.

> **Honest note (great for interviews):** a `switch` never disappears completely. It gets pushed to *one* place (the wiring/factory/DI container) instead of being scattered through business logic. That is the real win.

## Example 4: Extension by composition (Decorator)

Sometimes you want to add behavior (logging, retry, caching) to something that already works, without touching it.

```java
public interface MessageSender {
    void send(String to, String message);
}

public class EmailSender implements MessageSender {        // existing, tested, untouched
    public void send(String to, String message) {
        System.out.println("Email to " + to + ": " + message);
    }
}

// NEW behavior wrapped around the old one
public class RetryingSender implements MessageSender {
    private final MessageSender delegate;
    private final int maxAttempts;

    public RetryingSender(MessageSender delegate, int maxAttempts) {
        this.delegate = delegate;
        this.maxAttempts = maxAttempts;
    }

    public void send(String to, String message) {
        for (int attempt = 1; attempt <= maxAttempts; attempt++) {
            try {
                delegate.send(to, message);
                return;
            } catch (RuntimeException e) {
                if (attempt == maxAttempts) throw e;
            }
        }
    }
}

// Usage
MessageSender sender = new RetryingSender(new EmailSender(), 3);
```

`EmailSender` was extended with retry logic **without one line being modified**. Java's own `BufferedReader(new FileReader(...))` uses the same idea.

## Real examples in the JDK you already use

- `Collections.sort(list, comparator)` / `list.sort(...)`: sorting logic is closed; you extend it by passing a new `Comparator`.
- `Runnable`, `Callable`, `Predicate` in streams: `filter(...)` is closed, and behavior comes from the lambda you pass.
- JDBC: your code uses the `Connection` interface; new database drivers extend the system without changing your code.

## Techniques to achieve OCP

| Technique | Use when |
|---|---|
| **Strategy** (interface + implementations) | Swappable algorithms (discounts, payments) |
| **Decorator** (wrap same interface) | Adding behavior layers (logging, retry, cache) |
| **Template Method** (abstract base with hooks) | Fixed workflow, variable steps |
| **Factory / DI registry** (Map of implementations) | Choosing the implementation without a `switch` |

---

## Smells that signal an OCP violation

- `switch` / `if-else` on an enum, string, or type code
- `instanceof` chains
- The same `switch` duplicated in multiple classes
- A PR for "add new X" touching many existing files
- Fear of editing a class because "it might break something"

## Don't over-apply it (interviewers love this)

- **Don't abstract in advance.** If you have only one payment method and no signs of more, an interface is premature. Follow the **Rule of Three**: the first time, write it directly; the second time, notice the duplication; the third time, refactor to an abstraction.
- **You can't be closed against everything.** Choose which changes to protect against, based on what is *likely* to change. This is called **strategic closure**.
- A simple `switch` on a **stable, closed set** (days of the week, or a Java `sealed` type with exhaustive pattern matching) is perfectly fine.
- Too many interfaces with one implementation add indirection without value.

## Common misconceptions

| Myth | Truth |
|---|---|
| "Never edit a class ever" | Bug fixes and refactoring are fine. It's about not editing *to add new variants of behavior*. |
| "OCP means use inheritance" | Modern OCP favors **interfaces + composition**, not deep inheritance trees. |
| "Every class needs an interface" | Only where you have a real axis of variation. |
| "OCP = no `if` statements" | Ifs are fine. Type-based branching that grows with features is the problem. |

## How to explain OCP in an interview

**30-second answer:**

> "The Open/Closed Principle says classes should be open for extension but closed for modification: I should be able to add new behavior without editing existing, tested code. For example, if a `DiscountCalculator` uses an `if/else` chain on customer type, every new type forces me to modify and retest it. Instead I define a `DiscountPolicy` interface, implement each discount as its own class, and the calculator depends only on the interface. To add a student discount, I add one new class and touch nothing else. It reduces regression risk and merge conflicts. I'd apply it where I expect variation, not everywhere, to avoid over-engineering."

**Order to follow:** Definition → Violation (switch/if-else) → Fix (abstraction + polymorphism) → Benefits → Caveat (premature abstraction).

**Likely follow-ups:**

1. **"How do you achieve OCP in Java?"** Interfaces/abstract classes and polymorphism, with patterns like Strategy, Decorator, and Template Method, and dependency injection to wire the implementations.
2. **"Doesn't the switch just move somewhere else?"** Yes, to one composition point (factory or DI container) rather than spread through business logic.
3. **"Which design patterns rely on OCP?"** Strategy, Decorator, Observer, Factory, and Template Method.
4. **"Give a real example."** Spring's `List<PaymentProcessor>` injection, or `Comparator` in `Collections.sort`.
5. **"When would you NOT apply it?"** When there's no realistic variation, or the set is stable and small.
6. **"How does OCP relate to SRP?"** SRP gives each class one reason to change, which makes classes small enough to be extended cleanly. Splitting `Invoice` from `InvoicePrinter` in Lesson 1 is what makes adding a `PdfInvoicePrinter` possible without touching `Invoice`.
