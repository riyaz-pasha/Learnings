---

## What it says

> **"Clients should not be forced to depend on methods they do not use."** (Robert C. Martin)

Instead of one big "fat" interface, create several small, focused interfaces (often called **role interfaces**), so each client only sees the methods it actually needs.

Think of a restaurant menu. A customer who wants only a drink shouldn't have to read, or be responsible for, a 40-page kitchen manual.

---

## 1. Why do we need it? (The problem)

When an interface is too big:

1. **Forced empty or throwing implementations:** a class must implement methods that make no sense for it, so you write `throw new UnsupportedOperationException()` (an LSP violation from Lesson 3).
2. **Unwanted coupling:** if the interface changes because of method X, every implementer and client is affected, even those that never use X.
3. **Recompilation and redeployment:** changing one unused method forces changes across many modules.
4. **Hard testing:** a mock or fake must implement 15 methods when the test needs 1.
5. **Unclear intent:** a signature like `process(BigInterface x)` doesn't tell you what the method really needs.

## 2. When do we need it?

- When implementers leave methods **empty** or **throw exceptions**.
- When different clients use **different subsets** of an interface's methods.
- When an interface keeps **growing** with each new feature.
- When you're writing an interface for **multiple kinds of users** (admin vs. customer, reader vs. writer).
- When mocking an interface in tests is painful.

## 3. How does it solve the problem?

**Split by client need (role), not by implementer.** Each small interface represents one role. A class that plays multiple roles implements multiple interfaces. Each client depends only on the role it uses.

```
Before:  Client A ─┐
         Client B ─┼──► FatInterface (10 methods) ◄── every implementer must do all 10
         Client C ─┘

After:   Client A ──► RoleA  ─┐
         Client B ──► RoleB  ─┼── implemented by classes that pick only the roles they support
         Client C ──► RoleC  ─┘
```

## Example 1: `Worker` and `Robot` (the classic)

### ❌ Violation

```java
public interface Worker {
    void work();
    void eat();
    void sleep();
}

public class Human implements Worker {
    public void work()  { System.out.println("Human working"); }
    public void eat()   { System.out.println("Human eating"); }
    public void sleep() { System.out.println("Human sleeping"); }
}

public class Robot implements Worker {
    public void work()  { System.out.println("Robot working"); }
    public void eat()   { throw new UnsupportedOperationException(); }  // 💥
    public void sleep() { /* does nothing */ }                          // 💥
}
```

A lunch-break scheduler calling `worker.eat()` on every `Worker` will crash on a `Robot`.

### ✅ Fix

```java
public interface Workable { void work(); }
public interface Eatable  { void eat(); }
public interface Sleepable { void sleep(); }

public class Human implements Workable, Eatable, Sleepable {
    public void work()  { System.out.println("Human working"); }
    public void eat()   { System.out.println("Human eating"); }
    public void sleep() { System.out.println("Human sleeping"); }
}

public class Robot implements Workable {
    public void work() { System.out.println("Robot working"); }
}
```

```java
static void lunchBreak(List<Eatable> eaters) {
    eaters.forEach(Eatable::eat);      // a Robot can't even be passed in
}
```

`Robot` no longer carries methods it can't honor, and the lunch scheduler's parameter type says exactly what it needs.

## Example 2: Multifunction printer

### ❌ Violation

```java
public interface MultiFunctionDevice {
    void print(Document d);
    void scan(Document d);
    void fax(Document d);
    void staple(Document d);
}

public class OldPrinter implements MultiFunctionDevice {
    public void print(Document d) { System.out.println("Printing"); }
    public void scan(Document d)  { throw new UnsupportedOperationException(); }
    public void fax(Document d)   { throw new UnsupportedOperationException(); }
    public void staple(Document d){ throw new UnsupportedOperationException(); }
}
```

### ✅ Fix

```java
public interface Printer { void print(Document d); }
public interface Scanner { void scan(Document d); }
public interface Fax     { void fax(Document d); }

public class SimplePrinter implements Printer {
    public void print(Document d) { System.out.println("Printing"); }
}

public class AllInOneMachine implements Printer, Scanner, Fax {
    public void print(Document d) { System.out.println("Printing"); }
    public void scan(Document d)  { System.out.println("Scanning"); }
    public void fax(Document d)   { System.out.println("Faxing"); }
}
```

**Bonus:** if you still want a convenient "all-in-one" type, compose it from the small ones:

```java
public interface MultiFunctionDevice extends Printer, Scanner, Fax { }
```

Small interfaces come first, and big ones are built from them, never the reverse.

## Example 3: Repository, read vs. write (realistic backend)

### ❌ Violation

```java
public interface UserRepository {
    User findById(long id);
    List<User> findAll();
    void save(User user);
    void delete(long id);
    void bulkImport(List<User> users);
}

// A reporting module only needs to READ, yet:
public class ReportService {
    private final UserRepository repo;   // it can also delete users! Dangerous.
    public ReportService(UserRepository repo) { this.repo = repo; }
}
```

Problems: `ReportService` has the power to delete data it should never touch, and a test fake must implement 5 methods when the service uses 2.

### ✅ Fix

```java
public interface UserReader {
    User findById(long id);
    List<User> findAll();
}

public interface UserWriter {
    void save(User user);
    void delete(long id);
}

public class JdbcUserRepository implements UserReader, UserWriter {
    public User findById(long id)       { /* ... */ return null; }
    public List<User> findAll()         { /* ... */ return List.of(); }
    public void save(User user)         { /* ... */ }
    public void delete(long id)         { /* ... */ }
}

public class ReportService {
    private final UserReader reader;     // read-only by construction
    public ReportService(UserReader reader) { this.reader = reader; }
}
```

Now `ReportService` **cannot** delete users, since the type system prevents it. Testing needs only a 2-method fake, and this is also the seed of the CQRS (read/write separation) idea.

## Example 4: Different clients, different views (admin vs. customer)

### ❌ Violation

```java
public interface OrderService {
    Order placeOrder(Cart cart);          // customer
    void cancelMyOrder(long orderId);     // customer
    void refund(long orderId);            // admin
    void exportAllOrders();               // admin
    void changeOrderStatus(long id, String status);  // warehouse
}
```

The customer-facing controller depends on `refund` and `exportAllOrders`, and could call them by mistake.

### ✅ Fix

```java
public interface CustomerOrders {
    Order placeOrder(Cart cart);
    void cancelMyOrder(long orderId);
}
public interface AdminOrders {
    void refund(long orderId);
    void exportAllOrders();
}
public interface WarehouseOrders {
    void changeOrderStatus(long id, String status);
}

@Service
public class OrderServiceImpl implements CustomerOrders, AdminOrders, WarehouseOrders {
    // one implementation, three narrow views
}
```

Each controller injects only the interface it needs:

```java
@RestController
class CustomerOrderController {
    private final CustomerOrders orders;   // can't see refund()
    CustomerOrderController(CustomerOrders orders) { this.orders = orders; }
}
```

**Key point:** ISP does **not** require one implementation class per interface. One class can implement many role interfaces. The split is on the **client side view**.

## Example 5: ISP inside the JDK (great for interviews)

**Good examples (ISP followed):**

- `Runnable` (`run`), `Callable` (`call`), `Comparable` (`compareTo`), `Comparator` (`compare`), `Supplier`, `Predicate`: tiny single-purpose interfaces. This is *why lambdas work so well in Java*.
- `AutoCloseable` / `Closeable`: only `close()`, so try-with-resources works with anything.
- `Iterable` (just `iterator()`) is separate from `Collection`, so anything can be used in a for-each loop.
- `RandomAccess` is a marker interface, so algorithms can check whether index-based access is fast.

**Bad or compromised examples:**

- `java.util.List` includes mutating methods (`add`, `remove`), so read-only lists (`List.of()`, `Collections.unmodifiableList`) must throw `UnsupportedOperationException` (the same LSP compromise from Lesson 3, caused by a fat interface).
- `MouseListener` (AWT/Swing) has 5 methods (`mouseClicked`, `mousePressed`, ...). Most clients care about one, so the JDK added the workaround class `MouseAdapter` with empty implementations. That's a symptom of a fat interface being patched.

## Java-specific twist: `default` methods are not a cure

Java 8 `default` methods let you add methods to an interface without breaking implementers.

```java
public interface Worker {
    void work();
    default void eat() { }     // "solves" the Robot problem?
}
```

This **hides** the smell instead of fixing it. `Robot` now silently "eats" nothing, and clients still depend on a method they don't need. Use `default` for **backward-compatible evolution** of a published API (like `List.sort` or `Iterable.forEach`) and for genuinely sensible defaults, not to dodge splitting a fat interface.

## Smells that signal an ISP violation

- Implementations with **empty methods** or **`throw new UnsupportedOperationException()`**
- Interface names like `IManager`, `IService`, `IEverything` with 10+ methods
- Interface methods that are unrelated (`print`, `login`, `calculateTax`)
- A client using **only a few methods** of the interface it receives
- Test mocks/fakes with many stubbed, irrelevant methods
- Adding a method to an interface forces edits in classes that don't care
- Existence of `*Adapter` classes with only empty bodies

## Don't over-apply it (interviewers love this)

- **Don't create one interface per method** by reflex. That's "interface explosion", and it makes navigation painful.
- Group methods that are **always used together** by the same clients. Split when *different clients use different subsets*.
- A cohesive interface with 6 related methods is fine. Judge by **client usage**, not by method count alone.
- Start with a reasonable interface, and split when a real second client with different needs appears.
- Avoid creating interfaces that have exactly one implementation and one client with no expected variation.

## Common misconceptions

| Myth | Truth |
|---|---|
| "Every interface should have one method" | Only when clients need them separately. Cohesive groups are fine. |
| "ISP is about classes being small" | ISP is about **interfaces** and what **clients** depend on. |
| "One class = one interface" | A class can implement many role interfaces. |
| "ISP = SRP" | Related but different (see below). |
| "`default` methods solve ISP" | They hide the problem and can mask design errors. |

---

## ISP vs. the other principles

| Pair | Relationship |
|---|---|
| **ISP vs SRP** | SRP: a *class* should have one reason to change (one actor). ISP: a *client* should depend only on the methods it uses. SRP is about the implementer, ISP about the consumer's view. |
| **ISP vs LSP** | Fat interfaces force `UnsupportedOperationException`, which breaks LSP. ISP is often the *fix* for an LSP violation (as in `Bird`/`Flyable` and `Withdrawable` from Lesson 3). |
| **ISP vs OCP** | Small stable interfaces are easier to extend by adding new implementations, and adding a method to a fat interface *modifies* every implementer. |
| **ISP vs DIP** (next lesson) | DIP says depend on abstractions. ISP says make those abstractions small and client-shaped. |

## How to explain ISP in an interview

**30-second answer:**

> "The Interface Segregation Principle says clients shouldn't be forced to depend on methods they don't use. Instead of one fat interface, I create small role-based interfaces. For example, a `Worker` interface with `work()`, `eat()`, and `sleep()` forces a `Robot` to implement `eat()` with an exception or empty body, which also violates Liskov. I split it into `Workable`, `Eatable`, and `Sleepable`, so `Human` implements all three and `Robot` only `Workable`. In backend code, I'd split a repository into `UserReader` and `UserWriter`, so a reporting service physically can't delete data, and tests only need small fakes. The JDK follows this with `Runnable`, `Comparable`, and `AutoCloseable`. I'd avoid overdoing it: split based on how different clients actually use the interface, not one interface per method."

**Order to follow:** Definition → Problem (fat interface, forced empty methods) → Fix (role interfaces) → Real backend example (reader/writer) → JDK examples → Caveat (interface explosion).

**Likely follow-ups:**

1. **"How is ISP different from SRP?"** SRP concerns the reasons a class changes. ISP concerns what a client is forced to depend on. Different lens, and both push toward small, focused units.
2. **"How does ISP relate to LSP?"** Fat interfaces cause subclasses to throw `UnsupportedOperationException`, which breaks substitutability. Splitting interfaces restores LSP.
3. **"Can a class implement multiple interfaces in Java?"** Yes, that's what makes ISP practical in Java, unlike with single class inheritance.
4. **"Do default methods violate ISP?"** They can be used to hide a violation. Fine for API evolution, wrong as a shortcut to avoid splitting.
5. **"Give a real example from the JDK or Spring."** `Runnable`/`Callable`; `List` as a counter-example. In Spring Data, `CrudRepository` vs `PagingAndSortingRepository` vs `ListCrudRepository` (you choose the capability level you need), or a repository that extends only `Repository<T, ID>` and declares just the methods you want.
6. **"How do you decide whether to split?"** Look at clients: if different clients use different subsets, or implementers leave methods empty, split.
7. **"Isn't this too many interfaces?"** It can be, so split on real client differences and compose bigger interfaces from smaller ones when a convenient union is useful.
8. **"How does ISP help testing?"** Smaller interfaces are easier to fake or mock, so tests are shorter and less brittle.
